## 判据

1. 采用 Owner 最新边界：反馈修改并保留到后续任务/轮次的 Harness 提示、工具代码/库、技能文件、上下文/记忆管理机制、控制流、环内验证器或改进器；权重不是主要训练对象。
2. 只积累记忆条目、经验数据或检索状态不自动属于 Harness；先标 experience_world_model 或边界待核，必须另见管理策略/机制或可执行技能的修改证据。
3. 模型策略训练、训练环境/奖励/用户模拟器、外部任务产物与静态框架不自动计作 Harness；混合方法只将有证据的 Harness 子路径作为相关路线。
4. 优化任务 Harness、训练编辑器、改变编辑策略与递归自写元程序是不同机制；固定外层不否定内层更新，具身或科研应用也不决定改进对象。
5. 奠基、评测、理论、综述可以合理引用；它们的书目数量不等于主方法数量。
6. 分类基于现有目录和选定公开摘要，不验证效果数字、不补写证据 yes/no；全部仍需全文核验，机制不清一律保留待确认。

## 系统性问题

- 98是主题书目总数，不能当作98个纯Harness RSI主方法；36条位于奠基/评测/综述栏目，13条在模型协同栏目，另49条位于五个Harness方法栏目。奠基栏目本身也含DGM、ADAS等真方法，故36不是“无关论文数”。 建议：保留总数并直接显示角色拆分；另统计经边界核对的方法条目，不用98代替。
- Harness-R1、Harness Learning TTA确是学习型Harness优化方法，但公开摘要说的是训练proposer/engineer权重。improver栏目“改进器自身进化”容易被读成递归重写改进器程序；Meta^n又明确固定元操作Ω。 建议：在improver内区分训练型编辑器、固定元操作递归层级、持久编辑策略更新和可自改元程序。
- EvoHarness-RL展示离线策略学习与运行时BPE状态更新；HELIX只验证一轮Harness演化并构造后续训练数据；MetaRSI显式融合Data/Harness/Model。它们不能统一包装成已验证的纯Harness递归共进化。 建议：分别标训练+运行时状态、单轮原型、跨对象复合；需全文核查的持续性和轮数不得补写。
- 此前广义 Harness 口径把跨任务外部记忆本身算组件演化；这与 Owner 最新判据不一致。Living-Harness、ACE、RecuRIS 改为经验/机制待核，PILOT 与 ContextEvo 单列技能表示或策略表示待核。 建议：在审计中明确收紧判据；原 papers.yaml 不改。未读正文前，不把这些边界项算作确认的纯 Harness RSI。
- memory/skills 同时见于 Harness 与 experience_world_model，需用实际修改对象区分。Owner 已明确排除只累积记忆/经验；AIDE² 则要区分 Agent 运行机制与外部研究产物，EMHO/SHAPER 的具身场景本身不构成排除。 建议：先标改进对象；只有技能指令/代码、控制或记忆管理机制被反馈修订并保留才计 Harness。应用/元层及共同更新对象另加标签。
- AlphaEvolve明确不改Harness；Gödel Machines是一般理论；Harness Engineering: Anatomy是结构定义；EVOHARNESSBENCH主要研究外部Harness变化下的适应。它们可作为背景或评测保留，不能算成自进化主方法。 建议：保留角色标签，不以全部条目共享的Harness页面标题代替条目类型。
- HARBOR 有真实配置优化；EMHO/SHAPER 冻结模型并修改外部 Harness。固定工具、固定元 Agent 或具身环境不是排除证据；Living-Harness 虽有持久状态，却仍需区分经验条目与实际控制机制。 建议：不要求所有 Harness 方法都改源码，但必须存在指令、技能、配置或管理/控制机制更新；仅累积状态不够。
- 各directions页面的整体解读仍为TODO；大多数条目只有目录摘要，未记录边界出处。现有needs_reading仅13条，不能使其余条目被误读为已全文审定。 建议：为对象、角色、参数更新、持久性和改进器更新方式分别记录来源；不修改现有证据值以假装完成审读。
