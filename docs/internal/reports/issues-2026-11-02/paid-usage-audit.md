| 位置 | 文件数 | 与主缓存关系 |

三份续跑准备目录共有 **10,989 份完全相同的复制文件**，没有证据表明这些复制动作产生模型请求。不能把目录文件数直接累加算消费。

另一方面，[45 例评测输入清单](../maintenance-2026-10-30/harness-gate-eval/input-manifest.json)明确记录 `fresh_cache: true`。这次独立评测生成 **123 个成功结果**：45 次相关性结果、42 次分类结果、36 次 Harness 闸门结果；模型分别为 Flash **87**、V4 Pro **36**。其 85 个请求键虽然在主缓存也存在，但两个目录的答案确实不同。这是有证据的重新请求，增加了全量积压以外的模型工作量；没有记录它对应的人民币金额。

## 为什么现在无法核账

原 `FeedLLM.run` 只保存答案、模型、提示词哈希和格式重试次数，**丢弃了 SDK 返回的 usage**。在主缓存与隔离缓存中都没有历史 token 或费用字段；另外检查的 1,596 份执行日志和报告中也未找到 token 用量记录。

`model-processing-network-resumed.log` 有一个明确 HTTP 402 的请求 ID；同一异常在 traceback 中出现两次，不能算两次失败请求。历史报告还记录过前一次余额不足，但不能因此把所有 `APIStatusError` 都当作 402，或假设失败请求全部收费或全部免费。

同一请求可以命中缓存；提示词版本、论文版本、模型或修正反馈改变则可能产生新请求。现存数据确有多版提示词结果和格式重试，但缺少逐次请求流水，不能精确拆分每一类的消费占比。文件复制也改变了大量缓存的修改时间，**不能把 11 月 2 日的文件时间当成当日扣费**。10 月 31 日和 11 月 1 日的维护报告记载付费处理保持暂停；这些报告并非平台账单，也不能用累计缓存反推“昨天花了多少”。

## 已补的最小修复

只修改 `scripts/feed/llm.py` 和 `tests/feed/test_llm.py`，后续每次真实 SDK 尝试追加一行到 **`data/feed/usage.jsonl`**：

- 记录 UTC 时间、阶段、模型、provider、条目 ID、缓存键、从 1 开始的尝试序号，以及 SDK 的 `usage`、请求 ID、响应 ID。
- 在 JSON/schema 检验之前记录返回，所以格式失败后重试的两次请求各有一笔；缓存命中不新增记录。
- SDK 没有返回用量时写 `null`，不猜金额；异常只记类型与 HTTP 状态，不写异常正文、密钥、base URL、完整提示词或模型正文。
- HTTP 402 留下一笔失败回执后继续立即终止；并发线程的日志追加由锁保护。

这项修复只能记录未来调用，无法补回历史账单。没有改模型、采样、质量阈值、输出 token 限制，也没有重跑付费评测。

离线验证命令：

```text
.venv/bin/python -m pytest -q tests/feed/test_llm.py tests/feed/test_judge.py tests/feed/test_cli.py
```

结果：**64 passed，5.29 秒**；`git diff --check` 通过。测试覆盖真实 SDK 形状的 usage、usage 缺失、缓存不重复记账、schema 两次失败都记录、并发追加、网络异常脱敏及 402 单次停止。全部使用本地 fake transport，测试没有在实际数据目录创建用量日志。

核对历史费用需要对应时段的 provider 账单或用量导出，至少包含时间、模型、输入/输出及缓存 token 分类和费用。本报告仅说明可核验的工作量来源，历史费用和 token 总量仍为 unknown。
