Code: https://github.com/junnie00/TTHE Abstract The behavior of an LLM agent is determined not only by the underlying model, but also by its harness : the executable program that constructs context, invokes tools, verifies intermediate results, and recovers from failures. Existing approaches typically optimize harnesses on training or development data and freeze the resulting programs at test time, limiting adaptation to shifts in task distributions, failure modes, and tool interactions. We ask whether the harness can instead be optimized during evaluation using unlabeled execution traces. We introduce Test-Time Harness Evolution (TTHE), which treats the executable harness as the state of test-time adaptation. On each unlabeled test batch, TTHE iteratively evolves a population of candidate harnesses through agentic proposers that reason over execution traces and explore diverse edit directions. A judge selects a candidate using execution traces and execution-derived proxy signals. The selected harness determines the current batch’s outputs and initializes adaptation on the next. Crucially, the solver, proposers, and judge operate through different harnesses around the same frozen LLM, without weight updates, access to final-answer labels, or a separately trained adaptation model. Across six execution-grounded benchmarks spanning text-to-SQL, competitive programming, software engineering, data-science coding, terminal-based tasks, and agentic tool use, TTHE improves fixed ReAct-style baseline harnesses through persistent, inspectable program adaptation. These results recast test-time adaptation for LLM agents as evolution over executable control programs and identify execution-derived proxy reliability as a central challenge for robust unsupervised agent improvement. 1 Introduction Modern LLM agents are increasingly built as executable systems rather than single-call predictors.
Their behavior depends not only on the model, but also on the executable harness around
it—the control program that constructs context, invokes tools, verifies intermediate results,
and implements recovery strategies. Following prior work on model and agent
harnesses ( Lee et al., 2026 ; Zhang et al., 2026a ) , we focus on this program as the object
of adaptation. Its context construction and control flow determine how the model’s capabilities
are used. A common development workflow, however, is to inspect failures, adjust prompts and
control flow, and tune tool-use logic before evaluating the resulting harness as a fixed artifact.
Its operating procedure then remains unchanged even when the target workload exposes different
requirements or failure modes. This convention treats evaluation as a scoring stage, even though execution itself produces rich
operational evidence. Every attempted task leaves an execution trace: model calls, tool actions,
intermediate outputs, database responses, test results, runtime errors, and recovery decisions.
Such traces can reveal not only whether an execution satisfies available checks, but also how
its operating procedure might be improved. A text-to-SQL agent may retrieve the correct table
but apply an inconsistent value normalization; a coding agent may generate plausible patches
without verifying them before submission; a data-science agent may compute an intermediate
result but omit it from the final report. This is precisely the kind of evidence a human harness engineer would inspect when
revising the scaffold. Crucially, this evidence is available during evaluation without
access to gold labels. Using this evidence to revise the harness, however, is different from using it to
refine individual responses. Self-debugging and reflection use feedback to revise
candidate answers or retain textual experience for later
attempts ( Chen et al., 2024 ; Shinn et al., 2023 ) . Automated prompt and workflow
search targets the surrounding task-solving procedure, but typically optimizes it
against a training or development objective before evaluating the resulting workflow
as a fixed artifact ( Khattab et al., 2023 ; Hu et al., 2025 ; Zhang et al., 2025b ) . More recent
work revises agent source code, harnesses, and configurations using execution feedback
or task-level evaluation
signals ( Cai et al., 2026a ; Lee et al., 2026 ; Zhang et al., 2026a ; He et al., 2025 ) .
Building on these lines of work, we ask: can an LLM agent adapt its harness at test time using its own execution traces,
without final correctness feedback? We propose Test-Time Harness Evolution (TTHE), which treats the executable harness as
the state of test-time adaptation. Rather than searching for a harness on labeled development
instances and freezing it for evaluation, TTHE moves harness optimization into the evaluation
process itself. On each unlabeled test batch, TTHE executes a population of candidate harnesses
and iteratively refines them through trace-guided proposers that explore diverse edit directions.
A judge selects one candidate using the traces and execution-derived proxy signals; the selected
harness determines the current batch’s outputs and initializes adaptation on the next.
Final correctness feedback is used only for post-selection evaluation. The solver, proposers, and judge use the same frozen LLM in
different roles, so adaptation changes the executable program rather than model weights and
requires no separately trained adaptation model. This evaluation-time formulation offers two practical advantages. First, it adapts at the point
where the relevant evidence appears: after the agent encounters the schemas, repositories,
tests, tools, and runtime constraints of the target workload. It can therefore use task-specific
execution evidence without requiring an additional labeled development set tailored to that
workload. Second, updating an executable program requires no gradient access and permits
explicit changes to context construction, multi-sample generation, tool-mediated grounding,
deterministic contract checks, and conditional recovery branches. These changes alter the
procedure used to solve tasks rather than only revising an individual response. A central challenge, however, is that execution evidence is not a correctness oracle. A query
can execute successfully while answering the wrong question; code can pass visible tests while
failing hidden ones. TTHE therefore presents proxy signals together with candidate code and
the underlying execution traces, allowing proposers and the judge to interpret these signals
in the context of how an outcome was produced rather than relying on a single surrogate score.
Because an edit intended to repair a failure can also disrupt previously correct behavior,
we complement this design with a conditional analysis of a class of trace-triggered harness
edits, characterizing when corrective gains outweigh unintended regressions. We evaluate TTHE on six execution-grounded benchmarks, where it
improves fixed ReAct-style baselines and yields inspectable grounding, verification, and recovery
policies. On the evaluated BIRD dataset, TTHE achieves 48.7 % 48.7\% mean execution
accuracy over three runs, compared with 12.7 % 12.7\% for the fixed baseline. A separate ten-run
execution-result consistency-voting control achieves 16.0 % 16.0\% . Harnesses selected by DeepSeek for each BIRD batch
also improve MiMo V2.5 and GPT-5.5 over their respective fixed-harness baselines on the
corresponding batches, without further harness evolution. These results provide evidence of
cross-model transfer of the evolved task-solving procedures. Search diagnostics reveal
non-monotonic effects of search budget and distinguish candidate-availability limitations from
selection errors. Together, these findings support executable harness adaptation as a practical
path to test-time self-evolution in LLM agents. Contributions. • We introduce Test-Time Harness Evolution (TTHE) , a framework that
recasts test-time adaptation as evolution over executable control programs.
TTHE enables an LLM agent to transform its own execution experience into
harness updates, without modifying model weights or accessing final
correctness feedback. • We demonstrate gains on evaluated tasks across six execution-grounded benchmarks,
compare TTHE with fixed-harness repeated sampling on BIRD, and show that batch-specific
evolved harnesses can benefit other execution models on the corresponding tasks. • We present inspectable harness examples, provide a conditional analysis of corrective
gains and unintended regressions for a class of trace-triggered edits, and use search

Two questions guide its design: (Q1) What evidence can support adaptation without final
correctness feedback? (Q2) How can this evidence guide program revision and candidate
selection? We address Q1 with execution traces and task-dependent partial checks, and Q2 with
iterative evolution of multiple harness branches followed by batch-level selection.

logic. TTHE revises how the harness constructs context, invokes tools, validates intermediate
results, and recovers from failures, while keeping the model and the outer proposal-and-selection
procedure fixed. The baseline H 0 H_{0} is a ReAct-style scaffold ( Yao et al., 2023 ) , fixed before
evolution begins. A code edit can change a prompt, introduce a database probe before generation, add a deterministic
output check, or create a conditional repair branch. It can also implement multiple-sample generation
and aggregation ( Wang et al., 2023 ) or execution-based self-debugging ( Chen et al., 2024 ) .
The search is therefore not confined to choosing among predeclared prompt templates or workflow settings.
The distinction from response-level refinement is the object of the update: a revised query is an output,
whereas a new rule for constructing and checking queries changes the procedure applied to the batch. 3.3 Execution Evidence Executing a candidate records its model prompts and completions, tool calls and responses, stdout/stderr,
intermediate artifacts, runtime states, errors, and probe results; long fields are truncated. A trace
exposes how a harness operates: which tools it calls, whether intermediate artifacts are consumed,
when validation or recovery branches fire, and how the final output relates to the preceding computation.
These details provide context for diagnosing a failure and proposing changes to the operating procedure.
For an input x x and outcome o o , TTHE also exposes task-dependent proxy signals: • Execution health s ∈ { 0 , 1 } s\in\{0,1\} records whether the output executes and satisfies available
format or shape checks, such as returning a scalar for a counting query. • Round-trip consistency b ∈ [ 0 , 1 ] b\in[0,1] compares the input to a description reconstructed from
the output: x ~ = RT ⁡ ( o ) \widetilde{x}=\operatorname{RT}(o) and b = match ⁡ ( x , x ~ ) b=\operatorname{match}(x,\widetilde{x}) . A mismatch
provides evidence of possible semantic drift without requiring a reference answer. • Public-test pass rate p ∈ [ 0 , 1 ] p\in[0,1] records the fraction of exposed examples or repository
tests passed, where such tests are available. These signals provide complementary but incomplete evidence: successful execution does not establish
semantic correctness, and different candidates may agree on an incorrect result. TTHE therefore
presents the signals together with candidate code and the underlying execution traces, rather than
aggregating them into a single scalar objective. Proposers use this evidence to diagnose weaknesses
and propose program changes, while the judge uses it to compare the resulting candidates. 3.4 Evolution and Selection Let H r g H_{r}^{g} denote branch g g after round r r , with H 0 g = H t H_{0}^{g}=H_{t} for all g g .

evidence, directing repairs, and coordinating tool use. On BIRD, an evolved
harness probes database values before SQL generation, grounds filter values
in their stored casing, and infers the required output shape from the question.
Structural violations, execution errors, and output-shape mismatches are
returned as targeted feedback for subsequent attempts
(Figure 4 ). Generation is therefore coupled with
explicit checks and failure-specific revision, rather than repeated without
diagnosing the preceding attempt. On SWE-bench, an evolved harness adopts a reproduce-first workflow with
root-cause localization, post-edit verification, and execution of existing
tests, alongside an increased step budget. It also adds a recovery branch
triggered when the initial rollout returns an empty patch. This branch
supplies concrete starter commands and a reproduction template, turning
the absence of a usable artifact into an explicit condition for changing
the execution strategy (Figure 5 ). The harness thus
addresses not only how to verify a patch, but also how to resume execution
when the agent fails to produce one. On LiveCodeBench, an evolved policy
uses a low-cost path by default and escalates to additional verification
and repair after a public-test failure. In claw-eval, the evolved instructions address how information and actions
are linked across services. They specify single-line tool payloads, service
chaining through exact identifiers rather than display names, and a
pre-delivery completeness check requiring citations of retrieved record
identifiers. They also require reported actions to be supported by executed
tool calls. Across these examples, evolution changes
what evidence the agent obtains before acting, which observations trigger
revision, and how execution proceeds after failure. Execution experience
is incorporated into the rules governing task solving, rather than used
only to correct an individual answer. 6 Limitations TTHE demonstrates the potential of harness self-evolution without final
task-correctness supervision. However, the feedback guiding evolution
remains limited by the informativeness of execution traces and partial
checks. Successful execution or agreement among candidates can coexist
with semantic errors, making it difficult to distinguish effective
program improvements from changes that merely satisfy available proxies.
Our diagnostics show that useful candidates can already exist in the
search pool yet remain unselected. This highlights a central challenge:
an agent must draw on its own experience both to identify promising
changes and to assess whether those changes constitute genuine progress.
Developing principled mechanisms for extracting more informative feedback,
guiding program exploration, and selecting beneficial updates while
preserving useful behavior remains an important direction for advancing
reliable unsupervised agent self-evolution. 7 Conclusion TTHE turns test-time execution experience into updates to an agent’s executable
harness, without changing model weights or accessing final correctness feedback
during adaptation. Across six execution-grounded benchmarks, it improves over
fixed baseline harnesses on the evaluated task sets and produces inspectable
grounding, verification, and recovery policies. Transfer experiments further
show that batch-specific evolved harnesses can benefit other execution models
on the corresponding tasks. Our conditional analysis characterizes the balance
between corrective gains and unintended regressions for trace-triggered edits,
while search diagnostics show that generating useful candidates does not ensure
that they are selected. Together, these findings support executable harness
adaptation as a practical path to test-time self-evolution, with reliable

class EvolvedSQLHarness(SQLHarness):
  def solve(self, question):
    # (1) ground filter values vs the DB (exact casing)
    grounding = self.ground_values(question)
    # (2) infer expected output shape (#cols, 1 vs many)
    shape = self.explain_shape(question)
    # (3) generate -> validate -> run -> self-debug (<=6x)
    err = ""
    for _ in range(6):
      sql = extract_sql(self.llm(
          self.prompt(question, grounding, shape, err),
          system=RULES))
      if (msg := self.validate_structure(sql, question)):
          err = msg; continue        # e.g. SELECT *
      res = self.execute(sql)
      if not res["ok"]:
          err = "SQL error: " + res["error"]; continue
      if not res["rows"]:
          err = "0 rows -- recheck WHERE casing"; continue
      if (msg := self.check_columns(question, res)):
          err = msg; continue        # wrong / extra columns
      return self.fix_shape(question, sql, res)
    return sql Figure 4: Source of an evolved Text-to-SQL harness (excerpt, lightly abridged), discovered from label-free

baseline. The grader is disabled during in-loop observation, so no task score or
rubric target enters the proposer or judge; gold grading is applied only to the
committed harness for measurement. The baseline and TTHE scores, 48.9 % 48.9\% and 69.4 % 69.4\% ,
are each averaged over three runs (Appendix H ). The tasks are ordered by ascending baseline difficulty, so this evaluation does not
isolate the effect of cross-batch accumulation. C.2 Discovered policies From label-free traces alone the
accumulated harness adds four general rules to the baseline: single-line tool payloads for reliable
action capture; citation of every retrieved record identifier under a completeness checklist before
delivery; chaining services by exact identifier (email or ID) rather than display name; and grounding
every reported action in an executed tool call. Appendix D Related Work Prompt and workflow optimization. Research on optimizing the system around a language model spans instructions,
workflows, and executable programs. APE and OPRO search for
instructions [ Zhou et al., 2023 , Yang et al., 2024a ] , while Promptbreeder and EvoPrompt
use evolutionary prompt optimization [ Fernando et al., 2024 , Guo et al., 2024 ] .
DSPy optimizes declarative language-model pipelines against a
metric [ Khattab et al., 2023 ] ; ADAS and AFlow extend the search to agent designs
and code-represented workflows [ Hu et al., 2025 , Zhang et al., 2025b ] . FunSearch
illustrates the broader potential of executable program
search [ Romera-Paredes et al., 2024 ] . More recently, GEPA uses natural-language
reflection on reasoning and tool-use trajectories to propose prompt updates and
combine complementary improvements from a Pareto frontier [ Agrawal et al., 2026 ] .
Thus, interpreting execution traces is already an important optimization mechanism;
TTHE studies its use for revising and selecting an executable harness on the
current test batch without final task-correctness feedback. Executable harness evolution. A related line modifies agent source code or accumulates executable components.
STOP and the Darwin Gödel Machine revise agent
scaffolds [ Zelikman et al., 2023 , Zhang et al., 2025a ] , Voyager builds a reusable skill
library [ Wang et al., 2024 ] , and MOSS studies source-level rewriting from
failure trajectories [ Cai et al., 2026a ] . Among harness-level methods, Self-Harness
validates edits through verifier-grounded evaluation and regression tests with a
fixed model [ Zhang et al., 2026a ] ; Meta-Harness gives its proposer access
to historical code, scores, and traces from a search set before held-out
evaluation [ Lee et al., 2026 ] . HarnessX provides composable harness
primitives and a trace-driven multi-agent evolution engine, with both
harness-only adaptation and a harness–model co-evolution loop that reuses
trajectories for model training [ Chen et al., 2026 ] . HASE unifies task-solution
generation and harness editing in an agentic reinforcement-learning process,
co-evolving model weights, harness components, and
solutions [ Luo et al., 2026 ] . TTHE shares the executable-program optimization
target but keeps the solver, proposers, and judge frozen, and excludes final
correctness feedback from both current-batch program revision and commitment. Transfer and reliable adoption. Beyond aggregate performance, recent work examines what evolved harnesses retain
and when their updates can be trusted. One Recipe, Many Harnesses analyzes
artifacts produced by a common evolution recipe across languages and models,
distinguishing transferable strategies from ecosystem-specific
adaptations [ Yang et al., 2026 ] . A theory of reliable harness self-evolution
studies adoption conditions that balance gains on failed tasks against preservation
of successful behavior, together with the limits imposed by verification and
evaluation costs [ Cai et al., 2026b ] . TTHE’s transfer experiments instead
execute batch-specific evolved programs with other backbones. Its conditional
analysis concerns a class of trace-triggered edits under a fixed execution coupling. Self-directed model adaptation. Self-improvement can also change the model itself. STaR bootstraps reasoning by
fine-tuning on generated rationales that lead to correct
answers [ Zelikman et al., 2022 ] ; related work fine-tunes on high-confidence
solutions generated from unlabeled questions [ Huang et al., 2023 ] .
SEAL learns to generate its own adaptation data and update directives, using
post-update performance to train the self-editing policy [ Zweiger et al., 2026 ] .
AgentEvolver combines self-generated tasks, experience-guided exploration, and
trajectory-level credit assignment to improve agent reinforcement
learning [ Zhai et al., 2025 ] . These approaches use experience to improve
parameterized capabilities or the process that trains them. In TTHE, experience
instead changes the executable procedure through which an unchanged model
acquires context, uses tools, verifies results, and recovers from failures. Test-time adaptation and reinforcement learning. TTT, Tent, and MEMO adapt model parameters or normalization statistics using
self-supervised, confidence-based, or augmentation-based objectives on unlabeled
test inputs [ Sun et al., 2020 , Wang et al., 2021 , Zhang et al., 2022 ] . For language-model
reasoning, TTRL performs reinforcement learning directly on unlabeled test data,
estimating rewards from agreement with majority-voted model
outputs [ Zuo et al., 2026 ] . It therefore shares the absence of ground-truth
answers during adaptation, but uses the inferred rewards to update model weights.
TTC-RL constructs test-time curricula from an available training pool for targeted
reinforcement learning [ Hübotter et al., 2025 ] , while TTT-Discover trains on
experience from a particular test problem, using continuous rewards to prioritize
exceptional solutions [ Yuksekgonul et al., 2026 ] . These studies establish
test-time learning as more than repeated inference. TTHE pursues a different
adaptation state: the model remains fixed, while execution evidence informs
program updates and candidate selection without being reduced to a scalar
training objective. Test-time memory and context evolution. Parameter-free adaptation is also studied through persistent memory and evolving
contexts. Dynamic Cheatsheet maintains a self-curated memory of strategies,
code snippets, and reusable insights at inference time without explicit
ground-truth labels [ Suzgun et al., 2026 ] . ACE treats contexts as
evolving playbooks, using generation, reflection, and curation with incremental
updates; it supports both offline context optimization and online adaptation
from execution feedback [ Zhang et al., 2026b ] . EvoTest evolves prompts, memory,
hyperparameters, and executable state-extraction logic across interactive
episodes, using transcripts for updates and environment-score statistics for
candidate selection [ He et al., 2025 ] . These methods already demonstrate
experience accumulation beyond an isolated answer. TTHE focuses on revising the
task’s control program and committing a single harness whose cached outcomes
are scored on the same batch, with final evaluation feedback excluded from
the adaptation loop. Response refinement and execution feedback. Chain-of-thought, self-consistency, and ReAct organize reasoning and tool use
within an inference procedure [ Wei et al., 2022 , Wang et al., 2023 , Yao et al., 2023 ] .
Self-debugging and Self-Refine revise candidate
answers [ Chen et al., 2024 , Madaan et al., 2023 ] , and Reflexion retains
textual experience for later attempts [ Shinn et al., 2023 ] . Domain-specific
systems incorporate these ideas into fixed procedures: DIN-SQL and DAIL-SQL use
structured prompting and execution-related processing for
text-to-SQL [ Pourreza and Rafiei, 2023 , Gao et al., 2023 ] , while code-generation
systems use tests to select candidate solutions [ Chen et al., 2022 , Li et al., 2022 ] .
Learned verifiers and LLM judges provide further evaluation
signals [ Lightman et al., 2024 , Zheng et al., 2023 ] . TTHE can express verification
and repair within a harness, but adapts the program that specifies when and how
these operations occur, rather than only revising a particular response. Appendix E Cross-Database Transfer and Continued Adaptation TTHE targets adaptation to the current unlabeled batch. As a complementary

∎ F.4 Interpretation and Application Boundaries Failure soundness is one-sided. A sound rejection flags a final outcome that cannot satisfy the task. Acceptance need not imply
correctness. A runtime failure is sound rejection only when it invalidates the submitted outcome under
the specified environment. Visible tests qualify only when they are authoritative necessary conditions;
noisy, stale, unrelated, or flaky tests do not automatically qualify. A correct SQL query may return zero
rows, and an intermediate exception may be recovered from before a correct outcome is submitted. Such
signals require potentially imperfect precision π \pi , rather than being classified as sound by default. Repair precision and locality. The mass m ​ π m\pi identifies incorrectly behaving executions targeted by an edit; m ⁡ ( 1 − π ) m(1-\pi) identifies
correct ones exposed to modification. A high trigger rate alone says nothing about their balance.
Without a repair-quality assumption, r ≥ 0 r\geq 0 and u ≤ 1 u\leq 1 give e ′ ≤ e + m ⁡ ( 1 − π ) + ε = e + ( 1 − e ) ​ f + ε . e^{\prime}\leq e+m(1-\pi)+\varepsilon=e+(1-e)f+\varepsilon. Soundness removes falsely triggered correct outcomes, and exact locality removes possible off-trigger
harm. Neither condition asserts r > 0 r>0 . Likewise, clearing a failure flag does not measure r r , because
correct and incorrect outputs can both pass an incomplete check. Relation to the search procedure. TTHE can express local repair branches as well as global prompt and grounding edits. The preservation
result applies to transitions satisfying the stated soundness and locality conditions; extending it to
a sequence requires these conditions at each committed transition. The complete search procedure is
evaluated empirically. Binary versus graded outcomes. The analysis uses binary correctness, as in exact SQL or hidden-test evaluation. For graded loss,
merely detecting an outcome that is not fully correct does not make replacing it safe: a partly
successful outcome can be made worse. An analogous preservation conclusion would require a stronger
condition, such as the trigger certifying maximal loss. It is not claimed for claw-eval’s graded score,
nor does the correctness analysis account for additional latency, tokens, or execution costs.
