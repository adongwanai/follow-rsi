Scaling computer-use agents from individual actions to complex software work requires experience that connects decisions to complete outcomes. We present NorthCUA , an integrated system for turbocharging computer-use agents through experience at scale. Its Experience Flywheel supplies diverse executable tasks to the NorthCUA Harness, which sustains long interactions, records decisions, and checks task outcomes. The Flywheel uses these records to curate verified trajectories. For unsolved tasks, recursive self-improvement evolves reusable skills and preserves verified milestones so later attempts build on earlier progress. Staged Learning combines this experience with grounding data from the Flywheel to develop GUI competence through mid-training and long-horizon supervised fine-tuning. The policy then learns from fresh attempts in the same Harness through joint desktop–web reinforcement learning, closing the loop between experience production and policy improvement. The resulting Nano, Mini, and Pro family achieves state-of-the-art results among open-source models across GUI grounding, desktop execution, and Web interaction under the reported evaluation settings (Figure 1 ). For more responsive Web workflows, NorthCUA -Ultrafast pairs direct action selection with open-ended generation on pre-RL Nano, offering a measured quality–latency tradeoff. Together, these advances establish NorthCUA as a high-performing model family and a reusable foundation for agents that carry complex software work from intent to completion.

Computer-use agents (CUAs) extend the capabilities of large language models from generating responses to operating computers and automating software tasks ( Zhang et al., 2025b ; Wang et al., 2025b ) . They can invoke software functions through application programming interfaces (APIs) and command-line interfaces (CLIs). Graphical user interfaces (GUIs) extend this access to functions that applications do not expose programmatically, providing a critical last mile for software automation ( Zhang et al., 2025a ; Zhang et al., 2025c ) . Through GUI interaction, agents interpret the screen and translate natural-language goals into mouse and keyboard actions. Advances in visual grounding and action generation have expanded the range of operations these agents can perform ( Qin et al., 2025 ; Wang et al., 2025c ; Zhou et al., 2025 ) . As agents combine these operations into longer workflows, earlier actions shape the software state on which later decisions depend. Reliable completion requires agents to preserve intermediate progress and the user’s constraints, adapt to changing interfaces, and recover from errors while keeping the overall goal in view ( Zhang et al., 2026 ; Lu et al., 2026 ) .

Training agents to coordinate such workflows therefore requires experience that develops precise interface skills and connects successive decisions to complete task outcomes. Obtaining this experience at scale begins with constructing varied tasks, each of which needs a request grounded in available software and content, a usable initial environment, and a reliable way to judge success ( Ge et al., 2026 ; Zhou et al., 2026b ) . Once these tasks are available, collecting experience from them requires an agent framework that sustains long interactions and records decisions and outcomes across desktop and web environments. The resulting demonstrations can teach the policy how to complete workflows, but independent execution may lead it into states absent from those demonstrations. Continued improvement therefore requires fresh interaction and outcome feedback from the policy’s own attempts ( Wang et al., 2025c ; Jung et al., 2026 ; Lu et al., 2026 ) . Meeting these linked needs calls for co-designing how tasks are constructed, how agents execute them, and how the resulting experience is used for learning.

We present NorthCUA , an integrated system for turbocharging computer-use agents through experience at scale . Our central idea is to co-design the production and use of experience, making software interaction a continuing source of learning. We connect executable tasks to policy updates through three components (Figure 2 ), focusing on GUI-based software operation. The Experience Flywheel constructs executable tasks for the NorthCUA Harness to run and assess. The recorded trajectories and outcome evidence guide curation, supplying Staged Learning with demonstrations that complement the Flywheel’s separately constructed grounding examples. This mixture develops interface understanding and workflow completion. Shared execution and outcome interfaces also let the learner collect fresh attempts from the policy itself, extending the same system from demonstration collection to continued policy improvement.

We design the NorthCUA Harness as full-lifecycle infrastructure that executes software tasks and turns the resulting attempts into inspectable experience for learning. This requires keeping the agent’s decisions connected to its workspace and outcomes, from environment preparation through execution and evaluation to record preservation. Within the shared runtime, visual context and task memory help agents build on progress across long workflows ( Zhang et al., 2026 ; Zhang et al., 2025d ) . An evaluator uses the execution record and live workspace to check task completion and execution quality, supplementing task-specific verifiers where their coverage is incomplete ( Zhuge et al., 2025 ) . To scale this process, the Batch Rollout Service coordinates parallel workers and overlaps lifecycle stages, supporting efficient, high-concurrency experience collection (Section 3 ).

With a runtime for collecting and checking software experience, the next challenge is to supply enough varied, useful work for the agent to learn. The Experience Flywheel addresses two levels of supervision: single-step grounding examples for locating controls and assessed agent trajectories for completing tasks. Grounding pairs screenshots with queries and target locations. Visual and structural annotations provide broad coverage ( Lu et al., 2024 ; Li et al., 2025a ) , while application documentation helps explain a control’s function when appearance alone is insufficient. At the trajectory level, three complementary construction routes supply tasks to the harness. Scaling Intents derives requests from available software and content, while Scaling Environments builds the workspaces needed by sourced requests or reconstructs reference websites. For tasks with executable checks, Scaling Verifiers creates further tasks by adapting requests, initial states, and verifiers together ( Ge et al., 2026 ; Lu et al., 2026 ; Lv et al., 2026 ) . When a valid task remains unsolved in ordinary collection, we use recursive self-improvement (RSI) for hard-task collection. Skill-guided exploration retains tested procedures for later attempts, while milestone-guided search preserves software states and agent context at verified milestones to explore alternative ways of completing the remaining work. Task outcomes and execution quality determine which trajectories become demonstrations for learning (Section 4 ).

A model’s ability to coordinate a long workflow builds on familiarity with the interfaces and operations it uses. Staged Learning follows this progression, starting with Broad GUI mid-training on grounding examples and desktop and web trajectories judged to complete their tasks ( Wang et al., 2025c ; Jung et al., 2026 ) . The broad trajectory corpus spans over four million GUI interaction steps across dozens of applications. Building on this operational foundation, Verified long-horizon supervised fine-tuning (SFT) concentrates on carefully selected, complete workflows whose outcomes pass executable task verifiers and whose intermediate results support later decisions. Independent execution can still lead the policy into states absent from its demonstrations. Joint desktop–web agentic reinforcement learning therefore lets one policy practice in both domains and learn from fresh successes and failures. Task verifiers score these attempts, and group-relative policy optimization (GRPO, Shao et al., 2024 ) uses their outcomes to update the policy (Section 5 ).

Shared task, execution, and assessment interfaces connect these learning stages to experience collection (Figure 2 ). An updated policy can return to the same Harness, where its new attempts are evaluated and can be curated into subsequent training experience. This return path lets advances in model capability support further collection, giving NorthCUA a reusable foundation for continued learning across desktop and web environments.

The resulting NorthCUA family comprises Nano (9B), Mini (35B), and Pro (397B), all built on Qwen3.5 ( Qwen Team, 2026a ) . We evaluate this family on six benchmarks spanning GUI grounding, desktop execution, and Web interaction. The suite follows the agent from locating controls to completing long workflows and checking whether Web applications behave as intended. NorthCUA establishes state-of-the-art results among open-source models in all three domains (Figure 1 ). With 397B parameters, Pro outperforms trillion-parameter Qwen3.8-Max and Kimi-K3 on both grounding benchmarks, OSWorld-Verified, and WebArena-Verified ( Qwen Team, 2026c ; Kimi Team, 2026 ) . The 35B Mini also surpasses Kimi-K3 on OSWorld-Verified and Qwen3.8-Max on WebArena-Verified. Stage comparisons show desktop and Web gains across all three model sizes after long-horizon SFT and joint RL (Section 6 ).

Long workflows also accumulate the latency of successive model decisions. To reduce this cost, NorthCUA -Ultrafast adapts pre-RL Nano with a Jev-inspired choice head, selecting finite actions directly while retaining generation for open-ended outputs ( Almeida, 2026 ) . Its Head + LoRA variant completes matched successful WebArena-Verified tasks 2.3 × 2.3\times faster on average than full generation (Section 6.8 ). We release all three models, the full NorthCUA Harness code, and this technical report, providing an open foundation for developing agents that carry software work from user intent to completed outcomes.

We study two capability targets in desktop and web environments (Figure 3 ): locating a requested control in a screenshot and completing a task through software interaction. We evaluate these targets separately.

Given a screenshot and a natural-language query, the model predicts the coordinates ( x , y ) (x,y) of the target UI element in the original image ( Cheng et al., 2024 ; Li et al., 2025b ) . The model completes the task with one prediction over a fixed screenshot. The query can describe the element’s appearance or function, such as locating the zoom tool in Figure 3 (a).

An end-to-end task combines a user request, an initial software environment, and conditions for judging completion. The environment provides the applications, files, and website records needed for the request. The agent observes the current state, takes an action, and uses the resulting feedback to decide what to do next. Later decisions can use information and results from earlier steps. The request and completion conditions stay fixed throughout the attempt, so the final files or software state can be checked against the original goal ( Zhou et al., 2024 ; Xie et al., 2024 ) . Figure 3 (b) illustrates the two interaction settings:

Desktop agents observe desktop screenshots and operate applications through mouse and keyboard actions, including clicking, typing, scrolling, and dragging. Tasks may span multiple applications and files.

Web agents observe webpage screenshots and document object model (DOM) information, and interact through browser tools for navigation, element-based or coordinate-based actions, text input, and tab management.

Both settings follow the same observation, action, and feedback loop, using their respective desktop or browser interfaces. The acting policy uses these interfaces to perform the task. Preparation, annotation, and evaluation can use additional programmatic tools with separate permissions.

The experience loop in Figure 2 connects task construction to execution and learning. Its handoffs specify how an executable task becomes an assessed record and then a training sample.

The Experience Flywheel packages each executable task as a CaseSpec , a task specification containing the request, input materials, environment configuration, and setup instructions, together with requirements for assessing the result. For the invoice task in Figure 3 (b), this means providing the workbook and spreadsheet application and specifying that the exported PDF should highlight overdue invoices.

Using this specification, the NorthCUA Harness prepares the environment, uploads input files, and runs setup and launch commands before starting the agent on the request. Observations, actions, and feedback are recorded throughout the attempt so that its outcome can be assessed in the context of the work that produced it. Task-specific checks, an evaluator, or both inspect the result against the declared requirements. For the invoice task, this means checking the saved PDF and its highlighted contents. These outcome and execution-quality assessments give the Experience Flywheel the evidence needed to select demonstrations. Valid tasks that remain unsolved can instead enter the hard-task collection branch, where skill-guided exploration or milestone-guided search produces further attempts for the same assessment process (Section 4.3 ).

Staged Learning turns this collected experience into capability in three steps. Broad GUI mid-training combines diverse task trajectories with the Flywheel’s separate screenshot–query–target examples, building a foundation in interface understanding and software operation. Grounding supervision is used only in this stage. Verified long-horizon SFT then focuses on high-quality, complete workflows with checked outcomes, teaching the policy to carry information and intermediate results across dependent steps. This prepares the model to learn further from its own interaction.

For joint desktop–web agentic reinforcement learning, we first select tasks on which the SFT policy’s trial attempts have different outcomes. This focuses initial collection on tasks with useful outcome differences for comparing executions. The Harness collects fresh groups of attempts, executable verifiers score their outcomes, and GRPO uses comparisons within each task group to update one shared policy (Section 5.3 ). The updated policy returns to the Harness for subsequent attempts under the same task and outcome interfaces.

The following sections explain these components in detail. Section 3 presents the execution and assessment framework, Section 4 describes task construction and experience curation, and Section 5 develops the staged learning recipe.

The NorthCUA Harness provides full-lifecycle infrastructure for executing desktop and web tasks and turning each attempt into inspectable experience for learning. During execution, a persistent workspace and retained task context let the agent build on earlier progress. We retain its execution record and resulting artifacts for outcome assessment, keeping the original environment available when live checks need to inspect the state the agent produced. Resources are released after the required inspection and record preservation are complete. By carrying each attempt through assessment and preservation, this lifecycle keeps decisions, outputs, and judgments connected to the same task attempt (Section 2 ).

Desktop and web agents follow the same basic loop: observe the software, choose an action, execute it, and use the feedback to continue. What differs is how each platform exposes its state and controls. Building on shared-runtime approaches to computer use ( Zhang et al., 2026 ; Yan et al., 2025 ) , we design Agent Kit to separate this common loop from platform-specific observation and action tools. Long-horizon support and evaluation reuse this same execution foundation.

We use a shared runtime to organize interaction as a ReAct-style loop with visual feedback ( Yao et al., 2023 ) . It assembles the request, observation, and relevant history into the next model input, invokes the policy, and executes the resulting tool calls. Returned observations and action results then inform the next decision. Common runtime services manage progress, budgets, and termination, while environment-specific implementations supply the observations and operations. To build an agent for another platform, developers supply its perception functions, action tools, and observation processing hooks. The shared runtime then carries these components through the complete decision and recording loop, without rebuilding the agent flow. Section 3.1.3 details the desktop and web instances.

CUA execution also involves several timescales. Application and browser sessions persist across actions, a user request can require many decisions, and each decision produces feedback needed by the next. We represent these lifetimes through three nested scopes:

Session maintains the agent’s execution state and associated software resources, such as a browser session, across a sequence of user requests.

Round tracks the processing of one user request, including its multi-step execution, budget, and termination status.

Step records one policy decision and the resulting tool execution and feedback. Each step can contain multiple tool calls.

These runtime scopes organize interaction, while the task attempt supplies the collection-level identity used to associate actions, artifacts, and assessment. Each recorded action retains its request and session context, supporting task-level inspection and collection recovery. Session resources are managed within the broader environment lifecycle coordinated by the collection or training system. Appendix H.1 gives the execution-scope details.

Desktop input, browser interaction, and workspace inspection expose different operations, whose implementations may run beside the agent or near a remotely hosted application. To make these capabilities available to the shared decision loop, we use a common tool interface that allows their implementations to evolve independently.

Tool definitions describe operations and their arguments, while dispatch connects each call to its implementation and returns the result to the requesting step. The Agent Kit integrates local functions and tools exposed through Model Context Protocol (MCP), whose standard tool descriptions and invocation messages support capability discovery and execution ( Model Context Protocol, 2025 ) . Both paths feed the same interaction history and recording services. Platform-specific controls can therefore be added through tool bindings while reusing task progression and feedback handling.

To reduce the repeated inference overhead of long GUI workflows, we allow the model to issue multiple action calls in a single response. The runtime executes these calls serially in the specified order, allowing actions that can be planned together to share one model invocation.

For computer use, tool feedback also needs to describe the state after an operation. Post-action observation hooks attach fresh screenshots or page observations to state-changing tool results, giving the next decision a current view of the interface. Section 3.2.1 develops this action-aware feedback design. The same tool separation supports centralized agents operating remote devices, whose collection lifecycle is described in Section 3.4 .

The same separation provides a path to additional platforms. Mobile extensions, for example, would supply screen observations, touch operations, and application/session handling around the shared runtime. Across the desktop and web instantiations, this reusable execution foundation also exposes a common challenge: carrying earlier constraints and intermediate results into decisions made much later in a workflow.

Long-horizon execution is a central challenge in practical computer use. Real software work can require many fine-grained GUI operations across applications, files, and intermediate artifacts, with later actions depending on earlier discoveries and decisions ( Yuan et al., 2026 ) . Editing a document may still require a value read from a spreadsheet and an output requirement encountered much earlier. Meanwhile, repeated visual observations and tool feedback enlarge the history supplied to each decision ( Lu et al., 2026 ; Lv et al., 2026 ) . Sustaining these workflows requires controlling context growth while keeping current state, earlier progress, and task-relevant knowledge available for continued action.

We separate the decision context presented to the model from the complete execution record retained for inspection and learning. To keep later decisions informed within a limited context budget, we design three complementary mechanisms: action-aware visual context for recent states and operations, task-preserving compaction for earlier progress and remaining work, and structured working memory for facts and decisions the agent chooses to retain. The visual window shows the steps leading to export, the summary keeps export marked as pending, and an agent-written note carries the overdue total into the report. Each view supplies information needed for continued action without replacing the full execution record.

Repeated GUI interaction produces an image-heavy history whose size grows with the workflow ( Lu et al., 2026 ) . Its visual content serves two related purposes: the current screen guides the next action, and recent states help the agent interpret what it just did. The resulting screen alone can leave the location of a preceding click or the path of a drag unclear, particularly after a window or page changes. Visual context therefore needs to preserve both current state and the spatial meaning of recent operations within a limited image budget.

We use a sliding window to provide a bounded visual history of up to k k recent frames, including the latest clean screenshot. Textual action and tool-result history survives image eviction, retaining a longer account of the interaction until the text-history policy calls for compaction. To keep the newest frame current, post-action observation hooks supply fresh post-action feedback alongside state-changing tool results. The next policy invocation receives this screenshot directly, avoiding a dedicated model turn solely to request the resulting screen.

To help the agent connect its previous operation with the change now visible on screen, we design a complementary action view in the historical frames. Visual prompting work shows how spatial marks can make image regions easier to refer to ( Yang et al., 2023 ) . Our historical action overlays mark the corresponding pre-action image, using different cues for different operations. As shown in Figure 6 , a click marker locates the control that opens a dialog, a drag path links the clip’s old and new positions, and a scroll cue identifies the direction in which the page moved. Text and key badges record operations that are less clear from a spatial marker alone. Figure 6 pairs each annotated pre-action view with its clean resulting state to make the operation and observed change easy to compare. In the runtime’s decision context, historical overlays identify recent operations, while the latest clean screenshot provides the current interface for the next decision. Replacing an earlier clean frame with an overlay changes the image history. The training-segment rule in Section 5.3.3 preserves the input seen before that change.

This bounded visual history preserves both the spatial meaning of recent actions and the current interface state. The textual record continues to accumulate across these visual windows, creating the next context-management challenge.

Bounding images leaves another source of context growth: assistant messages, reasoning, tool feedback, and intermediate task information accumulate throughout the workflow. Earlier constraints and discoveries may still be needed when this text approaches the model’s usable input budget. Context-management methods consolidate long histories to retain useful information within finite prompts ( Ye et al., 2026 ) . We adapt this principle to computer use by designing task-preserving compaction around three priorities. When older history needs to be summarized, we preserve the immediate action–feedback context, retain task progress, and avoid carrying stale GUI locators into later decisions:

Protect current interactions. The task request, latest GUI observation, and latest few steps remain protected. Assistant actions stay grouped with their tool results, and open exchanges remain intact until their responses arrive. This preserves the immediate action–feedback context, including the current GUI observation whether it appears in a user message or a tool result.

Summarize task progress. The summary organizes goals, constraints, supported facts, decisions, completed and failed work, current state, open items, and artifact references around task continuation. Desktop and web profiles instruct the summarizer to retain semantic software state and observed effects while condensing routine navigation. For example, an extracted spreadsheet value, its source file, and a pending export requirement can therefore remain available after the navigation history is compressed. The instructions also distinguish issued actions, observed effects, and unresolved completion claims: an export command and an observed saved file represent different evidence about progress.

Handle transient GUI locators. Coordinates and element references can become stale after a page update or application switch. The summary-input projection filters these volatile fields, and the summary instructions exclude old locators from current executable state. The retained current observation remains available for grounding subsequent actions.

Later compaction updates the existing summary with newly eligible history, with source references available for inspection. This gives continued work a compact account of its dependencies while keeping the full execution record available for outcome assessment. Alongside this budget-triggered consolidation, the agent can actively preserve important information as it is discovered.

During a long task, an agent encounters information with clear future value: a figure read from another file, a requirement for the final deliverable, an unsuccessful approach, or a plan for remaining work. Assistant messages can mention these details in the chronological history, where their later visibility depends on history retention and summarization. Giving selected information an explicit working-memory representation lets the agent decide what to retain and revise during execution, following the broader principle of agent-controlled memory management ( Packer et al., 2024 ) .

To let the agent preserve useful information when it discovers it, we design a dedicated text-only note tool. The agent can call this tool proactively to record a spreadsheet value before switching to a document, or to preserve a correction while revising an unsuccessful approach. The right-hand panel of Figure 5 shows this transfer: note N1 records the overdue total from the workbook for later use in the report. Notes are stored independently of the history summary and can be presented in subsequent decision contexts. This complements compaction: a summary consolidates accumulated work under budget pressure, while a note explicitly preserves information the agent expects to use again.

Notes serve three purposes: (i) retaining reusable knowledge and choices through facts , constraints , and decisions , (ii) recording lessons and risks through corrections and precautions , and (iii) tracking progress and unfinished work through checkpoints . This organization encourages concise entries with a clear role in later decisions.

As work progresses, replacement notes can supersede outdated entries. The memory service maintains them within the authorized task and session, then supplies a budgeted view of active entries to prompt construction. A corrected value or revised plan can therefore replace the corresponding obsolete item in working context, keeping remembered information aligned with the agent’s evolving understanding of the task.

Together, these mechanisms keep the current screen, accumulated progress, and reusable knowledge available for continued action. The complete execution record connects these decisions to the resulting workspace, providing the evidence for outcome evaluation and subsequent training. Selecting GUI trajectories for learning requires accurate outcome judgments across a growing variety of tasks. Dedicated verifiers become difficult to write and validate when correctness depends on content, presentation, or application-specific state ( Rosset et al., 2026 ) . We therefore use an adaptive evaluator that interprets the declared task requirements and gathers the evidence needed to assess the work. We build the evaluator as an agent-as-a-judge ( Zhuge et al., 2025 ) , reusing Agent Kit tools. After the acting phase ends, it selectively retrieves saved records and artifacts and can inspect the original workspace using authorized shell, GUI, and browser tools. It adapts its inspection to each requirement and seeks further evidence when the available observations leave the outcome unclear. This combines reusable inspection capabilities with task-specific judgment, extending assessment to requirements that lack dedicated executable checks. Task-grounded rubrics guide this process, and multidimensional reports connect the findings to experience selection and failure analysis. In Figure 7 ’s export example, the evaluator checks that the PDF exists and opens it to compare its contents with the source. This artifact inspection supplies the evidence for its final report. We require this report to associate each criterion-level judgment with its evidence, uncertainty, and evaluator operations.

The evaluator receives the task request, assessment criteria, and a compact view of the execution records. Requirements may concern an earlier action, a final file, or a state that is visible only inside an application. To reach these different forms of evidence, it uses two complementary tool groups:

Recorded evidence. Retrieval tools expose selected steps, screenshots, tool results, and retained artifacts. They let the evaluator inspect relevant parts of a long trajectory as questions arise, while the full record remains available outside its current context.

Live task state. Live tools inspect the original device or sandbox through fresh screenshots, read-only shell commands, and GUI or browser operations. Web probes can reuse the actor’s browser session, including its tabs and page state. This access makes environment-resident results available for checking while the workspace is still alive.

Appendix H.2.3 lists the evaluator’s retrieval tools, authorized live interfaces, and report schema.

The evaluator chooses between these sources according to the requirement under review, continuing its investigation when an observation leaves an important question open. This environment-aware approach is also studied in Shi et al. (2026) . For a document export, for example, a recorded action can show that export was attempted, a file check can establish whether an output exists, and an application inspection can reveal its rendered contents. Comparing these contents with the task inputs supports judgments about their correctness. Each observation answers a different part of the acceptance question. Selective retrieval and live access thus connect the history of an operation to its actual result.

To preserve attribution, the assessment protocol pairs pre-inspection terminal evidence with a separate record of evaluator operations. Each judgment is linked to the submitted work and the observations used to assess it, making the investigation traceable to the original attempt. The rubric then connects this evidence to task fulfillment and execution quality. Appendix H.1 details the inspection and attribution protocol.

The value of a GUI trajectory depends on both its result and the behavior it demonstrates. Successful attempts can contain unnecessary detours or unintended changes, while an attempt blocked late by the environment can contain useful completed subtasks. Data curation therefore needs answers to two complementary questions: (i) which task requirements were fulfilled , to establish what the trajectory accomplished, and (ii) how the agent performed the work , to assess the behavior available for learning. We therefore design the rubric to combine task-grounded acceptance criteria with multidimensional execution assessment ( Rosset et al., 2026 ) .

For task fulfillment , the request and declared acceptance conditions define the intended outcome. The rubric expresses these obligations as specific, individually checkable questions. Export tasks may require the right contents, destination, and format. Explicitly required procedures also form part of acceptance. Request-derived criteria are generated before scoring the trajectory, with the original task requirements governing their interpretation. Assessing these obligations individually identifies complete, partial, and unresolved fulfillment, including which requested subtasks have supporting evidence.

For execution assessment , the report records process quality, efficiency, side effects, and failure diagnosis alongside judgment uncertainty. These dimensions explain the path taken to the result: repeated ineffective actions may reduce its value as a demonstration, while a successful recovery can provide useful behavior to study. Failure diagnosis distinguishes agent errors from environment blockers, and uncertainty identifies judgments that need further checking. Findings are linked to the relevant requirements and recorded steps so that their scope can be inspected. Table 2 summarizes the dimensions and their uses.

Together, the rubric and execution report describe both the result achieved and the behavior that produced it. Their links to specific requirements and recorded steps make the judgments useful for selecting complete demonstrations, reviewing local segments, and analyzing recurring errors.

We use the report’s separate rubric scores to select data for different learning goals. Task fulfillment identifies completed work, while process quality, efficiency, and side-effect assessments let us adjust selection thresholds for each data cohort. For example, a cohort of concise successful demonstrations can apply stricter efficiency criteria, while a cohort meant to teach recovery can retain useful corrections and exploration within successful attempts.

At the trajectory level , these criteria select complete demonstrations. At the segment level , requirement-linked evidence can guide review of completed subtasks or recovery sequences, with the original decision context and local outcome kept alongside the behavior. Figure 7 ’s report separates completion from execution quality so that these dimensions can be used together in selection. Section 5.1 applies the reports to trajectory curation, and Section 5.2 retains complete episodes for long-horizon SFT.

The preceding mechanisms turn one task attempt into assessed experience. Producing a large training corpus requires many such attempts to run in parallel, each with its own software state. Their preparation, GUI execution, evaluation, and recording take different amounts of time and consume different resources ( Xie et al., 2024 ; Yuan et al., 2026 ) . Simply launching more agents can therefore create a backlog at another stage, while an interruption after execution can leave useful work without a complete record.

To support efficient large-scale collection, we design a Batch Rollout Service that coordinates the entire task lifecycle. Following the environment-lifecycle perspective also explored in Peng et al. (2026) , we combine centralized agent control with isolated workspaces, prepare upcoming tasks alongside ongoing execution, and manage load and recovery through record delivery. Figure 8 shows the two relationships behind this design. Panel (a) connects one controller to independent device workers. Panel (b) shows how their lifecycles overlap: the same-time marker crosses evaluation, execution, and preparation in three different attempts. The service coordinates this concurrent work so that completed attempts produce usable experience records.

As collection grows, prompts, model settings, and agent logic continue to change. Placing that logic inside every task environment would require updating those environments whenever the agent changes. We therefore separate centralized agent control from device execution , as shown in Figure 8 (a):

Centralized controller. One service manages multiple agent runners and their device workers. It maintains prompts and agent configuration, assembles context, invokes the model, and dispatches actions.

Device worker. Each worker runs inside one task’s isolated sandbox. It executes tool calls and captures observations from that environment. The worker starts with its sandbox and ends when the sandbox is released.

The controller maintains a long-lived WebSocket connection to each worker, sending actions and receiving observations over the same connection. Related distributed device orchestration appears in Zhang et al. (2025d) . Here, each runner communicates with the worker assigned to its task, keeping the concurrent attempts separate.

This division lets us update compatible prompt and model configurations centrally for later batches while reusing the same device-worker implementation and software templates. The device layer remains focused on observation and tool execution, so routine agent changes do not require changing that layer. We save each batch’s configuration for resumed collection and retain its trajectories on the controller side, where they survive sandbox release. With control and recording shared, scaling execution then depends on preparing enough independent task environments.

A new attempt needs the files and software state specified by its task. Reusing a workspace changed by an earlier attempt could alter those starting conditions ( Xie et al., 2024 ) . We therefore give each attempt its own initialized sandbox in our fresh-start collection mode. For Linux desktop and browser tasks, we choose E2B to create and manage these isolated environments ( E2B, 2026b ) , with its desktop extension providing the graphical workspace ( E2B, 2026a ) . Custom templates supply the operating system and shared applications, while per-task setup uploads files, launches applications, and prepares the required state. This lets tasks reuse a software template without inheriting another attempt’s changes.

Creating a fresh environment takes time, so preparing tasks only when an agent is ready would leave collection waiting on setup. We address this with a task-bound preparation queue : upcoming environments are prepared while earlier attempts are executing or being evaluated. Figure 8 (b) makes this overlap visible in the offset Prepare blocks. Each ready workspace is assigned once to its matching task, provided enough time remains for execution and cleanup. It stays available through the required outcome checks and output capture, then is released. Preparation can thus run ahead without sacrificing fresh starting conditions or losing the evidence needed for assessment.

Preparation, execution, and evaluation progress at different rates. Independent admission can leave prepared environments waiting for execution or completed attempts waiting for evaluation. We coordinate admission with two controls. Stage-specific concurrency limits bound the number of attempts admitted to each stage. Because resource demand can vary within these limits, controller-pressure feedback slows new admissions when the shared controller remains busy. The first control limits local demand, while the second responds to load across the concurrent attempts.

When a connection is lost or a downstream process fails, we first check whether the affected attempt is still running or has completed. Completed execution records can support retries of record-based evaluation or artifact processing, preserving the work already done. If the task itself needs to be rerun, we start it in a fresh environment.

Before delivery, we check that the required trajectory, observations, and assessments are complete and linked to the same attempt. Appendix H.3 gives the configuration and recovery details.

Together, these designs carry the same runtime from individual task execution to sustained delivery of complete, inspectable experience. The Experience Flywheel in Section 4 builds on this foundation to construct tasks and curate the resulting records for model training.

The NorthCUA Harness provides the execution infrastructure, but training a computer-use model also requires a large and varied supply of experience. The model needs examples of which control a request refers to, as well as trajectories that show how successive decisions achieve a complete goal. We design the Experience Flywheel to construct and curate these two levels of supervision. Single-step grounding pairs a screenshot and a query with the location of one visible control. End-to-end task construction supplies user goals, prepared workspaces, and outcome checks from which the harness can collect multi-step trajectories.

These levels require different construction methods. For grounding, we start from visible controls and generate language that identifies them. For complete tasks, we connect available software and content, sourced requests, or verified seed tasks to the environments and assessments they need. This gives three complementary routes for scaling intents, environments, and verifiers. Executing the resulting tasks supplies experience for learning, although successful trajectories can remain scarce for the hardest workflows. We address that remaining gap through recursive exploration that retains useful skills and verified progress across attempts. Together, these methods supply localization examples and curated trajectories for the staged learning in Section 5 .

Single-step grounding takes a screenshot and a natural-language query, then predicts the location of the requested control ( Cheng et al., 2024 ) . Each training example contains a screenshot, a query that identifies a visible control such as a button or toolbar icon, and the control’s coordinate in the original image. The main construction challenge is to write queries that identify the same control across different visual states and ways of describing an operation, especially in specialized applications ( Lu et al., 2024 ; Li et al., 2025a ) .

We construct these examples through two complementary routes:

Broad visual and structural coverage. We use screenshot evidence and available interface metadata to describe visible controls across diverse applications and states (Figure 9 ).

Documentation-grounded functional localization. We retrieve application knowledge when a control’s appearance leaves its function unclear, then use the matched function to generate queries (Figure 10 ).

The first route expands interface and language coverage. The second fills gaps that visual evidence alone leaves unresolved. Both preserve the target’s original location and produce the same screenshot–query–coordinate format, so their candidates can pass through shared quality and coverage checks.

To obtain broad grounding coverage, we first need screenshots of varied interfaces, then a way to turn their visible controls into language targets. We use the three-step procedure in Figure 9 . Panel (a) collects interface states, including states encountered during agent work. Panel (b) associates one visible control with its appearance and original location. This target record gives the query generator in (c) a fixed referent: it can vary how the control is described while keeping the location label unchanged.

To collect these states, we combine public UI datasets, web-collected GUI screenshots, and screenshots from agent trajectories, including real Linux desktop interaction. Trajectories contribute intermediate states such as open dialogs, expanded menus, and partially completed forms. We then use OmniParser, a screen-parsing system that detects interactive regions and describes icons, to obtain candidate control boxes and descriptions ( Lu et al., 2024 ) . Accessibility annotations, when available for the same state, add control names and roles. These sources provide complementary evidence for identifying a target. Visual parsing supports screenshots collected without accessibility metadata, while names and roles help connect visible controls to the language used in requests.

For each target, we consolidate this evidence into one control record that keeps the crop and original image position together with the available name, role, color, appearance, and surrounding context ( Zhang et al., 2026 ) . For the calendar example in Figure 9 (b), the record identifies the blue Week tab between Day and Month , together with a point inside its clickable region. The full screenshot preserves the neighboring controls needed to make a description specific.

With this record in place, we use an LLM to generate several queries from the record and full screenshot. The descriptions refer to the control’s name, appearance, position, or an operation supported by the available evidence. In the example, Select the Week tab names the control directly, while Select week view expresses its purpose. Each query becomes a separate candidate example paired with the clean original screenshot and the same coordinate. This variation broadens the language supervision without changing which control the model learns to locate ( Chen et al., 2026a ) .

This route supplies broad coverage of interfaces and visual states. When a control’s operation depends on application-specific knowledge, the documentation route provides the missing functional description.

Some controls belong to specialized applications whose functions are hard to infer from a screenshot alone. Parsing may locate a toolbar icon while a general-purpose LLM remains unsure what the icon does. This distinction matters when several visually similar controls perform different operations, as in a layout editor with alignment controls for different parts of a document ( Wang et al., 2025c ) .

We design a data-construction agent to supply the missing application knowledge before query generation. Figure 10 illustrates three steps. The agent identifies the application and target, then searches online documentation for candidate functions. It uses the surrounding GUI to select the function that fits the visible context.

In the alignment example, the same-looking alignment symbol could refer to moving objects or formatting text. Matching its documented function resolves what a query can reliably ask the agent to do with the already located control.

This route begins with the same OmniParser-based screen parsing, which provides candidate control boxes and crops while preserving their locations in the original screenshot ( Lu et al., 2024 ) . Given the screenshot and a target crop, the construction agent identifies the application and any visible version information, such as Inkscape 1.3 in panel (a). These details constrain the documentation search to the software in which the control appears, while the crop provides the visual target to match.

Using that application identity, the agent searches online user guides and manuals and extracts illustrated controls with their function descriptions. We keep each illustration with its function description and page context, so that a visually similar icon retains the information needed to interpret its operation. Image-embedding similarity then narrows these references to top- k k candidates ( Radford et al., 2021 ) . Panel (b) shows both parts of this step: the online manual search and the candidate operations retrieved for the target icon.

Visual similarity supplies candidates but can leave the operation ambiguous. The agent therefore compares their descriptions with the full screenshot, neighboring controls, and active tool group. This contextual check matters because similar icons can denote different operations.

In Figure 10 , object alignment and paragraph alignment provide plausible visual candidates. Object alignment moves selected canvas objects to align their left edges, whereas paragraph alignment left-aligns the text within a text object. The visible Align and Distribute panel identifies the relevant tool group, and the selected canvas objects provide complementary evidence for the object-alignment interpretation. The accepted match therefore links a specific function description to the control already located in the screenshot.

Once the function is resolved, we give the accepted description, target crop, and full screenshot to an LLM to generate query variants. One can request the documented operation, such as aligning selected objects along their left edges. Another can identify the same control through its tool group and appearance. All variants inherit the original target coordinate. Thus, application knowledge enriches the query while preserving the common grounding format. The documentation and retrieval candidates remain construction-side evidence, and the resulting samples enter the shared quality checks below.

Both routes produce the same candidate format: a clean screenshot, a query, and a target coordinate. We use two complementary checks before adding a sample to the corpus:

Correctness check. Geometry checks confirm that the point lies inside the annotated control. Multimodal review then checks that the control supports the described operation, the query refers to it, and the description is unambiguous among nearby controls. Documentation-derived examples also carry their accepted function match into this review.

Coverage check. Deduplication removes repeated screenshots and near-identical descriptions. Selection retains useful variation across applications, UI states, control types, and query styles, so that different ways of referring to a control remain represented.

These checks address different reasons a larger candidate pool may fail to provide useful supervision: incorrect target labels and repetitive coverage. Geometry or identity failures return to construction when they can be repaired, while unresolved cases are excluded. Selection then retains accepted examples across interfaces and language styles. Appendix B records the annotation, matching, and curation settings.

The accepted examples enter mid-training as direct localization supervision. Screenshots acquired during multi-step collection can also enrich this pool with states encountered in actual software work. For a desktop base task, we need to connect a supported software operation to material on which it makes sense. Figure 13 illustrates the three steps used to generate the request. We first choose an application and one of its supported functions. That choice establishes the requirements for selecting a compatible source file. The selected file’s content then supplies the facts from which an LLM writes a grounded request. Once the request is defined, we prepare its starting workspace and assessment to form the complete task shown in the lower panel.

Select a function. We begin with E2B templates that provide installed applications and their dependencies for office work, media, file management, browsing, and system settings. Each application has a profile of supported operations and readable file formats. We choose the target application and an eligible operation according to the desired coverage of software and functions. Selecting Calc and filtering, for example, determines both what the eventual request will ask for and what kind of input it needs.

Match a file. To supply these inputs, we collect tens of thousands of files from public and open resources and supplement them with agent-generated materials ( Ge et al., 2026 ) . We index their formats and extract bounded content summaries, including spreadsheet fields and sample values or document text excerpts. With the function selected, we use its format and material requirements to find usable candidates. A spreadsheet-filtering task needs a readable workbook whose fields support a meaningful selection condition. Sampling favors files used less often within the construction run, and the selected files’ summaries become inputs to request generation. For settings tasks, the relevant material is the application preference state instead of a source file.

Write the request. We give an LLM the selected function and file summaries, together with a persona describing the user’s role and motivation ( Jung et al., 2026 ) . The function fixes the operation, and the summaries identify the concrete subjects, fields, and values to which it can be applied. For example, a workbook summary that identifies a Status column containing Pending supports a request such as “Filter the open spreadsheet to show only the pending records and save it.” The filtering condition comes from the workbook, and the persona guides how the user expresses the need.

Assemble CaseSpec . The request now describes feasible work, but the executing agent still needs the corresponding files and application state. To establish this starting point, we specify where the harness should place the selected files in the sandbox, which software template and dependencies to use, and which application or document to open before the first action. In the example, opening the workbook in Calc makes “the open spreadsheet” an unambiguous reference. Tasks involving several files instead identify them by name or workspace-relative path.

The same requested change determines the completion criteria. The workbook should be saved with the pending-record filter applied and all source rows retained. The request, workbook, startup instructions, and required result form one CaseSpec . The same selection therefore supplies the content of the request, the file the agent operates on, and the result to inspect.

Base-task generation connects a function to suitable content. Long-horizon construction extends these local matches into a coherent workflow, especially across applications, by defining how later stages use information or results produced earlier ( Yuan et al., 2026 ; Ge et al., 2026 ) .

Finally, we use this grounded plan to write the request and package the starting workspace and outcome requirements. Plan the workflow. We encode recurring workflows as scenario blueprints , each defining a final deliverable, candidate stages, their applications and materials, and their prerequisites. For the office scenario, a source review, a delivery-record update, and a final document all contribute to preparing the same delivery package.

For each instance, target task length, application coverage, and desired interaction challenges guide the choice of a blueprint and a compatible stage combination. We favor less-used scenarios and components, then use seeded sampling among eligible combinations to vary the work. A combination is retained when its prerequisites are present and every selected stage contributes, through its dependencies, to the overall workflow goal. Operation variants further specify the requested result, such as requiring the PDF’s text to remain searchable.

We represent the selected workflow as a directed acyclic graph (DAG), a planning abstraction also used for cross-device orchestration in UFO3 ( Zhang et al., 2025d ) . Here the graph specifies the task-construction plan. Each node is a work stage, such as inspecting a document for approved content, and may require several GUI actions. Edges can express use of earlier information or artifacts, or a required execution order. We retain the blueprint’s dependencies and, when constructing longer workflows, add precedence between selected stages that use shared facts.

Figure 14 (1) shows an office-delivery example of this planning process. The shared goal is to produce a current delivery package and reconcile its business record. We organize that work into four stages. Source inspection (A) establishes the approved content, which guides the search for obsolete wording in an older deck (B). Record reconciliation (C) can begin independently. The final PDF stage (D) uses the findings from A and B. The blueprint also places the record update before PDF production, shown by the dashed C-to-D edge. This edge specifies workflow order, while the updated record remains a separate deliverable with its own check.

Before preparing the materials, we check the assembled plan for cycles, missing prerequisites, and inconsistent production or use of files. The checked plan associates each stage with its application, required inputs, and expected output, so material preparation can follow the dependencies of the workflow.

Ground the workflow in materials. The DAG specifies what each stage should accomplish, but its nodes still need concrete information to operate on. We ground each node by selecting or generating the files and service records required by that subtask. Existing-file selection follows the same principles as base-task selection, matching application support, file format, and content. Long-horizon construction also considers whether the selected files belong to a shared project or directory and whether their contents support the relationships between stages. File summaries supply the names, values, and other details used to specify stage goals and acceptance conditions.

When the workflow calls for generated materials, we instead choose scenario facts and place them in the files or records the agent will inspect. The office sample follows this path in Figure 14 (2). The approved document supplies a value that the final PDF should include, while the older deck contains obsolete wording that the PDF should exclude. The business record supplies the initial state for a reconciliation update. Each material therefore has a role in both the work stage and its outcome condition. The example requires two results: the PDF and the updated record.

We check that the required information is available through the selected applications and that generated files contain their assigned content. Linking each requirement to its source and its later use keeps the workflow grounded across stages. The output is a task plan with concrete input files, specified initial record values, stage goals, and corresponding outcome criteria.

Create the executable task. With the work and its materials fixed, we use an LLM to write the user request. It receives the user-visible goal, references to the available materials, and required constraints, together with a selected persona and expression style. These choices vary how users describe their work while preserving the constructed task. Facts designated for discovery remain in the workspace for the executing agent to find. The request can ask for a reconciled delivery record and a searchable PDF index without revealing the values or obsolete terms the agent needs to discover. Query checks compare the wording with the task plan, return inconsistencies for revision, and filter semantically duplicate requests.

Outcome assessment checks the requested PDF, record changes, and source preservation. Together with the request, these components form the CaseSpec executed by the harness. The shared task plan keeps the goal, workspace, and assessment aligned as the collection expands to longer, multi-application workflows.

An existing website supplies records and pages that can be read or changed through interface controls. We generate requests from this material in three steps. Examining the content and controls first establishes what work the site supports. We then select a goal involving that content and ask an LLM to express it as a user request. The chosen goal determines the initial records to prepare and the outcome to assess, completing the web task.

We first identify the information visible on the relevant pages and the controls used to access or modify it. On an illustrative task-management site, these include task names, due dates, and status values, together with controls for filtering the task list, opening a task, and changing its status. This combination supports requests to find tasks with particular properties and apply a corresponding update.

Using this account of the site, we select conditions that match records in the starting data and an operation available through the interface. We then use an LLM to express the grounded goal as a user request, for example: “Mark tasks due before 1 September 2026 that are still In progress as Needs follow-up.” The due dates and current statuses determine which tasks qualify, and the status control provides the requested operation. Other requests use different items, conditions, and available actions to cover information retrieval, comparison, and form filling.

The generated request determines which initial state to prepare and which result to assess. We record its entry page, startup instructions to open that page in the browser, and any setup needed to make the selected records available. In the example, the starting records establish which task identifiers satisfy the date and status conditions. Outcome assessment checks the updated status of those same tasks after execution. Keeping their identities tied to the starting data lets the check follow the requested items even after their status changes.

The next route starts with an existing request or reference website and builds the workspace needed to support it.

Scaling Intents uses the workspaces already available to generate new requests. Sourced requests offer a complementary resource: they describe useful work, but often omit the files, dependencies, or application state needed to execute it. Reference websites and software issues likewise describe interactions without necessarily providing an isolated environment for collection. We design Scaling Environments to build these missing execution conditions. For desktop requests, this means preparing the files and applications assumed by the user. For Web tasks, we collect open-source frontends and reconstruct workflows from public URLs to create local environments that we can initialize and reuse. We also develop repository-based frontend testing as a distinct web-agent application, where a runnable project lets browser interaction test a candidate code repair.

Forums contain user-reported software problems, while tutorials and help resources describe practical workflows and their intended results ( Wang et al., 2025b ) . These sources provide goals grounded in software use, but their descriptions often assume attachments or workspace state that the collector does not have. We collect tens of thousands of such requests and task seeds from forums, wikiHow, and help resources. The construction problem is then to supply the inputs and startup conditions each seed assumes while preserving the work it asks the agent to do.

We therefore design an environment-building agent, EnvAgent, to interpret each request and prepare its input files and startup plan. Figure 15 illustrates three construction steps. The agent first retrieves and reads candidate files to establish which requirements are already supported. Any missing inputs then guide file generation, using the retrieved material to keep related records consistent. With the inputs available, the agent specifies the request and startup plan and checks that they agree. A failed check returns the affected input or instruction for revision before the package becomes a CaseSpec . Together, these routes expand environment supply from user requests, reference websites, and runnable software projects. Their prepared workspaces support experience collection, and reconstructed sites also feed new task generation through Scaling Intents. Tasks equipped with reliable executable verifiers offer a further route to expansion: the next section uses their goals and outcome checks as seeds for additional task construction.

Task datasets and manually authored cases provide user goals already paired with executable verifiers. A reliable verifier makes the intended outcome explicit and supplies a repeatable check on collected trajectories. Creating additional checks is costly, however, because each needs to match its task and distinguish correct results from plausible mistakes. We design Scaling Verifiers to expand this resource by adapting existing task–verifier pairs ( Wang et al., 2026a ; Lv et al., 2026 ) .

Figure 19 illustrates the construction and validation phases. We first use a seed’s goal and success conditions to construct related tasks, changing the request, initial state, and verifier together. The new pair then undergoes a GUI execution trial and tests of the verifier’s judgments. Their findings guide repairs before the pair enters collection.

This joint treatment matters because changing a request’s selection criterion also changes which records the verifier should accept as updated and which it should require to remain intact.

The construction agent reads the seed request, initialization, and verifier to identify useful subgoals, their prerequisites, and the observable changes that establish success. A subgoal can involve several GUI actions, such as editing a document and exporting the result. We use these subgoals in three different ways. Decomposition extracts a meaningful part of the seed task. Variation changes the condition or operation while retaining its basic structure. Composition connects subgoals into a longer workflow, whose later work uses earlier results. The approval example in Figure 19 shows the effect of each choice on the requested work and the corresponding outcome checks.

Figure 19: Expanding tasks and their verifiers together. The agent extracts a subtask, changes a selection criterion, or joins approval with export, adapting completion and preservation checks to the new task. The lower composition example separates a GUI execution trial from verifier tests on prepared outcomes. The verdict column gives the requirement-derived response for each probe. Testing checks whether the verifier returns it. The task lists, generated GUI views, and hypothetical judgments illustrate the construction procedure. The ellipsis omits intervening GUI actions, including export. Initial-state preparation and repair iterations are not shown.

Decomposition turns a meaningful part of the workflow into a task of its own. Extracting record selection yields a request to identify the qualifying records, an initial state containing the required data, and a verifier for the returned selection and preservation of all records.

Variation changes the materials, parameters, or operations. A new selection criterion leads to a new target set derived from the corresponding input records. The request and verifier are updated to express and assess that change.

Composition joins compatible subgoals through their inputs and outputs. Adding a summary export to an approval task makes the approved identifiers the contents of the later file. The adapted verifier checks the updates, the exported summary, and preservation of the records the request protects. The added dependency can produce a more demanding multi-stage task.

Across these changes, the agent resolves the actual identifiers and file references used by the request, environment, and verifier. In the composition example, the targets established during selection remain the targets during assessment, even when the update changes a field used for selection. Desktop compositions carry the same relationship through documents and intermediate files. Requirements that matter during a stage are checked there, while final-state requirements are assessed at completion.

Each rewritten task undergoes two complementary checks before collection. A GUI trial examines whether an agent can carry out the request from the prepared state. Verifier probes examine whether the checker judges known outcomes as the task requires. The lower part of Figure 19 keeps these two sources of evidence separate.

For the execution trial, we run a CUA from the declared initial state with the rewritten request. Its interaction and resulting state reveal problems such as missing inputs, unreachable controls, or instructions inconsistent with the workspace. These findings identify which setup or request needs repair.

To test the verifier itself, we construct outcome probes whose expected verdicts follow from the request and starting data, then compare those verdicts with the verifier’s outputs. In the approval-and-export example, a complete result should pass, whereas an otherwise correct update without the required export should fail. Additional probes isolate incomplete updates, changes to protected records, and allowed alternative outputs. A disagreement identifies a checker rule to revise, even when the GUI task itself can be completed.

We collect trial failures and verifier disagreements into a construction report. Setup and instruction failures return to task construction, while incorrect verdicts return to the verifier. After the revision, we rerun the affected tests against the same intended requirements before admitting the pair to collection. Requirements that need contextual judgment use the evaluator in Section 3.3 . This feedback loop keeps task expansion connected to executable conditions and meaningful outcome assessment.

The three construction routes supply tasks to the shared collection service (Section 3.4 ). Executing these tasks produces trajectories and outcome assessments. Obtaining successful experience from the hardest tasks introduces the next challenge.

The routes in Section 4.2 supply executable tasks whose rollouts provide experience for learning. During collection, however, we encounter long and difficult tasks that remain unsolved within the ordinary budget. Collecting demonstrations of sustained planning and recovery from these tasks requires addressing two recurring obstacles. Repeated attempts can lose useful discoveries and repeat ineffective procedures. A late failure can also force a new attempt to rebuild substantial earlier work.

We design two recursive self-improvement (RSI) pipelines for collecting experience from these tasks. Each carries forward the information needed to address one of these obstacles.

Knowledge accumulation. Skill-guided recursive exploration turns trial-and-error findings into tested procedures that guide subsequent attempts (Figure 20 ).

Progress accumulation. Milestone-guided trajectory search preserves completed work and resumes exploration from the corresponding software state and agent context (Figure 21 ).

Both use feedback from earlier trials to shape later exploration ( Zhu et al., 2026 ) . They target tasks that pass construction checks but remain unsuccessful in ordinary collection. The original acceptance conditions stay fixed. We check the completed task before admitting an assisted trajectory as a full-task demonstration. Milestone-guided collection can also retain verified subtask traces from attempts that leave the full task unfinished.

Some GUI tasks require a procedure that the agent has not discovered. The difficulty may be an unfamiliar application command, a hidden prerequisite, or a sequence whose useful effect becomes clear only after trying it and inspecting the result. Repeated attempts can make partial discoveries, but those discoveries remain scattered across their histories unless the collector carries them forward. We therefore need a way to turn trial-and-error experience into reusable operating guidance.

We design a skill-guided loop with four stages, shown in Figure 20 . Task-directed exploration first produces observations about useful operations and unresolved obstacles. A skill creator then reviews that experience and consolidates actionable findings into written guidance. A separate agent tests the candidate instructions before they are supplied to a new task attempt. That attempt can use the validated procedure to make further progress, and its new discoveries feed the next round of skill refinement. The loop accumulates tested knowledge across attempts while retaining full-task verification for the final result.

Further exploration yields a text-preserving procedure. An agent follows its fixed instructions in a separate trial and searches the resulting PDF. The validated skill then guides a new attempt in the original workspace, where full-task checks determine trajectory acceptance. The return arrow depicts a failed task attempt, while failed validation also prompts revision. Accepted trajectories retain the supplied skill in context. GUI scenes, controls, actions, and outcomes are illustrative, with intermediate exploratory trials omitted.

We use a computer-use agent to attempt the original query in its prepared workspace. It inspects the relevant applications and files, tries controls, and adjusts its action sequence as it observes their effects. An unsuccessful attempt can still reveal an important prerequisite, an ineffective action to avoid, or a way to reach a previously inaccessible state. Successful operations likewise show procedures worth retaining. We examine these findings in the trajectory and result, using evaluator observations of the live state to help identify the remaining obstacle (Section 3.3 ) ( Shinn et al., 2023 ) .

In the representative report workflow in Figure 20 , exploration may reveal several export options. One trial produces a PDF with all the required pages but represents their text as an image. The searchability check then focuses further trials on which export settings preserve text. The initial exploration has thus turned a broad completion goal into a specific procedural question that can be tested in the application.

The skill creator reviews the accumulated trajectories and their outcomes. When the useful procedure is still unclear, further exploration or focused practice tests alternative operations. The creator turns the resulting findings into textual guidance that states when the procedure applies, which actions to take, and how to check its intended effect ( Wang et al., 2024 ; Wang et al., 2026c ) . For the PDF example, this means recording the text-preserving export settings and a search check, together with the image-only choice to avoid. The candidate gives later attempts a concrete procedure and the relevant pitfall.

Guidance inferred from exploratory trials may omit a prerequisite or misidentify why an operation worked. We therefore freeze the candidate and give it to a separate agent in an independent validation trial. The agent applies the instructions and checks their claimed effect in the environment.

In the PDF example, it exports using the specified settings and searches for a phrase from the source document. Finding the phrase establishes the intended effect of this skill, while a failed check returns the instructions to exploration and revision. The revised candidate is tested again before admission for reuse.

We provide the validated guidance to a new attempt at the original task. The agent can now use the tested procedure when it reaches the relevant operation. If it encounters another obstacle, or discovers a useful way to complete a later stage, that experience feeds the same consolidation and validation loop. Previously validated skills remain available, so each round can build on what earlier attempts established.

The process continues until an attempt satisfies the original task’s full acceptance conditions or the exploration budget is exhausted. Accepted attempts supply trajectories with the actual guidance retained in their decision context. The skill library also makes a tested procedure available to later tasks that meet its applicability conditions. This accumulation is designed to improve hard-task collection by carrying useful knowledge between attempts. The TERRA dashboard case in Section 4.3.3 follows how a charting problem becomes revised guidance that a fresh attempt applies (Figure 22 ).

For a long workflow, however, even a better-informed attempt can spend substantial effort repeating earlier work. The next pipeline addresses that remaining cost by retaining execution progress.

A long task can be difficult to finish in a single attempt even when its individual stages are within the agent’s reach. When a late failure ends an attempt, restarting from the initial state repeats work already completed. This motivates a second RSI strategy in which collection focuses on smaller, verifiable goals and retains the work that reaches them.

We design milestone-guided trajectory search to implement this strategy. We first decompose the original task into dependent milestones and their checks. GUI attempts then work toward one milestone at a time, saving the workspace and agent context when a check passes. Further attempts restore that checkpoint to explore the next stage, following the principle of returning to useful states for exploration ( Ecoffet et al., 2021 ) . After the final milestone, the original verifier checks the complete result before the selected path becomes a full-task demonstration. Figure 21 illustrates how this process builds successful continuations on retained progress. It reduces the work each trial needs to repeat while keeping acceptance tied to the original task. A construction case in Section 4.3.3 follows this accumulation of progress from an empty Blender scene to a complete collected trajectory (Figure 23 ).

We use a planning agent to read the user request and the original verifier code, identify dependencies, and propose meaningful intermediate goals. Each milestone pairs a subtask with a check on its observable result. The goal should represent useful progress and leave a state from which later work can continue. Reviewing the pairs against the original requirements ensures that local checks support the intended full task. This uses the decomposition principle in Section 4.2.3 , here to guide collection within one long task.

For the office workflow in Figure 21 , the original goal includes updating a business record and producing a searchable PDF. We organize it into three milestones: complete the record update (M1), prepare the report (M2), and export the searchable PDF (M3). Their checks inspect the corresponding records, document content, and output file. The executing agent receives the permitted subtask guidance, while private verifier constants remain in the checking context.

The harness supplies the first subtask to a computer-use agent in the initial workspace and runs repeated attempts within the collection budget. When an attempt passes the milestone check, we save an E2B workspace snapshot together with the agent context about completed work, useful findings, and remaining goals. Restoring both gives the next attempt a consistent starting point for the following milestone (Section 3.2 ). We retain the full interaction prefix alongside the bounded decision context and can keep several passing states to support different continuations.

Retained checkpoints form the nodes of a search tree, and GUI action sequences toward the next milestone form its branches. Each continuation restores its parent checkpoint in an isolated instance, observes the interface, and attempts the next stage. Passing results become checkpoints for the next milestone. If a continuation stalls or fails its check, its parent remains available so that a new attempt can try a different sequence without replaying the earlier stages.

We can also retain selected recoverable failed states for further exploration. These states keep their unresolved milestone labels. A continuation attempts the necessary correction before advancing to later goals, allowing the collected path to include genuine recovery from an earlier mistake. Thus the tree can support both alternative attempts from verified progress and recovery attempts from a useful but incomplete state.

In Figure 21 , branches A and C fail the export requirement, while B produces a searchable PDF. All three begin at M2, retaining the same earlier record update and report preparation. A failed export can also trigger the skill exploration described above, whose validated guidance can be used by a new continuation. The saved checkpoint preserves the work already done, and the skill helps the agent choose how to perform the unresolved operation.

After the final milestone, the original task verifier assesses candidate completions against all requirements, including those established in earlier stages. For the office task, it checks the PDF, the required record update, and source preservation. Search continues until a branch passes this final check or the budget is exhausted. A passing branch yields a search-assisted trajectory : the actual parent–child path from the initial state to completion, combining its retained prefix with the selected continuations. It keeps the path’s observations, actions, and supplied guidance, including mistakes followed by recovery. Failed sibling branches remain exploration records and are not spliced into the accepted trajectory.

If an attempt completes only part of the milestone sequence, we retain only the trace portions associated with passed milestones as subtask-level demonstrations, preserving their original decision context. This recovers useful supervision from unfinished attempts and makes fuller use of the collection budget.

The Experience Library assembled by the Experience Flywheel provides quality-selected demonstrations of software work, alongside grounding examples and executable tasks for further collection (Section 4 ). The next step is to turn these resources into a policy that can reason about interfaces and carry out user goals across desktop and web applications. We design a three-stage learning pipeline that develops this capability progressively, as outlined in Figure 2 .

Broad GUI mid-training first establishes familiarity with controls, application functions, and their effects through diverse software experience.

Verified long-horizon SFT builds on that foundation and concentrates learning on high-quality demonstrations that carry dependent work to completion.

Joint desktop–web agentic reinforcement learning then lets the policy learn from its own decisions and their outcomes in interactive environments.

Each stage uses the preceding policy as its starting point while changing the learning emphasis, from operational breadth to sustained completion and then outcome-driven improvement.

Computer-use agents encounter many applications, interface layouts, and ways of performing similar operations. To work across these settings, a policy needs experience recognizing controls, interpreting their functions, and observing how actions change software state. We use broad GUI mid-training to build this foundation from diverse demonstrations ( Wang et al., 2025c ; Jung et al., 2026 ) .

Through the collection routes in the Experience Flywheel , the reported broad task corpus contains over 100,000 trajectories and over 4 million GUI interaction steps, spanning dozens of applications and hundreds of operation families. This range exposes the policy to different tasks, materials, and interfaces within and across applications. We complement the trajectories with approximately 40,000 single-step grounding examples to train spatial recognition and control localization directly. The following collection and selection choices determine what experience enters this mixture.

We select commonly used desktop applications and organize their functions into operation families. These profiles guide the task requests and CaseSpec environments used for experience collection, making it possible to vary the operations demonstrated within each application. Sampling across applications and operations, together with variation in source files and user goals, broadens this coverage. Representative coverage in the application profiles and workflow templates includes:

Office work. Calc tasks cover formulas, auditing and reconciliation, filtering, pivot tables, and print layout. Writer adds document formatting and annotation, while Impress covers slide composition, content insertion, styling, and synthesis of source material into presentations.

Visual and media work. GIMP tasks include cropping, resizing, annotation, and export. Inkscape adds vector text, color, alignment, and grouping operations. Image viewers, PDF viewers, and VLC provide content inspection and playback tasks.

Workspace and information management. File-manager tasks cover organization and batch processing. Thunderbird, browsers, and VS Code add message handling, browser configuration, information lookup, and GUI-based file editing.

CAD and 3D workflows. Expanded workflow templates define model review and part design in FreeCAD and SolveSpace, together with scene organization in Blender.

Medical-image and anatomy visualization. 3D Slicer scenarios cover inspecting image volumes, checking orientation, annotating landmarks, and saving review scenes.

To extend this coverage beyond individual functions, we also use the long-workflow construction in Section 4.2.1 . Its dependent tasks provide experience combining operations, carrying information between applications, and maintaining progress toward a shared deliverable. Mid-training therefore includes sustained workflows as part of its broad foundation, before the next stage concentrates on selected verified examples.

We further enrich web experience with (1) information retrieval, (2) form filling, (3) human-verification flows, and (4) frontend testing. Retrieval and form filling represent common everyday uses of websites. Human-verification flows add visually conditioned interactions encountered during web use, while frontend testing exercises the effects of controls and the persistence of state changes. Together, these settings diversify both what users ask and how an agent must interact, complementing desktop operation with web-specific workflows. The web scenario library also provides browser-game and sliding-puzzle tasks. Grounding examples add direct practice locating the requested control, including specialized controls handled by the documentation-guided route in Section 4.1 . Broad coverage is useful for learning only when the collected behavior provides a worthwhile demonstration. Large-scale attempts can also leave tasks incomplete or spend many actions without progress. We therefore use the agent-as-a-judge evaluator in Section 3.3 to inspect each candidate’s requested outcome, trajectory, and resulting artifacts or state ( Zhuge et al., 2025 ) . Its assessment selects completed work with useful execution behavior for the training corpus. This selection limits the inclusion of incomplete or low-quality traces while preserving examples of successful software use across the coverage pool.

Among the trajectories that pass review, selection preserves broad application and operation coverage. Meaningful exploration and recovery remain part of this experience when they lead to completed work, giving the model examples of how actions and subsequent observations inform the next decision. Outcome-based filtering thus makes quality control part of building a large and varied training corpus.

The selected mixture teaches both where to act and how to continue a task. For grounding examples, the model predicts the target control’s coordinates from the request and screenshot ( Cheng et al., 2024 ; Lu et al., 2024 ) . Trajectories train the model to predict each recorded assistant response from the task and the observations and history available at that decision. Targets include recorded reasoning, text responses, and action tool calls, while screenshots and tool results provide context. This response-level objective connects interpreting the interface, deciding what to do, and issuing the operation.

We also include evaluator trajectories as a separate judgment-task source. These examples condition the model on the evaluator’s inspection context and train its recorded assessment responses, providing demonstrations of how to check an outcome and support a judgment with evidence. Actor demonstrations retain their original decision-time context, separate from these evaluation inputs. The evaluator therefore serves two distinct purposes in mid-training: its reports select task demonstrations, and its own trajectories teach assessment. Appendix E.1 distinguishes the sample types and their response targets.

Through this broad mixture, mid-training develops familiarity with diverse GUI functions, action effects, and ways of interpreting results. This provides the operational foundation for learning more demanding workflows. The next stage sharpens that foundation using a concentrated set of high-quality, verified long-horizon demonstrations.

Mid-training gives the policy broad experience operating software, including extended workflows. Sustaining correct work over a long and difficult task requires a more concentrated learning signal: later decisions need to use earlier findings, preserve constraints, and complete the final deliverable. We therefore continue from the mid-trained checkpoint with supervised fine-tuning on selected long-horizon trajectories whose complete outcomes pass executable task verifiers ( Yuan et al., 2026 ; Lu et al., 2026 ) . The cohort contains approximately 3,000 trajectories and 310,000 GUI interaction steps.

We start with tasks and executable checks supplied by Scaling Verifiers (Section 4.2.3 ) and collect successful completions. For difficult tasks that ordinary attempts do not solve, the skill-guided and milestone-guided RSI routes in Section 4.3 provide additional ways to obtain candidate demonstrations. Skills carry useful operating knowledge between attempts, while retained checkpoints let exploration build on completed intermediate work. In either route, a candidate enters this stage only after its final result passes the original task verifier. Appendix D lists the source contributions that remain to be reported separately from this aggregate cohort.

Within this accepted pool, we prioritize difficult workflows with long-range dependencies while maintaining application diversity. We use length to identify sustained work, then inspect how later actions use earlier results to assess its dependencies. We then check whether these demonstrations provide usable training sequences. Data cleaning rejects unusable records and traces with malformed or unmatched tool calls or unproductive loops. This screening retains coherent recovery when the trace shows an error, its correction, and verified completion. Each retained trace keeps its original action–observation sequence, preserving the context needed to learn that recovery. These checks combine programmatic outcome acceptance with demonstrations of purposeful work across stages.

With this selected corpus, we fine-tune the mid-trained policy to predict the recorded assistant responses from the request and decision-time context. The objective remains response prediction, but the data now emphasize maintaining task state, using intermediate results, coordinating work across applications, and recovering without losing the original goal. For assisted demonstrations, any supplied skill or milestone guidance remains in the context under which the recorded response was produced. Representation and sampling requirements are described in Appendix E.1 .

This stage strengthens sustained task execution on top of the broad operational foundation. The resulting policy is the starting point for autonomous rollouts, where its own choices can create states absent from the demonstrations. Reinforcement learning provides the next learning signal by connecting those choices to their task outcomes.

Mid-training and long-horizon SFT provide a policy that can recognize interfaces and follow demonstrated workflows. To develop its ability further, we let it learn from autonomous interaction. Its own choices determine which states it encounters, and task outcomes provide feedback on whether those choices accomplish the user’s goal. We use agentic reinforcement learning to connect this fresh experience to policy improvement ( Qi et al., 2025 ; Lai et al., 2026 ) .

We train a single policy jointly on desktop and web tasks. The shared runtime in the NorthCUA Harness already expresses both as repeated observation, reasoning, and tool-based action, making it natural to learn from them through one training loop. Platform-specific observations and tools retain the differences needed to operate each interface. Task-specific verifiers then provide outcome feedback for the work performed in either domain.

Figure 24 follows an attempt from task preparation to a policy update. The Task and Environment Manager selects executable cases and prepares their isolated workspaces and verifiers, giving NorthCUA Rollout Workers the conditions needed to act with the current policy. Once those attempts have been recorded and scored, the Experience Adapter pairs the model calls with their task outcomes to construct training samples. These task-grouped samples let the Policy Learner compare alternative attempts with GRPO and update the shared policy ( Shao et al., 2024 ; Zhu et al., 2025 ) . Returning the new weights to the workers closes the loop, so subsequent interaction uses the updated model. The following subsections explain how we select useful tasks, obtain comparable feedback, and preserve executed decisions as that feedback enters learning.

GRPO obtains its task-level learning signal by comparing the rewards of multiple attempts at the same task. An attempt’s relative outcome determines its advantage within that group. If all valid attempts receive the same terminal reward, their terminal group-relative advantages are zero. Since GUI rollouts are costly, we first identify tasks on which the SFT policy produces different outcomes, so initial collection can provide informative comparisons.

For each model, the Task and Environment Manager starts from human-reviewed desktop and web tasks associated with its SFT data. For each candidate case, we collect at least five rollouts under the SFT checkpoint with fixed task and execution settings. The task verifier scores each attempt’s outcome, and we select cases with variation among these valid verifier scores. Valid task outcomes determine this selection, while environment and verifier errors are recorded separately. This focuses RL collection on tasks where outcome feedback distinguishes alternative executions.

The selected cases form the initial RL task pool. Fresh grouped attempts supply the subsequent learning data. Appendix E.2 describes the screening protocol and the fields needed to record valid repeats and the selection rule for each run.

With the task pool selected, we generate fresh attempts and turn their outcomes into the comparisons used by GRPO. For each case, the manager first establishes equivalent starting conditions. Workers then act in those environments, and the task verifier assesses each completed attempt. The recorded decisions and outcome are converted into samples for policy learning.

The Task and Environment Manager prepares a separate E2B sandbox for each attempt in a task group. All members receive the same request, initial files and application state, verifier, and execution budget. Their sandboxes are isolated, so one attempt’s edits do not change another’s starting conditions. This makes differences in outcomes interpretable as alternative executions of the same task.

NorthCUA Rollout Workers use the policy to carry out each multi-turn attempt. Desktop and web execution follow the same runtime loop, using their respective screen or browser observations and allowed tools. After execution, the manager runs the task verifier on the resulting workspace. Its valid verdict supplies the complete attempt’s terminal reward. Both successful and unsuccessful attempts contribute to the comparison, while setup or evaluation errors follow the separate invalid-attempt path.

The Experience Adapter binds each outcome to the model calls from that attempt. It reconstructs training samples from the recorded multimodal inputs and responses, retains behavior-policy likelihoods and versions, and marks which response tokens are learning targets. Each sample keeps its task and attempt identity so that the Policy Learner can compute relative advantages within the correct task group and apply the GRPO update. Desktop and web groups contribute to the same shared policy through this procedure.

This completes the path from an executable case to outcome-driven learning. For long GUI attempts, however, converting the record into training samples requires additional care. The next subsection explains the two rules we use to preserve both the original decision conditions and the attempt’s learning contribution during that conversion.

The rollout procedure provides complete attempts and their outcomes, but the learner must also preserve the conditions under which each decision was made. Our harness maintains a sliding window of recent screenshots and can compact earlier history. As a task proceeds, an image may leave the window or a summary may replace earlier messages. Using only the final history to train every response would therefore change the evidence available to some decisions. Preserving the sampled input is also a central concern in harnessed agentic RL ( He et al., 2026 ) .

To accommodate this context management, we design the Experience Adapter around two preservation rules. First, each response is learned with its recorded decision-time input, starting a new training segment when the history no longer extends consistently. Second, those segments retain the reward attribution and learning weight of their original complete attempt. This matters because frequent context changes can split one attempt into more segments than another. Figure 25 illustrates input preservation in panel (a) and attempt-level comparison and aggregation in panel (b). Together, the two rules let the harness manage long histories without turning a representation change into a different learning problem.

Training associates each response with the context that produced it. To preserve this association through context changes, we capture each model call’s input, delivered response, generation log-probabilities, and behavior-policy version. The adapter joins consecutive calls only when their text and ordered image histories form a confirmed prefix extension under the same version. Image identity includes its content digest, so replacing a clean frame with the historical action overlay from Section 3.2.1 also breaks this prefix. The adapter starts a new segment from the captured input whenever images are replaced or evicted, a summary rewrites history, or the behavior version changes.

Earlier responses can still appear as history in a later segment, but they serve only as context there, following the history-masking principle used in ScaleCUA ( Lv et al., 2026 ) . Response masks assign each learning target to its original occurrence. Save is supervised when first generated and serves as context for Finish. This construction lets the learner use the harness’s actual decision conditions while keeping only new responses as targets. Appendix E specifies processor alignment and masks.

Preserving inputs can produce different numbers and lengths of segments across attempts. If these segments were treated as separate reward-bearing attempts, more frequent context changes would alter the group comparison. Averaging segment losses independently would also give an attempt more weight simply because it was split more often. Neither change reflects additional task experience.

We therefore retain the complete attempt as the comparison unit. GRPO computes its relative advantage once, and all of its segments receive that same value. In Figure 25 b, the two segments of attempt 1 share A 1 A_{1} , while attempt 2 receives A 2 A_{2} . Loss aggregation then preserves the same unit. In the supported trajectory-mean configuration, we use the trajectory-level normalization also adopted in Qwen-CUA ( Lu et al., 2026 ) . We sum the masked policy losses over all target tokens of an attempt, divide by its total target-token count, and average these per-attempt means:

All segments of an attempt enter the same optimizer step, so the denominator covers the complete attempt across microbatches. Appendix E defines the reduction and the run-specific optimization fields. This normalization prevents segmentation alone from increasing an attempt’s contribution when its target tokens and losses are unchanged. Combined with decision-time input preservation, it allows one continuous execution to yield several training segments without creating extra reward comparisons or increasing the attempt’s weight in the policy loss.

Training from long GUI rollouts is costly even after the samples are correctly constructed. Overlapping screenshot windows repeat visual preprocessing and carry large tensors to the learner. Meanwhile, task durations vary, so waiting for every active task before updating the policy can delay the next learning cycle. We address these two costs separately: visual-delivery mechanisms reduce redundant input preparation and transfer, while asynchronous coordination lets policy updates proceed without restarting ongoing tasks.

Adjacent decision windows often contain unchanged screenshots. Processing every window from scratch repeats work on those images. For a supported per-image processor, the Experience Adapter therefore reuses the preprocessing tensors of unchanged images within an attempt and processes only new images. It reconstructs the requested image order under the same processor settings. Changed images or settings require fresh processing. The reuse saves CPU preprocessing while retaining every image in the model input. The neural visual encoder still processes the complete visual input.

Large image tensors also add delivery cost after preprocessing. The object-store path supports lossless tensor compression, retaining a compressed payload only when it is smaller. The learner decodes the microbatch it is about to consume, recovering the same values, shape, and type. Bounded CPU workers prepare samples, and group admission counts completed work awaiting delivery so that preparation does not create an unaccounted queue. These mechanisms target redundant processing and payload transfer while preserving the sample’s contents. Appendix E.4 describes the implemented reuse and transport paths, their configuration, and the checks used to assess sample equivalence and delivery cost.

In asynchronous mode, completed groups can supply the learner while other workspaces remain active. To publish an update, the system pauses new model calls, waits for calls already in progress, commits the new weights, and resumes calls. Ongoing tasks keep their workspace and completed work, so later decisions can use the updated policy.

The captured behavior version and generation probabilities identify the policy that produced each response. A version change starts a new segment, so each policy ratio uses the corresponding behavior probabilities. For attempts spanning several versions, the clipped objective is an off-policy approximation. Preserving the recorded inputs keeps the sampled decisions identifiable, while policy lag affects the resulting update. Appendix E.2 defines policy lag and mixed-version attempts and distinguishes asynchronous coordination from synchronous collection. This coordination lets learning continue while ongoing tasks retain their environments and completed work.

Together, these mechanisms address the cost of supplying visual experience and coordinating updates, while the preceding preservation rules keep learning tied to the executed decisions and complete task outcomes. Our evaluation follows the progression from identifying a control to completing a software task. We first compare grounding, desktop, and Web performance, then examine how results change through long-horizon SFT and joint desktop–Web RL. Trace analyses and selected cases connect these scores to concrete decisions, while an engineering profile measures the cost of delivering visual experience to the learner. Finally, we study NorthCUA-Ultrafast to assess how direct action selection changes the balance between task success and execution latency.

Reliable grounding also requires recognizing when a requested target is absent. OSWorld-G tests this distinction alongside visible-target localization. Across three draws, Pro averages 91.7% on the 510 visible-target items, compared with Mini’s 88.6%. Its correct-refusal rate reaches 75.9% on the 54 absent-target items, compared with Mini’s 74.1% (Table 7 ). The larger gain is therefore in locating visible controls, while recognizing when to decline a location request remains harder across all three tiers. This distinction matters when a predicted coordinate becomes an agent’s next action.

Repeated sampling then reveals whether correct predictions persist across draws. Pro is correct in all three draws on 489 of 564 items, compared with 469 for Mini and 445 for Nano. Its pass@3 reaches 94.0%, covering 530 items, while its three complete runs range from 89.4% to 91.0%. Pro also succeeds at least once on 36 of Mini’s 53 persistently missed items, including 26 that Pro gets right in every draw. Thus, its stronger aggregate result accompanies both more stable successes and coverage of additional difficult items.

Completing a user request and detecting defects require different judgments. Given these test items, the agent must exercise the application and distinguish genuine defects from correctly implemented behavior. Table 11 reports task-averaged precision, recall, and F1. Long computer-use tasks accumulate the latency of many successive model decisions. Some decisions require open-ended content, but others reduce to choosing an operation and a control already present on the page. Predicting these finite choices directly could remove the decoding cost of routine actions. Jev provides a relevant interface for this purpose by answering structured choice questions without generating their answers token by token ( Almeida, 2026 ) . We adapt this idea to NorthCUA -Nano through NorthCUA -Ultrafast, which combines a choice head for finite decisions with the original model’s generation path for open-ended outputs.

Figure 32: Choice-based Web execution. The input shows the title before editing. Generated GUI views illustrate filling the new title (right) and a subsequent Save click (left). At each decision, current controls support operation and target selection. A direct choice executes without decoding, while a generation route triggers a second full-model call with the original prompt and a fresh cache. Optional LoRA adapters are active only for classification. Route and target checks are omitted.

Figure 32 illustrates the resulting division of work. The classifier receives the task and recorded interaction history, including page observations, screenshots, and action overlays. Candidate controls are bound to the latest valid page observation for execution. One backbone forward pass supplies the features used to score the operation and its applicable targets. A selected click, hover, or checkbox change can then be converted directly into a tool call.

Filling a field additionally requires text, so it triggers a new call using the original model prompt and generation head. Other tool actions and final responses use the same generation path. The executor validates the returned tool and arguments, and uncertain finite choices can fall back to native generation. This preserves the original output interface while allowing routine finite actions to bypass decoding. Appendix E.7.4 specifies the routing and validation profiles.

We study how much adaptation this choice interface requires, starting from the long-horizon-SFT NorthCUA -Nano checkpoint before joint RL. Following Valen’s head-training approach ( Liuziyu77, 2026 ) , Head-only freezes all original weights and trains a 4.21M-parameter choice head, about 0.045% of the complete multimodal checkpoint. Head + LoRA also trains low-rank updates in the language layers ( Hu et al., 2022 ) , bringing the trainable total to 47.49M parameters. These adapters are enabled for classification and disabled for native generation, which keeps the original generator common to both variants. Both use about 226,000 training decision states, with fixed validation and test sets of 5,203 and 6,087 states. Supervision covers the recorded operation and its required target. Appendix E.7 gives the readout, training objective, and recipe.

We first evaluate whether the choice interface retains the recorded decisions. Head-only and Head + LoRA reach validation route-and-target accuracies of 86.1% and 88.2%, respectively. On the held-out test set, Head-only reaches 85.4% route-and-target accuracy against Full generation’s 85.0%, while their full-action exact-match scores are 64.0% and 64.6%. Generated parameters account for much of the remaining full-action error. The LoRA result is a validation comparison. Appendix E.7 gives the separate metrics and checkpoint-selection details.

NorthCUA connects computer-use learning with the tasks and execution systems that supply its experience. We review these foundations in three parts. We first discuss policies and learning methods, then the construction of tasks and experience, and finally the harnesses and infrastructure that support their collection and use in training.

Accurate GUI actions depend on linking instructions to screen elements. SeeClick studies grounding pre-training ( Cheng et al., 2024 ) . GUI-Actor develops attention-based pointing, while GUI-Cursor refines cursor movements through visual feedback ( Wu et al., 2025 ; Zhao et al., 2026 ) . End-to-end policies build on this capability to coordinate actions over time. UI-TARS integrates perception, reasoning, and action prediction, and OpenCUA develops reflective supervision from human demonstrations ( Qin et al., 2025 ; Wang et al., 2025c ) . Learning from outcomes offers a further source of improvement. ComputerRL scales live-desktop RL ( Lai et al., 2026 ) , while VEM learns offline value estimates to guide environment-free policy exploration ( Chen et al., 2026b ) . UI-TARS-2 and Qwen-CUA connect staged training with interactive learning ( Wang et al., 2025a ; Lu et al., 2026 ) . For long trajectories, learning methods also specify how history and outcome feedback are carried across training segments. ScaleCUA masks reused history and shares rollout rewards and advantages across segments ( Lv et al., 2026 ) . Qwen-CUA preserves episode credit across slices and normalizes each trajectory’s objective over active policy tokens ( Lu et al., 2026 ) . NorthCUA combines broad GUI mid-training, verified long-horizon SFT, and joint desktop–web RL. Our emphasis is on integrating decision-time input preservation and complete-attempt weighting with the Harness and experience-production pipeline.

Scaling workflow learning creates a corresponding demand for executable tasks and reliable outcomes. OS-Genesis derives tasks from exploratory interaction ( Sun et al., 2025 ) , while GUI-360 combines sourced requests, environment templates, execution, and filtering for Windows data collection ( Mu et al., 2025 ) . ProCUA-SFT grounds tasks in real materials and checks preconditions before rollout ( Jung et al., 2026 ) . For outcome-driven learning, CUA-Gym and Qwen-UI-Agent synthesize compatible tasks, initial states, and verifiers ( Wang et al., 2026a ; Zhou et al., 2026b ) . WEFT extends this whole-system view to tool-use post-training, using execution feedback to revise interacting components and fresh rollouts to evaluate each revision ( Mao et al., 2026 ) . NorthCUA organizes construction around available software and content, sourced requests, or verified seed tasks. Each route produces an executable CaseSpec . A separate grounding route uses application documentation to identify control functions and construct screenshot–query–location supervision.

Hard tasks also motivate retaining procedural knowledge across executions. Work2Skill turns synchronized human GUI demonstrations into reusable skills through on-demand inspection of action, visual, and available accessibility evidence ( Huang et al., 2026 ) . WebXSkill extracts executable procedures with language guidance from trajectories ( Wang et al., 2026c ) . Search complements procedural guidance by considering alternative decisions. Computer-Using World Model simulates UI transitions for action selection ( Guan et al., 2026 ) , and Everything of Thoughts combines learned guidance with tree search for reasoning ( Ding et al., 2024 ) . Our RSI collection retains validated textual skills and real workspace checkpoints, so later attempts can reuse procedures or resume partial progress before full-task verification.

Such collection and learning require an execution layer that preserves both software state and training evidence. UFO introduces hierarchical Windows interaction ( Zhang et al., 2025c ) . UFO2 adds application-specialized agents and GUI–API integration ( Zhang et al., 2026 ) , and UFO3 extends orchestration to heterogeneous devices through a task DAG ( Zhang et al., 2025d ) . For reuse across training systems, Agent Lightning v1.0 separates harness execution from RL optimization ( He et al., 2026 ) . Orchard provides shared sandbox lifecycle services ( Peng et al., 2026 ) , while Polar reconstructs token-faithful training trajectories from recorded model calls ( Xu et al., 2026a ) . NorthCUA focuses on integrating these system responsibilities for stateful visual interaction. Its shared desktop/web runtime, live outcome inspection, and parallel lifecycle service support experience collection. The Experience Adapter then preserves the recorded decisions when converting online attempts into learning samples, connecting execution and assessment to policy training through the same task and outcome interfaces.

NorthCUA operates across diverse applications, while unfamiliar software and changing interface conventions remain challenging. Documentation-guided grounding expands the functional knowledge available during data construction, and skill- and milestone-guided collection revisit workflows that ordinary attempts leave unfinished. Extending this coverage to new software and maintaining reliable execution as applications evolve remain important directions for the experience pipeline.

Executable verifiers and live-workspace inspection tie learning feedback to the work actually produced. Feedback quality depends on predicate coverage and the calibration of model judgments for open-ended content ( Zheng et al., 2023 ) . Controlled verifier probes and evidence-linked judgments help check both. Long workflows also concentrate many decisions into a terminal outcome. More informative intermediate feedback could improve credit assignment and help agents reach correct results with fewer unnecessary actions.

Isolated workspaces, explicit tool profiles, and retained execution records provide controls for deployment. Operating real software also requires authorized access, least-privilege credentials, and confirmation for consequential actions. External pages and documents can carry indirect prompt injections ( Debenedetti et al., 2024 ) , motivating adversarial testing appropriate to each application. Released materials should undergo licensing, privacy, and credential review alongside the operational checks.

We presented NorthCUA , an integrated system for developing computer-use agents through experience at scale. By connecting the NorthCUA Harness, Experience Flywheel , and Staged Learning through shared tasks and outcome checks, the system supports learning from both verified demonstrations and fresh policy interaction. Improved policies can return to the same infrastructure to collect further experience. Recursive self-improvement extends collection to difficult workflows by preserving useful procedures and verified milestones, allowing later attempts to build on earlier progress.

Across six benchmarks, the Nano, Mini, and Pro family achieves state-of-the-art results among open-source models in GUI grounding, desktop execution, and Web interaction. At 397B parameters, Pro outperforms the trillion-parameter general-purpose baselines on both grounding benchmarks, OSWorld-Verified, and WebArena-Verified. Stage comparisons further show improvements in desktop and Web execution across all three model sizes following long-horizon SFT and joint RL. Alongside these gains in task completion, NorthCUA -Ultrafast explores a complementary route to faster decision-making.

We release the three models, the full Harness code, and this technical report so that the work can be extended at both the policy and system levels. Together, they provide an open foundation for adapting agents to new software and developing better ways to collect and learn from experience. The broader goal is to make reliable software execution a general AI capability, allowing users to delegate complete workflows from intent to verifiable outcome.

This appendix defines the runtime choices needed to interpret an interaction record, including the observations presented to the policy, the tools available to each role, environment ownership, and demonstration selection. The learning-side segment and update rules are consolidated in Appendix E.5 .

A context profile determines which retained interactions enter each model call. The sliding visual profile counts the latest clean frame within its image budget and keeps textual action/result records after image eviction. Other profiles replay visual history within a compaction epoch. Text windows, image budgets, and semantic compaction are separate settings. The generic context manager defaults to off. Shadow mode records decisions without applying them, and enforce mode applies its configured policy.

Historical overlays mark issued actions on pre-action images, while the latest clean frame shows the currently observed state. Text-only tools, including notes, do not add visual frames. A later application change can require waiting or a fresh observation. After a timeout or failed refresh, state inspection precedes retry. Web element references belong to the observed page state, and failed refreshes invalidate affected aliases.

Compaction retains a structured account of the goal, constraints, supported facts, completed work, failures, current state, open items, and artifact references. Summaries and notes carry their temporal provenance and remain distinguishable from observations. The summary prompt, protected recent interactions, trigger/target budgets, and failure policy determine the resulting input. Note categories are fact, correction, precaution, constraint, decision, and checkpoint. Compatibility names map mistake to correction and plan / other to checkpoint. The exposed schema, replacement behavior, and prompt budget control which notes remain visible.

A session binds the agent to its environment and resources. A round tracks one request and execution budget, and a step records one policy-decision and action-execution iteration. A step can contain several tool calls, so model decisions, tool calls, and GUI interactions are different counts. The dispatcher validates declared arguments before invoking local handlers or connected MCP tools and returns results to the requesting step. Appendix H.2 specifies the model-facing interfaces. Runtime probes use a separate permission profile from actor tools.

Evaluation binds a task and rubric to an evidence source, inspection permissions, budget, and report schema. The rubric-generation template requests three to seven criteria. The Agent Kit desktop entry path can use a request-level fallback, while the web profile supplies eight fixed criteria. The selected profile determines which criteria, weights, applicability rules, and reward conversion apply. Report-format validation checks the report’s structure.

Artifact tools inspect retained records. Live tools additionally require authorization and a dispatcher bound to the evaluated workspace. Artifact-only replay has no live device access. Read-only probes are preferred. Shell inspection uses an allowlist, and state-changing GUI or browser inspection requires explicit permission. The workspace remains reserved through required live checks.

Actor credit depends on the state before evaluator intervention. Terminal evidence and evaluator actions are therefore recorded separately. Inspection checks the submitted artifact or page state. A potentially mutating check needs a procedure that preserves the original state, such as a prepared evaluation copy. When that basis cannot be preserved, assessment uses retained evidence or leaves the condition unresolved. Probe failure, conflicting evidence, and an exhausted inspection budget are distinct from a supported task-failure verdict. When evaluator protection is enabled, recognized evaluation failures remain unresolved without replacing the actor’s terminal status.

Task preparation binds CaseSpec to its inputs, initialization procedure, application/tool profile, budgets, and optional post-run checks. Placement considers configured evaluator requirements as well as actor requirements. Resumed work uses the original task and configuration identity. Supported context-managed settings are retained in batch-local snapshots, while external dependencies keep their own version records.

Fresh single-use sandboxes isolate new collection attempts. Task-specific fixtures also cover external accounts and service state. An optional prepared queue, disabled by library default, performs initialization ahead of execution. Reservations are task/attempt-specific and assigned once. On-demand acquisition is a separate fallback. Prepared queues and warm pools have different allocation and reuse rules. An externally owned environment retains its own termination authority.

Creation, preparation, execution, submission, and status-query limits govern different resources. Assignment checks the remaining provider lifetime against the task timeout and release margin. Attempt identifiers link scheduler state to controller state, and reconciliation checks an existing attempt before starting another. A scheduler claim and a device execution lease represent distinct ownership decisions.

Live evaluation and environment-resident output capture finish before owned resources are released. Once a sandbox is destroyed, replay is limited to retained artifacts. Unconfirmed cleanup remains unresolved and continues to incur resource cost until destruction is confirmed. This lifecycle distinguishes transport disconnection from environment termination.
