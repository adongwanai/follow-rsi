In procedural tool-use domains, how much of the gap between base models is procedure rather than capability? We build an explicit program from a teacher’s traces and run it in front of unchanged small models, including an 8B model. The construction, PLVR , takes the reasoning traces of a teacher, Kimi-K3, clusters their segments to locate recurring operations, has a frontier model author one typed primitive per operation, each run by a small frozen model and checked by a deterministic verifier, and assembles the program by A ∗ search over a rule library mined from the same traces, under a reference-action objective: the distance between the actions the program takes and the actions the teacher took on the training tasks. At inference the program takes one of two forms: for troubleshooting and tool search it produces the chain of thought the student would otherwise generate for itself, and the student acts on it; for multi-turn tool matching the student proposes each action and the program checks, repairs, or retries it before it goes out. On the official τ 2 \tau^{2} -Bench Retail and Telecom test sets and on LiveMCPBench, with three Nemotron base models and the same program for each, the answer depends on the domain. On Telecom, Granite-4.2-8B as the student goes from 43.0% to 91.2% under the program, and every Nemotron student reaches 93.3–94.4%, against at most 58.2% for fine-tuning on the same traces, prompt optimisation of the student, or two token-matched baselines. With Granite-4.2-8B as the student, the program is within 2 to 3 points of the Nemotron students on Telecom and within 3 on Retail, and 3 to 13 points below them on LiveMCPBench: on τ 2 \tau^{2} Telecom an 8B student is enough, and on tool search the student still matters. The Telecom result is in-domain compositional generalisation: the program is built from synthetic tasks in the benchmark’s own environment and run on the benchmark’s unseen test tasks. On Retail and LiveMCPBench the program is competitive with the best baseline. The spread between base models shrinks from about 7 points to about 2, averaged over the suites, with no weights changed.

A small model that fails a multi-step tool-use task may lack the capability for the task, or may only lack the procedure: which record to read first, which check to run before which fix, when to stop. The two look alike in an end-to-end score. They differ in what fixes them. Capability is addressed by a bigger or better-trained model; procedure can be written down.

This paper asks how much of the gap between base models in procedural tool-use domains is procedure. We build an explicit program from a teacher’s traces and run it in front of unchanged models of different sizes, down to an 8B model. If the gap is mostly procedure, the choice of model under the program should matter little; if it is mostly capability, the program should help the stronger model more and the model should still matter. The answer we find depends on the domain: on troubleshooting and multi-turn tool matching an 8B student under the program is level with larger ones, and on tool search the student still matters.

PLVR takes the teacher traces that supervised fine-tuning would consume and decompose them instead. Clustering the traces’ segments proposes where recurring operations occur; a frontier model decides what each operation is and writes it as a primitive , a call to a small frozen model scoped to one operation, with a typed input, an output schema, and a deterministic verifier that rejects ill-formed or ungrounded outputs; and the primitives are composed into a program by search. The student’s weights are never updated; the program is the object that is built.

A base model asked to reason before acting generates a plan for itself at inference time and then follows it. For troubleshooting and tool search, the program is that plan, constructed once, from the teacher’s traces, as a typed composition of primitives, and at inference runs it to produce the chain of thought the student then acts on: the program replaces the student’s reasoning. For multi-turn tool matching the program is a guard around the student: the student proposes each action, and the program checks it against the records, the rules, and the user’s consent, repairs it, or sends it back to be proposed again. In both forms the student is the same model with the same weights; what changes is whether its reasoning is written for it or its actions are checked for it.

Assembling the program is a discrete search with no gradients. A frontier model first mines a library of rules from the traces, one line each. Starting from a hand-written seed, A ∗ adds rules from that library, scoring each partial program by the distance between the actions a program takes and the actions the teacher took on the same task, read off the trace by code: a reference-action objective. We report the seed’s and the final program’s accuracy on the test suites so the search’s contribution is visible.

Four results, all in Table 2 . First, on τ 2 \tau^{2} Telecom, Granite-4.2-8B as the student goes from 43.0% to 91.2% under the program, and Nemotron 3.5 Lightning, Nemotron 3 Nano, and Nemotron 3 Super reach 94.4%, 93.3%, and 93.3%; no other arm on any student exceeds 58.2%. Second, with Granite-4.2-8B as the student the program is 2.1 to 3.2 points below the Nemotron students on Telecom, within 2.7 points of them on Retail, and 3.2 to 12.6 points below on LiveMCPBench: on τ 2 \tau^{2} Telecom an 8B student is enough, and on tool search the student still matters. On Retail and LiveMCPBench the program is competitive with the best baseline, above it on some students and below it on others. Third, the spread between the three students shrinks from 6.6 points to 1.9 averaged over the suites, with no weights changed; per suite, from 15.8 to 3.5 on Retail, 15.0 to 1.1 on Telecom, and 10.9 to 9.4 on LiveMCPBench. Fourth, the search contributes: on Lightning it takes the hand-written seed from 73.1%, 68.4%, and 37.9% on the three suites to 82.7%, 94.4%, and 50.5% (59.8% to 75.9% averaged).

The method needs intermediate outputs that admit checking. Tasks whose quality is a matter of judgement rather than satisfaction, such as summarisation and open generation, are outside its scope, and we make no claim about them. Extraction was run on one teacher and three kinds of tool-use task, and we do not claim the primitives transfer to other domains.

Trace-guided program construction ( PLVR ). A frontier model authors 37 primitives from clusters of teacher-trace segments, each a typed call to a small frozen model carrying a deterministic verifier, so that every primitive is checked as it runs; a rule library is mined from the same traces; and A ∗ assembles the program under a reference-action objective read off the traces by code (§ 3 , Appendix D.1 ). The search itself is plain A ∗ and is not claimed as a contribution.

Knowledge distillation transfers a teacher’s behaviour into a student’s parameters, classically through soft targets and in the LLM setting through supervised fine-tuning on the teacher’s outputs or reasoning traces ( Ouyang et al., 2022 ) . RLHF fits reward models to human preferences ( Christiano et al., 2023 ; Ouyang et al., 2022 ) ; RLVR instead rewards programmatic checks such as test execution or answer matching ( Guo et al., 2025 ) . PLVR consumes the same traces as trace-based SFT, but puts the result into a program over frozen components rather than into weights, and the student’s parameters are not changed; its objective is the distance to the teacher’s actions rather than a reward.

Program-of-thought and PAL-style methods have a model emit executable code in place of free-text reasoning ( Gao et al., 2023 ; Chen et al., 2023 ) , and later work distils such programs into smaller models ( Zhu et al., 2024 ) . These write the program to a fixed template per example. PLVR writes one program per task family, from operations mined out of the teacher’s traces, and runs it either to produce the reasoning the student then follows or, in its guard form, to check and repair the actions the student proposes; the second form is closer to runtime guardrails and output verifiers than to program-of-thought.

Process supervision scores intermediate steps ( Uesato et al., 2022 ; Lightman et al., 2023 ; Wang et al., 2024 ; Xi et al., 2025 ; Kamoi et al., 2026 ) . ProTeGi, TextGrad, Trace, and GEPA optimise language-model systems through textual or trace feedback without derivatives through the model calls ( Pryzant et al., 2023 ; Yuksekgonul et al., 2024 ; Cheng et al., 2024 ; Agrawal et al., 2026 ) . DSPy, ADAS, AFlow, and AgentFlow compile or search declarative pipelines and workflows ( Khattab et al., 2023 ; Hu et al., 2025 ; Zhang et al., 2025 ; Li et al., 2026 ) . Logic-LM, Proof-of-Thought, and SEVerA couple language models with symbolic structure and executable checks ( Pan et al., 2023 ; Ganguly et al., 2024 ; Banerjee et al., 2026 ) . PLVR differs from these in where its components come from: the primitives are authored from clusters of a teacher’s traces rather than declared in advance, and the process signal is read off those same traces rather than learned or annotated. The search itself is plain A ∗ over a mined rule library and is not claimed as a contribution.

A PLVR program is a composition of typed primitives arranged by a small set of operators. We describe the training data and teacher traces (§ 3.1 ), the primitive library (§ 3.2 ), the expert actions read off each trace and the distance to them (§ 3.3 ), and the search (§ 3.4 ); the primitives and the clusters each is drawn from are in Appendix D.1 .

The three evaluation suites differ in the shape of their tasks, so we built a synthetic training set of 553 tasks in three subsets, one per kind of task (Table 1 ). The retail subset is 142 tasks in the τ 2 \tau^{2} retail format, multi-turn tool matching against a policy. The telecom subset is 178 tasks in the τ 2 \tau^{2} telecom format, mostly troubleshooting. The tool-search subset is 233 tasks in the LiveMCPBench format, tool search over a large registry. Each subset is split into training and held-aside tasks: 119/23 for retail, 122/56 for telecom, 183/50 for tool-search.

Claude 5 Opus generated the tasks. For retail and telecom it used τ 2 \tau^{2} -Bench’s own tools, environment, and policies and wrote new questions against them; for tool-search it used LiveMCPBench’s registry format and wrote new questions against that.

No benchmark task, and nothing that could stand in for one, appears in the training set:

No benchmark instances. Every benchmark task is excluded by id, including held-out ones. On LiveMCPBench the benchmark’s tasks were never read at all.

No shared underlying data. A training task may not reuse what a benchmark task is built on: the same issue type and fault set (telecom), or the same customer or order (retail).

No near-duplicates. Training task text is checked mechanically against benchmark text, and close matches are rewritten or dropped.

Held-aside tasks stay out. Each subset’s held-aside split is fixed up front and never used for training or search.

No uninformative tasks. Tasks that always pass or cannot be solved are removed.

Kimi-K3 is run on every task with the task’s tools and a system prompt that asks it to work through the task, record its steps, and finish with the tool calls; it names no operation and no primitive. We keep the reasoning the provider returns separately from the reply. Traces that do not reach the task’s ground truth are discarded: retail and telecom traces must re-score 1.0 under the τ 2 \tau^{2} evaluator, and tool-search traces must pass both an LLM judge and the task’s deterministic label. Every telecom and tool-search trace is kept; on retail, 128 of 142 are (90.1%). The 539 kept traces are the only demonstrations in this paper: they are what the primitives are extracted from, what the search scores against, and what every baseline is trained on. Two frontier models take part in building the program and see no benchmark data: Claude 5 Opus writes the primitives from the clustered traces (§ 3.2 ), and Claude Sonnet 4.5 mines the rule library the program search draws on (§ 3.4 ).

The primitives are trace-grounded and model-authored. The kept traces are processed by segmenting each trace, typing each segment as a reason , a call , a message , or a question , embedding, and clustering with k k -means within each kind. This gives 3,141 segments in 35 clusters: 15 reason, 8 call, 9 message, 3 question (segmentation rule and embedding model in Appendix D.1 ). Clustering locates where an operation lives in the traces; it does not by itself separate which decision a segment witnesses, since one segment can show several (a call segment shows the function chosen and the parameters filled). Clustering therefore proposes where operations occur; a frontier model, Claude 5 Opus, post-processes the clusters, decides what the operations are, and writes each primitive: its input–output signature, prompt, verifier, and fallback. The result is 37 primitives in six groups: understanding the message (7), finding the tools (5), building the call (8), checking the policy (7), troubleshooting conditions (6), and finishing (4). Each primitive is anchored to the clusters its segments come from; a primitive draws on 1 to 14 clusters and on 1 to 195 segments, and a cluster carries 1 to 14 primitives. Fifteen of the 37 are used in more than one subset; the rest are specific to one kind of task. The full mapping between primitives and clusters is in Appendix D.1 .

Each primitive is one call to Granite-4.2-8B, frozen, under its own prompt. It has named inputs plus a shared context (the facts gathered so far, the latest user message, the agent’s previous message, and where relevant the policy), a JSON output schema, a deterministic verifier , and a fallback returned when the verifier rejects. No prompt is tuned against a benchmark or an end-task reward. The verifier makes each primitive checkable: an output that violates its schema, quotes text not verbatim in its source, cites a fact that does not exist, or gives an expression that does not evaluate is rejected and the fallback is used.

Segmentation, typing, embedding, and clustering involve no language model and no hand-picked segments; the clusters, and which segments belong to them, are decided by the clustering alone. The frontier model decides which operations the clusters show and drafts each primitive’s signature, prompt, verifier, and fallback from the clusters’ members. Names are the authors’. The claim is not that the primitives were recovered automatically; it is that each one is anchored to segments of the teacher’s traces, and that the whole library was authored from the kept traces at negligible compute.

Each kept trace gives, by code alone, the expert actions for its task: the sequence of state-changing actions the teacher took (a device action by the user, or a write or tool call by the agent), each with its arguments; reads are left out. A program is scored by running it on a task and comparing the conversation’s sequence of actions with the expert actions for the same task. The distance counts 1.0 for each expert action that is missing or has wrong arguments, 0.5 for each action out of order, 0.5 for each extra state-changing action, and 1.0 for an abnormal ending, divided by the number of expert actions. Lower is better, and a program’s score is the mean distance over the search set. This is the reference-action objective the search minimises; no model judges a conversation.

A program is the seed plus a set of rules, each a line in the same form as the seed’s, and its primitives. The rules come from a library that Claude Sonnet 4.5 mines from the kept traces once, before the search: 61 rules from the tool-search traces and 64 from the telecom traces, each a one-line behaviour the expert shows (Appendix E ). The combined library of 125 rules is the candidate set for every block; the retail block has no library of its own and draws on the rules mined from the telecom and tool-search traces.

A ∗ starts from the seed. A successor inserts one rule, or one group of rules, from the library into the current program; it is kept only if the program still compiles and runs without errors. Partial programs are scored by the distance of § 3.3 plus a small cost per rule,

where | P | |P| is the number of rules in the program and d ⁡ ( P ) d(P) is the mean distance to the expert actions over the search set, so of two programs at the same distance the smaller wins. The final program is the one with the best task outcome on the training tasks among those the search reached.

The search scored 32 programs for the telecom block, 87 for the retail block, and 9 for the tool-search block (the seed, six group edits, their merge, and the final program). Settings are in Appendix A .

The seed is three hand-written blocks, one per subset of the training set, joined into one program. The telecom block walks the policy’s checklist in order, reads the system state before each fix rule, does not repeat a fix already in place, and re-runs the check until it passes. The tool-search block retrieves candidate tools for each request, picks one, fills its parameters, calls it, and checks whether the request is achieved. The retail block takes the base model’s proposed action each turn and checks it before it goes out: unknown tools and malformed ids are rejected, a change must take every value from a record that was read or from the customer’s words, the customer must be identified and own the record and the policy rule must hold, a change goes out only after the customer’s yes and is never made twice, and a claimed “done” without the call is retried. The search added rules to all three blocks. Both programs are listed in full in Appendix B . On Lightning, the seed scores 73.1% on Retail, 68.4% on Telecom, and 37.9% on LiveMCPBench; the final program 82.7%, 94.4%, and 50.5%.

We train on the set of § 3.1 and evaluate on the official τ 2 \tau^{2} -Bench Retail and Telecom test sets and on LiveMCPBench. τ 2 \tau^{2} -Bench is multi-turn dialogue against a stated policy, judged by the benchmark’s user simulator, where a small tool set makes correctness turn on ordering and admissibility. LiveMCPBench is tool selection and invocation over a large MCP registry, where correctness turns on choosing the right tool from many and binding arguments that resolve. Each suite has a training subset in its format (§ 3.1 ).

The primitives run on Granite-4.2-8B, frozen, each under its own prompt. The students are Nemotron 3.5 Lightning, Nemotron 3 Nano, and Nemotron 3 Super. Each receives every treatment: vanilla, fine-tuning on the traces, GEPA, the two token-matched baselines, and the program.

Every arm consumes the same kept teacher traces and the same synthetic training set; no arm uses any other demonstrations.

The student is fine-tuned on the traces in two variants. The process arm trains on the teacher’s reasoning followed by its final calls, so the student learns to reproduce the procedure before answering. The outcome arm trains on input to final calls only, with the reasoning removed. Learning rate, LoRA rank, and epoch are swept per model and variant and selected by solved count on the held-aside traces of each subset. One fine-tune per model is evaluated on the benchmarks and is the fine-tuning comparator in Table 2 . Construction and sweep are in Appendix C .

The student’s own system prompt is optimised with GEPA ( Agrawal et al., 2026 ) on the training set, and the student is then run as a native tool-calling agent with no program. This tests whether optimising the student’s prompt alone reaches what the program reaches. Construction, budget, and the optimised prompt are in Appendix H .

The student with chain-of-thought prompting and no other treatment. The program replaces this chain of thought, or checks the actions it leads to.

Two arms spend the same tokens per task as the final program, with Granite-4.2-8B doing the extra work, so that the program is compared against other uses of the same budget on the same small model. ReAct runs a plan–act–reflect loop in the style of ReAct ( Yao et al., 2023 ) : each turn, Granite-4.2-8B plans, the student acts from that plan placed where its own reasoning would go, and Granite critics review the action, with up to two revisions; the loop runs under the program’s Granite token budget (Appendix F ). Sample-and-judge samples five candidate responses and has Granite-4.2-8B, as a judge, select one, so that the total tokens match the program’s. The judge prompt is in Appendix G .

The program is built once from the training set (§ 3.4 ) and held fixed. The program is evaluated three times on τ 2 \tau^{2} Telecom and once on every other suite; every other arm is evaluated once per cell. Reported scores are means over those runs. Token counts per task are recorded for every arm, with the student’s and Granite’s tokens separated.

The three suites give different answers. On Telecom the program with Granite-4.2-8B as the student scores 91.2%, every Nemotron student under it 93.3–94.4%, and no other arm above 58.2%; the procedure is nearly the whole result, and on this suite an 8B model is enough to run it. The result is in-domain compositional generalisation: the program is built from synthetic tasks in the benchmark’s own environment, with its tools and policies, and is run on the benchmark’s test tasks, which it has not seen; it is not a claim about transfer to another domain. Telecom is also where the program’s student runs longest, about 40 turns per task against about 9 on Retail. On Retail the program with Granite as the student scores 82.5%, within 2.7 points of the Nemotron students, so there too the choice of student matters little under the program, though the program’s margin over the baselines is small. On LiveMCPBench the program with Granite as the student reaches 42.1% and the Nemotron students are 3.2 to 12.6 points ahead of it; the student’s tool choice and argument binding still count. We read the part of the gap between base models that the program closes as an estimate of how much of that gap is procedure; the program also carries the frontier models’ prior knowledge (§ 5.6 ), so the estimate is an upper bound.

The program is the same object in every row: the primitives run on Granite-4.2-8B, the search was run once, and no part of it is tuned to a student. Under it, the three Nemotron students land within 1.1 points of each other on Telecom and 3.5 on Retail, and Granite as the student lands within 3.2 points of them on both; on LiveMCPBench they stay 9.4 points apart. Where the base model still matters is where the student is doing part of the work.

The cost of the program is in inference tokens: the student reads 3.3 to 5.4 times as many input tokens as under the other arms, and Granite’s calls add more than that again; per task this is 4.7 to 9.8 times the FLOPs of a vanilla run. Producing the program cost 3.0 × 10 19 3.0\times 10^{19} FLOPs in Granite scoring, counting every Granite token in full and excluding the rule-mining calls, once for all three students; producing one fine-tune cost 7.7 × 10 17 7.7\times 10^{17} to 3.1 × 10 18 3.1\times 10^{18} for the selected run and 1.6 × 10 19 1.6\times 10^{19} to 6.4 × 10 19 6.4\times 10^{19} for the sweep that selected it, per student. No weights change, and the search was run once and the resulting program is shared by every student.

The gain is not attributed to the traces alone. The hand-written seed, Claude 5 Opus (which writes the primitives), and Claude Sonnet 4.5 (which mines the rules) all contribute, and neither frontier model is a blank slate about customer service or tool use; the ablation that removes the traces and the primitives still reaches 75.9% on Telecom (§ 5.6 ), and that ablation covers Retail and Telecom only. All cells but the program’s Telecom cells are single runs, so differences of a few points are not resolved. The synthetic training tasks share the τ 2 \tau^{2} Retail and Telecom domains with the test suites and the LiveMCPBench format with LiveMCPBench, so domain knowledge can pass from the training set into the primitives, the rules, and the fine-tunes. The training tasks and their answers are different from the test tasks; the authors verified this.

We compiled a teacher’s procedure into a program rather than into a student’s weights: primitives authored by a frontier model from clusters of the teacher’s traces, each run by a small frozen model and verified as it runs, assembled by A ∗ over a rule library mined from the same traces under a reference-action objective, and used at inference to write the student’s chain of thought or to check the actions the student proposes. Run in front of three Nemotron base models and on its own, the one program estimates how much of each domain is procedure. On τ 2 \tau^{2} Telecom the estimate is that nearly all of it is: Granite-4.2-8B as the student goes from 43.0% to 91.2%, every Nemotron student reaches 93.3–94.4%, and no other arm passes 58.2%; on that suite an 8B model is enough. This is in-domain compositional generalisation, from synthetic tasks in the benchmark’s environment to its unseen test tasks. On τ 2 \tau^{2} Retail the 8B student under the program is within 2.7 points of the Nemotron students; on LiveMCPBench the Nemotron students are 3 to 13 points ahead of it. On those two suites the program is competitive with the best baseline. No weights are updated, the program is the same for every base model, and the spread between base models shrinks where the program does the work. The program was produced once, at 3.0 × 10 19 3.0\times 10^{19} FLOPs, and costs 5 to 10 times a vanilla run to execute. Its output is a program rather than a checkpoint: it can be read at every step, it is the same for every base model, and it can be revised one primitive at a time. The next test is cross-domain transfer: a program built in one environment run in another.

The kept traces are split into 3,141 segments, each typed as a reason, a call, a message, or a question. Segmentation walks each trace’s message list. Only assistant messages produce segments, and each produces one segment per thing it emitted: a non-empty reasoning field gives one reason segment; each entry in the tool-call list gives one call segment; non-empty content gives one message segment, or a question segment if it ends in a question mark. User and tool messages produce no segments; they accumulate into the context (the last user message and the pending tool results) that is attached to the next assistant segment, and the pending results are cleared after each agent turn. The cut is therefore per emitted product rather than per turn: one assistant turn with reasoning, two calls, and a closing message becomes four segments. A segment is represented by the agent’s output at that point only, truncated to 2,000 characters: for a reason, the reasoning span; for a call, the literal name({json args}) ; for a message or question, the message text. The surrounding context (user message, tool results, turn, domain, function) rides on the segment and reaches the frontier-model stages but is never embedded. Segments are embedded with text-embedding-3-small (1,536 dimensions, L2-normalised); all similarities are cosine. Segments are clustered with k k -means within each kind, giving 35 clusters: 15 reason (876 segments), 8 call (1,064), 9 message (1,159), and 3 question (42).

Clusters locate which segments a primitive lives in; they do not separate which decision that segment witnesses. Claude 5 Opus post-processes the clusters: it decides which operations they show and writes each primitive’s prompt, input–output signature, verifier, and fallback.
