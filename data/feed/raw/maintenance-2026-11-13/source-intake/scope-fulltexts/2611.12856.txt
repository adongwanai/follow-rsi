Recent agent harnesses allow the model to instantiate worker agents and to author the executable workflow that coordinates them, shifting the design of system structure from developers to the model at run time. The quality of this organization therefore constitutes a distinct capability, yet existing benchmarks either measure end-to-end task completion or evaluate coordination under structures specified in advance. We formalize this capability as workflow orchestration and introduce WorkflowArena , a benchmark of 145 long-horizon tasks spanning 8 professional domains, from software engineering and formal mathematics to legal analysis and 3D production. Each task specifies an initial workspace and an integrated deliverable composed of interdependent components, which is assessed by a hidden verifier. Agents determine autonomously whether and how to delegate, and all delegation is recorded, enabling joint evaluation of deliverable quality and the organization of the underlying work. Experiments with nine models show that no single configuration performs best across all domains and that systems exhibit distinct delegation strategies: at high effort, Claude models in Claude Code invoke workflows less frequently but with larger worker groups, whereas GPT models in Codex delegate more frequently in smaller units. When the executing model is held fixed on a challenging subset of tasks, workflows authored by Claude Opus 5.5 substantially improve weaker executors, indicating that workflow organization is itself a measurable determinant of task performance. 1 Introduction Large language models have evolved from text generators into agents that act in external environments and pursue goals over long horizons [ 1 , 2 , 3 ] . As tasks grow longer, the limiting factor shifts from what a single agent can accomplish to how the work is organized. Long-horizon tasks consist of interdependent subtasks that call for different expertise and independent verification, and a single context that must retain the entire history of such work soon becomes a bottleneck. Further progress therefore depends on system intelligence , the ability of an agent system to organize multiple intelligent components into a coherent and adaptive whole [ 4 ] . Current systems already delegate and replan dynamically [ 5 ] , and recent harnesses allow the model to author the executable workflow that coordinates its workers [ 6 , 7 ] . The structure of a multi-agent system, once fixed by its developers, is thus increasingly determined by the model at run time, and its quality becomes a property of the model that requires evaluation in its own right. We refer to this capability as workflow orchestration . A workflow is an executable specification of how a task is partitioned among agents, which context each agent receives, and how intermediate results are verified and integrated. These decisions shape system behavior beyond the control of any individual agent. Running independent units in parallel, for instance, shortens the critical path but adds coordination cost, whereas an explicit verification point can catch an error before it propagates to downstream work [ 8 , 9 , 6 ] . The appropriate organization depends on the dependency structure of the task and on the available budget. Because the same agents can succeed or fail depending on how their work is organized, a premise we test directly in § 4.5 , orchestration is a system-level capability rather than an implementation detail. This leaves a central question that current evaluations do not answer: To what extent can LLM agents autonomously orchestrate multi-agent workflows to accomplish realistic long-horizon tasks? The inner ring shows domain totals, the outer ring shows task-form counts, and the surrounding panels illustrate representative deliverables. Existing benchmarks address parts of this question. End-to-end agent benchmarks measure task completion in realistic environments, including long-horizon and compositional work [ 10 , 11 , 12 , 13 , 14 , 15 ] , but they treat the agent as a single unit, so how its work is divided remains invisible. Multi-agent benchmarks study collaboration under predefined coordination protocols or among independently tasked agents [ 16 , 17 ] ; the structure under evaluation is chosen by the benchmark designer rather than by the model. Workflow benchmarks evaluate generated plans and workflow structures [ 18 , 19 , 20 ] , typically offline or in simulation, so the decisions they score never play out on real artifacts. None of them observes a workflow that the model writes itself and then adapts as its workers report back on real work. We introduce WorkflowArena to evaluate this capability directly. Evaluating orchestration requires tasks in which the way work is organized changes the result, and a protocol that leaves this organization to the model while recording it and charging its cost against the task. WorkflowArena provides both. Its 145 tasks span 8 work domains and 17 task forms (Figure 1 ) and are built from versioned professional artifacts or from authored scenarios whose dependencies are fully specified. Each task requests a deliverable composed of many separable units that depend on one another, such as clause-level analyses that must be reconciled across a contract portfolio or proofs that build on earlier results, so decisions about decomposition and integration change the outcome. A hidden verifier scores the submission against the task contract, including checks that individually correct but unreconciled components cannot pass. The agent decides whether to delegate at all, and the time spent organizing the work is drawn from the same budget as the work itself. Because every delegation passes through a recorded interface, each outcome can be read together with the workflow that produced it. Our empirical analysis operates at two levels. At the system level, we evaluate 25 configurations of nine models running in Claude Code or Codex. The strongest configuration, Claude Opus 5.5 with Claude Code at max effort, resolves only 36.95% of tasks on average across domains, and no configuration performs best in every domain. Execution traces reveal distinct delegation strategies: at high effort, Claude Opus 5.5 and Claude Sonnet 5.5 with Claude Code launch fewer workflows than GPT-6 Astra and GPT-6.1 Sol with Codex, but each workflow contains more workers. Because system-level results combine orchestration with the capability of the agents that carry out the work, we also hold the executor fixed: a source model writes and revises the workflow without editing the workspace, and every worker is an instance of a weaker execution model. On a challenging subset of tasks, workflows authored by Opus raise the continuous scores of all four execution models, by 6.41 points on average in the static mode, whereas workflows from Astra, itself far stronger than these executors, help them far less and lower the scores of two of them. Orchestration quality is thus a measurable source of performance that appears distinct from the ability to complete the task alone. Our contributions are: • Benchmark. We construct WorkflowArena, 145 long-horizon tasks across 8 domains and 17 task forms, in which each deliverable contract is paired with domain-specific hidden verification. • Evaluation protocol. We route every delegation through a recorded interface under a shared time budget while leaving the decision to delegate to the agent, so that its organization of work can be analyzed alongside deliverable outcomes and resource use. • Empirical findings. We compare 25 model–effort configurations by resolved rate and delegation behavior, and use a fixed-executor transfer experiment to isolate the contribution of the workflow and distinguish orchestration quality from solo task performance. 2 Related Work Long-horizon agent benchmarks. Agent evaluation has shifted toward interactive environments with outcome-based verification. AgentBench, WebArena, OSWorld, AppWorld, and SWE-bench ground evaluation in heterogeneous environments, websites, operating systems, applications, and software repositories [ 10 , 11 , 12 , 13 , 14 ] . GAIA and AssistantBench assess tool-using assistants on realistic web tasks, while WorkArena and WorkArena++ study enterprise software use and compositional workflows [ 21 , 22 , 23 , 15 ] . TheAgentCompany, MLE-bench, and ScienceAgentBench extend evaluation to workplace tasks, machine learning engineering, and scientific programming [ 24 , 25 , 26 ] , and the τ \tau -bench family evaluates policy-constrained interaction and coordination in shared environments [ 27 , 28 ] . Many of these tasks already involve long horizons and interdependent steps, but the agent is scored as a single unit. WorkflowArena retains their executable environments and independent verification while making the organization of the work observable, since every delegation the agent makes is recorded alongside its deliverable. Multi-agent system design and automation. MetaGPT, ChatDev, and AutoGen organize collaboration through specialized roles and programmable agent conversations [ 29 , 30 , 31 ] . MultiAgentBench compares coordination protocols, ParallACT studies conflicts among independently tasked agents in shared codebases, and MAST categorizes failure modes of existing systems [ 16 , 17 , 32 ] . A second line of work automates system design by searching over computational graphs, code-defined agents, executable workflows, and modular architectures [ 33 , 34 , 35 , 36 ] ; MaAS samples query-dependent systems from a learned supernet [ 37 ] , and MAS-Loop refines generated systems using execution trajectories [ 38 ] . ADAS and AFlow further report that the designs they discover transfer across models [ 34 , 35 ] . Other systems adapt their structure at run time: DyLAN dynamically selects and connects agents, Magentic-One delegates and replans during execution, and DynaFlow generates executable workflow programs [ 39 , 5 , 7 ] . These methods produce structures through design procedures, fixed controllers, or trained orchestrators, and assess them through downstream task accuracy. WorkflowArena instead treats the structure as an output of the model under evaluation, and its transfer experiment holds the executor fixed so that the contribution of a workflow can be measured separately from the model that authored it. Workflow generation and evaluation. ReAct and Reflexion interleave execution with observation and feedback, ReWOO separates planning from tool observations, and LLMCompiler schedules function calls in parallel [ 1 , 2 , 40 , 9 ] . FlowBench studies planning with supplied workflow knowledge, WorFBench evaluates generated sequence and graph structures together with their downstream utility, and OrchBench isolates orchestration-plan quality through deterministic simulation and validates its scores against real executions [ 18 , 19 , 20 ] . SkillsBench evaluates procedural knowledge by comparing matched conditions with and without skills [ 41 ] . These studies separate the quality of a workflow structure from its realized utility, but they evaluate structures largely offline or in simulation. Interface design and simple execution pipelines can also materially affect task performance, as SWE-agent and Agentless illustrate [ 3 , 42 ] , which motivates evaluating the model together with its harness. WorkflowArena evaluates workflows as they execute on professional artifacts, where the model revises its plan from the results its workers return and the time spent on orchestration counts against the task. 3 The WorkflowArena Benchmark WorkflowArena evaluates agents that organize their own work on long-horizon tasks. A benchmark for this capability must satisfy five requirements. First, organization must be consequential : tasks must contain enough separable and interdependent work that decisions about decomposition and integration change the outcome. Second, it must be autonomous , since a benchmark that prescribed roles or a workflow would measure compliance with that structure rather than the ability to choose one. Third, evaluation must be integration-sensitive , so that individually correct but uncoordinated components do not earn full credit. Fourth, the cost of organizing must be accounted for , so that every organizational step competes with the work itself for time. Fifth, the organization must be observable , so that each outcome can be related to the workflow that produced it. After formalizing the task (§ 3.1 ), we describe how the task design satisfies the first and third requirements (§ 3.2 ) and how the evaluation protocol satisfies the remaining three (§ 3.3 ). The transfer experiment in § 4.5 complements these properties by separating the contribution of a workflow from the capability of the agents that execute it. 3.1 Task formulation A WorkflowArena task is a tuple τ = ( s 0 , g , 𝒰 , ℰ , ℬ , V ) , \tau=(s_{0},g,\mathcal{U},\mathcal{E},\mathcal{B},V), (1) where s 0 s_{0} is the initial environment state, g g is the goal stated to the agent, 𝒰 \mathcal{U} is the public action and tool surface, ℰ \mathcal{E} is the set of task artifacts and execution environments, ℬ \mathcal{B} is the resource budget, and V V is an independent verifier. The agent observes the instruction and the public part of ( s 0 , 𝒰 , ℰ , ℬ ) (s_{0},\mathcal{U},\mathcal{E},\mathcal{B}) , but never the verifier, gold values, or hidden tests. During execution, the agent makes the organizational decisions that define a workflow, and these decisions are realized through tool calls and workspace updates recorded in the execution history h T h_{T} . Execution within budget ℬ \mathcal{B} yields a terminal state s T s_{T} containing the final artifact, which the verifier evaluates together with any task-relevant state transitions: r = V ⁡ ( s T , h T ) ∈ [ 0 , 1 ] . r=V(s_{T},h_{T})\in[0,1]. (2) The reward depends on the task outcome and on any required process constraints, but not on the number of workers or the shape of the workflow. A single sequential agent is therefore a valid workflow. The benchmark rewards whichever organization suits the task rather than presupposing that additional agents or parallelism are beneficial, which leaves the choice of organization to the model. The 8 domains identify the work setting, ranging from software and enterprise operations to law and 3D production, and the 17 task forms identify the deliverable and its verification structure within each domain. Tasks are selected for three properties that together make organization consequential. A substantial workload supplies separable units of work that can be assigned to different workers. Dependencies or shared constraints among these units make their ordering and integration matter. Scoring criteria defined on the integrated deliverable ensure that these decisions are reflected in the result. The properties constrain what the agent must deliver while leaving decomposition and execution order to the agent, as summarized in Figure 2 . Task materials. Tasks are built from real professional materials, from open-source repositories and formal mathematics libraries to corporate filings, legal agreements, and media assets; Table 3 lists the sources for each task form. These materials supply the scale, structure, and domain conventions of the work. Where a setting requires controlled state transitions or exceptions, as in operational processes and multi-entity accounting, the materials are embedded in authored scenarios whose dependencies are fully specified. Interdependent work. Interdependence gives decomposition and integration their consequences, and it is expressed as requirements on the final deliverable. In a contract-portfolio task, each agreement can be analyzed clause by clause, yet the deliverable also requires relations and conflicts across contracts, so separately produced analyses must be reconciled into one consistent report. In a multi-entity consolidation task, adjustments to each entity propagate through intercompany balances into the consolidated ledger. In formal proof construction, the target proofs belong to a development in which later results rely on earlier ones, and in 3D scene construction, separately built components must meet at shared spatial interfaces. Predictive modeling instead rewards exploring alternative approaches that are later compared and combined. In every case, units may be developed separately, but the evaluation examines how they fit together in the submitted result. Instantiation and acceptance. Each task specifies an initial workspace, a target deliverable, and task-specific constraints. For reconstruction tasks, the target work is removed while the surrounding context is retained. The task contract states the requirements on the deliverable, whereas reference outputs and hidden checks are excluded from the agent-facing workspace. Acceptance is defined on the final artifact. Wherever units of work depend on one another, the contract includes checks that only an integrated result can pass, such as regression tests in software or reconciliation in accounting. Operational tasks are additionally evaluated on their action histories, because a correct final state can be reached through an invalid process. Review and verifier testing. Human experts review the instructions, materials, and scoring criteria of each task, and tasks with ambiguous requirements, defective materials, or no substantive integration are excluded. Each retained verifier is tested against reference solutions and against submissions that should fail. Among the latter, submissions with correct components but no integration keep the evaluation integration-sensitive, since delegated components that are never reconciled cannot pass; submissions that reach a correct outcome through an invalid process play the same role for process constraints. Appendix A details the source material and instantiation of each task form. 3.3 Evaluation protocol We evaluate complete model–harness configurations under a common end-to-end wall-clock budget of four hours. Each task starts from a clean container workspace, and the budget is shared by the main agent and its workers. It covers all activity after the task starts, whereas environment preparation and grading lie outside it. Because the budget is shared, organization has a cost: parallel workers can shorten the critical path, but every step needed to coordinate them consumes the same time as the work itself. Task outcomes therefore reflect deliverable quality under a fixed time constraint, while token consumption and estimated inference cost characterize the resources each configuration uses. Agent interface. The agent has full access to the task workspace, including the shell, tests, and direct file editing. It is also given a Workflow tool that launches background workflows with up to 16 concurrent workers and allows the agent to inspect, stop, and revise them. We write Workflow for this tool and its invocations, and workflow for the general concept. Each worker is a fresh instance of the agent itself, with the same model, harness, and effort. Because workers start from a fresh context and share only the workspace, the agent must decide what each worker needs to know, which makes context allocation part of the evaluated behavior. Native sub-agent mechanisms are disabled, so every delegation passes through the Workflow tool and is recorded. Using the tool remains optional, which leaves the decision to delegate entirely to the agent. The agent may revise its workflow in response to public execution feedback until it stops or exhausts the budget, after which the verifier scores the final artifact. Each execution thus yields a trace of Workflow invocations, worker executions, and revisions, together with the time and tokens consumed by the main agent and each worker. Scoring and aggregation. Agent errors, missing deliverables, and budget exhaustion are not treated separately; the resulting submission is scored under the same task-specific rules. 4 Experiments The experiments address the research question from three perspectives. After describing the setup (§ 4.1 ), we measure how far agents accomplish the tasks through task performance (§ 4.2 ) and resource use (§ 4.3 ). We then examine how they organize the work, characterizing delegation across systems, effort settings, and domains (§ 4.4 ). Because system-level outcomes combine orchestration with execution capability, a transfer experiment holds the executor fixed to isolate the contribution of the workflow itself (§ 4.5 ). Finally, three 3D construction tasks illustrate in detail what the resulting workflows look like (§ 4.6 ). 4.1 Experimental setup Evaluated systems. To separate the two, we hold the executor fixed and vary only the source of the workflow on a challenging subset of 32 tasks (Appendix E ). Astra and Opus serve as workflow sources at max effort, and Kimi, DeepSeek, Luna, and Doubao serve as execution models; every worker is an instance of the execution model. In the static mode, the source model reads the task instruction and the clean initial workspace, writes a Workflow program, and then stops; the frozen program runs in a fresh workspace, where its internal branches, loops, and parallel stages still execute. In the dynamic mode, which follows Claude Code dynamic workflows [ 6 ] , the source model launches Workflows, observes worker results, and revises the workflow throughout execution. Unlike the main agent in § 3.3 , the source model cannot edit the workspace in either mode, so all task work is performed by the execution model’s workers. Workflow generation counts against the same wall-clock budget. For each execution model, we compare the four transferred settings against its own dynamic workflow (Table 2 ). Its 145 tasks span 8 domains and 17 task forms, and each pairs professional source material or an authored scenario with an explicit initial state, an interdependent deliverable, and hidden domain-specific verification. Every delegation passes through a recorded interface under a shared time budget, so each result can be read together with the workflow that produced it. Returning to the question posed in the introduction, current agents can orchestrate multi-agent workflows for long-horizon tasks, but they remain far from accomplishing them reliably: the strongest configuration, Opus with Claude Code at max effort, fully resolves only 36.95% of tasks on average across domains, and no configuration leads every domain. How the agents organize their work also differs systematically. At high effort, the Claude models in Claude Code delegate less often but in larger groups, whereas the GPT models in Codex delegate more often in smaller units, and within each system the task domain further shapes how often and how widely work is delegated. Holding the executor fixed on a challenging subset shows that this organization matters in its own right: workflows authored by Opus raise the score of every execution model, while workflows from Astra, itself a much stronger system than these executors, help far less. The quality of orchestration thus appears to be a measurable source of performance that is distinct from the ability to complete the task alone. Limitations. Each configuration is evaluated once per task, so differences between closely ranked configurations are reported without variance estimates. Each model is evaluated in a single harness, and differences between the Claude and GPT systems therefore reflect the model and its harness jointly; the non-GPT models that run in Claude Code provide only a partial basis for separating the two. Content and 3D deliverables are graded against task rubrics by an LLM judge, and agreement with human graders is not measured in this work. The transfer experiment uses a subset of the benchmark and two source models, and because source models also write the instructions given to workers, its gains may combine better organization with task knowledge conveyed in those instructions. Because WorkflowArena records both the deliverable and the workflow that produced it, it also supports future study of heterogeneous systems in which the orchestrator and its workers use different models, as well as adaptive budgets and interactive task execution. Each package contains an agent-facing instruction ( instruction.md ), an environment specification ( environment/ ), a verifier entry point ( tests/ ), and task metadata. The instruction defines the required deliverable and execution constraints, while the environment provides the initial workspace and task inputs. Hidden tests and reference assets are kept separate from the agent-facing materials. After execution, the verifier evaluates the final submission and any task-relevant state transitions to produce the task score. Appendix C Task-Specific Scoring Criteria Each task is evaluated with a continuous score on a 0–100 scale. The verifier assesses the submitted deliverable against the requirements in the task contract. Component checks contribute to this score through the task-specific scoring rule. Software and formal mathematics scores reflect progress across functional groups or required targets, together with build and integrity checks. Operational scores combine outcome, process, and constraint checks. Financial and legal scores account for both local analyses and their integration into a consistent final report. Scientific reproduction uses target-specific numerical tolerances, while predictive modeling uses the official metric and a fixed reference population. Content and 3D scores use weighted rubrics covering substantive requirements and delivery quality, including narrative coherence, geometry, and cross-component consistency where applicable; these rubrics are scored by Gemini-3.8-Flash. The task contract specifies the scoring weights, tolerances, equivalence rules, and required checks. Artifact evaluation combines technical inspection with semantic review: media must satisfy the requested narrative and editing requirements, and scenes must satisfy the specified geometry and spatial relationships. The resulting score captures the extent to which the final deliverable fulfills the task. Appendix D Execution and Resource Accounting D.1 Model and execution configuration Table 4 lists the API model identifiers and harness versions. The main agent and its workers use the same registered model, harness, and effort. Model identifiers are passed to the API through the execution broker, which also enforces the effort setting. Codex is pinned to version 0.164.0 and Claude Code to version 2.1.280. The trial registration records the agent profile, protocol options, task-package hash, and container image identifiers. At execution start, the runner archives its Python implementation, prompt templates, JavaScript runtime, and interface schemas with SHA-256 hashes. These artifacts identify the executable configuration of each trial independently of subsequent repository changes. Containers and resources. Task execution takes place in Docker containers, with model inference accessed through the broker. The task package specifies CPU and memory limits for each agent container; these override the generic agent-profile defaults. The runner records the effective limits, CPU affinity when applicable, and resolved image identifier in the execution record. A host-level admission controller reserves CPU and memory before starting a container and holds the reservation until cleanup. Its capacity is bounded by 90% of the host’s reported CPUs and 85% of its memory, with any explicitly configured host caps applied as additional limits. The resulting capacity and container reservations are recorded alongside the trial. Thus, task-level resource declarations and effective container allocations specify the compute available for shell commands, tests, rendering, and other local work. Wall-clock accounting and request handling. The four-hour protocol uses a 14,400-second deadline shared by the main agent and all workers. The execution loop establishes this deadline using a monotonic clock and passes the remaining time to each agent invocation. Worker dispatch, container admission waits, tool execution, provider queueing, and retry backoff consume the same budget; launching or resuming a Workflow does not reset it. Task preparation precedes this execution window, and grading follows it. Worker concurrency is capped at 16. The broker separately limits simultaneous upstream requests to the registered concurrency and applies a 240-second queue timeout. Transient transport failures, rate-limit responses, and provider overloads are handled by the broker. Backoff grows exponentially, is capped at 30 seconds, and adds up to 0.3 seconds of jitter; a valid provider Retry-After value of at most 120 seconds can extend the wait. Retries remain bounded by the request deadline and the transport policy in the archived implementation. The broker records the attempt limit, response status, queue time, elapsed time, and backoff for each request. Native harness request retries are disabled when broker-managed retries are enabled, avoiding nested retry loops. Delivered model or tool events are not replayed after a stream failure. Provider-side service capacity is external to the container resource allocation; its observed waits are included in the execution time. D.2 Prompts and tool interfaces The initial message to the main agent consists of three parts. The first sets up the task. It points the agent to the task instruction in /testbed/instruction.md , states that the workspace is writable, and allows the agent to work directly, to delegate through Workflows, or to combine the two, without a required planning stage and without prescribed roles, topology, or worker count. It asks the agent to prioritize correctness and completeness before elapsed time and token consumption, to coordinate file ownership among workers that share the workspace, to give each worker the context it needs because workers start from fresh conversations, and to confirm that the final deliverable is in place before finishing. It also reports the total and remaining time budget and notes that launching a Workflow does not reset it. The second part defines Workflow programs, including their script format and the interface described below, and advises that the structure of a workflow should follow the task rather than a fixed template of stages. The third part describes runtime details, such as where execution transcripts can be inspected and how changes made in isolated worktrees must be integrated. Each subsequent turn begins with a short continuation message that reports execution feedback and the remaining budget. The harness retains its versioned native instructions. Benchmark messages and worker assignments are supplied explicitly; automatic discovery of host project instructions, memories, and skills is disabled. Workflow workers start with fresh conversations and receive the assignment and public task workspace. Optional role instructions use the harness instruction channel: Codex’s developer instructions or Claude Code’s appended system prompt. The runner saves the rendered worker prompt and role-instruction hash. Workers share /testbed by default; isolated Git worktrees require explicit integration by the agent. The main agent receives five Workflow interfaces: Workflow launches a background JavaScript program; WorkflowList lists runs and active workers; WorkflowOutput retrieves status or results and can wait for up to 30 seconds; WorkflowStop cancels a run and its workers; and WorkflowControl pauses or resumes dispatch, or stops or restarts an individual worker. Their JSON schemas are supplied through MCP. Workflow programs compose agent , parallel , and pipeline calls, the primitives of Claude Code dynamic workflows [ 6 ] , with ordinary JavaScript control flow; both harnesses receive the same interface. Environment operations are performed through worker tools. Claude Code exposes reading, searching, shell execution, and file editing; Codex exposes the corresponding native workspace tools and local image inspection. Native sub-agent tools are disabled, so delegation passes through the recorded Workflow interface. D.3 Token categories and inference-cost calculation For each task, usage is summed over the main agent and Workflow workers, including recorded retry attempts. We normalize usage into four disjoint categories: uncached input I I , cache reads R R , cache writes W W , and output O O . For Responses-style records, the reported input count already includes cached input, so I = T input − R − W I=T_{\mathrm{input}}-R-W . For Messages-style records, the reported input count excludes cache reads and writes, so I = T input I=T_{\mathrm{input}} . In both cases, total token consumption is I + R + W + O I+R+W+O . Reasoning tokens already included in output are not added again, and audit summaries of the same calls are not counted as additional usage.
