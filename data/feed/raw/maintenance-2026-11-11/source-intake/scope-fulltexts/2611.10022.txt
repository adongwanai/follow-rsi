Specialization for Token-Efficient Skill Use Jiayi Ni 1 Zac Wang 1 Alex Zhang 1 Zheng Liu 1 Roopa Prabhu 1 † † footnotetext: 1 NVIDIA. Preprint. Abstract Reusable skills guide large language model (LLM) agents through recurring requests, but each
invocation still requires the model to interpret the skill and reconstruct its orchestration.
Can agents automatically compile this orchestration into an executable fast path without human
intervention? We first study zero-shot skill specialization , which compiles without execution evidence,
and find that despite the skill’s procedural guidance, incorrect assumptions about runtime bindings
can make generated plans brittle and recovery costly. This motivates SkillCache, a one-trace skill specialization method that compiles a completed invocation into a
parameterized capsule of programs and natural-language steps, replays it before reuse, and drives it with a plan
executor that returns control to the model only when needed, keeping the source skill for recovery.
With the Claude Code harness, warm execution of the same request reduces tokens on 87 SkillsBench tasks by 81%
with Claude Sonnet 4.6 and by 74% with Claude Opus 4.8 at comparable
reward, and capsules stay effective under controlled request changes. Capsules also transfer across models,
raising three open-weight models’ mean reward by 12–25 percentage points while reducing their
tokens by 72–81%, suggesting that execution-grounded compilation is a promising approach to
efficient repeated skill use and cross-model transfer. 1 Introduction Many large language model (LLM) agent workloads contain recurring requests of the same type, such as the same analysis over
new datasets ( Zhang et al., 2025b ; Li, 2026 ; El Yadouni & Li, 2026 ) . Agent Skills package instructions and supporting files as
reusable procedures for such requests ( Zhang et al., 2025a ; Anthropic, n.d.b ) .
Well-written skills can improve overall task accuracy and sometimes reduce exploration and
tokens ( Li et al., 2026a ; Zhong et al., 2026 ) , yet the agent still needs to plan and reason over the matched skill on every invocation. In particular, irrelevant skill context and
repeated reasoning add runtime overhead ( Xu et al., 2026 ) . Recent source-level compilers transform skill specifications into structured or executable forms ( Ouyang et al., 2026b ; Xu et al., 2026 ; Dantanarayana et al., 2026 ) , but operate mainly on skill packages instead of specializing orchestration for a concrete request. Other methods evolve or optimize skills. Some use execution trajectories and task-level
rewards ( Mi et al., 2026 ; Xia et al., 2026 ; Yang et al., 2026a ) , held-out rollout evaluation ( Yang et al., 2026b ) ,
or official verifier feedback ( Rao & Kalluru, 2026 ) to learn, select, or repair updates, yet such
signals may be unavailable in deployment. Human-authored skills also outperform the automatic alternatives evaluated by Zhong et al. (2026) . Thus, we study a complementary setting that preserves the
human-authored skill as the source of truth and stores execution-derived specialization separately. Building on systems that separate planning from tool execution ( Xu et al., 2023 ; Kim et al., 2024 ; Erdogan et al., 2025 ) , we first study zero-shot skill
specialization , where an agent compiles the skill and request into a reusable capsule of programs and natural-language steps before
execution. The goal is to pay the compilation cost once and reuse the resulting capsule instead of repeatedly
interpreting the skill. On 87 SkillsBench tasks ( Li et al., 2026a ) , however, compiling and executing once uses
more tokens than direct skill use on 58 of the 84 tasks without a timeout, and 1.24 × 1.24\times as many per task in geometric mean. On the 32 tasks
with a compiled-program failure, execution alone uses 0.92 × 0.92\times the direct tokens, against 0.71 × 0.71\times over all tasks. Including compilation raises the ratio on these 32 tasks to 1.34 × 1.34\times . Figure 1: The same request, run cold and warm (SkillsBench llm-prefix-cache-replay , Claude
Opus 4.8). In the warm run, the model fills in the paths from the request, and the executor runs
the compiled programs. These failures motivate using execution evidence alongside the skill source during specialization.
Prior work derives reusable procedures or executable artifacts from observed behavior ( Chen et al., 2026c ; Ni et al., 2026 ; Chen et al., 2026b ; Li, 2026 ; El Yadouni & Li, 2026 ) , sometimes by aggregating
multiple trajectories or using an external evaluator to confirm success. In our setting, the supplied skill already provides the general procedure. We
introduce SkillCache , a one-trace skill specialization method that uses a single
completed trajectory to recover the runtime bindings and execution structure. An evaluator-blind compiler agent automatically
compiles the unchanged skill and trace into a parameterized capsule of programs and natural-language
steps. At reuse, SkillCache drives the capsule with a plan executor that runs consecutive programs
and returns control to the model only for its input, its judgment, or a failed program, so the model
no longer orchestrates each call. The source skill remains available for recovery.
We call the initial execution cold and subsequent capsule-augmented executions warm ,
and Figure 1 shows both on an example request. Our contributions are as follows: • We first show that specializing a skill from the request and skill alone does not reliably reduce
tokens, because the compiler may guess runtime bindings incorrectly and failed programs are expensive to
recover. • We thus present SkillCache, a one-trace skill specialization method that turns one completed
execution into a capsule of programs and natural-language steps and replays it before reuse for qualification. • Building on the capsule’s structure, we also present an executor-driven design, which runs
the programs and passes values between them, returning control to the model only when needed. • We evaluate SkillCache on 87 SkillsBench tasks. Averaged over three runs, warm execution
reduces tokens by 81% with Claude Sonnet 4.6 and by 74% with Claude Opus 4.8 at comparable reward, repaying the dollar cost of compilation after 1.1 and 1.5 reuses in aggregate. Capsules also transfer to three open-weight
models, raising their mean reward by 12–25 percentage points. We further show that capsules stay
effective under controlled request changes and that the executor-driven design and replay both
contribute to the savings. 2 Background 2.1 Agent Skills and Their Orchestration Cost LLM agents combine reasoning with environment actions and external
tools ( Yao et al., 2023 ; Schick et al., 2023 ; Patil et al., 2024 ) . Agent harnesses such as Claude
Code ( Anthropic, n.d.a ) , Codex ( OpenAI, 2025 ) , and
OpenClaw ( OpenClaw, n.d. ) manage context, tools, and multi-turn execution.
Agent Skills extend an agent with reusable procedures, each a directory with a SKILL.md file of instructions and optional scripts and reference
files ( Zhang et al., 2025a ; Anthropic, n.d.b ) . The model first reads each
skill’s name and description, decides whether the skill applies, and opens its instructions and
files when it needs them. It then interprets the skill and orchestrates its procedure through
tool calls in the harness. Each model call takes the
instructions and the execution history so far as input, so input tokens accumulate across calls.
Provider prompt caching makes repeated prefixes cheaper ( Lumer et al., 2026 ) , but their
cost still grows with every call. Each call also generates new output tokens and adds latency. In the cold executions of our main study (Section 7 ), a request takes a median of 14 calls with both Sonnet 4.6 and Opus 4.8. Many of these calls do mechanical work, such as composing a command or copying a value from one
output into the next. Only
judgment needs a model, yet every recurring request has the model redo the
mechanical work. Together, these observations suggest compiling the mechanical work of a skill invocation into programs that later requests reuse, and involving the model only where judgment is needed. 2.2 Tracing JIT Compilation Tracing just-in-time (JIT) compilers reuse compiled code for frequently executed paths within a program
run ( Gal et al., 2009 ) . While interpreting a program, they record a path, called a trace, and only then generate
code specialized to the types observed along it. This specialization assumes that later executions
follow the same path with compatible types, and guards check these assumptions at runtime. If a guard
fails, execution leaves the compiled trace and can return to the interpreter through deoptimization.
The compiler must preserve the program’s meaning across specialization and
deoptimization ( Flückiger et al., 2017 ) . In Section 4 , we detail how

It works in three phases. (1) Observe : It records the cold invocation’s observable trace τ obs \tau_{\mathrm{obs}} , which holds the tool calls with their arguments, results, and errors, and the
agent’s messages. The trace identifies the branch the skill took and carries its runtime arguments,
intermediate observations, and recovery actions. (2) Compile : An isolated compiler turns τ obs \tau_{\mathrm{obs}} into a capsule , fusing adjacent
deterministic tool calls into programs, keeping judgments as natural-language steps, and lifting
request-dependent values into bindings (Figure 2 ). The host admits a capsule only after its programs pass a replay in the task’s
sandbox, and otherwise falls back to a written procedure (Section 5 ). (3) Execute : In a later, warm execution, a plan executor
runs the programs and hands natural-language steps and failed programs to the model
(Section 6 ). Each phase runs in a fresh sandbox, and no phase sees
the benchmark’s tests or verifier (Appendix A.3 ). These phases follow a tracing JIT compiler (Section 2.2 ). The cold execution
is the recorded path, and the capsule is the compiled trace, kept for later requests of the same kind
as a trace cache keeps compiled traces ( Gal et al., 2009 ) . SkillCache’s compiler is an LLM agent that can write failing programs, which is
why the host replays each candidate before admitting it. A program can still fail later when
the request, the model’s decisions, or the environment differ. Like a failed guard, a failed program
leaves the compiled path through deoptimization, but only for that step, and the rest of the plan stays
compiled. 5 Compiling a Capsule 5.1 The Capsule Representation The compiler emits a parameterized capsule z = ( μ , B , P , π , V ) , z=(\mu,B,P,\pi,V), (4) where μ \mu describes when the capsule applies, B B holds the bindings (the named values that programs
read or write), P P contains programs, π \pi interleaves program calls with natural-language steps, and V V is an
optional verification of the postconditions that the request and source skill state. V V runs after π \pi and, like π \pi , mixes
program calls with natural-language steps. Each binding describes how to obtain its live value, from the request or workspace, a natural-language
step, or a program’s output. Each program declares the bindings it reads and those it sets for later
programs, so values pass from one program to the next without the model. Programs are language-agnostic. Each has source files, a command,
and a syntax or build check, reads its inputs from a JSON file, and prints one JSON result or
exits nonzero with a diagnostic. Alongside z z , the compiler returns examples E E , the values the bindings had in the observed
execution. They serve only to qualify the capsule (Section 5.3 ). The
host removes them when it mounts the capsule, so a warm execution never receives E E . 5.2 Trace-Guided Compilation The compiler reads ( q , S , τ obs ) (q,S,\tau_{\mathrm{obs}}) in a fresh sandbox that holds none of the task’s
files. The compiler prompt and the
program interface are fixed across tasks, and the prompt (Appendix B )
specifies four specialization rules. Path pruning : The compiler removes failed
exploration, keeps the skill’s requirements, and adds no behavior that neither the skill nor
the trace shows. Binding lifting : Values that a program needs and that depend on the
request or workspace become bindings, each with an instruction for obtaining its live value, while
other values stay as the execution used them. Region fusion : Deterministic operations
become programs, and adjacent ones share one program. Where the execution ran code, such as a
skill’s script, the program reuses that code and changes only the bindings. A step that needs
semantic judgment or a new observation stays a natural-language step. Grounded postconditions : V V checks only the observable postconditions that the
request and source skill state, together with any inspection by which the execution checked and
corrected its own result. The prompt forbids comparing a result with the answer the observed
execution produced, and the compiler never sees the evaluator. 5.3 Capsule Qualification To reduce program failures at reuse, where recovery is costly (Section 3 ), the host
qualifies each candidate before admitting it to the cache, through three gates that do not call the model. Gate 1: Structure and dataflow. The host parses the capsule and checks its dataflow. Steps call exactly the programs in P P , and the
programs’ inputs and outputs are exactly the bindings in B B . Each output comes from only one program,
which runs before any program that reads it. Gate 2: Program checks. The host creates a fresh sandbox from the task image and runs the check the compiler wrote
for each program, such as python3 -m py_compile . This gate catches programs that do not parse
or build in the task’s environment. Gate 3: End-to-end replay. In a fresh task sandbox, the host replays the plan with the same plan executor used at reuse.
The examples E E supply every binding that no program outputs. Programs execute on task inputs and pass their outputs through the bindings. If a
program fails, replay records its diagnostics, substitutes its observed outputs from E E , and
continues to collect failures from later programs in the same replay. The compiler receives the collected failures and its previous answer, then returns a repaired
capsule. The host allows up to three attempts at the hybrid form, a capsule with programs. If no
candidate qualifies, the host compiles the same trace into a written procedure, the textual form, with a prompt that follows the same rules. If that also fails, later executions run with the source skill alone.
Appendix B gives the prompts for both forms. 6 Executing a Capsule 6.1 The Plan Executor If the model called each program itself, it would still read the whole plan from the start and orchestrate every call. A capsule, however, explicitly interleaves program
steps with natural-language steps and declares each program’s input and output bindings. This structure lets
consecutive programs run back to back without invoking the model. We thus introduce an executor-driven design, in which a plan executor, skillcache-run ,
advances through the program steps and returns control to the model
when the plan needs its input or judgment. The executor runs each program through the runtime, skillcache-tool . Both skillcache-run and skillcache-tool are command-line programs that the host places in the agent’s sandbox, and
the model invokes them with its ordinary shell tool, so the agent harness runs unchanged. paragraph. Protocol. The prompt shows the capsule’s name and description, and the model decides whether it applies. On a
miss, the model serves the request with the skills and its normal tools, as in a cold execution. On a
hit, the model first performs any steps before the first program, such as locating an input, and
then starts the executor once with skillcache-run run and the bindings that the programs read before the
first hand-over. A textual capsule has no programs, so the model follows its steps directly. The
executor runs program steps in order and returns to the model with one of three
reports (Figure 4 ), each listing the programs completed since the previous report with
their results. needs_bindings asks at once for every binding that the programs up to the next
hand-over read but were not given. your_steps hands over the next natural-language steps, including any step whose program failed
(Section 6.2 ), and asks for the bindings that the next programs read. complete reports that no program is left, with the remaining
natural-language steps for the model. The model answers the first two with skillcache-run continue and the bindings asked
for. Plan state. Each run or continue is a short process that prints its report and exits. A plan
state file records the next step to run ( position ), the step a continue resumes at
( awaiting ), every binding known so far ( bindings ), the steps whose program
failed with their diagnostics ( failed ), and the programs completed since the last report with their
results ( completed ), as Figure 4 lists. The executor saves it before each program runs, so when the agent’s
command limit ends a call in the middle of a plan, a later continue reruns the interrupted
program. Fewer and smaller calls. The executor passes each program’s outputs to the programs that read them and asks
at once for the other bindings that the programs up to the next hand-over read. Thus, the programs
run back to back without returning to the model for an input. When several natural-language steps come in a row, the executor
hands them over in one report, and the model performs them all before a single continue with the bindings asked for. Each call also reads less of the plan, since later steps reach the model only when the

A cold execution serves the request with the skills alone, a compiler agent with the same model

execution. Raw trace adds the trace itself, as systems that

same compiler writes it from the trace with the prompt of the capsule’s textual form
(Appendix B ). Both baselines are agent-driven. SkillCache adds the capsule and runs it with the plan executor. To separate the representation
from the executor, Section 7.7 also runs the capsule agent-driven against both
baselines. Metrics. We report provider-reported tokens, which include cache reads and writes, list-price cost, model
calls, latency, and verifier reward. Reward is the task verifier’s score in [ 0 , 1 ] [0,1] , which is 1 when every
check passes, and a few tasks give partial credit. Latency is the span from a task’s first model call to the end of its last,
so it includes the commands and programs between calls. A missing outcome scores zero reward, and tokens, cost, and calls cover the tasks on which every
context (cold included) recorded tokens and reward. Warm executions exclude the compile cost because a one-trace capsule is compiled after its
request is served. We report this cost separately and amortize it over reuses in

Because SkillsBench gives each task a single request, we additionally build three kinds of probes, each changing
one thing in a source task, to test whether a capsule still works when a recurring request changes. An instance probe changes the input content or a parameter the
request states, a rename probe changes the paths of files the request names, and a reword probe rewrites one to three sentences of the request. A probe is kept only if, in its task’s container,
its reference solution passes its verifier and, for an instance probe, the source task’s reference
answer fails. We build 23 instance, 19 rename, and 24 reword probes for 24 of the 44
tasks whose cold execution succeeded in the first Sonnet run, all of which also succeeded with Opus
(Appendix A.9 ).

the idea of compiling a completed execution into programs that an executor drives on later
requests. It could also benefit recurring agent tasks without skills or in other harnesses. Extending SkillCache to these settings is one direction for future work. SkillCache also incurs a one-time compilation cost and is most useful when later requests amortize it
(Section 7.6 ). In addition, each capsule is compiled from one cold execution and
may carry useful patterns alongside brittle assumptions, errors, or biases. Replay in qualification also runs
the programs only with the original request’s values and inputs, so a capsule that hard-codes one of
those values can still pass, as the instance probes in Section 7.5 show. Future work could let a capsule learn from its warm executions and improve
with use, much as a tracing JIT compiles paths it discovers later ( Gal et al., 2009 ) . Finally, as SkillsBench supplies each task’s skills, our evaluation supplies each task’s capsule and does not
test retrieval.
Production use would require reliable retrieval and selection as the cache grows, along with execution
safeguards and cache invalidation when a skill or its environment changes. Integrating these
lifecycle and security mechanisms in persistent deployments is another direction for future work. 9 Related Work Skill evolution and source-level compilation. Skill-evolution methods construct or refine skills using rewarded trajectories ( Mi et al., 2026 ; Xia et al., 2026 ; Yang et al., 2026a ) , held-out
rollouts ( Yang et al., 2026b ; Tang et al., 2026 ) , or other execution feedback ( Ni et al., 2026 ; Zhang et al., 2026b ; Zhou et al., 2026 ; Zhang et al., 2026a ) . A separate line of work compresses skill content ( Gao et al., 2026 ) or translates skill packages into typed representations ( Ouyang et al., 2026b ) , runtime
interfaces ( Xu et al., 2026 ) , and executable harnesses ( Dantanarayana et al., 2026 ) .
SkillCache complements both by preserving the supplied skill and separately storing a
specialization compiled from one completed skill-guided invocation. Execution-grounded specialization. Existing systems learn code routines, executable skills, or workflows from interactions,
demonstrations, and traces ( Wang et al., 2024 ; Wang et al., 2025a ; Zheng et al., 2025 ; Chen et al., 2026c ; Wang et al., 2026 ; El Hattami et al., 2026 ; Guo et al., 2026 ; Shao et al., 2026 ) .
SkVM ( Chen et al., 2026a ) compiles skills for different
model-harness targets and promotes code patterns after repeated signature matches across
invocations. TraceCompiler ( El Yadouni & Li, 2026 ) compiles clusters of agent traces
into mostly deterministic workflows. SkillTracer ( Li et al., 2026b ) localizes failures within skill plan graphs and repairs
the affected structure.
When external evaluation is available, PreAct ( Li, 2026 ) compiles one successful GUI trace
into a gated state machine, and SkillDroid ( Chen et al., 2026b ) compiles such a trace into an
action template replayed without per-step model calls. Other work likewise validates artifacts with verifier
feedback ( Rao & Kalluru, 2026 ) or deterministic checks ( Lu et al., 2026 ) . SkillCache instead specializes one
completed skill-guided invocation without benchmark reward or verifier access and retains the source skill for
recovery. Planning, program compilation, and harness optimization. ReWOO ( Xu et al., 2023 ) and Plan-and-Act ( Erdogan et al., 2025 ) separate planning from
execution, LLMCompiler ( Kim et al., 2024 ) parallelizes function calls while respecting task
dependencies, and Agent JIT Compilation ( Winston et al., 2026 ) turns web-task descriptions into
cost-ranked code plans before execution. DSPy ( Khattab et al., 2024 ) compiles LM programs, Meta-Harness ( Lee et al., 2026 ) searches
over harness code, and SoL-Pi ( Liu et al., 2026 ) searches for
token-reducing harness mechanisms, among them fusing a file edit and its follow-up command into one
tool call. SkillCache instead specializes a
supplied skill from one completed invocation into a capsule whose programs take whole runs of
deterministic tool calls away from the model. Unlike LLM-as-Code ( Qi et al., 2026 ) , where a program
also owns control flow and calls the model only for reasoning, our executor drives the capsule inside an unchanged agent harness. Procedural reuse and inference caching. Prior systems reuse model-readable insights, workflows, or procedural memories ( Zhao et al., 2024 ; Wang et al., 2025b ; Ouyang et al., 2026a ; Fang et al., 2026 ) , cache plan templates and
transitions ( Zhang et al., 2025b ; Kim et al., 2026 ) , build reusable tools ( Cai et al., 2024 ) , or
synthesize executable response generators ( Chakraborty et al., 2025 ) . At the inference layer, Prompt Cache ( Gim et al., 2024 ) reuses attention states across prompts, while Don’t Break the
Cache ( Lumer et al., 2026 ) evaluates exact-prefix prompt
caching for agentic workloads. SkillCache instead caches programs and natural-language steps derived from a
skill-guided trace. 10 Conclusion We study how repeated skill orchestration can be compiled into reusable execution. Compiling from the
skill and request alone does not reliably reduce tokens, so SkillCache
grounds each capsule in one completed execution, replays it before reuse, and drives it with a plan
executor, keeping the source skill for recovery. Warm executions use 81% and 74% fewer tokens with Sonnet and Opus at comparable

in zero-shot specialization and cross-model transfer. Matched conditions use the same provider defaults for
temperature and top_p . Within a task, executions run one after another. The cold execution, and
the direct execution of the zero-shot study, run first, and the order of the others rotates across tasks
so that none always runs first. An attempt runs again when the harness fails before the agent starts or
when the agent produces no output for ten minutes, and executions that could not run as planned run
again in a later invocation. In both cases the last finished attempt counts, regardless of reward. The
first run of each model reuses cold executions recorded earlier under the same execution protocol,
which serve as both its cold baseline and the input its compiler reads. The raw trace
baseline receives the observable trajectory the compiler reads, as JSON, with each image’s encoded bytes
replaced by a note, so that the baseline is not charged for base64 text that the cold model saw as an
image. In cross-model transfer and the cross-query probes, token comparisons exclude task-run pairs with
missing or incomplete usage records, including seven cross-model pairs with partially recorded provider
usage. Rewards cover every task and probe. Because parallel execution introduces
contention, we treat latency as system-descriptive. Latency additionally excludes tasks if any compared
execution ends in an error or lacks timing records. Cost uses the published list prices per million
tokens, $3 for input and $15 for output with Sonnet 4.6 and $5 and $25 with Opus 4.8, with cache
reads at 0.1 times and five-minute cache writes at 1.25 times the input price. We access all models
through hosted APIs. For environment compatibility, we patch three task images in every run. Two seismic images pin setuptools<81 to preserve the pkg_resources interface required by their dependencies,
and the civ6-adjacency-optimizer image makes its output directory writable by the unprivileged agent
user. The same images are used across matched conditions, with no change to requests, skills,
fixtures, evaluators, or scoring. For the later cross-model runs, the multilingual-video-dubbing image also pins four packages to their previous releases, because new releases broke its build. A.2 Zero-Shot Specialization This study runs once, with medium effort for direct execution, compilation, and capsule execution.

that no execution has happened yet, that it should use only the request and the source skills without

Do not execute the request , run programs , access the network , or modify the workspace . Return one capsule JSON object . ## What to keep The capsule serves future requests of the same kind with what worked in the observed execution . It repeats that path and does not re - derive or improve it . - Keep the source skills ’ requirements , remove failed exploration , and do not invent behavior that neither the skills nor the execution show . - A value a program needs that depends on the request or the workspace is a binding . This includes every value the request states . Keep every other value as the execution used it . - Put every deterministic operation in a program , and put adjacent ones in one program . - Reuse the code that worked , without rewriting it . If the execution ran a script that comes with a source skill , the program runs that same script from ‘ SKILLCACHE_ASSETS ‘, passes it the same arguments , and uses the same parts of its output . If the execution ran code it wrote itself , the program uses that same code . In both cases only the bindings change . - Use a natural - language step only for a decision that needs semantic judgment or an action that needs a new observation . The step says what to decide and what evidence to use . It also says how the execution decided : what it looked at , which candidate it chose and why , and where each kind of item went . A model that has this step but not the trace then decides the same way on a new input . Do not write the values the execution found or decided . - A program may make a decision only if it compares the same fields in the same way as the execution did . Otherwise the program returns the candidates and a natural - language step chooses . ## How the capsule runs A runtime executes the capsule . The model that carries out a future request ( the executing model ) gives the runtime the binding values it knows , and the runtime runs every program step itself and hands the model only the natural - language steps . - Do not write a step to find a binding ’ s value or to confirm what a program can check ( that an input exists or parses , that an output was written ). Put such checks in the programs . - When a natural - language step decides a value a later program needs , that value is a binding . The program lists it in ‘ inputs ‘, and the runtime asks the model for it after the step . - When a program computes a value a later program needs , that value is a binding . The program that computes it lists it in ‘ outputs ‘ and returns it in its ‘ result ‘, and the program that needs it lists it in ‘ inputs ‘. The runtime passes it on . - A binding carries a value a program needs ( e . g . a path , a parameter the request sets , a decision ). When a natural - language step produces a file ’ s content ( e . g . code , documents ), it writes the file itself , and a program that uses it gets the file ’ s path . The content is never a binding . ## Programs Programs are language - agnostic . - ‘ files ‘ holds complete source files by relative path . ‘ command ‘ runs them , and ‘ check ‘ checks their syntax or builds them without side effects . ‘ command ‘ and ‘ check ‘ are argument arrays that refer to the program ’ s directory as ‘{ package }‘. The host runs ‘/ tmp / skillcache - tool -- check ‘ on the capsule you return . Do not run it yourself . - A program reads its ‘ inputs ‘ from the JSON file at ‘ SKILLCACHE_INPUT ‘. The workspace is at ‘ SKILLCACHE_WORKSPACE ‘, the program ’ s own files at ‘ SKILLCACHE_PACKAGE ‘, and the source skills ’ files at ‘ SKILLCACHE_ASSETS ‘: the same ‘/ tmp / skillcache - source - skills ‘ you read . - Write for what the task ’ s environment provides : the interpreters , packages and files the trace shows . A Python 3 interpreter with its standard library is always available . - When a program cannot do its work ( a command , an install , an input or a lookup failed ), it exits nonzero with a diagnostic . It never reports a result it did not produce . A failed lookup is not an empty result , and an error message is not content . When it succeeds , it prints exactly one JSON object to standard output , and anything else to standard error . Its ‘ result ‘ holds what later steps need and any answer the request asks for : ‘‘‘ json {" status ":" complete "," result ":{}} ‘‘‘ ## Validation Record in ‘ examples ‘ the value each binding had in the observed execution , including those a natural - language step decided and those a program computed . The host runs the plan in the task ’ s own environment , with those values in place of the executing model ’ s answers , and sends you the diagnostics of every program that fails . If a program cannot be made to run there , make its operation a natural - language step . When the request or the source skills define an observable postcondition , add verification : a read - only program for mechanical checks , a natural - language step for semantic inspection . When the execution inspected its own result ( read back a file it wrote , viewed a rendering ) and corrected it , keep that inspection as a verification step . Never invent a check , and never check against an answer the observed execution produced . ## Output Return only this JSON object , with no wrapper : - ‘ name ‘: a lowercase identifier . - ‘ description ‘: the operation , when it applies , and what it answers and produces , specific enough that a model can tell when a request asks for something else . - ‘ bindings ‘: an object mapping every binding name , including each program ’ s ‘ inputs ‘ and ‘ outputs ‘, to how to obtain its live value ( for an output : what it is and which program computes it ). - ‘ programs ‘: an object mapping program names to ‘{" command ": [...], " check ": [...], " inputs ": [...], " outputs ": [...], " files ": {...}}‘. ‘ inputs ‘ and ‘ outputs ‘ are arrays of binding names . ‘ outputs ‘ is optional , lists only values a later program reads , and never repeats an input . ‘ files ‘ maps relative paths to complete file contents . - ‘ steps ‘: a non - empty array of ‘{" instruction ": ..., " program ": ...}‘, with ‘ program ‘ only on a program step . - ‘ verification ‘: an array of steps in the same form as ‘ steps ‘, empty when no grounded check exists . - ‘ examples ‘: an object mapping binding names to their observed values . It only tests the capsule and is never shown to the executing model . An answer the request asks for goes in a program ’ s ‘ result ‘, not in ‘ outputs ‘. Every program appears in a step . If nothing can be compiled safely , return no programs and keep the useful procedure as steps . Never include credentials or generation - time paths .
