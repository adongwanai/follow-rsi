The lower layers run exactly up to a split; from the split layer’s state a per-layer map predicts every later layer’s input, and each late layer writes its cache from that prediction. The design follows YOCO and DeepSeek-V4.1-Flash, where the projection is trained into the model. RidgeFill retrofits it onto models that were never trained for it: the map is a ridge regression fitted once in closed form from one pass over calibration text, the layer’s own projections run unchanged, and a chosen set of rows, the last few thousand tokens, and every decoding step run the full model. Nothing is trained and no token is dropped. Most of the work was in measurement, finding a repeatable methodology. Loss averaged over all tokens hides RidgeFill’s error. Needle retrieval in the filled region, loss on tokens that depend on distant context, and splice tests that swap filled keys or values for exact ones show which component carries it: the keys on Llama-3.1-8B, half of it in their scale, and the values and the recurrent state on Qwen3.5-9B. On Qwen3.8-27B in a llama.cpp fork on an A100, time to first token is 1.25 to 1.31 × \times faster at 16K to 120K tokens with the maps in VRAM; RULER changes by − - 1.2 and − - 1.4 points and LongBench v2 by − - 1.4; the 95 % intervals include zero but do not rule out losses of a few points. On Qwen3.8-Flash-Next in vLLM it is 1.50 to 1.60 × \times faster than exact at 9K to 32K tokens, with RULER’s needle tasks at 99.8 against 100.0 and perplexity on novel tokens 2.65 % higher [ − - 0.02 %, +4.93 %]. On three 8 to 9B reference models, at the same split and tail as the identity fill, the fitted map retrieves 49.1 and 49.6 more filled-region RULER points on the two dense models (at that split Llama’s loss is worse), and its long-document loss is within 0.03 nats of the released SwiftKV checkpoint’s. 1 Introduction For a long prompt, prefill is the wait before a response, and the user sees nothing until it completes. Before the first output token, a decoder runs every prompt token through every layer. At 120,000 tokens on Qwen3.8-27B that is 128 seconds on an A100. Decoding the answer afterwards is comparatively fast. RidgeFill shortens the wait by not fully computing most of the upper layers. It runs the lower layers exactly up to a split layer, whose depth is one of two settings a deployment chooses. From the split layer’s hidden state, RidgeFill predicts the input to every later layer. Each late layer then computes only its key and value projections from that prediction, or in a Gated DeltaNet layer its recurrent state update, and skips the rest of the layer, MLP included, for most prompt tokens. Seen this way, the method is speculative decoding (Leviathan et al., 2023; Chen et al., 2023) run backwards (Figure 1 ). Decoding is bandwidth-bound and has compute to spare, so a draft model or head (DeepSeek-AI, 2024) spends that compute guessing tokens the model then verifies. Prefill is the opposite. Each weight read is reused across hundreds of prompt rows, so the GPU is limited by arithmetic, not by memory bandwidth. RidgeFill spends the spare bandwidth on extra reads: one map for each late layer, held in VRAM or in host memory. Each map predicts its layer’s input. For most prompt rows, the layer writes its cache from that prediction and skips the rest of its computation. Figure 1: Speculative decoding and RidgeFill each spend the resource their phase has spare. Decoding is bandwidth-bound, so a draft head spends the spare compute guessing tokens and the full model verifies every guess. Prefill reuses each weight read across hundreds of prompt rows, so it is limited by arithmetic. RidgeFill spends the spare bandwidth on extra reads, the fill maps from VRAM or host memory, and in return skips most of the late layers’ arithmetic. A filled cache has no affordable verifier, so the rows most likely to matter are kept exact instead (§ 2.4 ). The idea comes from DeepSeek-V4.1-Flash (DeepSeek-AI, 2026), which builds on YOCO (Sun et al., 2024). In that model the upper layers take their caches from a projection of a middle layer’s state, and the whole model is trained to absorb the error. The day it came out, Hugging Face user “kishida” retrofitted the design onto Qwen3-8B as the KVA projector (kishida, 2026): trained per-layer heads that write the late layers’ keys and values directly from the layer-18 state. RidgeFill differs in three ways (Figure 2 ). First, it predicts each late layer’s input rather than its keys and values, so the layer’s own projections run unchanged, and on a hybrid model so does its recurrent state update. Second, the map is a ridge regression, fitted once in closed form from one pass over calibration text. The process requires no training steps. Third, it does not approximate every token the same way. Some rows, meaning a token’s entries in the late layers’ caches, are computed exactly, and choosing which ones turned out to be most of the challenge. Figure 2: Two ways to fill a late layer’s cache from a middle layer’s state. (a) kishida’s KVA projector: trained heads on the layer-18 state write each late layer’s keys and values directly, bypassing the layer’s own key and value projections. (b) RidgeFill: a closed-form ridge map predicts each late layer’s input; the layer’s own projections run unchanged, and on a Gated DeltaNet layer so does its state update. Exact rows (§ 2.4 ) skip the map and run the layer from its exact input. Initial efforts focused on finding the method’s ceiling. An approximation has random error in it, and the problem resembled digital-to-analog conversion: a lossy stage whose output has to land inside the next stage’s acceptance band. So we reached for the tools that solve that problem in other domains, where they work. Jensen’s inequality for the softmax, Gaussian closures for the keys, Nyquist’s argument for what could be interpolated between exact samples. None of them beat what we already had. The Jensen and Gaussian corrections left the attention error they target unchanged or made it worse, by up to 80 %. The best of the other corrections lowered that error by 8.6 % and left the loss where it was. The fill’s error is close to white noise from one row to the next, so there is nothing between exact samples to interpolate (Appendix I.1 ). The analogy fails on its premise. A converter normalizes its input and knows its target. A prompt is not known until it is being processed, it is different every time, and the only definition of the correct output is the full model run on it. Those tools also treat the error as independent of what will be asked. It isn’t. The underlying structure that we spent most of our time in pursuit of showed up initially in needle tests. The first results were not inspiring: on needles inside the filled region, the model returned the right number, save for the last digit, which was wrong (Appendix I.2 ). The fallout from this illuminated our primary concepts of how to improve accuracy. We had been reading the needle test as a score, but it is also an error instrument. It says where the fill fails, and it failed on strings the model has to copy exactly: numbers, identifiers, names. Rather than trying to project those, we stopped filling them and ran the rows exactly. Running them exactly resulted in the digit needles recovering. Exact digit rows did little or nothing for needles that were not numbers (Appendix I.2 ). Using this methodology, we applied similar concepts elsewhere and generalized the rules; the selectors that shipped choose rows by attention or by token class, not by digit (§ 2.4 ). That is also precisely where we discovered our initial means of measurement to be wrong. We had been measuring how far the fill erred on each token. That error is nearly flat across kinds of tokens, which is reassuring and tells you nothing. What is not flat is what an error costs in relation to specific tokens. The damage concentrates in a small share of the prompt’s tokens (Appendix I.3 ), and which tokens those are depends on what will be asked. The useful measurements are which part of the cache carries the error and which way it leans. Splice tests answer the first: swap the filled keys for exact keys and see how much loss goes away, then the values, then both. On Llama-3.1-8B the error is in the keys, half of it in their scale. On Qwen3.5-9B it is in the values and the recurrent state. On Qwen3-8B keys and values have to be fixed together. The corrections in the method answer the second. The value rescale and, in Flash-Next’s quality mode, the terminal-state correction each target an average error of the kind the splices exposed, pushing the filled cache back toward the mean; neither was ablated on its own in the final runs. The exact rows remove the error outright where it costs the most. Unlike speculative decoding, RidgeFill cannot verify (Figure 1 ). The only judge of a filled cache is the full model, and running the full model on every row is exact prefill at exact prefill’s cost. We have tried this. It works. Cheaper checks only say where to look: one that scores every filled row at each decoding step added 8 to 18 % to decoding time, and one that checked each row every few steps missed rows that needed repair in 15 to 98 % of steps (Appendix I.4 ). So the goal inverted. Not to make the fill right as often as possible, which ends in training it, but to find what it gets wrong the most and compute those rows exactly. The rest followed from asking what else predicts where the damage lands. Attention does. Put the question at the end of a long prompt and the lower layers’ attention from those last tokens falls on the rows that answer it. Running those rows exactly restores retrieval on two of the three reference models (§ 6.5 ). Hiding the question from the selector costs 16 and 14 points, more than half of what choosing the rows adds over random rows of the same count. An exact tail of the most recent tokens does the same for recent context; its length is the second setting a deployment chooses. On Qwen3.8-Flash-Next, an optional quality mode also keeps exact the rarest tokens of the classes that carried the most damage in development. Each of these is a rule a server can apply with no training. The attention rule rests on a property of softmax attention: a token’s influence on the output is bounded in proportion to the attention it receives (§ 2.4 ), so the rows that receive the most attention from the queries that will be asked are the rows to keep. One tradeoff does not move. In an architecture that prefills every token through every layer, a method that skips part of that work cannot be both lossless on every prompt and faster than exact (Table H.1 ). One that manages both is a better kernel, and that is someone else’s paper. Exact rows buy quality at exact cost. Filled rows buy speed at some loss. The split depth and the tail length pick the point on that curve. This paper measures the curve rather than claiming a point on it. For orientation, at split 16 of 64 on Qwen3.8-27B, with the maps in VRAM, prefill is 1.25 to 1.31 × \times faster at 16K to 120K tokens. The cost is 1.2 and 1.4 points on RULER at 16K and 32K and 1.4 points on LongBench v2. The intervals include zero but do not rule out losses of a few points. We measured on official protocols where they exist, and where they do not, on the community’s own instruments: perplexity and KL against the unmodified model, which on the 27B we call stock. Other ways to skip late layers. Prior methods differ in what happens to a skipped token’s cache and in whether anything is trained (Table 1 ). POP (He et al., 2026) fills the cache with the identity and trains nothing. SwiftKV (Qiao et al., 2025) fills it with distilled projections, and KV Prediction (Horton et al., 2024) with a trained auxiliary model. TokenGate (Patel et al., 2026) drops tokens above a learned gate and fine-tunes the backbone, and SPEED (Oh et al., 2026) drops prompt tokens from the upper layers and fine-tunes for it, while FastKV (Jo et al., 2026), GemFilter (Shi et al., 2024) and LazyLLM (Fu et al., 2024) drop tokens by attention-based rules. RidgeFill fills the cache with a closed-form map and trains nothing. At the same split and tail, the fitted map scores 39.7 and 49.6 points higher than the identity fill on filled-region needle retrieval for Llama-3.1-8B (8K to 64K) and Qwen3-8B (8K to 32K). On the hybrid Qwen3.5-9B the gap is 3.3 points, with an interval through zero. RidgeFill stays non-inferior to POP on retrieval, within a 3-point margin, even when it skips more layers than POP’s published configuration, though at more multiply-accumulates than POP below about 46K tokens on Llama and 59K on Qwen3-8B (§ 6.4 ). SwiftKV is the trained version of the same idea. Its authors released it for three Llama models; we test the 8B, Llama-3.1-8B, whose distillation run took about 680 million tokens. As released, at its own split, it ties RidgeFill: +0.010 nats, with an interval through zero. Placed inside RidgeFill’s pipeline with the same exact tail, SwiftKV’s trained projections beat the ridge map by 0.024 nats. That is what the training buys on that model, with our tail. We do not compare against TokenGate at a matched budget. It trains and drops tokens, which puts it in a different cell of Table 1 , and it reports larger speedups for that cost. Of the fill methods in Table 1 , RidgeFill is the only one that improves on the identity fill without training: on filled-region retrieval, by a wide margin on both dense models, although at Llama’s primary split its loss is worse. A prompt has N N tokens. We call each prompt token’s position a row. A deployment chooses two numbers: the split S S , which is a layer number, and the tail length T T , which is a number of tokens. Layers 0 0 to S − 1 S-1 run exactly for every row. The last T T prompt tokens, the tail, run every layer exactly, as does every generated token. The remaining N − T N-T prompt tokens are the prefix. In the late layers, from S S up, a prefix row is either exact or filled. An exact row runs every layer normally, like the tail; § 2.4 describes how exact rows are chosen. Filled rows are where the savings come from. In a normal forward pass, each layer’s input is the previous layer’s output, so reaching layer 40 means running layers 16 through 39 first. RidgeFill breaks that chain for filled rows. Write x ℓ x_{\ell} for the hidden state entering layer ℓ \ell . RidgeFill predicts each late layer’s input, x ^ ℓ \hat{x}_{\ell} , directly from a single state, x S x_{S} , the hidden state entering the split layer. On the 27B, with the split at 16, a filled row’s input to layer 40 comes straight from its layer-16 state, so layer 40 doesn’t wait on layers 16 to 39. From x ^ ℓ \hat{x}_{\ell} , each late layer computes only what later tokens will read from that row: keys and values in an attention layer (and, on Flash-Next, the sparse-attention indexer’s keys, § 5.1 ), and the recurrent state update in a Gated DeltaNet layer. Everything else in the layer, including the MLP, is skipped for that row. The tail reads the filled rows, so the tail’s outputs can differ from exact even though the tail itself is computed exactly. That cost is included in the compute-matched controls (§ 3.3 ), in the POP comparison (§ 2.5 , § 6.4 ), and in the 27B’s multiply-accumulate shares (§ 4.2 ). 2.3 Hybrid layers and two corrections Three of the five models are hybrids. Qwen3.5-9B, Qwen3.8-27B and Qwen3.8-Flash-Next interleave Gated DeltaNet layers (Yang et al., 2025b) with attention layers. A Gated DeltaNet layer keeps one recurrent state instead of a key-value cache. At every token, it multiplies its state by a gate between 0 and 1 and then adds the new token’s update, so older tokens fade. That difference decides where the fill’s error ends up. In an attention layer, a filled row’s error stays in that row’s keys and values. In a Gated DeltaNet layer, every filled row updates the shared state from its predicted input, so all of their errors are folded into the state the tail inherits. Two corrections push the filled cache back toward the exact one. Each removes an average error rather than predicting any one token’s error, and neither is trained. Value rescale. In each late attention layer, the first c c tail rows go through the layer’s value projection twice: once from their true input and once from the map’s prediction for the same rows. For each key-value head, the ratio of the exact value norm to the predicted one, averaged over the c c rows, gives a scale. The filled prefix rows’ values are multiplied by that scale before the tail reads them. The scale is measured on every request, from that request’s own tokens. The correction targets values because the Qwen models normalize their keys, which fixes each key’s size and leaves a key rescale little to correct (§ 6.6 ), while values have no such normalization. On Llama-3.1-8B, which does not normalize its keys, a key rescale halves the fill’s added loss (the added loss on novel tokens, § 3.1 , falls from +1.006 to +0.502 nats at split 12) and a value rescale makes it worse (§ 6.6 ). Of the three deployments, only the 27B uses the value rescale, with c = 512 c=512 (Table 4 ). Terminal-state correction. Flash-Next’s quality mode (§ 5 ) corrects the recurrent state directly. At the end of the prefix, it adds ρ ℓ ​ Δ ​ M ℓ \rho_{\ell}\,\Delta M_{\ell} once to the state of each filled Gated DeltaNet layer. Δ ​ M ℓ \Delta M_{\ell} is the average difference between the exact and the filled state, per layer and value head. It is measured every 2,048 tokens (62 states per layer) on 13 calibration prompts kept apart from the maps’ calibration text and from every evaluation set. ρ ℓ \rho_{\ell} is the share of the state that still comes from filled rows. Each token’s update is shrunk by every gate that comes after it, so a token’s weight in the state is the product of those later gates. ρ ℓ \rho_{\ell} is the filled rows’ total weight divided by all rows’ total weight, read per request from the gates the fill computes anyway. Scaling by ρ ℓ \rho_{\ell} makes the correction match how much of the state is actually filled: Appendix H shows that, in a simplified model without the delta rule’s erase term, if the fill shifted every filled row’s update to the state by the same amount, this scale removes the shift exactly and any other scale leaves part of it. Behind an exact tail, the filled rows’ share of the final state is tiny on layers whose gates are small, because they have faded by the time the tail ends; the error and the correction fade together (Figure 4 ). The 27B and the reference study run without it. 2.4 Exact prefix rows A chosen subset of prefix rows runs every layer exactly, in addition to the tail. These rows cost full-model compute, so the selector’s job is to spend them where the fill’s error would do the most damage. The paper uses three selectors, one per deployment. None has a trained component, and each works from quantities available at prefill time. Attention-selected rows. The reference study (Llama-3.1-8B, Qwen3.5-9B and Qwen3-8B) keeps exact, in its “+ rows” arms, the 10 % of prompt tokens that receive the most attention from the last 64 prompt tokens. Attention is summed over the heads of every attention layer among layers 3, 7, 11 and 15 that lies below the split. When a question ends the prompt, these are the tokens the question attends to, so the selector is query-aware. In the long-document loss measurements, the 64-token window is the stretch just before the scored continuation, which is not a question. Every selection is compared with two controls of equal cost: the same number of randomly chosen rows, and the same number of rows added to the exact tail. Why attention. The rule rests on a bound on how much a row’s error can change what a later token reads from it. Take a query i i , a token near the end of the prompt, and let a i ​ j a_{ij} be the attention it pays to row j j . Let V V be the largest value norm among the rows query i i attends to. If row j j ’s value vector changes by δ \delta , query i i ’s attention output changes by exactly a i ​ j ​ δ a_{ij}\delta . If row j j ’s attention score (the logit before the softmax) changes by ε \varepsilon , the output changes by at most 2 ​ V ​ a i ​ j ​ ( e | ε | − 1 ) 2Va_{ij}(e^{|\varepsilon|}-1) . Both bounds scale with a i ​ j a_{ij} . So if the fill’s error were the same size at every row, keeping exact the rows with the largest summed attention would minimize the total of these bounds over the queries. It is not the same size everywhere, which is why the other two selectors also protect tokens by what they are. The reference selector measures attention in the lower layers, as a proxy for the late layers that read the filled rows. The 27B probe below measures it in the late layers directly. Protected-token rows. The quality mode of § 5 , Qwen3.8-Flash-Next, protects tokens by what they are rather than by what the question attends to. Four token classes are eligible: capitalized word starts, capitalized word pieces, lower-case word pieces, and mixed tokens (not all letters, not all punctuation, and not digits with punctuation). On a 300-document development corpus, measured on Llama-3.1-8B and Qwen3.5-9B at split 12, these classes carried 1.2 to 1.7 times their share of the fill’s first-order damage (Appendix I.3 ). Lower-case word starts carried 0.8 to 0.9 times their share and plain numbers 0.8 to 1.05 times theirs, so neither class is eligible. Of the eligible tokens, the rarest 25 %, by add-one unigram frequency over the calibration documents, run exactly. On the Flash-Next run this came to 3 to 10 % of prefix positions. The selector does not read the question. The 27B selector. Qwen3.8-27B (§ 4 ) keeps exact the rows chosen by a probe, plus special tokens and lexical-net rows, on top of the tail. Figure 5 shows the order in which these run. Figure 5: The two-sweep prefill on Qwen3.8-27B, split at layer 16. (1) The first sweep runs layers 0 to 15 for every row and writes the prefix rows’ late attention caches from the maps; the tail and the late Gated DeltaNet layers are not yet computed. (2) The probe: the last 256 rows run the exact late layers over the filled cache, with the Gated DeltaNet layers starting from an empty state, and every prefix row is ranked by the attention it receives from them. The probe runs once the first sweep (Figure 5 ) has run the lower layers for every row and written the prefix rows’ late attention caches from the maps. The last 256 prompt rows then run the exact late layers over that filled cache, and every prefix row is ranked by the attention it receives from those 256 rows, summed over the late attention layers and their heads. The highest-ranked rows are kept exact. Because the probe reads the real late layers’ attention on the real filled cache, it measures what the question attends to in the layers that will answer it. The number of rows the probe keeps is a count, not a share (Figure 6 ). It equals the number of rows the base rules would have selected on the same prompt: the union of the rarer half of the protected-class matches, every digit token, and 20 % of the prefix ranked by lower-layer question attention, multiplied by a budget factor that is 1.0 in this paper. The probe’s ranking replaces the rows those rules would have chosen, and only their count carries over. Digit tokens therefore set the size of the budget but are not kept exact unless the probe ranks them highly. On the 27B timing prompts the count came to 28 to 31 % of the prefix. The probe itself costs 256 rows through the late layers, about 1.6 % of a 16K prompt’s late-layer rows, plus their attention over the prefix. Figure 6: How the probe’s budget is set. The base rules, the rarer half of the protected-class matches, every digit token, and the top 20 % of the prefix by lower-layer question attention, are used only to count E E , the number of exact prefix rows. The probe fills E E with the rows that receive the most late-layer attention from the last 256 rows; lexical-net rows are reserved inside E E , at most 5 % of the prefix. Special tokens are added on top, and the 4,096-token tail is outside the count. On the 27B timing prompts E E came to 28 to 31 % of the prefix. Special tokens (control, unknown and user-defined tokens) also run exactly, on top of the probe’s count. A prompt contains few of them, and there is no cap. Lexical-net rows catch the identifier the question names. A sentence of the prefix is kept exact if it shares a run of four or more words with the last 64 content tokens of the prompt, and that run contains a word occurring no more than twice in the whole prefix. Content tokens exclude control and chat-template tokens, so in a chat prompt the window is the end of the user’s last turn. At most the first 80 rows of a sentence are kept, and at most 5 % of the prefix in total. Unlike special tokens, lexical-net rows count against the probe’s budget. Appendix H gives the word and sentence normalization rules. The tail is separate from all of this. It runs exactly in every deployment and never counts against the selector’s budget. Its length is 4,096 tokens everywhere except Flash-Next, which uses 2,048 (Table 4 ). Two sweeps. The 27B prefill therefore runs in two sweeps. The first sweep runs the lower layers for every row and writes the prefix rows’ late attention keys and values from the maps; the tail and the late Gated DeltaNet layers wait. The probe then runs the last 256 rows through the exact late layers, with the Gated DeltaNet layers starting from an empty state, and ranks the prefix. The second sweep runs the late layers for the exact rows and the tail, reusing the filled keys and values for every other row. In the Gated DeltaNet layers the state has to be carried through the prompt in order, so the second sweep computes it once, over every prefix row: from the true input on exact rows and from the predicted input on the rest. Section 4 calls this the two-sweep prefill (Figure 5 ). Each selector is a rule the server applies at prefill time. The probe is the training-free counterpart of a learned gate: instead of a scorer trained to predict which rows the late layers will attend to, it reads that attention directly. 2.5 Compute A simple count gives a ceiling on the speedup. On Qwen3-8B at the primary split, the fitted fill and the identity fill differ by 0.019 nats of loss on novel tokens, the ones the model cannot copy from earlier in the document, a number small enough to read as nothing or as a slight cost. On the same runs the identity fill retrieves 44.0 % of the needles that lie in the filled region and the fitted fill retrieves 93.7 % (Figure 8 ). As it turns out, loss averaged over tokens was the wrong stick. Most scored tokens do not depend on the prefix, so the fill’s error is diluted by tokens it cannot affect. Figure 8: Qwen3-8B at the primary split: loss on 90 documents (63 for key tokens) and filled-region retrieval on 138 RULER samples. Every measure in this section is chosen to avoid that. A needle in the exact tail is never filled and says nothing about the fill, so filled-region retrieval excludes it. A token the model predicts as well from the last 4,096 tokens as from the whole prompt does not test the prefix cache, so key-token loss excludes it. Splice tests replace one component of the filled cache with its exact counterpart, so the loss that remains names the component. And a mean with a heavy tail is reported next to its median: on the 27B, the mean KL at 32K is driven by five copy-heavy documents, while the median is 0.004. The line between fixing what a benchmark shows and fitting to the benchmark is thin. We drew it in three places. A fix had to be a general rule, not a pattern matched to the test: token classes, attention received, and rarity. The tests that count are official suites we did not build, with count-matched random controls beside every selected-row arm in the reference study. And once our own needle suites passed a configuration that failed RULER’s multi-key tasks, we stopped using them for any decision (Appendix I.5 ). This scores RULER’s needle tasks only on the samples whose needles all lie in the prefix, before the exact tail (Figure 9 a). The set of samples is fixed per model and shared by every arm and split; this works because the tail has the same length at every split. Loss on tokens that need the prefix. On long documents we report Δ \Delta NLL, an arm’s loss minus the exact arm’s, in nats per token. We report it on two subsets of the scored tokens, because the average over all of them hides the fill’s effect. Novel tokens are those not inside any 8-token run that also appears earlier in the prompt, so the model cannot simply copy them. Key tokens are those whose exact loss rises by more than 2 nats when the context is cut to its last 4,096 tokens, that is, when the prefix is removed (Figure 9 b). These are the tokens the prefix actually helps, so Δ \Delta NLL on key tokens measures how much of the prefix’s contribution the fill keeps. This deployment differs from the 27B in engine, architecture and hardware, and it reads most routed-expert weights over PCIe during prefill. 5.1 Model, engine, hardware Qwen3.8-Flash-Next (Qwen Team, 2026b) has 48 layers. Every fourth layer, 12 in all, is a sparse-attention layer, and the other 36 are Gated DeltaNet. Each sparse-attention layer has a small indexer, four 128-wide query heads sharing one key head, that picks which blocks of keys each query attends to. The feed-forward blocks are mixtures of experts, and the residual stream is four Gated Residual streams (§ 2.2 ). We serve an MXFP4/FP8 quantization of the model (Smith, 2026a) in a vLLM fork (Smith, 2026b). One file in the fork is replaced to make the indexer’s block selection deterministic, which costs 5 to 7 % of decode throughput; every arm runs with it (Appendix F lists the builds). The model runs tensor-parallel on two AMD Radeon AI PRO R9700 GPUs. About two thirds of the routed experts, 16,042 of the 24,576 on each GPU, live in pinned host memory and are read over PCIe during prefill. Every arm uses the same placement. 5.2 Configuration The split is at layer 24 of 48, which leaves 6 sparse-attention and 18 Gated DeltaNet layers above it, and the exact tail is 2,048 tokens. The maps are the public release TheCacheIsALie/RidgeFill-Projector-Qwen3.8-Flash-Next-i8 : one int8 map per late layer, fitted with λ \lambda = 0.03 on activations of the quantized model as served, captured through the engine from 151 calibration documents (§ 2.2 , Appendix G ). In the sparse-attention layers, filled rows write the indexer’s keys as well as the attention keys and values. Plain RidgeFill keeps no exact prefix rows and uses neither correction. Quality mode adds the terminal-state correction and protected-token rows (§ 2.3 , § 2.4 ). Table 4 (§ 2.6 ) lists both configurations. Exact, plain RidgeFill and quality mode each ran their quality measurements on their own server start, meaning their own launch of the serving process; exact also runs inside the other two starts for the timings. The perplexity and RULER results are paired per document or per sample against exact’s start; only the timings alternate with exact inside a single start. Two checks support comparing across starts, and one is missing. Exact’s two perplexity passes on its start are bitwise identical on all 90 documents. With the fill switched off, the quality-mode start reproduces exact bitwise on 6 of 6 documents. The plain RidgeFill start ran no such check, though it used the same container image, replaced file and arguments. 5.3 Results How each number is measured. Table 15 gives quality and Table 16 speed. This deployment does not test the premise that prefill is compute-bound with bandwidth to spare. Filled rows run no expert block in layers 24 to 47, and plain RidgeFill keeps no exact prefix rows, so only the tail reads the late layers’ experts. If each chunk of the prompt reads only the offloaded experts it uses, expert traffic over PCIe shrinks by the same ratio as compute, to about 0.61 of exact at 9K and 0.53 at 32K (the r r of § 2.5 ). A compute-bound prefill and a PCIe-bound one therefore predict the same ceiling, and reaching 85 to 92 % of it can’t tell them apart. Expert traffic was not measured. No 126-document interval exists for RidgeFill at 5/8 − - POP native, so only its point estimate is shown. 7 Related work Methods that skip late layers for prompt tokens differ in what happens to a skipped token’s cache and in whether anything is trained (Table 1 ). This section takes the cells of that table in turn, then the closest neighbors outside it. Fill, pretrained in. YOCO (Sun et al., 2024) and the causal encoder-decoder of DeepSeek-V4.1-Flash (DeepSeek-AI, 2026, Sec. 2.2) serve the upper layers’ caches from a projection of a middle layer’s state, and train the whole model with that structure in place. RidgeFill retrofits the same design onto models that were not trained for it. Fill, trained retrofit. SwiftKV (Qiao et al., 2025) prefills later layers’ KV caches from an earlier layer’s output and recovers quality by distilling the skipped layers’ Q/K/V projections from the original model, about 680 million tokens for Llama-3.1-8B. KV Prediction (Horton et al., 2024) runs a small auxiliary model over the prompt and maps its cache to the base model’s with a trained predictor, keeping the base model frozen. It reports a 25 to 50 % cut in prefill compute with little loss in accuracy, and quality falling off quickly beyond 50 %. On the day DeepSeek-V4.1-Flash was released, kishida retrofitted its design onto Qwen3-8B as the Q3-8B-KVA-Projector (kishida, 2026), with trained per-layer key and value heads that read from layer 18. 1 1 1 The name KVA comes from kishida’s projector and is kept in our engine code. RidgeFill differs from all three in two ways: its fill is fitted in closed form and predicts each layer’s input, so the layer’s own projections still run, and it keeps an exact tail. Fill, identity. POP (He et al., 2026) prunes the last third of the layers during prefill. Each pruned layer writes its keys and values from its own projections of the unchanged hidden state, and the last prompt token runs through the full model. POP reports up to 1.37 × \times faster prefill at 2K tokens and a sharp decline past 50 % pruning. Its long-context evaluation uses two LongBench QA tasks and no needle tests. At the same split and tail, POP’s fill is the identity arm of § 6 . Both SwiftKV and POP report quality falling off once more than half the layers are skipped. RidgeFill’s primary split skips about 5/8 of them. On the two Qwen models its novel-token loss there stays within 0.05 nats of exact, but on Llama it rises to +1.006, the same falling-off; at half depth Llama recovers to +0.085 (§ 6.1 ). Drop, trained. TokenGate (Patel et al., 2026) places a learned gate at an early layer, layer 1 in its main experiments, and keeps only the highest-scoring tokens. The layers above the gate neither process the pruned tokens nor write cache entries for them. TokenGate fine-tunes the backbone with LoRA jointly with the gate, separately for each task, and reports 1.4 to 11.3 × \times faster time to first token and 1.5 to 3.4 × \times lower peak memory on Qwen3-1.7B and Qwen3.5-2B. SPEED (Oh et al., 2026) keeps prompt tokens’ cache entries only in the lower layers, apart from a start-of-sequence anchor, and runs decoding at full depth. On Llama-3.1-8B, instruction-tuned for it, with 75 % of the layers for prompt tokens, it reports 33 % faster time to first token at 128K and a benchmark average of 51.2 against 51.4. Dropping a token removes its cache entry, and the memory with it; filling keeps both. Neither method is compared at a matched budget: TokenGate trains per task, SPEED trains once, and both drop tokens. Drop, training-free. FastKV (Jo et al., 2026) keeps the full context up to a chosen layer and propagates only the selected tokens past it. GemFilter (Shi et al., 2024) uses an early layer’s attention to pick the tokens that matter and reruns the model on those alone. LazyLLM (Fu et al., 2024) prunes tokens progressively across layers and can bring a pruned token back at a later step. Speculative Prefill (Liu et al., 2025) belongs here too, despite its name: it uses a small model to pick which prompt tokens to keep and drops the rest. All four select tokens without training. Linear replacement of layers. ReplaceMe (Shopkhoev et al., 2025) removes a run of transformer blocks and replaces them with one linear map estimated from a small calibration set, with no training. It is one of the closest training-free uses of a fitted linear map. ReplaceMe changes the model for every token, decode included, while RidgeFill leaves the weights and the decode path untouched and approximates only the prompt’s late-layer caches. Heo et al. (2026) fit per-head ridge maps in closed form to transfer KV caches between models of one family, so that a larger model can skip its own prefill. Query-aware selection. The attention-selected rows of § 2.4 follow SnapKV (Li et al., 2024a), which scores prompt tokens by the attention they receive from an observation window at the end of the prompt. Quest (Tang et al., 2024) is query-aware in the same sense at decode time, choosing cache pages by their estimated attention to the current query. Those methods use the scores to evict or skip cache entries. Here the scores choose which prefix rows run exactly, and the question-blind control (§ 6.5 ) measures how much of the selection’s value depends on the question being in the window. Sparse attention and prompt compression. MInference (Jiang et al., 2024) and FlexPrefill (Lai et al., 2025) reduce the attention computation itself, and LLMLingua-2 (Pan et al., 2024) shortens the prompt. Both approaches are orthogonal to skipping layers, and Flash-Next (§ 5 ) already runs RidgeFill on top of its native sparse attention. Speculative decoding. Speculative decoding (Leviathan et al., 2023; Chen et al., 2023) speeds up decoding by having a cheap draft propose tokens that the full model then verifies in one pass. Medusa (Cai et al., 2024) and EAGLE (Li et al., 2024b) draft with extra heads on the model itself, and LayerSkip (Elhoushi et al., 2024) drafts with the model’s own early layers. DeepSeek-V3 (DeepSeek-AI, 2024) trains a multi-token-prediction module that can serve as a drafter, and Flash-Next ships one. Section 1 frames RidgeFill as the same trade run in the other direction (Figure 1 ). 8 Limitations Shallow splits on a model without QK-norm. QK-norm normalizes each query and key before attention, and Llama-3.1-8B has none. On Llama at the primary split, 3/8 depth, RidgeFill’s novel-token loss is 0.50 nats above the identity fill’s. On long documents it is worse than no fill at all: on 32 of the 36 documents of 64K tokens or longer, and on none of the 90 shorter ones. The worst is 128K tokens of source code, where RidgeFill’s Δ \Delta NLL against exact is +8.19 nats and no fill’s is +0.74. Its filled-region retrieval is still 39.7 points above the identity fill’s, 49.4 against 9.7. Splicing exact keys and values into the filled cache puts the error in the keys, and half of it in their scale (§ 6.6 ). At half depth the order reverses: the fitted fill’s loss is 0.478 nats below the identity fill’s on the 126 documents and 0.533 below on 30 fresh ones (§ 6.7 ). On a model without QK-norm we recommend a split at half depth or deeper, or attention-selected rows, which bring the source-code document down to +0.180 (§ 6.5 ). Those rows depend on the question, which has its own cost (below). Key tokens. Key tokens are the ones whose loss rises by more than 2 nats when the context is cut to its last 4,096 tokens (§ 3.1 ), so they measure what the prefix contributes. On them, RidgeFill alone at the primary split is 1.2 to 3.3 nats above exact across the three reference models, and attention-selected rows bring that down to 0.4 to 0.7. A needle score does not show this cost. With the rows, Llama and Qwen3.5 retrieve 99.5 and 99.9 from the filled region, level with exact, and their key-token loss is still 0.41 and 0.43 nats above it. Check key-token loss, and not only retrieval, before choosing a split. Row selection. The paper uses three row selectors, one per deployment, each tuned on its own development data, and we do not claim that any of them is the right selector for a new model. Two of the three depend on the question. Attention-selected rows lose 16 and 14 points of filled-region retrieval on Llama and Qwen3.5 when the question is hidden from the selector (§ 6.5 ). The 27B’s probe ranks rows by the attention they receive from the last 256 prompt rows, which normally hold the question, and it was never run with the question hidden. On Qwen3-8B, attention-selected rows lower retrieval from 93.7 to 89.9 while random rows of the same count reach 93.8, and we have not established why. Caches reused across questions. A cache filled once and then asked several questions should not rely on a selector that reads the first question. Appendix D asks each reference model a second question of a cache filled, and its rows chosen, for the first. With the rows, Llama and Qwen3.5 still retrieve every second needle in the filled region, but the test is weak for this purpose. The second question asks for another key from the same template, and the rows chosen for the first already cover a median of 85 % and 86 % of the second needle’s tokens. It does not show that rows serve an unrelated question. For such a cache, the option the evidence supports is a deeper split with no rows: on Llama at half depth, RidgeFill alone retrieves 96.1 at 8K to 32K (§ 6.7 ). A selector that ignores the question, such as the protected tokens of Flash-Next’s quality mode, is the other candidate, but quality mode’s paired difference from plain RidgeFill, − - 1.02 % [ − - 2.87 %, +0.80 %], does not establish a gain (§ 5.3 ). Calibration length. The longest calibration document, which every set of maps uses, is about 30K tokens (30,465 tokens on the Qwen3.5-9B and 27B tokenizers, 29,009 on Qwen3-8B’s and 28,352 on Llama’s), so no map was fitted on a position much beyond that. The median calibration document is 11.2K to 11.6K tokens, depending on the tokenizer (Appendix G ). The test documents run to 128K. On Llama at the primary split, RidgeFill’s filled-region retrieval falls from 79.8 at 8K to 30.3 at 64K. We have not tested whether longer calibration documents would close that gap. The 27B. No identity-fill arm was run on this model, so its results compare RidgeFill with stock only. Of the RULER tasks, common-word extraction drops the most, by 10.0 points at 16K and 13.5 at 32K on 20 items each, with intervals that include zero; no other task moves by more than 5 points (§ 4.5 ). RULER and the agreement study stop at 32K. Above that, the only quality evidence is LongBench v2’s long group of 108 items, where RidgeFill is 0.9 points below stock with an interval from − - 7.4 to +6.5 (§ 4.6 ), too wide to rule out a loss of several points. At 32K, on the 20 documents where the two arms disagree most, ten in each direction, and five near the median, the full-precision BF16 model is closer to stock than to RidgeFill on 22 of the 25 (§ 4.7 ). RidgeFill’s much lower loss on copy-heavy documents is therefore a departure from the model, not a gain. The probe’s row count, inherited from the base rules, and its 256-row window were set on development data and not swept. The value rescale was not measured on its own in the final runs. The 27B’s calibration text shares license headers, and nothing else, with 12 of LongBench v2’s Code Repository items: runs of 78 to 85 words with documents its maps were fitted on, and up to 162 words with documents only its token-frequency table counts (Appendix G ). Flash-Next. The perplexity interval runs from − - 0.02 % to +4.93 % (§ 5.3 ). It does not separate the 2.65 % rise from zero, and it allows a rise of nearly 5 %. The plain RidgeFill server start did not check that switching the fill off reproduces exact. The quality-mode start did, bitwise on 6 of 6 documents, and both starts used the same container image, replaced file and arguments (§ 5.2 ). About two thirds of the routed experts are held in host memory and read over PCIe during prefill, so this deployment cannot separate the compute the fill saves from the PCIe traffic it saves (§ 5.3 ). The fork’s image is public, but its patches are not (Appendix F ). Speed, memory and compute. Every prefix row still gets a cache entry, so the fill saves no cache memory, and the maps add VRAM. On the 27B they add 1.6 to 2.9 GiB when held in GPU memory and 0.3 to 1.7 GiB when streamed from host memory (§ 4.4 ). Methods that drop tokens do save that memory. TokenGate, for example, reports 1.4 to 11.3 × \times faster time to first token and 1.5 to 3.4 × \times lower peak memory on Qwen3-1.7B and Qwen3.5-2B (§ 7 ). Our speedups are 1.19 to 1.31 × \times on the 27B, across resident and streamed maps, and 1.50 to 1.60 × \times on Flash-Next. We do not compare with any token-dropping method at a matched budget. On both serving models the measured speedup is below what the skipped compute allows, and we have not profiled why (§ 4.4 , § 5.3 ). In the reference study, RidgeFill at 5/8 depth costs more multiply-accumulates than POP below about 46K tokens on Llama and 59K on Qwen3-8B, because of its tail and maps, so it costs more across the whole 8K to 32K needle range (§ 2.5 , § 6.4 ). Follow-up analyses. The 5/8-depth comparisons with POP (§ 6.4 ) were chosen after the primary-split results were in and registered only before their own runs, so they are follow-ups. The 30 fresh documents (§ 6.7 ) were registered to test their loss results on new text, and they confirmed them; the retrieval results have no such test. The half-depth retrieval check of § 6.7 was registered before it ran but stated no prediction. Scope. The evidence comes from three reference models of 8 to 9B parameters and two serving models. Both serving models are hybrids of Gated DeltaNet and attention, both run quantized weights, and they are the only models whose speed was measured; the reference study reports multiply-accumulate counts only. Qwen3-8B runs to 32K tokens only, since it needs YaRN beyond that. Decode agreement on the reference models uses 20 documents, and LongBench v1 runs on Llama only. Flash-Next’s 64K RULER is one task, niah_single_1, on 25 samples, and its time-to-first-token medians come from prefixes of one document. The ceiling r of § 2.5 assumes every layer costs the same, which neither hybrid meets, so for speed the measured numbers are the ones to use. 9 Reproducibility and recipe Code, maps and data. These settings come from five models, and a new architecture or workload may need others. 1. Fit the maps. Run the unmodified model over calibration text, record the hidden state at the split and the input to every later layer, and solve one ridge regression per layer (§ 2.2 ), with the ridge penalty’s setting λ \lambda chosen on held-out documents (Appendix G ). One capture pass serves only the splits chosen before it runs: a new split needs a new pass, and a new λ \lambda needs only new solves. 2. Choose the split by whether the model normalizes its queries and keys (QK-norm). On the two reference models with QK-norm, novel-token loss stays within 0.05 nats of exact at 3/8 depth. Llama-3.1-8B, which has no QK-norm, needs half depth or deeper (§ 6.1 ). Attention-selected exact rows also remove Llama’s shallow-split failure, but they lowered retrieval on Qwen3-8B (§ 6.5 ) and depend on the question (§ 8 ). For comparison, the 27B runs at 1/4 depth with 28 to 31 % of the prefix exact, and Flash-Next at half depth with no exact prefix rows. 3. Use an exact tail of 2,048 to 4,096 tokens, the range of the final runs. Shorter tails were tried only in exploratory work. The tail runs every layer, but it reads the filled prefix cache, so its outputs can still differ from exact. 4. Check that the engine with the fill switched off reproduces exact bitwise, so that every difference you measure is the fill’s. 5. Before shipping, measure two numbers against exact: filled-region needle retrieval and key-token Δ \Delta NLL (§ 3.1 ). Novel-token loss alone can hide the difference: on Qwen3-8B the fitted and identity fills differ by 0.019 nats on it and by 49.6 points on retrieval (§ 3 ). A needle score near 100 can hide key-token loss (§ 8 ). If you add exact rows, compare them with the same number of random rows, and with the question hidden if the cache will serve more than one question. The prompts are the niah_multikey_1 samples, which carry four keyed needles. The second question asks for one of the other three keys, chosen by a per-sample seed that is the same on every model. It is appended after the first answer and runs exactly on the carried cache; rows are not chosen again. An answer counts if the first seven-digit number in the reply is right, which is stricter than RULER’s substring match. Appendix E RULER prompts in the serving engines Both engines put the question and the answer format in a single user turn, prefill no answer prefix, and run with thinking off. They word the instruction differently. • On Qwen3.8-27B (llama.cpp), the prompt keeps RULER’s question line and appends Answer with the requested answer(s) in the form: [answer prefix] <answer(s)>. • On Qwen3.8-Flash-Next (vLLM), the prompt replaces the question line with Answer the following question: [question] and adds In your answer, respond with the following format: [answer prefix]: <number>, … , with one <number> per expected value. The script and its result are in the data repository. Appendix H Derivations and formal statements Exact rows and the cost model. An exact prefix row does the same compute in the late layers as a tail row, but it takes κ \kappa times as long there, because it shares each read of the layer weights with far fewer rows. On the 27B, the exact rows are scattered through the prompt, so the second sweep runs them in smaller, less efficient batches than the contiguous tail, and each of those micro-batches reads the late layers’ weights in full (§ 4.4 ). On Flash-Next the sharing happens inside each expert. Flash-Next prefills in chunks of 2,048 tokens, and each late layer sends every token to 10 of its 512 routed experts. A tail chunk touches nearly every expert, so each expert’s weights are read once for about 40 tokens. In a prefix chunk under quality mode, only the protected rows run the expert blocks. On the Flash-Next run they were 3 to 10 % of each prompt’s prefix, so about 60 to 200 rows of a chunk if they spread evenly. If routing spreads evenly, those rows still touch about 70 to 98 % of the experts, so nearly the same weights are read for a tenth of the rows or fewer, about 10 to 24 times a tail row’s expert traffic per row. The routed experts held in host memory, about two thirds of them (16,042 of 24,576 per GPU), are read over PCIe; the rest, the shared expert and the attention weights stay in VRAM. The even-routing assumption is ours, and neither deployment was profiled, so both accounts are explanations that a profile would have to confirm. So the prefill time grows in a straight line with the number E E of exact prefix rows: τ ⁡ ( E ) = τ 0 + E ​ σ , \tau(E)=\tau_{0}+E\,\sigma, where τ 0 \tau_{0} is the time with no exact rows and σ \sigma , the time one exact row adds, is κ \kappa times a tail row’s time in the late layers. If prefill time follows this model, two measured times fix the line: τ 0 \tau_{0} , and τ ⁡ ( E 1 ) \tau(E_{1}) for some number E 1 E_{1} of exact rows, which give σ = ( τ ⁡ ( E 1 ) − τ 0 ) / E 1 \sigma=(\tau(E_{1})-\tau_{0})/E_{1} . RidgeFill with E E exact rows is then no slower than exact prefill, whose time is τ exact \tau_{\text{exact}} , when E ≤ ( τ exact − τ 0 ) / σ . E\leq(\tau_{\text{exact}}-\tau_{0})/\sigma. In words, the time RidgeFill saves with no exact rows, divided by the time each exact row costs, is the number of exact rows it can afford. κ \kappa has to be measured, and the final runs did not measure it: the 27B timings cover only stock and the full configuration, and no count of exact rows was recorded for the Flash-Next timing prompts. Quality mode adds exact rows and is slower than plain RidgeFill on Flash-Next (§ 5.3 ). It also adds the terminal-state correction, but that is one addition per layer, so the rows are the likely cost; the final runs do not separate the two. Lexical-net normalization. Words are runs of Unicode letters and number characters; punctuation, underscores and combining marks separate them. ASCII letters are lower-cased, and every other character is kept as it is. A final s is dropped from words of four or more characters unless the word ends in ss. A sentence ends at a line break; at a period, exclamation mark or question mark followed by whitespace or the end of the text; at the CJK full stop, exclamation mark or question mark; and at control, user-defined, unknown and unused tokens. Why the terminal-state correction is scaled by ρ \rho . A Gated DeltaNet layer keeps a running state. At each token it multiplies the state by a gate between 0 and 1, which fades older tokens, and adds the token’s own update. The terminal-state correction adds a fixed offset Δ ​ M ℓ \Delta M_{\ell} to the state of layer ℓ \ell at the end of the prefix, scaled by ρ ℓ \rho_{\ell} , the filled rows’ share of that state. Under a simple model of the layer, that scale removes the fill’s shift exactly. Take one layer. The delta rule also erases part of the old state before each write, in the direction of the token’s key; for simplicity, drop that erase term. The state after token t t is then M t = g t ​ M t − 1 + u t M_{t}=g_{t}M_{t-1}+u_{t} . The state M t M_{t} and the update u t u_{t} are matrices of the same size, one per head, and the gate g t g_{t} is one number between 0 and 1 per head and token. Unrolling over the n n prefix rows gives the state at the end of the prefix: M n = ∑ j = 1 n w j ​ u j , w j = ∏ k = j + 1 n g k . M_{n}=\sum_{j=1}^{n}w_{j}u_{j},\qquad w_{j}=\prod_{k=j+1}^{n}g_{k}. Row j j ’s weight w j w_{j} is the product of every gate after it, and the last prefix row’s weight is 1. The fill changes the updates of filled rows. Suppose, as an idealization, that it shifts each one by the same amount δ \delta , a matrix the size of the state. The state at the end of the prefix is then off by δ ​ ∑ j ​ filled w j \delta\sum_{j\,\text{filled}}w_{j} . A fully filled prefix would be off by δ ​ ∑ j w j \delta\sum_{j}w_{j} , and that is what Δ ​ M ℓ \Delta M_{\ell} estimates. Multiplying Δ ​ M ℓ \Delta M_{\ell} by ρ ℓ = ∑ j ​ filled w j ∑ j w j , \rho_{\ell}=\frac{\sum_{j\,\text{filled}}w_{j}}{\sum_{j}w_{j}}, the filled rows’ share of the weight at the end of the prefix, gives δ ​ ∑ j ​ filled w j \delta\sum_{j\,\text{filled}}w_{j} , which removes the shift exactly. Any other scale leaves part of it, and the unscaled correction overshoots by the exact prefix rows’ share. Because the correction is added at the end of the prefix, the tail’s gates fade it exactly as they fade the error, so it cancels in the final state too. Behind the exact tail, the filled rows’ share of the final state is small on layers that fade quickly (Figure 4 ). Suppose every gate is at most γ \gamma < 1 and the last m m rows of the prompt are exact. Each filled row then has at least m m gates after it, so the filled rows’ total weight in the final state is at most γ m + γ m + 1 + ⋯ = γ m / ( 1 − γ ) \gamma^{m}+\gamma^{m+1}+\dots=\gamma^{m}/(1-\gamma) . The total weight of all rows is at least 1, the last row’s weight, so the filled rows’ share is at most γ m / ( 1 − γ ) \gamma^{m}/(1-\gamma) . For γ \gamma = 0.4 and m = 16 this is 7.2 × 10 − 7 7.2\times 10^{-7} . Only layers whose gates stay near 1 need the correction. The bound also holds with the erase term: two runs that receive the same last m m inputs end with states that differ by at most γ m \gamma^{m} times their difference before those inputs. I.4 Checking a filled cache during decoding On Qwen3.8-27B in a development build of the engine, a decode-time check bounds the attention each filled row receives from the current query and flags rows that cross a threshold for exact recomputation.
