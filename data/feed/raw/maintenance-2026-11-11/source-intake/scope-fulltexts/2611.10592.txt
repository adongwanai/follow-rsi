Affiliation: Stanford University Affiliation: Figma Ashvini Kumar Jindal 1 1 footnotemark: 1 Affiliation: Figma Chuhua Wang Affiliation: Figma Sumithra Bhakthavatsalam Affiliation: Figma Abstract Large language models can generate motion graphics from static images and natural language requests, but it remains difficult to evaluate how well models can follow requests that combine spatial, appearance, and temporal requirements.
We introduce MotionGraphicsBench, an expert-curated benchmark of 100 instances for animating an input static SVG with a motion edit prompt.
By supplying all required visual elements, our editing task reflects a designer-like workflow and isolates motion generation from graphic generation.
Derived from real-world Lottie motion designs, our benchmark contains diverse combinations of spatio-temporal animation behaviors.
Each benchmark instance pairs its model input with a deterministic, human-readable verification program that accepts different valid implementations and reports which prompt requirements pass or fail, rather than comparing against a reference animation or using a VLM judge.
We construct these programs with a multi-agent pipeline using human-labeled animations and synthesized test cases.
On a balanced test set of 180 animations, our programs achieve 93.3% raw agreement with human judgments, compared with 83.3% for a GPT-6 Astra VLM baseline, and outperform the baseline in both approval and rejection recall.
Across 47 configurations from 32 LLMs and 12 providers, pass@1 ranges from 6.0% to 67.7%.
Across 15 models evaluated at their highest available reasoning effort with 32 attempts per instance, additional attempts improve every model, but pass@32 still ranges from 38.0% to 95.0%.
Our analysis of verification programs reveals that generated animations often fail to match reference poses, follow requested motion trajectories, or coordinate related events.
We release our benchmark at https://huggingface.co/datasets/figma-ai/motion-graphics-bench . 1 Introduction Motion graphics animate static imagery through coordinated changes in spatial structure, appearance and visibility, and temporal sequencing.
Large language models (LLMs) can now generate such animations from static images and natural language prompts ( Tseng et al., 2025 ; Park et al., 2025 ) , but it remains difficult to evaluate how well the resulting animation realizes the requested motion: a single user request may combine multiple spatio-temporal conditions, but an animation may satisfy only some of it while missing others.
Natural language motion requests often describe salient animation behaviors and relative spatial and temporal relationships rather than exact parameters ( Talmy, 1975 ; Talmy, 1983 ; Tversky and Lee, 1998 ) .
The same input can therefore correspond to several valid animations that differ in their trajectories and timing ( Ma et al., 2026 ) .
Existing related benchmarks on animation and video often evaluate outputs through metrics that compute resemblance to a target “ground truth” ( Chen et al., 2026 ; Yang et al., 2026 ; Huang et al., 2024 ; Ling et al., 2025 ) , or through VLM-based judges that assess rendered frames against the prompt ( He et al., 2024 ; Lin et al., 2025b ) .
Comparison with a single target is too restrictive because a generated animation can satisfy every requested condition while differing from the reference in its trajectory or timing.
VLM-based judges avoid comparison with a single reference animation.
However, their judgments can be stochastic and it is difficult to inspect how individual prompt requirements affect their decisions. We introduce MotionGraphicsBench, an expert-curated benchmark of 100 instances for evaluating vector animation generation.
We formulate motion graphics generation as an editing task: given an input static SVG and a motion edit prompt in natural language, a model generates an animation by adding requested motions to the static image, which contains all visual elements needed for the edit.
This setup mirrors a designer-like workflow in which the static design is first created before motions are added, and isolates motion generation from the separate problem of generating the graphic itself. To ground our benchmark in real world motion designs rather than synthesized examples, we derive our instances from LottieAnimation-660K, a large collection gathered from professional online animation platforms including IconScout and LottieFiles ( Chen et al., 2026 ) .
To more comprehensively evaluate model abilities, we curate our benchmark instances with diverse combinations of spatial, temporal, and appearance changes that challenge LLMs while remaining clearly describable in natural language.
Our final benchmark covers 17 animation requirement types grouped into spatial structure, appearance and visibility, and temporal sequencing.
We rank source animations by structural complexity and manually retain moderately complex, unique motions that can be clearly described in natural language.
For each selected source animation, we construct an input static SVG and motion edit prompt through LLM assistance and human review.
The SVG provides a reference state for the animated elements while retaining every visual element needed to realize the edit.
Our motion edit prompts request salient animation behaviors and their relative spatial and temporal relationships.
The prompt states what should move or change, how elements should relate, and when actions should occur without prescribing exact measurements ( Talmy, 1975 ; Talmy, 1983 ; Tversky and Lee, 1998 ; Ma and Agrawala, 2025 ; Ma et al., 2026 ) . Figure 1: Overview of MotionGraphicsBench. Given an input static SVG and a motion edit prompt, our benchmark uses a human-readable verification program to evaluate whether the generated animation satisfies the input requirements and outputs a report. Here, the scissors have the correct motion sequence but fail the verification because the blades remain too far apart when closed. Because each motion edit prompt specifies different requirements, evaluating model-generated animations requires instance-specific checks.
Our deterministic evaluation framework therefore pairs each benchmark instance’s model input with a human-readable verification program.
Each program consists of deterministic checks corresponding to the requirements in its motion edit prompt.
The program measures how visual elements change across the generated SVG frames and returns a verification report with the overall decision and individual check outcomes. To construct one prompt-specific verification program for every benchmark instance, we combine human-labeled generated animations with a multi-agent construction pipeline.
To support both verification program construction and evaluation, we collect human judgments of whether model-generated animations satisfy their motion edit prompts.
We use human-labeled construction animations to build the programs and reserve a held-out test set for evaluating the resulting programs.
Our pipeline consists of a verification program writer and a test case synthesizer.
The writer drafts and revises the program using the motion edit prompt, source Lottie animation, human-labeled construction animations, and synthesized test cases, while the synthesizer creates and reviews those test cases. Deterministic decisions are useful only if the verification programs capture human judgments of whether an animation satisfies the prompt.
We therefore evaluate our programs on 180 human-labeled test animations.
Our programs achieve 93.3% raw agreement, 90.0% approval recall, and 96.7% rejection recall.
The GPT-6 Astra VLM baseline achieves 83.3% raw agreement, 82.2% approval recall, and 84.4% rejection recall on the same animations. Using our verification programs, we evaluate 47 configurations from 32 LLMs across 12 providers on all 100 benchmark instances.
Across these configurations, pass@1 ranges from 6.0% to 67.7%.
From the 47 configurations, we select the highest reasoning effort configuration for 15 models and run 32 independent generation attempts per benchmark instance.
Additional attempts improve model performances, but pass@32 still ranges from 38.0% to 95.0%.
By examining our verification programs and reports, we identify three main failure modes across our benchmark.
Generated animations may fail to match reference poses, follow requested motion trajectories, or coordinate related events.
Together, MotionGraphicsBench provides a curated benchmark grounded in real world motion designs, deterministic evaluation through interpretable verification programs matching human judgments, and a broad analysis of model performance and generated animation failures.
We release our benchmark at https://huggingface.co/datasets/figma-ai/motion-graphics-bench . 2 Related Work Vector animation generation. Recent vector animation systems either use end-to-end generation or editing setups.
LottieGPT and OmniLottie generate both graphics and motion from text or visual conditions, so their evaluations reflect both capabilities ( Chen et al., 2026 ; Yang et al., 2026 ) .
Editing methods begin with existing graphics: Keyframer and Decomate support language-guided SVG editing, AniClipart optimizes clipart motion, Vector Prism, LiveSVG, and VAnim animate supplied vector graphics, and MoVer adds and verifies prompt-specified motion in existing SVG scenes ( Tseng et al., 2025 ; Park et al., 2025 ; Wu et al., 2024a ; Yun and Choo, 2026 ; Levy et al., 2026 ; Liang et al., 2026 ; Ma and Agrawala, 2025 ) .
Our benchmark follows the editing setup: an input static SVG supplies every required visual element, and a motion edit prompt derived from a source Lottie animation specifies the motion, isolating motion generation from graphic generation. Benchmark task construction. Existing benchmarks either construct prompts around predefined capabilities or curate tasks from existing artifacts or user requests.
VBench designs prompts by evaluation dimension and content category, while GenEval, ConceptMix, and T2V-CompBench target specific objects, attributes, relations, motions, or combinations ( Huang et al., 2024 ; Ghosh et al., 2023 ; Wu et al., 2024b ; Sun et al., 2025 ) .
MoVer and Self-Consistency similarly use synthetic template-based prompts to evaluate motion relations or trajectory families ( Ma and Agrawala, 2025 ; Ma et al., 2026 ) .
DS-1000 derives problems from Stack Overflow, SWE-bench from repository issues and tests, ScienceAgentBench from scientific datasets and tasks, and WildBench from real-user queries ( Lai et al., 2023 ; Jimenez et al., 2024 ; Chen et al., 2025 ; Lin et al., 2025a ) .
Our benchmark similarly selects existing Lottie animations and constructs motion edit prompts from their motion designs.
Our motion edit prompts span 17 animation requirement types, while each prompt-specific verification program evaluates one instance’s exact requirements. Verification of generated outputs. Because several animations can satisfy one motion edit prompt, evaluation should test its requested relationships without requiring a target trajectory.
VBench applies dimension-specific metrics to motion smoothness, temporal consistency, and spatial relationships, producing broad capability profiles rather than prompt-specific decisions over all requested behaviors ( Huang et al., 2024 ) .
Reference-based comparisons in LottieBench and MMLottie-Bench can penalize valid deviations, while VCode and VideoScore use flexible model-based judgments that depend on the judge and prompting procedure ( Chen et al., 2026 ; Yang et al., 2026 ; Lin et al., 2025b ; He et al., 2024 ) .
MoVer maps prompts to first-order spatio-temporal predicates but evaluates 5,600 synthetic prompts generated from templates and LLM rewrites.
Our benchmark instead derives human-reviewed prompts from existing Lottie animations, pairs each input with a deterministic verification program, and validates decisions against held-out human judgments. To isolate motion generation from graphic creation, we formulate vector animation generation as a motion editing task.
We provide each model with an input static SVG and a motion edit prompt written in natural language, then ask it to generate an animation that realizes the requested motion.
An input static SVG is a vector scene that contains all scene geometry, including elements that may not be visible when rendered.
A motion edit prompt describes how the input static SVG should be animated, including what should move or change, how elements should relate, and when actions should occur.
Because it is often difficult for users to specify exact keyframes, coordinates, or frame numbers (e.g., how many degrees the scissor blades in Figure 1 should rotate), each prompt in our benchmark requests salient animation behaviors in terms of relative spatial and temporal relationships, consistent with findings from cognitive psychology on how people describe animation ( Talmy, 1975 ; Talmy, 1983 ; Tversky and Lee, 1998 ) .
As a result, a prompt often does not fully specify a unique animation ( Ma et al., 2026 ) .
The input static SVG provides a reference appearance, but it does not necessarily define frame 0.
The prompt may ask the model to construct a different frame 0 based on the input SVG or to make the animation reach the SVG’s depicted state later (e.g., the Scissors prompt asks the blades to return to the open pose shown in the input SVG in Figure 1 ). Evaluating model outputs. Multiple model outputs may therefore satisfy the same prompt while differing in their trajectories and timing.
To evaluate a model output against animation requirements rather than one target animation, each benchmark instance pairs an input static SVG and motion edit prompt with a prompt-specific verification program.
The program encodes the animation requirements as deterministic, human-readable checks.
Section 4 describes how our evaluation framework applies the program to model generated animations. 3.2 Model Input Construction Source Lottie corpus selection. To ground our benchmark in real-world motion designs rather than synthetic examples, we select 100 source Lottie animations from LottieAnimation-660K, a collection gathered from professional animation platforms ( Chen et al., 2026 ) .
Lottie preserves layers, shapes, transforms, keyframes, and easing curves, which lets us identify the elements and motions needed to construct each model input.
We use each source Lottie animation only to construct the input static SVG and motion edit prompt.
To keep the task focused on motion generation rather than identifying unnamed SVG elements, we retain animations whose animated layers or objects have names that support clear references in a motion edit prompt.
We rank the remaining candidates by their animated property types, animated objects, and keyframes to capture motion variety, scene complexity, and temporal structure.
We manually review 1,000 candidates near the median complexity to balance challenge and describability, removing duplicate graphics and motions and animations that cannot be clearly described in natural language. Input static SVG construction. To model a workflow in which an artist supplies an existing static design, we exclude frames that are empty, cropped, or transitional.
We select a remaining frame in which the visible objects are recognizable, opaque, and normally sized.
To keep our benchmark focused on motion editing rather than graphic creation, the input static SVG must contain every visual element needed by the requested animation, including elements hidden in the selected frame.
A single-frame Lottie render can omit elements that are inactive or fully transparent at the selected moment, even when the requested animation needs them later.
We therefore recover this hidden geometry while preserving the selected frame’s visible appearance ( Liang et al., 2026 ) .
The completed SVG preserves the reference appearance while making all required graphics available for animation.
Appendix Figure 6 illustrates the process. Motion edit prompt construction. Because the source Lottie animations do not include model-facing instructions for adding motion to a static SVG, we construct each motion edit prompt through LLM-assisted drafting and human review.
As motivated in Section 3.1 , each prompt states what should move or change, how elements should relate, and when actions should occur.
We describe these requirements through relative spatial and temporal relationships rather than exact keyframes, coordinates, or frame numbers ( Ma and Agrawala, 2025 ) .
When needed, a prompt specifies a visible path, timing pattern, or easing behavior without requiring exact reproduction of the source Lottie animation ( Ma et al., 2026 ) .
An LLM drafts each prompt from the input static SVG and evidence from the source Lottie animation.
The draft names the relevant elements and states their required spatial and temporal relationships, including end states.
These details distinguish a complete edit from one that captures only the general motion.
A human reviewer compares each draft with the input static SVG and source Lottie animation, then approves it, edits it, or requests a targeted revision to remove ambiguity, unsupported claims, and implementation-specific wording.
See Appendix A.1 . 3.3 Benchmark Composition and Coverage Our MotionGraphicsBench contains 100 benchmark instances constructed from 100 distinct source Lottie animations.
Each instance pairs an input static SVG and a human-reviewed motion edit prompt with a prompt-specific verification program.
The source Lottie animations have a mean duration of 3.50 seconds (SD 1.89).
The motion edit prompts have a mean length of 193.8 words (SD 57.2).
To characterize the animation behaviors requested by our motion edit prompts, we identify 17 animation requirement types grouped into three families: spatial structure, appearance and visibility, and temporal sequencing (Table 1 ).
Our benchmark centers on the temporal ordering and geometric state constraints needed to specify coherent motion, while extending its coverage to deformation, reveal and erasure, and color, fill, and stroke appearance.
Each motion edit prompt combines between 7 and 14 animation requirement types.
All prompts combine spatial and temporal requests; 65 include appearance or visibility. 4 Evaluation with Verification Programs 4.1 Verification of Generated Animations Prompt-specific verification. Motion edit prompts describe intended spatial and temporal behavior without fully specifying an exact trajectory, timing curve, or grouping ( Talmy, 1975 ; Talmy, 1983 ; Tversky and Lee, 1998 ) .
Multiple animations can therefore satisfy the same prompt ( Ma and Agrawala, 2025 ; Ma et al., 2026 ) .
Because each prompt imposes different requirements, we evaluate each instance with a prompt-specific verification program rather than shared similarity measures.
The program implements the prompt requirements as verification checks that evaluate spatial structure, appearance and visibility, and temporal sequencing as applicable to the instance.
These checks allow different animation implementations to pass when they satisfy the requested behavior while detecting partial results that generic visual metrics may miss.
We describe how we construct a verification program for each instance in Section 4.2 . Verification procedure. Vector animations can be created through many mechanisms, such as Lottie, GSAP, anime.js, CSS animations, and SMIL ( Chen et al., 2026 ; Doyle, 2025 ; Garnier, 2025 ; MozDevNet, 2025 ; W3C SYMM Working Group, 2008 ) .
Animations produced through any of these mechanisms can be represented as sequences of SVG frames.
Because each frame records the vector scene at one point in time, the resulting sequence provides a common representation that allows verification to operate independently of how the motion is produced.
In our experiments, we ask models to generate JavaScript programs with GSAP, whose timeline API lets our renderer seek to fixed timestamps and deterministically capture the resulting SVG frames ( Doyle, 2025 ; Ma and Agrawala, 2025 ) .
The verification program takes the SVG frames as input, measures each element’s geometry, appearance, and motion over time, evaluates the prompt requirements, and returns a verification report with the overall decision, individual check outcomes, and any errors.
An attempt is one model request for one benchmark instance and counts as a success only if it produces an animation that passes every verification check. 4.2 Verification Program Construction Because a motion edit prompt can be satisfied by several valid implementations, each verification program must accept allowed variation while rejecting animation requirement violations.
We construct one program for each instance with a pipeline of two agents:
we have a verification program writer that writes and revises verification programs, while a test case synthesizer creates synthesized test case animations that expose missing or overly restrictive checks (Figure 2 ).
Both agents use GPT-6 Astra. Figure 2: Verification program construction. The writer drafts and revises a candidate program using the benchmark inputs, source Lottie animation, and human-labeled construction animations, while the synthesizer independently creates test case animations.
We run the candidate on these real and synthesized animations, and then return the reports to the writer for revision. Construction data. To ground construction in diverse model outputs, we use a human-labeled construction set of 1,585 model-generated animations from 25 generation configurations across all 100 benchmark instances, comprising 410 approvals and 1,175 rejections.
Appendix Table 6 marks these 25 configurations and the four held-out configurations.
These animations come from the broader collection of human judgments described in Section 5 , where the same review procedure with two annotators covers construction animations and test animations reserved for evaluation.
Before construction, we split the animations; agents receive only construction animations, review notes, instance inputs, and the source animation (Appendix C.1 ). Verification program writer. To keep each verification program grounded in the requested motions, the verification program writer receives a construction example set alongside the input static SVG and motion edit prompt.
The set consists of the source Lottie animation, human-labeled construction animations, and synthesized test cases.
The source Lottie animation supplies one valid realization of the requested edit, while examples approved by humans show allowed variation and examples rejected by humans and their review notes identify possible violations to inspect.
Together, these inputs help the writer interpret the requested edit without treating one animation as the definition of correctness or adding requirements absent from the input static SVG or motion edit prompt.
The writer uses an animation matrix of SVG attributes and measurements; Appendix B.1 gives implementation details.
The writer therefore bases its measurements and tolerances on the requested behavior and measured animation properties rather than choosing thresholds solely to match the construction approvals and rejections.
Using our verification library , which derives spatio-temporal measurements from the animation matrix, the writer implements these requirements as a Python verification program (Figure 1 ).
During construction, the writer tests each candidate program on the complete construction example set.
Each candidate must classify every example in the set correctly: the source Lottie animation and every approved or positive example must pass, while every rejected or negative example must fail. Test case synthesizer. Human-labeled construction animations and the source Lottie animation may leave a requirement untested or combine several violations in one example, causing a candidate verification program to become too permissive or overly restrictive.
The test case synthesizer therefore creates synthesized test cases that probe allowed variation and targeted violations.
It receives the motion edit prompt, source Lottie animation, human-labeled construction animations and review notes, and descriptions of earlier cases, but not the candidate program or its reports.
Using our animation transformation library , which deterministically changes motion timing, direction, extent, position, appearance, and SVG structure, it transforms the source Lottie animation or a construction animation approved by humans.
Positive cases preserve the requested edit while varying allowed choices, whereas negative cases introduce a violation.
When useful, paired cases isolate one relevant property.
To account for the imbalance between approvals and rejections, the synthesizer requests more negative cases when approvals are more common and more positive cases when rejections are more common.
The assigned labels remain claims made during construction rather than independent human judgments.
See Appendix B.2 . Testing and revision. After the writer produces a candidate verification program, it runs the program on the complete construction example set, inspects the individual check outcomes, revises the candidate when the tests expose missing or overly restrictive checks, and reruns the set.
A synthesized-label disagreement may reveal a faulty test case, which the agents resolve within the loop (Appendix B.2 ).
This iterative construction loop resembles counterexample-guided synthesis and selection of generated tests ( Solar-Lezama et al., 2008 ; Chen et al., 2022 ; Jain et al., 2025 ; He et al., 2026 ) .

We collect human judgments for 1,980 model-generated animations, and use 1,585 of those for verification-program construction (Section 4.2 ) and reserve a disjoint set of 180 animations to evaluate how well the resulting verification programs align with human judgment.
We assign two annotators to independently inspect the motion edit prompt, input static SVG, and generated animation and judge prompt satisfaction rather than aesthetic preference or exact source reproduction.
Annotators may reveal the source Lottie animation as one valid clarification (Appendix Figure 7 ).
To keep judgments independent, we hide the generating model, verification decision, and the other annotator’s initial decision.
When their decisions differ, the same pair revisits the animation and discusses the prompt, and we assign a binary final label only after agreement, following established independent-annotation and consensus practice ( Banea et al., 2008 ; Hromei et al., 2025 ) .
For rejections, annotators identify unsatisfied prompt text and the visible violation without adding new prompt requirements; these comments support the decision but need not enumerate every failure.
See Appendix C.1 . Held-out evaluation. We evaluate 180 held-out animations, balanced between 90 human approvals and 90 human rejections, covering all 100 benchmark instances.
The animations come from Gemini 3.1 Pro, Gemma4, GPT-5.5, and Sonnet 5, spanning multiple providers and both open-weight and proprietary models.
For comparison, we use a VLM baseline that receives the input static SVG rendering, motion edit prompt, and up to 64 timestamped frames from each generated animation.
See Appendix C.2 . Validation results. Our verification programs agree with human judgments on 93.3% of test animations, 10% above the VLM baseline at 83.3%.
They recover 90.0% of human approvals and 96.7% of human rejections, compared with 82.2% and 84.4% for the VLM baseline.
Our programs also achieve higher raw agreement within each of the four generation configurations represented in the test set.
To understand the remaining errors, we review all 12 cases in which a verification program decision differs from the final human label.
The cases span 11 benchmark instances and comprise nine false rejections across eight instances and three false approvals across three instances, so they are not concentrated in one instance.
In all three false approvals, our programs miss required relative motion between sub-elements.
Most false rejections enforce timing, coordination, or geometry too strictly; Appendix C.2 gives the complete audit. 6 Model Performance and Failure Analysis We report pass@1 for 47 model configurations representing 32 LLMs from 12 providers, including 16 open-weight and 16 proprietary models.
For pass@k, we select the highest-available-effort configuration from 15 models and generate 32 independent attempts per benchmark instance.
Each attempt asks one model to generate one animation for one benchmark instance.
This design yields 51,200 attempts across the 100 benchmark instances.

We map checks to failure modes and apply them to saved reports; Appendix D.3 gives the full method.

We provide additional qualitative examples in Appendix D.4 and on our website.
For each mode, we report failure over attempts on instances whose prompts request the corresponding animation behavior.
Coverage is the share with enough evidence to decide whether the mode occurred. Figure 5: Failure modes. We analyze our verification programs to identify top model failure modes. We most often observe reference-pose mismatch , with a 41.5% failure rate (94.3% coverage).
This spatial-structure failure occurs when an element misses a pose shown by the input static SVG or requested by the motion edit prompt.
In the Scissors example, the blades close but merge instead of remaining distinct (Figure 5 ).
Beyond reaching the correct pose, models also struggle with motion trajectory mismatch , or errors in path, direction, or distance.
We observe a 38.8% failure rate (88.6% coverage) for this second spatial-structure failure.
In TWS Earbuds, one earbud descends instead of following the requested mirrored upward-and-outward path (Figure 5 ).
For temporal sequencing, event coordination mismatch has a 32.4% failure rate (93.0% coverage).
This occurs when related motions have the wrong order or overlap.
In Speed-2, the green status remains visible after the needle leaves its range instead of fading as it departs (Figure 5 ). 7 Conclusion We introduced MotionGraphicsBench with 100 expert-curated instances that pair an input static SVG and motion edit prompt with a prompt-specific verification program.
On a balanced test set of 180 animations, our programs achieve 93.3% raw agreement, compared with 83.3% for a VLM baseline.
Across 47 configurations from 32 LLMs and 12 providers, no configuration exceeds 67.7% pass@1, while additional attempts improve success substantially but unevenly within the 15-model cohort.
Our failure analysis shows that generated animations often fail to match reference poses, follow requested motion trajectories, or coordinate related events. Limitations and future work. Our detailed motion edit prompts, while effective for precise verification, do not capture interactions where a user begins with shorter or underspecified requests and refines them over multiple turns.
Moreover, although our framework evaluates SVG frames independently of the animation generation mechanism, our experiments use the GSAP library; other mechanisms such as CSS, SMIL, and other JavaScript libraries may yield different performances.
Our 100 instances also do not cover complex deformation, large scenes, or highly interactive animation behavior.
Future work can use our check-level reports for MoVer-style iterative correction ( Ma and Agrawala, 2025 ) , online or offline reinforcement learning, and multi-turn refinement that combines verification with user feedback. Acknowledgments We thank Maneesh Agrawala for valuable discussions.

Verification Programs B.1 Evaluation Implementation and Scoring Frame rendering. We use the rendering engine provided by the open-source MoVer repository to execute each generated GSAP program in a browser and produce the SVG frame sequence consumed by verification ( Ma and Agrawala, 2025 ) . Animation matrix. To give each verification program a structured view of SVG elements over time, we follow MoVer and use an animation matrix ( Ma and Agrawala, 2025 ) .
MoVer organizes an animation as a two-dimensional matrix with objects as rows and frames as columns.
Each cell stores atomic motion attributes for one object at one frame, while static object information is stored separately.
Our matrix serves a related purpose but stores one row for each measured SVG node and keys each row by its document path, which remains unambiguous when element identifiers are missing or duplicated.
For every frame, Chromium records the element hierarchy, absolute and element-owned transforms, local bounding box, outline length and endpoints, sampled contour, stroke width, visible fraction, clip and mask bounds, SVG attributes, and relevant computed styles.
The matrix also records the frame count, frame rate, duration, source-frame indices, and canvas dimensions.
Our verification library derives higher-level geometry, motion, timing, visibility, and inter-element relations from these measurements. Verification checks and reports. Each verification program contains readable Python checks that receive the animation matrix and test one prompt requirement.
Each check returns a pass or fail decision with supporting details and measurements.
The verification report records every check’s outcome and evidence together with any execution error.
An animation passes only when the program defines at least one check, every check passes, and execution completes without error.
Missing or malformed measurements and execution errors produce explicit failed outcomes rather than successful or missing decisions. Attempt scoring. We compute pass@1 as the mean success rate across benchmark instances.
For pass@ k k , let n i n_{i} be the number of attempts for instance i i and c i c_{i} the number that succeed.
We use pass ​ @ ⁡ k = 1 N ​ ∑ i = 1 N [ 1 − ( n i − c i k ) ( n i k ) ] . \operatorname{pass@}k=\frac{1}{N}\sum_{i=1}^{N}\left[1-\frac{\binom{n_{i}-c_{i}}{k}}{\binom{n_{i}}{k}}\right]. Each benchmark instance therefore receives equal weight regardless of its number of retained attempts. B.2 Verification Program Construction Construction configuration. Appendix C Measuring Alignment with Human Judgment C.1 Human Judgment Protocol Decision rules. Annotators label an animation as a match only when it satisfies every requirement in the motion edit prompt, and one violated requirement is sufficient for a non-match.
Specified timing, magnitude, pivot, pose, and relation requirements are part of this decision, while aesthetic preference is not.
We instruct annotators to mark an animation as a non-match when content moves out of view, becomes clipped, or becomes too small to inspect unless the prompt requests that behavior.
Annotators use cannot judge only for technical failures that leave no meaningful animation to inspect, such as a crashed program that renders a still frame.
The input static SVG provides the expected scene geometry and appearance when the prompt refers to it, while the source Lottie animation is one valid clarification rather than an exact target.
Before reviewing the collection, annotators complete starter calibration examples and receive clarifications for recurring edge cases. Interface and review record. Figure 7 shows the information and controls available during review.
Each annotator inspects the input static SVG, generated animation, and motion edit prompt and can reveal the source Lottie animation when the prompt needs clarification.
For a non-match, annotators select the unsatisfied prompt spans and describe the visible violation.
They also record their reasoning for cannot-judge decisions and for matches that require a judgment call.
These comments support the final label but need not enumerate every violation when an animation fails many requirements. Independent review and consensus. Each animation receives independent decisions from two assigned annotators.
Because only three annotators are initially available and reviewer capacity later grows to six, we divide the reviews into two batches.
Review Batch 1 assigns 1,055 animations to two of the initial three annotators, and Review Batch 2 assigns 925 animations to two of six annotators.
Together, the batches yield 3,960 assigned reviews across 29 generation configurations from seven providers.
We hide the generating model, verification-program decision, and the other annotator’s initial decision.
When binary decisions differ, the same pair revisits the animation and discusses the prompt, and we assign a binary final label only when both annotators agree.
Because the final exports retain only active revised decisions rather than overwritten initial decisions, we cannot reliably reconstruct initial agreement and do not report it. Review outcomes. Across the 1,980 reviewed animations, annotators approve 500, reject 1,449, jointly mark 28 as cannot judge, and leave three approval–rejection differences unresolved.
Among the 1,949 animations with binary labels, we use 1,585 for construction, reserve 180 for held-out testing, and exclude 184 human rejections. Because a check can combine several conditions, failing one check does not necessarily mean missing exactly one animation requirement. D.3 Failure Mode Analysis Identifying failure modes. Because our verification checks test specific animation requirements, their reports let us analyze how an animation fails, not just whether it passes.
We use GPT-6 Astra with maximum reasoning effort to review each motion edit prompt, the verification program, and the measurements in our verification reports.
We annotate the checks with the failure modes in Table 9 and apply these annotations to all attempts.
When a check tests several requirements, we use its individual comparisons to identify the failure rather than assign every associated mode. Table 9: Definitions of the 16 failure modes.
Each definition applies only to the animation requirements supported by the corresponding prompt and verification checks.
The prerequisite rules below determine when an unavailable dependent comparison counts as failure or remains unknown. Failure mode Condition violated Reference-pose mismatch A requested starting, ending, return, or resting pose does not match its reference. Motion trajectory mismatch A translation or rotation follows the wrong path, direction, excursion, angle, or destination. Event coordination mismatch Related actions have the wrong order, phase, overlap, or coordination. Linked-part or joint mismatch Carried or attached parts, rigid groups, or named joints do not preserve their requested relationships. Spatial relation or contact mismatch Positions, alignment, separation, contact, or geometric containment violate a requested relationship. Transform-origin mismatch A rotation, scale, or deformation uses the wrong requested center, hinge, pivot, or anchor. Easing or speed mismatch Motion has the wrong pace, deceleration, easing, or smoothness. Repetition mismatch An action trace has the wrong event count or repeated within-cycle pattern. Shape or scale mismatch A shape, aspect ratio, scale change, or deformation misses its requested form or amount. Duration or hold mismatch An action or state has the wrong pause, hold length, relative duration, or required continuity. Visibility-state mismatch A hidden or visible state, opacity, fade, or illumination violates the prompt. Occlusion or clipping mismatch Covering, masking, clipping, or visible-region relationships violate the prompt. Missing or incomplete action A requested action is absent or incomplete. Required stationarity mismatch A target, part, axis, or geometric state required to remain fixed changes. Reveal or erasure mismatch A stroke, band, or region is exposed or removed with the wrong spatial progression. Appearance-preservation mismatch Requested color, paint, stroke, or appearance preservation is violated. Interpreting check failures. Some requirements depend on others: a missing object cannot follow its requested path.
If a failed check cannot evaluate a requirement because a necessary earlier condition is unmet, we count that dependent requirement as failed.
We mark a mode absent only when all its relevant requirements are confirmed to pass, and leave other inconclusive cases unknown.
This analysis does not change our original verification decisions or benchmark scores. Failure rates and coverage. We compute each mode’s failure rate only over benchmark instances with a check for the corresponding requirement.
To avoid giving configurations with more attempts extra weight, we calculate each configuration’s fraction of attempts with that failure mode on each instance, then average equally across these instances and all 47 configurations.
Coverage is the share of those attempts with enough evidence to decide whether the mode occurred, using the same weights; unknown cases remain in the denominator.
To keep a high rate on a rare requirement from dominating the benchmark-wide ranking, we multiply each rate by the fraction of our 100 instances with a relevant check.
The modes overlap, so these rankings do not describe independent capabilities.
