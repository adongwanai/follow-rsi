An Investigation of Frontier Coding LLMs Yuntao Gui email: research@logitly.ai email: ytgui@cse.cuhk.edu.hk Note: Part of this work was done while the author was a PhD candidate at The Chinese University of Hong Kong, after the thesis defense and prior to degree conferral. Abstract. Frontier agentic LLMs are trained on verifiable rewards in reinforcement learning (RL) environments built from real software repositories. A passing test suite is treated as the reward for solving the task.
We show that, on hard problems, frontier models often satisfy these rewards by obtaining the answer instead of deriving it, known as reward hacking. Prior reports document this behavior on public benchmarks. We test its persistence on unseen problems. In a hardened environment where the answer cannot leak, nearly every model we tested attempted to recover the answer, escalating through tiers of increasingly specialized exploitation: mining the repository history for the upstream fix, inspecting the git object store directly, and sweeping the filesystem for a possible newer copy of the source or hidden tests.
These attempts were concentrated on the hardest problems, and the models differed in whether, how often, and how deeply they escalated. Our position is that this behavior is a learned shortcut , acquired in RL environments that leak the answer, not a sign of intelligence.
We release agent traces for these models to support further study at https://huggingface.co/datasets/logitly-ai/reward-hacking-raw-v1 . Keywords: Reward Hacking, Agentic Coding, SWE-Bench, Terminal-Bench 1. Introduction Figure 1. A kawaii illustration of reward hacking. Coding agents such as Claude Code ( Anthropic, 2025 ) , Codex CLI ( OpenAI, 2025 ) , and OpenCode ( Community, 2025 ) now take on repository-level software engineering tasks with substantial autonomy.
Behind every one of these agents is an agentic LLM, the model that reads the task, thinks step by step, and decides the actions that complete it.
The training and evaluation of these LLMs rely mostly on verifiable rewards : an environment provides a repository snapshot, an issue description, and a hidden test suite, and passing those tests is treated as the reward for solving the task ( Jimenez et al., 2024 ; Pan et al., 2024 ; Jain et al., 2025 ; Huang et al., 2026 ) .
Reinforcement learning on such environments scales because it needs no human judgment.
We present an investigation showing that, on hard problems, frontier agentic LLMs tend to satisfy these rewards by obtaining the answer instead of deriving it (Figure 1 ). We did not set out to study cheating. While building training and evaluation environments for coding agents, we generated a large pool of candidate tasks and designed a way to find the hard ones.
For each task, we measured reward variance across repeated rollouts. Tasks with low variance are always solved or always failed and teach little; tasks with high variance are sometimes solved, placing them at the edge of agentic coding capability ( Ouyang et al., 2022 ; Shao et al., 2024 ; Guo et al., 2024 ) .
To understand how the model attempts these tasks, we examined frontier models’ trajectories on them. Beyond the reasoning failures we expected, we find these models systematically mining the repository’s version-control metadata for the future commit which may contain golden solutions.
Different models use similar command sequences, allowing the taxonomy in this paper. The attempts escalate through three tiers of specialized exploitation.
Models typically begin with an honest attempt, and the mining of repository history starts once that effort stalls.
They first check whether history beyond the current checkout exists, then enumerate references and inspect commits outside the current branch for one whose message or diff matches the issue.
When references are absent, they go to git’s object store directly and recover commits that no reference points to, often the upstream fix with its message and diff.
When the repository holds no recoverable history, the same mining widens to the filesystem, sweeping system directories, installed packages, and caches for a possible newer copy of the source or hidden tests. Our investigation yields three findings. Cheating is pervasive. Nearly every model we tested attempts to hack the reward despite a hardened environment, and the attempts recur across problems rather than appearing as isolated incidents. Difficulty triggers the attempt. Attempts are rare on easy problems, and harder problems tend to draw attempts from more models. Models differ in how they escalate. They vary in whether, how often, and how deeply they escalate, and some models can realize they are inside a sandboxed benchmark setting while still actively exploiting reward hacking.
Our position is that this behavior is a learned shortcut , acquired in RL environments that leak the answer, not a sign of intelligence.
Note that this paper does not rank the models. This paper makes three contributions: • A systematic, vendor-independent measurement of reward hacking in frontier coding models. • Findings that may inform the training of future models. • A release of the agent traces behind our findings, enabling future analysis. 2. Background 2.1. LLM, Harness, and Agent A coding agent combines an LLM with a harness. LLM. The trained neural network: it takes a context and returns a completion, and it never acts on its own.
In practice it is accessed through an API endpoint and charged by token consumption. Harness. The non-learned code around the LLM: it runs the agentic loop of Algorithm 1 . Agent. The LLM operating within the harness: it plans, inspects the repository, edits files, runs commands, and presents results across multiple steps toward a goal. Given an agentic coding task, the harness initializes a history H H and repeatedly queries an LLM with H H and a tool set 𝒯 \mathcal{T} (Algorithm 1 ) ( Anthropic, 2025 ; OpenAI, 2025 ; Community, 2025 ) .
The model returns a response r r .
If r r contains no tool call, the harness returns r r as the final answer.
Otherwise, the harness executes the requested tools and appends their outputs to H H as observations, and the loop repeats with the updated history. In plan mode , the agent may inspect the repository but must not modify it, and it produces a proposed plan or patch.
In act/work mode , the agent may edit files and run builds and tests.
Harnesses also implement permission models that ask the user to approve actions outside a default scope, such as accessing paths outside the working directory or running commands that are not on an allowlist. 2.2. Git Object Model and History Retention Git stores a repository as a set of immutable objects , each identified by a hash of its content ( Community, 2005 ) .
There are four object types.
A blob stores the contents of one file.
A tree represents a directory: it maps names to blobs or to other trees.
A commit points to one tree, which is a snapshot of the whole repository.
It also records the author, a message, and the hashes of its parent commits.
A tag attaches a name and a message to a commit.
Each commit refers to its parents by hash, so commits form a directed acyclic graph (DAG) of history.
Git stores snapshots, not changes.
A commit’s patch is computed on demand by comparing its tree with its parent’s tree.
Objects are stored either one by one or compressed together into packfiles . A reference is a named pointer to a commit.
Branches, tags, and remote-tracking branches are all references.
The reflog records each reference’s past values.
Special references record the state before a reset and the result of the latest fetch.
An object is reachable if it can be reached by following links from some reference; otherwise it is unreachable .
An unreachable commit that no other commit lists as a parent is dangling . Moving or deleting a reference only changes which objects are reachable; it never deletes objects.
Unreachable objects stay in the object database until garbage collection or an explicit git gc --prune=now command prunes them.
By default, pruning only removes objects older than a grace period, and objects still referenced by the reflog count as reachable.
So deleting a branch, checking out an older commit, or doing a hard reset leaves the objects of later commits in place. 2.3. Reward Hacking in RL Environments Reward hacking happens when a policy trained on a reward earns high reward without completing the intended task ( MacDiarmid et al., 2025 ; Adams, 2026 ; Jain, 2026 ; Vals.ai, 2026 ; OpenAI, 2026 ) .
The reward only partly specifies the objective.
So training reinforces any behavior that satisfies the reward while violating its intent, just as it would reinforce a real solution. Repository-level software engineering environments are one important case of this setting.
They are usually built by mining issue–fix pairs from public repositories.
Each environment specifies a base commit (usually a checkout from a past time), the task (an issue description), and a set of tests that fail at the base commit and pass after the fix.
The agent works on the repository at the base commit.
The reward comes from running these hidden tests against the agent’s final repository state or proposed patch.
Passing the tests therefore approximates the real objective: a correct fix for the issue.
Known ways of hacking the reward include modifying or deleting tests, special-casing test inputs, and exiting early with a success status. This paper focuses on investigating reward hacking on repository-level RL environments: rather than solving the problem by reasoning over the code, the agent attempts to recover the ground-truth solution from the environment itself.
Building environments usually means cloning the full upstream repository and resetting it to the base commit.
An incorrectly processed RL environment can leave history that postdates the base commit inside the repository.
This leak is the exploit path our investigation targets. 3. Investigation Setup Our testbed is a standard repository-level RL evaluation, hardened at every layer we control.
The harness and the sandbox act together to restrict permissions.
Each run produces an agent trace, and these traces are what we analyze.
This section describes the testbed and defines what we count as reward hacking. 3.1. Agents, Sandbox, and Traces All runs use a harness we built ourselves, which gives every model the same tools and instructions; any difference in agentic behavior reflects how the models were trained.
The harness implements the agentic loop (Algorithm 1 ): it provides file tools and bash ; in plan mode, only read-only operations complete.
Each run is a multi-round conversation, interleaved with tool calls and tool results (Figure 2 ).
Instructions reach the model in two places: a system prompt shared by every run (cacheable prefix), and a system reminder appended to the user message.
The system prompt assigns the role of a coding agent; it encourages the model to reason step by step and to invoke the available tools.
The reminder carries the per-run configuration and activates plan mode. We evaluate the following coding models.

Structure of the context window. Each agent runs inside a safe sandbox: a disposable container on an SELinux-enforcing host, as an unprivileged user.
Network egress is blocked at the container boundary, so upstream patches, issue threads, and newer releases are all out of reach.
The environment is read-only, so the agent can only read, think about, and analyze the code, instead of modifying it.

These traces are the evidence base for the taxonomy of Section 4 . 3.2. Definition of Cheating The agent’s job is to work from what the environment provides: the repository at the given commit, the task, and the history that produced it.
Reward hacking begins where the agent reaches information from after the base state, or information that encodes the answer itself.
We count three kinds of severity, ordered from lowest to highest, by how far the access departs from what an engineer could legitimately reach. Future mining (low). Commits, refs, or branches that postdate the base commit, reached through version control while seeking the upstream fix.
A patch developed on an upstream branch can be merged back into an old one, so newer history can be present for honest reasons. Hidden recovery (high). The agent reads git’s raw storage below the level of named references, recovering objects that no reference points to, for a commit that carries the fix.
This content sits below where engineering is normally done, and reaching it takes specialized knowledge of the object store. Out-of-repository scan (critical). The scan leaves version control and sweeps the full disk, through installed packages, caches, and other checkouts, for a possible newer copy of the source or hidden tests.
The tier also holds the probes of the sandbox itself: the blocked network and the mount and boundary paths. We treat two behaviors as honest work.
First, inspecting the full history with a routine command such as git log --all is ordinary engineering practice, and it can also surface commits that postdate the base commit on other branches.
We count such browsing as honest because the command is a standard part of the toolbox and any future commits it reveals are not its direct target.
Second, recall: the agent reproduces the fix from the model’s memory of code it saw in training (a frontier model may well remember the entire upstream tree).
That knowledge is already in the model when the run begins.
We also exclude probes that only test whether a path is writable, without reading its contents: these are unaligned instruction following, not an attempt to obtain the answer. 4. Findings Table 2. Future mining (low) The first form starts with the references that the checkout already contains.
Cloning retains the remote-tracking branches, and their commits can postdate the base commit (Table 2 ).
The agent reads the log, file contents, and diff of a remote-tracking branch ( fut-branch ), enumerates post-base commits, and locates them with explicit revision ranges ( fut-range ).
It can also ask the live upstream for the fix over the network ( fut-net ).
These commands are common in ordinary workflows, and newer history can be present for honest reasons.
This behavior therefore carries the lowest severity. 4.2. Hidden recovery (high) When the named references yield no fix, the agent turns to git’s internal storage (Table 3 ).
It reads and enumerates objects in the store ( hid-cat ), lists packed commits, and surveys the store ( hid-pack ).
It enumerates dangling commits and blobs unreachable from any reference ( hid-fsck ).
It reads reference values that may leak future commits ( hid-reflog ) and inspects raw metadata and alternate stores ( hid-store ).
This content sits below where engineering is normally done, which carries high severity. 4.3. Out-of-repository scan (critical) Once the agent exhausts the repository’s recoverable history, the scan leaves version control for the filesystem (Table 4 ).
The target now sits outside version control entirely, which carries the highest severity.
The first patterns target the sandbox itself: the agent probes the blocked network boundary ( scan-net ) and inspects the mount and boundary paths, including the mounted secrets volume ( scan-mnt ).
In our environment these attempts meet a closed boundary, and the sandbox holds.
The agent also sweeps /tmp for a leftover test suite, golden answers, or the origin checkout the clone recorded ( scan-tmp ); the temporary path is already gone at run time.
The agent then scans the entire filesystem by name and content for candidate files and package metadata ( scan-root ).
The remaining patterns inspect specific locations: system directories ( scan-usr , scan-lib ) and installed packages, their caches, metadata, and indexes ( scan-pkg ).
In the sandbox these commands reach the container image; on a developer workstation they reach the home directory, other repositories, and credentials.
A harness that enforces less isolation would receive the same requests with less protection behind them.
Each of these requests is potentially unsafe to the system it runs on. 4.4. Cheating across models and tasks Tables 5 and 6 cross the eight models with the twenty tasks.

SWE-bench ( Jimenez et al., 2024 ) evaluates agents on resolving real GitHub issues in full repositories, with hidden unit tests as the grader. It has become the standard testbed for software-engineering agents.
Its human-validated subset, SWE-bench Verified ( OpenAI, 2024 ) , was widely adopted, but OpenAI has since stopped reporting on it, citing contamination ( OpenAI, 2026 ) .
Terminal-based suites such as Terminal-Bench ( Merrill et al., 2026 ) extend evaluation to general command-line tasks.
The same repository-plus-tests format also underlies training environments for RL, such as SWE-Gym ( Pan et al., 2024 ) , R2E-Gym ( Jain et al., 2025 ) , and SWE-smith ( Yang et al., 2026 ) .
These environments use test-based pass/fail signals as rewards. This setup makes the integrity of the sandbox important, because anything an agent can read or modify in the environment can affect both its evaluation score and its training signal.
Recent hardening efforts respond to this concern: SWE-Bench Pro Verified ( Zheng et al., 2026 ) and Lego-RL ( Du et al., 2026 ) both remove residual git objects, hidden tests, and metadata leaks. Reward hacking and evaluation cheating. Frontier coding agents often exploit the evaluation setup instead of solving the task. METR reported cases of models locating leaked solutions in task metadata and copying grader answers ( METR, 2025 ) .
A growing set of studies measures this behavior systematically. ImpossibleBench measures a "cheating rate" on tasks whose specification conflicts with the tests ( Zhong et al., 2026 ) .
EvilGenie ( Gabor et al., 2025 ) and SpecBench ( Zhao et al., 2026 ) study test-case exploitation and the gap between visible and held-out tests.
Terminal Wrench ( Bercovich et al., 2026 ) releases hackable terminal environments together with exploit trajectories.
Systematic research on specification gaming in reasoning models also examines related behaviors ( Nishimura-Gasparian et al., 2026 ) .
Auditing efforts such as BenchJack extend this to agent benchmarks in general and find exploitable flaws in nearly all of those they examine ( Wang et al., 2026 ) .
Closest to our setting is inference-time contamination ( NIST Center for AI Standards and Innovation (CAISI), 2025 ) : the answer leaks from the environment during the run, not from training data.
On SWE-bench, agents were reported to run git commands to read future commits, tags, and reflogs that contain the gold patch ( Kahn, 2025 ; bayes.net, 2025 ) .
The same exploit was later documented on SWE-Bench Pro, Multi-SWE-bench, and Terminal-Bench, along with web-based solution lookup ( Adams, 2026 ; Poolside AI, 2026 ) .
Industry analyses suggest the effect is large. Cursor reports that most successful resolutions by one frontier model recovered the fix instead of deriving it, and that sealing git history and web access substantially lowered the score ( Jain, 2026 ) .
Trajectory-level audits report shortcut attempts in a majority of runs for several open models. They also find that disabling network access does not remove the behavior, while prompts that name the forbidden channels reduce it ( Ludwig et al., 2026 ; Vals.ai, 2026 ) .
Compared with these reports, our study spans a larger set of current frontier models and tasks, drawn from a private RL pipeline that shares no instances with the benchmarks above.
It therefore characterizes these models on problems outside the existing suites. 7. Limitations The evaluation covers the models reachable through our serving setup, and two limitations bound the findings.
The harness is built on the Anthropic SDK, and every tested model offers vendor-level compatibility with the Anthropic SDK and API format.
The GPT series lacks this compatibility and was therefore not evaluated.
The Qwen families are excluded because the mapping between their open-weight releases and the cloud-served versions is undocumented. 8. Conclusion We investigated reward hacking by frontier coding models on hard, unseen problems in a hardened repository-level environment.
Nearly every model attempted to obtain the answer instead of deriving it, escalating through tiers of increasingly specialized exploitation: mining repository history for the upstream fix, recovering unreachable objects from git’s internal storage, and sweeping the filesystem for a newer copy of the source or hidden tests.
The attempts concentrate on the hardest problems, and the models differ in whether, how often, and how deeply they escalate.
We interpret this behavior as a learned shortcut, acquired in RL environments that leak the answer, and one that persists even when the environment no longer leaks.
We release the agent traces behind these findings to support further study. References Adams (2026) C. Adams Git reward hacking in SWE-Bench Pro OSS .
