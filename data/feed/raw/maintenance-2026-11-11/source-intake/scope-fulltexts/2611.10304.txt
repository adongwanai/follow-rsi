A.6 Case Study of Problem-Statement Repair A.7 Repair-Round Distribution A.8 Detailed Dataset Composition A.9 Agent Model Configurations License: CC BY 4.0 arXiv:2611.10304v1 [cs.SE] 06 Nov 2026 Longtail-SWE: High-Quality SWE Tasks for Underrepresented Languages Vladimir Dobrovolskii 1 , Ibragim Badertdinov 1 , Alexander Golubev 1* 1 Nebius * Correspondence to: alex_golubev@nebius.com Abstract Challenging repository-level benchmarks remain limited for many programming language ecosystems, where filtering scarce candidates with ambiguous descriptions or defective tests can discard valuable engineering problems. We introduce Longtail-SWE, a benchmark of 202 issue-resolution tasks across 13 languages with limited coverage in existing repository-level benchmarks: Clojure, Dart, Elixir, Erlang, F#, Haskell, Julia, Kotlin, Lua, OCaml, R, Scala, and Swift. Its construction uses a solver–judge–repairer pipeline: a solver attempts each candidate task, and a judge reviews the task together with the solver’s trajectory and test results to guide revisions to tests and task descriptions. These revisions aim to correct tests that reject valid alternative implementations or accept incorrect solutions while retaining challenging tasks and preserving their intended requirements. We evaluate nine model configurations, including frontier models, and analyze task-solving performance, consistency across repeated attempts, and resource usage. We release all benchmark instances, executable environments, complete construction and evaluation tooling, and agent trajectories, together with an additional set of easier tasks to support evaluation of smaller models. 1 Introduction Repository-level benchmarks evaluate whether coding agents can resolve real software issues in existing codebases Jimenez et al. (2023) . SWE-bench Jimenez et al. (2023) has introduced a pipeline for task collection for Python, and later Multi-SWE-bench Zan et al. (2025) , SWE-PolyBench Rashid et al. (2025) , and SWE-Bench Pro Deng et al. (2025) have broadened this setting beyond it. However, many programming language ecosystems remain sparsely represented in dedicated issue-resolution evaluations. This limits the evidence available about how well agents work with different libraries, toolchains, and development practices. Extending this coverage requires executable tasks that are both challenging and reliably evaluated. Such tasks are commonly built from historical issues and pull requests (PRs), whose original fixes serve as reference patches. However, checking that a reference patch resolves test failures without regressions does not establish evaluation reliability Yu et al. (2026) . PR-specific tests may reject valid alternative implementations, and descriptions may omit requirements that agents cannot infer from the available context Chowdhury et al. (2024) , while insufficient tests may accept incorrect solutions Yu et al. (2025) . Filtering can discard repairable tasks and bias benchmark composition: the SWE-bench Multilingual release notes that requiring clear descriptions and unambiguous tests favors small code changes Khandpur et al. (2025) . Recovering such candidates is especially important in underrepresented ecosystems with limited task pools. Building on prior work on test strengthening Yu et al. (2026) , specification repair Wang et al. (2025) , and agent-informed review Desai et al. (2026) , we jointly refine descriptions and tests to retain challenging tasks. We introduce Longtail-SWE , a benchmark of 202 tasks derived from real pull requests across 13 programming languages: Clojure, Dart, Elixir, Erlang, F#, Haskell, Julia, Kotlin, Lua, OCaml, R, Scala, and Swift. These languages span diverse programming paradigms and application domains, providing a dedicated setting for examining agent performance beyond the ecosystems emphasized by existing issue-resolution benchmarks. We construct Longtail-SWE using a solver–judge–repairer pipeline. A solver attempts each task; a judge compares its trajectory and test results with the task description, reference patch, and tests to distinguish solver errors from task defects. The judge’s findings guide a repair agent in revising tests and appending clarifications to the description. These revisions aim to reject incorrect solutions without excluding valid alternatives or prescribing implementation details, while preserving the task’s intended engineering requirements. Our contributions are threefold: • Task recovery and refinement. Our central contribution is a solver–judge–repairer pipeline that coordinates revisions to task descriptions and tests, allowing scarce repository-level tasks with repairable defects to be retained rather than discarded. • Benchmark and companion set. Applying this method yields Longtail-SWE, a benchmark of 202 challenging tasks across 13 underrepresented programming languages, together with a companion set of easier tasks. • Empirical analysis. We quantify how task recovery and refinement improve executable candidate yield and final task retention. We evaluate nine model configurations, comparing task-solving performance across languages, consistency across repeated attempts, and resource usage. 2 Related Work Repository-level and multilingual benchmarks. Longtail-SWE uses solver trajectories and judge feedback to guide coordinated repairs to descriptions and tests, aiming to preserve intended requirements while addressing both incorrect acceptance and incorrect rejection of agent solutions. 3 Method Longtail-SWE builds on SWE-rebench V2 for task collection and executable environment construction. We modify the candidate selection and environment installation procedures, and add a solver–judge–repairer stage that uses solution attempts to identify and repair task defects, followed by benchmark finalization based on additional solver runs for quality and difficulty assessment. The goal is to retain challenging tasks whose descriptions and tests support reliable evaluation. 3.1 Task Definition and Pipeline Overview Longtail-SWE follows the repository-level issue-resolution setting of SWE-bench. Each task consists of a public problem statement, a repository at a pre-fix revision (the base commit ), an executable environment, a reference patch , and an evaluation test patch . We obtain the problem statement from a GitHub issue and extract the reference and test patches from its associated merged pull request (PR). Our pipeline comprises four stages: collection, construction, repair, and dataset finalization (Figure 1 ). Throughout curation, we retain the original issue and PR data and keep the reference patch unchanged. During task construction, we identify FAIL_TO_PASS (F2P) tests by applying the same evaluation test patch at the base commit and after the reference patch: these tests fail in the first state and pass in the second. PASS_TO_PASS (P2P) tests pass in both states and serve as regression checks. The solver receives the statement and repository environment and produces a solution patch. We evaluate each solution patch in a fresh, separate container, discarding solver changes to test files before applying the evaluation test patch. We use this evaluation procedure consistently across pipeline stages. An attempt is successful if its solution passes all designated F2P and P2P tests. Figure 1: Longtail-SWE pipeline. Executable candidates enter a solver–judge–repairer loop with execution revalidation; judge-accepted tasks proceed to difficulty selection and final quality review. 3.2 Candidate Collection and Screening Source collection and prioritization. For each target language, we independently use the GitHub API to collect merged PRs linked to a single issue from eligible repositories. Candidates require a usable base commit and nonempty, separable reference and test patches. Appendix A.1 lists the repository eligibility criteria and PR filters. When processing capacity is limited, we prioritize larger reference patches by modified-file count, then patch length, both in descending order. Semantic screening. Kimi K3 Kimi Team et al. (2026) assigns diagnostic categories inherited from SWE-rebench V2. We retain A (well-specified and solvable as-is) and two potentially repairable categories: B2 (tests require names, signatures, or values absent from the statement) and B5 (tests may depend on incidental reference-implementation details). Other categories, including tasks requiring unavailable external information, visual context, or non-English understanding, are excluded. 3.3 Environment Construction and Initial Validation Environment preparation and initial audit. For each language, we prepare one or more versioned base Docker images to accommodate differences among repositories in runtime versions, build systems, and dependencies. Starting from the base commit, an auditor agent inspects the repository documentation, configuration, and CI, determines the project-native installation, build, and test commands, then installs task-specific dependencies and verifies the installation with existing tests. It also compares the problem statement, repository context, reference patch, and test patch, revising tests when necessary to generalize implementation-specific checks or add missing test coverage of the required behavior. The auditor may replace implementation hints in the problem statement with [HIDDEN] , leaving other text unchanged. Examples of such replacements can be found in Appendix A.4 . The subsequent repair procedure described in Section 3.4 is append-only. We preserve the raw issue, installation/build/test commands, and resulting test patch. Reproducibility checks. We repeat installation, building, and testing from scratch in a clean container based on the task’s selected base Docker image. We run the evaluation tests before and after applying the reference patch, requiring at least one F2P test and all designated evaluation tests to pass with the reference patch. We then build an image for each task with its repository dependencies pre-installed and repeat the checks inside it, comparing the results with the saved test groups and task configuration. Candidates enter the next stage only after these checks succeed; unsuccessful construction attempts are returned for revision or excluded. 3.4 Solver-Guided Task Diagnosis and Repair Diagnosis from solution attempts. For each executable candidate, a solver attempts to complete the task. A judge then reviews the solver trajectories, solution patches, and evaluation outcomes in the task-specific Docker image, alongside the statement, reference patch, and tests. The verdict can expose underspecification or overly restrictive checks, while test-passing solutions that are still incorrect can reveal missing test coverage for edge cases. The judge distinguishes implementation errors from description, test, or environment defects and accepts the candidate or requests repair. Once the judge accepts the current task version, the task proceeds to a judge agent using a different model configuration; if that judge identifies a new issue, the task returns to repair before judging continues. A task completes this process only after acceptance from all three judge models: GPT 5.6 Luna (xhigh), GPT 5.6 Terra (high), and Kimi K3 (high). Permissible repairs. A separate repair agent receives the active judge’s diagnosis and may revise the evaluation test patch and/or append clarifications to the problem statement. The statement produced by the initial task audit, including any [HIDDEN] replacements, remains immutable during repair. Clarifications are placed in an addendum (which may be revised during description repair) to specify the expected behavior while preserving the source issue’s meaning and keeping the reference implementation undisclosed. Test changes aim to address false positive/negative cases, where wrong solutions might pass due to missed edge cases or incomplete checks, and correct solutions might fail due to overly restrictive or incorrect expectations. For description repair we use solver attempts from Kimi K3 (high), GPT 5.6 Terra (high), and GPT 5.6 Luna (xhigh); after the complete statement and its addendum are frozen for the test-repair phase, solver attempts use GPT 5.6 Sol (high). The full model configurations for the auditor, solver, judge, and repairer are provided in Appendix A.9 , and the complete agent prompts are available in our code repository. The environment remains fixed within this loop. Environment defects require returning to the construction stage. The repairer may not introduce production-code fixes through the test patch. Validation and reuse of solution attempts. Revised tests must satisfy the execution criteria above at the base commit and with the unchanged reference patch. If a revision fails, we retain the last validated version and return error logs to the repairer. Tasks with faulty reference patches are discarded. After validation, we save the updated task and return it to the solver–judge loop. Within this repair loop, test-only changes trigger reevaluation of existing solution patches, whereas changes to the problem statement require new solver attempts so that the solver can use the revised specification. The active judge reassesses the task using updated outcomes and available trajectories. Iteration and audit history. We run diagnosis–repair–validation cycles in sets of up to five rounds until all three sequential judges accept the task or we identify a faulty reference patch and discard the task. Candidate processing for a language stops once at least 30 tasks are accepted for difficulty calibration. Across the 237 difficulty-selected tasks (see Section 3.5 on difficulty calibration), repair takes 4.2 rounds on average (median 4, range 0–14). Figure A3 in Appendix A.7 shows the full distribution by language. All intermediate revisions, trajectories, and verdicts are preserved. For each judge-accepted task, we run Qwen 3.8 27B Qwen Team (2026) with xhigh reasoning three times using a 262K-token context window to guide difficulty-based selection. We exclude tasks solved in all three attempts unless doing so would leave fewer than 15 tasks in a language. In that case, we retain enough of these tasks to meet the minimum, prioritizing those with the longest average Qwen trajectory length across the three attempts. This minimum applies before post-evaluation validation; subsequent exclusions leave 12–27 tasks per language in the final 202-task benchmark. Post-evaluation validation. After evaluation, we refined the preliminary difficulty-selected pool of 237 tasks through an iterative audit, repair, and exclusion process informed by 5,688 stored solver attempts from eight model configurations, with three attempts per configuration per task (see Section 4.1 ). We first corrected evaluator defects in patch application and test-output parsing, then replayed the stored solution patches. We subsequently examined problem statements, tests, reference implementations, solver patches, and execution logs to identify tests that rejected valid solutions or accepted solutions that violated stated requirements. This semi-automated process combined human review with assistance from GPT 6 Luna, Claude Opus 5.5, GPT 6 Astra, and GPT 6 Sol, which also helped refine the tests and problem descriptions. We checked test changes by replaying stored solution patches and ran new solver attempts when problem statements changed. We excluded tasks that could not be repaired without changing their intent, such as those whose tests left requested functionality untested or conflicted with the reference patch.
We retained only tasks that passed revalidation, excluding 35 tasks and yielding the final benchmark of 202 tasks. Table 4 (Section 5.1 ) presents the full selection funnel. Each configuration uses a SWE-agent-like scaffold for three attempts per task. We compare these specific model–agent configurations, with reasoning modes and context limits listed in Table 1 . We evaluate the judge on an audit set of 65 tasks stratified by language and pipeline stage, used exclusively for evaluation rather than judge development. Two engineers independently assessed each task against predefined criteria using the task artifacts, solver trajectory, and evaluation test patch, with optional agent assistance for code inspection. Every decision required a written justification, including concrete evidence whenever tests rejected valid solutions or accepted incorrect ones. The two annotators marked 44 and 41 of the 65 tasks as problematic, respectively, agreeing on 40 tasks (Cohen’s κ = 0.15 \kappa=0.15 , reflecting the difficulty of identifying subtle task defects). They then reconciled their notes to establish a consensus gold label for every task. Of the 25 initial disagreements, 21 were resolved as REJECT , typically because one annotator spotted a defect missed by the other. The remaining four received ACCEPT : one flagged test omission involved behavior outside the problem statement, one concerned a negligible corner case, and two involved non-standard test-result parsing that proved valid. The final gold set comprises 14 accepted and 51 rejected tasks. Judge setup and results. After freezing the gold labels, we ran our sequential three-judge protocol (Section 3.4 ) using GPT 5.6 Luna (xhigh), GPT 5.6 Terra (high), and Kimi K3 (high), which returns ACCEPT only upon unanimous acceptance and routes any REJECT to repair to prioritize sensitivity to defects. The protocol rejected 56 tasks in total, correctly identifying 49 of the 51 problematic gold tasks. Treating rejection as the positive class, the judge achieves 87.5 % 87.5\% precision and 96.1 % 96.1\% recall: only 3.9 % 3.9\% of human-identified defective tasks were missed, while 12.5 % 12.5\% of rejected tasks were sent to repair unnecessarily. Our results provide a starting point for studying coding agents in these ecosystems. Revising task descriptions and tests helps recover tasks from a limited candidate pool. Our fixed-patch ablation isolates the effect of test refinement on a subset with unchanged descriptions. Further ablations are needed to separate the effects of other refinement steps and assess whether construction-time solver choices favor particular models. The human audit evaluates judge reliability on a small sample drawn from multiple pipeline stages. It does not establish the error rate of the final benchmark; this requires an independent audit of the released tasks. 6.1 Threats to Validity Construct validity. Fixing the reference patch and allowing only appended clarifications limit changes to task intent, but revisions may still alter the task contract. The paired analysis of 63 tasks with unchanged descriptions supports the test revisions; description changes are not separately evaluated in that analysis. The 65-task human audit shows high recall for problematic tasks (49/51, 96.1%) but low specificity for acceptable tasks (7/14, 50.0%), alongside low initial annotator agreement. This low specificity sends some acceptable tasks through unnecessary repair, increasing the computational resources required by the construction process. Internal validity. Difficulty selection with Qwen 3.8 27B may bias its reported scores. Some evaluated models also participate in construction and may benefit from the resulting task interpretations, though models not used during construction offer a partial check. In future work, we plan to investigate how a model’s involvement in benchmark construction affects its scores. Contamination. Tasks derive from public issues and pull requests, so overlap with training data cannot be ruled out. Because training cutoffs are often undisclosed and not determined by release dates, it is difficult to ensure that a fixed task set postdates the training data of all evaluated models. However, our pipeline can collect tasks created on or after a specified date, restricting evaluation to tasks created after a given model’s training cutoff. External validity. Repository and PR filters (permissive licenses, minimum popularity, single-issue links, prioritization of larger patches) shape the sample. With 12–27 tasks per language, language-level differences reflect these tasks and the evaluated configurations rather than inherent language difficulty. 7 Conclusion We introduced Longtail-SWE, a benchmark of 202 issue-resolution tasks from 129 repositories across 13 underrepresented programming languages. Building on SWE-rebench V2, we developed a solver–judge–repairer pipeline designed to retain challenging candidates by addressing defects in task descriptions and tests. Across nine evaluated configurations, the highest observed scores are 81.52% Pass@1 and 89.11% Pass@3. The benchmark supports evaluation across these ecosystems and further research on reliable benchmark construction; current data and code availability is described in Section 3.5 . Appendix A Appendix A.1 Detailed Collection and Filtering Rules Repository-level collection and filtering rules. Repository collection uses the following criteria and search procedures: • Repositories are searched separately for each target language using the GitHub language label. • Repositories must have at least 10 GitHub stars. • Repositories must have been updated on or after January 1, 2026. • Archived repositories are excluded. • Disabled repositories are excluded. • Only licenses on the permissive SPDX allowlist are accepted: 0BSD, Apache-2.0, BSD-2-Clause, BSD-3-Clause, BSL-1.0, CC0-1.0, ISC, MIT, PostgreSQL, Python-2.0, Unlicense, and Zlib. • Missing or unknown licenses are rejected unless an exception is explicitly recorded. • No filter is specified in the default configuration for total file count, lines of code, or checkout size. • Searches reaching the 1,000-result cap are split into nonoverlapping date or star-count ranges; results are then deduplicated. Pull-request-level collection and filtering rules. PR collection uses the following criteria, with processing order noted separately from eligibility: • Only merged PRs are accepted. • Each PR must be linked to an issue. • PRs linked to multiple distinct issues are excluded; duplicate records of the same PR–issue pair do not count as multiple issues. • PRs must fall within the configured inclusive date window. • Bot-generated PRs are excluded. • Automated dependency updates are excluded. • PRs may change at most 1,000 files. • The production/reference patch must modify at least one supported file. • The test patch must modify at least one supported source or test-bearing file. • The production patch must contain at least five added lines by default. • The combined size of recognized diff sections for code files must be less than 100,000 characters. • The problem statement must be less than 100,000 characters. • No upper limit on test patch size is imposed by the default language-specific procedure. • Both the reference patch and the test patch must be nonempty. • A usable base commit must exist. • Candidates are rejected if tests are detected inside production (non-test) files. • Some language batches are sorted by change size; this determines processing order rather than serving as a universal acceptance filter. A.5 Case Studies of Test Repair We sampled two illustrative cases from the 63 released tasks whose problem statements did not change during repair. This restriction allows the same solver trajectories and solution patches to be evaluated against the pre-repair and post-repair tests: for each corresponding run, the Opus 5.5 (high) trajectory and submitted patch are identical across the two evaluations. The cases illustrate two distinct test defects and are not intended to estimate their prevalence in the dataset. Removing an unstated representation constraint. The esl__amoc-193 task asks that a required module attribute accept a binary description, making Elixir strings usable alongside the existing Erlang charlist form. All three Opus patches add a binary clause to check_mandatory_fields while retaining the existing charlist clause. The pre-repair tests correctly check that a binary description is accepted, but also require a charlist description to be stored as a binary and make additional exact-value assertions about nested character data and Unicode. The problem statement does not require conversion of existing charlists. All three patches fail the pre-repair suite at the charlist assertion even though they implement the requested binary-acceptance behavior. The post-repair tests continue to require the binary description to be preserved exactly. For the legacy charlist, however, they check successful processing without prescribing its stored representation; they also remove the nested-character-data and Unicode-normalization assertions. The test identifiers and command remain unchanged. Under the post-repair tests, the same three Opus patches pass. This repair prevents rejection of solutions that meet the stated requirement but do not reproduce the reference patch’s normalization choice. Adding coverage for an incomplete implementation. The intersectmbo__cardano-ledger-5671 task asks for NoThunks instances to be removed from predicate failures throughout the codebase and from ContextError types in every era. The run 2 Opus patch removes many such instances but leaves five in the TPraos protocol code. The reference patch removes all five. The pre-repair tests check only five Shelley predicate-failure types and a Void control case, so they do not exercise the remaining TPraos types and incorrectly accept the run 2 patch. The post-repair tests expand the checks across eras and protocol rules while retaining a control for the detection mechanism. When the identical run 2 patch is evaluated against the post-repair suite, 5 of 74 examples fail—exactly the five remaining TPraos instances. The test command is unchanged. Thus, the post-repair tests turn a false positive into a failure by covering behavior explicitly required by the problem statement.
