Forks show the logical structure and strips the physical sequence, where red bars are delimiters and a tilde, as in p ~ 1 \tilde{p}_{1} , marks an answer that may differ. 1 Introduction Large language models increasingly serve as core decision engines within complex systems for tasks such as routing requests ( Ong et al., 2024 ) , evaluating responses ( Zheng et al., 2023 ) , and deciding the next steps of agents ( Yao et al., 2023 ) .
Generating text to make categorical choices wastes computational resources on unnecessary tokens and increases latency, leading to the emergence of Jev ( TypeSafe AI, 2026 ) and other specialized decision models ( StartLux, 2026 ; Open-Jev, 2026 ) for these tasks.
These models typically process extensive context, such as a lengthy conversation or an agent trajectory, to answer several questions about it, outputting probability distributions over multiple discrete choices.
When deployed on every routed request and agent action, with strict thresholds acting on their probabilities ( Decision Index, 2026 ) , these confidence-sensitive models call for an inference engine that is both fast and precise. However, current inference engines severely constrain the application of decision models since they are optimized for text generation, where the fundamental unit of work is a single linear sequence.
When processing decisions, frameworks like vLLM ( vLLM Project, 2026d ) and SGLang ( SGLang Project, 2026c ) treat every question as an independent prompt, rendering, tokenizing and scheduling the shared context once for every question.
The latest vLLM computes the shared context of a request once before its questions ( vLLM Project, 2026b ) , yet every question still runs as a sequence of its own and resumes from the prefix cache.
On hybrid architectures this cache restores recurrent states only at block boundaries ( Pan et al., 2025 ; Jing et al., 2026 ) , and every question and every agent step thus computes the tokens past the last boundary again.
Alternatively, multi-item scoring ( SGLang Project, 2026a ) appends all questions to a single context with a delimiter token before each.
Every question then reads this extra token, which changes its hidden states and corrupts its output probabilities compared to isolated prompts ( SGLang Project, 2026b ) .
Furthermore, under dynamic batching, the order of floating-point sums changes with the batch ( He and Thinking Machines Lab, 2025 ) , which can yield fluctuating decisions for the identical request under varying server loads.
All of these issues severely compromise the reliability and efficiency of decision model serving. The root cause is a mismatch between the logical structure of a decision request and the physical structure in which current engines execute it.
Logically, the questions of a request are separate branches of a tree whose trunk is the shared state, and each branch must see only the trunk and itself.
Physically, these branches should run together over a single copy of the trunk, which speeds up inference by computing the trunk only once and letting many short branches fill the GPU in one pass.
Generation engines tie the physical layout to the logical one, running every question as a separate sequence that computes or reloads the trunk again.
Multi-item scoring ties them the other way and does run the branches together.
Yet it writes the tree into the sequence itself, and its delimiter tokens enter the input of every branch and, as Figure 1 illustrates, shift the probabilities and flip decisions.
Closing this gap means running the branches together while each still computes exactly what it would compute alone, so the physical stream must keep apart the branches it places side by side.
An attention layer can keep them apart with a mask, yet the Gated DeltaNet layers ( Yang et al., 2025 ) of hybrid models such as Qwen3.5 ( Qwen Team, 2026 ) fold every earlier token into one recurrent state, through which a branch would inherit its siblings.
Separating the branches there requires each of them to restart from the exact state of its trunk, inside the same pass that computes the trunk. To address this, we propose Flide (Flat-Graph Inference for Decision Models), an efficient and exact inference engine that separates the logical structure of decision requests from their physical execution on the GPU.
Flide lays a round of requests out as one flat token stream and records their dependencies in GPU-resident metadata.
With ForkAttention, the attention and Gated DeltaNet layers follow these dependencies, and in exact arithmetic every question computes what it would compute alone.
Since the request structure is encoded in data, a small set of recorded execution graphs can serve different request compositions.
The same state-forking mechanism also supports growing agent histories, allowing later requests to resume from checkpoints saved during earlier inference passes.
In addition, an optional batch-invariant mode fixes floating-point reduction orders to keep answers bitwise identical across server loads. We evaluate Flide against state-of-the-art inference engines on workloads ranging from one question per passage to articles and agent trajectories with many questions.
Experimental results show that Flide answers up to 9.5 times faster than vLLM and SGLang on public hybrid models and leads on dedicated decision models.
Its throughput leads at every concurrency level whenever a shared state carries several questions.
Meanwhile, as multi-item scoring shifts probabilities to gain throughput, Flide yields outputs closest to the float32 reference distributions in total variation distance.
These results establish that separating the logical structure of decision requests from their physical execution lets an inference engine be exact and fast at once. Our contributions are threefold. • We trace both the repeated computation and the shifted answers of current engines to one root cause, the coupling between the logical structure of a decision request and its physical execution. • We propose Flide, which keeps each request as a tree in GPU metadata while running every round as one flat stream, and forks every state exactly with ForkAttention. • On public hybrid and decision models, Flide answers up to an order of magnitude faster than vLLM and SGLang while staying closest to the float32 reference in total variation. 2 Related Work Prefix Sharing and State Branching. Modern serving systems reduce redundant computation by caching key-value representations of reusable prompt prefixes ( Kwon et al., 2023 ; Zheng et al., 2024a ; Zheng et al., 2024b ) .
Specialized execution kernels retrieve these cached representations during decoding via cascade attention ( Ye et al., 2025 ; Juravsky et al., 2024 ; Ye et al., 2024 ; Zhu et al., 2024 ) or sequence-tree traversals ( Yao et al., 2025 ) .
For hybrid architectures containing recurrent states ( Gu and Dao, 2023 ; Yang et al., 2025 ) , existing frameworks either constrain state materialization to coarse block boundaries ( Pan et al., 2025 ; vLLM Project, 2026c ; Jing et al., 2026 ) or require predefined checkpoint positions ( Shirokikh and Nikolenko, 2026 ) .
Speculative decoding verifies token trees with tree attention ( Miao et al., 2024 ; Cai et al., 2024 ) , and its hybrid variants propagate recurrent states along the branches ( Wu et al., 2025 ; Ghantasala, 2026 ; Ma, 2026 ) .
Domain-specific frontends fork requests into isolated sequences that query a shared prefix cache ( Zheng et al., 2024a ) .
However, all of these mechanisms mandate a strict temporal separation where shared prefixes must complete execution and populate memory buffers before downstream queries can consume them.
Flide eliminates this decoupled caching phase by evaluating both the shared context and every branching question within a single forward pass, dynamically propagating both attention and Gated DeltaNet states across a flattened token sequence. Decision Model Serving and Execution Exactness. Decision-making architectures operate under strict latency budgets and rely on well-calibrated categorical distributions ( TypeSafe AI, 2026 ; OneJev Team, 2026 ; Open-Jev, 2026 ; vLLM Semantic Router, 2026 ) .
Existing engines handle these single-token workloads either by processing questions as isolated sequences ( Du et al., 2025 ; vLLM Project, 2026d ; SGLang Project, 2026c ) , which repeats prefix calculations, or by concatenating candidate queries with delimiter tokens ( SGLang Project, 2026a ) , which invalidates isolated query semantics and requires CPU-managed segmentation that breaks CUDA graph capture.
Standard graph capture strategies mitigate prefill dispatch overhead by padding requests to static shapes ( SGLang Team, 2026 ) , but still treat the individual sequence as the primitive unit of execution.
Even when the prefix is computed once beforehand ( vLLM Project, 2026b ) , every question resumes from the cache as a sequence of its own.
Other specialized variants incur latency penalties by scanning block masks ( Chouhan and Perry, 2026 ; Antunes et al., 2026 ) , packing spoken input streams into eager passes ( Jin et al., 2026 ) , or evaluating candidate trees across segmented passes ( Ma et al., 2026 ) .
Compounding these systemic overheads, LLM serving engines let co-scheduled requests change the outputs of one another, whereas database systems share work across concurrent queries while keeping each query isolated ( Sellis, 1988 ) .
Prefix cache substitutions create observable discrepancies compared to isolated evaluation ( Patodiya, 2026 ) , and dynamic reduction orders cause floating-point nondeterminism ( He and Thinking Machines Lab, 2025 ) .
Existing batch-invariant kernels slow serving by 34 percent on Qwen3-8B in SGLang ( SGLang Team, 2025 ) , and the batch-invariant mode of vLLM cannot execute recurrent Gated DeltaNet layers ( vLLM Project, 2026a ) .
Flide resolves these scheduling and numerical conflicts simultaneously by executing multi-branch rounds through GPU-resident metadata.
This approach preserves full CUDA graph replay across dynamic workloads while every answer equals its standalone computation in exact arithmetic.

As illustrated in Figure 2 , Flide keeps the tree of each request as its logical structure and runs every round of requests as one flat token stream on the GPU. 3.1 Problem Formulation A decision model receives a state and several questions about it in one request, as in the System One API ( TypeSafe AI, 2026 ) that vLLM ( vLLM Project, 2026d ) and SGLang ( SGLang Project, 2026c ) serve.
A decision request r = ( s , q 1 , … , q n ) r=(s,q_{1},\dots,q_{n}) comprises a state s s of P P tokens and n n questions, where question q i q_{i} has | q i | |q_{i}| tokens, as illustrated in Figure 2 (a).
Flide renders the prompt for every question exactly as it would appear if asked in isolation.
It defines s s as the longest sequence of leading tokens that all such prompts share before the text of their questions begins.
Consequently, the concatenation s ⊕ q i s\oplus q_{i} matches the standalone prompt for q i q_{i} token for token.
Let h i h_{i} denote the final hidden state at the last token of q i q_{i} when the model processes s ⊕ q i s\oplus q_{i} .
Each question q i q_{i} comes with a set of options O i O_{i} , and the engine computes the probability of each option as p i ​ ( o ) = exp ⁡ ( w o ⊤ ​ h i ) ∑ o ′ ∈ O i exp ⁡ ( w o ′ ⊤ ​ h i ) , o ∈ O i , p_{i}(o)=\frac{\exp(w_{o}^{\top}h_{i})}{\sum_{o^{\prime}\in O_{i}}\exp(w_{o^{\prime}}^{\top}h_{i})},\qquad o\in O_{i}, (1) where w o w_{o} is the row of the output head corresponding to option o o .

In exact arithmetic, p i p_{i} depends only on s s and q i q_{i} , remaining independent of other concurrent questions or requests. Naively processing s ⊕ q i s\oplus q_{i} as a separate sequence for every question requires n ​ P + ∑ i | q i | nP+\sum_{i}|q_{i}| token computations, which redundantly evaluates the shared state n n times.
Computing the state and each question exactly once reduces this cost to P + ∑ i | q i | P+\sum_{i}|q_{i}| .
While prefix caching approximates this efficiency, it still forces every question to execute as an independent sequence that resumes from the cache.
To reach this count, Flide computes the shared state and all of its questions jointly in a single forward pass, which raises three challenges once every answer must stay exact. • First , every question must keep its exact standalone computation, which rules out any change to its input such as a delimiter before each question.
Hybrid models make this harder, since their Gated DeltaNet layers ( Yang et al., 2025 ) compress all prior tokens into a single recurrent state and leave no attention matrix to mask. • Second , rounds mixing requests of arbitrary numbers and lengths must run with minimal GPU launch overhead, given that a short decision request takes only a few milliseconds of GPU time.
CUDA graphs remove these launches but fix the shape of every launch, whereas the tree of a round changes from one round to the next. • Third , when a state grows incrementally over the successive steps of an agent, the engine must reuse the unchanged part of the previous state and compute only its short mutable tail and the newly appended tokens. 3.2 ForkAttention To resolve the first challenge, ForkAttention structures each decision request as a computational tree where the shared state forms a common trunk and the questions fork as independent branches.
Evaluating the shared trunk once allows every question to inherit the prefix representation without redundant computation or prompt modifications.
Pointwise operations, including linear projections, normalization layers, and multilayer perceptrons, remain indifferent to this tree structure because they process each token in complete isolation.
State forking therefore requires intervention only in the token-mixing layers, which must grant questions access to the shared trunk while isolating sibling branches from each other.
Flide maps this tree onto the GPU by flattening an entire round of requests into a single continuous token stream without padding.

Proposition 3.1 . For a causal model in exact arithmetic, the hidden state computed by Flide at any token of question q i q_{i} is identical to the hidden state at that token when the model processes s ⊕ q i s\oplus q_{i} in isolation, regardless of other requests and questions in the same round. The proof proceeds by induction over the layers and is provided in Appendix A .
In other words, the result that the tree of a request defines holds under any flat layout of the round.
In floating point, the differences stay at the rounding level, which the tests of Appendix G check on every change of the engine. 3.3 Flat-Graph Execution Flat-graph execution resolves the second challenge by turning the forks of a round into GPU work with negligible launch overhead, as illustrated in Figure 2 (c).
A short decision request on a small model takes only a few milliseconds of GPU time, which launching several thousand kernels one by one would dominate.
Although CUDA graphs eliminate these sequential launches, a captured graph fixes the shape of every kernel launch, whereas a server encounters rounds containing requests of highly variable numbers and lengths.
To reconcile this, Flide keeps the tree of a round purely as GPU data.
The shape of every launch then depends on the length of the flat stream alone, and a small collection of captured graphs accommodates any mix of requests and questions. 3.3.1 GPU-Resident Metadata All variables determined by the round composition, including segment lengths, positional indices, key ranges, and state indices, reside in compact device buffers populated before graph replay, from which every kernel derives its workload.
The attention kernel fetches keys from two sources, the shared state of the request and the query’s specific question, and skips the states of other requests interleaved in the stream.
The kernel constructs its tile table directly on the GPU, loads the fully visible key blocks without applying a mask, and restricts masking exclusively to partially visible blocks.
The Gated DeltaNet layers iterate over a list of fixed-length chunks populated by each round, with any unused entries beyond the active chunks returning immediately.
Consequently, altering the mix of requests only modifies the buffer contents while preserving the exact launch configuration of the captured graph. 3.3.2 Graphs over Stream Lengths Building on length-bucketed CUDA graph capture ( SGLang Team, 2026 ) , Flide allows rounds with different decision-tree structures to reuse the same captured graph.
At server initialization, Flide captures a family of flat graphs indexed by stream capacity T T .
Each graph also reserves fixed capacities for requests, question segments, Gated DeltaNet chunks, and readout rows.
The actual request boundaries and question dependencies are supplied through GPU-resident metadata, allowing different request mixes to share the same execution graph.
For each round, Flide selects the smallest graph whose buffers can accommodate both its flattened stream and associated metadata.
Tokens are packed without padding between requests; padding occurs only at the tail, where dense layers still perform computation but no valid token accesses the padded positions.
If a round exceeds the largest graph’s capacity, Flide splits it along request boundaries into multiple replays.
An individual request exceeding this capacity runs through the same flat-stream execution without CUDA graph replay. 3.3.3 Selective Readout The output head of Equation 1 reads only the last token of every question, so in the final layer every token still contributes its keys and values while the rest of the layer, its MLP included, runs only at these rows.
An index buffer of fixed size in every graph holds the rows, which skips most of the final-layer work without changing any output in exact arithmetic. 3.4 Incremental State Forking Successive steps of an agent trajectory often share most of their state, and therefore most of the trunk of their decision trees.
Flide exploits this overlap by checkpointing the state of a request at an internal position m m .
A later request can resume from the checkpoint when its tokens up to m m match.
Each checkpoint stores the float32 recurrent state and convolution window of every Gated DeltaNet layer at m m , together with the keys and values of the full-attention layers before m m .
This allows a resumed request to compute the same function as a fresh one in exact arithmetic.
Flide places m m slightly before the end of a state so that tokens likely to change at the next step, such as those at the end of a conversational turn, fall after the checkpoint. Flide generates the checkpoint during the same forward pass that computes the request’s answers.
To achieve this, Flide divides the state segments of the stream into two levels at their checkpoints.
Each Gated DeltaNet layer processes the two levels sequentially, saving the final states of the first level as checkpoints and passing them to the second through the same state-indexing mechanism used for question forking.
For full attention, cached keys and values precede newly computed ones in a buffer representing each state’s history, allowing resumed states to be processed without occupying a contiguous span of the flat stream.
At each agent step, Flide thus computes the new tokens and a short uncached tail only once for all questions, saves a checkpoint for the next step, and forks the questions from the completed state, as illustrated in Figure 2 (d). 3.5 Bitwise Determinism Proposition 3.1 makes the result of the tree independent of the flat layout in exact arithmetic, yet in floating point a matrix product over more rows may pick another kernel, tile shape or reduction split and reorder the sums of an output element ( He and Thinking Machines Lab, 2025 ) .
Flide therefore offers an optional mode, in the spirit of batch-invariant inference ( He and Thinking Machines Lab, 2025 ) , in which no reduction depends on the composition of the round.
Every matrix product sums each output element in a fixed order whatever the number of rows, and every question gets attention tiles and Gated DeltaNet chunks of its own, which start its reductions exactly at the fork.

Table 3 compares the three engines on Qwen3.5 and Gemma 4, while Figure 3 summarizes their relative speeds across workloads, from which we draw three findings. First, Flide is faster even with a single question per state.
On Qwen3.5, it cuts the latency of a lone request by up to 3.2 times on the smallest model.
The gain comes from one flat-graph replay per round, against the heavier front ends and schedulers of generation engines.
Under load, where model computation dominates, Flide matches the best baseline. Second, the advantage grows substantially when multiple questions share a state.
Flide leads at every model size and concurrency level, achieving up to 9.5 times lower latency and 8.5 times higher throughput than the best baseline.
The largest gains occur on QuALITY and MultiRC, which carry the most questions per state, since ForkAttention computes the shared state once for all of them while conventional engines repeatedly compute or restore it.
Multi-item scoring also shares the state but introduces delimiter tokens and runs without CUDA graphs.
Flide achieves higher throughput while preserving each question’s standalone computation in exact arithmetic. Finally, Flide also maintains its advantage on full-attention models.
Even against vLLM’s prefix cache, which already computes the shared state of Gemma 4 once, Flide cuts the latency of multi-question requests by 1.1 to 2.9 times.
These results highlight the efficiency of executing an entire request in one forward pass, beyond the computational savings provided by prefix caching. 4.3 Answer Fidelity One question per state All Regardless of the agent count, Flide ultimately completes 4.4 to 7.2 times the steps per second of the strongest baseline. 5 Conclusion In this paper, we presented Flide, an efficient and exact inference engine for decision models that decouples the logical tree structure of each request from its physical execution within a single flattened token stream.
By leveraging ForkAttention, Flide forks intermediate states precisely across both attention and recurrent layers, replaying arbitrary execution rounds through compact pre-recorded graphs while extending agent histories directly from checkpoints saved in earlier passes.
This architecture resolves the fundamental conflict between hierarchical request logic and sequential token execution, eliminating both the redundant prefix computations and the delimiter tokens that shift the answers of existing serving engines.
Extensive evaluations across hybrid and full-attention architectures, specialized decision benchmarks, and real-world agent trajectories demonstrate that Flide achieves substantial speedups over current state-of-the-art frameworks while staying closest to the float32 reference distributions on Qwen3.5.
By unifying high-throughput parallel execution with strict mathematical exactness, Flide establishes a principled foundation for scalable, latency-critical decision intelligence in next-generation LLM agent systems. Every token of s ⊕ q i s\oplus q_{i} enters the stream with the token id and position it has in the standalone sequence, and norms, projections, the MLP and the rotary embedding act on one token at a time.
A full-attention layer lets each token of q i q_{i} see exactly the tokens before it in s ⊕ q i s\oplus q_{i} by Equation 3 , and each Gated DeltaNet layer continues q i q_{i} from the recurrent state 𝐒 P \mathbf{S}_{P} and the convolution window that s s reaches alone.
Equal inputs to a layer therefore give equal outputs, and induction over the layers proves the proposition, since no step involves another request or question of the round.
A checkpoint restores the values that a fresh pass reaches at its position, and selective readout only drops rows that no read uses, so both keep this equality. Flide ships its kernels compiled and tuned in a bundle independent of the Triton installation.

The kernel tests compare the attention and fused pointwise kernels with a PyTorch ( Paszke et al., 2019 ) reference over head sizes, grouped heads, sliding windows and every layout of a round, where every error stays at the rounding level of float32 and bfloat16 and the key blocks read without a mask return the same bits as with one.
