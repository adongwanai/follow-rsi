We present ReSkill, a selective self-improvement framework that concentrates revision on capability gaps.
A coding agent constructs an object-centric task graph from an instruction and a skill library, then uses node-level execution records to locate failures.
At the task level, it revises stage organization, hand-off conditions, and recovery routes; at the skill level, it strengthens perception, motion, manipulation, and verification capabilities that repeatedly fail.
Candidate revisions undergo full-task evaluation and paired comparisons before adoption, allowing local changes to accumulate into validated skills and an independently executable policy.
The agent participates only during development; the deployed policy calls the retained skills without invoking the agent at run time.
On the same development set, average success across ten RoboDojo tasks rises from 30.0% for the initial versions to 86.2% for the final adopted programs; retained programs achieve 83.6% in recorded robustness and model-selection evaluations. Across eight real-world tasks, ReSkill succeeds in 72 of 80 rebuilt-simulation trials and 62 of 80 real-robot trials (77.5%).
The median revision changes only three functions, approximately 0.5% of a program, while 39% of task-specific functions in later-added tasks directly reuse existing implementations.
These results show how locating local deficiencies, validating candidate changes, and accumulating reusable skills can improve execution of compositional manipulation tasks. ReSkill revises the task graph and local skills during development, validates the changes, and retains reusable skills and an executable policy requiring no run-time Agent calls. 1 Introduction When a robot encounters a new manipulation task, the capability it lacks often covers only part of the task.
A compositional task may involve observation, approach, grasping, transport, placement, and return; existing controllers or skills can already handle many of these stages, while a few fail on new objects, layouts, occlusions, or execution conditions.
Robot foundation models have expanded robots’ ability to act on visual and language inputs [ 23 , 1 ] , while language-model agents have enabled flexible task decomposition and skill coordination [ 6 , 7 ] .
Nevertheless, new multi-stage tasks are often treated as unified learning or adaptation problems.
This can require relearning capabilities the robot already has and increase the costs of data, computation, and real-world interaction.
This raises a more fundamental question: when a robot encounters a new compositional manipulation task, what exactly should it improve? Existing research addresses this problem through end-to-end policy learning, skill composition, and agent self-improvement, but still lacks explicit modeling of where capability gaps occur.
End-to-end policies map observations and task instructions directly to actions [ 23 , 1 ] , making it difficult to distinguish stages that already work reliably from those that need improvement.
Agentic manipulation systems based on task decomposition, programmatic control, and skill calls [ 6 , 7 , 13 , 5 ] flexibly compose existing capabilities, but mainly improve how those capabilities are organized and used: when a skill repeatedly fails under new conditions, replanning or calling the same skill again does not change the skill itself.
Voyager accumulates executable skills, Reflexion stores reflections from task feedback, and Self-Refine iteratively critiques and revises model outputs [ 17 , 12 , 11 ] .
For robot manipulation, candidate revisions must also be assessed across layouts: an improvement on a few development scenes may not persist under different initial conditions.
The unresolved question is therefore: how can a robot first locate the capability gaps in a task, improve only those parts, and reliably judge whether the improvement is real and worth retaining and reusing? We introduce ReSkill, a framework for selective self-improvement on compositional manipulation tasks (Figure 1 ).
The robot first identifies the task structure and assesses its existing capabilities, then concentrates improvement on the gaps that remain.
A coding agent serves as the learning orchestrator, constructing an object-centric task graph from a task description and, optionally, one demonstration.
Each node specifies a skill call, its object roles, entry and completion conditions, and budget; edges specify success, failure, and recovery routes.
Within this graph, explicit geometric routines handle stages that can be programmed directly, and library skills cover interactions the robot already knows how to perform.
Repeated execution failures reveal the unresolved stages or skills and direct the agent’s revisions, allowing development to preserve and build on capabilities that already work. Improvement proceeds at two scales, using the same node-level execution records and visual traces.
At the task level, the agent locates the earliest stage that deviates and revises stage decomposition, hand-off conditions, skill bindings, or recovery procedures.
For example, in cup nesting it changes the release-stage completion condition to require both release and the intended nesting relation, while keeping the grasping and insertion skills unchanged.
At the skill level, improvement is organized around four types of reusable capability: perception skills estimate object geometry, motion skills generate feasible trajectories, manipulation skills perform interactions such as grasping and placement, and verification skills check outcomes and guide correction.
Failure evidence accumulated across tasks identifies which skill needs strengthening; validated improvements are shared through the skill library or transferred into other task programs.
New tasks therefore start from the existing task with the closest skill requirements. Every revision at either scale must pass multi-stage evaluation before adoption.
Candidates are screened on a few development layouts, evaluated on the full development set and robustness layouts, and compared with the incumbent on paired test layouts available only to the orchestrator.
When results are close, paired evaluations are repeated on layouts where outcomes disagree.
This links local revision to evidence that determines whether an improvement should be retained and reused. We evaluate ReSkill on ten RoboDojo simulation tasks [ 3 ] and eight real-world tasks on the Xtrainer platform.
For each real-world task, a single teleoperated demonstration is used to rebuild the corresponding scene in MuJoCo (real-to-sim); development takes place in the rebuilt environment, and the resulting program is deployed on the real robot (sim-to-real).
This process supplies a development environment for real-world tasks and is not itself part of the method.
The coding agent participates only during development, revising task graphs and skills, submitting evaluations, and deciding which revisions to adopt; the deployed program is frozen and makes no external large-model calls at run time.
Model selection uses test layouts accessed by the orchestrator.
On RoboDojo, retained programs make zero run-time API calls and achieve an average success rate of 83.6% across the ten tasks in 337 recorded evaluation episodes.
During development, average task success rises from 30.0% for the initial task graphs to 86.2%.
On the eight real-world tasks, ReSkill succeeds in 72 of 80 trials in rebuilt simulation and 62 of 80 trials on the real robot.
We further analyze revision locality, the evolution of failure types, cross-task skill reuse and how quickly new tasks get started, the role of a single demonstration, and development-agent model usage. Our main contributions are as follows. Selective Self-Improvement via Task Graphs We introduce a selective self-improvement framework that organizes stages, skills, and recovery routes in an object-centric task graph and focuses improvement on the stages and skills that actually fail during execution, rather than relearning the entire task. Two-Scale Improvement: Task-Graph Revision and Skill Reuse We unify failure-driven task-graph revision with skill organization, improvement, and reuse in a single development loop, and provide a multi-stage evaluation and adoption protocol centered on paired comparisons on model-selection test layouts to assess which revisions improve task execution. Empirical Study of How Skills Improve, Transfer and Pay Off We evaluate the framework on ten RoboDojo simulation tasks and eight real-world tasks on the Xtrainer platform, and use more than ten thousand verified simulation episodes and code snapshots from 774 revisions to quantify revision locality, the evolution of failure types, function-level skill reuse, the role of demonstrations, and development cost. 1.1 Related work 1.1.1 Agentic and self-improving robot systems Recent robot systems increasingly use high-level agents to decompose complex tasks into combinations of programmatic operations and learned skills.
SayCan and Code as Policies demonstrate language models’ ability to decompose tasks and invoke skills [ 6 , 7 ] ; the more recent Harness VLA [ 22 ] combines a frozen vision–language–action model with analytic primitives and extends the policy’s effective range through re-grounding, staging, and skill orchestration.
ASPIRE, Zetta, and RISE explore robot self-improvement through programmatic skill accumulation, failure recovery, and policy-level optimization, respectively [ 9 , 4 , 19 ] .
ReSkill couples task-graph revision with local skill improvement: execution records identify whether a failure calls for a change in task organization or skill implementation, and paired evaluation determines which updates are retained for later tasks.
Our central questions are where improvement is actually needed and how improvements can be reliably retained and reused. 1.1.2 Skill libraries and code as policies Earlier work on long-horizon bimanual manipulation also used staged learning: Mixline learns subtasks with online reinforcement learning and combines them through offline learning from the resulting trajectories [ 14 ] .
Programs provide a natural representation for organizing robot skills: Code as Policies and ProgPrompt use language models to write programs that call perception and control primitives [ 7 , 13 ] ; Inner Monologue returns execution feedback to the planner as text [ 5 ] ; Voyager stores generated skill code in a retrievable library for later tasks [ 17 ] ; and Eureka uses a coding agent to iteratively rewrite reward functions [ 10 ] .
ReSkill likewise represents skills and task graphs as programs, but does not generate them on the fly at deployment: programs are repeatedly executed during development, failures are attributed to stages, and programs are frozen after multi-stage evaluation and remain unchanged during deployment.
We also measure at the code level how extensively skills are reused verbatim or with rewriting across tasks (Section 3.5 ), a quantity rarely reported systematically in prior work. 1.1.3 Agent-driven iterative improvement Reflexion uses task feedback to guide subsequent attempts [ 12 ] , and Self-Refine iteratively critiques and revises an output using feedback generated by the same model [ 11 ] , while The AI Scientist delegates the propose–implement–experiment–summarize process to a model [ 8 ] .
Robot-task feedback varies across layouts, and development layouts are limited; relying on those layouts alone can mistake fitting specific scenes for a capability improvement.
We therefore treat improvement during development as a version-selection problem, using multiple layout splits, progressively stricter adoption rules, and paired comparisons on the model-selection test layouts to decide which revisions to retain (Section 2.4 ). 2 Methods Figure 2 : ReSkill constructs and improves an executable task policy.

Given a task description ℓ \ell (a natural-language instruction and a description of the success criterion), the robot’s observation and control interfaces, and optionally one demonstration τ D \tau^{D} , the system outputs a task program 𝒫 = ( G , Π , Λ ) , \mathcal{P}=\bigl(G,\ \Pi,\ \Lambda\bigr), (1) where G G is an object-centric task graph, Π \Pi is a versioned skill library, and Λ \Lambda records node–skill bindings, parameters, and budgets.
The goal is for the same program to handle variation in initial object positions, object counts, and geometry within an object category while keeping the task goal and success criterion fixed. At run time, the program may use only observations: head and wrist camera images, camera calibration, joint states, the robot model, and instruction text.
Object poses, simulator state, and evaluation results are not inputs; success is determined solely by the environment’s native criterion, and the controller cannot declare success itself.
On RoboDojo, we enforce this through three layers of input auditing—static code checks, interception of run-time file access, and an environment boundary that exposes only the control interface—and deploy the program as a separate policy-server process that exchanges observations and actions with the simulator only through the official client. ReSkill organizes program construction and improvement at two scales (Figure 2 ).
The task level determines which stages compose a task, how stages hand off to one another, and how to recover from failure; the skill level determines whether the skill called at each stage is sufficiently reliable and improves the skill itself when it is not.
Both scales use the same execution records, and revisions occur between episodes: within an evaluation, the task graph and skills remain frozen, and only the closed-loop checks within nodes retry from new observations.
Revisions at both scales enter the next program version only after the multi-stage evaluation in Section 2.4 . 2.2 Object-centric task graph Nodes and edges. The task graph is G = ( V , E ) G=(V,E) , with nodes v i = ( s i , ℛ i , P i , T i , B i ) , v_{i}=\bigl(s_{i},\ \mathcal{R}_{i},\ P_{i},\ T_{i},\ B_{i}\bigr), (2) where s i s_{i} is the skill or program called by the node, ℛ i = ( Actor , Object , Goal / Reference ) \mathcal{R}_{i}=(\mathrm{Actor},\mathrm{Object},\mathrm{Goal/Reference}) specifies the object roles, P i P_{i} and T i T_{i} are the entry and completion conditions, respectively, and B i B_{i} is the action and retry budget.
Executing a node returns r i = ( status , cause , evidence , actions ) , status ∈ { Pass , Fail , Unknown } . r_{i}=(\text{status},\ \text{cause},\ \text{evidence},\ \text{actions}),\qquad\text{status}\in\{\textsc{Pass},\textsc{Fail},\textsc{Unknown}\}. (3) Edges E E specify a successor for each of the three outcomes: another node, termination, or return home.
A node returns Unknown when a required observation is missing, which does not count as success.
Execution ends upon reaching a terminal node, exhausting the action budget, exceeding a node’s limit on consecutive unsuccessful attempts, or exceeding the total transition limit.
The status, cause, evidence, action count, and duration of each node visit are recorded as the common basis for failure attribution at both scales. Executor bindings. Nodes use two kinds of executors: stages with clear geometric goals—approach, transport, release, push, and return—are written directly as programs that calculate motion targets from current object relations, while interactions with reliable implementations in the library—such as grasping with empty-grasp verification and placement with offset verification—reuse skills.
Both kinds are implemented in code, with no new policy network trained for an individual task; the only end-to-end learned model used by a program is the segmentation model SAM 3, while all other perception, motion, and verification use geometric calculations and rules. Graph structure. Starting from fine-grained nodes with large-scale path search, nearly all task graphs converged during development to a few coarse nodes with an act–observe–retry loop inside each node.
A typical structure is survey → \rightarrow per-object work loop → \rightarrow return home; the work loop selects a target, grasps, verifies, transports, places, and checks again, with retries, arm switching, or hand-overs inside the node when an action fails.
Any failed or unknown node routes to the return-home node, ensuring that enough actions remain for both arms to return.
Tasks with strong structural dependencies retain more nodes: build tower, for example, has nine nodes organized by the support relations between parts.
The graph handles stage order, hand-off semantics, and recovery routes, while skill composition takes place within nodes; this division allows task-level revision and skill-level improvement to proceed separately. 2.3 Skill level: organizing, improving, and reusing skills Skill organization. The skill library Π \Pi contains four categories: perception skills convert images and depth into object geometry, including depth clustering using the table plane and height bands, point clusters within segmentation masks, color and shape discrimination, and moving the arms away before observing to avoid self-occlusion; motion skills convert target poses into joint trajectories, including damped least-squares inverse kinematics seeded at the current joints and constrained to the real joint limits [ 16 ] , Cartesian straight-line interpolation, and whole-arm collision checks; manipulation skills carry out interactions, including vertical or tilted grasping, lift–translate–forward-tilt-and-lower placement, pushing, dragging, and bimanual hand-overs; and verification skills judge interaction success through visual empty-grasp checks after lifting, offset and tilt checks after placement, and pre-grasp checks that the target remains in place.
Each skill records its role interface, admissible entry states, termination conditions, and version.
Figure 3 shows representative inputs, execution stages, and inspected states for these four categories. Skill improvement. Skill-level improvement is driven by failure evidence across tasks.
Execution records attribute each failure to a specific node and cause, such as an empty grasp, tilt after placement, or a missing observation; when the same skill fails for the same cause across tasks or layout types, the agent revises that skill individually without changing the task graph.
For example, objects swinging around the gripper during transport and landing off target led to a rule that grasps tall objects above their center of mass; objects appearing to be in their slots but not scoring, diagnosed from video as not lying flat, led to a verification skill that measures tilt after placement and presses the object flat or places it again; and the arms spreading the box walls and pushing the box away during insertion led to a release rule that opens the gripper only to the grasp width plus 1 cm inside the box, then opens it fully after lifting vertically above the rim.
An improved skill is first screened on the layouts where it failed and then undergoes full-task evaluation with the task program. Skill reuse. Skills are reused across tasks in three ways: generic implementations in the shared library that tasks call directly; cross-task transfer, which copies a validated skill implementation together with its parameters and verification logic into another task’s program, either verbatim or with rewriting; and a cross-task lessons file, maintained by the orchestrator, that records rules confirmed by native evaluation together with their source tasks—for example, “move both arms out of the head camera’s view before observing” and “grasp tall objects above their center of mass”—and serves as a starting point for every new candidate.
New tasks start from the existing task with the closest skill requirements rather than an empty skeleton, retaining its task-graph structure and skill implementations and changing only what the new task requires.
Section 3.5 quantifies implementation reuse across task-specific modules. Skill replacement. The skill-level interface also allows an entire class of skills to be replaced while the task graph remains unchanged.
One example is motion: the generic inverse-kinematics solver used early in development did not use the current joints as its seed, often jumped between solution branches, and returned solutions outside the real joint limits that swung the arm backward, causing motion-planning failures or planning times of several hundred seconds.
We replaced it with damped least-squares inverse kinematics seeded at the current joints and constrained to the real joint limits [ 16 ] , with planning and execution sharing the same solver; each task’s graph and other skills remained unchanged, while planning time fell from several hundred seconds to 1–15 s.
Another example is placement: the original tool-storage skill carried tools through the air and released them above their slots, allowing slender tools to swing and miss the slots; it was replaced by a skill that slides the tool along the table to the outside of the box wall, lifts it over the wall at the lowest feasible height, and lowers it vertically, with graph nodes and hand-off conditions unchanged (Section 3.8 ). In round r r , program 𝒫 ( r ) \mathcal{P}^{(r)} produces execution records 𝒟 ( r ) \mathcal{D}^{(r)} on development layouts, including node-level status and causes, multi-view visual traces sampled every ten actions, and the observations actually received by the controller.
The agent follows the graph to the earliest node that deviates and proposes a revision in light of its predecessor states: 𝒫 ( r + 1 ) = Revise ⁡ ( 𝒫 ( r ) , 𝒟 ( r ) ) . \mathcal{P}^{(r+1)}=\operatorname{Revise}\bigl(\mathcal{P}^{(r)},\ \mathcal{D}^{(r)}\bigr). (4) Task-level revisions affect stage decomposition (splitting long stages or inserting re-observation or hand-over nodes), hand-off conditions (rewriting completion conditions to match the native criterion), skill bindings (switching a stage to another grasping or placement skill), and recovery routes (retrying, switching arms, or putting an object down and re-grasping after failure).
Skills themselves are revised at the skill level as described in Section 2.3 ; the task level reorganizes execution through existing interfaces. Multi-stage evaluation. Each candidate is first screened on three development layouts; if it is no worse than the current best, it is evaluated on the full development set using the task score J = 100 × SR DEV + S ¯ DEV , 0 ≤ J ≤ 200 , J=100\times\mathrm{SR}_{\mathrm{DEV}}+\overline{S}_{\mathrm{DEV}},\qquad 0\leq J\leq 200, (5) where SR DEV \mathrm{SR}_{\mathrm{DEV}} is full-task success on the development set and S ¯ DEV \overline{S}_{\mathrm{DEV}} is the mean native partial-completion score from RoboDojo (0–100, reflecting progress through the task).
We call J J the task score: the maximum of 200 means that every development episode succeeds, and partial-completion scores distinguish versions with the same success count.
Promising candidates are then evaluated on two groups of robustness layouts, after which the orchestrator compares each candidate with the incumbent on paired test layouts and decides whether to adopt it.
The test set is used for model selection, and its execution records are hidden from the development agent; once a task’s test failures have been inspected, selection switches to a second test set.
Final validation requires evaluating the selected program on layouts that were not used in revision or model selection. Adoption rules. We progressively tightened the adoption rules to require improvements beyond the development layouts.
The development set contains only eight similar layouts, and candidates repeatedly improved on development layouts without improving on test layouts, or even regressed there; for such tasks, adoption therefore requires a strict improvement on the model-selection test set without regression on robustness layouts.
When the incumbent already succeeds on every test layout, the challenger must be strictly better on robustness layouts.
When two versions differ by at most four successes in a full evaluation of 64 episodes, each must be rerun at least twice on layouts where their outcomes disagree, and adoption uses the aggregate comparison rather than individual episodes. Parallel exploration. Several structurally different candidates may coexist for a task—for example, one that drags a box closer before placement and another that stages objects outside the box—and each iterates within its budget; candidates that fail to surpass the incumbent are stopped, but validated local changes can be transferred back to the main program. 2.5 Implementation The learning orchestrator uses Claude Code with Claude Opus 5.5 at two levels.
The orchestrating agent is a long-running session that checks the queue and candidate progress every 30 minutes, launches and stops candidates, runs candidate comparisons, decides adoption, maintains the cross-task lessons file, and promotes shared skills across tasks; development agents edit their own candidate programs and submit evaluations.
Humans provide only occasional directional instructions, such as stopping investment in demonstration-assisted candidates or adding tasks; they neither edit program code nor decide adoption.
Each candidate has an independent workspace containing its code and notes on hypotheses, changes, and results; when a session exhausts its context, a new session starts in the same workspace and continues from the notes and completed evaluations, making the notes the only memory across sessions.
All evaluations run on GPUs through a shared job queue, and each episode’s native result, execution record, visual trace, and input-audit report are saved.
The only learned model used at run time is the segmentation model SAM 3 [ 2 ] , with public weights kept frozen. 2.6 Experimental design and evaluation Tasks and platforms. The experiments use two task groups.
Ten RoboDojo tasks [ 3 ] run on a bimanual ARX X5 robot in Isaac Sim, covering stacking, language-conditioned manipulation, classification, organization, and storage with different stage structures; each has a native action limit of 200–1300 control steps, with each step lasting 1/25 s, and a native success criterion.
Eight real-world tasks are evaluated in rebuilt MuJoCo environments and on the Xtrainer robot, with the same task goals and separately reported results. Observations and run-time configuration. RoboDojo controllers use only RGB-D images from the head and both wrist cameras, camera calibration, joint states, the robot model, and instruction text; they read neither simulator state nor measured finger opening, because the official observation interface provides only commanded finger values.
The coding agent participates only during development; the deployed program is frozen and runs as a separate policy-server process, exchanging observations and actions with the simulator only through the official client and making no external large-model calls at run time.
All main results are from final versions with zero run-time API calls. Real-to-sim-to-real development. For each real-world task, we use one teleoperated demonstration and an agent-assisted real-to-sim process to reconstruct the corresponding robot, objects, and initial scene in MuJoCo, construct and revise the task graph in the rebuilt environment, and then deploy the frozen program on the real robot.
This process supplies a development environment for real-world tasks and is not itself part of ReSkill.
SAM 3 provides object masks in real images. Splits and protocol. RoboDojo evaluation uses development layouts to score and screen candidates, robustness layouts to assess changes across initial conditions, and a test set for orchestrator-led model selection.
The test-set execution records are hidden from development agents. We use test to denote model-selection evaluations and reserve validation for final reporting after selection.
Development uses the task score J J defined in Section 2.4 : it adds full-task success (0–100) to the native RoboDojo partial-completion score (0–100, reflecting progress through the task), giving a range of 0–200, with the maximum meaning that every development episode succeeds.
The RoboDojo results summarize the recorded evaluations of retained programs at seed 1, layouts 10–54. These records combine robustness and model-selection evaluations, including episodes used to select the retained versions; they therefore measure performance during development rather than independent final validation.
Full-task success uses the native criterion and counts episodes, including every repeat on the same layout in the denominator; the reported average is computed by first calculating the success rate of each task and then averaging these rates with equal task weights. Comparison methods. The RoboDojo Agent-as-Policy (Astra) and π 0.5 \pi_{0.5} columns reproduce full-task success from the official evaluation report [ 21 ] : Astra uses a zero-shot setting, medium reasoning effort, one seed, and 50 episodes per task; π 0.5 \pi_{0.5} uses the leaderboard snapshot of 10 September 2026 included in the report.
These public results reflect each method’s original inputs, training data, and evaluation protocol and are not fully comparable with our measurements.
We also report each task’s initial task graph on the development set—the first version written from scratch by the development agent and evaluated on the full development set—to measure improvement during development.
For the real-world tasks, we report only ReSkill’s success (Section 3.2 ). 3 Results and Discussion The experiments address four questions: (1) how well the task programs built by ReSkill complete simulated and real-world tasks, and at what execution cost (Sections 3.1 and 3.2 ); (2) how task- and skill-level improvements raise success, how much each revision changes, and how failure types evolve (Sections 3.3 and 3.4 ); (3) how extensively skills are reused across tasks (Section 3.5 ); and (4) what a single demonstration and development cost contribute (Sections 3.6 and 3.7 ).

Across the ten tasks, average success on the fixed development layouts rises from 30.0% for the initial task graphs to 86.2% for the final adopted programs.
Block stacking, language-conditioned block stacking, bowl stacking, build tower, and object classification reach or approach full success within 3–7 evaluated versions, whereas table organization, box packing, tool storage, and language-conditioned classification require 25–69 versions.
The harder tasks improve through a sequence of local changes.
In tool storage, the agent first revises the placement path to clear the box wall, then adjusts grasp-point selection for the wrench and pliers, and finally adds a post-placement tilt check followed by pressing or re-grasping.
Each candidate is evaluated as a complete task program before adoption, allowing successful changes to accumulate while preserving the stages that already work. Local execution success does not imply task completion.
Figure 6 shows how failure types change during development.
For example, tool storage succeeds in 176 of 202 late episodes, yet 24 of the 26 remaining failures pass the node checks, showing that the current local completion criteria still miss errors that prevent full-task success.
This finding indicates that self-improvement must strengthen both skill execution and the checks for node completion and stage hand-offs, so that subsequent actions start from the correct intermediate states.
Full-task evaluation therefore provides essential feedback for local revision: it exposes errors missed by node checks and guides further changes to skills, completion conditions, or recovery logic. Figure 6 : Composition of failed episodes during development.

Two consecutive snapshots of the same candidate program form one revision, giving 774 revisions.
For each revision we parsed all functions of both versions (excluding the evaluation harness), compared their abstract syntax trees, and counted added, removed, and modified functions.
Functions that build the task graph and the node entry functions they reference were assigned to the task level , all other functions (perception, motion, manipulation, and verification skills) to the skill level ; revisions that changed only parameter files were counted separately.
This assignment follows code structure and is approximate, because node entry functions often contain skill-composition logic.
For the 317 revisions whose two versions each have at least eight verified episodes on the same layouts, we also compared full-task success on those layouts. Revisions are highly local.
The median program comprises 578 functions and about 11,700 lines of code, whereas the median revision changes 3 functions—0.5% of the functions and 0.3% of the lines—and 90% of revisions change at most 1.9% of either.

Among revisions that raised success, two-level revisions contributed 48% of the total gain and skill-only revisions 36%.

Besides the ten benchmark tasks, we include four RoboDojo tasks added midway through development (bottles to bin, ring-stacking toy, eggs to tray, and laptop-and-headphone storage), which are used to examine reuse in new tasks and are excluded from the ten-task benchmark and revision statistics.

ReSkill focuses improvement on parts that repeatedly fail during execution: the median revision changes only 3 functions, and once a task graph converges to a few coarse nodes, most gains come from revising the skills within those nodes.
This works best under two conditions.
First, failures must be attributable to specific nodes and causes: node-level records of status, causes, and evidence allow the agent to decide whether to revise the task graph or a skill.
In tool storage, diagnosing the episodes in which self-checks passed but the native criterion failed as tools not lying flat led to a concrete verification skill and a substantial rise in success.
Second, the perception on which skills depend must be relatively stable: the placement, verification, and re-grasping skills accumulated during development all rely on dependable estimates of object geometry.
Object-centric semantic fields offer a complementary way to stabilize part-aware representations across observations and object instances [ 15 ] ; integrating these representations into perception skills is a direction for future work. Limits of selective improvement. Local revision may be insufficient when these conditions do not hold.
First, performance remains sensitive to the quality of the geometry estimates: the tool-storage placement skill reaches 41/47 with accurate depth geometry, whereas another lineage of the same task reaches 2/32 with less accurate depth geometry.
Second, reuse cannot supply a capability entirely absent from the library: laptop storage requires inserting a laptop at a specific orientation into a slot only about 3 mm wider than the laptop, and development went a long time without a full success because there was no reusable ancestor skill.
Third, in multi-object, long-sequence tasks such as table organization and box packing, remaining failures are distributed across placement quality, exhausted budgets, and criterion mismatch; each revision fixes only a small part, and progress slows over successive rounds.
High-precision contact and long sequences are the conditions hardest to cover with rule-based closed loops and most in need of local learning or online adaptation; enabling the agent to decide when to switch from editing code to learning a small policy is a natural next step for selective self-improvement. From simulation to self-improvement on real robots. Self-improvement in this work takes place mainly in simulation: RoboDojo development ran more than ten thousand episodes, and task graphs and skills for the real-world tasks were revised in rebuilt simulations before deployment on the real robot.
Simulation offers conditions that are difficult to obtain on hardware, including unrestricted resets, parallel execution, repeated evaluation of the same layout, and automatic scoring consistent with the task criterion.
Performing the same self-improvement directly on a real robot would require addressing automatic resets, success detection, and evaluation cost, and remains to be explored.
Our results nevertheless provide a reference: with sufficiently extensive evaluation, an agent starting from a task description and improving only what is insufficient can reach 83.6% average success across ten tasks in recorded evaluations while leaving skills that transfer across tasks.
The next step is to determine which parts of this development loop can be transferred to real robots. 4 Conclusion We introduced ReSkill to identify capability gaps in compositional manipulation, improve the relevant parts, and retain skills for continued use.
An object-centric task graph organizes existing capabilities, while node-level execution records guide revision at two scales: the task level changes stages, hand-off conditions, and recovery routes, and the skill level improves perception, motion, manipulation, and verification routines.
Candidate revisions are retained only after screening, full-task evaluation, and paired comparisons on the model-selection test set.
The resulting policy executes independently, without an agent at run time. Experiments show that local revisions can accumulate into improved full-task performance: retained ReSkill programs average 83.6% success across ten RoboDojo tasks in recorded evaluations and succeed in 72 of 80 rebuilt-simulation trials and 62 of 80 real-robot trials across eight real-world tasks.
Across 774 revisions, the median change involves only three functions, and 39% of the functions in later-added tasks directly reuse existing implementations.
Development thus leaves validated skills and execution logic that subsequent programs can build on.
The current improvement process relies mainly on simulation with repeatable evaluation and on programmatic skills supported by visual observations.
Future work will introduce local policy learning where these skills are insufficient and extend failure diagnosis, candidate validation, and skill retention to real robots. Acknowledgments Author Contributions Zheng Sun conceived the study, performed the experiments, and wrote the manuscript.
