World In-Context Learning for Agentic
Robot Manipulation
Heng Fang1, Zehui Guo1, Yuehan Zhang1, Mingyang Du1,2, Dingkang Liang1,2, Xiang Bai1
1Huazhong University of Science and Technology, 2ArcheOne AI
{hengfang,dkliang,xbai}@hust.edu.cn
Abstract
Trained action policies write manipulation skill into network weights, tying what is learned to the
distribution it is learned from. In-context learning (ICL) avoids this coupling but has not matched
trained policies, because a demonstration recorded in another scene carries no feedback from the
world the robot currently faces. We observe that what an agent learns in context is semantic,
recording task steps and object roles rather than visual appearance, so experience gathered in
one world transfers to another. Based on this insight, we propose World In-Context Learning
(WICL), a paradigm in which a frozen model starts from a demonstration, rehearses the task
in a world such as a simulator, and writes the feedback into its context rather than its weights.
We build RoboScript, a modular infrastructure that implements WICL for agentic manipulation.
From a single demonstration, RoboScript learns each task through rehearsal in simulation, freezes
the learned knowledge as a Task Memory, and deploys the frozen memory on new scenes with
data isolation that ensures every deployment input is available on a real robot. On all 50 tasks
of RoboTwin 2.0, RoboScript reaches 83.4% mean success across clean and randomized settings
with one demonstration per task and no gradient updates, exceeding the strongest trained action
policy by over 20 points. The method generalizes across visual distributions, improves through
reflection, scales with the foundation model, and transfers to a physical dual-arm robot through
cross-embodiment memory adaptation. With a world in the loop, a robot can learn a manipulation
task in its context as well as it learns one in its weights.

Introduction
In-context learning (ICL) is a defining capability of foundation models. A model with frozen weights adapts
to a new task from what its context shows, without any gradient update [5, 14]. Robot manipulation has
long followed a different path. The dominant approach trains an action policy, either a vision-language-action
(VLA) model [2, 3, 41, 55, 59, 104] or a world action model (WAM) [12, 86], and writes manipulation skill
into network weights. This approach has made clear progress, but it ties what is learned to the distribution it
is learned from. FastWAM [89], a widely adopted WAM trained on clean demonstrations of RoboTwin 2.0,
reaches 77.8% mean success on clean scenes but drops to 1.9% under domain randomization [11]. Every new
task or distribution requires new data and new training. ICL has recently emerged as a promising alternative
that avoids this coupling. Recent models can perform a new manipulation task from a single demonstration
given in their context, without any weight update [26, 68, 97]. This progress raises the question we study.
Can a robot learn a manipulation task in its context as well as it learns one in its weights?

demonstration from a different layout in its prompt, although some of its traces show it correcting its actions

Our key observation is that what an agent learns in context is semantic. It records object roles, task steps,
and what went wrong, not the visual appearance of the world. Experience gathered in one world therefore
carries over to another, as long as the two worlds agree on the semantics of the task. A cheap world that is
faithful to the task, such as a simulator, a learned world model, or a latent model of the scene, is enough to
learn in. Rehearsal in such a world is also safe, unlike acting directly on real hardware, where unsafe actions
have damaged equipment [92].
We formalize this insight as World In-Context Learning (WICL), a learning paradigm that extends in-context
learning with feedback from a world, as illustrated in Fig. 1a. A WICL learner keeps its weights frozen, starts
from a demonstration, rehearses the task in a world, and distills the feedback into its context. The resulting
knowledge is semantic and transfers from the rehearsal world to the deployment world without retraining.
After rehearsal, the context is frozen and evaluated on instances that were never rehearsed, so the result
measures generalization, not memorization. The context is readable text, which allows the agent to review its
own evaluations and rewrite what it has learned, enabling recursive self-improvement (RSI) without gradient
updates. The world makes every round of improvement safe. Coding agents have shown that this loop already
succeeds in software engineering, where the terminal serves as the world [76, 83]. Now that foundation models
have reached this capability, a simulator can serve the same role for a robot.

lifecycle that the agent carries out entirely without gradient updates. The foundation model first builds skills
for a new environment on shared entry points. It then learns each task from a single demonstration and from
rehearsal on training scenes, and freezes what it learns as a Task Memory. At deployment, it acts with the

We conduct extensive experiments and present the main results on all 50 tasks of RoboTwin 2.0, leading
to five findings. 1) One demonstration with rehearsal is sufficient. With one clean demonstration per task,
RoboScript reaches 83.4% mean success across the clean and randomized settings without gradient updates,
whereas the strongest trained action policy, trained with 50 demonstrations, reaches 61.7%. 2) What is
learned in context generalizes across distributions. Rehearsing only on clean scenes, RoboScript maintains
comparable success under domain randomization, whereas trained action policies retain at most 65.1% of
their clean success. 3) Reflection improves the frozen memory. Each round of reflection rescues more episodes
than it breaks on difficult tasks. 4) The framework improves with the foundation model. Without any change
to code, prompts, or protocol, GPT-6.1-Sol reaches 83.6/83.2% on clean/randomized scenes, GPT-5.6-Luna
reaches 79.8/76.0%, and even DeepSeek-V4.1-Flash, a lightweight model, reaches 77.8/78.4%, surpassing the
strongest trained action policy. 5) Task Memories transfer across embodiments. With a lightweight adapter
that rewrites an existing memory for a new robot, RoboScript deploys on a physical dual-arm robot without
retraining or re-rehearsing. These findings jointly show that with a world in the loop, a robot can learn a
manipulation task in its context as well as it learns one in its weights.
Our contributions are as follows.
• We formulate WICL, a learning paradigm that extends in-context learning with feedback from a world.
WICL decouples task skill from network weights and opens a path toward recursive self-improvement
without retraining. We explain why the resulting knowledge transfers across worlds.
• We build a modular infrastructure for agent-centric manipulation with strict data isolation that ensures
deployability on real hardware. We implement WICL on RoboScript with a lifecycle covering skill building,
task learning, deployment, and recursive self-improvement, all without gradient updates.
• We conduct extensive experiments with one demonstration per task and report results on RoboTwin 2.0,
across distributions, over multiple rounds of self-improvement, with three foundation models, and on a
physical dual-arm robot via cross-embodiment memory transfer, achieving state-of-the-art performance.

Related Work
Action Policies for Manipulation. The dominant approach to robot manipulation trains an action policy
and stores skill in network weights. Vision-language-action (VLA) models learn visuomotor skills end to end
from demonstrations, typically after pretraining on large cross-embodiment datasets [2, 3, 6, 40, 41, 55, 59, 61,
81, 104], with the VLA paradigm also advancing autonomous driving [21, 22, 100] and benefiting from efficient
3D representations [49, 50]. World action models (WAMs) generate future observations or latent plans and
derive actions from them [9, 16, 42, 80, 86], and driving world models jointly predict future scenes and 3D
structure [52, 98, 99]. Reinforcement learning optimizes a policy from simulator feedback [46, 62, 95] or from
real-robot trials [39, 56, 57]. All three families have advanced rapidly, yet they share a structural limitation.
Because skill resides in weights, trained policies degrade under distribution shift [11, 18, 25, 90, 101], and each
new task or domain requires additional data and gradient updates. WICL offers an alternative route. It keeps
the weights frozen and stores what it learns in context, so a new task requires rehearsal rather than retraining.
In-Context Manipulation. In robotics, in-context learning has mainly taken the form of imitation. One-shot
and few-shot methods interpret a demonstration given at test time [17, 20, 24, 36, 60, 73], while other methods
pass keypoints or keyframes to a frozen model [13, 63, 87] or retrieve demonstrations for a trained policy
[69, 82]. Recent work has shown that in-context manipulation from a single demonstration is increasingly
effective [26, 68, 97]. A parallel line uses frozen models as agents. Training-free systems compose APIs, value
maps, or keypoints [19, 23, 32, 34, 53], while hierarchical systems place a language model above a trained policy
[10, 15, 33, 35, 51, 65]. Embodied harnesses add tools, verification, and memory [27, 31, 54, 75, 93]. These
methods place demonstrations, instructions, or tool descriptions in the context, but none distills experience
from a world into a reusable memory. Among these, HarnessVLA learns from interaction but depends on a
trained policy for contact [93], and FAEA reasons iteratively within an episode but reads privileged simulator
state [72]. In contrast, RoboScript removes the trained policy from the loop and enforces data isolation by
construction. WICL adds the missing feedback. Where ICL gives the context a demonstration, WICL also
gives it outcomes from a world, and the acting agent perceives the scene through cameras only.
Self-Improving Agents and World Feedback. Language model agents can improve from interaction
while their weights stay frozen. Reflexion stores reflections on failed trials, Voyager grows a library of code
skills, and ExpeL extracts insights from past trajectories [66, 74, 94]. Later work rewrites the context
itself [1, 77, 91]. Coding agents solve real software tasks through the same loop [76, 83], though they learn
within a single episode and do not distill experience across episodes. These methods work in text and code.
WICL brings the same principle to physical manipulation, where the learned knowledge is semantic and
transfers across worlds. In-context reinforcement learning trains a model on prior interaction data so that it
improves within its context at test time [43, 44], but it requires this supervised pretraining. In manipulation,
self-improving systems collect practice data and retrain their policies [4, 64, 71, 102], and frozen language
models have used simulator feedback to write reward functions that then train policies [58]. All of these use
world feedback to update weights. World models have been used to learn behaviors in imagination [30, 37, 78],
to train policies with reinforcement learning [103], to evaluate existing policies [29, 48]. WICL uses the world
differently. It feeds outcomes back into the context with frozen weights, distills experience across episodes
into a reusable memory, and extends the loop to recursive self-improvement without gradient updates.

instances, split into a rehearsal set Ereh and an evaluation set Etest with Ereh ∩Etest = ∅. A world W takes an
instance e and a policy, and returns a trajectory τ together with feedback r. Learning starts from a context
built from the demonstration and alternates between rehearsal and revision, as shown in Fig. 3a,

Transfer across Worlds. The knowledge in C⋆transfers across worlds because it is semantic, as illustrated
in Fig. 3c. Let σ(e) denote the semantic content of an instance, namely the objects present, their roles, the
instruction, and the relative geometry on which the task depends. The context C⋆refers only to σ and to
quantities that are measured at execution time. Suppose a second world W ′ agrees with W on the semantic
content of its instances and on how behaviors change it, that is, σ(W) = σ(W ′). Then the knowledge rehearsed
in W still applies in W ′, even if W ′ differs in appearance, lighting, or physics parameters. Weights trained in
W behave differently. They absorb every regularity of W that helps fit the training data, including regularities
that W ′ does not share. This asymmetry is why WICL can learn in a cheap world and deploy in another,
whether that is a randomized simulator or a real robot.
Recursive Self-Improvement. The learner can also improve from its own evaluations, as shown in Fig. 3b.
Let B0, B1, . . . be disjoint blocks of evaluation instances and let G0 = ∅. After evaluating on Bj with context
(C⋆, Gj), the learner reflects on the resulting records Dj and writes guidance for the next block,
Gj+1 = Vθ(Gj, Dj).
(3)
The records Dj contain only what a deployed system would observe, together with whether each episode
succeeded. They do not say why an episode failed, so the learner must diagnose the causes itself. Each block
is evaluated before the learner sees its outcomes, and the next block is always unseen. This realizes recursive
self-improvement with frozen weights.
What a World Must Provide. A world is useful for WICL if it meets three conditions. It must be faithful to
the task, so that behaviors change the semantic content σ in the world as they would in the target environment.
It must be resettable, so that a behavior can be retried and compared. And it must keep rehearsal instances
apart from evaluation instances. When no world is queried, WICL reduces to ICL, with C⋆= C0 = Iθ(d). In
this paper, the world is the RoboTwin 2.0 simulator [11], and Sec. 4 describes our implementation.

4
RoboScript
RoboScript implements WICL for robot manipulation. Fig. 4 shows the pipeline together with the data tier
of each role. The world W is a simulator, the demonstration d is a single expert trajectory, and the learned
context C⋆is a Task Memory. The agent builds its action interface (Sec. 4.1), learns a Task Memory from
one demonstration (Sec. 4.2), and deploys it on unseen instances (Sec. 4.3). It can then improve the frozen
memory through reflection (Sec. 4.4). Infrastructure and protocol parameters are given in the appendix.
4.1
Perception and action
The agent perceives and acts only through tools, and the same tools run in simulation and on a real robot.
Geometric-first perception. The agent observes RGB-D images from head and wrist cameras together
with proprioception. Object detection starts from the depth channel. A height-map above the workspace
produces connected-component proposals, each lifted to a 3D bounding volume with an attribute card that
records its center, extent, and orientation. Object identity is resolved by a three-way vote among Set-of-Mark
annotation, a grounding model, and a VLM. Once identified at the start of an episode, an object is tracked by
its grasp relation to the end effector instead of re-detected after every action. Part-level localization follows
the same pipeline on a cropped region.
Action interface with receipts. The agent acts through a three-layer API. Shared entry points for grasping,
placing, corrective motions, reachability checks, and coordinated bimanual motion are environment-independent.
An environment binding discovered by automated probes supplies coordinate frames, joint limits, table height,
and gripper characteristics. Before learning, the agent builds environment-specific skills on these two layers.
It segments each demonstration into action primitives, identifies which segments the existing entries cannot
explain, and hands each gap to a coding agent that writes a skill. A driver validates each skill by running it
on the demonstration scene and checking that it transfers to other layouts without encoding any absolute
position. The loop repeats until coverage stops improving, and the final skill set is frozen before task learning.
Every action returns a receipt reporting the commanded pose, the achieved pose, the measured gripper
opening, and whether an object is held. Receipts make the feedback r in Eq. (1) concrete. Agent distinguishes
a command that was executed from an effect that was achieved to decide its next step. Receipts are derived
from proprioception and the motion planner, not from simulator state, so they match on a real robot.
4.2
Task learning from one demonstration
The agent learns a Task Memory C⋆from a single demonstration d in two stages that together realize Eq. (1).
Both stages rehearse in the world, differing only in which instances the agent faces. As shown in Fig. 4, border

Task Memory as semantic knowledge. The Task Memory is a structured Markdown document that
describes the roles of the objects and how to find them, the workflow of each stage, specifications for grasping
and placing, learned parameters, and lessons from past attempts. GraspSpec and PlaceSpec are relative
specifications expressed in terms of perceived object parts, such as “approach the handle from the left and
grasp at its midpoint.” They never contain positions in a particular scene. This representation is the concrete
form of the semantic knowledge in Sec. 3. The memory refers only to object roles and relative geometry and
therefore applies to any scene that contains the same objects in reachable positions. A memory linter enforces
this property by rejecting coordinates, ground-truth terms, and instance identifiers.
Imitation (S1). Imitation starts from the initialization C0 = Iθ(d). A reader role studies the demonstration
and writes an initial Task Memory. An acting role then practices the task on the demonstration instance, and
a reviewing role revises the memory after each attempt until the agent succeeds repeatedly.
Rehearsal (S2). Rehearsal extends this to new training instances, realizing Ck+1 = Uθ(Ck, τk, rk). The agent
practices on one instance after another, and only its first attempt on each instance counts. After a failure,
the reviewing role receives a ground-truth diagnosis and revises a cached copy of the memory. The revision
is merged into the shared memory only if it makes that instance succeed. Edits are typed and subject to a
budget that decreases with experience, so the memory stabilizes as the agent practices. Rehearsal stops when
enough recent first attempts succeed, and the memory is frozen after passing the linter.
Data isolation during learning. As Fig. 4 indicates, every acting agent observes only deployable data, the
same inputs available on a real robot. Privileged data enters only as supervision. In S1, the reader uses it to
understand the demonstration. In S2, the reviewer receives a ground-truth diagnosis of each failure. What
this supervision teaches reaches the acting agent only through the Task Memory, and the linter ensures that
the memory holds semantic knowledge, not simulator facts. The actor therefore runs entirely on data that a
real robot can provide and never accesses any simulator-specific privileged information. This isolation ensures
that the learned memory is not specific to any simulator.
4.3
Deployment with anticipation and recovery
At deployment, the agent acts with the frozen memory C⋆on instances it has never seen and receives no
feedback r from the world, as defined by Eq. (2). It runs under the official protocol of the benchmark with
unseen instructions. As Fig. 4 shows, the deployed actor uses only deployable data.
Scene anticipation. Before manipulating an object, the agent maps the demonstration’s semantic blueprint
onto the current scene. It identifies which object plays each role in the memory, checks which arm can reach
each grasp and placement, and verifies that the planned sequence is feasible. This step may call the motion
planner but never receives feedback about success and uses only deployable data.
Failure recovery without reset. A failed action does not end the episode. The agent moves to a safe pose,
observes the scene again, and continues from the current state without resetting the environment, bounded
only by the official step limit. The agent declares the task done only after its perception confirms that the
scene matches the final state of the demonstration. The simulator’s success check is the final judge, so a wrong
declaration never counts as a success. On a real robot, the same procedure runs under human supervision.
4.4
Recursive self-improvement
The reflection loop realizes the recursive self-improvement defined by Eq. (3). After an evaluation block, a
reflection agent reads the episode records, which contain only what a deployed robot would observe together
with whether each episode succeeded. It identifies failure patterns and their causes and writes a guidance
document for the next block. Since the blocks never overlap, each round tests whether the guidance generalizes
to unseen instances. Repeating this loop over several rounds lets the agent improve without gradient updates or
privileged data. No instance is ever revisited, so the improvement measures generalization, not memorization.

Experiments
We conduct extensive experiments in simulation and on real hardware, organizing the evaluation around six
questions. Can one demonstration with rehearsal compete with policies trained on many demonstrations
(Sec. 5.2)? Why does success hold under domain randomization (Sec. 5.3)? Where do the gains come from
(Sec. 5.4)? Can the agent improve from its own evaluations (Sec. 5.5)? What does it cost (Sec. 5.6)? Does the
learned knowledge transfer across embodiments to a real robot (Sec. 5.7)?
5.1
Experimental Setup
Benchmark and protocol. RoboTwin 2.0 [11] defines 50 dual-arm tasks in a clean setting (fixed background)
and a randomized setting (randomized textures, lighting, table height, and distractors). The agent first builds
its skill set across all 50 tasks, then learns each task from one automatically selected clean demonstration,
with rehearsal on clean scenes only. The frozen Task Memory is evaluated in both settings with the official
server, unseen instructions, and the official step limit. Each task is evaluated on 10 episodes per setting (1,000
episodes total), as each episode requires dozens of model calls. We report success rate averaged over all tasks,
the mean of the two settings, and retention (randomized divided by clean).

5.2
Main Results
Tab. 1 compares RoboScript with trained action policies and agents with trained policies on all 50 tasks.
One demonstration with rehearsal is sufficient. With one demonstration per task and no gradient
update, RoboScript (GPT-6.1-Sol) reaches a mean of 83.4% (83.6 clean, 83.2 randomized), with a 95% Wilson
interval of 81.0 to 85.6. The strongest trained policy, 4D-WAM trained on 50 demonstrations per task, reaches
61.7% (81.5 clean, 41.8 randomized). The two are comparable in the clean setting, yet the mean differs by
21.7 points because trained policies lose most of their success under randomization. These gains come from a
single demonstration and rehearsal in a simulator, without any training data, gradient computation, or access
to the randomized distribution.
What is learned in context holds across distributions. The three foundation models retain 95.2% to
100.8% of their clean success under randomization, whereas trained policies retain at most 65.1%. The Task
Memory stores semantic knowledge that does not depend on visual appearance, so it applies equally to both
settings. Even though the agent rehearses only on clean scenes and never observes any randomized instance,
RoboScript exceeds HarnessVLA (58.4% randomized), which fine-tunes its base policy on RoboTwin data, by
24.8 points. Sec. 5.3 analyzes where the remaining failures come from.
The advantage does not depend on the strongest foundation model. DeepSeek-V4.1-Flash and
GPT-5.6-Luna reach means of 78.1% and 77.9%, both above every trained policy. GPT-6.1-Sol leads them by
5.3 and 5.5 points, and a paired bootstrap over tasks keeps both gaps above zero (95% intervals 0.7 to 10.0
and 0.8 to 10.2). The two weaker models differ by only 0.2 points. All three use the same code, prompts, and
protocol, suggesting that performance scales with model capability. Since the knowledge lives in the context
and not in the weights, any foundation model with sufficient capability can serve as the base. Sec. 5.6 reports
the cost of each model.

6
Conclusion
We have introduced World In-Context Learning (WICL), a paradigm that extends in-context learning with
feedback from a world, and implemented it in RoboScript, a modular infrastructure for agentic manipulation
with strict data isolation. On all 50 tasks of RoboTwin 2.0, the agent builds its own skills, learns each task
from one demonstration and rehearsal in a simulator, and reaches 83.4% mean success across clean and
randomized settings without gradient updates, exceeding every trained action policy. The learned knowledge
is semantic, so it transfers across visual distributions, works with three different foundation models, and
improves through reflection over successive rounds. A lightweight adapter transfers the same memories to a
physical PiPER robot with a different kinematic structure, producing working behavior without re-recording
any demonstration or repeating any rehearsal. These findings suggest that task skill need not reside in network
weights, and that with a world in the loop, a robot can learn a manipulation task in its context as well as it
learns one in its weights.

A
Extended Discussion about WICL
We discuss how WICL relates to established learning paradigms, what distinguishes it from prior work, and
why it has become feasible for physical manipulation.
Relation to Other Learning Paradigms. Skill acquisition differs along two dimensions. The first is the
source of learning, either demonstrations alone or feedback from a world. The second is where the learned
skill is stored, either in network weights or in the context of a frozen model. Imitation learning writes
demonstrations into weights. Reinforcement learning adds a world whose feedback is also written into weights.
In-context learning stores demonstrations in context. WICL adds a world whose feedback is also stored in
context (Fig. 1a). The world provides a feedback signal that demonstrations alone cannot offer, because a
demonstration is recorded in a different scene and cannot tell the learner what will happen in the scene in
front of it. Writing this feedback into context instead of weights avoids the distribution coupling that limits
weight-based methods.
Distinction from In-Context RL and Experiential Learning. In-context reinforcement learning [43, 44]
also improves within the context, but its weights are first trained on learning histories from the target domain,
so the model itself is specialized. WICL uses a general foundation model without such training. Experiential
learning in LLM agents [66, 74, 94] is the closest relative. Some of these methods improve through repeated
trials on the same instance [66], which conflates memorization with generalization. The split between Ereh
and Etest in WICL rules this out and ensures that every reported success measures generalization.
WICL in Physical Manipulation. Applying WICL to physical manipulation introduces requirements that
do not arise in software or text domains. The context must be grounded in camera observations of a scene
that changes as the robot acts. The feedback from the world includes physical outcomes such as whether an
object was grasped, not only textual signals. The context must therefore record task-relevant semantics from
visual observations while remaining independent of the visual appearance of any particular world. In our
implementation, a linter enforces this by rejecting coordinates, ground-truth terms, and instance identifiers.
Feasibility Conditions. Simulators and robot APIs have been available for years [53], but WICL also requires
a model that can use tools over a long context, read feedback, and accumulate experience. The progress of
coding agents on real software repositories shows that foundation models have crossed this threshold [76, 83].
Their terminal is their world, and a simulator can now serve the same role for a robot. The remaining
requirement is a world that is faithful to the task, resettable, and keeps rehearsal apart from evaluation
instances.

Figure 12 Detailed architecture of RoboScript, expanding Fig. 2. The model gateway handles endpoint routing, session
management, and reliability. The core separates an agent plane (agent loop, tool hub, skills) from a control plane
(protocol runner, memory management, verification). Services, operations, and plugins are independently replaceable.

Model gateway. Every model call, whether from the acting agent, a reviewing role, or perception, passes
through one gateway. The gateway exposes a single interface over several provider endpoints. It keeps a
session on the endpoint that served it, moves to another endpoint when one fails, and adapts the number of
concurrent requests to what each endpoint sustains. Changing the foundation model of a run is a change of
configuration, and the same setting applies to every role and to perception.

opens, the hub fixes the tools that each role may see from the stage, the role, and the data tier. Every call
then passes through one ordered pipeline that validates it, checks the budgets and the stage rules, executes it,
and renders the result. Evaluation stages admit tools of the deployable tier only, and the hub refuses any
privileged call made in them, including a call that one tool makes on behalf of another.
Scheduling and reproducibility. For each task, a job graph runs imitation, rehearsal, and deployment in
order. A scheduler places jobs on GPUs according to their measured memory, starts the services of a GPU
when a job first needs them, and resumes interrupted jobs from their records. Infrastructure failures, such
as a lost connection to a model endpoint, are retried and are not counted as task failures. Across machines,
tasks are assigned to workers that run the same code version and configuration, and their results are copied
back and verified with checksums. A run does not start from an unversioned or modified code tree. Every

episode records its code version, configuration, memory version, token usage, and duration, and the event log
of an episode is sufficient to reconstruct everything the model saw.
Extensibility. All major components, including benchmarks, embodiments, perception backends, motion
planners, model clients, and methods, are registered through plugin interfaces with conformance tests. The
method in this paper is one such plugin built on these mechanisms.

Skills and Specifications
Shared and environment-specific skills. Skills are divided by whether they depend on the environment.
Shared entry points cover common operations such as observing, grasping, placing, corrective motions,
reachability checks, arm selection, and coordinated bimanual motion. These entry points hold no convention
of any environment. Environment conventions, including coordinate frames, end-effector-to-fingertip offsets,
gripper normalization, the collision world, and arm names, enter the shared entry points as data through a
binding. An operation that holds only in a particular environment is an environment-specific skill, and it
becomes visible only when that environment is loaded.
Specifications instead of poses. Grasps and placements are described by specifications instead of poses.
A grasp specification names the part to hold and the approach relative to that part. A placement specification
names the target and the offset and orientation relative to it. The frames of these specifications are perceived
objects, their parts, landmarks, or the robot base, and no specification stores the absolute position of an
object. At execution time, the skill solves the specification on the perceived geometry of the current scene,
mirrors it when the other arm acts, and keeps the first solution that the motion planner can reach. The
parameters of the specifications belong to the Task Memory and are learned during rehearsal.
Receipts. Every physical action returns a receipt. The receipt states whether the action succeeded, the pose
that was actually reached, and whether an object is held. It also reports the deviation from the target and a
reason when the action failed. The model therefore learns from what happened, not from what it commanded.
C.2
Skill Building
Coverage of the demonstrations. Skill building starts from the demonstrations of all tasks.
Each
demonstration is cut at its gripper events into segments of seven kinds, namely grasp, place, carry, touch,
release, move, and return home. A segment is explained when an existing entry point or written skill, with
parameters fitted to the demonstration, reproduces it from the state where the segment starts. Each task is
checked in two ways. Every segment is replayed from its own start, and the plan of the whole task is also
rolled out once from the reset, so that each call starts where the previous calls left the scene. Segments that
no entry explains are gaps, and gaps of the same kind and failure class are grouped into clusters.
Written skills. Each cluster is handed to a coding agent that works in a sandbox with fixed budgets of case
runs, wall-clock time, and tokens. A written skill has two parts. The action part runs at the deployable tier,
exactly as the agent runs it in rehearsal and deployment, and it uses only the action API, the object handles
it receives, and its parameters. The fitting part runs only during skill building and may read the recording
and the ground-truth scene. It returns the parameters that reproduce one segment. These parameters hold
no absolute position, since the fit is repeated on the demonstration moved across the table and a parameter
that moves with it by more than 1 cm rejects the fit.
Gate. The driver accepts a skill only through its own checks and never relies on the report of the coding
agent. A static check rejects imports outside an allowed set, task names, object labels, and position literals.
The skill must then explain the gaps it was written for. A transfer check runs its fitted parameters on the
same segment of up to three other demonstrations whose object lies at least 5 cm away, and rejects a skill
that explains none of them, so that a replay cannot pass as a skill. Finally, all sweeps of the round run again
with the accepted skills and the candidates, and a candidate is dropped when its confirmed losses outweigh its
gains. Every process that imports a written skill runs in the sandbox.

Stopping and freezing. Rounds repeat until coverage stops growing, measured by explained segments, task
rollouts that reach the end, official successes of the rolled-out plans, and completed stages. The accepted skills
are then frozen as the skill set of the environment. The task plans that the builder uses to measure coverage
stay in its records and never enter the skill set, a Task Memory, or any input of learning or deployment.
C.3
Perception
Perception separates geometry from semantics. Positions, sizes, and orientations come from the depth images
and the calibrated cameras, and foundation models are asked only which object or part is which. At the
start of an episode, the agent identifies the objects of the task once, and an identity is accepted only when a
majority of independent detectors agree. An ambiguous result is reported to the agent instead of resolved
silently. During the episode, objects are tracked through the grasp relations that the actions record instead of
being detected again, which keeps their identities stable while the arms occlude them. Points that belong to
the robot are removed with its kinematic model.
C.4
Task Learning
Imitation. S1 involves three roles. A demonstration reader studies the recorded demonstration, including its
frames, the motion of the robot, and the key operations extracted from gripper events. It writes the first
version of the Task Memory. An acting role attempts the task on the instance of the demonstration. Some
attempts may consult the demonstration as hints, and the others rely on the memory alone. A reviewing
role reads the record of each attempt and revises the memory. An attempt passes when the official success
check fires and the key operations of the demonstration were carried out in order. S1 ends once the attempts
without hints pass consistently within a window of recent attempts. Tab. 4 lists the values used in all runs.
Rehearsal. S2 runs on new training instances in order, and only the first attempt on each instance counts. If
it fails, the reviewing role edits a cached copy of the memory, and the instance is retried with that copy. The
edits enter the shared memory only if a retry succeeds. The number of edits allowed per revision and the step
size of numerical updates both decrease as rehearsal proceeds, so the memory changes quickly at first and
stabilizes later. Rehearsal stops when enough recent first attempts succeed within a sliding window, or after a
fixed instance budget. If the budget is reached before the early-stopping rule triggers, the version with the
best record of first attempts is frozen.
Task Memory. The Task Memory is a structured Markdown document. Its sections hold the instruction,
the roles of the objects and how to find them, the workflow of each stage with its completion criteria, lessons,
and notes. A separate table holds typed parameters such as grasp and placement specifications. Reviewing
roles change the memory only through typed edits, each with a stated reason, and every version is stored and
hashed. Before a version is committed, a linter rejects simulator names, evaluator terms, instance identifiers,
absolute positions, distances measured from the robot, and fixed assignments of arms. The memory thus stays
semantic and independent of any instance.

C.5
Completion Check
Before the agent may declare a task done, it checks the scene against the final state of the demonstration.
The check uses the completion criteria in the memory and a visual comparison with the final frames of the
demonstration. Only the success check of the simulator credits an episode.
C.6
Information Boundary
Two tiers. Tab. 5 lists the data available to each role. The deployable tier contains RGB-D images from
the head and wrist cameras, camera intrinsics and extrinsics, measured and commanded joint states, gripper
openings, feedback from the motion planner, the step count, and the instruction.
The privileged tier
contains ground-truth object poses, asset annotations and meshes, articulation states, contacts, ground-truth
segmentation, the success check, and expert trajectories.
Enforcement. The boundary is enforced by construction. Agent-side code reaches the simulator only through
an interface that returns deployable data, and only the control plane holds the privileged interface. The
hub derives the tools of each role from its tier and refuses privileged calls in evaluation stages. Deployment
mounts no privileged tool at all, and observations, error messages, and tool outputs are filtered so that no
privileged value passes through them. Automated tests check that every evaluation stage refuses privileged
tools, that a single module alone may access privileged state, and that no text shown to the model in rehearsal
or deployment is tied to a particular task.
Supervision during learning. Privileged data serves only as supervision during learning. Every role in
imitation runs at the privileged tier, since imitation takes place on the instance of the demonstration. In
rehearsal, the reviewing role receives a ground-truth diagnosis of each failure, stated in terms of the objects
and roles of the episode. This supervision reaches the acting agent only through the memory, which must
pass the linter. A privilege-free variant that removes all of this supervision is evaluated in Sec. 5.4.
