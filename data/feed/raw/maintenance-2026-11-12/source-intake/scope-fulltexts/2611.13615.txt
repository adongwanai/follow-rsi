Abstract Large language model agents reuse execution experience to improve reliability on complex tool-based tasks.
Systems such as Sentry call large models to generate failure diagnoses before retrieving advice, adding inference cost to experience reuse.
We present Synapse-Control , an agent runtime whose lightweight control plane selects advice and determines when to send it to the task-executing model.
Rules shortlist relevant advice, and a lightweight 1.7B classifier fine-tuned on teacher-labeled state–suggestion pairs scores those candidates instead of generating a diagnosis.
Micro-contracts encode reusable interface checks, such as required arguments or valid options, without prescribing complete task programs.
A Prompt Value Table records earlier guidance and feedback to limit repeated suggestions through cooldown and token-budget checks.
Across 1,308 attempts per method in AppWorld and WebShop, Synapse-Control achieves 270 successes (29.8% more than Base) , replaces 4,987 generative diagnosis calls , and reduces auxiliary control time relative to Sentry by 50.2% and 51.0% , respectively. 1 Introduction Reusing execution experience helps large language model agents perform complex tool-based tasks without repeatedly reconstructing procedures and interface requirements.
An agent alternates between reasoning, tool actions, and observations; its action-generating model, the actor , supplies arguments, interprets returned state, and determines completion.
Existing systems retain skills, procedural insights, and lessons for subsequent tasks [ 1 , 2 , 3 , 4 ] .
Using this knowledge to correct a failed action or stalled execution is called runtime recovery .
We focus on locally served agents that repeatedly use stable APIs or web interfaces, where both reliability and the cost of experience reuse matter. Deciding when and how to reuse experience can itself require costly model inference.
Sentry examines the recent trajectory, generates a failure diagnosis, retrieves matching lessons, and verifies subsequent execution before publishing new experience [ 4 ] .
Whenever this diagnosis path is triggered, it generates intermediate text before the actor can use an existing lesson.
That work can be disproportionate to the correction needed, such as supplying a required argument.
Retrieved advice can also repeat a completed check or conflict with the current state.
Reducing this overhead requires both cheaper selection and a check that the advice is still useful. Our central insight is a computational asymmetry between generating a diagnosis and judging a supplied suggestion.
Diagnosis generation constructs an explanation through successive token predictions; classification assigns scores to fixed labels for an already retrieved candidate. Synapse-Control exploits this asymmetry by using execution evidence and keyword matches to retrieve at most five suggestions, then learning only their suitability in the current state.
The 1.7B sidecar thus solves a different computational problem from the 9B detector: direct assessment replaces diagnosis generation.
Selection and delivery form the control plane, while the 9B actor retains planning and action generation. Task-specific training makes this decomposition operational.
We fine-tune the complete 1.7B backbone and classification head on target-actor states collected with and without earlier guidance.
A 32B teacher labels the exact suggestion available at each state as useful, unnecessary, or conflicting.
The optimization objective concentrates adaptation on these recurring state–constraint distinctions.
The relevant requirement becomes discrimination at this decision boundary, rather than the breadth of a general response generator. We represent reusable interface checks as micro-contracts : short statements of local constraints and when they apply.
They specify facts such as required arguments or selected options while leaving task values and program composition to the actor.
Rules check for an unmet need and shortlist relevant entries; the classifier assesses the resulting suggestions.
Selected guidance is added to the actor’s next-action prompt, which we call delivery ; the resulting actions and observations remain in its execution history. We use a Prompt Value Table (PVT) to record each suggestion’s delivery history and feedback within a task.
It withholds advice while feedback is pending, evidence is unchanged, or a cooldown is active.
Earlier feedback adjusts the ranking of eligible suggestions; token-budget checks and a single-hint-per-step limit constrain what reaches the actor.
These controls suppress repeated guidance when execution stalls. We evaluate Synapse-Control on AppWorld API programming and WebShop shopping tasks using the same actor and task workload for all primary methods.
Across 1,308 attempts per method, it achieves 270 successes, compared with 256 for Sentry and 208 for Base, with the lowest cumulative task time among these methods.
Auxiliary control time decreases by 50.2% in AppWorld and 51.0% in WebShop.
Controlled studies examine knowledge representation, candidate selection, and delivery history; the history ablation reduces repeated deliveries by approximately two thirds in both benchmarks. Our contributions are: • A decomposition of experience selection into rule-based retrieval and specialized candidate scoring, replacing 9B diagnosis generation with a fine-tuned 1.7B classifier. • A runtime combining micro-contracts, rule-based filtering, and delivery-history and budget management. • A two-benchmark evaluation of task success, benchmark score, and complete execution cost, supported by controlled component studies. 2 Background and Motivation Experience reuse extends an agent’s execution loop with knowledge from earlier interactions; its efficiency depends on both knowledge construction and runtime use.
The main costs arise when the runtime diagnoses a failure, selects advice, and processes the resulting intervention. 2.1 Experience and runtime recovery Execution experience allows an agent to reuse information about tool behavior and earlier outcomes across steps and tasks.
An interactive agent selects an action, executes it in the environment, and incorporates the returned observation into its next decision.
Actions can be API calls expressed as code or operations on a webpage, while observations reveal returned values, invalid arguments, unavailable actions, or a lack of progress.
ReAct and CodeAct illustrate this reasoning–action loop for tools and executable code [ 5 , 6 ] .
Retaining the procedures and checks learned from such interactions can reduce repeated exploration in later executions. Runtime recovery uses corrective guidance to restore valid or productive execution after an error or a stall.
Stored interface checks, conditional instructions, and verified lessons supply this guidance.
For example, an API constraint can identify a missing argument, while a previous recovery lesson can suggest a check after repeated unsuccessful reads.
The agent still generates and executes the next action; the recovery mechanism supplies information for that decision. Experience systems construct reusable knowledge in several forms.
Voyager stores executable skills, ExpeL extracts insights from trajectories, Agent Workflow Memory retains procedures, and ACE maintains an evolving playbook [ 1 , 2 , 3 , 7 ] .
These representations range from complete programs to conditional instructions.
Their common runtime requirement is to connect stored knowledge to the current execution state before using it. Sentry organizes recovery around a diagnosis–guidance–verification lifecycle [ 4 ] .
As shown in Figure 1 , invalid actions enter a hard-repair path that handles execution errors directly; for other failures, a large-model monitor examines the recent trajectory and generates a diagnosis containing retrieval labels and local evidence.
The runtime then retrieves matching playbook entries and constructs guidance for the actor.
A verifier checks the subsequent execution, and verified recovery produces a new reusable lesson.
This design already includes intervention-need checking and an external experience store; the remaining question is the cost and precision of the decisions connecting them. Solid arrows show the guidance path; the dashed arrow publishes verified lessons. 2.2 The cost of diagnosis and verification Sentry makes auxiliary model calls to diagnose failures, verify corrections, and generate lessons.
The actor additionally processes the delivered guidance and may follow a different action sequence, so complete task time captures both control work and the resulting execution.
Separating these quantities identifies which overhead can be reduced by changing the control mechanism. Sentry’s measured control workload is substantial relative to actor inference in both environments (Figure 2 a).
Auxiliary requests consume time equivalent to 21.4% of actor request time in AppWorld and 18.2% in WebShop .
Actor request time averages 47.29 and 47.85 seconds per attempt, with 10.10 and 8.72 auxiliary seconds, respectively.
Generated diagnosis accounts for 5.74 and 5.21 auxiliary seconds; verification and lesson updates account for the remainder.
Normalizing to actor request time exposes the scale of repeated control work within each environment. Repeated diagnosis is a concrete optimization target when relevant knowledge is already available.
A runtime with a small candidate pool needs to assess specific suggestions against visible evidence, yet generative diagnosis first produces an intermediate explanation and retrieval labels.
Assessing the candidate directly can reduce control work while preserving verification and lesson publication. Figure 2: Recovery requires both economical control and effective guidance. (b) In the AppWorld development probe (342 attempts per condition), a larger actor-output cap increases Base completions but does not improve Sentry completions. 2.3 State-dependent suitability of retrieved knowledge Topical relevance and present suitability answer different questions about a retrieved knowledge item. Relevance asks whether the item concerns the same tool, operation, or task topic; suitability asks whether following its concrete advice addresses an unmet need without conflicting with the current state.
Lexical matching and interface identity support the former, whereas the latter requires the visible action, observed values, and checks already completed. Visible execution state can change suitability even when the task topic remains unchanged.
In a shopping task, advice to change an option may match the product vocabulary but be unnecessary after the requested color has already been selected.
A generic instruction to search again can likewise redirect an otherwise ready purchase.
In API programming, an application-name match alone cannot distinguish a missing authentication fact from a pagination or argument constraint.
These cases require evaluating the proposed content against the current evidence, rather than treating retrieval as authorization to intervene. Knowledge granularity and delivery history further determine how retrieved advice affects execution.
A required argument or visible-state check can be represented as a compact fact without prescribing an entire task program.
Such a fact still needs an applicability condition, and previously delivered advice may remain unresolved or redundant.
The runtime must therefore combine content assessment with a separate decision about repeated presentation. Additional actor-generation capacity does not by itself ensure more effective recovery guidance.
In a separate AppWorld development probe (342 attempts per condition), increasing the actor-output cap from 384 to 768 tokens raises Base completions from 30 to 44 , while Sentry completions decrease from 38 to 36 (Figure 2 b; Appendix A ).
This response motivates evaluating guidance at the state and candidate level rather than relying on a larger actor-output budget to resolve control errors.

For each candidate, a forward pass produces three label scores without autoregressively decoding a diagnosis.
At most five candidates and 1,024 tokens per input bound scoring work by configuration rather than knowledge-bank size.
All backbone parameters and the classification head are fine-tuned on the same state–suggestion objective, concentrating adaptation on distinctions needed by the target actor.
On held-out Contract candidates, the specialized scorer achieves 94.0% Helpful admission precision in AppWorld and 98.15% in WebShop; Section 5.4 reports coverage and downstream execution costs. Executable skills and reusable workflows encode an action structure [ 1 , 3 ] ; reusing such procedures requires reconciling their ordering and state assumptions with the current task.
Micro-contracts reduce this coupling by exposing local interface constraints that the actor can satisfy within its own plan.
Argument synthesis, variable bindings, and workflow composition remain with the actor.
The control plane supplies checks at the interface boundary instead of substituting an external program for task planning.
Rules match applicability conditions against execution evidence to shortlist suggestions. Contract contents. History reorders the high-confidence pool; suitability, cooldown, and budget eligibility are checked first, so historical success cannot bypass them. 4 Implementation Each worker colocates the actor and classifier, constructs bounded state inputs, and routes verification and lesson updates through the existing recovery host. Serving and state construction. Each evaluation worker colocates the Qwen3.5-9B actor service and Qwen3-1.7B classifier on one H20 GPU. Tensor parallelism is one; the actor service admits one active sequence and starts with memory utilization 0.65. The implementation replaces a generative request on the control path; it does not require another GPU for each actor. Bounded state construction preserves the information needed for a state–candidate judgment within a fixed classifier input. The controller retains at most five recent execution steps, including bounded observation values and entity samples. It preserves the objective, current action, and complete candidate payload. Older steps are removed first, followed by bounded observation compaction. If the required state and payload do not fit, the candidate is skipped. Four limits govern different resources: 1,024 tokens per classifier input; 2,048 added guidance tokens per task; 768/384 actor-output tokens in AppWorld/WebShop; and a 40,960-token actor-service context. Learning and delivery settings. Domain-specific fine-tuning converts Qwen3-32B teacher judgments into a frozen 1.7B suitability classifier. We train the full backbone and classification head with AdamW, BF16 parameters, and FP32 loss logits. The two domain classifiers are trained independently from the same initial checkpoint, using 456 optimizer updates for AppWorld and 450 for WebShop. The reset three-class checkpoints are selected on development data and frozen before final evaluation. Calibrated Helpful probability must exceed 0.90. PVT uses α = 0.5 \alpha=0.5 , λ = 0.1 \lambda=0.1 , and a three-step cooldown. Deterministic item identifiers break ranking ties. Training splits, hyperparameters, teacher prompts, and realized sampling distributions appear in Appendix A . Offline construction and online reuse. The WebShop adapter supplies the same visible action constraints to every evaluated method using text observations. Search requires a visible search input; clicks require a visible target. The search check supplements the original text interface. A rejected action returns feedback and consumes an actor step. Generic contract families cover option state, empty search, visible actions, evidence checks, and purchase readiness. Before a proposed purchase, visible unmet requirements can trigger the same scoring and PVT path. At termination, pending recovery can be checked against the available shortened continuation. Single-GPU serving colocates both models throughout evaluation. Porting the runtime involves the observation adapter, local interface facts, and controller calibration for the target actor; admission, suitability, and delivery have explicit interfaces.
Appendix F evaluates direct reuse of the frozen controller in a Llama-based runtime without retraining. Separating immutable knowledge assets from task-local state also supports a shared-store layout. A CPU object-layout replay reduces serialized store capacity by 59.3% at six workers by storing immutable assets once while retaining private task metadata (Appendix D ). Versioned files, an object service, or a future CXL-backed store could supply that immutable base. Private trajectories, credentials, and PVT feedback remain local. The layout isolates knowledge ownership and publication from task-local recovery decisions. 6 Related Work We position lightweight experience control relative to agent knowledge representations, recovery mechanisms, and inference optimizations. Our runtime operates before these serving optimizations: it changes which recovery requests are issued and which guidance reaches the actor. 7 Conclusion Synapse-Control reduces the cost of reusing experience by assessing existing suggestions directly instead of generating a diagnosis to retrieve them.
A small classifier evaluates advice against the current state; micro-contracts express interface checks; PVT regulates repeated use through feedback and budgets.
Across the evaluated AppWorld and WebShop workloads, this division improves successful task yield over Base and Sentry while halving auxiliary control time.
Component studies link learned selection to lower execution cost and delivery-history checks to fewer repeated suggestions.
