Implementation 10 Conclusion References License: CC BY-NC-ND 4.0 arXiv:2611.13236v1 [cs.AI] 09 Nov 2026 NCP: Verifier-Guided Optimization of Weight-Space Control Policies Ekrem Aksoy November 5, 2026 Abstract We present the Neural Control Plane (NCP), a closed-loop system that
observes language-model execution, synthesizes candidate weight-space
intervention rules, evaluates them, and maintains a versioned table of
admitted policies. NCP separates a pretrained model’s inference data
plane from the control policy that selects temporary parameter
interventions. W-ISA supplies transactional execution and parameter
restoration; NCP supplies telemetry, candidate synthesis, admission
criteria, priorities, and rule lifetime management. The optimization
state consists of active rules and an archive of evaluated candidates,
while base-model parameters are restored after each request. In a local
SmolLM-135M-Instruct experiment, NCP generated three candidates from
development telemetry and evaluated them on separate task examples and a
4,095-target WikiText-2 slice. One projection reduced validation token
repetition from 0.4133 to 0.2191, with a perplexity change of -0.0574%.
All candidates produced zero newly correct exact answers, so the
configured admission gate archived all three and retained the original
active policy. Fresh-process repetition and saved-table resumption
reproduced the measured outcomes. NCP provides an executable framework
for studying recursive self-improvement at the control-policy level
through explicit synthesis, verification, and state transitions. Keywords: neural control plane; recursive self-improvement;
inference-time optimization; weight-space interventions; model editing;
transactional execution. 1 Introduction Inference-time adaptation can be expressed through changes to prompts,
intermediate activations, auxiliary memory, or model parameters. Each
choice creates a different optimization state and execution lifecycle.
NCP studies the policy that decides which weight-space intervention to
apply to an incoming request. We explicitly credit Rikiya Takehi, Jayden Teoh, Alex Zhang, and Omar
Khattab’s Sparks of Weight-Space Programming: LLMs can natively
read & write neural network weights [11] as a conceptual
foundation. Their November 2, 2026 article presents reasoning-driven
weight inspection and editing, describes a tool-assisted loop-reduction
experiment on Qwen3.5-0.8B, and identifies recursive self-improvement as
a research direction. NCP develops a verifier-guided control-policy
architecture around this weight-space programming perspective, using
W-ISA for scoped execution. The system observes task outcomes and output-token telemetry, extracts
an activation direction associated with development failures, and
constructs explicit match-action candidates. A verifier compares the
current policy with the policy that would result from admitting each
candidate. Accepted rules become part of the active flow table;
evaluation records preserve the outcomes of every trial. Our architectural starting point is the separation of control and data
planes used in software-defined networking. OpenFlow provides a
flow-table interface through which a controller manages
packet-processing behavior [1]. NCP adopts this separation as a
software design: the language model performs tensor computation, the
W-ISA runtime executes parameter interventions, and the controller
selects and evaluates rules. The recursive self-improvement (RSI) research objective is improvement
of this control policy across successive feedback cycles. An admitted
rule changes the behavior observed in later requests, which changes
subsequent telemetry and candidate generation. The implemented loop uses
a deterministic synthesizer and an explicit verifier, making each
proposed policy transition inspectable. The central question is: Can a language-model control policy be improved through repeated
generation, temporary execution, and verification of
activation-conditioned weight-space rules while preserving a stable base
parameter state? The present contribution is an executable architecture for this
question: a versioned neural flow table, deterministic candidate
generation, a routed-task and forced-action admission gate, and a
reproducible local evaluation protocol. 2 Background and Related Work 2.1 Weight-space programming Takehi et al. [11] study general-purpose LLMs reading and writing
weights under natural-language objectives, including experiments with
controlled forward-pass budgets. Their discussion of model correction
and recursive self-improvement motivates the NCP research objective. The
present implementation supplies deterministic candidate templates,
routed task evaluation, forced-action corpus checks, and evidence-bound
policy admission. 2.2 Control-plane separation OpenFlow exposes switch flow tables through an interface for adding and
removing entries [1]. The corresponding NCP objects are activation
predicates, W-ISA action programs, priorities, and rule lifetimes. The
analogy concerns programmatic control and policy management; NCP’s
matching signals are neural activations, and its actions modify selected
parameter tensors within an inference scope. 2.3 Feedback-driven
improvement Self-Refine iteratively revises outputs using model-generated feedback
[2]. Reflexion maintains linguistic feedback in episodic memory to
influence later trials [3]. NCP instead makes a table of executable
intervention rules the persistent optimization state. Its current
synthesis step is a deterministic Python procedure driven by observed
task labels and captured activations. OPRO generates and evaluates candidate solutions using a language model
conditioned on earlier solutions and their scores [12]. DSPy
separates declarative language-model programs from metric-driven
pipeline optimization [13]. These studies, also referenced by Takehi
et al., provide context for separating candidate representation,
proposal generation, and evaluation. NCP applies this separation to a
table of activation-conditioned weight interventions. 2.4 Neural interventions ROME and MEMIT construct parameter updates for factual associations
[4, 5]. Contrastive Activation Addition derives behavioral
directions from activation differences [6]. pyvene provides
configurable intervention schemes [7], while NNsight supports
tracing, persistent intervention definitions, and conditional execution
[8]. These works provide related edit constructions and intervention
infrastructures. NCP builds on the W-ISA execution interface described in the companion
manuscript [9]. W-ISA handles instruction validation, weight writes,
snapshots, synchronization, and restoration. NCP handles the question of
which program to propose, which evidence to collect, and which rule to
admit. 2.5 Repetition and directional
interventions Pipis et al. [14] analyze looping in reasoning models, including its
relationship to decoding temperature and temporally correlated errors.
Their study motivates measuring repetition separately from answer
correctness. NCP records token n-gram repetition, decoding-score
entropy, and exact-answer outcomes as distinct signals. Arditi et
al. [15] provide a related example of studying model behavior
through a residual-stream direction; NCP’s current projection candidates
use development-derived directions in a selected MLP input space. 3 System Model Let f θ f_{\theta} denote a pretrained model with registered base

The implementation assigns score zero to a zero activation. Higher
numeric priority is considered first, and equal-priority rules retain
registration order. The first matching rule is selected. Activations are
measured before the selected parameter intervention is applied. 4.2 Lifecycle and evidence The table records candidate, active, rejected, expired, and retired
states. Promotion requires accepted evidence for the rule’s fingerprint
and the current active-table version. Changes to the active policy
invalidate evidence measured against an earlier version. Accepted rule definitions persist in the table. Their weight effects
remain temporary and are reconstructed during matching requests. The
runtime holds a shared model lock, applies the selected program,
performs generation using a fresh KV cache, and restores the
request-entry weights. Hard timeout is elapsed wall-clock time since promotion. Idle timeout is
elapsed time since promotion or the most recent completed selected
request. Expiration is applied during table inspection for dispatch or
admission; an in-flight request completes under its selected scope.
Persisted timestamps preserve elapsed time across process restart. Token
budgets are separate from these time-based fields. Table snapshots preserve status, order, timestamps, hit counts,
definitions, and evidence. Persistence writes a flushed temporary JSON
file and atomically replaces the destination. 5 Telemetry and Candidate
Synthesis 5.1 Output and task
measurements Each observation records generated text, token IDs, elapsed time,
token-budget completion, and per-step entropy of the decoding-score
distribution: H t = − ∑ j p t , j log p t , j . H_{t}=-\sum_{j}p_{t,j}\log p_{t,j}. Repetition telemetry uses token n-grams. For G G observed n-grams and U U distinct n-grams, the repeated fraction is R = G − U G , R=\frac{G-U}{G}, with R = 0 R=0 when G = 0 G=0 . The implementation also records the first
adjacent repeated-block position and the maximum consecutive repetition
run. The default n-gram size is four. Terminal EOS is removed from the
repetition sequence. Task scoring uses an explicit expected-answer specification. In the
recorded fixture, the requested format ends with Final answer: <number> . The scorer
takes the last answer-pattern capture, or the complete response when the
pattern is absent, and applies case and trailing-period normalization
before exact comparison. 5.2 Activation profiles Development outcomes label prompt-end activations. When both classes are
present, the profile is v error = μ failure − μ success . v_{\mathrm{error}}=\mu_{\mathrm{failure}}-\mu_{\mathrm{success}}. For an all-failure development set, the implementation uses v error = μ failure v_{\mathrm{error}}=\mu_{\mathrm{failure}} and records the source as failure_centroid . Capture and matching use the same activation
site and pooling method. Zero-norm directions produce an empty candidate
set for that site. 5.3 Deterministic action
templates For each configured transformer block and attention head, the initial
synthesizer constructs: Candidate W-ISA action MLP projection Remove the profiled input direction from the block’s
down-projection Head scaling Scale the selected head’s columns in the attention output
projection Combined Execute head scaling followed by the MLP projection The block and head dimensions are read from the loaded model. Candidate
identifiers are deterministically derived from the action and matching
configuration. Compilation checks the generated instruction sequence
against the actual parameters before evaluation. 5.4 Controller-agnostic candidate
representation The NeuralRule representation separates a candidate’s origin
from its execution and evaluation. It holds model identity, an
activation predicate, a W-ISA source program, numeric operands and
lifecycle fields. TorchBackend.compile() binds that source to
the model through the W-ISA compiler. Caller-constructed rules can
therefore use the supported instruction set independently of the
templates in Section 5.3. The public path is FlowTable.submit(rule) , followed by Verifier.evaluate(rule,table,cases,corpus_tokens) ,
and then promotion or rejection using the returned evidence. The
verifier evaluates the proposed policy and the forced action; promotion
checks the accepted flag, fingerprint and active-table version. These
interfaces operate on trusted local rule and evidence data. The
controller’s step() method assembles this path around the
deterministic synthesizer used in the recorded experiment. 6 Verification and Policy

Microbenchmark 7.1 Protocol The recorded run uses HuggingFaceTB/SmolLM-135M-Instruct , revision b5f4b394abe60fe0e4d666139e57bfce520302a9 , with FP32
weights on MPS and CPU FP64 intervention arithmetic. The runtime is
PyTorch 2.15.0 with Python 3.12.9. Generation is greedy with a 128-token
budget. The nine-question handwritten fixture is an architectural microbenchmark
of telemetry, candidate generation, admission and persistence. It
contains three development, three validation, and three final-test
questions with disjoint IDs and prompts. Development questions cover
addition, sequence continuation, and counting grouped objects.
Validation and final-test questions use separate arithmetic scenarios.
Final-test inference begins after candidate selection finishes. The language-modeling corpus is the cached WikiText-2 raw test split
[10]. Its tokenized stream is partitioned into two disjoint
4,096-token slices. The first supplies the verifier corpus and the
second supplies final corpus evaluation. Each slice scores 4,095 targets
once, with context length 512 and stride 256. These are explicitly
bounded corpus slices. 7.2 Generated candidates Development exact-answer scoring was 0/3. Synthesis therefore used the
failure centroid at the last prompt token’s input to model.layers.9.mlp.down_proj . This direction has
1,536 dimensions and norm 3.6363433948. The three candidates target the tenth transformer block: an MLP
projection, scaling query head 0’s output contribution by zero, and
their ordered combination. The cosine threshold is 0.8. Each candidate
was selected on all three validation prompts. 7.3 Task and corpus results Baseline validation repetition fraction was 0.41333333. Baseline

coverage The initial end-to-end run took 44.38 seconds. A new-process two-cycle

all 4,095 target counts and aggregate perplexity values. Direct

records. The NCP suite contains 25 passing tests. Controlled fixtures exercise
both promotion and rejection through actual W-ISA parameter writes.

to the archive. The controlled promotion fixtures exercise the
complementary active-table transition. 8 Control-Policy Optimization The optimization state has two parts with distinct effects. The active
table changes inference routing, while the archive records search
history. In the measured cycle the archive grew by three candidates and
the active table stayed empty. On the next cycle, deterministic
candidate identifiers retrieved the existing decisions. Saved-table
resumption retained the same search state across process boundaries. The verifier separates task progress from repetition and corpus cost. In
the projection trial, repetition decreased by 0.19427160 and the
forced-action corpus score satisfied the configured budget. The
corrected-answer count remained zero, so the rule was archived under the
one-correction admission criterion. This decision illustrates how the
configured objective determines a policy transition rather than treating
every change in an auxiliary signal as an improvement. Proposal construction and acceptance remain separate operations. The
representation in Section 5.4 carries a program regardless of its
producer, while the verifier binds evidence to the exact candidate and
current policy. Once a rule is active, priority matching and expiry
determine its execution lifetime; the W-ISA scope determines the
lifetime of its parameter effects. The companion W-ISA study [9] measures this execution layer on
SmolLM-135M and Qwen2.5-1.5B, including a 45-request comparison between
materialized rank-one updates and equivalent PyTorch hooks. NCP’s
microbenchmark measures the controller lifecycle on SmolLM. The shared
abstraction is an explicit intervention program whose temporary weight
effects are restored before the next policy evaluation. 9 Reproducibility and
Implementation The implementation contains the schema, flow table, telemetry, local
backend, candidate synthesizer, verifier, and controller. It reuses
W-ISA’s instruction compiler and request-scoped runtime. Public APIs
include NeuralControlPlane , NeuralRule , FlowTable , TorchBackend , TaskCase , GatePolicy , and Verifier . Rule tables are trusted local control data. Model identity, rule
fingerprints, active-table versions, corpus-token hashes, and task
fixtures are retained in the reports. Persistence uses a flushed
temporary file followed by atomic replacement. Runtime scopes own
parameter restoration; table promotion persists policy definitions. Separate records retain the initial run, fresh-process repeat and
saved-table resumption. The reasoning fixture defines expected answers
and disjoint task splits; the tests exercise scoring and lifecycle
transitions. The companion W-ISA manuscript [9] describes the
execution substrate separately. The experiment runner exposes options for the device, task fixture,
corpus, candidate layers and heads, thresholds, timeouts, token budgets,
and output location. Section 7 specifies the settings used for the
recorded microbenchmark. Code uses the MIT License, copyright 2026 Ekrem Aksoy. Model and corpus
materials retain their upstream attribution and license terms. 10 Conclusion NCP makes a language model’s intervention policy an explicit
optimization state. Telemetry generates candidates; W-ISA executes them
within owned scopes; a verifier evaluates routed task effects and
forced-action corpus effects; and a versioned flow table records
admission decisions. The initial local experiment produced three
reproducible candidate evaluations, retained the configured correctness
criterion, and restored the base model after every trial. This
architecture provides a concrete basis for studying recursive
self-improvement through successive, evidence-bound changes to neural
