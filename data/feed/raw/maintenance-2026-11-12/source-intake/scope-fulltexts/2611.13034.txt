strategies from execution feedback, yet a fixed practice source leaves the
search for new weaknesses unchanged. Useful practice depends on the agent’s
current capabilities, so the procedure that chooses practice must also be
revisable. We present RoboACE (Robot Adversarial Co-Evolution), a framework

responds with reusable revisions that expand execution capabilities. Alternating updates hold one

RoboRSI refines reusable skills, Zetta develops critics and recovery skills,
and DynaHarness revises interfaces between semantic decisions and physical
execution [ 33 , 5 , 3 ] .
Together with RAX, which turns exploration feedback into reusable programs,
these systems make execution procedures revisable [ 11 ] .
An equally important choice is what the agent practices next, because a
fixed source leaves unprobed weaknesses outside the feedback driving
revision. Improving execution alone leaves this choice unchanged. Useful practice changes as an agent’s capabilities develop. A drawer skill
that succeeds alone can still fail when composed with object placement,
so practice must probe the composition as well as its individual steps.
Selecting such practice requires interpreting prior outcomes, identifying
prerequisites, and retaining conditions that reveal regressions. Automatic
curricula already connect practice selection with skill accumulation [ 28 ] , but the selection procedure itself must also
adapt as failures are resolved and new interactions emerge. Earlier rules
for finding informative challenges can then become inadequate. This motivates a
robot self-improvement loop that revises how it chooses practice alongside
how it executes tasks. We introduce RoboACE (Robot Adversarial Co-Evolution), in which a
curriculum harness and an execution harness evolve through an adversarial
interaction (Figure 1 ). A harness contains the
prompts, skills, tools, interfaces, and agent-readable memory that organize
behavior around frozen foundation models. The curriculum side uses prior
capability evidence to expose weaknesses in the current execution
harness. The execution side responds with reusable revisions that expand execution capabilities, and
its changing capabilities redirect the curriculum’s search. Independent
agents make runtime decisions on each side, while external optimizers
use the resulting evidence to install revisions for future runs. Adversarial challenge generation requires a stable reference for judging
progress, so RoboACE alternates the two updates. With execution
fixed, the curriculum side revises its procedures and proposes practice;
admission checks validity and consistency before fixing a comparison
snapshot. The execution side then evaluates candidate revisions on that
snapshot, and consolidated outcomes inform the next curriculum update.
This order separates challenge selection from the response it elicits,
while an infrequently invoked Strategic Advisor reviews longer histories
to reconsider repetitive or stalled revision directions. RoboACE brings together software self-improvement and evolving
curricula through persistent revisions to both harnesses. RPG constructs
practice from offline data and refines execution on the resulting fixed
task set [ 32 ] ; our curriculum side also revises the procedures
that select and construct subsequent practice. POET evolves environments
together with their solutions [ 30 , 31 ] ;
our implementation instead adapts the software that organizes challenge
production and robot execution around frozen models. The changing task
library is an output of curriculum-harness evolution, alongside the
execution revisions it prompts. We instantiate this loop in simulated manipulation, beginning with a compact
set of LIBERO practice conditions and evaluating frozen deployments on
LIBERO, LIBERO-Plus, LIBERO-PRO, and LIBERO-X. The final deployment outperforms
the evaluated systems on all four panels (Table 2 ).
On LIBERO-PRO, it improves over the initial deployment by 15.0 percentage
points and over direct execution by the same VLA controller by 13.5 points.
Case studies show how evidence-reading guidance changes independent
practice selection and how execution revisions clarify skill grounding
and controller handoffs. Together, the framework and empirical study
establish a concrete implementation of robot self-improvement in which
both the practice-selection procedure and the execution software remain
open to revision. 2 Related Work Embodied agents around foundation models. Agent software connects foundation-model reasoning to physical control.
Code as Policies expresses closed-loop robot behavior as language-model
programs [ 16 ] , while CaP-X evaluates robot coding agents
and the use of execution feedback for skill synthesis [ 9 ] . RPent augments a controller with prompt-based experience [ 34 ] , and VoLo combines subgoal decomposition, VLM
monitoring, and grasp replanning around a VLA controller [ 2 ] . Related systems also organize closed-loop control
through execution-aware agent harnesses [ 6 , 18 ] .
Our focus is the revision of such harnesses across rounds, together with
the procedures that determine which challenges those rounds contain. Embodied self-improvement. Execution feedback can support persistent changes to robot software.
RoboRSI structures reusable skill improvement and provides the execution
infrastructure used in our implementation [ 33 ] .
Zetta develops runtime critics and recovery skills around a frozen policy [ 5 ] , and DynaHarness uses contracts and failure-driven
revisions to connect semantic decisions with execution [ 3 ] . RAX and ASPIRE convert exploration into
programs and skills [ 11 , 20 ] ; EmbodiedEvo distills
physical feedback into code skills and diagnostic lessons [ 15 ] . RPG generates simulated practice from offline
data before refining prompts and skills on that task set [ 32 ] , while EmbodiedRSI selects experiments to distinguish
hypotheses about code and skill changes [ 27 ] .
RoboACE extends the object of revision to the curriculum harness that
uses execution evidence to select and construct future practice. Curriculum and challenge evolution. Changing challenges can guide learning toward abilities that a fixed task
source overlooks. Voyager connects automatic curricula with skill
accumulation [ 28 ] , and Eureka generates reward functions
for robot training [ 21 ] . POET jointly develops environments
and solutions [ 30 , 31 ] , PAIRED uses regret
to guide environment design [ 4 ] , and asymmetric
self-play builds robotic curricula through proposer and solver roles [ 23 ] . Eurekaverse generates environment programs [ 17 ] ; OMNI-EPIC produces tasks and rewards in
response to learning progress [ 7 ] ; GenEnv co-evolves
agent and environment policies [ 10 ] . In RoboACE, both
the challenge-selection procedures and the execution procedures receive
persistent software revisions while foundation-model weights remain fixed. Pretrained robot control. Generalist controllers supply action priors learned from large robot
datasets. OpenVLA and π 0.5 \pi_{0.5} illustrate this approach [ 13 , 1 ] , while OpenVLA-OFT improves the
fine-tuning and inference recipe and π 0 \pi_{0} -FAST studies efficient action
tokenization [ 12 , 24 ] . Harness adaptation changes
how an agent invokes such controllers, combines them with other tools,
and responds to feedback. We use π 0.5 \pi_{0.5} as the frozen controller
throughout development and revise the software around it. 3 Adversarial Co-Evolution of Robot Harnesses Figure 2 : Alternating revisions connect challenge production and execution. The curriculum side uses prior capability evidence to probe a fixed
execution deployment. Admitted conditions form a fixed snapshot for
comparing execution revisions, whose outcomes inform the next round.
Independent agents run the harnesses, external optimizers revise them,
and the Strategic Advisor periodically reviews the longer history. 3.1 Framework Overview RoboACE takes prior capability evidence and the current pair of harnesses
as input and returns revised harnesses together with evidence for the next
round. The curriculum harness guides practice selection and construction;
the execution harness organizes planning, code skills, and pretrained
control. Each contains reusable prompts, skills, tools, interfaces, and
agent-readable memory. All foundation-model weights remain frozen.
Figure 2 shows how the two sides exchange evidence while
updating in alternating phases. Each side separates runtime decisions from persistent revision. An
independent agent runs its harness to propose practice or attempt
a task. An external optimizer examines the resulting evidence,
proposes changes, and tests them through further independent runs.
We call the accepted harness version Stable and a proposed revision Candidate . A phase can retain its incoming Stable version, and its
revision history records the tests and the reasons for adoption or rejection.
The Strategic Advisor can review evidence across multiple local updates
without taking over these decisions. In round k k , the curriculum side receives the prior Capability Profile P k P_{k} and a fixed execution deployment. Its admitted proposals and the
internal benchmark form a fixed task snapshot 𝒯 k \mathcal{T}_{k} . The execution
side first measures its incoming deployment on this snapshot, then tests
revisions and selects a deployment. Consolidated execution evidence yields P k + 1 P_{k+1} . This ordering separates the curriculum’s prediction of useful
practice from the difficulty and response measured afterward.
Appendix A specifies the operational protocol. 3.2 Phase 1: Evolving the Curriculum Harness The curriculum must choose conditions that reveal actionable gaps in the
current execution capability. Its agent reads P k P_{k} , which summarizes
demonstrated abilities, applicable lessons, unresolved gaps, and uncertainty.
Using this profile, task statistics, and descriptions of available tasks
or assets, the agent retains, replaces, or adds practice conditions.
Selection balances new challenges with prerequisites and familiar
conditions that can expose regressions; increasing difficulty alone is
not the objective. The curriculum optimizer revises how the agent makes these choices.
It tests whether a candidate harness supports better use of evidence,
maintains coverage, and recovers from failed retrieval or construction.
The revised assets persist across future curriculum-agent runs, whose
practice choices remain independent. Section 4.4 illustrates
this distinction through a revision to evidence-reading guidance and the
retrieval interface. Admission and handoff. A challenge must qualify before it replaces an existing condition.
Native tasks retain their source definitions and initializations.
For constructed worlds, admission checks physical validity and reachability,
then a Judge checks agreement among the instruction, goal, and scene.
Failed or inconclusive checks return the proposal for revision.
These checks use no fresh VLA rollouts to pre-screen difficulty and do
not certify a complete executable solution. A separate Benchmark Curator
maintains reference coverage and core anchors. At handoff, the curriculum
deployment is fixed, and admitted practice and internal benchmark
conditions form 𝒯 k \mathcal{T}_{k} . Task definitions and initializations
remain fixed throughout the execution phase.
Appendix A.2 details the checks. 3.3 Phase 2: Evolving the Execution Harness The execution phase turns the admitted challenges into evidence for
reusable changes. The execution agent first attempts 𝒯 k \mathcal{T}_{k} with
the incoming Stable harness. It chooses among code skills and VLA control,
which can address a whole task or a shorter language goal.
The environment’s native predicate determines task completion, so a
successful local operation, such as grasping an object, can still leave
the overall task unfinished. The execution optimizer diagnoses failures from outcomes, trajectories,
public observations, and tool feedback. Diagnosis distinguishes failures
of a skill from misleading skill descriptions or inappropriate tool choices,
because these require different revisions. Candidate changes are tested
through independent agent runs with task definitions, initializations,
model settings, and budgets held fixed. Conditions shared by practice and
the internal benchmark use the same execution record.
Targeted runs diagnose individual mechanisms, while comparisons across
the full snapshot inform adoption. The optimizer considers successes,
regressions, reuse, and cost before installing Candidate or retaining Stable. 3.4 Closing the Loop with Execution Evidence Execution outcomes must inform future practice without exposing evidence
reserved for other roles. The Experience Consolidator converts permitted
task-level results and lessons into P k + 1 P_{k+1} . The curriculum receives
this profile and task statistics, through which unresolved gaps can prompt
new challenges and resolved gaps can redirect practice. Raw images,
trajectories, model and tool calls, and implementation differences remain
on the execution side. Geometry reserved for the Judge remains outside
the execution agent’s observations. A diagnosis becomes useful to future agents only when it reaches a
deployable prompt, skill description, or retrievable manual. The optimizer
checks whether the agent actually receives and uses the revised material.
Persistent assets are versioned with each deployment and kept separate
from episode workspaces. Appendix A.3 describes this interface.
Final evaluation remains outside the loop and does not inform curriculum
choices or version selection. 3.5 Long-Horizon Strategic Guidance Local revisions can repeatedly address nearby failures while leaving the
broader direction of improvement unexamined. The Strategic Advisor offers
an infrequent, on-demand review across multiple updates. It reads the
requesting optimizer’s permitted evidence and revision history to identify
recurring failures, stalled revision patterns, and gaps in coverage.
Its output proposes directions for investigation rather than installing
harness changes. The local optimizer translates this advice into experiments, evaluates
the evidence, and decides which revisions to adopt. Recommendations about
the inactive side wait for that side’s next update phase. This separation
allows a longer view of the campaign while preserving the alternating
comparison protocol and local responsibility for adoption. 4 Empirical Study We evaluate whether the final frozen deployment improves over its initial
version and alternative controllers or agent systems. We then examine
recorded revisions to identify how the curriculum and execution harnesses
changed during development. 4.1 Development and Evaluation Scope We instantiated RoboACE with GPT-6.1 (Terra) and pretrained tools including
SAM 3 and π 0.5 \pi_{0.5} control [ 1 ] . The campaign
maintained 30 practice conditions and an internal benchmark of up to
40 conditions, with 27 saved round records. Both harnesses received
persistent software revisions; no LLM or VLA weights were trained or
fine-tuned by this project. Development remained within the LIBERO ecosystem. The evolving practice
libraries included 76 distinct native LIBERO conditions across rounds,
together with constructed worlds that passed admission. Evaluation tests
transfer both to reserved LIBERO conditions and to LIBERO-Plus,
LIBERO-PRO, and LIBERO-X. Development uses only LIBERO conditions. The held-out LIBERO panel is condition-disjoint from the audited development history, while LIBERO-Plus, LIBERO-PRO, and LIBERO-X are not used during development. The record illustrates how longer-horizon review can connect recurring
local failures to a common question about control selection. 5 Conclusion We presented RoboACE, a robot self-improvement framework that revises
both the selection of practice and the software used to execute it.
A curriculum harness proposes challenges from prior capability evidence,
and an execution harness responds with persistent revisions around
frozen foundation models. Alternating phases connect the two through
admitted tasks, fixed comparison snapshots, and consolidated feedback. The final deployment achieves the highest success rate among the evaluated
systems on four LIBERO-family panels, with gains of up to 35.5 percentage
points over the initial deployment. Recorded cases show changes to
practice selection, skill grounding, and controller intervention.
These results support adversarial harness co-evolution as a concrete
approach to joint curriculum and execution revision. Establishing its
behavior across independent campaigns, broader environments, and physical
robots is the next empirical step. References [1] Kevin Black, Noah Brown, James Darpinian, Karan Dhabalia, Danny Driess, Adnan

material. An optimizer journal can contain a useful diagnosis without
making it accessible to future agents; deployment requires incorporating
it into an exposed description, prompt, or retrievable manual.
