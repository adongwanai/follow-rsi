Large Language Model (LLM) agents can follow an SOP written in natural language, but they call an LLM to choose every step of every run, which adds latency and cost at scale. We present ReTrace , which turns an SOP and a few logged agent runs into a reusable workflow in which code, not an LLM, selects the next step. The agent’s reasoning, the explanation it writes with each tool call, often states why it took an action; the tool calls alone do not. ReTrace extracts the condition behind each step, merges these conditions across runs into a compact rule document, and generates an executable workflow from it. Only this last stage depends on the platform, so rule documents can be compiled for different orchestration platforms. On 79 79 procedures from our production platform, ReTrace workflows reach 93.8 % 93.8\% completion, against 96.8 % 96.8\% for the agent, at 24 % 24\% lower cost per task. On τ 2 \tau^{2} -bench , they reach 75.8 % 75.8\% task success (agent: 80.6 % 80.6\% ) and run in 1.3 1.3 s instead of 170 170 s; three rounds of repair on training failures lift k = 2 k{=}2 workflows from 66.7 % 66.7\% to 81.2 % 81.2\% . On eight SOP-Bench procedures, ReTrace without repair trails few-shot generation ( 80.6 % 80.6\% vs. 83.6 % 83.6\% ), but repair from labeled training failures lifts it to 87.8 % 87.8\% at 0.40 0.40 s per task, compared to 85.5 % 85.5\% in 46.6 46.6 s for the agent. 1 Introduction Many business processes run thousands of times on different inputs: a support case is triaged, a form is checked, an order is escalated. Automating such a process has traditionally meant building a workflow by hand, wiring tools, inputs, and branches in code or in a workflow editor ( Object Management Group, 2011 ; van der Aalst et al., 2018 ) . Large Language Model (LLM) agents remove most of this effort. A process owner writes a Standard Operating Procedure (SOP) in natural language, and the agent reads it and calls the available tools ( Yao et al., 2023 ; Li et al., 2025 ; Nandi et al., 2026 ; Wang et al., 2026 ) . The price is paid at run time: the agent calls an LLM to plan, route, and transform data at every step of every execution, which is slow and expensive at high volume. Figure 1 : From agent runs to executable workflows. The agent, and methods that reuse its past runs as examples or memory, call an LLM to choose each step. ReTrace turns the agent’s reasoning and tool calls into rules before deployment; at run time, code selects the next step. These costs are visible in production. Of the 5,115 5{,}115 automations that customers created on our enterprise business process automation platform between April and June 2026, 91.8 % 91.8\% were agents that plan at run time, yet seven of the ten most frequently executed automations were fixed workflows. For agents using three to five tools, choosing the next step took 37 37 – 43 % 43\% of execution time, on top of the token cost. For a procedure that runs often, building a workflow once pays off: from the measured savings and a τ 2 \tau^{2} -bench construction cost, we estimate that construction is recovered after about 75 75 executions, while each of those seven workflows ran 297 297 k– 528 528 k times in three months (Appendix L ). Logged agent runs, or traces , show how a procedure is carried out, and prior work reuses them as written guidance, skills, or code ( Wang et al., 2023 ; Wang et al., 2025b ; Zhao et al., 2024 ; Wang and Lu, 2026 ; Li et al., 2026 ) . Replacing the agent with a workflow, however, requires knowing when each tool should be called and where each of its inputs comes from. Tool calls alone often do not say. If an agent looks up an order and then escalates to a human, the trace does not show whether the shipping status caused the escalation. The agent’s reasoning often does, and it can also mention alternatives that no logged run took. Giving a model more raw traces is not enough: with many long traces, the workflow generator eventually writes worse code (Section 5.1 ). We present ReTrace , which builds a reusable workflow from an SOP and agent traces that include reasoning (Figure 1 ). It extracts the condition, tool, and input sources behind each step, merges them across traces into a compact rule document that links every rule to its evidence, and generates an executable workflow from that document. LLMs are used only in this one-time construction; at run time, code selects the next step, though a tool may still call a model, for example to classify a document. Our contributions are: • Rules from agent reasoning. We combine the agent’s reasoning with its tool records to recover action conditions, input sources, and alternatives that no logged run executed. • One rule document, several platforms. Only the final stage depends on the target, so the same pipeline yields Python code for two public benchmarks and typed workflow graphs for our production platform. • Evidence from production and two public benchmarks. On 79 79 production procedures and on τ 2 \tau^{2} -bench , ReTrace workflows come within 3 3 and 5 5 points of the agent, respectively, while cutting enterprise cost per task by 24 % 24\% and τ 2 \tau^{2} -bench time per task from 170 170 s to 1.3 1.3 s. Removing the agent’s reasoning costs 8.8 8.8 and 6.2 6.2 points, respectively, and gains 1.7 1.7 on SOP-Bench. Repaired workflows reach 81.2 % 81.2\% on τ 2 \tau^{2} -bench (agent: 80.6 % 80.6\% , n.s.) and 87.8 % 87.8\% on SOP-Bench (agent: 85.5 % 85.5\% ), where unrepaired ReTrace trails few-shot. 2 Related Work Reusing agent experience. Agent Workflow Memory (AWM) stores workflow descriptions as written guidance for an agent, while ExpeL and ReasoningBank store lessons and strategies ( Wang et al., 2025b ; Zhao et al., 2024 ; Ouyang et al., 2026 ) . Voyager, ASI, SKILL-DISCO, and NSI instead produce reusable code, or skills, that an LLM agent selects and calls at run time ( Wang et al., 2023 ; Wang et al., 2025a ; Guo et al., 2026 ; Shao et al., 2026 ) . Skill Factory builds skills from successful runs, but a model still picks a skill and fills its inputs for each task ( Wang and Lu, 2026 ) ; BPOP learns only which actions must precede others ( Li et al., 2026 ) . In all of these but BPOP, a model keeps choosing steps; ReTrace compiles conditions and input sources into a workflow that does not need one. SOP benchmarks test whether an agent follows a written procedure at run time ( Li et al., 2025 ; Nandi et al., 2026 ; Wang et al., 2026 ) ; ReTrace instead compiles the procedure once, so no agent has to follow it on each run. Compiling executable workflows. TraceCompiler tracks how tool outputs feed later inputs and builds mostly deterministic workflows that may still call an LLM to fill some inputs; on AppWorld, it escalates when a required branch never appeared in the logged runs ( El Yadouni and Li, 2026 ) . Trace2Policy reconstructs experts’ decision rules from behavior records with a Vision-Language Model (VLM) and revises them on validation errors; its deployed version is human-refined Python that runs without an LLM ( Zha et al., 2026 ) . Concurrent work on τ 2 \tau^{2} -bench keeps a model in the loop at run time: PLVR guides or checks a small model that still generates actions, and STAGE runs model-backed judgment nodes inside a code-controlled graph ( Bhat et al., 2026 ; Luo et al., 2026 ) . ReTrace differs in its evidence: it reads the conditions and alternatives stated in the agent’s own reasoning, which can cover branches that no logged run took. Workflow search and optimization methods tune agent designs, prompts, or LLM-calling steps ( Zhang et al., 2025 ; Hu et al., 2025 ; Zhuge et al., 2024 ; Zhou et al., 2024 ; Khattab et al., 2024 ; Yuksekgonul et al., 2025 ; Cheng et al., 2024 ) ; we instead recover workflow rules from an SOP and logged runs. We use k k traces 𝒯 k = { τ ( 1 ) , … , τ ( k ) } \mathcal{T}_{k}=\{\tau^{(1)},\dots,\tau^{(k)}\} of an agent on such inputs. A trace τ = ( s 1 , … , s L ) \tau=(s_{1},\dots,s_{L}) records each of its L L steps as s t = ( r t , a t , v t , o t ) s_{t}=(r_{t},a_{t},v_{t},o_{t}) , where r t r_{t} is the agent’s reasoning for the step, a t a_{t} the tool called, v t v_{t} its inputs, and o t o_{t} the result. The output is an executable workflow π \pi , built once per procedure and reused on new inputs. At run time, code chooses the next step without calling an LLM; this is what we mean by planner-free . Individual tools may still call models. The workflow is Python code on the public benchmarks and a typed graph of steps on Internal , our enterprise dataset. 3.2 Building the workflow Construction has three stages: extraction reads each step, aggregation merges evidence across traces into an Intermediate Representation (IR) ℐ \mathcal{I} (a compact rule document); synthesis generates the workflow from it. Algorithm 1 in Appendix B gives the full procedure. Extraction: reading each step. For each step, an LLM extracts a record z t = ( g t , α t , a t , v t , ω t ) z_{t}=(g_{t},\alpha_{t},a_{t},v_{t},\omega_{t}) . The reasoning supplies the condition g t g_{t} under which the action applies and the intended action α t \alpha_{t} . The condition may use only information available before the action: “airplane mode is on” can justify turning it off, but the result of turning it off cannot. The tool record supplies the tool a t a_{t} , its typed inputs v t v_{t} , and the source ω t \omega_{t} of each input, such as a task input, an earlier result, or a constant; unknown sources are marked as such. Case-specific values, such as a customer ID, become variables filled from each new task. The record also keeps alternative actions that the reasoning mentions but the agent did not take. Aggregation: combining traces into rules. An LLM first summarizes each trace against the SOP, matching its steps to the procedure and noting alternatives that were mentioned but not executed. A merge step then combines the summaries: it unifies repeated steps, works out how earlier results feed later inputs, checks the reasoning against the recorded calls and outcomes, and resolves disagreements using the SOP, giving a reason for anything it drops. The result is a completion check and an ordered list of rules: ℐ = ( χ , ⟨ ( g 1 , α 1 ) , … , ( g m , α m ) ⟩ ) . \mathcal{I}=\big(\chi,\langle(g_{1},\alpha_{1}),\dots,(g_{m},\alpha_{m})\rangle\big). (1) Here χ \chi tests whether the task is complete, and rule j j pairs a condition, or guard , g j g_{j} with an action α j \alpha_{j} , its tool, and its input sources. The rules form a decision list ( Rivest, 1987 ) . Each rule cites the trace steps or SOP statements that support it, and alternatives that no trace executed are marked unwitnessed ; for example, the reasoning for turning off airplane mode may also name disabled mobile data as a cause, which becomes an unwitnessed rule (Appendix I ). A final check uses rule names and citations to confirm that no rule or named alternative was dropped silently; it does not judge whether a condition is right. Beyond eight traces, the rest are added one at a time (Appendix D ). The workflow generator reads the IR, not the raw traces; on τ 2 \tau^{2} -bench at k = 16 k{=}16 , its input is 24.5 24.5 k tokens, against 101.4 101.4 k with full traces (Table 9 in Appendix I ). Synthesis: generating and checking the workflow. An LLM converts the IR into code or the platform’s workflow format. Let h h be the state of a run: the task input plus every tool call and result so far. At each step, the workflow stops if the completion check succeeds; otherwise, it runs the first rule whose guard holds: π ⁡ ( h ) = { stop if ​ χ ​ ( h ) , α j ⋆ ​ ( h ) ​ ( h ) otherwise , \pi(h)=\begin{cases}\texttt{stop}&\text{if }\ \chi(h),\\[2.0pt]
\alpha_{j^{\star}(h)}(h)&\text{otherwise},\end{cases} (2) where j ⋆ ​ ( h ) = min ⁡ { j : g j ​ ( h ) ​ holds } j^{\star}(h)=\min\{j:g_{j}(h)\text{ holds}\} . The action calls its tool with inputs taken from h h or constants, and the result updates h h . If the completion check fails and no rule applies, the workflow stops as incomplete and never asks an LLM for a step. Before deployment, generated code must load and must not be able to make planning calls. On the public benchmarks, candidates may import only approved libraries and run in a sandbox; we reject any candidate that makes a planning call when re-executed on the training inputs and keep the one that reproduces the most recorded steps. On Internal , the platform builds a single workflow graph, which must contain no node that asks a model for the next step. Neither check establishes task correctness (Appendix D ). Where the benchmark can be re-executed offline, the workflow can also be repaired from its failures on training inputs: an LLM revises the code, and the IR is left unchanged (Appendix C ). 4 Experimental Setup 4.1 Benchmarks and traces τ 2 \tau^{2} -bench . This public customer-support benchmark provides tools that act on a simulated environment ( Barres et al., 2025 ) . We use the telecom domain’s official split of 74 74 training and 40 40 test inputs across three task families (MMS, mobile data, and service issues) in solo mode , without a simulated user (Appendix A ). We collect eight agent runs per training input. Unless noted, traces come from Sonnet 4.6 with native thinking, which returns its reasoning alongside tool calls. Construction uses only successful traces and Sonnet 4.6 in all three stages. Five-fold cross-validation on the training inputs selects configurations, including k k ; the main comparisons use k = 4 k{=}4 . Test inputs are never used for trace generation, configuration selection, or candidate checks. SOP-Bench. This public benchmark pairs industrial SOPs with tools and labeled task inputs ( Nandi et al., 2026 ) . We admit 8 8 of its 14 14 domains (Appendix A explains the exclusions). The 8 8 procedures use 3 3 – 10 10 tools and SOPs of 4 4 – 12 12 k characters, and each asks for a decision such as escalating or resolving a case. SOP-Bench has no official split, so we split each procedure in half, stratified by label, into 758 758 training and 744 744 test inputs. Traces come from eight runs of Sonnet 4.6, as a two-pass ReAct agent, on each training input. We develop with five-fold cross-validation on the training inputs: in each fold, a method that uses traces draws three samples of k k successful traces from the other four folds, builds one workflow per sample with Sonnet 4.6, and is scored on the held-out fold, for k ∈ { 1 , 2 , 4 , 8 , 16 } k\in\{1,2,4,8,16\} . Table 1 uses k = 16 k{=}16 , the best k k in cross-validation (or within 0.1 0.1 points of it) for every method. For the test, we regenerate the workflows at the k k selected in cross-validation, from a new set of agent runs on the training inputs, and run them on the 744 744 test inputs; the agent runs three times on each test input. Intervals resample test inputs within each procedure and do not reflect variation across the trace samples used to generate the workflows. Internal . This proprietary dataset contains 79 79 production procedures, sampled by customer usage from our platform (Section 1 ). They use 23 23 tool types and range from three-step extractions to multi-tool reviews with conditional steps. Each procedure has 20 20 construction inputs and up to 20 20 disjoint test inputs. We split procedures into Low, Med, and High complexity using only the procedure text and input/output definitions (Appendix A ). Traces come from the platform’s two-pass ReAct agent (Sonnet 4.0), which explains each step before calling a tool. Every method uses the same k = 3 k{=}3 traces per procedure and generates one workflow. For ReTrace , extraction and aggregation use Opus 4.8, and the platform generates the final workflow graph with a model of its choice. 4.2 Compared methods All methods receive the procedure and tool definitions. The original agent , which produced the traces, is the reference for task outcomes and execution costs. Zero-shot gets only these, few-shot also gets k k full traces, and execution-only gets the same traces with the reasoning removed; all three use ReTrace ’s generation prompt but, unlike ReTrace , keep their first valid workflow. Zero-shot and few-shot run on all three datasets. On τ 2 \tau^{2} -bench and SOP-Bench, we also evaluate AWM ( Wang et al., 2025b ) , which keeps a model that chooses steps at run time, and Skill Factory ( Wang and Lu, 2026 ) , whose generated code we run with inputs supplied directly instead of through its model-based skill selection. On τ 2 \tau^{2} -bench only, we evaluate the Bayesian partial-order method BPOP ( Li et al., 2026 ) , which learns tool order but cannot produce SOP-Bench’s decision output (Appendix H ). Finally, we repair workflows for up to three rounds using failures on training inputs: ReTrace on both public benchmarks and zero-shot on τ 2 \tau^{2} -bench , with the same feedback, repair model, and stopping rule within each benchmark (Appendix D ). 4.3 Metrics Build rate is the fraction of requested constructions that yield a usable workflow: the code must load and, for planner-free methods, pass the planning-call checks. On SOP-Bench, code is regenerated until it parses, so every method builds; these retries count as construction calls. Task success is the benchmark’s score among built workflows, with execution errors counted as failures. On SOP-Bench an answer counts only if it uses the SOP’s output format and every scored field matches the label; this is stricter than the benchmark’s own substring match, so our numbers are not comparable to published SOP-Bench results. SOP-Bench results are macro averages over its 8 8 procedures. Enterprise completion is the fraction of executions the platform marks as successfully finished, averaged over procedures. We also report time per task, model calls for construction and execution, and enterprise cost per task. Without them, ReTrace averages 58 58 s per task against the agent’s 92 92 s, at 19 % 19\% of its cost (Figure 5 b in Appendix E ). Some agent runs with no successful tool call still count as complete (Appendix E.2 ). 5.5 Lessons for practitioners First, check tool outcomes, not only completion flags (Section 5.4 ). Second, test the model that writes the workflow: it matters more than the extraction model, and a larger model did not help (Appendix E.4 ). Third, when traces are long, give the generator few of them: more full traces eventually hurt (Section 5.1 ). 6 Conclusion ReTrace turns an SOP and a few logged agent runs into a workflow in which code, not an LLM, picks each step. The agent’s reasoning adds 6.2 6.2 points of task success on τ 2 \tau^{2} -bench and 8.8 8.8 points of enterprise completion, but not on SOP-Bench’s short procedures. The workflows cut τ 2 \tau^{2} -bench time per task from 170 170 s to 1.3 1.3 s and enterprise cost by 24 % 24\% . For high-volume procedures, compiling an agent into a workflow can pay off. 7 Limitations ReTrace relies on the agent’s reasoning, which may be wrong or may not reflect why the agent acted. Our construction checks confirm that generated code loads and contains no planning calls and, where re-execution is available, count how many logged steps it reproduces; they do not show that the recovered conditions are correct. We evaluate new inputs to the same procedures, not transfer to new procedures, and a change to an SOP or its tools may require rebuilding the workflow. Poor or incomplete traces limit what can be recovered. Enterprise completion is reported by the platform, which can mark failed runs as complete (Section 5.4 ); a human audit of outcomes would give a more reliable measure. The public evaluation covers only the telecom domain of τ 2 \tau^{2} -bench and eight SOP-Bench domains. SOP-Bench results use one workflow generation per trace sample, and its repair feedback includes training labels. Aggregation lets the SOP override traces that contradict it (Section 5.1 ); revising a rule when its cited evidence disagrees is left to future work. We also draw traces at random, without regard to which branches they cover, although the draw matters: results on a single SOP-Bench procedure vary by as much as 50 50 points across trace samples. Mixing successful and failed traces tends to help on τ 2 \tau^{2} -bench , though not significantly (Appendix E.3 ), and with long traces, full traces hurt beyond a dataset-dependent k k . We choose k k by cross-validation among a few small values ( k ≤ 4 k\leq 4 on τ 2 \tau^{2} -bench ), since each trace costs a live agent run. Choosing traces that cover different branches and outcomes, and setting k k from trace length, could give a complete IR from fewer agent runs and a workflow that succeeds on its first build, without repair. Future work should also verify that recovered conditions hold before the actions they justify and should cover more public domains. 8 Ethical Considerations Public benchmarks. τ 2 \tau^{2} -bench and SOP-Bench provide publicly available task data and evaluation code ( Barres et al., 2025 ; Nandi et al., 2026 ) . Evaluation on these benchmarks uses existing task data and test environments, without collecting new data from human participants or interacting with real customers. Enterprise data. Agent traces can contain sensitive information in task inputs, tool results, and explanations. We report only aggregate enterprise results and do not name the platform. Deployment. Reusing a workflow can repeat an incorrect condition or an unfair decision across many cases. The agent’s reasoning and written procedures may preserve biases from the original agent or business process; code-based step selection does not remove those biases. Workflow owners should review recovered conditions, restrict tool access, and require human review for actions with significant consequences for users. Access restrictions also matter because the same automation could scale unauthorized collection or use of sensitive data. Our evaluation does not assess differences in error rates across user groups. Appendix C Prompts Traces can come from agents with native thinking, which return their reasoning alongside each tool call, or from two-pass ReAct agents ( Yao et al., 2023 ) , which write an explanation before each call. Both provide the step fields s t = ( r t , a t , v t , o t ) s_{t}=(r_{t},a_{t},v_{t},o_{t}) of Section 3.1 . The three stages of Section 3.2 use five kinds of model calls: extraction once per trace step; a per-trace summary and a cross-trace merge, which together make up aggregation; and workflow generation with at most one fix call. We wrote the prompts for τ 2 \tau^{2} -bench and used them on Internal and SOP-Bench without changes (apart from the SOP-Bench input-field note in Appendix A ), including their example values, so a few τ 2 \tau^{2} -bench tool and argument names appear in them as format examples. Because nothing was re-tuned, Internal also tests whether the extraction and aggregation prompts transfer; on Internal every method uses the platform’s own generation prompt. Apart from the trace-loading code, our implementation contains no tool names from Internal or SOP-Bench. We summarize each prompt below. Models for each stage. On τ 2 \tau^{2} -bench all three stages use Sonnet 4.6. Appendix E.4 changes the extraction or synthesis model while keeping the others fixed; we never change the aggregation model. On Internal , the traces come from a Sonnet 4.0 agent, extraction and aggregation use Opus 4.8, and the platform generates the workflow with its own prompt and model, which we do not control. Sampling the merge. We run the merge several times rather than once: five independent runs on the same evidence for k ≤ 2 k\leq 2 and three for larger k k . We measure agreement between runs by the tool calls each rule contains rather than by its wording, and take the most common structure as the base. A rule that only some runs contain is kept as an open item; regenerating the whole document instead worked worse in our tests. When a single new trace is added to an existing IR, we run the merge once, since the existing IR already serves as the base. Extraction (Stage 1). This prompt turns one trace step into a record. The model replaces case-specific details (names, IDs, quoted values) with typed variables and reports only decision logic that carries over to new inputs: the situation the step responds to, the action it takes, the observable condition that justifies the action, and whether the step ends the task. Each field must be grounded in the tool called and the result just received, and a condition may use only information available before the action. The reasoning-side fields are precondition (the condition g t g_{t} ), action (the intended action α t \alpha_{t} ), state , and is_terminal ; the tool-side fields are the tool, its arguments with their JSON types, and the source of each argument. Per-trace summary (Stage 2). For a single trace, this prompt records which procedure steps the trace visited, under what conditions, with what arguments and results, which steps it skipped, and where the run went wrong and how it ended. Merge and IR format (Stage 2). This prompt combines all per-trace summaries and the recorded tool results into the IR, a document with a fixed format. It lists the opening steps, the completion check, and an ordered list of decision rules , each pairing a condition with the action it selects and the evidence for it. While the completion check fails, the first rule whose guard holds runs. The opening steps are a printing convention, not a separate component: they are the rules whose conditions hold before any tool has been called. The document also marks unwitnessed branches that no trace reached, named either by the SOP or by a step’s reasoning, and lists material that was explicitly excluded. Every element cites the trace steps or SOP statements that support it. When a new trace is added to an existing IR, the prompt must keep every existing rule, or remove it with a stated reason, and may confirm, narrow, extend, or contradict it. Workflow generation and consistency check. The generation prompt turns the IR into a workflow with a single decision function and forbids model calls that choose steps during execution. Before generation, a check uses rule names and citations to confirm three things, without judging what the rules mean: every rule from the summaries is kept or explicitly removed, every merged step has a citation, and every alternative named in the reasoning appears either as a branch or as cited excluded material. Repair from training failures. Repair starts from a built workflow (round 0 0 ) and runs it on a fixed set of training inputs of the same task family ( 4 4 on τ 2 \tau^{2} -bench , 16 16 on SOP-Bench). If any input fails, the repair model receives one prompt and returns a complete replacement workflow. The new workflow passes the same static checks as the first; when it fails them, the model gets up to two more attempts with the static-check error, separate from the repair rounds. The loop stops when every repair input succeeds, after three revisions, or when a revision cannot be built. It keeps the round with the highest score on the repair inputs, preferring the earlier round on ties. Validation and test inputs never enter the loop. The repair prompt receives neither the IR nor the traces, so repair changes only the code, and the IR remains the IR used for round 0 0 . Infrastructure faults stop construction instead of being shown as failures. We do not run repair on Internal : the platform provisions each workflow, and we currently cannot re-execute candidates offline during construction. Enforcing no planning calls (public benchmarks). On τ 2 \tau^{2} -bench and SOP-Bench we enforce the no-planning-call rule in three layers. First, a static check requires that the generated code parses and loads, exposes a single synchronous decision function, imports only the tool actions and a restricted part of the standard library, and contains no reflection, model-provider code, or dynamic evaluation. Second, the code runs in a separate sandbox process whose import hook blocks every model provider and which limits memory and time. Third, each candidate is re-executed on the training inputs, and we reject any candidate that makes a planning call. Code that passes all three layers made no planning call in any execution we observed. On Internal the platform builds a typed workflow graph that we cannot run in our sandbox, so none of the three layers applies; there, the guarantee is that the graph contains no planner node. Choosing among candidates (public benchmarks). When candidates can be re-executed, generation produces up to three of them and keeps the one that reproduces the most recorded steps, breaking ties in favor of fewer decision steps. Each later candidate sees the earlier ones and their results on each example, so the choice is a small guided search rather than a single filter. This selection is not available on Internal , where the platform builds the workflow and we cannot re-execute candidates, so we generate one workflow per procedure there. Few-shot gives the workflow generator complete traces, including the reasoning. Execution-only removes the reasoning but keeps the tool calls, inputs, and results.
