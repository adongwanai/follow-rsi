Small language models (SLMs) running on mobile devices can keep user data
private and work without connectivity. But they perform well only when
fine-tuned for the target task and sized for the target device, a process that
today requires repeated expert tuning. We present Mobile AI Factory , an
agentic system that builds a fine-tuned, quantized SLM for a given task and
phone. Given a task specification and a target phone, an orchestrator LLM
chooses whether to tune hyperparameters, mine real data, or generate synthetic
examples, while fixed rules roll back changes that hurt accuracy. The factory
searches from small to large models across base models and quantizations,
adapts its accuracy goal as it searches, and uses real measurements of the
target phone across inference engines and backends. We evaluate Mobile AI
Factory on ten tasks and four Android phones. On an unseen testset, its on-device models outperform two five-shot frontier
models on five tasks, by up to 0.34, and match them on
three more. Its search comes within 0.03 of exhaustively training all 27 model
variants on an entity extraction task, while using 19 × \times less GPU time.
Phone measurements also matter: the best configuration changes across phones. Without phone measurements, Claude Opus 5.5, given the full hardware and model specifications, misses the app’s requirements in 25% of easy and
moderate cases and in 60% of hard ones. Code is available at: https://github.com/evanly-gh/SLM_Factory . 1. Introduction Small language models that run directly on mobile devices could enable numerous applications. For example, a keyboard app could rewrite a hastily typed message into a more professional response, an email client could summarize messages and draft replies, and a voice assistant could help users with motor impairments fill out forms and navigate applications. Running these models on the device, rather than in the cloud, has two key advantages. First, sensitive data, like a patient’s medication schedule or a customer’s bank details, can remain on the device. Second, applications can operate in scenarios where connectivity is limited or intermittent, such as translating a conversation on a hiking trail or providing navigation when a vehicle loses network access. Figure 1 . Mobile AI Factory. It takes a task specification and a budget, and builds a specialized model for a phone. Smartphones now include capable CPUs and GPUs, and mobile inference engines
such as llama.cpp and MNN can run quantized SLMs at practical
speeds ( contributors, 2023 ) . The harder problem is building the models
themselves. Each application needs a model that is trained for its task and
small enough to run on the target phone. Even with training data available, developers still need to fine-tune
a base model, iterate on accuracy, decide on the model size and quantization
level, and test the resulting model on the target phone. This process must be manually repeated by a human expert for every phone model, which makes it impractical
for all but the largest companies. The Facebook app alone runs on more than
ten thousand smartphone and tablet models spanning many distinct
SoCs ( Wu et al., 2019 ) . New phones are released every year, and roughly
two new open foundation models are released every week ( Maslej et al., 2024 ) .
A configuration that performs well on one phone may perform poorly, or fail
entirely, on another. For example, in our measurements, llama.cpp GPU prefill
is 5.4 × \times faster than CPU prefill on the OnePlus 15, but 7.4 × \times slower on the OnePlus 8 Pro. Similarly, Qwen3-4B at 8-bit precision decodes
12.6–13.8 tokens/s on the OnePlus 15, but only 0.7–4.8 tokens/s on the
OnePlus 8 Pro. We ask the following question: given a task specification and a target phone, can we automatically produce a fine-tuned, quantized SLM that meets both the task’s accuracy goal and the phone’s resource budget?
The developer inputs the specification, which includes any available data sources, the evaluation metric, a verifier for the model’s outputs, optionally an accuracy goal, and the app’s resource requirements, such as prefill and decode speed, memory, and energy. This is difficult because we cannot know in advance which model will meet these requirements while achieving the best accuracy. Further, we may not know how large a model a task needs until we train it. We present Mobile AI Factory , an agentic system that builds specialized SLMs. Its core is a loop that curates training data, fine-tunes and evaluates a model, then decides what to try next. An orchestrator LLM chooses one intervention per iteration, while fixed rules handle rollback, budgets, and model scaling. Three components support this loop: a teacher model that generates synthetic data, a held-out-data agent that prepares a held-out set before training and shares only aggregate results with the orchestrator, and a phone profiler that benchmarks models across quantization levels, runtimes, and backends once per phone, reusing the results across tasks to identify configurations that meet app requirements. At its core, our factory uses three key techniques. • Agentic search with rollback and adaptive accuracy goals. We model each training attempt as a pipeline of dataset, hyperparameters, and learning strategy. At each iteration, the orchestrator chooses one intervention: tuning hyperparameters (LoRA rank, scaling, learning rate, weight decay, and number of epochs), mining more real data (if available) from the task’s sources, or having the teacher generate synthetic examples aimed at the failure categories that hurt accuracy most. A contamination check removes any row that also appears in the held-out test set. Since most interventions do not help, any change that lowers accuracy is rolled back to the best model so far, and the orchestrator tries something different. Finally, a fixed accuracy target may be too easy for some tasks and unreachable for others. Instead we set the goal to the teacher model’s five-shot score on the task (zero-shot where five examples do not fit its context), with a floor of 0.8. If the factory reaches the goal quickly or with little effort on the current model, the orchestrator can choose to raise it and continue its search. This lets it keep improving on tasks where the goal was set too low. • Bucketed search from small to large models. A model’s size depends on both its parameter count and its quantization: a 2B model at 4 bits is smaller than a 16-bit 0.8B model. We group all combinations of base model and quantization into N N buckets by size, and start with the smallest bucket. Within a bucket, the orchestrator picks which combination to train. If accuracy stops improving before reaching the goal, the factory moves to the next bucket. This avoids two extremes: letting the orchestrator pick one combination from the whole pool, which gives no guarantee of a small model, and training every
combination, which is too expensive. • Profiling the target phone. Whether a model meets the app’s requirements cannot be reliably determined from its specifications; it must be measured on the phone. The phone
profiler measures prefill and decode speed, peak memory, and energy on the
target phone for all combinations of base model, quantization, runtime
(llama.cpp or MNN), and backend (CPU or GPU). Each phone is profiled once,
and the profile is reused across all tasks. The profile also determines how
to run the final model, since the best runtime and backend differ across
phones, models, and quantization levels. The factory can then search only over models that meet the
app’s requirements on that phone, and the model it outputs is far more
likely to run within them. We implement Mobile AI Factory using Claude Sonnet 5 as the orchestrator. Each run uses two NVIDIA L40S GPUs: one trains and scores the model, and the other hosts a local teacher model (Qwen3.6-35B-A3B) that generates synthetic data. The model
pool contains nine base models from 135M to 4B parameters, from the SmolLM2, Gemma 3, Qwen3, and Qwen3.5 families, each at 4-bit, 8-bit, and 16-bit precision, for 27 combinations. We group these into five buckets by size on disk, with boundaries at 300 MB, 750 MB, 1.5 GB, and 2.5 GB. We profile four Android phones, ranging from a current flagship to a budget phone whose GPU the inference engines cannot use due to the lack of OpenCL: the OnePlus 15, Galaxy S23, OnePlus 8 Pro, and Redmi 9A. We evaluate the factory on ten tasks: biomedical entity extraction, fine-grained entity extraction, calendar event extraction, function calling, command parsing, 151-way intent classification, spam detection, emotion detection, grammatical error correction, and dialogue summarization. Our results are as follows: • On an unseen test set, the factory’s small models outperform both
Claude Sonnet 5 and DeepSeek v4 Flash, given five examples, on five tasks,
by 0.024 to 0.342, and match them on three more. The gains are largest where
the output format is strict: on biomedical entity extraction, a 517 MB
model scores 0.828, while Claude scores 0.652 with five examples. • With the phone in the loop, the factory returns models whose profiled cost on the phone meets every limit. On a Galaxy S23 whose limits rule out the factory’s best model for call summaries, it returns a model within 0.013 of it. • Phone measurements cannot be replaced by reasoning. Given every
specification but no real measurements, Claude Opus 5.5, with high reasoning effort enabled, misses the
app’s requirements in a quarter of easy and moderate cases, and in 60% of
hard ones. It misjudges run-time memory and the backend, neither of which
appears on a spec sheet. • After the first fine-tune, search adds a median of 8 points on the
smallest models and 2 points on the largest. On biomedical entity
extraction, bucketed search comes within 3 points of training all 27
combinations at a nineteenth of the GPU time. When a goal is reached within
a few iterations, the orchestrator raises it; in seven of the nine runs
where a raise led to more training, the model improved, by 3.6 points. Contributions. (1) We present Mobile AI Factory, to our knowledge the first agentic system that builds a fine-tuned, quantized SLM for a given task and a given phone. In contrast to optimizing accuracy on a single model ( Atreja et al., 2026 ) , our factory searches from small to large models and uses measurements from the target phone. (2) We profile four Android phones across 364 configurations (104 per phone with a GPU, 52 on the Redmi 9A) of model, quantization, runtime, and backend, and show that the best configuration differs across phones, models, and quantization levels. (3) We evaluate the factory on ten tasks and show that, on unseen test sets, its on-device models outperform two five-shot frontier models on five tasks and match them on three more, and that, with the phone in the loop, it returns models whose profiled cost on the phone meets every limit. 2. Related Work Agentic and Automated Fine-Tuning. Classical AutoML automates model selection and
hyperparameter search over predefined
spaces ( Thornton et al., 2013 ; Feurer et al., 2015 ; Bergstra and Bengio, 2012 ; Li et al., 2017 ; Falkner et al., 2018 ; Liu et al., 2024a ) , but cannot
change the training data.
MLE-bench ( Chan et al., 2025 ) and Kaggle-style agents ( Nam et al., 2025 ; Jiang et al., 2025 ) evaluate agents on end-to-end modeling tasks.
AutoML-Agent ( Trirat et al., 2025 ) proposes multiple LLM agents to go from a task
description to a working
model, but not one optimized to a particular device. Prompt
optimizers ( Khattab and others, 2023 ; Yang and others, 2024 ; Agrawal and others, 2026 ) instead improve the prompts given to a
fixed model. Over the past year, researchers have begun using agents to fine-tune
language models ( Li et al., 2026a ) .
PostTrainBench ( Rank et al., 2026 ) studies whether agents
can post-train base language models under a fixed compute budget.
Pioneer Agent ( Atreja et al., 2026 ) , the closest work, acquires data, builds evaluation sets, and
trains small language models by jointly searching over data,
hyperparameters, and learning strategy. Other
work uses agents to curate or process training data for a fixed student
model ( Luo et al., 2026 ; Huang et al., 2026 ) , or to generate synthetic data aimed at
the student’s weaknesses ( Zhang et al., 2025 ) . Tools such as
Slemify ( AWS Samples, 2026 ) automate a fixed pipeline of synthetic data
generation, fine-tuning, and quantization for models served on CPU servers. These systems share a key assumption: the model they produce will run on a server, so accuracy is the only objective. On a phone, this assumption breaks in four ways. First, a search that maximizes accuracy favors the largest model. Our factory instead treats the base model and its quantization level as a single choice and searches from small to large, moving to a larger model only when the current one stops improving. Second, a model evaluated at full precision may not be able to run on the phone; 4-bit quantization can significantly lower the accuracy: on the same weights, MNN’s default 4-bit export loses up to 0.19 (§ 3 ). Our factory therefore scores every model after quantization. Third, the same model can meet the app’s requirements on one phone and fail them on another, since the best runtime and backend differ across phones, and even a frontier model given full specifications picks a configuration that fails the app’s limits in 60% of hard cases (§ 5.3 ). Our factory uses a measured profile of the target phone to decide which models to search and how the final model runs. Finally, tasks differ widely in difficulty, so a fixed accuracy target is either unreachable or trivial. Our factory sets its goal from a teacher model and raises it when the goal is met easily. Hardware-Aware Model Design. Hardware-aware
neural architecture search includes device cost in the search objective,
either by measuring latency on real phones ( Tan et al., 2019 ) or by estimating
it with predictors and lookup tables ( Cai et al., 2019 ; Wu et al., 2018 ) . Other work
specializes networks for different devices ( Cai et al., 2020 ) or for
microcontrollers ( Lin et al., 2020 ) . nn-Meter ( Zhang et al., 2021 ) predicts DNN inference
latency, and ( Wang et al., 2019 ; He et al., 2018 ) search quantization and compression policies with hardware feedback. These
methods design architectures or compression policies for a given dataset,
rather than adapting pretrained language models to a new task. In contrast,
we fine-tune pretrained language models for a new task and treat quantization
as part of the search. We also measure each configuration on the phone
instead of predicting it, since run-time memory and the best backend differ in
ways a predictor or a specification sheet may miss. Recent work also gives LLM agents feedback from hardware, to write embedded
firmware ( Yang et al., 2026 ; Xu et al., 2025b ; Li et al., 2026b ; Raval et al., 2025 ; Zhang et al., 2026 ) or generate inference
engines ( Kamahori et al., 2026 ) . These systems optimize
the software around a model, or preserve a model that already performs the
task. Our factory instead builds the task capability itself, for language
models on phones. Adapting Models to Devices. NestDNN ( Fang et al., 2018 ) builds
multi-capacity models that trade accuracy for resources at runtime,
LegoDNN ( Han et al., 2021 ) scales models block by block to fit each device, and
AdaptiveNet ( Wen et al., 2023 ) adapts a deployed model to diverse edge
environments. These systems start from a model that already performs the task
and adjust its size. Our factory starts from a task specification, builds the
task capability through fine-tuning and data, and chooses the model, its
precision, and its runtime from measurements of each phone. On-Device LLM Inference and Measurement. A
number of engines run quantized language models on phones, including
llama.cpp ( contributors, 2023 ) , MNN ( Jiang et al., 2020 ; Wang et al., 2024 ) , MLC-LLM ( MLC team, 2023 ) , and
ExecuTorch ( Meta AI, 2024 ) . Research systems further reduce latency using
mobile NPUs ( Xu et al., 2025a ) and activation sparsity ( Xue et al., 2024 ) , and
MobileLLM ( Liu et al., 2024b ) designs sub-billion-parameter models for phones.
Prior work also measures LLM performance, memory, and energy across phones
and frameworks ( Laskaridis et al., 2024 ; Murthy et al., 2024 ) , profiles models on real devices
in device farms ( Qualcomm Technologies, Inc., ) , and selects a backend for each device at
runtime ( Cactus Compute, Inc., ; Meta AI, 2024 ) . These systems run or measure an existing
model. In contrast, our factory builds the model, and uses per-phone
measurements to decide how it runs on each target phone. Training Data and Quantization. Prior work shows
that data generated by a teacher model lets small models perform well beyond
their size ( Wang et al., 2023 ; Abdin et al., 2024 ; Mukherjee et al., 2023 ) , and that a small
set of high-quality examples can outperform a larger one ( Zhou and others, 2023 ) . Small
models can outperform much larger
models ( Hsieh et al., 2023 ; Zhao et al., 2024 ) ; our factory automates
this process and targets it at a phone. Later work targets this data at
the student’s failures ( Kessler et al., 2026 ; Zhang et al., 2025 ) , filters it for
quality ( Bansal and others, 2025 ) , and warns that self-generated data can narrow a
model’s outputs ( Shumailov et al., 2024 ) . Our factory uses synthesis as an intervention, anchored to real training examples and filtered by
programmatic checks before training. Similarly, models are typically fine-tuned with
LoRA ( Hu et al., 2022 ) and quantized after training ( Dettmers et al., 2022 ; Frantar et al., 2023 ; Lin et al., 2024 ) .
In contrast, our factory makes quantization part of the search, choosing
between a larger model at lower precision and a smaller one at higher
precision, and scores both after quantization. Unlike systems that
fine-tune on the phone ( Geng et al., 2026 ) , our factory runs on a server. 3. Motivation for hardware profiling Deploying a small language model on a phone requires choosing an inference engine, a backend (CPU or GPU), and a quantization. These choices depend heavily on the phone. Measurement setup. We benchmark 26 of the 27 model variants that Mobile AI Factory searches over: nine base models from 135M to 4B parameters, each at 4, 8 and 16 bits, except the 16-bit Qwen3.5-4B, which exceeds the RAM of two of our four phones. We run them on four phones that span five years: a OnePlus 15 (Snapdragon 8 Elite Gen 5, 16 GB RAM), a Galaxy S23 (Snapdragon 8 Gen 2, 8 GB), a OnePlus 8 Pro (Snapdragon 865, 12 GB) and a Redmi 9A (MediaTek Helio G25, 4 GB). Each variant runs on llama.cpp ( contributors, 2023 ) and MNN ( Jiang et al., 2020 ) , on the CPU and the GPU; the Redmi 9A’s GPU lacks OpenCL, so it runs on the CPU only. We follow the protocol of ( Cai et al., 2026 ) : a 256-token prompt, then 256 generated tokens, four CPU threads, and three repetitions after one warm-up. Every run starts with the battery temperature at or below 28 ∘ C (32 ∘ C on phones that idle above it), with the CPU clocks uncapped, on battery, in airplane mode with Wi-Fi left on for adb, and with the screen off; the OnePlus 8 Pro stays awake with only its panel off, since it caps its CPU when it sleeps. Energy is the whole phone’s battery energy, read from the fuel gauge every 100 ms, minus idle power.  At 4 bits, the profiles use Q4_0 for llama.cpp, since the pinned build’s OpenCL backend has no Q4_K_M kernel, and MNN’s default export; the factory scores accuracy on the Q4_K_M and HQQ exports of the same weights (§ 4.3.3 ). We attempted 364 configurations (104 on each phone with a GPU, 52 on the Redmi 9A), and 288 ran to completion. Repeated runs differ by 0.1–5% within a session (up to 38% for MNN’s CPU prefill on the OnePlus 15), while GPU decode throughput varies by 10–20% between sessions, small next to differences of up to 94 × \times . Moving from 4 to 8 bits with llama.cpp on the CPU costs at most 21% of decode speed on the OnePlus 15 and the S23, but 16–43% on the OnePlus 8 Pro (Fig. 3 c). On the S23’s GPU, Qwen3-0.6B even decodes faster at 8 bits (26.5 tokens/s) than at 4 (14.9), likely because llama.cpp keeps a 4-bit file’s output layer at 6 bits and the S23’s OpenCL kernel for that format is slow. • Inference engines can change accuracy. To see what this means for a developer, we take the biomedical entity-extraction task and its accuracy for the 26 profiled variants, and ask: if a request (a 256-token prompt and a 48-token answer) must finish within a fixed time, what is the most accurate model each phone can run? Under a 1 s budget, each phone needs a different model, on a different engine and backend, and accuracy ranges from 0.719 to 0.835 (Table 2 ). Under a 4 s budget, the OnePlus 15 and the S23 both reach the best accuracy any variant achieves on this task, through different engines. These measurements shape three decisions in Mobile AI Factory. First, the configuration cost has to be measured on each phone; the measurements do not depend on the task, so we run them once per phone and reuse them for every model the factory builds. Mobile AI Factory Design Our factory takes two inputs: a task specification and a target phone. It returns a fine-tuned, quantized model for that phone, together with the inference engine and backend. 4.1. Agentic Architecture Overview Fig. 4 shows our two-stage system. The setup stage, run once per task, looks up the target phone’s measured profile, removes every configuration that exceeds the developer’s budgets on that phone, and picks the inference engine and backend for each remaining variant. The search loop runs until the goal is met or the budget runs out. The orchestrator LLM decides which intervention to try next, which model to try within a tier, and whether to raise the accuracy goal. It does not decide when to stop, when to roll back, or when to move to a larger model; those are deterministic rules. We split the roles this way for two reasons. First, a run calls the orchestrator most often when it is stuck, so the rule that notices it is stuck should not depend on the orchestrator. Second, most of the orchestrator’s ideas do not work: in the run with the most iterations (nested intent parsing, 109 evaluations, 104 of them interventions), 88% of the interventions made the model worse and were rolled back. The rules ensure steady progress. Each run uses three models: the orchestrator, a local teacher that writes synthetic training data, and the small model being built for the phone. 4.2. Setup Stage The setup stage finds the configurations the phone can run, writes a brief for the teacher model, and builds the evaluation set. 4.2.1. Phone Profiles and Feasibility We measure each phone once, using the protocol in § 3 . A configuration is one of the model variants run on one engine (llama.cpp or MNN) and one backend (CPU or GPU). For each configuration, the profile stores prefill and decode throughput, peak memory, and energy per token; configurations that crash, run out of memory, or are rejected by the GPU driver are stored as failures. The developer gives budgets for a typical request: latency, memory and energy. The factory computes each configuration’s latency from its measured throughput and the request’s prompt and output lengths, and drops configurations that exceed a budget or failed on this phone. For each surviving variant, it keeps the engine and backend that decode fastest on that phone. The factory groups the feasible variants into five tiers by their size on disk, with boundaries at 300 MB, 750 MB, 1.5 GB and 2.5 GB. A 2B model at 4 bits (1.3 GB) thus shares the third tier with a 0.6B model at 16 bits (1.4 GB). Of the 27 variants, 6, 5, 5, 4 and 7 fall in tiers 1 to 5. A phone profile only removes variants; it does not change the tier boundaries. 4.2.2. Task Analysis and the Brief The orchestrator reads a sample of training rows and writes a short brief describing the task, what a correct answer should look like, and the mistakes most likely to make an answer incorrect. It never sees the held-out set. The brief is included in every prompt that asks the teacher to generate or check a training row. 4.2.3. Evaluation Setup The factory draws up to 1,000 rows, balanced across labels for classification tasks, and freezes them as the held-out set. The set is scored on every iteration, so we cap it. Four firewalls check for overlap with the held-out set, by exact match after normalization, at four points: (1) when a dataset is loaded, where training rows that repeat a held-out row are dropped and any overlap that remains stops the run; (2) on every row mined or generated later; (3) again after quality control, which can rewrite rows; and (4) through the label set, which is fixed from the held-out rows so that no later step, including the teacher, can add a label. The trainer also keeps its own validation split for choosing checkpoints, so the held-out set is never seen during training. The held-out set guides every search decision, so its scores can read slightly high; § A measures this on unseen test sets. To label difficulty, the factory runs the smallest and the largest base models over the held-out set, without fine-tuning. A row is easy if both answer it correctly, medium if only the larger one does and hard if neither does. This measures the gap the tiered search aims to close. A fixed accuracy target such as 0.9 may be trivial for some tasks and out of reach for others, so the factory scores the teacher, prompted with five real training examples, on the held-out set through the task’s own scorer and sets the goal to that score, with a floor of 0.80 and a cap of 0.99. The run starts in the lowest tier. 4.3. Search Loop The loop decides which model to train (§ 4.3.1 ), what to change (§ 4.3.2 ) and whether a change helped (§ 4.3.3 ). 4.3.1. Small-to-Large Search The factory starts in the cheapest tier and moves up only when that tier stops improving. Escalation rule. The factory escalates when the score has not risen by more than 0.02 over the last 15 evaluations, or after 30 evaluations in one tier without reaching the goal. Both counts include rolled-back attempts. On escalation, the orchestrator picks one variant in the next tier. The run keeps its training data, and the rest of the search starts over. Increasing the goal. When the run reaches its goal, the factory stores the result and asks the orchestrator whether to raise the goal, by at least 0.005 above the highest goal so far and to at most 0.99. A raised goal sends the run back into the loop. The orchestrator may lower the goal when failures look like a model size limit, but only after a raise, and never below the starting goal. Output. The run returns the best model in each tier it visited, with its engine and backend. Since the search climbs from the cheapest tier, the developer reads off the cheapest one that meets their bar. If no tier does, the run returns its best model and why it stopped: tiers, steps or time ran out. 4.3.2. The Orchestrator and Its Interventions In each iteration, the orchestrator proposes exactly one change. Input and output. The orchestrator sees the evaluator’s report (the overall score, accuracy on easy, medium and hard rows, and the most common failure categories from the task’s own scorer, such as wrong entity boundaries or a call to an undeclared function), and the run memory, built from the search graph, which lists every attempt, whether it was kept, and what has failed since the last improvement. It returns a JSON object, naming the change, its parameters and a hypothesis. The factory validates it, and replaces a hyperparameter setting already tried on the same data with an untried neighbor. Hyperparameters. A hyperparameter intervention holds the data fixed and adjusts up to five values: LoRA rank, the ratio of α \alpha to rank, weight decay, learning rate and epochs. Batch shape follows from the GPU and dropout is fixed at zero. Data. A data change adds rows and keeps the best hyperparameters so far. Rows come from two sources. Mining first reads further into the task’s own sources, and searches the web for new datasets only when those are exhausted, giving up after two empty rounds. Targeted synthesis has the teacher write 25–600 rows per failure category, in proportion to its failure count, and drops a category whose count does not fall. Synthesis passes three gates. (1) The teacher must score at least 0.80 on the task with five real examples, the way synthesis prompts it, or synthesis is off for the run; our main runs bypass this gate on seven tasks (§ 5.1 ). Examples matter: on biomedical entity extraction the teacher scores 0.13 without them and 0.32 with five. (2) Each row passes a programmatic check where one exists, for example that every extracted entity appears verbatim in its text. (3) The teacher can check each row against the brief (§ 4.2.2 ), using only real examples as references; our runs turn this check off where a strict programmatic check exists and, on the other tasks, record its verdicts without dropping rows. The training set only grows; rows leave only through quality control, the firewall, or the rollback of the change that added them. Rollbacks. Three mechanisms limit each failure to one iteration. Training always restarts from the base model, so rollback exactly restores the previous behavior. Control then returns to the orchestrator, which must try a different change rather than repeat the same regression. A watchdog stops runs that stop making progress, like three consecutive synthesis rounds that add nothing or a training set that shrinks by 25% (or 1,000 rows) in one step. We require repeated or large failures so the watchdog does not trigger on noise; we added it after one run spent eight hours on eight data changes that added no examples. Scoring Each Iteration The setup stage freezes a held-out evaluation set that training cannot access (§ 4.2.3 ). The loop adds three rules. • Each iteration merges the adapter, exports 4- and 8-bit models to their deployment format, loads them in the target engine, and scores them on the held-out set; 16-bit models are scored in Transformers. For MNN, we use 4-bit HQQ with 32-weight blocks because its default quantization loses up to 0.19 accuracy (§ 3 ). • The evaluator returns scores, failure counts, and the fraction of parseable outputs, but not the evaluation rows. This separates wrong answers from malformed outputs. Any decision that quotes a held-out row is rejected. • The base model is the first candidate, and any fine-tuned model that scores worse is discarded, so the loop can conclude that fine-tuning does not help. A failed evaluation is recorded as missing, not zero. An early run used zero and incorrectly credited fine-tuning with a gain of 0.85. 4.4. Implementation Details Mobile AI Factory’s loop is a LangGraph state machine. The orchestrator is Claude Sonnet 5, called through its API, and the teacher is Qwen3.6-35B-A3B, served locally with vLLM. Training uses LoRA adapters on 4-bit base models, through Unsloth, PEFT and Transformers, with loss computed on the answer tokens only and the checkpoint chosen on a validation split. Each run uses two NVIDIA L40S GPUs on a SLURM cluster: one trains and scores the model, and the other serves the teacher. Scoring exports each 4- or 8-bit model with llama.cpp or MNN’s own tools and runs it in that engine on the same GPU. A run can take several days, longer than a cluster job is allowed to run, so the run state is checkpointed to SQLite after every step, and a job nearing its time limit checkpoints and requeues itself. 5. Evaluation 5.1. Setup Tasks. We use ten tasks. Five are bound by their output format: biomedical entity extraction (BC5CDR), calendar extraction to JSON, nested intent parsing (TOPv2), entity extraction over 33 fine-grained types (MultiCoNER) and function calling (BFCL). In four, the label cannot be read off the input: 151-way intent classification (CLINC150), spam detection, 28-way emotion classification (GoEmotions) and grammatical error correction (BEA-19). In the last, dialogue summarization (DialogSum), the base model can already do the task and fine-tuning mainly teaches the answer style. Each task starts from 2,600–5,000 real training rows. Its held-out set has 1,000 rows, except for DialogSum (500), Calendar JSON (535) and MultiCoNER (871). Factory configuration. The model pool holds the 27 variants from § 4.2.1 : nine base models from 135M to 4B parameters, each at 4, 8 and 16 bits, from three families: SmolLM2 (135M, 360M), Gemma 3 (270M) and Qwen (Qwen3 at 0.6B, 1.7B and 4B; Qwen3.5 at 0.8B, 2B and 4B). Every run in this section uses the full pool and the five size tiers of § 4.2.1 , and scores every 4- and 8-bit model as a llama.cpp file (Q4_K_M or Q8_0) on the training GPU; 16-bit models are scored in Transformers. § 5.3 then runs the factory with the phone profiles. The orchestrator is Claude Sonnet 5 and the teacher is Qwen3.6-35B-A3B. Every run starts from LoRA rank 16, α \alpha 32, learning rate 2 × 10 − 4 2{\times}10^{-4} , weight decay 0.01 and 3 epochs. Goal settings. Every task runs with the factory’s default goal, the teacher’s five-shot score with a floor of 0.80 (§ 4.2.3 ); for intent classification, whose five examples do not fit the teacher’s context, its zero-shot score. Discussion and Limitations A developer still provides the task specification: data sources, the metric, and a verifier for model outputs. Our results suggest that the verifier matters most. Rejecting malformed outputs made synthetic data usable, while tasks where few generated rows survived quality control saw little benefit from synthesis. Building this harness is the most hand-engineered part of the pipeline. An agent that decomposes a task into its type, such as classification, extraction or generation, and assembles a matching scorer and verifier would make the factory far more autonomous. So would an early check of synthetic-data survival rates. We also restrict the factory to a predefined set of decoder models from 135M to 4B. This is practical when developers prefer specific model vendors, but the restriction is not fundamental. The factory could instead download candidate base models on demand, and once a task is known to be classification, add encoder models of 1–50M parameters, far smaller than any model in our pool. Training is LoRA fine-tuning only; preference optimization, reinforcement learning or distillation from a larger model are natural additions. Synthesis writes a few hundred rows per round from a local 35B teacher. This keeps each round cheap and targeted, but may cap what synthesis can add; larger rounds from a stronger teacher are worth exploring. Our phone profiles cover CPUs and GPUs. Recent work shows that mobile NPUs can process prompts an order of magnitude faster while offering little decode advantage over CPUs ( Cai et al., 2026 ) . Adding NPUs would require only extending the hardware profile, and would make backend selection even more important. We also measure each configuration alone, from a cool start, at one prompt length, with four threads, and with the phone otherwise idle. A deployed model shares the phone with other apps, other models and changing thermal state, so sustained and concurrent use, and longer prompts, may change which configurations meet a requirement. Profiling a phone is slow, largely because it must cool between runs, but this cost is paid once and shared across tasks. Future work could measure only a subset of configurations on a new phone and predict the rest, while validating those predictions before the factory relies on them. 7. Conclusion We present Mobile AI Factory, an agentic system that builds a fine-tuned, quantized small language model for a given task and phone. We showed that the right model and configuration change from phone to phone, and that even a frontier model cannot make this choice without measurements. Taking a step back, ML and agent researchers mainly optimize metrics and rarely think about mobile devices. Mobile systems researchers, on the other hand, build inference engines and take the model as given. Mobile
AI Factory suggests a near-future in which agents build many phone-specific small,
specialized models, and rebuild them as

Synthesis won all ten tier comparisons (Fig. 10 ), eight of them by more than our 0.015 noise level and four of them by more than 0.03. Tiers within a run share a growing training set, so they are not independent. How much synthesis helped depended on what limited the small model.

We reran every task with only 100 real rows (151 for intent classification, one per intent), mining off and synthesis enabled. Nested parsing kept its full-data score, but its loader always adds a fixed 674-row in-domain adaptation set, so we leave it out of the counts that follow. Four of the other nine tasks retained at least 97% of their full-data score. Calendar extraction kept 98%, but only on the 4B model; the 0.8B model fell 0.18 behind, suggesting real data matters more for smaller models. Grammar correction and summarization lost 7–10%, while entity and emotion tasks lost 16–30%. Teacher accuracy did not predict this loss. The two largest drops came on the two tasks where the fewest synthetic rows passed quality control: 3% for biomedical extraction and 24% for fine-grained entities, against more than 60% on every other task. This pass rate is cheap to estimate before relying on synthesis. Appendix C Hardware requirements Tables 7 – 9 list the 60 requirements used in § 5.3 . Each deploys one of our ten tasks in a way an app would use it, on one phone. A requirement sets four limits: peak memory, a minimum prefill speed, a minimum decode speed, and a maximum energy per request. A configuration meets the requirement only if it meets all four. The kind of deployment sets the memory budget and the response time (Table 6 ). A fixed memory budget is capped at 25% of the phone’s RAM, which matters only on the 4 GB Redmi 9A. The task’s real request then sets the speeds: prefill must process the request’s input within the first-token time, and decode must finish the answer within the remaining time. The fixed part of each prompt, such as instructions, label lists and tool schemas, is computed once and cached, so a request prefills only its input. A summary the user reads as it streams instead needs at least 5 tokens/s. The energy budget is a share of the phone’s battery divided by the deployment’s requests per day. The same deployment therefore has different limits on different phones. The tier of a requirement is the share of the phone’s configurations that meet it: easy if at least 60% do, moderate if 30–60% do, and hard if fewer than 30% do. From the 38 deployments run on all four phones, we chose 20 requirements per tier, spread across tasks, phones and deployments, and kept only requirements that at least one configuration meets.
