Its central operation maps batches of scalar inputs to points on curves represented in B-spline or Legendre polynomial bases, with differentiation through both inputs and coefficients. Curve coefficients can be optimized jointly with the surrounding model or produced by another network. The library provides trainable modules, reusable basis modules, and a functional interface, supporting applications ranging from continuous feature embeddings to Kolmogorov–Arnold networks and functional regression. Its implementation combines classical evaluation algorithms with vectorized PyTorch operations, emphasizing readability and maintainability without custom hardware kernels. Timing experiments compare curve evaluation against NumPy and SciPy and KAN training against EfficientKAN across a range of problem sizes. The results illustrate where this generality remains computationally practical and where overhead is substantial. Input: a mini-batch of numerical features of size. Output: a mini-batch of points on multi-dimensional curves. The use of parametric curves spans a wide variety of scientific and engineing disciplines, both in machine learning and outside of it. Examples include spline regression, continuous features embeddings ( Shtoff et al., 2024 ) , Kolmogorov-Anrnold networks ( Liu et al., 2025 ) , computer aided design ( Bézier, 1968 ) and others. Yet, there seems to be no software library providing a common, composable interface for curves as learnable primitives, but rather every re-implements its own high-level object directly. TorchCurves puts the learnable parametric curve as a primitive in its own right, and facilitates its use in a variety of model achitectures. Its genericity allows PyTorch ( Ansel et al., 2024 ) users to build models that include learnable parametric curves as a component. The essence of TorchCurves is one operation - transforming a mini-batch of input features to a mini-batch of points on curves in ℝ d \mathbb{R}^{d} , as depicted in Figure 1 . At this stage we support B-Spline and Legendre polynomials. Our implementation is vectorized and there are no loops on the feature, batch and curve dimensions. But we do not have custom kernels for specialized hardware - we chose to implement everything in pure PyTorch for readability and maintainability reasons. This basic operation is differentiable in both its parameters, the input features and the curve parameters, allowing both learning a curve and back-propagating to previous network layers. The next sections are structures as follows: in Section 3 we present the main components of the library and present examples of applications: continuous feature embeddings, Kolmogorov-Arnold networks, and functional regression. In Section 4 we discuss some implementation and testing details. 2 Related work Polynomial and spline representations are well established in numerical software. NumPy ( Harris et al., 2020 ) and SciPy ( Virtanen et al., 2020 ) provide routines for representing, evaluating, and differentiating such functions. Differentiable spline packages also exist within the PyTorch ecosystem: torchcubicspline ( Kidger, n.d. ) constructs natural cubic interpolants from observations, while torch-bspline ( Melchers and Cochran, 2025 ) provides differentiable B-spline evaluation. In machine learning, mappings from scalar values to learned vectors appear in numerical feature embeddings ( Gorishniy et al., 2022 ; Shtoff et al., 2024 ) . Learnable univariate functions also constitute the edges of Kolmogorov-Arnold networks ( Liu et al., 2025 ) , with specialized implementations such as EfficientKAN ( Cao, 2024 ) . These applications illustrate several roles that parametric curves can play within a larger model. TorchCurves takes the curve itself as the reusable abstraction: a parameterized mapping from a scalar input to a vector output, differentiable with respect to both its input and its coefficients. It provides a common interface for B-spline and Legendre polynomial representations, whose coefficients can be learned directly or supplied by another model. Its contribution is to make these curves convenient to compose with other learning components, without requiring an interpolation problem or prescribing a particular network architecture. 3 API and applications We first present the basic API, and then show use-case examples where it can serve. 3.1 The API The library provides two basic components, BSplineCurve and LegendreCurves , which are one-dimensional curves embedded in a high-dimensional space. Each curve is represented as 𝒄 ⁡ ( x ) = ∑ i = 1 n 𝒗 i ​ B i ​ ( x ) , {\bm{c}}(x)=\sum_{i=1}^{n}{\bm{v}}_{i}B_{i}(x), where B i B_{i} are the appropriate basis functions, B-Spline or Legendre, and 𝒗 1 , … , 𝒗 n {\bm{v}}_{1},\ldots,{\bm{v}}_{n} are its (possibly) learned coefficients. Each component can evaluate a bulk of curves 𝒄 1 , … , 𝒄 m {\bm{c}}_{1},\ldots,{\bm{c}}_{m} simultaneously, as shown in Figure 1 . Below is an example: ⬇ import torch import torchcurves as tc u = torch . rand (4, 3) # 4 samples with 3 features. curve = tc . BSplineCurve ( num_curves =3, dim =2 # 3 curves in 2 dimensions ) y = curve ( u ) # (4 samples, 3 curves, 2 dimensions) print ( u . shape , ”->” , y . shape ) # torch.Size([4, 3]) -> torch.Size([4, 5, 2]) Of course, mathemaically inclined readers will say this example is incomplete. And justifiably so - both B-Spline and Legendre polynomial bases require configuration, such as the polynomial degree, the number of knots in case of B-Splines, and others. Moreover, splines and polynomial approximations work in a compact interval , which is nowhere to be seen in the above example. Indeed, we provide the modules with defaults, but they are are fully configurable. Both B-Splines and Legendre polynomials are assumed to approximate inputs on the interval 𝒰 = [ − 1 , 1 ] \mathcal{U}=[-1,1] , and can be configured with a mapping for transforming their input to that interval. For example: ⬇ spl_curve = tc . BSplineCurve ( num_curves =3, dim =2, # dimensions input_map = ’real.arctan’ , # maps ‘x‘ to ‘2 arctan(x) pi‘ num_knots =20, # 20 uniformly-spaced knots, with not-a-knot endpoints degree =5 # polynomial splines of degree 5 ) lgd_curve = tc . LegendreCurve ( num_curves =3, dim =5 # dimensions input_map = ’arctan’ , # same as above degree =50 # degree-50 Legendre polynomials ) Mapping functions include the above-mentioned arctangent function, which is also the default, but also x → x / 1 + x 2 x\to x/\sqrt{1+x^{2}} called real.rational and is inspired by by its use in the differential equations literature on unbounded domains ( Guo and Wang, 2004 ; Boyd, 1987 ; Wang and Guo, 2004 ) , and a simple clamping to 𝒰 \mathcal{U} called real.clamp . The prefix real means these mappings are designed for arbitrary real numbers. The library also has nonneg.rational and nonneg.arctan for non-negative numbers. The users can also provide their own, in the form of a Python callable. Trainable modules are useful, but they do not cover all use-cases the library aims to support. Thus, the library provides three API levels which we shall explain below: (a) trainable modules, as we just seen; (b) basis modules, which cache tensors to avoid their recomputation but have no trainable parameters; (c) a fully functional API, akin to torch.nn.functional . The fully functional API, as its name suggests, consists of pure functions that have no state. Below is an example: ⬇ import torchcurves . functional as tcf bspl_func = tcf . bspline_curves ( inputs , # (B, C) - a batch of input points for each curve coefs , # (C, P, D) coefficients of C B-Spline functions having P coefficients in D dimensions knots , # B-Spline knots. unif. spaced in [-1, 1] with not-a-knot conditions, if unspecified. degree =5 # the piecewise-polynomial degree. 3 if unspecified. ) leg_func = tcf . legendre_curves ( inputs , # (B, C) - a batch of input points for each curve coefs , # (C, P, D) coefficients of C legendre polynomials having P coefficinets in D dimensions degree =50 # the polynomial degree. We always have P=degree-1. These are useful if the coefficients are not learned directly, but come as an output of another module. Note, that in case of B-Spline functions, the connection between the number of knots and the number of coefficients P must be 𝙿 = | 𝚔𝚗𝚘𝚝𝚜 | − 𝚍𝚎𝚐𝚛𝚎𝚎 + 1 \mathtt{P}=|\mathtt{knots}|-\mathtt{degree}+1 . If the knot vector is not specified, the number of uniformly-spaced knots is automatically determined from the degree and the number of coefficients P . Finally, in between learnable modules and fully functional API we have the basis modules. A basis module is similar to the functional API, but stores immutable buffers, such as the knot vector, for convenience. That way, if a model is moved from CPU to an accelerator, such as a GPU, the buffer automatically moves with it by PyTorch. Below is an example: ⬇ import torchcurves as tc # quadratic splines with 50 B-Spline functions and a rational mapping to [-1, 1] bspl_basis = tc . BSplineBasis ( degree =2, knot_config =50, input_map = ”real.rational” ) # evaluate a B-Spline function. Note - 50 coefficients for our 50 B-Spline functions. bspl_func = bspl_basis ( input , # (B, C) - a batch of input points for each curve coefs # (C, 50, D) - the coefficients of C B-Spline functions in D dimensions. ) 3.2 Applications One of the first applications that comes to mind is producing embeddings for continuous features, such as height, weight, BMI, the time since the last visit of the user on our website, and others. Imagine we have a model whose inputs are embedding vectors, such as a Factorization Machine, or a Transformer. For discrete, or categorical features - we can just map features to embeddings using a standard embedding table. But for a continuous value, we need a mapping of the value to a vector in the embedding space - and a curve is such a mapping. In theory, we can think of any model f ⁡ ( 𝒙 ) f({\bm{x}}) as ”functional regression” - just partition 𝒙 = ( 𝒙 1 , 𝒙 2 ) {\bm{x}}=({\bm{x}}_{1},{\bm{x}}_{2}) and define the model as the function f ⁡ ( 𝒙 1 , ⋅ ) f({\bm{x}}_{1},\cdot) . The point is not in the model’s architecture, but as the study of the model, including its performance, as such a function. Since the authors come from the online advertising field, one prominent example is fitting the probability of winning an ad auction given auction features and a non-negative bid. See Pan et al. (2020) ; Zhou et al. (2021) . Note that this is a CDF - it must be nondecreasing. Our efficiency goals are modest - we aim for the best we can achieve using pure PyTorch code, without custom kernels. Thus, we implement vectorized versions of well-known algorithms, both for B-Spline and Legendre polynomial evaluation. The main feature of the B-Spline basis is its sparsity - at any given point, only 𝚍𝚎𝚐𝚛𝚎𝚎 + 2 \mathtt{degree}+2 basis functions are non-zero. An efficient algorithm for exploiting the sparsity is the well-known Cox-deBoor method ( COX, 1972 ; De Boor, 1972 ) . The algorithm provides both an efficient sparsity-exploiting way to compute the value and the derivative. These, in turn, are used in a custom PyTorch autograd function to facilitate efficient back-propagation through the inputs and the coefficients. The implementation is done in a vectorized manner without iterating on any of the input dimension, but does require iterating on the degree. Thus, a spline of degree five does require six Python iterations to compute. For Legendre polynomials we have the well-known Clenshaw recursion ( Clenshaw, 1955 ) . Here, as well, we do not iterate on any input tensor dimensions, but we do iterate on the degree. Since typically good approximation is achieved with high-degree polynomials, higher than B-Splines, this may be less efficient in some situations. For example, a polynomial of degree 50 will require 51 Python for-loop iterations. In our implementation we do take special care to avoid memory allocation of tensors. We do not claim optimality, but merely a best-effort. Again, our efficiency claim is modest - to be fast enough to be useful. The library is thoroughly tested, and in particular, the results are compared to SciPy ( Virtanen et al., 2020 ) splines and NumPy ( Harris et al., 2020 ) Legendre polynomials. Derivatives are validated using internal gradient-checking mechanisms of PyTorch, that compare numerically approximated derivatives to those of back-propagation. Comparisons were done for both 32 and 64 bit floating point numbers. 5 Experiments Our objective here is giving the reader a qualitative understanding of what we mean by ”our efficiency claim is modest”. To that end, we perform two comparisons: (a) speed of inference-only computation of Legendre polynomials and Splines on CPU, compared to NumPy and SciPy; and (b) training speed of a KAN, compared to EfficientKAN ( Cao, 2024 ) , both on CPU and GPU, each implemented in its idiomatic form. Our aim is not to outperform specialized implementations, but to show that the flexibility of treating curves as general-purpose trainable primitives remains computationally practical, even when composing them into higher-level architectures such as KANs. All measurements were done on a Lenovo P14s Gen-7 laptop, with an Intel Core Ultra 7 356H CPU, and a NVIDIA RTX PRO 500 Blackwell GPU. The experiments were running on Ubuntu 26.04.01, with Python 3.12, NumPy 2.5.4, SciPy 1.18.1, and PyTorch 2.15 (CUDA 13.2). CPU affinity is limited to the first cores 1-4, which are the performance cores of that CPU, to both allow PyTorch exploit parallelism and obtain consistent speed measurements. We note that both NumPy and SciPy do not provide an autograd mechanism, thus they are by definition “inference-only” libraries. Therefore, our comparison in (a) are inference-only in nature - we perform no backpropagation, but only compute the value of the spline / Legendre polynomial functions using each library, and compare the number of milliseconds per call for various coefficient counts, curve dimensions, curve counts, and batch sizes. The results are in Figures 2 and 3 . We can see that torchcurves is slower for small number of curves or small batch sizes, and in the ballpark or faster for larger scales. It is our conjecture that at smaller scales Python overhead wins, whereas for larger scales vectorized PyTorch code lets it exploit multiple cores, while NumPy and SciPy remain serial.
