The data must come from the Web, the strategy lives in the user’s head, and correctness depends on time, so an agent can fail silently: a strategy the user never asked for, unverified data, or a backtest that uses the future yields a report as convincing as a correct one. Existing benchmarks close the world somewhere, fixing the task, the data, or the timeline, and thereby remove these failures instead of measuring them. We introduce F i n C o s m o s , an open-world evaluation paradigm for agents doing financial work. A simulated user holds a hidden strategy sampled from a compositional grammar and reveals it only when asked. The agent receives no data, so it must acquire data from the Web, build its own backtest under a data cutoff, and deliver verifiable results. Grading needs no reference answer. Programs verify point-in-time correctness and recompute every reported metric, the delivered strategy is checked against the hidden specification, and a run is accepted only when the user is satisfied and none of 15 veto checks fails. Across four coding agents and a model without tools in 150 sessions, no session is accepted: every session that the simulated user signed off fails a program check, and agents raise only 54–64% of the details they were not told. Human experts attribute 88.33% of failures to the agents. With F i n C o s m o s feedback, an agent with persistent memory learned all ten tasks. 1  Introduction data/equity_curve.csv − - − - − - Figure 1 : A silent failure. The user is satisfied, yet the delivery gets the intent and the data wrong; only time is right. Language agents no longer just answer questions. They work for users in the open world, where the Web is both their source of information and their place of work [ 8 , 69 , 38 ] . Given a request, agents search for sources, call data APIs, write and run code, and hand back results that the user acts on but rarely checks. The question is no longer whether an agent can solve a task, but whether it can be trusted with one. Finance is where this question is hardest to answer and where a wrong answer costs the most. The data lives on the Web, not in the model. Prices, filings, and news are vast, numeric, and change every day, so an agent that relies on memory hallucinates the figures its results rest on, and even with retrieval, models still miscompute them [ 5 ] . The task intent lives in the user’s head. Few investors want quite the same strategy, and its details surface only when the agent asks [ 60 , 25 , 7 ] . Correctness lives in the point-in-time. A decision may use only what was public on its date, yet the Web keeps revising itself, so today’s data carries the future into the past. Each of these produces a silent failure , in which nothing crashes and the report looks as convincing as a correct one (Figure 1 ). Existing benchmarks each close the real world somewhere, and each closure removes a silent failure instead of measuring it. An agent given curated data, explicit user intent, and an enforced time cutoff never encounters these failures. As a result, none of them verifies what an agent delivers when the data, the user’s intent, and the timeline all stay open (Table 1 ). Closing the intent removes the strategy the user never asked for. Nearly every benchmark states the task in full at the start, whether it is a question over given filings [ 6 , 19 ] , a strategy to implement [ 53 , 65 ] , a research query [ 70 ] , a fact to find on the live Web [ 36 , 54 ] , or a shopper profile [ 23 ] . Simulated-user benchmarks do require elicitation, but over a closed database in customer-service workflows [ 60 , 2 ] . Closing the data removes the figure the agent never retrieved, since most financial benchmarks hand the agent curated documents or price series [ 57 , 39 ] . Closing the timeline removes the backtest that peeks ahead. Trading benchmarks replay history in their own environment or evaluate agents only in live markets [ 27 , 26 , 42 ] , so the agent never builds a backtest of its own, and they score realized returns, which are biased [ 28 ] and say little about whether the agent built what the user wanted [ 43 ] .
Only an evaluation that leaves all three open can tell whether an agent is ready to work for a real user. We introduce F i n C o s m o s , an open-world evaluation paradigm and the first framework that preserves the uncertainties of real financial work (implicit user intent, independently sourced Web data, and point-in-time constraints) and evaluates whether agents can deliver trustworthy results under these conditions (Figure 2 ).
A simulated user, played in one of three personas, holds a strategy specification and reveals each detail only when the agent asks, so eliciting the request becomes part of what is tested. Because a task needs only a specification and no reference answer, specifications are sampled from a compositional grammar over six strategy components, which yields about 3.8 million distinct strategies before parameter values are chosen, so new tasks can be drawn whenever a released set saturates or leaks.
Rather than working with curated data, the agent retrieves the data it needs from the open Web, and a fixed data cutoff turns respecting time into a property that can be checked rather than assumed.
To distinguish trustworthy deliveries from convincing but incorrect ones, the evaluation verifies the delivery itself rather than matching a reference.
Each run is graded on 45 dimensions, combining programmatic verification with checks of strategy fidelity against the hidden specification.
Programs check data provenance, point-in-time correctness, and whether reported metrics can be independently recomputed from the delivered trade log.
Fifteen dimensions serve as vetoes: a run is accepted only when the user is satisfied and none of these critical veto checks fails, so a silent failure cannot pass. We evaluate four general-purpose agents and a model without tools on ten frozen tasks, with three independent sessions per task and system (150 sessions total). F i n C o s m o s is far from saturated: no session is accepted, and pre-veto quality ranges only from 20.2 to 37.2 out of 100. Its grades are diagnostic. They locate where each agent breaks along the workflow: of the 120 agent sessions, 25 deliver the investor’s strategy, 15 of these also keep their data within the cutoff, 14 also backtest without look-ahead, and none delivers trades that reproduce its reported returns. Agents raise only 54–64% of the details they were not told and get 66–83% of the rest wrong. Its design is necessary. The investor signed off in 23% of sessions, and the vetoes an LLM judge decides would accept 11%, yet every one of these sessions fails a program check; grading by sign-off or by an LLM judge would also reorder the agents. Human experts attribute 88% of failed runs to the agent and agree with the LLM judge at κ = 0.87 \kappa=0.87 . Finally, F i n C o s m o s is solvable. With its leak-free feedback, an agent with persistent memory learned all ten tasks, none of which it passed at the first attempt. They range from trading agents with memory, tools, and multi-agent roles [ 61 , 64 , 62 , 56 , 59 ] to research agents that mine alphas, automate factor research, write reports [ 50 , 31 , 32 , 22 ] , and audit XBRL filings [ 14 , 52 ] . Each is evaluated in a setting its designers choose, and look-ahead errors slip in even there [ 32 ] . Benchmarks for these agents have moved from answers to workflows, but they still fix the request when the session starts. Question-answering benchmarks test reasoning over given reports and filings, across languages and modalities [ 6 , 19 , 58 , 57 , 39 ] , with results tracked on public leaderboards [ 33 ] . Their questions stay fixed even when they come from real users [ 13 ] . Research benchmarks open the data but pose fully specified questions, graded by accuracy or against expert ground truth [ 3 , 70 ] . Strategy benchmarks hand the agent a specification and curated data [ 53 , 65 ] , and AlphaOpsBench [ 21 ] starts from coarse hypotheses but offers no user to ask. Agent environments for enterprise decisions likewise pose fixed goals [ 15 ] . Trading benchmarks evaluate decisions in historical or live markets [ 27 , 26 , 42 ] , and some enforce point-in-time data inside their own pipelines [ 43 , 40 ] , so the agent never keeps time on its own. FinTrace [ 4 ] evaluates tool calls along the trajectory, but on predefined tasks. Each opens at most one of intent, data, and time (Table 1 ). 2.2  Open-World Agent Evaluation Outside finance, benchmarks open either the intent or the data, rarely both. Simulated users open the intent. τ \tau -bench [ 60 ] pairs a tool-using agent with an LLM-simulated user, and its successors add users who act on a shared environment [ 2 ] , full-duplex voice [ 44 ] , and a banking domain with a knowledge base and discoverable tools [ 46 ] . In all of them the user’s intent is hidden, but the world is closed: the agent works over a fixed database and is graded against a target state [ 41 , 25 , 49 ] .
In finance, benchmarks evaluate advisors and recommenders over multi-turn dialogue, including against a user’s latent utility [ 51 , 12 ] , but they grade decisions rather than verifiable research deliverables. The fidelity of simulated users is limited: success rates shift with the simulator model [ 45 ] , stronger assistants make weaker simulators [ 37 ] , and no LLM faithfully reproduces the decisions of individual investors [ 16 ] . F i n C o s m o s therefore uses its simulator as an examiner that discloses a hidden strategy under fixed rules, and validates it with human experts (Section 4.3 ). Web benchmarks open the environment instead. Agents are evaluated on sandboxed sites [ 69 ] , on recorded or live websites [ 8 ] , and on open-Web tasks with checkable answers [ 36 , 54 , 38 ] , but the task is stated in full, even when it is personalized [ 23 ] . Deep research benchmarks keep the output open and grade it with LLM judges [ 10 , 47 ] , which have known biases and can be gamed [ 66 , 67 , 35 ] , and flaws in tasks and grading can shift agent scores substantially [ 71 ] . Fixed task sets also go stale once models train on them, which LiveBench counters by refreshing its questions [ 55 ] and GDPevo by regenerating tasks [ 68 ] . F i n C o s m o s keeps both the user and the Web open, grades by program-verified invariants wherever possible, and samples new tasks from a grammar rather than a fixed pool. 2.3  Look-Ahead Bias in Financial Evaluation Backtests have long been known to overstate performance [ 1 ] , and LLMs add new routes for leakage. Models memorize financial values from before their training cutoff [ 11 , 34 ] , LLM trading agents can profit from leaked outcomes [ 30 ] , and effective cutoffs can lie months before the dates vendors report [ 20 ] . One line of remedies acts on the model, training it only on data before each date [ 9 , 17 ] or dampening memorized outcomes at inference [ 29 ] . Another targets the backtest: switching one convention at a time measures how much each inflates results [ 63 ] , LLM auditors flag clean backtests as rigged [ 48 ] , short evaluation windows overstate LLM strategies [ 28 ] , and few financial LLM papers discuss these biases at all [ 24 ] . These studies audit models or fixed pipelines. They can make a check fail and never make it pass. The agent is thus judged as a real user would judge it, by what it hands over. 3.2  Strategy Generator Strategy space. It separates who the user is (the persona) from what the user wants (the belief), and a disclosure policy fixes how the belief is revealed. Persona and belief. The persona pool has three personas: a retail investor, a generalist analyst, and a biotech specialist (Appendix D ). Their prompts forbid evaluation vocabulary, such as “point-in-time” and “cutoff”. The user states the date up to which data may be used in plain words, but never says that it will be checked. The belief b b enters the prompt as plain-language convictions with exact numbers, such as “cut to cash if the drawdown reaches 20%”, which the user holds and does not read out. Disclosure policy. Let H H be the set of items that the belief voices, one for each option and parameter value it states, and let H k ⊆ H H_{k}\subseteq H be the items of component k k . Parameter values that the belief does not state, such as the window of a volatility estimate, are not in H H , and the agent is never held to them. Let O ⊆ H O\subseteq H be the items in the opening request, and S t ⊆ H S_{t}\subseteq H the items the user has stated by turn t t , with S 0 = O S_{0}=O . The opening request is a single vague idea, so | O | ≪ | H | |O|\ll|H| . After that, the user states only what the agent raises: S t ∖ S t − 1 ⊆ Q ⁡ ( a t ) , S_{t}\setminus S_{t-1}\subseteq Q(a_{t}), (2) where Q ⁡ ( a t ) ⊆ H Q(a_{t})\subseteq H is the set of items that the agent asks about or proposes in turn t t . Asked for a specific value, the user gives it directly. When a proposal conflicts with b b , the user objects and says what it wants. When a deliverable deviates from b b , the user names the wrong part, such as the position sizing, without restating the strategy. The agent therefore learns the strategy only by asking the right questions. We write S = S n S=S_{n} for the items stated by the end of the session. The simulator is prompted to follow this policy, and the Evaluator measures S S from the user’s turns, with a phrase matcher and an LLM check for undecided items, rather than assuming it. Turn decisions and termination. In each turn, the simulator reads the conversation and the latest deliverables and returns a structured decision: an action, an observation for every goal that cites the supporting messages or files, and its next message. A program validates the decision before the message is sent (Appendix D ). The simulator may close the session only when every core goal is met with cited evidence: a backtest of this strategy on real data, whose return, Sharpe ratio, maximum drawdown, and number of trades trace back to trade dates and prices, and a report that covers the summary, method, results, and limitations. User satisfaction is thus a claim that can be checked against h h and D D . 3.4  Evaluator The Evaluator measures how well the agent served the user and tells it what to fix. Programs recompute numbers, an LLM judge grades only semantics, and every score carries its source and evidence. It grades a package built from D D (the full conversation, the last two reports, and the tables and code blocks in the delivered files) against b b , c c , and facts computed by programs. Dimensions. Each session is graded on 45 dimensions in seven categories (full rubric in Appendix B ). Five categories K K are scored: data (6 dimensions, 1 veto), strategy (12, 7), backtest (8, 4), assessment (5, 1), and user experience (6, 2). Their 37 dimensions each receive a score s j ∈ { 0 , … , 4 } s_{j}\in\{0,\dots,4\} , with an anchored description for every level. Cost (3 dimensions) and process transparency (5) are reported but not scored. Program judges grade 17 dimensions, an LLM judge 19, and both together 6, while the 3 cost dimensions are measured directly. Where an LLM grade has a program counterpart, the program bounds it, s j = min ⁡ ( s j LLM , s j P ) s_{j}=\min(s_{j}^{\mathrm{LLM}},s_{j}^{\mathrm{P}}) . A polished report therefore cannot hide a leaky or irreproducible backtest, while Q Q keeps the partial credit that a veto removes. Key checks. Four groups of checks target the three silent failures, and the last three carry most of the vetoes. Data provenance. The agent receives no data, so every series it delivers must be traceable to a source, such as a URL or an API call with its query parameters, and untraceable data earns no credit. Programs also measure missing values, gaps, duplicates, stale prices, and outliers in the delivered data (Appendix B ). Point-in-time correctness. F i n C o s m o s does not hide future data; avoiding look-ahead is the agent’s responsibility. Every dated row in the delivered data is dated no later than t cut t_{\mathrm{cut}} , and a single late row fails the veto. Every fill comes on a later date than its signal, and fundamentals used at entry were announced no later than the entry date. Independent recomputation. The program does not trust the reported equity curve. It rebuilds the returns from the delivered trade log, or from the weight log and prices, and compares every reported metric with its own value, within fixed tolerances such as 0.02 for returns and drawdowns and 0.5 for the Sharpe ratio. A missing trade log or price series fails the veto, and mismatches lower the score. Strategy fidelity and elicitation. An agent that never asks cannot earn full credit, but it is not failed for requirements that never came up. Feedback. After a session, the agent receives the score, source, and evidence of every dimension, such as the quotes matched, the files read, and the values recomputed. Section 5 reports the results. 4.1  Agents and Environment Agents. We evaluate four commonly used agents, each with a recent model from its vendor: Claude Code with Claude Opus 5.5, Codex with GPT-6.1 Sol, Gemini CLI with Gemini 3.8 Flash, and Kimi Code with Kimi K3 (open-weight model). Each agent brings its own harness, tools, and context management. As a baseline, Claude Opus 5.5 answers the same requests without tools. Memory features are off, so nothing carries over between sessions. Open-World Environment. Each session runs in a sandbox with a consistent runtime environment. Every agent receives the same environment and prompt settings. We provide the same prompt instructions, allowing agents to search for and retrieve web pages and run code in their working directory. We equipped the agents with the “Financial Modeling Prep” MCP server 2 2 2 https://site.financialmodelingprep.com/ , which contains 247 commonly used financial APIs to cover the data resources required for financial work. Search and web scraping tools are provided by the respective vendors; each session consists of up to six rounds, with each round lasting 300 seconds. All ten tasks involve U.S. stock trading, with portfolios ranging from a small basket of stocks to a specific sector or the entire market. Simulator and evaluator. The user simulator runs on Claude Opus 4.8 with low reasoning effort. It is told that the assistant has web and shell access, also for the bare model, which has neither. The LLM judge runs on Claude Opus 5.5 through the Claude CLI with its default settings. We limit the judge model bias risk in two ways. We use the ten tasks of the released benchmark. Each agent attempts every task three times in independent sessions. Metrics. Our primary metric is the acceptance rate , the share of sessions with AC = 1 \mathrm{AC}=1 (Equation 5 ). To measure reliability, we also report pass^ k k [ 60 ] , the probability that an agent is accepted in all of k k independent sessions on a task. With N = 3 N=3 sessions per task, of which N AC N_{\mathrm{AC}} are accepted, we estimate it as the mean of ( N AC k ) / ( N k ) \binom{N_{\mathrm{AC}}}{k}/\binom{N}{k} over tasks, for k ≤ 3 k\leq 3 . For every session, we also report the pre-veto quality Q Q (Equation 3 ) and the five category scores, which keep the partial credit that a veto removes. To show how agents fail, we report the share of sessions in which each veto fails and the distribution of end reasons (Appendix C ). The silent failure rate is the share of sessions that end with e = satisfied e=\texttt{satisfied} yet fail at least one veto, which we also break down by veto. As a counterfactual, we recompute acceptance from the LLM-judged dimensions alone, to measure how many of these sessions a judge would accept on its own. Two metrics describe how an agent handles the user. They use the item sets H H , O O , and S S of Section 3.3 , with S S recorded by the Evaluator. Because the user reveals details only when asked (Equation 2 ), the items in S ∖ O S\setminus O were elicited by the agent. The clarification coverage is | S ∖ O | / | H ∖ O | |S\setminus O|/|H\setminus O| . The assumption rate is the share of unstated items, H ∖ S H\setminus S , that the delivered strategy does not match. Because program judges score every turn, we also track how the score and the number of failed vetoes change over the turns of a session. Finally, we record the cost of each session: wall-clock time, tokens, tool calls, and turns. We test differences between agents with paired permutation tests over tasks, with Holm–Bonferroni correction. Learning from feedback. To test whether F i n C o s m o s feedback supports self-improvement, we set up a learnable agent in a “Claude + Memory” configuration: Claude Code with a memory that persists across sessions. After each graded session, a review step reads the leak-free report (Section 3.4 ) and the per-turn program scores, and edits the memory before the next session. Through these edits, the agent learns from the evaluator’s diagnosis of its failures, acquires new skills, and reuses past experience. It practices each of the ten tasks until its first acceptance. We count the sessions and the memory-editing learning steps it needs, compare the failed vetoes early and late in practice, and grade every accepted session under the current rubric. 4.3  Human Evaluation Study Two financial experts annotate the sessions of the main experiment to check whether the simulator, the LLM judge, and the evaluator can be trusted. Neither expert took part in building F i n C o s m o s . They complete three tasks: (1) Simulator fidelity. The experts label every user message as error-free, task-benign, or task-critical against the hidden strategy. A task-benign error is a slip that does not affect whether a correct agent is accepted. A task-critical error can prevent a correct agent from being accepted, for example contradicting the hidden strategy, revealing details that were not asked for, or ending the session against the evidence. (2) Judge agreement. On a calibration set of 30 of these sessions, the experts grade the four LLM-judged vetoes on the judge’s anchored 0–4 scale, and we compare their grades with the judge’s. (3) Failure attribution. For every failed veto, the experts mark whether its reason holds, and for every session, whether the first critical error came from the agent, the simulator, or the evaluator. Both experts label every item independently and resolve disagreements by discussion. We report Cohen’s κ \kappa on the calibration grades. The two strict completeness checks, process completeness (3.8) and the verifier audit (3.7), fail in nearly every session (120 and 119 of the 120 agent sessions) and do not separate the agents. Without them, 2 of the 150 sessions would be accepted, both by Codex: their returns can be partly rebuilt but do not match the report, and they fail no other veto. Their pre-veto quality is 50.8, against 21.0 for the other sessions of the four agents ( p < 0.001 p<0.001 , permutation test), and their user-experience score is 69.6, against 35.0. All 150 sessions are valid. The program validated every simulator decision before it reached the agent (Appendix D ). Grading failed for 2 sittings, which were rerun under the same conditions. The 60 annotated sessions comprise 13 for each of the four agents, covering all ten tasks, and 8 for the bare model, stratified by end reason within each agent. The calibration set takes three sessions per task from the four agents and covers the vetoes 2.7, 4.1, 5.1, and 5.6. Agent names are masked, and the experts see the automatic grades only after tasks (1) and (2) of Section 4.3 , when they check failed vetoes and attribute failures. Simulator. Both experts flag a task-critical simulator error in the same 3 of the 60 sampled sessions, most often the user ending the session while the agent was still working. The user walks away in 41 of the sampled sessions, so at most 3 of these exits are premature: the early endings of Section 5.3 mostly reflect agents that stall, not an impatient user. The experts attribute 53 of the 60 failed sessions (88%) to the agent, 3 (5%) to the simulator, and 4 (7%) to the evaluator, so the lack of accepted sessions reflects the agents, not the benchmark. Judge. On the calibration set, the LLM judge agrees with the experts at κ = 0.87 \kappa=0.87 , close to the two experts’ agreement ( κ = 0.93 \kappa=0.93 ). The judge is thus reliable on what it grades; the silent failures it lets through (Section 5.2 ) do not show in the conversation or report it reads, and only program checks on the delivery catch them. 5.5  Learning from Feedback F i n C o s m o s is built for agents that learn from feedback. A task can be attempted again, and each attempt returns a diagnostic, leak-free report together with per-turn program scores. Every score records the evaluator version that produced it, and the leaderboard records every attempt. Together, these provide the infrastructure for recursive self-improvement: an agent attempts a task, receives its grades, updates itself, and attempts again, while the hidden strategy stays sealed. The Claude + Memory agent uses this loop to learn tasks that it could not pass at first (Table 6 ). No task is accepted at the first attempt, and the median task fails 8 vetoes in its first session. Through practice, the agent reaches acceptance on all ten tasks, after a median of 34.5 sessions per task (range 12–132, 506 in total), and every accepted session passes all 15 vetoes under the current rubric. Practice reduces failures (Figure 3 ). For the median task, the agent fails 6.3 vetoes per session over its first five sessions and 2.6 over its last five before acceptance. Progress is not always smooth: on three short runs, the last five sessions fail as many vetoes as the first five or more, and the task is then passed in a single step. Throughout practice, the simulated user is satisfied in a median of 34% of the sessions, long before the deliverable passes the vetoes, which is the gap that Section 5.2 describes. The memory changes as the agent learns: of the 155 learning steps in the latest round, 115 (74%) edited the memory, with 4.5 edits per step on average. Through these edits, the agent learns the deliverables that the evaluator demands, such as a trade log with fill prices, a specification table for the six components, and diagnostics with numbers. The last veto to clear is most often strategy ambiguity (2.7), in 6 of 10 tasks. It fails in 77% of the 496 sessions before acceptance and in 28 of the 42 sessions that failed exactly one veto. Its reasons are withheld by the leak-free rule, so the agent must infer them from the user’s words. Learning from feedback is thus possible under the leak-free rule, and F i n C o s m o s supplies both the loop and its measurement. 6  Conclusion Agents doing financial work fail silently: an unrequested strategy, unverified data, or a backtest that uses the future produces a report as convincing as a correct one. F i n C o s m o s measures these failures by keeping the user’s intent, the data, and time open, and by grading deliverables against the hidden specification and against invariants that programs can verify. Our experiments show that no agent completes the workflow. Agents break most often at its two ends, pinning down the user’s strategy and delivering verifiable results, grading by user sign-off or by an LLM judge would count their silent failures as successes, and an agent can learn from F i n C o s m o s feedback. Limitations. The benchmark freezes ten tasks with three sessions per agent, and its grammar covers long-only US equity strategies with a fixed-cost model. The simulator, the judge, and one evaluated agent come from the same model family; program checks and expert annotation limit, but do not remove, this risk. Most agent turns hit the 300-second limit, so longer turns may let agents get further. Program checks cannot prove that every figure is real, and feedback scores can leak information about the hidden strategy across attempts, so leaderboard results should come from frozen agents. Ethics Statement. F i n C o s m o s uses only public Web data, collects no personal data, and evaluates research assistance, not investment advice. The two annotators are paid team members doing this as regular work; judging agent outputs is not human-subjects research. Not a valid session; never accepted. Appendix D User Simulator Details Personas. Each persona consists of a background prompt, a speaking style, focus areas, example utterances, and a list of forbidden terms. A retail investor uses finance terms confidently but often imprecisely. A generalist analyst speaks in a neutral, professional way and asks about metrics such as drawdown, turnover, and Sharpe ratio. A biotech specialist uses heavy industry jargon and thinks in terms of events such as catalysts and FDA decisions.
The forbidden terms include evaluation vocabulary such as “point-in-time” and “cutoff”. Disclosure rules. The simulator’s prompt implements Equation 2 with five rules.
(1) Open with a single vague idea.
(2) Answer only what is directly asked. What is not asked, the user cannot recall and does not volunteer.
(3) Asked for a specific value or method, such as a stop-loss threshold, give it directly rather than asking the agent to propose one.
(4) When a proposal conflicts with the belief, object and say what you want.
(5) When a deliverable deviates from the belief, name the piece that is off, such as the position sizing or the factor source, but do not restate the strategy.
The prompt also forbids assistant-like phrases such as “let me lock a few things”. Turn decisions. In each turn, the simulator reads the conversation and the agent’s most recent deliverables: at most 20 files, 8,000 characters per file, and 12,000 characters in total, with the budget going to the newest files first. Long conversations are compressed to the last six messages and a summary of the earlier ones. The decision contains an action, one observation per goal of the task, and the next message. The actions are clarify (answer the agent’s question), follow up (push unfinished work forward), challenge (point out a visible inconsistency), close , and block , which ends the session without satisfaction and records a reason, such as the agent giving up or the user walking away. Each observation marks its goal as met, missing, uncertain, or not applicable and cites the IDs of the supporting messages or files. In the released tasks, the core goal is a backtest report on the user’s strategy. Decision validation. A program checks every decision before its message is sent. It rejects a decision that leaves a goal unobserved, marks a goal as met without citing the agent’s messages or files, closes the session while a core goal is not met, raises a challenge or a block without evidence, uses internal vocabulary such as file names of the grading pipeline, asks for more work in a closing message, or repeats an earlier message verbatim. A rejected decision is regenerated with the reasons for rejection, up to six times. If no valid decision results, the simulator run is voided and the session does not count (Appendix C ). Parts of the strategy that the user was never given, and replies stopped at the 300-second limit, are marked. Phase 1: without grades. (1) Every user message receives one label. Error-free : consistent with the hidden strategy; the message adds a detail only when the agent asked about or proposed it, or names the wrong part of a deliverable without restating the strategy. Task-benign : a slip that cannot change whether a correct agent is accepted, such as odd wording or an improvised value for a detail the strategy leaves open. Task-critical : an error that can stop a correct agent from being accepted, such as contradicting the hidden strategy, volunteering details nobody asked for, signing off on a deliverable that visibly misses a stated requirement, or giving up while the agent is still making progress.
(2) On the calibration sessions, the experts grade the four LLM-judged vetoes (strategy ambiguity, grounded conclusions, conversation experience, and internal leak) on the judge’s anchored 0–4 scale, using only the conversation and the delivered files. Phase 2: with the evaluator’s verdict. After submitting Phase 1, the experts see the vetoes that each session failed, with the evaluator’s reasons. (3) For every failed veto, they mark whether the reason holds for the delivery and is a real problem for an investor, or is wrong, for example because it flags something the user asked for.
