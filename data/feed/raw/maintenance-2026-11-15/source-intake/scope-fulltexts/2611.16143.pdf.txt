Abstract—It is difficult to verify the claim that an agent 
based on a large language model (LLM) learns from its own 
experience. Performance improvements could stem from 
information retrieval, an increased number of attempts, or the 
use of reference target data accessed by the agent via its own 
memory. Therefore, this paper presents an audit of the 
evaluation process and the results of an investigation into a 
self-learning agent, designed for migrating databases from 
Oracle to PostgreSQL, that includes an assessment of the 
reliability of the evidence. The agent retains experience, adopts 
rules based on confidence-level weighting, and adapts its 
strategy without updating the weight coefficients. On 1,833 
documentation-derived 
Oracle–PostgreSQL 
pairs 
(367 
held-out units in 136 groups, Qwen3-Coder-480B), persistent 
memory raised reference conformity (RC) over a no-memory 
baseline by 0.015 [0.004, 0.025], and the adaptive policy added 
nothing (−0.004 [−0.010, 0.001]). The audit found that 72% of 
held-out units share their PostgreSQL reference with a 
training pair. On the 103 leak-free units the memory effect fell 
to 0.002 [−0.008, 0.011]. A model-free baseline that copies the 
target of the most similar training source reached RC 0.222 
and beat every LLM system (at most 0.163). On a new split 
grouped by reference, copying falls to 0.119, and a rerun on 
374 test units in 118 reference groups found no memory effect 
at group level (0.005 [−0.003, 0.017]) and no policy effect 
(0.000); 88% of the unit-level gain came from one reference 
shared by 42 test units. A study based on evaluating the 
execution of 216–224 real-world PL/SQL units using Oracle 
data revealed that PostgreSQL’s acceptance mechanism 
overestimates correctness (10–22% of accepted units were 
incorrect) and that an agent that does nothing performs well 
on metrics that reward silence. Employing a pre-registered, 
human-supervised correction loop increased the number of 
clearly correct results from 98 out of 216 to 167 out of 224. An 
analysis of the knowledge base update process (write-back) 
revealed that increasing the knowledge base size from 12 to 
1,200 entries reduces retrieval reliability margins by 54%. 
Based on these findings, we formulate six rules for evaluating 
claims regarding the learning capabilities of agents. 
Keywords—LLM agents, self-learning agents, experience 
memory, 
evaluation 
leakage,

conformity, 
execution-judged evaluation, Oracle-to-PostgreSQL migration 
I.​
INTRODUCTION 
A.​ Background and Motivation 
Agents based on LLMs are increasingly being used as 
tools 
for 
software 
development tasks that require 
consideration of repository context and iterative feedback 
[1]–[3]. Code translation and database migration are natural 
targets for such agents, because migration units are 
numerous, 
structurally 
repetitive, 
and 
linked 
by 
dependencies, yet they also contain dialect-specific behavior 
whose semantics fluent output can silently distort [4]–[6]. 
Oracle-to-PostgreSQL migration illustrates the difficulty. 
Oracle SQL and PL/SQL combine constructs such as NVL, 
DECODE, CONNECT BY, ROWNUM, MERGE, package state, 
autonomous transactions, and DBMS_* calls, each of which 
may require a context-dependent PostgreSQL idiom. Earlier 
work by the authors’ group examined a fine-tuned migration 
framework [7] and token-optimization strategies for 
Oracle-to-PostgreSQL migration [8]. Related work also 
addresses specification-driven synthesis for intelligent 
monitoring systems [9]. 
Feedback-driven 
agents 
improve outputs through 
reflection, 
self-refinement, 
execution 
feedback, 
or 
self-debugging [10]–[12]. In most of these methods, 
however, the improvement is task-local: the same task is 
attempted repeatedly, and the benefit disappears when the 
next task starts. Whether an agent becomes better on 
previously unseen migration tasks because of experience 
accumulated on other tasks is a distinct question, and it is 
rarely separated from retrieval of similar examples, copying 
of references, or simply spending more inference budget 
[13], [14]. 
Additional motivation comes from earlier research on 
knowledge 
acquisition. 
Situation-oriented 
ontologies 
organized reusable diagnostic knowledge based on context 
and relationships, while tools for working with tabular 
knowledge bases supported the process of their creation 
[15], [16]. In cases of migration, we apply only the 
principles of situational suitability and clearly defined 
provenance. These materials are not presented as a 
demonstration of agent training based on LLMs. 
Our initial plan was to demonstrate that such an agent 
learns. The plan changed as soon as the results came in. 
Memory did help, but the gains were almost entirely 
concentrated on stored items that were also referenced 
during training. A program that simply copies the nearest 
training target performed better than any LLM-based 
system. Thus, this article describes an agent, an audit that 
uncovered a problem, the remediation of a gap, and two 
laboratory studies demonstrating which specific aspects can 
be safely optimized through a learning loop. The agent 
remains a subject of scientific research, with the migration 
from Oracle to PostgreSQL serving as a test environment. 
B.​ Research Questions 
The core question is whether continuous, evidence-based 
learning from previous migration pairs provides an 
advantage on unseen tasks compared to static prompting, 
nearest-example retrieval, and task-specific local reflection, 
under the same base LLM and inference budget. We have 
 

broken this down into four research questions, one for each 
study: 
●​
RQ1 (Study 1): Do experience (memory) and an 
adaptive policy strategy improve alignment with 
reference patterns (on data not used for training) 
compared to baselines, and does each of these 
components contribute to this result? 
●​
RQ2 (Study 2): What proportion of the observed 
uplift remains after accounting for shared links and 
comparing 
against 
baseline copying metrics 
derived without the use of models—and how does 
the picture change when the data is grouped by 
reference target? 
●​
RQ3 (Study 3): When results are evaluated by 
executing them and comparing them against Oracle 
execution ground truth, what specific signals can 
the training loop rely on for optimization—without 
being misled? And does a human-supervised 
correction loop actually provide real value? 
●​
RQ4 (Study 4): Does the knowledge write-back 
mechanism remain reliable as the knowledge base 
grows? 
Studies 1 and 2 utilize the same dataset and the original 
execution protocols from Study 1. Additionally, Study 2 
involves a separate re-run of the agent on a sample 
generated using a reference-based grouping approach. 
Studies 3 and 4 are part of other laboratory projects and rely 
on their own distinct datasets. In each study, the answer to 
the research question is formulated within the framework of 
the respective approach, and these answers are synthesized 
in Section XI. 
C.​ Scope and Contributions 
Studies 1 and 2 utilize a single dataset derived from 
documentation. Since no executable Oracle instance is 
available for this dataset, the outcome is measured by 
alignment with reference data rather than by the correctness 
of behavior. Study 3 employs different toolkits that use 
actual Oracle output and a PostgreSQL database for 
verification. Study 4 is a controlled information retrieval 
experiment. The base model remains unchanged; we 
therefore characterize the mechanism as non-parametric 
continual adaptation. 
The article makes five contributions. First, it specifies an 
evidence-graded 
learning 
agent 
with 
tiers 
G0–G3, 
verifier-grounded admission and a checkpointed policy 
(Sections III–V). Second, it reports a full run of that agent 
with ablations and controls, including a null result for policy 
learning (Section VII). Third, it gives a leakage audit with 
model-free copy baselines and a checkpoint monitor, shows 
that the memory gain is mostly reference reuse, builds a 
split grouped by reference and reruns the agent on it 
(Section VIII). Fourth, it reports execution-judged evidence 
on what accepted, empty and judged outputs really mean 
(Section IX) and on write-back at scale (Section X). Fifth, it 
turns these results into rules for claims of agent learning 
(Section XI). 
II.​
RELATED WORK 
A.​ Feedback-Driven and Self-Improving Code Agents 
Reflexion stores verbal reflections in an episodic buffer 
to improve later attempts, and Self-Refine iterates on a 
single output using the model’s own critique [10], [11]. 
CodeRL and LEVER use execution outcomes to train or 
rerank code generation, and Self-Debug and LLMLOOP 
feed execution or test feedback back into repair loops [12], 
[17], [18]. LLMLOOP in particular packages iterative 
compilation, static analysis, and test feedback for generated 
code and tests [19]. These methods provide the task-local 
reflection baseline used here, but they do not by themselves 
establish that experience transfers across tasks. 
DSPy compiles declarative language-model pipelines 
and optimizes prompts or demonstrations against a metric, 
which makes it a relevant comparator for automatically 
optimized demonstrations [14]. Early-experience agent 
learning studies how agents can learn from self-generated 
interaction data without explicit reward signals [13]. The 
present study differs in that experience units are typed, 
evidence-graded, and admitted only through deterministic 
verifier outputs, and in that learning is measured on a frozen 
held-out panel. 
ExpeL collects experiences across tasks and distils them 
into insights [20], and Voyager keeps a growing skill library 
[21]. Agentic context engineering treats a playbook as a 
context that evolves through generation, reflection and 
curation, without weight updates [22]. These systems are 
closest to our design, and they share its main risk: the stored 
experience may simply encode answers to the evaluation 
tasks. 
B.​ Agentic Software Engineering and Evaluation 
SWE-agent shows that the design of the agent–computer 
interface strongly affects software-engineering performance, 
and 
SWE-bench established realistic repository-level 
evaluation 
[1], 
[2]. 
Analyses 
of 
LLM-based 
software-engineering 
agents 
argue 
for 
simple, 
well-understood 
baselines 
before 
complex 
agent 
architectures 
[3], 
and 
RepairAgent, 
MetaGPT, 
and 
SOEN-101 
illustrate 
autonomous 
repair, 
role-based 
multi-agent 
collaboration, 
and 
process-model-driven 
generation [23]–[25]. For validity, EvalPlus shows that 
limited test suites can overstate the correctness of generated 
code, SWT-Bench evaluates whether generated tests 
validate real-world fixes, and a study on the reliability and 
explainability of program-generation models documents 
related evaluation limitations [26]–[28]. 
Leakage between training and evaluation data is a 
known cause of over-optimistic results in machine-learning 
research [29]. LLM judges such as G-Eval help score 
open-ended output [30], but their stability on repeated calls 
is rarely reported. For migration, a hybrid decomposition 
framework from our group measured routing, repair and 
decomposition on 1,448 tasks and found that small samples 
can reverse a comparison [31]. A metric-based model of 
software functional state combines several metrics into one 
index 
over 
the development life cycle and adds 
non-compensatory rules, so that strong secondary metrics 
cannot hide a critical defect; it was validated on 15 merged 
open datasets and five release scenarios [32]. RC in Study 1 
is a compensatory composite of this kind, which is one 
reason why Studies 2 and 3 examine its parts separately. 
C.​ Specification Reconstruction, Translation, and 
Migration 
Explain-then-translate 
shows 
that 
self-generated 
explanations can improve program translation, which 
motivates an intermediate textual specification [33]. 
UniTrans combines test-case generation, translation, and 
iterative repair for code translation, and XCodeEval 
provides an execution-based multilingual benchmark that 
2 

includes translation [4], [5]. Work on repairing ambiguous 
problem descriptions highlights that underspecified inputs 
degrade generation, which parallels the risk of inventing 
business semantics during specification extraction [34]. A 
knowledge-graph-based 
framework 
for 
LLM-powered 
database migration addresses system evolution, although its 
relevance to Oracle-to-PostgreSQL relational migration 
must be assessed separately [6]. Neuro-symbolic feedback, 
in which symbolic checks constrain neural repair, is 
explored for vulnerability repair [35]. 
D.​ Knowledge Representation and Contextual Applicability 
Situation-oriented 
ontology 
construction 
and 
knowledge-base authoring software represent knowledge as 
contextual cases with typed relations [15], [16]. This is 
related to, but distinct from, neural parameter learning. In 
the present design every case stores positive and negative 
evidence, source and target provenance, a dependency 
neighborhood, applicability predicates, and the strongest 
verified evidence tier, and the memory can retract, 
supersede, and deactivate conflicting cases instead of 
accumulating every generated explanation. 
The 
presentation 
[36] 
introduces 
self-learning 
monitoring agents that maintain shared knowledge about 
evolving software and reports repository-level experiments. 
Its evidence is treated here as preliminary, not as 
independent validation of migration-agent learning. 
E.​ Gap Addressed 
Existing 
work 
offers 
task-local feedback loops, 
experiential agents, benchmarks and translation pipelines. 
We are not aware of a migration study that grades 
source–target pairs by evidence tier, measures cross-task 
gain against a fixed-policy memory control on a frozen 
panel, and then audits that gain for reference sharing and 
against model-free copying. We also report what happens 
when the same question is asked with execution against 
Oracle.

E.​ Original Split 
The configuration asked for a split by documentation 
family, but the split script did not apply it: every pair formed 
its own component, so the split was random at pair level. It 
produced 1,099 training, 367 validation and 367 test units; 
109 of the 136 test families also occur in training. Retrieval 
excluded experiences of the same family at inference. 
Targets were not part of the grouping: 141 of the 236 
distinct test targets also occur as training targets. Training 
used 311 of the 1,099 training units, in seven batches of up 
to 50. Section VIII-E describes the repaired split.

A.​ Experience Representation 
An experience is a typed record with an identifier, the 
originating 
training 
pair, 
source-specification 
and 
dependency features, the selected strategy, a transformation 
rule, the observed outcome, the evidence tier, applicability 
conditions,

negative

a

and a knowledge version. Negative examples and 
contraindications are first-class fields, so that the memory 
distinguishes positive from negative transfer and does not 
assume that a G1 pair proves behavioral correctness. 
In the implementation, an experience stores the agent's 
own generated PostgreSQL code for a training unit, not the 
reference. An experience counts as verified when its own 
verifier result is a binary success. 
B.​ Ten-Stage Learning Loop 
Fig. 5 depicts the intended full loop; Study 1 
implemented 
a 
reduced 
version 
without 
per-unit 
specifications or a code-level dependency graph (Section 
IV). For each task, the agent (1) observes source-derived 
features, the dependency neighborhood, and applicable 
training examples; (2) retrieves with hybrid lexical, AST, 
and graph signals plus optional semantic ranking, excluding 
the current held-out target, task aliases, and duplicates; (3) 
selects among direct, source-spec-first, example-assisted, 
and dependency-decomposed migration, logging scores and 
rationale; (4) generates candidate PostgreSQL without 
reference leakage; and (5) verifies with parser, schema, and 
static dependency checks, optionally with PostgreSQL 
deployment, comparing to allowed references for training 
pairs only.

deprecation; (8) updates the policy; (9) consolidates 
duplicate patterns while separating positive and negative

The leakage audit and model-free comparisons in Study

E.​ Study 3: Execution-Judged Evaluation 
Study 3 comes from the lab's migration agent, which 
translates Oracle PL/SQL with a production routing 
(DeepSeek-V4-Flash, escalating to DeepSeek-V4-Pro). 
These names identify the reported routing choices; the 
specific provider-resolved model release for each run is not 
documented in this manuscript. Its corpus has 34 Oracle 
files with 216 units, later 224. Each unit is installed in a 
PostgreSQL validation database in dependency order and 
run against scenarios. Oracle ground truth comes from 
captured Oracle transcripts and, for disputed cases, from 
execution on an Oracle Database Free container. A unit is 
demonstrably correct when it is accepted and Oracle's own 
output and errors do not contradict it, or when it fails with 
exactly the error Oracle raises. Every change to the prompt 
or harness went through a pre-registered fix cycle: one 
change per arm, predicates written before the run, and 
promote, revert or hold decided against the real artifacts. We 
also ran a do-nothing agent beside every reported number.

B.​ A Gated Fix Cycle as Supervised Admission 
The fix cycle is a manual form of the admission step in 
Section V-C. Each candidate change is one prompt 
paragraph or one harness fix, tested on the full corpus 
against predicates written in advance, and kept only if the 
generated SQL shows the intended effect. Fig. 14 shows the 
do-nothing comparison and the progress of the cycle. 
 
Fig. 14. Study 3: (a) exact behavioural matches of a do-nothing script and 
the agent on 20 curated units; (b) demonstrably correct units over prompt 
versions (v77: range of three runs). 
Over about four weeks the count of demonstrably correct 
units rose from 98 of 216 to 167 of 224. Harness fixes 
explain much of this rise. One resolver defect alone blocked 
21 groups, 57% of the blocked cascade, and four harness 
fixes that cost no tokens raised the migrated units from 53 to 
74. Prompt fixes moved the ceiling one construct at a time, 
for example SELECT INTO STRICT for Oracle's 
NO_DATA_FOUND, TIMESTAMP(0) for Oracle DATE, 
cursor expressions, and OUT and IN OUT parameters. 
Many fixes were partial: a correct fix often exposed the next 
defect behind it. One fix produced five new accepted units 
that were all wrong; a whole-file comparison with Oracle 
output caught them. Two runs of the same configuration 
differed by about 10 units, so a single run is a point 
estimate.

XI.​
DISCUSSION 
A.​ Answers to the Research Questions 
RQ1. Memory raised RC on the full panel, but neither 
admission nor policy adaptation added anything, and the 
policy collapsed into one global switch. H1 and H4 were not 
supported, H2 and H3 could not be tested, and H5 was 
inconclusive. RQ2. Almost all of the memory gain sat on 
units that share a reference with training, and copying the 
nearest training target beat every LLM system. On leak-free 
units the agent beat copying but did not beat the no-memory 
baseline. A split grouped by reference closes this path and 
lowers the copy floor to 0.119. The rerun on it found no 
memory or policy effect at group level, with enough power 
to detect 0.018. RQ3. Under execution against Oracle, 
acceptance and silence-rewarding metrics mislead, and a 
single LLM judge is unstable. A gated cycle with human 
verdicts did accumulate gains, mostly by fixing the harness. 
RQ4. Write-back works at once and without regressions at 
small scale, but the safety margin shrinks as the base grows 
and depends on the embedding model. 
A related conference presentation by one of the authors 
[36] reports experiments on five Python repositories. 
Monitoring adaptation reduced detection lag for all five 
systems, but improved F1 only for three with lower import 
coupling and reduced F1 for two with higher coupling. 
These presentation-level results are not pooled with our 
migration experiments; they illustrate why averages can 
conceal negative transfer. 
B.​ Rules for Claims of Agent Learning 
The Study 3 harness reached the same conclusion as the 
non-compensatory rules in [32] by a different route: it 
reports four separate categories per unit and never a blended 
score, because each single number it tried rewarded the 
wrong behaviour. We draw six rules from the four studies: 
●​
Group splits by reference target as well as by 
source; report how many held-out references occur 
in training. 
●​
Report a model-free copy baseline next to every 
learning curve; a gain below copying is not 
evidence of learning. 
●​
Score a do-nothing agent beside every metric 
before trusting it. 
●​
Count only verdicts that resolved their references; 
acceptance by the target system alone is not 
correctness. 
●​
Repeat LLM-judge calls and report verdict churn; 
one call at temperature 0 is not deterministic. 
●​
Report the state behind the curve: verified entries, 
distinct examples shown, policy entropy and 
admitted rules. 
Applied to Study 1, the rules turn a positive-looking 
result into a null result for learning. Applied to Study 3, they 
make the reported gains believable, because each gain is 
tied to a pre-registered change and read against Oracle 
output. The first two rules cost no model calls, and Section 
VIII shows that both can be applied to a finished run.

​CONCLUSIONS 
We built an evidence-graded self-learning agent for 
Oracle-to-PostgreSQL migration and tested whether it 
learns. On a documentation-derived corpus, memory raised 
reference conformity by 0.015, admission and policy 
adaptation added nothing, and the policy collapsed to one 
strategy. An audit showed that 72% of held-out units shared 
their reference with training. On leak-free units the memory 
gain disappeared, and copying the nearest training target 
beat every LLM system on the full panel. The answer to the 
title question is therefore no for this corpus. 
A split grouped by reference removes the leak and 
lowers the copy floor from 0.222 to 0.119. A rerun on it 
found no memory effect (0.005 [−0.003, 0.017]) and no 
policy effect at the level of 118 independent reference 
groups; the unit-weighted gain of 0.029 came almost 
entirely from one reference shared by 42 units. The lab 
studies show what a sound learning signal needs. Judged by 
execution against Oracle, a pre-registered, human-gated fix 
cycle raised demonstrably correct units from 98 of 216 to 
167 of 224, while acceptance, silence and single judge calls 
would each have misled an automatic loop. Write-back of 
corrections works but loses margin as the knowledge base 
grows. 
Future work will review a stratified sample of pairs, 
rerun the remaining systems on the reference-grouped split, 
run the agent with per-unit source specifications, and 
replace the reference-conformity signal with execution 
evidence from the Study 3 harness, so that an automatic 
proposer can draft fixes while the gate keeps the verdicts.
