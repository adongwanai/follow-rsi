Flex-RSI: Benchmarking Recursive Self-Improvement of Frontier Agents

Flex-RSI: Benchmarking Recursive Self-Improvement of Frontier Agents

Frontier language models are increasingly deployed as agents, and how well an agent performs depends not only
on its model but also on its harness: the prompts, tools, memory, and control loop through which the model acts.
When an agent is applied to a new problem, a natural question is whether it can use the feedback of the task to
improve the way it works, and not merely its answer. Most existing benchmarks keep the agent’s harness fixed and score
the solution it produces, or target large-scale model training. We introduce Flex-RSI, a benchmark for the recursive
self-improvement of agents on vision and robotics tasks under a fixed budget. In each round, an executor improves
the task solution, which is kept only if it scores higher on held-out validation data, and an improver then revises
the harness, including the executor and itself. Every run starts from the same general-purpose harness, and the
final solution is scored on hidden test data. Evaluating closed-source and open-weight models on tasks spanning
perception, reasoning, robot action, 3D reconstruction, visual creation, and infrastructure, we find that
self-improvement helps most when the agent builds its own solution, that feedback recording only success or failure
holds back open-weight models, and that open-weight models fall furthest behind where outputs must pass strict checks
of physical stability or exact correctness. Paired runs further show that editing the harness itself contributes to
the gains.

1 Introduction

Frontier large language models now routinely act as agents that write code, conduct experiments, and read the results
over multiple steps ( Anthropic, 2026a ; OpenAI, 2026b ; Google DeepMind, 2026 ; Qwen Team, 2026b ; DeepSeek-AI, 2026 ; GLM-5 Team, 2026 ) .
An agent’s performance depends not only on the underlying model but also on its harness : the prompts, tools,
memory, and control loop through which the model acts. This raises a practical question for anyone who deploys an
agent on a new problem: given only the task, can the agent use the task’s feedback to improve the way it works under a fixed budget, and not merely its answer?

Most existing benchmarks run each model inside a fixed harness, often the vendor’s own, and score only the solution
or artifact it produces, mostly on machine-learning research tasks with a continuous
metric ( Chan et al., 2025 ; Wijk et al., 2024 ) ; those that also let the agent revise its
harness ( RSI-Exam Team, 2026 ) or that center on upstream model training at scale ( OpenRSI Foundation, 2026 ) remain within
machine-learning research. We introduce Flex-RSI to measure how well a frontier agent improves both its solution and
its own harness on
general vision and robotics tasks, a setting in which agents are increasingly deployed, each attempt consumes real
compute, and the goal is a better solution within hours to days.

In Flex-RSI, the harness consists of two components that alternate over rounds ( Figure 1 a). The executor improves the task solution: it modifies the solution, runs experiments, and evaluates them on the labeled
development data, and its candidate is kept only if it also scores higher on held-out validation data. The improver then reviews the round and modifies the harness itself, including the executor’s prompts, tools, and
workflow as well as its own prompts, settings, and lessons. Every run starts from the same general-purpose harness
and, on each task, the same starter solution.

The tasks differ in what the agent must produce (a single answer or a solution it builds), how the evaluator scores
it (on a scale or only as success or failure), and how strictly the output is checked.
From experiments on 24 tasks spanning perception, reasoning, robot action, 3D reconstruction, visual creation, and
infrastructure ( Figure 1 b), with 18 closed-source and open-weight models, we find:

1. Tasks in which the agent builds the solution leave more room for self-improvement: tasks whose
solution is a single answer to each question leave little room to improve, while tasks in which the agent builds its own solution leave the most, and there models
pull apart ( Figure 1 c).

2 Related work

2.1 Benchmarks for self-improving agents

Benchmarks for machine-learning engineering and scientific research measure whether agents can turn a task
description into a working result. MLE-bench evaluates machine-learning engineering on competition
tasks ( Chan et al., 2025 ) ; RE-Bench compares agents with human experts on research-engineering
problems ( Wijk et al., 2024 ) ; and PaperBench assesses the replication of machine-learning
research ( Starace et al., 2025 ) . Related evaluations examine the design and execution of machine-learning
experiments ( Huang et al., 2023b ) and the generation of executable programs for data-driven scientific
discovery ( Chen et al., 2025 ) . Their primary evaluation targets are the models, code,
and research results that an agent produces.

Evaluations framed around recursive self-improvement cover several different objects of improvement.
RSI-Exam supports executable research on both task methods and harnesses for frozen models, followed by hidden-test
evaluation ( RSI-Exam Team, 2026 ) . OpenRSI Index spans foundation-model development, including large-scale training
and lighter-weight inference, agent, and systems tasks ( OpenRSI Foundation, 2026 ) . Autonomous post-training is evaluated
through controlled training runs and assessments of the resulting
models ( Rank et al., 2026 ; Huang et al., 2026c ) ,
while algorithm-design tasks ask agents to improve training procedures that are subsequently evaluated by
retraining ( Chi et al., 2026 ) .
Sustained machine-learning research with repeated validation feedback and a separate hidden test is evaluated
in AutoResearchExam ( Ramesh et al., 2026 ) . Harness engineering also appears alongside model-training
tasks in Vals RSI Index ( Chen et al., 2026b ) . TraceTrial-Bench evaluates the reliability of agent harnesses
themselves rather than their improvement ( Cao et al., 2026 ) .
These settings share an interest in autonomous experimentation, but differ in whether the optimized artifact
is data, a training algorithm, model weights, or the harness around a model.

Complementary studies examine how experience becomes reusable improvement. Data-centric research under a fixed
post-training stack is studied in RSIBench-Data ( Meng et al., 2026 ) . Procedural-ability transfer and the
conversion of episodic experience into reusable skills are evaluated in EvoAgentBench ( Gao et al., 2026b ) and SkillEvolBench ( Lei et al., 2026 ) , respectively.
EvolveTool-Bench checks whether evolved tools satisfy independent conformance tests beyond completing the
current task ( Kaliyev and
Maryanskyy, 2026 ) .
The contribution of persistent experience to later personal-agent behavior is isolated through matched
persistence-on/off comparisons in PAST-Bench ( Xue et al., 2026 ) .
Whether self-evolving language-model agents learn new tasks without forgetting earlier ones is evaluated in a
related study ( Chen et al., 2026e ) . EmbodiedCLBench evaluates whether embodied agents can reuse the experience gained
on basic tasks to solve unseen compositions of them ( Huang et al., 2026b ) ,
and Embodied Skill Bench measures how packaged embodied skills help agents on physical tasks ( Han et al., 2026c ) . Together, these studies motivate evaluating both
immediate task gains and improvements that
remain useful on subsequent tasks.

Flex-RSI studies task-solution and harness improvement together on vision, robotics, and related downstream tasks.
For each task, every model starts from the same general-purpose harness and starter solution, then alternates
execution and harness revision under a fixed budget. The improver can edit the executor’s prompts, tools, and
workflow as well as its own prompts, settings, and lessons. This shared protocol separates three questions: how much the task solution
improves, what additional gains come from editing the harness, and whether a harness built by one model helps another
model on the same task. A review of the evidence behind recursive self-improvement claims finds that few
studies compare improvement procedures from identical starting artifacts at a matched budget ( Chen et al., 2026g ) ;
the paired runs with and without the improver ( Section 5.4 ) make this comparison.

2.2 Frontier agents

Language-model agents connect reasoning to actions and environmental feedback through an execution loop.
ReAct interleaves reasoning and tool use ( Yao et al., 2023 ) , Reflexion carries verbal feedback into subsequent
trials through episodic memory ( Shinn et al., 2023 ) , and Voyager accumulates executable skills through
open-ended interaction in Minecraft ( Wang et al., 2023 ) . Coding interfaces such as Claude Code and Codex CLI
expose file editing and command execution ( Anthropic, 2026c ; OpenAI, 2026d ) . OpenHands provides
infrastructure for software-development agents ( Wang et al., 2025b ) , while SWE-agent studies how an
agent–computer interface supports repository navigation, editing, and testing ( Yang et al., 2024 ) . Research
agents extend these capabilities to experimentation: AIDE searches over candidate
solution code ( Jiang et al., 2025 ) , and The AI Scientist combines research ideation, experiments, paper writing,
and review in an automated workflow ( Lu et al., 2024 ) . Frontier models have also been evaluated as robot agents that act in the control
loop ( Huang et al., 2026a ; Zhou et al., 2026b ; Yao et al., 2026c ) or write reusable robot tools ( Ge et al., 2026 ) , across
many embodiments ( Yang et al., 2026b ) and against learned policies ( Zhang et al., 2026f ) , and coding agents
have been asked to reconstruct dynamic scenes as executable graphics programs ( Shen et al., 2026a ) .

Automated agent design makes parts of this execution machinery optimization variables. Promptbreeder evolves
both task prompts and the mutation prompts that revise them ( Fernando et al., 2023 ) , while GEPA uses
reflection on execution traces to propose and select prompt updates ( Agrawal et al., 2026 ) . ADAS searches over
agent programs using an archive of prior designs ( Hu et al., 2025 ) , and AFlow searches over code-represented
workflows ( Zhang et al., 2025b ) . A builder model can also learn principles for constructing the execution
environment of a fixed target model ( Qian et al., 2026 ) . AlphaEvolve applies
evolutionary program search to scientific and algorithmic discovery, with executable evaluators selecting candidate
task programs ( Novikov et al., 2025 ) . These approaches optimize objects ranging from prompts to complete
programs, with different boundaries around the optimization procedure itself.

Self-modifying agents extend this search to their own implementations. STOP applies its code improver to the
improver itself ( Zelikman et al., 2024 ) ; Gödel Agent and SICA likewise revise agent logic and orchestration
code ( Yin et al., 2025 ; Robeyns et al., 2025 ) . The Darwin Gödel Machine retains an archive of empirically evaluated,
self-modified agents ( Zhang et al., 2025a ) , while the Huxley–Gödel Machine also considers
a candidate’s potential to produce better descendants ( Wang et al., 2026d ) . Meta-Harness searches harness code
using previous candidates, scores, and execution traces ( Lee et al., 2026b ) . RHI represents the harness as a
prompt-level specification of the agent loop and refines it using pairwise feedback over its own revision
history ( Lee et al., 2026a ) . Self-Harness uses execution failures
to guide revisions to the model’s own harness ( Zhang et al., 2026a ) , and AIDE 2 recursively revises research-agent
code ( Srikanth et al., 2026 ) .

Several systems explicitly distinguish task improvement from improvement of the process that produces it.
Hyperagents combine a task agent and a meta agent in a shared editable program, allowing the self-modification
mechanism itself to evolve and studying transfer of meta-level improvements ( Zhang et al., 2026b ) . HSI
separates a task harness, an evolver, and a meta-evolver under a fixed outer anchor ( Zhou, 2026 ) .
In robotics, RegenHarness revises harness configuration from execution records, with regression checks and release
gates governing acceptance ( Wang et al., 2026a ) . Harness evolution around frozen models now spans video
understanding ( Luo et al., 2026 ; Liang et al., 2026 ; Lin et al., 2026 ) , image generation with a frozen
generator ( Han et al., 2026a ) , 3D reconstruction ( Yao et al., 2026a ) , and embodied agents, including robot manipulation, where the
harness is revised from diagnosed execution failures ( Tian et al., 2026a ; Feng et al., 2026 ; Yu et al., 2026b ; Du et al., 2026 ) ,
experience is organized into knowledge or executable stacks shared across tasks ( Bao et al., 2026 ; Chen et al., 2026f ; Wen et al., 2026 ) ,
the system decides where to spend robot trials ( Song et al., 2026 ) ,
and changes are tested in simulation before they reach the robot ( Hu et al., 2026 ) .
Studies of these loops find that the number of rollouts the optimizer sees in each round and the selection rule
determine whether an evolved robot harness generalizes ( Wei et al., 2026b ) , that accepting any edit that raises an
aggregate validation score admits regressions and favors noise ( Wang et al., 2026e ) , that proxy improvements need not
hold where the update is deployed ( Wang et al., 2026b ) , and that an exact validation score after every attempt
opens the validation split to adaptive selection ( Yao et al., 2026b ) . RRSI addresses the risk that harness
evolution overfits its training tasks, with gains that shrink or vanish on out-of-distribution benchmarks, by
constraining how edits are proposed and selected ( Xia et al., 2026 ) . Other studies ask which failures harness
evolution can repair and when weight training should take over ( Tian et al., 2026b ; Wang et al., 2026c ) , argue that
rewriting the scaffold around frozen weights avoids diminishing returns but not an eventual
ceiling ( Bobadilla-Suarez et al., 2026 ) ,
and report that weak evaluators and early failures in long skill chains stall improvement over long robot
runs ( Wang, 2026 ) . Surveys organize these developments by the components that evolve and the feedback
that drives their updates ( Gao et al., 2026a ; Fang et al., 2025 ; Chen et al., 2026a ) , and recent surveys and position papers cover
recursive self-improvement in physical AI ( Han et al., 2026b ; Zhou et al., 2026a ) , agent harnesses for video
generation ( Fan et al., 2026 ) , and the use of frontier models for 3D modeling, computational design, and
robotics ( Dou et al., 2026 ) .

These systems propose particular ways to accumulate experience, search for agent designs, or revise an improvement
procedure. Flex-RSI evaluates the ability to make such revisions through a shared executor–improver harness
( Section 3.2 ). Each frontier model operates both components from the same initial harness and, on
each task, the same starter solution and budget. The executor changes the task solution; the improver changes the
executor and its own instructions and lessons. The evaluator, data splits, and budget accounting remain fixed.
This setting makes the model’s capacity to improve its operating machinery the object of comparison across vision,
robotics, and related tasks, while keeping changes to the solution distinct from changes to the harness.

2.3 Flex-RSI tasks

Flex-RSI draws its 24 tasks from six areas, combining established benchmarks, source datasets, and our own
curated creation tasks. Table 1 summarizes their sources and metrics. Each task provides a starter
solution, development data, hidden validation and test splits, and a fixed improvement budget, so that these
resources support the evaluation of changes to both task solutions and agent harnesses.

Action

The manipulation tasks use simulated environments from RoboDojo ( Chen et al., 2026d ) and RoboCasa365 ( Nasiriany et al., 2026 ) , which
extends RoboCasa’s household simulation platform ( Nasiriany et al., 2024 ) . Active Search uses H*Bench’s panoramic environments
for visual search ( Yu et al., 2026a ) , while RoboLab uses the RoboLab-120 suite to evaluate a generalist tabletop manipulation
policy ( Yang et al., 2026a ) . The LIBERO-based tasks ( Liu et al., 2023 ) examine robustness to changes in initial conditions and task
specifications through LIBERO-PRO ( Zhou et al., 2025 ) , and adaptation to changes during execution through LIBERO-MAX ( Zhang et al., 2026e ) . Embodied-SWE draws on EmbodiedSWE-Bench, where agents write robot-control programs and receive
scores based on physical task progress ( Shen et al., 2026b ) . Related simulation benchmarks extend such
evaluation to whole-body humanoid loco-manipulation, as in SIMPLE ( Wei et al., 2026a ) .

Reasoning

Ego-Exo Memory uses the Ego-Exo4D portion of EgoExoMem for memory reasoning across synchronized first- and
third-person videos ( Liu et al., 2026b ; Grauman et al., 2024 ) . Kinematics uses QuantiPhy to infer physical quantities such as sizes,
velocities, and accelerations from video ( Puyin et al., 2026 ) ; Mass adapts product photographs and metadata from Amazon
Berkeley Objects for weight estimation ( Collins et al., 2022 ) . Abstract reasoning spans grid transformations
in ARC-AGI-1 and ARC-AGI-2 ( Chollet, 2019 ; Chollet et al., 2025 ) and interactive exploration in ARC-AGI-3 ( ARC Prize Foundation, 2026 ) . Spatial-VSI
uses VSI-Bench’s spatial questions about indoor videos ( Yang et al., 2025 ) .

Creation

Image Editing uses our own curated images and editing instructions, and Text-to-Image uses original Chinese and
English prompts. Multi-turn Editing follows the five-turn sessions of MSE-Bench, introduced with VINCIE, in which
each instruction acts on the previous result ( Qu et al., 2026 ) . Video Generation uses the compositional prompts and
evaluation criteria of T2V-CompBench ( Sun et al., 2025 ) .

Reconstruction

3D Tracking adapts IGGT’s instance-tracking setting ( Li et al., 2026 ) on ScanNet and ScanNet++ ( Dai et al., 2017 ; Yeshwanth et al., 2023 ) . Scene from
Photo uses HARMONY300, introduced with HARMONY for reconstructing furnished rooms from single images ( Sun et al., 2026 ) ;
its synthetic scenes derive from 3D-FRONT ( Fu et al., 2021 ) . Scene from Video uses the indoor scenes released with HoloScene ( Xia et al., 2025 ) , drawn from Replica and
ScanNet++ ( Straub et al., 2019 ; Yeshwanth et al., 2023 ) , together with CoDimRecon’s geometry, rendering,
and physical-stability evaluation setting ( Xie et al., 2026 ) .

Perception

Visual Search combines high-resolution questions from V*Bench and HR-Bench 8K ( Wu and Xie, 2024 ; Wang et al., 2025a ) . Video Quality
combines subjective quality scores for YouTube-UGC videos ( Wang et al., 2019 ; Yim et al., 2020 ) with human preferences
on generated-video pairs from Rapidata’s Veo 3.1 comparison dataset ( Rapidata, 2025 ) .

Infrastructure

VAE Decode uses the variational autoencoder released with MiniMax H3 ( MiniMax, 2026b ) and asks the agent to accelerate its
decoder while preserving the reference outputs on unseen inputs.

3 Flex-RSI

Flex-RSI evaluates whether an agent, given a task and a fixed budget, can improve not only its solution to the task
but also the harness through which it operates. We first define the task setting ( Section 3.1 ), then the
self-improving harness ( Section 3.2 ), and finally how runs are evaluated ( Section 3.3 ).

3.1 Problem setup

Each task provides the agent with a starter solution, compute resources, a budget, and data partitioned into
three disjoint splits. The development split , including its labels, is available to the agent for
experimentation and evaluation. The validation split is withheld from the agent and determines which candidate
solutions are retained. The test split is likewise withheld and is used only once, after the run terminates,
to evaluate the final solution. The objective of the agent is to maximize the test score of its final solution within
the budget.

On a given task, every run starts from the same starter solution and is subject to the same budget, which limits
wall-clock time, GPU hours, model usage, the number of validation evaluations, and the number of rounds. The 24 tasks are listed in Table 1 and described in Appendix A .

3.2 The self-improving harness

A harness is the program that mediates between a language model and a task. Through its prompts, tools, control
loop, and memory, it determines the context presented to the model and the actions available to it. Since the harness
consists of code and text, the agent can modify it in the same manner as any other program, while the model weights
remain fixed. In Flex-RSI, the harness H = ( E , I ) H=(E,I) comprises two components that query the same model. The executor E E operates on the task solution: it modifies the solution, conducts experiments, and evaluates the
results on the development split. The improver I I operates on the harness: it analyses the executor’s
trajectories and results, diagnoses failures, and revises the prompts, tools, and workflow of the executor as well as
its own instructions and accumulated lessons.

The evaluator S S , the data splits, and the accounting of the budget are fixed and cannot be modified by the agent.
Differences between runs can therefore be attributed to the agents themselves, and runs of different models on the
same task are directly comparable.

3.3 Evaluation

We report the test score of the final solution, S ⁡ ( s T , 𝒟 test ) S(s_{T};\mathcal{D}_{\mathrm{test}}) , and its improvement over the
starter solution, S ⁡ ( s T , 𝒟 test ) − S ⁡ ( s 0 , 𝒟 test ) S(s_{T};\mathcal{D}_{\mathrm{test}})-S(s_{0};\mathcal{D}_{\mathrm{test}}) . Agent code is executed
in a sandbox without access to the validation or test data, so no run can read the held-out data.

4 Experiments

This section reports what the agents achieve, in the order in which a reader would ask about it: how well each model
does over all tasks and within each area ( Section 4.2 ), how much of that is due to self-improvement
( Section 4.3 ), in which rounds the gains arrive ( Section 4.4 ), and what they cost
( Section 4.5 ). It reports what happens; Section 5 examines why.

How results are reported

Each model is run once on each task it is evaluated on; where a run was repeated, the latest run is reported.
RoboDojo and RoboCasa are suites of 10 and 8 robot tasks, each run separately for 10 rounds and aggregated into one
suite score. A run’s result is the test score of its final solution on the task’s primary metric, on a 0–100 scale.
Because the metrics differ across tasks, models are compared through ranks: on each task, a model scores the share of
the other models evaluated on the task that it beats, from 0 (last) to 100 (first). Its score in an area is the mean
over the tasks of the area it was run on, and its overall score is the mean of its five area scores. To measure
self-improvement itself, we also report the validation score of the starter solution and the best validation score
reached during the run. The main results cover the 20 tasks evaluated with at least six models; the four tasks
evaluated with two models so far are reported in Table 12 .

4.3 How much self-improvement adds

The scores above combine what a model can do from the start with what it gains by improving. Figure 3 separates the two by comparing the starter’s validation score with the best validation score reached during the run.
Self-improvement raises the validation score in 150 of the 177 runs (85%), by a median of 10.4 points.

The gain depends on how much the task leaves to build. It is largest where the agent builds most of its solution
from a weak starter: on 3D Tracking, RoboLab and Active Search the median validation score rises from 19.4, 8.3 and
23.0 to 62.2, 45.8 and 52.7 ( Figure 3(a) ). It is smallest where the starter already solves most of the task, as
on ARC-AGI-1 and ARC-AGI-2 (median starter 91.9 and 82.5, a median gain of 0 points on both). Two tasks do not fit this
pattern: ARC-AGI-3 and Scene from Video start low (3.8 and 17.3) and still barely improve (to 4.1 and 18.5).

The gain also depends on the model. Closed-source models improve more often and by more: they raise the validation
score in 94% of their 85 runs, by a median of 14.9 points, against 76% of 92 runs and 8.5 points for open-weight
models. Per model ( Figure 3(b) ), the mean gain ranges from 26.7 points for Claude Opus 5.5 and 25.7 for
Gemini 4 Argon to 6.8 for Gemma-4-31B-it, and the four models with the highest scores in Figure 2(a) have four of the five largest gains.

4.5 Cost

Runs differ widely in what they spend. A run on one task, counting each robot task of RoboDojo and RoboCasa
separately, uses a median of 49.7 million tokens, and the middle 80% of runs use between 8.6 and 93.4 million. We
compare tokens rather than prices, since the open-weight models are served on our own GPUs. To compare models on the
same footing, Figure 4(b) expresses each model’s token use relative to the median model on the same task.
Spending more does not buy a higher score: across the 12 models, the rank correlation between relative token use and
score is − 0.05 -0.05 . Claude Opus 5.5, GPT-6.1 Sol and GPT-6 Astra, three of the four highest-scoring models, use 0.35 to 0.61 times
the median, whereas Gemini 4 Argon reaches a score close to that of Opus with 1.66 times. Five of the six open-weight
models use at least the median (1.0 to 1.75 times), and all six score below 50.

5.1 Tasks in which the agent builds the solution leave more room for self-improvement

On tasks whose solution is a single answer, the starter solution already passes each question to the model, so it
scores high from the start and its score depends on the model: its median validation score over these seven tasks is 78.2, and the
models are 27.5 points apart before the first round (medians over tasks). The largest gain that any run achieves is
14.8 points at the median, and at the end of the runs the models are 25.0 points apart, about as far as at the
start. On the tasks in which the agent builds the solution, every model starts from the same program, although
its score can depend on the model that it calls. On the nine of them
whose evaluator scores each episode on a scale, this program scores 19.4 at the median, the largest gain is 38.8
points at the median, and the models, 0.9 points apart at the start, end 38.8 points apart; on the four whose
evaluator records only success or failure, they move from 2.5 to 37.2 points apart. The same pattern appears in Figure 1 c. The
exceptions are Kinematics, whose solution is a single answer but whose starter solution scores only 27.7 and on which
a run gains 33.5 points, and Multi-turn Editing, on which the agent builds the solution but no run gains more than
4.2 points.

5.2 The granularity of feedback matters

On the nine tasks in which the agent builds the solution and the evaluator scores each episode on a scale, the
median gain over the open-weight runs of a task is 9.9
points at the median over tasks, against 28.4 for the closed-source runs, and on 3D Tracking and Active Search it is
close to that of the closed-source runs (39.8 against 42.8, and 29.3 against 28.4). On the four tasks whose evaluator records only whether an episode or a
level succeeded, namely RoboCasa, LIBERO-MAX, LIBERO-PRO, and ARC-AGI-3, the median open-weight gain falls to 1.6
points, while the closed-source runs still gain 16.9. The median open-weight run does not improve at all on
LIBERO-PRO and gains 0.2 points on ARC-AGI-3. Since a candidate is retained only if it raises the validation score
( Equation 2 ), a score on a scale rewards a change that improves part of an episode, whereas a score that
records only success or failure rewards a change only once it turns failed episodes into successful ones.

5.3 Strict checks of physical stability and exact correctness pose the greatest challenge

The difference between the best closed-source and the best open-weight model is largest on tasks whose evaluator
applies such a check: whether a robot task succeeds in simulation (RoboCasa, 50.0 points; RoboLab, 40.3; RoboDojo,
37.3), whether the output grid is exactly right (ARC-AGI-2, 49.2) or a level is cleared (ARC-AGI-3, 43.3; on ARC-AGI-1,
whose puzzles the starter solutions already nearly solve, it is 8.8), and
whether a reconstructed scene is physically and geometrically consistent (Scene from Video, 36.4; Scene from Photo,
26.5). It is smallest on tasks scored by a judge or with a tolerance: Video Quality (0.1), Mass (0.8), Multi-turn
Editing (1.0), Video Generation (2.5), and Image Editing (4.2). The component scores of the two scene tasks show how
plausible outputs fail these checks ( Tables 29 and 30 ). On Scene from Photo, the renderings of the
open-weight scenes resemble the photo, with an Appearance score of up to 81.8, but the furniture is not recovered as
complete and correctly placed objects: their Objects score is at most 16.5, against 62.5 for both closed-source
models. On Scene from Video, the Physics score, the fraction of objects that remain stable in simulation, is 0.0
for all four open-weight models, against 70.7 for Claude Opus 5.5 and 37.7 for GPT-6 Astra. The two LIBERO
tasks are the exceptions among the robot tasks: the best open-weight model matches the best closed-source model on
LIBERO-MAX (45.8) and trails it by 10.0 points on LIBERO-PRO.

6 Conclusion

We introduced Flex-RSI, a benchmark that measures whether a frontier agent can improve both its task solution and its
own harness within a fixed budget, with every run starting from the same general-purpose harness and every final
solution scored on a hidden test split. Across 24 tasks and 18 models, three findings emerge. Self-improvement
raises the score most on tasks in which the agent builds its own solution, and on these tasks models that start from
the same program end far apart, whereas on tasks whose solution is a single answer the starter solution already
scores high and the models end about as far apart as they began. Open-weight models improve when the evaluator scores each episode on a scale, but
barely improve when it records only success or failure. The largest gaps between closed-source and open-weight
models arise where the evaluator checks physical stability or exact correctness, even when the outputs look
plausible. Paired runs further show that editing the harness contributes to the improvement, most where
the unchanged starting harness makes little progress, whereas a harness built by a stronger model raised the score
of a weaker model on only two of four tasks.

The improvement measured here is mostly at the level of the harness. The evaluated model’s weights never change, and on
most tasks no model is trained; on some, the solution may train or fine-tune helper models on the development split.
Flex-RSI therefore does not measure a model that modifies its own parameters. Extending the benchmark to weight-level
self-improvement, and studying how it interacts with changes to the harness, is left to future work. The leaderboard is
maintained on the project page, https://flex-rsi.github.io .

Appendix B Protocol and harness

This appendix specifies the parts of the protocol that Sections 3.2 and 3.3 describe only in
outline: the structure of a round, the capabilities of the executor and the improver, the acceptance rule, the
budget and the conditions under which a run ends, and the measures that keep the evaluation intact. The rules are
identical for all models and tasks; the budget and two settings of the executor phase are fixed per task and
listed in Table 10 .

B.1 Round structure

A run begins by scoring the starter solution on the validation split, which gives the score against which the first
candidate is compared. Each round then proceeds in five steps: an executor phase that produces a candidate solution;
a check that reverts every change the executor made outside the files it may modify; the evaluation of the candidate
on the validation split; the acceptance decision of Equation 2 ; and an improver phase that revises the
harness.

The executor phase normally ends when the executor declares its work finished, and the solution in its final state
becomes the candidate. It ends earlier when one of the executor’s evaluations on the development split exceeds the
development score of the accepted solution by a fixed share of the distance between the starter’s validation score
and the validation score of a strong known solution ( Table 10 ); the solution as it was in that evaluation
is then submitted. If the phase is interrupted before the executor finishes, because it reached its call limit, its
time limit, or the budget, the best state that the executor’s development evaluations showed to exceed the accepted
solution is submitted, and nothing is submitted if there is none. A round that leaves the solution unchanged does
not use a validation evaluation.

B.2 Executor

The executor works in a copy of the run’s repository. Its tools allow it to run shell commands; to read, write, and
edit files; to view images; to run experiments on the compute allocated to the task, including GPUs where the task
provides them; to score the solution, or several variants of it at once, on the development split; and to query the
remaining budget. It may write only to the solution, to a notes file that persists across rounds and is shared with
the improver, and to a scratch directory that is emptied before each round. It observes development scores directly
and the validation scores of earlier rounds through the run records, but it has no access to the validation or test
data or to the evaluator. The starting harness allows 60 model calls per executor phase. Independently of the
harness, the protocol stops a phase after the number of model calls given in Table 10 or after 180
minutes (600 minutes on the ARC tasks), and an experiment after 240 minutes.

B.3 Improver

After each round, the improver receives the executor’s transcript, its experiments and notes, and the scores of all
rounds so far. It may modify the executor’s prompts, settings, control loop, and tools, as well as its own prompts,
settings, acceptance rule, and a file of lessons that it maintains across rounds. A single improver phase may change
at most 400 lines of the harness; a larger change is reverted in full. Every four rounds, the improver additionally
reviews its own process: which kinds of harness changes were followed by accepted candidates and which by stalls,
whether the acceptance rule is too strict or too permissive, and which lessons to record. Changes to the harness take
effect from the following round. In the frozen-harness runs of Table 8 , the improver is not run.

B.4 Acceptance rule

The margin δ \delta in Equation 2 is determined by the acceptance rule, which is part of the improver’s
harness. In the starting harness, a candidate is accepted if its validation score exceeds that of the accepted
solution by more than 2 ​ σ 2\sigma , where σ \sigma is the standard deviation of the starter’s validation score over
repeated evaluations ( Table 10 ). On tasks for which σ \sigma was not measured, it is set to zero, and any
improvement on the validation split is accepted. Because the rule belongs to the harness, the improver may revise
it. If the rule fails to return a decision, and in every run with a frozen harness, the starting rule δ = 2 ​ σ \delta=2\sigma is applied.

B.5 Budget and termination

A run ends at the first of the following events: the wall-clock time, GPU hours, tokens (input, including cached
input, and output), or cost in dollars reach the task’s limit; the number of validation evaluations reaches its
limit; the round cap is reached; or five consecutive rounds produce neither a candidate nor a change to the harness,
a rule that is not applied on LIBERO-MAX and LIBERO-PRO. The budget is checked before each model call, experiment,
and development evaluation and is charged when each of them ends, so that calls running concurrently can exceed a
limit by at most their combined cost. A submitted candidate is evaluated on the validation split even when the
budget is exhausted. Model calls that the evaluator makes on the validation and test splits, for tasks whose
solution calls the model, are recorded but not charged. Periods during which the model provider is unavailable are
not charged either, and a phase interrupted by such an outage is repeated. After the run, the final solution and
every accepted solution are scored on the test split ( Section 3.3 ).

B.6 Isolation and integrity

After every phase, any change outside the paths that the phase may modify, including changes made through shell
commands, is reverted and recorded as a violation; the evaluator, the data splits, and the protocol therefore cannot
be altered by the agent. Files larger than 5 MB are excluded from the run’s repository. If a phase crashes in two
consecutive rounds, the harness is restored to the last version that completed a round without a crash. When a phase
ends, all processes it started are terminated, so that no process left running can modify the solution afterwards.
All model calls, experiments, and development evaluations are routed through the benchmark, which charges them to
the budget and records them.
