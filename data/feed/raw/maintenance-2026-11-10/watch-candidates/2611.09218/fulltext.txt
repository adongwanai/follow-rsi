BoxBox : Recursive Harness Self-Improvement for Long-Running Performance Optimization

Automated harness optimization improves agents by learning from trajectories and task feedback. Existing offline methods use reference answers to optimize harnesses for reuse on held-out tasks. However, many real-world tasks are open-ended, while long runs expose new difficulties that offline-optimized harnesses may not address. To study harness optimization in these settings, we introduce PerfRace , a benchmark for long-running performance optimization of software projects, and investigate whether agents can use task-specific experience to recursively improve their harnesses during an ongoing task. To this end, we introduce BoxBox , which enables agent-triggered harness revision and kernel-managed hot reloading while preserving execution context. We evaluate BoxBox on PerfRace under matched test-time budgets, comparing it with Frozen Harness, offline Harness Evolution, and Harness Scaling. 1 Introduction

Large language model (LLM) agents interact with their environment through harness that determines both the available actions and the observations they receive ( Yang et al., 2024 ; Merrill et al., 2026 ; Lin et al., 2026 ) .
Recent studies have shown that harness design can substantially affect agent performance and behavior, even when the underlying model is fixed ( Lin et al., 2026 ; Wang et al., 2026b ) .
These findings have motivated automatic optimization of agent harness, in which an
optimizer analyzes agent trajectories and evaluation feedback, proposes modifications
to the harness, and evaluates the resulting agent on benchmark tasks.

Existing offline harness optimization methods ( Park et al., 2026 ; Zhang et al., 2026b ; Lin et al., 2026 ; Wang et al., 2026b ) often use reference answers or task-completion feedback to diagnose failures, and revise harnesses to improve performance on held-out tasks. This setup aligns with existing agent benchmarks that evaluate whether an agent completes a specified task ( Jimenez et al., 2024 ; Merrill et al., 2026 ; Froger et al., 2026 ) .

However, many real-world tasks are open-ended and long-running, making end-state evaluations alone insufficient to capture how agents progress throughout these runs.
Moreover, this setting poses two challenges for offline harness optimization. First, open-ended tasks make it difficult to identify useful harness revisions, as they may lack clear criteria for diagnosing what needs improvement. Prior evaluations show that harness evolution does not reliably improve performance without unit-test feedback ( Wang et al., 2026b ) . Second, continued execution exposes new task-specific difficulties that may limit the generalization of harness revisions learned from other tasks ( Nie et al., 2026 ; Wang et al., 2026b ) .

To study harness optimization in these settings, we introduce PerfRace , a benchmark for optimizing performance of real-world software projects. Our experiments show that offline Harness Evolution ( HE ) underperforms Frozen Harness on PerfRace (Figure 1 ), with no consistent improvement during training or validation (Appendix A.2 ), consistent with prior findings of unreliable gains and limited generalization ( Wang et al., 2026b ) .

Nevertheless, the current task’s trajectory can reveal difficulties encountered during execution and provide task-specific evidence for harness revision ( Nie et al., 2026 ) . We therefore investigate whether an agent can use this experience to improve its own harness during the ongoing task, making harness optimization an online, task-specific process.
Existing methods allocate budget between task execution and harness optimization through an outer loop, with harness updates scheduled by predefined triggers or a separate meta-agent ( Wang et al., 2026b ; Liu et al., 2026 ; Zhang et al., 2026c ) . However, external control limits the task-solving agent’s ability to respond to emerging difficulties. First, despite observing task progress, the agent cannot decide whether to spend its remaining budget on task execution or harness revision. Second, updates occur between task attempts or execution segments, delaying their use in the ongoing task.

2 Related Work

Automated harness optimization. Prior work has extensively studied the automated optimization of prompts for LLM-based systems ( Zhou et al., 2023 ; Pryzant et al., 2023 ; Yuksekgonul et al., 2025 ; Khattab et al., 2024 ; Agrawal et al., 2025 ) . Subsequent work extends automated optimization to agents, using execution trajectories and task feedback to improve their memory, skills, and workflows ( Zhao et al., 2024 ; Zhang et al., 2025 ; Ni et al., 2026 ; Hu et al., 2024 ; Zhang et al., 2024 ) . Meta-Harness and AHE further extend automated optimization to executable harness code, using trajectories and evaluation feedback to guide iterative revisions ( Lee et al., 2026 ; Lin et al., 2026 ) .

Building on this setting, offline methods revise harnesses using reference answers or task-completion feedback from training tasks, aiming to improve held-out performance ( Park et al., 2026 ; Zhang et al., 2026b ; Lin et al., 2026 ) . However, an evaluation finds unreliable gains without unit-test feedback and limited transfer from reusable harnesses, but reports gains from Harness Scaling, which alternates task attempts and harness revisions at test time ( Wang et al., 2026b ) .

Following this task-specific direction, JIT-Agent synthesizes a tailored harness for each task before execution begins ( Zhang et al., 2026a ) . TTHE further explores harness optimization without reference answers, using trajectories and execution-derived feedback to revise executable harnesses on unlabeled test batches ( Nie et al., 2026 ) . Continual Harness moves harness optimization into ongoing task execution through an outer loop that periodically invokes a refiner while preserving the task state ( Karten et al., 2026 ) . In BoxBox , the task-solving agent decides when to allocate its remaining budget to full-harness revision, while a separate kernel manages runtime hot reloading and preserves execution context.

Long-Horizon and Open-Ended Agent Evaluation. Existing agent benchmarks cover diverse capabilities but commonly evaluate tasks with explicit end states, reporting task success, pass rates, or final artifact quality ( Mialon et al., 2023 ; Liu et al., 2024b ; Jimenez et al., 2024 ; Xie et al., 2024 ; Merrill et al., 2026 ; Sun et al., 2026 ) . Recent iterative optimization benchmarks evaluate solution quality but still use reference implementations, human performance, or reference outputs for task construction or scoring ( Chan et al., 2025 ; Lyu et al., 2026 ; Imajuku et al., 2025 ; Xu et al., 2026 ; Mang et al., 2025 ; Zhu et al., 2026 ) . Closer to our setting, Frontier-Eng and FrontierSWE support iterative optimization of engineering designs and software projects, with tasks curated from established problems and expert contributions ( Chi et al., 2026 ; Chu et al., 2026 ) .

In contrast, PerfRace constructs long-running performance optimization tasks from real-world software projects and workloads without requiring reference optimizations. Its construction pipeline provides a scalable way to continually source new tasks from public software projects.

Benchmarks for Performance Optimization. Shypula et al. (2024) introduce PIE for evaluating LLMs’ ability to make performance-improving edits to single-file competitive programming solutions while preserving functional correctness. Subsequent benchmarks broaden the optimization domains to GPU kernels, general-purpose numerical programs, and algorithmic redesign, while retaining function- or file-level optimization tasks ( Du et al., 2024 ; Huang et al., 2024 ; Liu et al., 2024a ; Waghjale et al., 2024 ; Ouyang et al., 2025 ; Press et al., 2025 ) .

GSO and SWE-Perf extend evaluation to repository-level performance optimization, deriving tasks and human reference optimizations from GitHub commits and pull requests ( Shetty et al., 2025 ; He et al., 2026 ) . SWE-fficiency and FormulaCode further incorporate a targeted workload per task and multiple community-maintained workloads, respectively ( Ma et al., 2026 ; Sehgal et al., 2026 ) .

These repository-level benchmarks construct tasks around a targeted performance test, whereas real performance engineering starts from an end-to-end workload and discovers bottlenecks through profiling. PerfRace adopts this workload-first formulation, leaving agents to identify and implement correctness-preserving improvements without a known target patch.

3 PerfRace

PerfRace benchmarks real-world software performance optimization with three design principles: (1) Live : projects are continually sourced from public GitHub repositories; (2) Open-ended : tasks use project workloads without reference optimizations or known target patches; and (3) Long horizon : agents iteratively optimize code and choose when to submit for feedback within a fixed budget.

3.2 Construction

We construct PerfRace by identifying real projects with optimization potential
and building reliable tasks around realistic workloads (Figure 2 (a)).
Each PerfRace task adopts the Harbor Task Format ( Merrill et al., 2026 ) , as illustrated in Figure 2 (b).

Discovery. To identify less-explored optimization opportunities beyond mature, heavily maintained repositories, we search GitHub coding-agent activity for candidate projects. Specifically, we identified 103,475 candidate projects from public GitHub pull requests and branch pushes made by known coding agents between May and August 2026 (Appendix B.3 ).

Filter. We filter candidate projects in two stages. First, deterministic prechecks verify repository and source-revision accessibility, license redistributability, and repository size and popularity, retaining 7,257 candidates. We then use GPT-5.6-Luna to assess each candidate’s setup process, evaluable workload, runtime feasibility, and optimization potential from its source code. Of these candidates, 239 pass this assessment and proceed to Pair Verification (Appendix B.3 ).

Pair Verification. We use agent–human Pair Verification to construct runnable tasks and assess their quality against three criteria (Appendix B.4 ):

Specifically, we first let the agent derive workload inputs and scale from real project use and propose correctness checks, measurement boundaries, and performance metrics for human review.
Second, the agent configures warmup and runs repeated tests to detect flakiness and distinguish genuine speedups from noise; the reviewer uses these results to approve or revise the measurement protocol.
Finally, the agent conducts red-team tests against reward hacking using invalid, incomplete, hard-coded, and work-skipping solutions; the reviewer requests verifier fixes as needed before approving the task for packaging and release.
Eventually, we curated 100 tasks, each requiring an average of 9.1 hours of

3.3 Benchmark Composition

The resulting benchmark contains 100 tasks across seven domains (Figure 3 ): developer tools (30 tasks) compiles, builds and validates software; data systems (25 tasks) ingests, indexes and queries data; scientific computing (15 tasks) runs simulations and numerical solvers; media processing (9 tasks) renders graphics and audio; geometry (8 tasks) processes maps and 3D models; machine learning (7 tasks) trains models and runs inference; and security (6 tasks) encrypts data and analyzes attack logs.
Each task pairs a real project with a fixed workload; for example, one task optimizes CCC while it compiles SQLite. Appendix B.2 provides a detailed characterization of the tasks.

3.4 Evaluation

In the evaluation loop, the agent chooses when to submit snapshots for correctness and performance feedback from the Judge (Figure 2 (c)). The score s i s_{i} is the speedup over the unmodified project for correct submissions and zero otherwise. Runs without a correctness-preserving improvement receive a score of 1 × 1\times . During the final five minutes, the agent is prompted to end optimization and leave the project in a coherent state for the Judge’s final evaluation.

Prior studies show that agents can inflate scores by tampering with evaluation code or accessing reference outputs ( Wang et al., 2026a ; Von Arx et al., 2025 ) . We therefore use shadow verification , evaluating project snapshots in separate containers while keeping verifier code and held-out test data out of the agent’s workspace.

4.2 Kernel-Managed Harness Updates

BoxBox treats the harness as a task-specific implementation, allowing a revision to be tailored to the requirements of the ongoing task. To support such adaptations, BoxBox exposes the full executable harness, allowing the agent to translate task-specific needs into direct changes to tools, control flow, and state management. Let ℋ \mathcal{H} denote the set of harness implementations compatible with the execution interface. Methods with predefined editable components restrict candidate revisions to a subset ℋ bounded ⊆ ℋ \mathcal{H}_{\mathrm{bounded}}\subseteq\mathcal{H} ( Zhang et al., 2026b ; Lin et al., 2026 ; Park et al., 2026 ) , whereas BoxBox allows revisions H k ′ ∈ ℋ H^{\prime}_{k}\in\mathcal{H} .

In BoxBox , the harness is the editable agent implementation, while the runtime is its running version that controls the agent’s execution and maintains its state. These revisions change the agent’s execution code, so a faulty update can interrupt the task and make it difficult for the agent to recover on its own. BoxBox therefore introduces a separate kernel that manages runtime hot reloading and can safely retain or restore the previous runtime if an update fails validation or activation.

Specifically, we register boxbox() as a tool that yields control to the kernel, with boxbox() ∈ 𝒜 ⁡ ( H k ) \texttt{boxbox()}\in\mathcal{A}(H_{k}) . When the agent invokes boxbox() , the kernel suspends task execution and preserves the agent’s execution context, including the accumulated trajectory, terminal session, and workspace state. It then launches a review session for the agent to examine the trajectory, revise the harness as needed, and commit any changes. After the review session concludes, the kernel validates any new commits, loads the revised runtime on success, and otherwise retains the current runtime. During activation, the kernel transfers the preserved execution context to the new runtime and reattaches the existing terminal session. On successful activation, H k + 1 = H k ′ H_{k+1}=H^{\prime}_{k} , and subsequent interactions follow Eqn. 1 . Finally, the kernel returns control to the agent, allowing it to resume the ongoing task.

Beyond agent-initiated updates, runtime faults also trigger kernel-managed recovery and review based on the recorded fault evidence. Appendix C provides further implementation details.

4.3 Agent-Controlled Harness Optimization

Based on this mechanism, BoxBox lets the task-solving agent decide when to request a harness review, so it can adapt its harness in response to difficulties encountered during task execution. Unlike prior methods that use an outer loop ( Lee et al., 2026 ; Karten et al., 2026 ; Liu et al., 2026 ) , the agent itself allocates the shared budget B B between project-code optimization and harness revision to maximize S ⁡ ( B ) S(B) .

Within the review session, we provide a default skill (Appendix D.3 ) that guides the agent through a simple self-review strategy based on diagnosis and harness revision:

• Diagnosis. The agent examines the trajectory for execution failures, repeated work, and successful patterns that could be automated or reused. It uses these observations to identify limitations of the current harness, such as missing capabilities or costly tool interactions.

5.1 Experimental Setup

Baselines. We compare BoxBox with three baselines: Frozen Harness ( Frozen ) retains the initial harness throughout task execution. Harness Evolution ( HE ) optimizes the harness offline on training tasks and selects it by validation performance, then holds it fixed during test-task execution. Harness Scaling ( HS ) uses an external controller to revise the harness between attempts on the same task, using feedback from each completed attempt. Both HE and HS are adapted from Wang et al. (2026b) . Following Meta-Harness ( Lee et al., 2026 ) , all methods start from the same initial harness H 0 H_{0} , Terminus-KIRA ( KRAFTON AI and Ludo Robotics, 2026 ) , a simple terminal-based harness that executes shell commands and returns their outputs to the model.

Review frequency. BoxBox invokes a median of five reviews per run, with 92% of runs containing three to six (Figure 5(a) ). These results show that boxbox() provides an effective entry point for harness optimization during task execution, allowing agents to review their harnesses based on accumulated trajectories.

Budget allocation. Agents allocate most of their time budget to task execution. Harness reviews account for a median of 2.1% of the time budget and 13.8% of model cost per run (Figure 5(b) ). Together with BoxBox ’s higher speedup and lower model cost than Frozen , these results suggest that agents can effectively balance task execution and harness optimization within a shared budget.

Modification scope. Harness modifications span prompt rules, skills, tools, execution logic, and fault handling (Figure 5(c) ). These changes show that agents use full-harness editing to adapt both their capabilities and execution process. 6 Conclusion

In this work, we introduced PerfRace , a benchmark for long-running performance optimization of real-world software, and BoxBox , which combines agent-triggered, full-harness revision from task-specific experience with kernel-managed hot reloading that preserves execution context. On PerfRace , offline Harness Evolution yields inconsistent gains, whereas BoxBox achieves higher best-so-far correct speedup and greater time and cost efficiency than the evaluated baselines. It achieves a Speedup ​ @ ​ 4 ​ h \mathrm{Speedup@}4\mathrm{h} of 1.70 × 1.70\times , compared with 1.54 × 1.54\times for the strongest baseline, and reduces mean model cost by 29.3 % 29.3\% relative to Frozen Harness. These results support harness optimization as an agent capability for improving how it solves a task while continuing its execution.

Security and Responsible AI Limitations

BoxBox allows an agent to modify executable harness code during an ongoing task, which introduces security and Responsible AI risks beyond those of a fixed harness. In particular, the agent executes and modifies code that may originate from untrusted repositories, and harness revisions may introduce security regressions, weaken existing safeguards, or create unintended execution behavior. More generally, self-modifying agent mechanisms could be misused to alter controls or expand capabilities in ways not intended by system operators. Our evaluation is conducted in isolated research environments with kernel-managed validation and rollback for harness updates and separate shadow verification for task evaluation. These mechanisms reduce experimental risk but do not constitute a complete security boundary or guarantee safe behavior under adversarial conditions. BoxBox should therefore be viewed as a research prototype rather than a production-ready self-modifying agent framework. Any production deployment would require additional sandboxing, access control, security review, monitoring, and human oversight of agent-generated harness changes before they are activated.

A.3 Harness Scaling

Our HS baseline adapts the implementation of Wang et al. (2026b) to PerfRace . We describe the execution procedure, analyze model costs, and examine a failure case.

Setup. We adapt task execution and evaluation to PerfRace , using best-so-far correct speedup under a fixed time budget as the optimization objective. Each run shares a four-hour budget across task execution, harness optimization, and evaluation. An external controller revises the harness using feedback from each completed attempt and starts a new agent session, preserving project-code progress and resetting the execution context.

We record 2,132 HS attempts, with a median of 12 per run. Across 1,983 boundaries, the median interval between one attempt ending and the next beginning is 3.37 minutes, including harness optimization and runtime transition.

Model costs. HS ’s session resets can lower input-token costs by reducing the accumulated conversation history. Although project-code progress is retained, subsequent attempts may need to reconstruct earlier decisions or repeat experiments whose outcomes are no longer available in the execution context. BoxBox preserves this context across harness updates, allowing subsequent optimization to build directly on earlier findings. This trade-off helps explain why HS ’s lower total model cost does not necessarily translate into greater optimization progress per dollar.

Failure analysis. To examine HS ’s optimization process, we trace one kitops--minilm-pack run (Figure 8 ). During one harness optimization step, HS ’s controller reported that the agent repeatedly rebuilt the project, ran tests, and reran the workload on the same code version. It therefore added a repetition check to warn after three consecutive matching command batches.

Figure 8: HS optimization trajectory on kitops--minilm-pack . Annotations show selected harness revisions and an agent session containing 113 consecutive checks that produced no new performance measurements.

However, the new repetition check did not stop the agent from performing the same checks using different command forms. The agent ran 113 consecutive commands repeating the same checks, without modifying code or collecting new performance measurements. The check only looked for consecutive repetitions of the same commands, so it could miss repeated checks written in different ways. The run reached its best correct speedup of 1.649 × 1.649\times at checkpoint 5, with no further improvement in subsequent recorded checkpoints. The repeated checks revealed a need for further harness revision during execution, yet HS performs harness optimization only between agent sessions, leaving the current session to continue under the existing harness.

This case illustrates how session-level external control can delay harness revisions needed during ongoing task execution. The revised check missed repeated validation expressed through different commands, and the agent continued spending task time without making code changes or collecting new performance measurements. Allowing the agent to initiate further harness revision when these limitations become apparent would provide an earlier opportunity to address them.

A.4 Case Study

To analyze how BoxBox supports effective task execution, we examine two complementary aspects of harness optimization. Appendix A.4.1 traces how agent-triggered reviews address difficulties encountered during ongoing tasks. Appendix A.4.2 examines how full-harness editing can support task performance and reduce model costs through changes to agent guidance, tools, and execution behavior.

A.4.1 Harness Optimization Trajectories

We examine two four-hour runs, tracing the difficulties encountered during task execution, the resulting harness revisions, and their use in subsequent optimization.

CCC. To reduce CCC’s compilation time on SQLite, the agent profiles compiler stages and tests code changes through repeated compilation runs (Figure 9 ). During the first review, the agent identified repeated manual processing of timing output and added a helper for repeated runs, result recording, and candidate comparisons. Using this helper, the agent established a baseline and evaluated compiler changes, but still had to extract and compare individual stage timings manually. To automate this step, the agent added stage-timing summaries to the helper in the second review, then used them to investigate optimization passes and code generation.

Later, a change to CCC’s source code appeared to reduce compilation time by 9.4% in separately measured batches. Yet when the agent alternated runs of the modified and unchanged compiler versions, their median compilation times were nearly identical, suggesting that the apparent gain came from measurement variation between batches rather than the code change. The agent therefore incorporated this comparison procedure into the helper during the third review to improve measurement reliability, then used it to reject several compiler changes that showed no consistent speedup. Continuing with this helper, the agent developed mnemonic-parsing and operand-splitting changes that reduced official running time from 6.321 6.321 to 6.095 6.095 and then 5.792 5.792 seconds.

Annotations mark harness review outcomes and task-code changes; numerical gains are absolute and relative increases over the preceding best-so-far speedup.

FluidSynth. To optimize FluidSynth’s MIDI-to-WAV rendering performance, the agent tests code changes through repeated workload execution and output checks. Figure 10 traces harness revisions during this process. The first review noted that long-running commands required extra model calls to continue waiting, but retained the harness because a proposed waiting tool would duplicate existing functionality. As this pattern recurred, the second review extended waiting inside the existing command runner. During subsequent audio-write batching experiments, a single tool call completed a build, five renders, and output checks, allowing the agent to assess the candidate without an additional waiting call.

Comparing batch sizes still required repeated setup of builds, timing loops, and output checks. The third review therefore added benchmark_matrix , reusing the updated command runner to execute labeled experiments and report timings and exit status. The agent then used it for six repeated renders with output-hash checks and subsequent configuration comparisons. Rendering performance improved further after the agent disabled OpenMP in the build configuration. The fourth review retained the harness, judging its existing capabilities sufficient after the agent resolved a build-state issue through a clean rebuild. The run reached a best-so-far speedup of 1.183 × 1.183\times .

Case 1. Review feedback: redirecting an experiment

Task: n8n-mcp--tool-batch-speed

Background. The task is to reduce the end-to-end running time of the n8n-mcp server on a fixed batch of workflow-building tool calls while preserving response correctness. The agent attempted to reduce logging overhead, but local measurements showed no improvement. The review therefore used profiling evidence to identify a different direction for the next experiment.

Review feedback. The feedback directs the agent to stop revisiting logging and investigate SQLJS data-conversion and statement-management overhead. It also specifies an experimental workflow, asking the agent to preserve the current project-code version and test modifications on a separate branch through paired repeated workload measurements and response-hash comparisons. Modifications should be rejected if their measured gains fall within measurement noise or their responses differ.

Discussion. This case illustrates how review feedback can support performance optimization by guiding both experiment selection and evaluation. Redirecting effort away from an unsuccessful direction can reduce repeated exploration, while paired measurements and response checks help the agent distinguish useful code changes from measurement noise or incorrect behavior.

Case 2. Prompt rules and skills: comparing noisy measurements

Task: sum--text-attest

Background. The task is to reduce the running time of SUM’s batch text-attestation workflow while preserving its outputs. Across successive experiments, the agent encountered apparent gains that did not hold under more controlled measurements. Earlier reviews had already warned against drawing conclusions from warmup effects and uncontrolled measurement order, yet a later code change again appeared promising based on a single fast run. To address this recurring problem, the review incorporated the measurement guidance into the main prompt for use across subsequent experiments.

Harness update. The prompt rule instructs the agent to keep an unchanged reference version and test modified code on a separate branch. It requires the same warmup procedure for both versions, followed by alternating fresh-process workload runs with identical output checks. The agent should compare median running times and their spread before accepting or rejecting the modification, with the measurement procedure aligned with the official workload.

Discussion. This case illustrates how prompt revisions can provide consistent guidance for evaluating code changes across successive experiments. More reliable comparisons can help the agent distinguish genuine improvements from measurement noise, reducing the risk of retaining ineffective changes or discarding useful ones based on unstable timing evidence.

Case 3. Tool functionality: reducing model calls for command polling

Task: rust-clippy--cargo-package-lint

Background. During performance optimization on Rust Clippy, the agent builds the project and runs benchmarks to evaluate code changes. The command tool could return before these operations finished, requiring additional model calls simply to continue waiting. The review therefore extended the tool’s internal waiting behavior to reduce these repeated interactions.

Harness update. The update extends internal waiting to 180 seconds for ordinary commands, subject to the existing block timeout. The tool continues checking for the completion marker and returns as soon as it appears, or provides a progress snapshot when the waiting window expires.

The tool description is updated alongside the implementation, instructing the agent to request an additional wait only when the command outlasts the new window.

Discussion. This case illustrates how full-harness editing allows agents to adjust tool behavior adaptively to reduce model calls spent solely on waiting. When an unfinished command returns control to the agent, another model call processes the conversation context and generates a continuation request, incurring input- and output-token costs. Internal polling checks command status without invoking the model, allowing commands that finish within the extended window to return their results without these additional calls. Fewer waiting turns also add fewer messages to subsequent context. The potential cost reduction therefore comes from reducing model interaction during command execution, while commands exceeding the window may still require further calls.

Case 4. Execution logic: context compaction

Task: trixi-framework-trixi-jl--self-gravitating-sedov-amr

Background. During performance optimization on Trixi, the agent accumulated a long interaction history through profiling and repeated experiments. The review reported that late model requests contained approximately 145,000 input tokens, making repeated processing of the accumulated history a substantial source of model cost. The existing summarization mechanism had not sufficiently limited this growth, motivating a revision to the agent loop’s context-management logic.

Harness update. The update adds a message-count trigger before the existing optional summarization check. When the original task instruction is available, the loop attempts compaction if the history contains at least 64 messages and its message count is at least 24 higher than the count recorded at the last attempt. It records the current count before invoking the existing summarizer through a helper with a timeout. Successful results supply the continuation prompt and subagent references; if summarization fails, execution continues with the existing history.

Discussion. This case illustrates how full-harness editing allows agents to adapt context-management logic during ongoing tasks. By summarizing accumulated interaction history, the revised loop can reduce the amount of context processed in subsequent model calls and the associated input-token costs.

Case 5. Fault fix: terminal recovery

Task: rust-clippy--cargo-package-lint

Background. While the agent was waiting for a long Rust Clippy build, the persistent terminal shell exited. At the next agent-loop entry, the harness raised an exception before its existing session-recovery helper could run. This failure prompted a review of how the harness handles terminal loss during ongoing execution.

Harness update. The update replaces the exception with a call to the existing session-recovery helper, which preserves a live terminal or starts a replacement if the shell has exited. This prepares a usable terminal for the next model turn without automatically replaying commands whose completion is uncertain. Such commands may already have modified project files, so replaying them could duplicate their effects.

Discussion. This case illustrates how full-harness editing allows agents to revise error-handling logic when runtime faults interrupt ongoing tasks. By restoring terminal access, the revised harness can enable the agent to inspect the current task state and resume performance optimization after a shell failure.

Together, these cases illustrate how full-harness editing lets agents adapt guidance, tools, and execution logic to the needs of ongoing tasks. Changes to experiment selection and measurement can support task performance by focusing effort on promising hypotheses and improving the reliability of candidate evaluation. Changes to tool execution and context management can reduce model costs by avoiding unnecessary waiting calls and repeated transmission of long histories, while fault-handling revisions support continued execution.

B.3 Construction and Curation Statistics

This section describes the implementation of Discovery and Filter and reports the candidate counts and curation effort at each construction stage.

Discovery implementation. We query the ClickHouse github_events table for opened pull requests and branch pushes by a configured list of coding-agent accounts, then group matching events by repository.
For each repository, we retain the latest matching pull-request or branch URL and use the GitHub GraphQL API to record its canonical identity, default-branch revision, stars, primary language, license, disk usage, and repository status.

The resulting records are deduplicated by GitHub repository, and projects are excluded when their repository, default branch, or recorded source revision cannot be retrieved.
Each step writes its results incrementally, allowing interrupted collection and metadata retrieval to resume without repeating completed work.

From GitHub activity recorded between May and August 2026, we identified 118,517 repositories, retrieved metadata for 104,428, and retained 103,475 project candidates after these checks.

Table 8: GitHub activity signals used for Discovery. Signal Repositories Branch push by a coding-agent account 112,127 Pull request opened by a coding-agent account 6,390

Filter implementation. We first apply deterministic checks to repository metadata and the recorded Git tree.
These checks require an accessible source revision, a license permitting modification and redistribution, 10–4,999 GitHub stars, and a tracked Git tree of at most 500 MiB and 25,000 entries.

Projects that pass these checks are collected at the recorded revision with their README, setup documentation, package manifests, license files, and representative source paths.
We then use GPT-5.6-Luna to assess the project’s setup path, evaluable process, runtime fit, and optimization potential from this source snapshot using a structured response schema.
The prompt is provided in Appendix D.1 .

We require each structured response to address the following criteria.

B.4 Pair Verification

PerfRace uses Pair Verification to ensure that each task represents meaningful project use, produces reproducible measurements, and rejects shortcut solutions; this section describes the agent–human protocol and analyzes the resulting curation trajectories.

B.4.1 Protocol

Pair Verification combines agent-led task construction with human review to turn each project candidate into an executable task and assess its realism, reliability, and integrity.
The construction skill is provided in Appendix D.2 .
The agent develops the task in stages and pauses for a reviewer decision after completing the evidence required for each quality criterion.

Figure 18: Pair Verification alternates between agent-led task construction and human review at the Realism, Reliability, and Integrity gates.

Explore and Design. The agent first studies the project’s documentation, examples, code paths, and public usage evidence to understand its purpose, users, and performance-relevant operations.
The agent searches public release pages for source code, models, and assets, scientific or government data portals, downstream repositories, production archives, and real user exports to identify candidate workload inputs.
For each input, the agent records its download location, version, and applicable terms, and accepts it only when an explicit license, public-domain designation, or written authorization permits redistribution with the benchmark.

It uses these materials to identify candidate operations, but grounds the workload and scale in a real user or downstream application rather than repository-native tests, benchmarks, examples, or fixtures.
The agent compares plausible workload candidates, then traces the selected operation from its user-facing entry point through the relevant project code and demonstrates a small input-to-output execution on the unmodified revision.
During this run, it records dependency installation, project build, input preparation, and operation time to check that setup does not dominate the measurement and to estimate whether complete verification can finish within the 1,200-second budget.
The agent repeats the operation on identical inputs to detect run-to-run flakiness, including sporadic failures or inconsistent correctness-relevant outputs, and to identify any dependence of runtime on random state, network access, or external services.
A candidate is revised or rejected if its stochastic execution remains too variable for reproducible performance measurement after fixing available random seeds and aggregating repeated runs.

It then specifies the exact operation, workload and scale available to the agent, held-out correctness cases, observable correctness utility, performance metric, and measurement boundary.
Before requesting Realism review, the agent summarizes the project’s purpose and users, the selected execution path, the basis for the input and scale, and the alternatives it considered and rejected.
The reviewer approves Realism only when the operation, input, and scale represent meaningful project use, the metric measures the stated utility, and the workload inputs can be redistributed as part of the benchmark.

Build and Calibrate. After Realism approval, the agent derives the installation, build, and run commands from upstream documentation, CI configuration, and package manifests, and verifies them on the pinned source revision.
The agent implements the verifier, the task’s test program that measures the performance metric on a separate copy of the workload and checks additional held-out cases for correctness.
It then constructs the Harbor task files with instruction.md , task.toml , an environment/ directory containing the editable project and workload, and a separate tests/ directory containing the verifier code, workload copy, held-out cases, and expected outputs.
The agent pins the project revision, base image, language toolchain, dependencies, workload assets, and expected outputs so that the image can be rebuilt and the task rerun without downloading project source or workload inputs.
The task instruction tells the agent how to build and run the project, what it may edit, which behavior it must preserve, and which performance metric to improve.

The agent then builds a fresh image and runs the verifier on the unmodified project before calibrating performance measurements.
The agent selects the smallest resource profile that completes the workload without CPU, memory, or storage pressure and sets the verifier timeout within 1,200 seconds.
The agent uses pilot and repeated runs to choose the workload scale, warmups, repetitions, and aggregation, requiring the final measurements to have a coefficient of variation below 10% while keeping build and setup outside the timed operation.
The agent checks that the timing boundary covers the complete operation requested in the task while excluding one-time environment setup and verifier preparation that are unrelated to the optimization objective.

For the n n timed measurements retained after warmup, x 1 , … , x n x_{1},\ldots,x_{n} , we compute

CV = s x ¯ , x ¯ = 1 n ​ ∑ i = 1 n x i , s = 1 n − 1 ​ ∑ i = 1 n ( x i − x ¯ ) 2 . \mathrm{CV}=\frac{s}{\bar{x}},\qquad\bar{x}=\frac{1}{n}\sum_{i=1}^{n}x_{i},\qquad s=\sqrt{\frac{1}{n-1}\sum_{i=1}^{n}(x_{i}-\bar{x})^{2}}.

After fixing the workload, correctness checks, resources, and measurement protocol, the agent builds the final image and evaluates the unmodified baseline and one optimization candidate under the same conditions.
The reviewer examines the fresh-build correctness results, repeated measurements and CVs, verification time, resource allocation, and candidate trajectory.
The reviewer approves Reliability only when fresh builds and repeated runs return the same correctness verdict and stable performance measurements with the chosen warmups, repetitions, aggregation, and measurement boundary.

Validate Integrity. To identify reward-hacking paths that could receive a valid score without completing the task, the agent tests deliberately incorrect, partial, hard-coded, and work-skipping solutions and checks that workload inputs, expected outputs, and verifier-owned data cannot be replaced by agent-controlled files.
The agent inspects the evaluation image for leaked expected outputs, verifier code, or construction notes that could reveal the hidden checks.
For example, in rust-clippy--cargo-package-lint , removing Cargo dependency tracking made later runs reuse a cached lint result, which the verifier detects by touching clippy-driver , running the workload twice against the same warm target, and requiring each Cargo JSON trace to report a non-fresh compiler artifact for cargo .

The reviewer approves Integrity only when every requirement in the task instruction is checked, every verifier check follows from the declared task, and none of the tested shortcut solutions can receive a valid score.

Finalize. After all three reviews, the reviewer chooses accept , revise , or reject ; accepted tasks pass final compatibility checks before publication as a task package comprising an immutable Docker image and task artifact.

B.5 Evaluation Protocol

For each submission, the Judge snapshots the agent’s current container and starts a temporary shadow container from that snapshot.
The Judge creates the snapshot with docker compose commit , launches the shadow container under a separate Compose project, and removes its container, local image, and volumes after verification.
The agent container remains paused during verification and resumes from the same workspace state after the shadow container is removed.

Inside the shadow container, the verifier runs through tests/test.sh and emits the correctness verdict and performance metric as JSON.
The verifier code, workload copy, held-out cases, and expected outputs are absent from the agent container and available only inside the shadow container.
Each task declares its warmups, repetition count, aggregation rule, and required correctness pass rate in task.toml , and its verifier returns a performance metric only when that pass rate is met.

The task clock continues while the shadow is created, executed, and removed, so every submission trades part of budget B B for additional correctness and performance feedback.
After verification, the Judge returns the correctness verdict and performance metric to the agent as feedback for subsequent optimization.
For a correct submission, the Judge computes the speedup score by dividing the unmodified baseline metric by the submission metric.
Submissions that fail correctness, exceed the verifier timeout, or do not produce a valid performance metric cannot update the best-so-far trajectory S ⁡ ( t ) S(t) .

Five minutes before the deadline, the agent receives a final delivery prompt asking it to leave the project in a coherent state before the Judge performs one final shadow verification of the current workspace.

C.1 Effects on Subsequent Interactions

Equation 1 describes two ways a harness revision
can affect subsequent execution while the language model ℳ \mathcal{M} remains
fixed. Changes to how the harness constructs model inputs can alter p ℳ , H k p_{\mathcal{M},H_{k}} , influencing the agent’s next action. Changes to Execute H k \operatorname{Execute}_{H_{k}} can alter how that action is carried out and how
its result is returned as an observation. A revision can affect either or
both, so its influence extends to the trajectory generated after activation.

The current harness also governs the review loop. Once a revision is
activated, subsequent reviews use the updated implementation and can examine
the experience accumulated under it. Harness changes can therefore affect
both task execution and the process used to produce later revisions.
Appendix A.4 illustrates concrete changes to guidance,
measurement, command polling, and context handling.

C.2 Review

The task-solving agent requests review through boxbox() without
having to propose a patch. The initial harness requires intervening task
activity and a 30-minute cooldown after each completed review; once eligible,
the agent decides whether and when to request another review.
The kernel preserves the task conversation and launches a separate agent
review session under the current harness. The reviewer can inspect task
trajectories and Git history, but edits only the harness, treating project
code as read-only. It may retain the current harness, add guidance, or modify
executable behavior, committing any changes before ending review.
The default review skill is provided in Appendix D.3 .

C.3 Execution Context

Execution context includes both runtime-owned state and the existing task
environment. The former includes the task conversation, review history, and
records of which trajectory entries have already been reviewed. These are
exported as a state snapshot. The terminal session and project workspace
remain in place: shell state, ongoing processes, and project files are
preserved through the existing environment connection.

When the agent calls boxbox() , the runtime yields control to the
kernel, suspending the task interaction loop while review proceeds separately.
This pauses the agent’s task decisions, not the entire container or its
processes. Before importing state into a candidate runtime, the kernel makes
a separate copy, preserving the original snapshot for recovery if the
candidate fails. This separates changing the agent implementation from
restarting its task environment.

C.4 Hot Reloading

Harness revisions are tracked as Git commits, while the kernel remains
separate from the editable harness. Before switching, the kernel checks the
committed candidate, loads its runtime, and verifies that it supports task
execution and context transfer. The current runtime keeps its terminal
connection until the candidate successfully imports the copied state.
The kernel then transfers the same terminal session to the candidate and
returns control to it, resuming task interaction from the preserved
conversation in the same workspace. If activation fails, the kernel retains
or restores the previous runtime and context.
For agent-requested reviews, the reviewer can leave concise guidance on using
new capabilities and continuing the task. This guidance is preserved across
the update, and the resumed agent is prompted to read it before continuing.
Task execution and review share the same budget and cost accounting.

C.5 Recovery

The kernel retains a recovery point across harness updates. A newly activated
runtime remains provisional until it reaches the next agent-requested review
without a runtime fault. If it fails before that boundary, the kernel restores
the previous confirmed harness and state and initiates a review using the
fault evidence. Faults in a confirmed runtime also trigger review.
Runtime-fault recovery starts a fresh terminal, so shell-local state is lost,
but project files, harness history, and execution records remain available.
The retained records let subsequent reviews examine failed revisions and help
the task-solving agent determine how to continue interrupted work.
