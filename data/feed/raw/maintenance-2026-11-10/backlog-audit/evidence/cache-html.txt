As these trajectories grow, key-value (KV) cache I/O and storage become the dominant cost.
Trajectories can also exceed the LLM’s maximum context length, requiring control over active cache growth.
Prior work uses context engineering to reduce cache size by trimming or summarizing history.
However, modifying the trajectory prefix invalidates subsequent cached states and triggers costly re-prefilling of retained context.
Task accuracy can also suffer when too little context is retained to limit re-prefill costs.
We propose cache engineering as a new scheme.
It allows agents to directly control their active KV cache without modifying the trajectory or re-prefilling retained context.
Specifically, agents can proactively use drop \operatorname{drop} to exclude selected cache from future attention and repos \operatorname{repos} to adjust retained keys’ position encodings.
We formalize these cache operations and identify history dependence as a serving challenge: identical token sequences can yield different cache states under different cache operation sequences, making prefix matching insufficient for correct cache reuse.
Thus, we co-design the AKV serving engine.
It provides a stateless interface compatible with existing serving APIs, while internally managing stateful cache reuse, eviction, and restoration.

Our code is at https://github.com/thu-nics/AKV . 1 Introduction Large Language Model (LLM) agents are capable of increasingly long-horizon tasks.
Agents are generally composed of an LLM for reasoning and tool calling, and a harness that orchestrates tool execution and context.
Through repeated reasoning, tool use, and environment interactions, they can carry out complex work spanning hundreds of rounds ( Ye et al., 2025 ; Liu et al., 2025b ) . As agent trajectories grow longer, Key-Value (KV) cache growth poses challenges to both inference cost and task accuracy.
In terms of cost, retaining and repeatedly accessing accumulated KV caches incur substantial storage and I/O overhead ( Wu et al., 2026 ; Anthropic, 2026 ) . As shown in Figure 14 , KV cache reads take up 82.4% of the total API cost.
In terms of task accuracy, agents can suffer severe degradation if either the number of attended KV states or their positional range exceeds what LLM handles reliably ( Hsieh et al., 2024 ; Chen et al., 2026b ; Zhou et al., 2025 ) .
Therefore, it requires delicate control over the active KV cache for efficient and reliable agent execution. Prior work reduces the growing cache via context engineering , typically by trimming or summarizing historical messages.
While older messages are often less useful, editing them changes the trajectory prefix, invalidates subsequent KV states, and triggers re-prefill.
The earlier the edit, the more retained trajectory suffix that must be re-prefilled.
Common harnesses therefore defer reductions until an active context length threshold is reached, then trim or summarize most of the trajectory and retain only a few recent rounds to keep re-prefill short ( Pi, 2026 ; OpenAI, 2026 ) .
Such aggressive reductions risk losing useful information from intermediate rounds, exposing a dilemma between re-prefill cost and task accuracy. In this paper, we introduce cache engineering , a new scheme for agents to directly control their active KV cache.
As shown in Figure 1 , instead of modifying the text trajectory, it excludes only selected KV entries from future attention, and reuses all retained KV states without re-prefill.
This allows agents to incrementally drop older KV entries while retaining more suffix KV within a given cost budget.
To support this control, alongside the usual append \operatorname{append} operation that adds KV states for new tokens, we introduce two additional cache operations. Drop \operatorname{Drop} removes selected KV entries from future attention, and repos \operatorname{repos} adjusts the positions encoded in retained keys.
Throughout execution, the LLM and harness choose when and how to apply these operations, repeatedly interleaving them with append \operatorname{append} to shape the active cache.
This programmable control also enables agents to search, evaluate, and refine cache engineering strategies through recursive self-improvement (RSI). Figure 1: Full-context inference, context engineering, and cache engineering.
Full-context inference reuses all historical KV.
Context engineering removes irrelevant text and recomputes the retained history.
Cache engineering keeps the text history but drops selected KV entries, reusing retained states without recomputation.
Nested color blocks illustrate how retained KV can still carry information from dropped history. However, the history-dependent nature of cache engineering challenges current LLM serving systems.
With standard KV caching, the token prefix fully determines the cached states ( Kwon et al., 2023 ; Zheng et al., 2024 ) .
In contrast, the same token prefix and retained positions can result in different cache states under different cache operation histories.
As shown in Figure 5 , trajectories ① and ② both retain KV entries for B and C, but C’s KV is computed with attention to A only in ①, due to the different ordering of drop and append operations.
The serving system must therefore account for both token and cache operation histories to correctly track or reuse cache states. Thus, we co-design AKV, a user-friendly and efficient serving system for cache engineering.
It provides a stateless interface compatible with existing API-based serving, while handling the complexity of stateful cache management internally.
Agents simply submit messages as usual, accompanied by cache operation instructions, without tracking which KV states remain resident on the server.
The system uses an extended radix tree for correct reuse and timely eviction of history-dependent cache states, while segment-batch attention efficiently reconstructs missing states in a single prefill pass.
AKV turns the theoretical efficiency potential of cache engineering into lower wall-clock latency and higher throughput for real-world agent workloads. • Cache engineering formulation. We formalize cache engineering through explicit cache operations and their trajectories, providing a clear and deterministic description of history-dependent cache states.
This formulation also provides a programmable interface for agents to define and refine their own cache engineering strategies. • Serving system for cache engineering. We propose the first serving system that allows agents to directly control their caches, which were previously managed solely by the system.
We co-design a stateless interface, an extended radix tree, and segment-batch attention to support efficient cache reuse, eviction, and restoration. • Improving efficiency and benchmark performance. Across three LLMs and four agent benchmarks, a simple tool-response rolling-drop cache policy reduces average cost by 27.7% and improves average benchmark scores by 1.7 points, compared with conventional threshold-triggered summarization.
With AKV server, this translates to 1.18 × 1.18\times the output throughput and a 1.51 × 1.51\times speedup in P95 request latency.
An RSI-based policy additionally reduces cost by 7.1% on held-out tasks. 2 Related Work Agent context engineering .
At the text level, context engineering summarizes or trims interaction histories to reduce cost and enable agents to work beyond the LLM’s context window.
Existing methods trigger summarization through heuristics ( Wu et al., 2025 ) or agent decisions ( Ye et al., 2025 ; Sun et al., 2025 ) .
Further work improves summary quality through reinforcement learning ( Lu et al., 2025 ) or by optimizing compression guidelines ( Kang et al., 2025 ) .
To avoid the cost and complexity of summarization, trimming methods ( Lindenbauer et al., 2025 ; Zhang et al., 2026 ) directly remove less relevant context.
However, editing earlier context requires re-prefilling the retained suffix, creating a dilemma between re-prefill cost and information retention. KV cache compression, eviction, and reuse .
At the cache level, prior work reduces cache size or approximately reuses existing states to lower storage, access, and computation costs. Compression methods use low-rank representations ( Liu et al., 2024a ; Wang et al., 2024a ) , quantization ( Liu et al., 2024b ; Liu et al., 2026b ) , or aggregation ( Fu et al., 2025b ; Wang et al., 2024b ) to represent cached entries more compactly. Eviction methods typically rely on low-level signals such as token positions ( Xiao et al., 2024 ) or attention-based importance ( Zhang et al., 2023 ; Li et al., 2024 ; Fu et al., 2025a ; Yang et al., 2026 ) to remove less useful cache entries. Reuse methods adapt cached states to different positions or context prefixes through position encoding adjustments ( Gao et al., 2024 ; Ma et al., 2026 ; Ordonez and Parnell, 2026 ) or partial recomputation ( Wang et al., 2025 ) .
Our work focuses on eviction and reuse, enabling high-level eviction decisions by agents and harnesses, while providing a practical serving engine for efficient cross-request reuse and isolation.
We discuss concurrent agent-oriented eviction work in Appendix A.5 . KV cache management in serving systems .
Beyond algorithmic designs, previous works also explore system optimizations for efficient cache storage, sharing, and request scheduling.
Existing systems use prefix caching to share KV states across requests with common prefixes while preserving equivalence to full prefill ( Zheng et al., 2024 ; Ye et al., 2024 ) .
For agent workloads, recent systems batch context edits to reduce cache invalidation ( Xu et al., 2026 ) or overlap re-prefill with ongoing execution to hide its latency ( Pan et al., 2026 ) .
For cache engineering, it additionally requires tracking cache operation histories, since identical token prefixes can produce different states under different operations. 3 Cache Engineering Cache engineering lets agents directly control their active KV cache without rewriting the trajectory or re-prefilling retained context.
We introduce basic concepts in Section 3.1 and design motivations in Section 3.2 , then formalize cache operations and their trajectories in Sections 3.3 and 3.4 . 3.1 Preliminaries An autoregressive LLM predicts the next token conditioned on the preceding token sequence x 1 : t x_{1:t} : p θ ( x t + 1 ∣ x 1 : t ) . p_{\theta}(x_{t+1}\mid x_{1:t}). (1) Modern LLM serving uses KV caching to avoid recomputing earlier tokens’ states.
The next-token prediction is then conditioned on the current token x t x_{t} and the preceding tokens’ cache: p θ ( x t + 1 ∣ x t , 𝒞 1 : t − 1 ) , p_{\theta}(x_{t+1}\mid x_{t},\mathcal{C}_{1:t-1}), (2) where 𝒞 1 : t − 1 \mathcal{C}_{1:t-1} denotes the KV states computed from tokens x 1 : t − 1 x_{1:t-1} . An agent’s trajectory is the ordered text history used for the following model computation, including its prompt, assistant messages, and tool responses.
Formally, the trajectory is a logical token sequence x 1 : t x_{1:t} , and t t is its logical token length . In cache engineering, the cache size need not equal the logical token length.
We therefore define the active cache 𝒞 \mathcal{C} as the KV cache states available to subsequent attention.
The corresponding token sequence is the active context , whose length equals the number of token entries in 𝒞 \mathcal{C} .
Note that active refers to participation in attention at the algorithmic level, not physical cache residency in the serving engine.
A cache entry’s position encoding index can also be adjusted independently of its token’s logical index in the trajectory. Context engineering modifies the logical token sequence through trimming or summarization.
In contrast, cache engineering directly modifies the active cache through cache operations, while keeping the logical token sequence unchanged. 3.2 Design Motivation The design of cache engineering stems from our thinking about three key questions: why direct cache modification is needed, which parts of the cache to retain, and how to manage its encoding positions. We discuss the motivations and empirical evidence guiding our design decisions below. Figure 2: Attention over history.

Cache engineering alleviates the dilemma between re-prefill cost and task accuracy in context engineering.
We evaluate GPT-OSS-120B on the first 100 BCP tasks, with four trials per task and at most 100 agent rounds.
Trim-based context engineering (retaining only the latest 12 rounds of tool responses) costs 1.85 × 1.85\times as much as the full-context baseline.
Summary-based context engineering (48k threshold) reduces cost by about 7% but lowers accuracy by 5 percentage points (Figure 4 ).
In contrast, directly dropping older tool-response cache can reuse the remaining cache, simultaneously improving accuracy and reducing cost (Figure 4 ).
The retained cache may also preserve information from dropped history used in its computation ( Xiao et al., 2024 ; Fu et al., 2026 ; Zou et al., 2025 ) , as shown in Figure 1 . Which parts of the cache to retain .
Cache selection should reflect message roles, recency, and task needs, beyond token-level importance heuristics.
Figure 4 shows that older tokens receive less attention than recent ones, and tool responses receive less attention than assistant messages at comparable relative positions.
We therefore use tool-response rolling drop as our primary example, retaining cache for all reasoning and recent tool responses while dropping older tool-response cache.
We later explore alternative policies, including RSI-based cache engineering. How to manage position encodings .
By default, position encoding indices grow with the logical trajectory, even as the cache is reduced.
Dropping cache neither changes retained position encodings nor resets the next token’s position index, so indices can reach the model’s limit even with a small cache.
We decouple position encoding indices from logical indices and cache size, using a separate cache operation to reposition cached keys with RoPE rotations ( Su et al., 2023 ) without re-prefill. 3.3 Cache Operations Figure 5: Cache operation trajectories and history-dependent KV states.

We define three basic cache operations for cache engineering: append \operatorname{append} , drop \operatorname{drop} , and repos \operatorname{repos} , which directly manipulate cache without rewriting the existing logical token sequence. Append \operatorname{Append} .
Operation append \operatorname{append} is the standard cache update in LLM inference.
It processes a new token x t + 1 x_{t+1} conditioned on the active cache and appends its cache entry C t + 1 C_{t+1} : append ⁡ ( x t + 1 ) : 𝒞 ← [ 𝒞 ; C t + 1 ] . \operatorname{append}(x_{t+1}):\qquad\mathcal{C}\leftarrow[\mathcal{C};\,C_{t+1}]. (3) We represent 𝒞 \mathcal{C} as a sequence of KV entries ordered by their logical indices, where [ ⋅ ; ⋅ ] [\cdot;\cdot] denotes concatenation.
The token may come from the prompt, a tool response, or model generation.
Position encoding indices start at zero and advance by one after each append; repos \operatorname{repos} can reset the next index. Drop \operatorname{Drop} .
Operation drop \operatorname{drop} removes selected KV states from subsequent attention, while leaving the retained states, their position encodings, and the logical token sequence unchanged (Figure 1 ): drop ⁡ ( P ) : 𝒞 ← 𝒞 ∖ { C i : i ∈ P } , \operatorname{drop}(P):\qquad\mathcal{C}\leftarrow\mathcal{C}\setminus\{C_{i}:i\in P\}, (4) where P P is the set of active logical token indices selected for dropping, and ∖ \setminus denotes cache removal, preserving the order of retained entries.
Note that drop \operatorname{drop} does not change the position encoding indices used by subsequent append \operatorname{append} operations. Repos \operatorname{Repos} .
Operation repos \operatorname{repos} updates cached keys’ position encodings in logical token order, and resets the position index for subsequent append \operatorname{append} operations.
With r r retained cache entries, their position indices become 0 , … , r − 1 0,\ldots,r-1 , and the next appended token uses index r r .
For rotary position embeddings (RoPE) ( Su et al., 2023 ) , we move a cached key K K from position index p p to q q by K ← R ⁡ ( q ) ​ R ​ ( p ) − 1 ​ K , K\leftarrow R(q)R(p)^{-1}K, (5) where R ⁡ ( p ) R(p) is the rotation matrix at position p p .
Cached values remain unchanged. These operations define the cache visible to attention at the algorithmic level.
The serving system handles physical storage, eviction, and reuse of cache separately in Section 4 . 3.4 Cache Operation Sequence To provide a clear and deterministic description of cache operations, we use a cache operation sequence : o 1 : m = ( o 1 , … , o m ) , o j ∈ { append ( x ) , drop ( P ) , repos } . o_{1:m}=(o_{1},\ldots,o_{m}),\qquad o_{j}\in\{\operatorname{append}(x),\operatorname{drop}(P),\operatorname{repos}\}. (6) Here, m m counts operations, x x is a token, and P P contains the active logical token indices to drop.
For a fixed LLM, this sequence determines the current cache states, starting from an empty cache. Cache operation sequences are necessary because cache states are history-dependent: tokens and retained positions alone do not determine next-token probabilities.
For example, in Figure 5 , all three trajectories retain B B and C C , but A A ’s cache is available when computing both B B and C C in ①, only B B in ②, and neither in ③. Thus, C C ’s cache states are different in all three trajectories.
Similarly, repos \operatorname{repos} changes the position encodings used by later append \operatorname{append} operations, as shown in Figure 8 .
Correct cache reuse and restoration therefore require both token and cache operation histories. 4 AKV Serving System AKV follows the principle of stateless interface, stateful serving .

The serving interface must keep each request’s output distribution independent of physical cache residency and other requests’ cache operations.
For example, drop \operatorname{drop} must affect only the issuing request’s attention, leaving other requests’ output distributions unchanged even when they share the same prefix cache.
Each request must also fully describe the cache states it uses, without relying on physical cache retained from previous turns.
This allows the server to fully restore missing cache states if memory pressure causes eviction between turns. To meet these requirements, AKV extends the standard LLM serving API to specify both token and cache operation histories.
As shown in Figure 7 , the existing messages field provides the full logical token sequence, while the optional cache field specifies drop \operatorname{drop} and repos \operatorname{repos} operation sequence using an operate-after grammar.
Note that all entries in messages implicitly specify append \operatorname{append} operations.
Each key in drop identifies the message index after which to apply the operation; its value lists the message indices whose cache is dropped.
The reposition field lists the message indices after which to apply repos \operatorname{repos} .
Message indices are zero-based, and drop \operatorname{drop} precedes repos \operatorname{repos} when both occur at the same message boundary.
For multi-round agent workloads, clients extend the message and cache operation histories after each round, following the standard LLM serving workflow. 4.2 Cache State Management 4.2.1 Design Objectives and Challenges AKV aims to preserve three key properties of conventional LLM serving systems:
(1) reusing cached states if and only if they are equivalent to the required states,
(2) evicting unused cache states without compromising request isolation,
and (3) restoring evicted cache states within one prefill pass. Serving systems face three corresponding challenges in preserving these properties when supporting cache engineering:
(1) Token prefixes alone no longer determine cache states, so ordinary prefix matching can incorrectly reuse states from different cache operation histories (Figure 5 (b)).
(2) KV cache dropped by one request may still be needed by another, so evicting it without accounting for other requests can cause unnecessary recomputation or violate request isolation.
(3) Ordinary causal prefill cannot reproduce cache states resulting from drops and repositions, while replaying the operation history requires multiple forward passes.
AKV addresses these three challenges with an extended radix tree, drop-aware eviction, and segment-batch attention, respectively. 4.2.2 Drop-aware Cache Management Reuse with drop nodes .
AKV extends radix-tree prefix matching with drop nodes.
When a request invokes drop \operatorname{drop} , AKV inserts a drop node Δ \Delta at the trigger point along the request’s path, recording the logical token indices whose cache is dropped.
Because drop \operatorname{drop} leaves retained states unchanged but affects subsequent attention computation, this placement preserves prefix sharing while distinguishing later states.
Prefix matching on the extended radix tree reuses cache along matched token and operation prefixes.
In Figure 5 (c), trajectories ① and ② share the A A – B B prefix but keep distinct C C states because they drop A A at different points, while trajectory ③ follows a separate branch.
When processing D D , each trajectory directly reuses its corresponding B B and C C caches. Evict with drop-awareness .
AKV uses drop information to reclaim unused cache before requests finish.
A cache entry becomes evictable only when no ongoing computation or restoration needs it.
For example, in Figure 5 , A A ’s cache can be freed once both requests ① and ② drop it, even as they continue generating D D .
Eviction frees the physical storage but leaves the tree node as an empty placeholder, keeping cached descendants accessible through prefix matching.
Among evictable cache entries, AKV prioritizes evicting dropped cache over cache from completed requests, since the latter is more likely to be reused in the next round. Restore with segment-batch attention .
AKV uses segment-batch attention to restore missing cache states in a single prefill pass.
At each layer, queries are split at drop trigger points, and each segment attends causally to its own tokens and to active cache from earlier segments.
Note that dropped cache is excluded from later segments but remains available to earlier segments that originally used it, as shown in Figure 10 .
Only attention is segmented, while the FFN processes the full sequence as one batch.
This avoids repeating FFN weight reads, a major source of memory traffic, for each segment. 4.2.3 Reposition-aware Cache Management While drop \operatorname{drop} leaves retained cache unchanged, repos \operatorname{repos} efficiently modifies its keys’ position encodings.
Different requests may therefore need the same cache with different position encodings.

Appendix A Appendix A.1 AKV System Design Details A.1.1 Restore with Segment-batch Attention Segmentation .
Building on Sections 4.2.2 and 4.2.3 , AKV restores missing KV states by partitioning queries whenever a drop \operatorname{drop} or repos \operatorname{repos} operation changes the visible history or its position mapping.
Each segment selects the corresponding KV pages and applies standard causal attention, encoding historical visibility without constructing a dense custom mask. Figure 10: Restore with segment-batch attention. The request in (a) produces the four attention segments in (b).
Numbers denote query/key positions; colored cells indicate allowed attention. Example .
Figure 10 illustrates a complete restoration, treating each letter as one token and writing X p X_{p} for token X X at position p p .
Segment 1 computes A 0 , B 1 , C 2 A_{0},B_{1},C_{2} with causal attention.
After dropping B B and repositioning, Segment 2 computes D 2 D_{2} using keys ( A 0 , C 1 , D 2 ) (A_{0},C_{1},D_{2}) .
Dropping D D starts Segment 3: E 3 E_{3} attends to ( A 0 , C 1 , E 3 ) (A_{0},C_{1},E_{3}) .
Although Segments 2 and 3 share a position mapping, they require separate KV views because D D is no longer visible to E E ; drop \operatorname{drop} alone does not compact positions.
The second repos \operatorname{repos} moves E E from position 3 to 2, so Segment 4 computes F 3 F_{3} using ( A 0 , C 1 , E 2 , F 3 ) (A_{0},C_{1},E_{2},F_{3}) . Batched restoration .
Within each layer, AKV writes the newly computed KV states and constructs the additional position versions, such as C 1 C_{1} and E 2 E_{2} , by re-encoding K and copying V.
The segment-specific page lists and query ranges are then submitted together to batched attention.
Thus, all four segments execute within a single model forward pass, without recomputing hidden states for each position version or replaying separate forward passes at operation boundaries. A.1.2 Reposition Scheme Design objective .
Reposition-aware cache management must distinguish positional versions while reusing their shared computational states.
We therefore first identify directly reusable caches via exact matching, then use retrigger matching to find prefixes that are reusable via positional transformation, avoiding unnecessary hidden-state recomputation. Token-node representation .
Each token node is represented as T ⁡ ( x , p ) T(x,p) , where x x is the token ID and p p is the position currently encoded in its cached K.
The position label describes the stored cache, not necessarily the position at which the token was originally computed.
For example, C C is initially computed at position 2 in all three trajectories in Figure 11 .
After repos \operatorname{repos} , trajectories 1 and 3 use ( C , 0 ) (C,0) , while trajectory 2 uses ( C , 1 ) (C,1) .
Operation nodes along the path preserve the operation history that governs computation. Why position labels and reposition nodes are needed . Position labels distinguish cache representations that cannot be used interchangeably.
For example, C C has the same original computation history in trajectories 1 and 2, but is repositioned to 0 and 1, respectively.
Its K encodings therefore differ and require positional transformation before reuse. Reposition nodes distinguish states that share final positions but arise from different computations.
Trajectories 1 and 3 both drop B B after A ​ B ​ C ABC , but trajectory 3 executes R C R_{C} before computing D D .
When D D is computed, the positions of A A , C C , and D D are respectively ( 0 , 2 , 3 ) (0,2,3) and ( 0 , 1 , 2 ) (0,1,2) .
The relative distance between D D and A A changes, while that between D D and C C remains unchanged, potentially producing different hidden states and KV entries for D D .
Both trajectories subsequently drop A A and execute R D R_{D} to move C C and D D to positions 0 and 1.
This later transformation cannot erase the computational difference already established in D D .
The path must therefore retain R C R_{C} before D D to prevent incorrect reuse of D D and subsequent cached states. Exact and retrigger matching .
Exact matching compares all token-node fields: T ⁡ ( x , p ) ≡ T ⁡ ( x ′ , p ′ ) ⇔ x = x ′ ∧ p = p ′ , T(x,p)\equiv T(x^{\prime},p^{\prime})\iff x=x^{\prime}\land p=p^{\prime}, and requires identical operation nodes and their parameters.
Retrigger matching ignores only stored position encoding indices while preserving all operation records: ϕ ⁡ ( T ⁡ ( x , p ) ) = T ⁡ ( x ) , ϕ ⁡ ( Δ ​ P ) = Δ ​ P , ϕ ⁡ ( R ) = R . \phi(T(x,p))=T(x),\qquad\phi(\Delta P)=\Delta P,\qquad\phi(R)=R. Two prefixes are history-compatible if their projections are identical. The system initializes the result with the longest valid exact prefix, then searches compatible branches from the root.
A candidate replaces the current result only if it is valid and matches a strictly longer prefix, preserving exact matches in a tie.
Retrigger matching stops at the first token or operation mismatch.
Selected source caches are copied and positionally transformed as needed before use. Correctness of retrigger matching .
Under fixed model and position encoding configurations and exact arithmetic, identical projected prefixes preserve the token and operation history preceding each token’s original computation.
They therefore produce the same hidden states and unrotated KV content. Repos \operatorname{Repos} operations applied afterward change only K’s positional representation, allowing a source version s s to be transformed into a target version t t as K t = R ⁡ ( p t ) ​ R ​ ( p s ) − 1 ​ K s , V t = V s , K_{t}=R(p_{t})R(p_{s})^{-1}K_{s},\qquad V_{t}=V_{s}, without recomputing hidden states. Preserving operation nodes prevents this transformation from crossing a divergence in computational history.
For example, trajectories 1 and 3 disagree at R C R_{C} before D D , so retrigger matching cannot reuse D D across them.
Finite-precision transformations may introduce rounding error; this correctness argument does not require bitwise equivalence to recomputation. To emulate realistic long-horizon agent workloads with substantial accumulated context, we select the 80 SWE-bench Verified tasks with the largest context lengths in trajectories, without any summary operation. These tasks reflect the difficulty of tasks in long-context reasoning.
We rank tasks by this peak length and shuffle the selected tasks with a fixed seed.
All methods use the same tasks and ordering.
Each method replays trajectories collected under its own context/cache engineering policy, so the number of turns and the output budgets may differ between methods. Trajectory replay .
For each turn, we reconstruct the output token budget from the complete recorded message history, including reasoning and tool-call content, after subtracting the generation prefix already present in the input.
We use temperature 0 and ignore_eos=True to generate the prescribed number of tokens.
The newly generated assistant response is retained in the history for subsequent turns, while tool responses are replayed from the recorded trajectory rather than re-executing the tools.
Recorded terminal inputs without an available assistant response are excluded from replay. Concurrency and measurement windows .
We maintain C C client task concurrency and execute turns sequentially within each task.
The task-count target for each measurement window is max ⁡ ( 3 × C , 30 ) \max(3\times C,30) ; measurements include requests from supplemental tasks used to maintain concurrency.
For AKV at C ∈ { 14 , 16 } C\in\{14,16\} , we truncate the archived runs at the completion of the first 30 tasks in completion order, counting all requests within the resulting window rather than only requests from those 30 completed tasks.
For Standard at large concurrency, KV cache capacity pressure causes repeated prefill, resulting in severe serving degradation.
We therefore report these two runs over a fixed one-hour window, with some requests still unfinished at the cutoff. A.2 Experimental Details A.2.1 Evaluation Configurations Evaluation harnesses .

To explain why our tool-response rolling-drop policy prioritizes dropping older tool-response KV entries, we analyze the attention allocated to different types of historical messages.
Figure 15 shows attention per token across layers averaged over 10 BrowseComp-Plus trajectories.
Older tool responses receive less attention than older reasoning in most displayed layers, while recent history generally receives more attention.
This pattern suggests that direct attention to historical messages depends on both recency and message type, providing empirical support for retaining recent tool responses and reasoning while preferentially dropping older tool-response KV entries.

A.5 Additional Related Works Concurrent works .
Concurrent work adapts KV eviction to the changing attention needs of agent trajectories.
AgentKV ( Liu et al., 2026a ) scores KV entries using query buffers from different execution phases, retaining information that recency-based scoring can miss.
IntentKV ( Li et al., 2026 ) combines cross-turn query memory with learned importance estimates to preserve useful history under limited KV budgets.
SideQuest ( Kariyappa and Suh, 2026 ) explores model-directed retention through an auxiliary reasoning branch that identifies stale tool results and issues cache-deletion commands, but its current strategy is limited to tool responses, and its serving integration is tailored to this specific eviction workflow.
Context Language Models (CLMs) ( Shao et al., 2026 ) primarily study model-driven context management, treating the live context as an editable file and learning how to maintain it.
CLM also introduces Suffix Cache Reuse to preserve unchanged downstream KV states after text edits.
Its serving support centers on session-local reuse: relocated states remain in private buffers outside the shared radix cache, without a unified mechanism for indexing, managing, and recovering these history-dependent states.
AKV addresses these serving concerns directly by exposing policy-independent cache operations through a stateless interface and uses an extended radix tree to track both tokens and cache operation histories, integrating retained states into shared cache reuse, memory management, and recovery.
