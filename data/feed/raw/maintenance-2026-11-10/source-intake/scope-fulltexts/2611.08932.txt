License: CC BY 4.0 arXiv:2611.08932v1 [cs.MA] 06 Nov 2026 \workshoptitle SocialAgent Workshop ODD+LLM: Specifying LLM-Agent Behavior for Reproducible Social Simulation Justin Downes Affiliation: Amazon Web Services Email: jusdow@amazon.com Robby Milletich Affiliation: Amazon Web Services Email: rmilleti@amazon.com Newel Hirst Affiliation: Amazon Web Services Email: nhirst@amazon.com Abstract The ODD protocol is the de facto standard for describing agent-based models, but it lacks
vocabulary for the components that determine LLM-agent behavior: prompt assembly, memory
serialization, parsing, and retry logic. We propose ODD+LLM , a backward-compatible
extension adding five documentation blocks grounded in the CoALA cognitive-architecture
framework. To show that the gap matters, we conduct a multiverse analysis ( Steegen et al., 2016 ) of a published LLM naming-game simulation, varying six specification
choices a reimplementer must make. Variants that are defensible readings of the paper stay
within statistical noise of our baseline reconstruction. Missing one instruction that the
paper states but is easy to overlook (that the model answers as an outside observer rather
than as a player) raises the share of runs settling on the convention agents individually
favor from 0.35 to 1.00 and makes convergence three times faster, in a reimplementation
that uses a different model from the original. We complement the demonstration
with a reconstruction-sufficiency review of 28 published LLM-agent simulations, finding that
the details of how prompts are built and how model outputs are parsed are undetermined in
77% of cases, and that no paper fully specifies its main LLM call.
ODD+LLM gives the field a standard home for information it already produces but currently
scatters across code repositories, supplementary files, and undocumented defaults. 1 Introduction The ODD protocol ( Grimm et al., 2006 ; Grimm et al., 2010 ; Grimm et al., 2020 ) standardized agent-based model
description by providing a structured template complete enough that an independent modeler
can reimplement a model and recover its results. Its core is the Submodels block, where agent behavior is specified as equations or rules; the other blocks describe
the model around it. LLM-agent simulations have no Submodels block, and no vocabulary for writing one. ODD is
already being adopted for this purpose; YuLan-OneSim ( Wang et al., 2025b ) generates
executable simulators from LLM-authored ODD protocols across fifty social-science
scenarios, but the protocols it produces specify agent types and interaction patterns while
saying nothing about how context is assembled or how output becomes an action. An LLM
agent’s action is the output of a sampling
procedure applied to a token sequence assembled at runtime from a system prompt, a persona,
some subset of interaction history, some rendering of environment state, and an output
instruction, then parsed, possibly rejected, possibly resampled, and mapped onto a
simulation action. That assembly procedure is what a Submodels block for LLM agents must
describe. This matters in practice. Ye et al. (2026) hold persona content fixed and vary only its presentation (prose, bullet list, key–value table), observing a
76-percentage-point difference in cooperation rate ( N = 30 N{=}30 seeds, p < 0.001 p{<}0.001 ). Two papers
reporting “agents were given demographic personas” can therefore support opposite
conclusions about whether LLM agents cooperate. ODD+LLM is a reporting standard, not a new algorithm. Like ODD itself and reporting
guidelines such as CONSORT ( Schulz et al., 2010 ) and TRIPOD ( Collins et al., 2015 ) ,
its contribution is what it standardizes and the evidence that those items matter. We make
three contributions: 1. ODD+LLM : a backward-compatible extension to ODD adding five documentation
blocks for LLM-agent simulations (§ 3 ). Blocks C and D use repeated records (one per model role and one per call site), following ODD’s
existing pattern for submodels. The core of the protocol is Block D, the behavioral submodel,
which specifies each LLM call in the loop by signature, binding, and resolution. 2. A multiverse demonstration that specification salience is consequential
(§ 4 ). We take a published naming-game simulation ( Flint Ashery et al., 2025a ) , identify six specification choices (four from supplementary
materials, one in main text but non-obvious, one genuinely open), implement a baseline
and seven one-factor variants, and show that missing a single stated but easily
overlooked instruction determines the headline result. 3. A reconstruction-sufficiency review of 28 LLM-agent simulations coded for
where an independent implementer would have to guess (§ 5 ). 2 Related Work ODD and its extensions. ODD ( Grimm et al., 2006 ; Grimm et al., 2010 ) was extended to ODD+D for decision-making ( Müller et al., 2013 ) , ODD+2D for data-driven models ( Laatabi et al., 2018 ) , vODD-DD for visual
documentation ( Lee and Lazarova-Molnar, 2026 ) , and VISA for machine-reproducible descriptions ( He, 2026 ) . None address the prompt-assembly problem because it did not exist
before LLM agents. The closest antecedent is the move from verbal rules to equations in ODD
2020 ( Grimm et al., 2020 ) , which argued that natural-language descriptions of behavior are
insufficient for reconstruction, precisely the claim we make about LLM-agent descriptions.
VISA opens with nearly our framing (“two readers routinely reconstruct different models
from the same documentation”) but targets classical ABMs rather than LLM-agent behavior. ODD applied to LLM-agent simulation. YuLan-OneSim ( Wang et al., 2025b ) generates executable LLM-agent simulators from
ODD protocols across 50 social-science scenarios. They use ODD forward (natural language → \to ODD → \to code), whereas we test it backward (published study → \to could an implementer reconstruct it?). Their
generated protocols specify agent types and interaction patterns but contain nothing about
which model runs, how context is assembled, or how output is parsed; those choices are
resolved downstream by code templates and configuration. A system that already wants ODD for LLM agents is evidence of demand; that its protocols
stop where Blocks C and D begin is evidence of the gap. Validity critiques of LLM-agent simulations. Larooij and Törnberg (2025) review 35 papers and find systematic validation gaps. Zhou et al. (2025) propose six design-validity principles (PIMMUR) and re-run five papers. Ye et al. (2026) demonstrate that format-only perturbations move outcomes by up to
76pp, though the same perturbation on deepseek-v3 produces ∼ {\sim} 1pp, indicating strong
model-dependence. Barrie and Törnberg (2025) argue that naming-game results are observationally
equivalent to data leakage from pretraining; Flint Ashery et al. (2025b) respond that the
effect survives controls. Our work complements these critiques by providing a specification , and our multiverse analysis measures the range of outcomes
consistent with a description rather than testing whether a specific mechanism is correct. Representation-effect audits. Ye et al. (2026) ’s TRAILS-R taxonomy audits representation-level perturbations (formatting,
delimiter choice, output schema, instruction order, memory representation) that map onto our
Block D items DB-1 through DB-7. We adopt their three-level claim_strength hierarchy (exploratory, mechanism, policy) for our corpus metadata. TRAILS is an audit taxonomy (what to perturb to test robustness), while ODD+LLM is a documentation protocol (what to write down so a
finding can be reconstructed at all). Block D’s resolution layer (parser, validity
constraints, retry, failure cascade, failure rate) has no TRAILS analogue, and our
reconstruction-sufficiency review measures determinability rather than robustness.
TRAILS found that memory representation had the smallest effect among the representation
axes they tested, independently corroborating our Stage 2 finding that memory-format
and memory-order arms (M1, M2) produce small population-level effects relative to person
framing (M4). Cognitive-architecture frameworks. CoALA ( Sumers et al., 2024 ) provides a taxonomy of LLM-agent components (working memory,
long-term memory, internal/external actions, decision procedure). We adopt it as the
ontology for Block A rather than inventing one. DSPy ( Khattab et al., 2024 ) provides a
machine-readable signature format for LLM modules; Block D’s schema draws on it. 3 The ODD+LLM Protocol ODD+LLM adds five blocks to the standard ODD template. The existing ODD blocks (Purpose,
Entities/State Variables, Process Overview, Design Concepts, Initialization, Input Data,
Submodels) are retained unchanged; the extension occupies a new section between Design
Concepts and Initialization. Following ODD’s own pattern (Submodels is already one entry per submodel; State Variables is
a list), Blocks C and D are repeated records . Block C has one record per model role
and Block D one per LLM call site, so documentation grows with the system. A two-agent
dilemma with one call site stays a one-page specification, while a generative-architecture paper with nine distinct calls produces nine
records. 3.1 Block A: Cognitive Architecture (CoALA-structured) Documents the agent’s information-processing architecture using CoALA’s taxonomy (9 items):
working memory contents per cycle; long-term memory types, backing store, retrieval rule
(formula and cardinality), and write rule; internal and external action spaces; decision
procedure (including actions per activation); tools; and the inter-agent communication
channel with its visibility parameter. 3.2 Block B: Identity Documents persona source, content, surface form (the verbatim template), heterogeneity
method, behavioral constraints, and identity stability (static vs. drifting, with the
update rule). The surface-form item is marked as behavioral rather than cosmetic, following Ye et al. (2026) ’s finding. (6 items.) 3.3 Block C: Inference Configuration Block C has a two-item spine at the system level and a per-role record (6 items) repeated for each model or API in the behavior or measurement path. C-spine (system level). • CS1 : Known provider-side non-determinism sources (batching, routing,
caching) and their handling. • CS2 : Execution concurrency and ordering: whether calls are issued
sequentially, concurrently, or asynchronously, and whether intra-timestep ordering is
deterministic. C-role (repeated per model role). Roles observed in the corpus include agent , classifier , judge , embedder , generator (offline content), and external API . Each record
contains: • CR1–CR3 : Model identity (exact version string or pinned snapshot),
build identity (system fingerprint), and provider/endpoint/API version/access date. • CR4 : Decoding parameters, named unambiguously and distinguished from
same-named training or reward parameters. • CR5 : Serving precision and quantization. • CR6 : Training or adaptation (base checkpoint, method, data construction,
objective, selection criterion). Marked NA if used off the shelf. Every model role gets a record. An unnamed embedder is a role record scoring 0 on CR1, not
a footnote. 3.4 Block D: Behavioral Submodel Block D is the ODD Submodels equivalent for LLM agents. Like Block C, it has a two-item spine at the system level and a per-call-site record (15 items) repeated
for each distinct LLM call in the simulation loop. Items within a call-site record are
grouped into four sections: D-spine (system level). • DG1 : Temporal coupling: whether step t t output enters step t + 1 t{+}1 input, and in what form. • DG2 : Scheduling and activation: timestep duration, who acts when,
within-step ordering. Controlled vocabulary adopted from Concordia ( Vezhnevets et al., 2023 ) : simultaneous / sequential / asynchronous . Signature (what the call is). • DS-1 : Input bindings: which state variables feed this call. • DS-2 : Output type or schema. Binding (how it is rendered). • DB-1 : Static text (system prompt and fixed instructions, verbatim). • DB-2 : Serialization per slot: how each variable renders into text. • DB-3 : Component order and system-vs-user role placement. • DB-4 : History policy with cardinality (“top-ranked memories” without a k k is underdetermined). • DB-5 : Truncation/summarization rule with constants. • DB-6 : Token budget and drop order. • DB-7 : Action-space encoding: how the option set is presented. Resolution (how output becomes an action). • DR-1 : Parser: exact extraction procedure. • DR-2 : Validity constraints: what makes a parseable output invalid. • DR-3 : Retry policy: count, whether prompt is modified, fallback on final
failure. • DR-4 : Failure action and cascade: what the system does, and what other
agents observe. • DR-5 : Failure rate (an empirical result, included to force reporting;
analogous to ODD’s “Output Data”). Delegation. • DF-1 : Third-party framework: library name, pinned version , and
which part of assembly or resolution it owns. An unpinned framework dependency is
undetermined. Systems with multiple call sites. Complex architectures may call the LLM in several places (e.g., acting, reflecting,
summarizing memory). Document the primary call site, the one that produces the
agent’s behavioral output, against all 15 items. List any other call sites in a short
inventory that names each one and marks whether it is fully documented. A simple model
stays at one record, and readers can still see how much of a complex architecture is
specified. Block D is designed so that a .yaml configuration file satisfying the schema is the Block D documentation; no separate prose description is needed. The
arm configurations for our multiverse analysis (§ 4 ) are themselves
Block D specifications. 3.5 Block E: Validation Documents behavioral reference, validation level, replication count (E3a) and the unit over
which variance is reported (E3b), variance reporting, representation sensitivity (whether
any prompt-form perturbation was tested), population dispersion, ablation and non-social
controls (E7a), non-LLM or human baselines (E7b), and longitudinal stability. (10 items.) The E3 and E7 splits distinguish papers that state n = 1 n{=}1 from those that never state n n ,
and papers with ablation controls from those with human baselines, distinctions that
collapsed in an earlier draft and obscured the dominant failure mode. 4 Multiverse Demonstration We select Flint Ashery et al. (2025a) , “Emergent social conventions and collective bias in LLM
populations” ( Science Advances , 2025). In this naming game, N = 24 N{=}24 agents
repeatedly choose names from a pool of W = 2 W{=}2 letters; matching earns + 100 +100 , mismatching

disproportionately to one “strong” convention, driven by microscopic asymmetry in
stick-after-success vs. switch-after-failure behavior. We chose this paper because it is well documented by current norms. It reports model
versions, includes real controls, provides supplementary prompts, and publishes code
( github.com/Ariel-Flint-Ashery/AI-norms ). This makes it a conservative test case.

the branch almost never fires, which shows where specification effort matters. 5 Reconstruction-Sufficiency Review We code 28 published LLM-agent simulations (2023–2026) for reconstruction sufficiency,
stratified by architecture: minimal-choice agents, opinion dynamics, platform-scale
simulators, economic/market models, full generative architectures, policy testbeds, and
norm emergence. For each paper, we ask one question per item: could an independent
implementer, reading only this paper and its linked artifacts, determine this, or would
they have to guess? Instrument. Items are scored 0 (undetermined), 1 (partially determined: the
component is named but at least one behaviorally relevant aspect remains open), or 2
(determined). The key distinction is between asserting that a component exists and specifying it. “Agents have a
memory module” asserts a component exists; it does not specify what enters it, how it is
rendered, or when it is cleared. Assertion without operational content scores 1, never 2.
Every score of 0 or 1 generates a named decision point, an independently variable choice
that two implementers could set differently without contradicting the text. The instrument was derived from 10 papers screened in Pass 1 (9 eligible, 1 excluded on
read), during which the repeated-record structure emerged from corpus evidence
then frozen as v1. Pass 2 codes the remaining 19 papers with
the frozen instrument unchanged; decision points that do not fit the block structure are
recorded as misses and reported. Each paper carries a claim_strength label (exploratory, mechanism, or policy;
following the TRAILS hierarchy ( Ye et al., 2026 ) ), letting us test whether the strongest
empirical claims rest on the weakest specifications. Results. Of 32 papers screened, 4 were excluded on read (2 × \times E1, 1 × \times E3, 1 deferred), yielding 28
coded papers across 18 venues and 7 strata (2023–2026); all 28 are listed individually in

different denominators and raw item counts are not comparable. We therefore report three

asks only that it be written in a standard location. For our own study this took one
configuration file plus a results section (DR-5, Block E; Appendix E ). We
have not measured author burden more generally. Our multiverse arm configurations are Block D specifications, and losing one stated item from them produced a
qualitatively different outcome. Limitations. Demonstration. The multiverse is a single case study with 20 seeds per arm. It
shows that one specification item can determine a result but does not estimate how often
this happens across simulations. It uses one model (Claude Sonnet 4.6) with decoding
settings that differ from the original, so magnitudes may differ with other models. The
design is one-factor-at-a-time (8 arms), not a full factorial ( 2 6 = 64 2^{6}{=}64 ); interactions
between axes are untested. With 20 seeds, only M4 is statistically separable; the remaining
branches may modulate outcomes below our detection power. M4 is specified in the source
paper (“external observer”), so first-person framing is a sensitivity test of what happens
when salient-but-non-obvious information is missed, not a defensible reconstruction. Coverage of the protocol. The multiverse exercises six items (DB-1 to DB-4, DG2,
DR-3). The remaining items are motivated by how often the corpus leaves them undetermined
and by prior evidence such as Ye et al. (2026) , not by experiment; validating each item is
future work. Evidence for the standard. The rubric is new and was applied by a
single coder without inter-rater reliability estimation, so the 77% figure is indicative
rather than validated. We have not yet shown that ODD+LLM improves reconstruction or
measured its cost to authors. Double-coding a subset of the corpus and a study in which
readers reconstruct calls from completed specifications are the next steps. The current
protocol assumes text-in/text-out calls; multimodal inputs (images, video frames) to
vision-language models are not covered. Not a critique. Flint Ashery et al. is well-documented by current norms. The information exists;
what is missing is salience , a standard place for choices that are already made. Conclusion. ODD+LLM gives the LLM-agent simulation community a structured home for specification
decisions that determine behavior. It is a documentation convention that reduces avoidable
ambiguity. It cannot guarantee reproducibility, because models change, providers update silently, and
stochastic systems are inherently variable. But the choices a researcher can pin down
should be pinned down. Missing one stated instruction flips a reimplementation’s headline
result; 77% of binding and resolution items across 28 papers are undetermined. Adopting the protocol
costs one configuration file; Figure 1 shows the cost of leaving these
choices undocumented. References Akata et al. [2025] Elif Akata, Lion Schulz, Julian Coda-Forno, Seong Joon Oh, Matthias Bethge, and

What name will Player 1 choose in the next interaction? The first-person arm (M4) replaces the observer wording with second-person wording
(“You are playing a coordination game with another player…”, “What name do you
choose for this interaction?”); the other arms change only the memory block. Parser and retry (DR-1 to DR-4). def parse_choice(raw_output, name_pool):
    m = re.search(r"CHOICE:\s*(\S+)", raw_output, re.IGNORECASE)
    if m:
        cand = m.group(1).strip().strip(’"’).strip("’")
        for name in name_pool:
            if cand.upper() == name.upper():
                return name
    for line in reversed(raw_output.strip().split("\n")):
        for name in name_pool:
            if line.strip().upper() == name.upper():
                return name
