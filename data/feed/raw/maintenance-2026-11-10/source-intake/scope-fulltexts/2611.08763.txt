flexibly to varied instructions, whereas asking a large language model (LLM) to

the entities and actions it references exist in the current Unity scene. Accepted instructions are stored and remain continuously active as the simulation is running. and on a behavioural benchmark CrowdDirector follows user instructions more closely than handwritten
rules while avoiding repeated LLM calls. It therefore provides a practical
middle ground between fixed rules and continuous LLM control. Introduction Crowd simulation is commonly organized as a hierarchy. Global planning selects
routes, local navigation avoids collisions, and behavioural logic determines
which goals and interactions agents should pursue ( Reynolds, 1987 ; Helbing and Molnár, 1995 ; van den Berg et al., 2011 ; Treuille et al., 2006 ) . This separation
supports real-time animation, but the behavioural layer remains expensive to
author. For every event, a designer must decide in advance who is affected,
where those characters should go, and how their current activity is interrupted
or resumed. These requirements become restrictive in interactive
scenes, where the desired response may be introduced only after the simulation
has started. Natural language is an attractive runtime interface because a single
instruction can express intent, scope, and context: for example, “staff gather
at the entrance,” “the coffee machine is broken; redirect anyone waiting for
a drink,” or “keep visitors away from the spill.” Recent systems use
language models to generate agent plans, crowd scenarios, motion, dialogue, and
animation ( Park et al., 2023 ; Ji et al., 2024 ; Cao et al., 2026 ; Li et al., 2024 ; Liu et al., 2025 ) . Direct LLM control, however, is difficult
to place inside a repeated crowd-control loop. The model may reference
objects or actions that do not exist in the scene, or select the wrong agents.
Calling it at every update is also slow, costly, and nondeterministic, and its
output must still respect simulator constraints such as capacity and
navigation. This leaves a practical gap. A runtime authoring system must understand a new
instruction, determine whether it can be carried out in the current scene, keep
it active for the requested duration, and turn it into decisions for many
agents. Handwritten rules make these decisions efficiently, but only
for responses that were authored in advance. Per-tick LLM control can handle
varied instructions, but querying the model at every update multiplies latency
and API cost by the length of the session, even when the user’s
intent has not changed. Our central premise is that the LLM should interpret a new instruction, not
control every agent at every update. CrowdDirector therefore calls the LLM
only when the user introduces or revises an instruction, and only to convert the
text into a structured form. Each new instruction then passes through
three steps: (1) a fixed, programmatic scene validator resolves the named
agents, zones, and objects, checks whether the requested actions exist, and
reports whether all, part, or none of the instruction can be executed; (2) an
accepted instruction is stored as a directive , a checked instruction that
remains part of the simulation state while it is active; and (3) at each later update, a graph neural network policy (graph policy) chooses an available action and target for each agent. The graph policy is trained offline on generated
scenarios. For every decision, short simulation rollouts estimate how well each
available action would turn out, which gives a base training label. When a
decision is related to an instruction, an LLM additionally ranks the same list
of available actions, and this ranking is blended with the base label using
fixed weights (Section 3.5 ). This design uses language to guide responses to an
instruction without allowing the LLM to add actions or targets that the scene
does not support. Our contributions are: (1) A runtime crowd-control framework integrated with Unity that interprets
a natural-language instruction once, checks it against the current scene,
and stores it as an active part of the simulation instead of calling an LLM
at every update. (2) A graph policy that chooses from the actions and targets available to
each agent. It is trained from simulation rollouts, supplemented by
constrained LLM rankings for instruction-related responses. (3) An evaluation against handwritten rules and per-tick LLM
control. It measures whether instructions are checked correctly, whether the right agents respond, and how much each update costs in latency and API calls. 2. Related Work 2.1. Crowd Simulation and Authoring Foundational crowd models generate collective motion through local interaction
rules, continuous forces, reciprocal avoidance, and aggregate flow
fields ( Reynolds, 1987 ; Helbing and Molnár, 1995 ; van den Berg et al., 2008 ; van den Berg et al., 2011 ; Treuille et al., 2006 ; Narain et al., 2009 ) . Empirical work
has further identified compact interaction laws for pedestrian
motion ( Karamouzas et al., 2014 ) . These approaches primarily determine how agents move once a goal is known. Behavioural simulation adds
perception, roles, schedules, and cognitive state to determine what agents do ( Funge et al., 1999 ; Musse and Thalmann, 2001 ; Sung et al., 2004 ; Shao and Terzopoulos, 2005 ; Pelechano et al., 2007 ) . Crowd authoring systems expose higher-level controls through spatial painting,
behaviour trees, semantic environments, and smart objects ( Ulicny et al., 2004 ; Shoulson et al., 2011 ; Kallmann and Thalmann, 1999 ) . Recent learned approaches provide
controllable behaviour profiles, example-driven policies, or interpretable
mesoscopic parameters ( Panayiotou et al., 2022 ; Panayiotou et al., 2025 ; Lemonari et al., 2025 ) . LexiCrowd adds natural-language authoring by learning a
mapping from textual descriptions to continuous simulator parameters for goal
seeking, grouping, and interaction with areas of interest; its training data
consist of LLM-generated text–behaviour pseudo-pairs ( Lemonari et al., 2024 ) .
Its output is therefore a crowd-level behaviour profile. Our focus is different. We address live edits: an instruction arrives while the simulation is running and refers to the entities present in the scene at that time. 2.2. Language-Based Control of Virtual Agents and Crowds LLMs have enabled agents that plan, remember, converse, and acquire skills.
Generative Agents store memories and use them to plan long-horizon
social behaviour ( Park et al., 2023 ) ; Voyager uses repeated LLM calls to
acquire executable skills ( Wang et al., 2024 ) ; and SayCan combines language
with a separate estimate of executable affordances ( Ichter et al., 2023 ) .
Shan and Michel similarly combine an LLM with goal-oriented action planning:
natural-language player commands change the priorities of predefined NPC goals,
and the planner constructs an executable response ( Shan and Michel, 2024 ) . These works use a language model to reason on behalf of a single agent. In crowd animation, Text-Guided Synthesis of Crowd Animation generates group
distributions and velocity fields ( Ji et al., 2024 ) ; CrowdMoGen uses an
LLM-assisted planner for collective motion generation ( Cao et al., 2026 ) ;
and Gen-C uses LLM-generated scenarios to train graph generative models of
crowd actions and interactions ( Panayiotou et al., 2026 ) . These methods map
language to a generated animation, motion pattern, or reusable crowd model. CrowdVLA instead places language-conditioned reasoning inside the runtime
controller. It models each pedestrian as a vision–language–action agent that
uses an agent-centric visual observation to select one of 64 short-horizon
motion skills and replans after executing each skill ( Hwang et al., 2026 ) .
Its goal is context-aware navigation and social-norm compliance through an
end-to-end visual-language policy. Other runtime systems query agent-centric
LLMs to couple dialogue, social state, and navigation ( Liu et al., 2025 ; Wang et al., 2025 ) . CrowdDirector instead interprets a crowd-level instruction once when it arrives, and the resulting directive conditions later graph-policy decisions without further language inference. 2.3. Graph-Based Policies and LLM Training Labels Interactive scenes are naturally relational: agents belong to groups, occupy
zones, reserve objects, and respond to operations targeting other entities.
Graph networks provide an inductive bias for this structure ( Battaglia et al., 2018 ) ,
while relational graph convolutions distinguish typed edges ( Schlichtkrull et al., 2018 ) .
Pointer-style prediction is suitable when outputs select from a variable set of
available choices ( Vinyals et al., 2015 ) . We combine these ideas by
propagating state over a crowd graph and scoring the candidate actions available
to each agent rather than predicting from a fixed action vocabulary alone. Imitation learning and policy distillation train a policy from the
decisions of a more expensive
teacher ( Ross et al., 2011 ; Rusu et al., 2015 ; Hinton et al., 2015 ) . CrowdVLA
applies a related idea to crowd simulation, using simulator rollouts to
supervise the counterfactual outcomes of alternative motion
skills ( Hwang et al., 2026 ) . We follow the same approach, using simulation rollouts together with a language model ranking of the available actions as training labels for our policy. 3. Method 3.1. System Overview CrowdDirector applies an instruction to a running crowd simulation in five
stages (Figure 2 ): (1) an LLM converts the raw instruction into a structured instruction; (2) the scene validator checks that instruction and stores an accepted
result as a directive; (3) the current scene and directive are represented as a crowd graph, and
a candidate generator lists the actions available to each agent; (4) the graph policy selects one candidate action for each agent; and (5) the Unity execution layer carries out the selected actions and requests
replanning when necessary. Only the first stage requires language inference, and it runs only when an
instruction is introduced or revised. The remaining stages form the local
runtime loop. We use one running example throughout this section: in a cafe,
the user states, “The coffee machine is broken; redirect anyone waiting for a
drink.” Figure 2. Overview of CrowdDirector. (a) Offline policy

to scene state, such as disabling the drink affordance of the coffee machine. For the running example, a shortened JSON record is: { "operation": "disable_affordance", "target": {"object": "coffee_machine_1", "affordance": "drink"} } This example and the two later examples omit internal identifiers and timestamps
for readability. The
structured instruction is a claim about the user’s intent, not permission to change the
scene. The scene validator resolves every referenced entity against the live
simulation. For each name, it finds the matching entity in the current
scene and checks that this entity supports the requested action. It returns one of five states: • executable : the complete request is valid; • partially executable : a supported subset can be applied; • unsupported : the requested behaviour is outside the simulator
vocabulary; • ambiguous : several plausible groundings remain; and • invalid reference : a named entity does not exist or has the
wrong type. In the running example, the
validator resolves the coffee machine, verifies its drink affordance, and
accepts the operation. Its shortened output makes the decision explicit: { "status": "executable", "resolved_target": "coffee_machine_1:drink", "scope": "all" } Only executable structured instructions, or partial instructions explicitly accepted by the
user, modify the simulation. This boundary prevents the LLM from inventing an
unsupported action or silently bypassing scene constraints. It also separates
two questions that an LLM can otherwise conflate: what the user appears to
mean, and what the current simulator can actually execute. After validation, the resolved instruction is stored as a directive. It records
who is affected, what scene change is requested, and when the
request should stop. The directive is not a copy of the structured
instruction: it restates the request as a set of scene patches, and one
requested operation may expand into several. An abridged form is: { "intent": "object_disable", "scope": "all", "operations": ["disable drink at coffee_machine_1", "enable drink in lounge", "raise lounge attraction"], "lifetime": "60 ticks" } The directive does not name the agents it affects. It changes the scene rather
than selecting a group, and which agents respond is left to the policy.
The candidate generator and graph policy read all active
directives at every decision update. The coffee-machine directive therefore
continues to redirect agents who become thirsty later, without another LLM
call. A higher-priority interruption may temporarily override it; when that
interruption ends, the original directive becomes active again. 3.3. Representing the Current Crowd Scene The current scene is encoded as a crowd graph with six node
types: • agents , zones , objects , and groups , which
describe the scene itself; and • events and operations , which describe active directives.
An event node records an active situation, and
its operation nodes record the requested scene changes. Directed relations connect these nodes. They record which zone an agent is in, which group it belongs to, which affordances each object offers, and which agents an operation applies to. The graph is rebuilt at every decision update, so a new instruction adds only its own event and operation nodes, together with the relations linking them to the agents and objects it names. A fixed, Maslow-inspired rule ( Maslow, 1943 ) sorts an agent’s nine needs into three
tiers, from basic physical needs up to social and self-fulfilment needs, so an
urgent lower-tier need is addressed before a higher-tier one. Needs grow over
time and fall when the agent performs a relevant action. They follow fixed
simulation rules and are not learned, but they form part of the agent’s node in
the graph. For each agent, the candidate generator then lists at most 64
actions the agent could take now, drawn from the scene, these needs, and the
active directives. Table 1 gives the action types. Each listed
action also records its target and how easy that target is to reach and use,
such as its distance and whether it still has room. Table 1. Action types the candidate generator can list, with examples

targets and to reconsider them once the condition clears. Some directives assign a specific destination, as in
“staff gather at the entrance.” The entrance zone already appears in the graph
and in each staff member’s candidate list, but nothing yet tells the policy
which candidate the directive is pointing at. We therefore mark it with a
single binary directive-target feature: it is 1 for the candidate that
matches the agent’s assigned destination and 0 for every other candidate. This
is a marker, not a priority: it does not add an action or force its selection,
and the policy learns during training how strongly to follow it. 3.4. Choosing an Action for Each Agent The graph policy uses a three-layer relational graph neural network with a
64-dimensional hidden representation (Figure 3 ). Per-type encoders first project the six
node types into the shared space. Relation-specific message passing then
propagates information between connected entities. Each message-passing
layer moves information one edge further through the graph, so the number of
layers equals the maximum path length information can travel. Three layers
allow an agent to receive directive information along three-edge paths such as event → operation → target → agent . \text{event}\rightarrow\text{operation}\rightarrow\text{target}\rightarrow\text{agent}. The graph policy contains no text encoder: natural language has already been
converted into resolved operations and explicit graph state before inference. For each candidate action o o of agent a a , the policy scores
every entry of the agent’s candidate list and normalizes those scores into a
distribution over the list itself. This follows the idea of pointer
networks ( Vinyals et al., 2015 ) : the output is a selection from the input
list, so the number of choices can differ per agent and per update, unlike a
classifier with a fixed set of output classes. policy, and does not run during the loop above. The graph policy learns a probability distribution over each agent’s candidate
actions. Simulation rollouts generate a base label for every decision. For instruction-related
decisions with a valid LLM ranking, the rollout and language distributions are
averaged; routine decisions and invalid or missing LLM outputs use the rollout
distribution alone. Routine decisions. For every candidate action, the data generator clones the headless
simulation and performs K = 8 K=8 perturbed rollouts over a horizon of H = 5 H=5 committed steps. The return is dominated by need relief and event
progress, and penalizes costs such as travel delay and failed actions. Returns
are standardized within the candidate set and converted into a soft target
distribution q roll q_{\mathrm{roll}} . This distribution reflects consequences
that are difficult to infer from a static snapshot, including changing needs,
capacity, travel cost, and contention. Instruction-related decisions. For each world containing an active instruction, one temperature-zero LLM call labels all
agents in that world. The prompt describes the active operations, the
current scene state, each agent’s most urgent needs, and each agent’s numbered
candidate list. The LLM returns the top three candidate indices for each
agent. We assign probability masses of 0.60 0.60 , 0.25 0.25 , and 0.15 0.15 to the
first-, second-, and third-ranked candidates, respectively, forming q LLM q_{\mathrm{LLM}} . Invalid indices, missing predictions, and unparseable
outputs are discarded; in those cases, the simulation label is retained. The
LLM can therefore indicate which available response best follows the
instruction, but cannot invent a new behaviour. The ranking weights express a
strong first preference while retaining two alternatives; they are a fixed
data-generation choice rather than a tuned model parameter. q_{\mathrm{roll}},&\text{otherwise}.\end{cases} This blend retains information about travel, capacity, and contention from the
rollouts while shifting probability toward actions that better follow the
instruction. Both distributions follow the same candidate order, so their

determines how that decision is executed. Our implementation splits this across two
processes. A Python process holds the symbolic state, meaning agent needs,
active directives, and the crowd graph, and runs the trained policy. A Unity 2D
client holds the scene geometry and executes each selected action. The two exchange messages over a WebSocket: Unity
reports what has happened in the scene, and Python replies with the action each
agent should attempt next. After a level is instantiated, Unity reports which objects and zones actually
exist, where each object can be used from, and which of them can be reached.
The policy draws its targets from that report, so an object that was
never placed, or that cannot be reached, is never offered as an action. Unity
then handles path planning and collision avoidance, object interactions, and
animation transitions. An agent keeps its selected action until that action finishes, fails, or
the directive changes, so the policy runs less often than the animation and
agents do not stop and restart on the spot. The interface summarizes the nine needs as five bars, labelled hunger,
thirst, rest, comfort, and social, so that an observer can read an agent’s
state at a glance. This grouping affects the display only. 4. Evaluation We organize the evaluation around three questions. E1 asks whether
the system correctly identifies instructions that the current scene can
execute. E2 asks whether the graph policy selects the intended agents
and responses. E3 measures runtime cost and scaling relative to
handwritten rules and per-tick LLM control. Each question is reported in three parts: how the measurement
was made, what the result shows, and what it implies for the design. 4.1. Evaluation Setup and Comparison Methods Participant reference. Fifteen volunteers (11 male and 4 female; age 18–50+) completed an anonymous,

feasibility judgements and compare both against people. The LLM judges first:
while interpreting the instruction, it also states whether it believes the
scene can execute it. The scene validator then checks the same instruction
against the live scene and returns its five-state verdict, which we reduce to a
binary decision by treating executable and partially executable as supported,
and unsupported, ambiguous, and invalid reference as unsupported. The reference
is the majority Q1 judgement of the participants, and agreement is the

E2: Do Agents Respond to the Instruction? Method. E2 asks two separate questions about a response: whether the right
agents reacted, and whether they did the right thing. Q2 scores the affected
scope as the Jaccard overlap between the agents an approach moves and the
agents participants identified, so both missing an affected agent and moving an
unaffected one are penalized. Q3 scores the chosen response as the proportion
of cases matching the participants’ preferred candidate. The benchmark
additionally reports the acceptable and prohibited rates defined above, and
precision, recall, and F1 over the affected agents. Panel A compares the three
approaches on the matched subset. Panel B removes one component of
CrowdDirector at a time, holding the data, candidates, masks, labels, and
optimization identical, so a change can be attributed to that component. Results: comparison with rules and per-tick LLM. Panel A of Table 4 compares the three approaches.
The ordering is the same on every behavioural measure.
Per-tick LLM control is strongest, CrowdDirector is close behind, and the
handwritten rules are far below both. CrowdDirector roughly doubles the rule
set on both scope and response agreement, and it recovers most of the gap
between the rules and an LLM that reasons at every update.
On prohibited responses the two are effectively level, so the
remaining gap is one of coverage rather than safety: CrowdDirector sometimes
fails to find the intended response, but it is no more likely to choose one the
instruction ruled out.
These results match the intended operating point:
CrowdDirector does not reproduce the full flexibility of recurrent LLM
reasoning, but transfers substantially more instruction sensitivity into
local control than a fixed rule set. Why store an instruction. This comparison is the case for storing the instruction rather than
regenerating it. The handwritten rules show what is lost without language at
runtime: they are efficient, but they only cover responses someone anticipated,
and varied instructions fall outside them. Per-tick LLM control shows what
continuous language buys, and it is real but modest relative to its cost, since
it repeats the same inference even when the user’s intent has not changed.
Keeping the validated instruction as state captures most of that benefit once,
and leaves the repeated work to a component that can run locally. Results: component ablations. Panel B isolates two design choices. Removing the directive-target
marker leaves scope agreement untouched but roughly halves response agreement.
The two are therefore decided separately: the marker tells an already-affected
agent which destination the directive assigned, and contributes nothing to
deciding whether that agent is affected at all. Removing message passing
behaves differently. Response agreement falls less sharply, but affected-agent
recall and F1 both drop and the prohibited rate rises by more than half, which
is the clearest single degradation anywhere in the table. What the graph policy contributes. The two components address complementary failures. A policy cannot follow
an assigned destination unless that assignment is visible in its candidate
representation, which is what the directive-target marker supplies and why its
removal affects only the response. Relational context does something the marker
cannot: it connects an agent’s decision to the surrounding event, object, and
group structure, and without it the policy more often selects a response the
instruction ruled out. One ablation is worth noting against us. Removing the
directive-target marker lowers the prohibited rate slightly, because a policy
that less often pursues the assigned destination also less often reaches the
situation where a prohibited alternative is attractive. The marker improves
instruction following, and that is what it is for, but it does not by itself
make responses safer. 4.4. E3: Runtime Cost and Scaling Method. E3 tests the central runtime premise of CrowdDirector: language is used when
the scene or director’s intent changes, while repeated crowd-control updates
are performed locally. Let N N denote the number of user instructions and T T the number of decision updates in a session. Including one initial
scene-generation call, the API-call counts are (3) A CD = 1 + N , A LLM = 1 + N + T . A_{\mathrm{CD}}=1+N,\qquad A_{\mathrm{LLM}}=1+N+T. Both configurations retain language-based authoring. CrowdDirector removes the
recurrent T T calls from the crowd-control loop. The difference is small
symbolically and large in practice, because T T is the length of the session
while N N is only the number of times the user speaks: for five instructions
over 600 updates, six calls against 606.

estimated cost by nearly two orders of magnitude. Both configurations pay the
same price to author an instruction; the difference is entirely in what
recurs. Local runtime grows close to linearly with crowd size and adds no further
API calls, staying interactive well past the range the policy was trained on.
The whole-crowd LLM interface fails for a different reason: because it
enumerates one assignment per agent, its output grows with the crowd and it
stops returning complete responses shortly above the smallest size tested. Its
limit is the response format, not the reasoning. Multiple calls or a grouped
representation would move it, and CrowdDirector takes the compressed route by
naming the event, scope, and target once and expanding it locally. The policy was trained on crowds of 8–40 agents. The large-crowd experiment
therefore demonstrates computational scaling, not behavioural generalization.
It shows that the crowd graph and graph policy can be evaluated beyond the training
range without language cost; it does not establish that response quality is
unchanged for thousands of agents. Connecting decisions to Unity execution. These savings depend on the boundary the method draws. The Unity
implementation is not a separate decision maker but the execution side of the same
pipeline: the graph policy selects an action and target, and the engine plans
movement, carries the action out, and reports completion or failure. Keeping
that boundary explicit is what makes the recurrent loop cheap, since the
learned component never has to produce physically valid trajectories, and
established navigation and animation systems continue to do the work they
already do well. 5. Conclusion and Future Work We presented CrowdDirector, a framework for directing a running crowd
simulation with natural language. An LLM converts a new instruction into a
structured instruction, the scene validator checks it against the current
scene, the accepted directive remains active, and the graph policy selects a
candidate action for each agent. Unity then executes those choices with its
navigation and interaction systems. The evaluation shows that explicit scene
validation improves agreement with participant judgements and that the graph
policy follows instructions more closely than handwritten rules without
requiring language inference at every update. Per-tick LLM control achieves
higher response agreement in our benchmark, but with substantially higher
recurrent latency and API cost. CrowdDirector therefore provides a practical
middle ground between flexible instruction following and efficient runtime
crowd control. However, we identify several limitations of the present study as follows: (1) the current implementation supports only the actions and interactions defined in its operation library and has been evaluated in 2D environments; (2) the participant study involved 15 volunteers and a limited set of instruction scenarios; and (3) the policy was trained with crowds of 8–40 agents, so the larger-crowd experiment evaluates computational scaling rather than behavioral generalization beyond the training range. Future work will extend CrowdDirector
to richer environments and interactions, evaluate a broader range of
participants and instructions, and improve large-crowd efficiency. Acknowledgements. This work was conducted with the financial support of the Research Ireland
