Existing pruning workflows often target parameter counts, requiring practitioners to manually select model sizes that meet latency, throughput, and GPU memory limits. However, parameter count alone does not predict these metrics, which depend on the model architecture, workload, hardware, and serving engine.
We introduce AutoCompress , a hardware-guided compression framework that directly incorporates such constraints into differentiable architecture search. AutoCompress jointly optimizes global and per-layer structure to produce heterogeneous architectures, guided by serving-engine cost models validated against end-to-end latency, throughput, and memory measurements. We evaluate AutoCompress on long-context local coding, batched datacenter serving, and latency-sensitive in-game interaction.
Compared to the state-of-the-art Minitron pruning framework, AutoCompress improves average accuracy across eight benchmarks by 6.57, 2.35, and 0.57 percentage points on RTX 5070, RTX 5080, and H100, respectively. AutoCompress also compresses Nemotron 3.5 Super from 120B to 74B parameters for single-B200 BF16 serving at 128K context, retaining 95% of its mean benchmark score. 1 Introduction Large language models (LLMs) have demonstrated strong capabilities in reasoning, code generation, and long-context understanding. However, their substantial compute and memory requirements make them expensive to deploy, particularly on hardware with limited resources. In practice, the requirements for deploying an LLM vary considerably across applications and hardware. For instance, a local coding assistant must support long contexts within the limited memory of a consumer GPU, while a datacenter deployment must sustain high throughput when serving many requests concurrently. An in-game character presents a different challenge: the model must generate responses within a strict latency budget while sharing GPU resources with rendering. These scenarios place different demands on model compression, prioritizing memory capacity, batched throughput, or a combination of latency and memory limits. Effective compression therefore requires choosing an architecture that satisfies the specific deployment constraints while retaining as much of the original model’s quality as possible. Existing pruning frameworks provide effective recipes for deriving smaller models, but adapting them to specific deployment requirements still requires substantial manual effort. For instance, Minitron Muralidharan et al. (2024) ; Taghibakhshi et al. (2026) performs architecture search within a user-defined search space and parameter budget, leaving practitioners to translate deployment constraints into suitable pruning targets. Additionally, parameter count alone does not capture the cost of executing a model on the target hardware and serving engine (see Figure 1 ), and memory estimates based only on model weights and the KV cache omit additional allocations, such as execution workspaces and runtime buffers. The search space is another important consideration: restricting layers to uniform dimensions, as in Minitron’s search, excludes architectures that allocate capacity differently across layers. These considerations motivate an automated pruning framework that jointly searches model-wide and per-layer dimensions, supports explicit latency, throughput, and memory constraints, and uses cost estimates calibrated and validated within the target serving environment. To address these challenges, we introduce AutoCompress , an automated, hardware-guided model pruning framework that uses differentiable architecture search to identify compressed models subject to latency or throughput targets, parameter budgets, and memory limits, either individually or in combination. The search jointly optimizes global architectural dimensions and per-layer structure, allowing different layers to retain different sizes and shapes. It uses cost models derived from measurements and allocation rules within the target serving engine. Figure 2: AutoCompress overview. Given a base model and deployment constraints, AutoCompress automatically selects, prunes, and distills an architecture for on-device gaming, local coding, or datacenter serving. The compressed models meet their latency, memory, or throughput targets, measured on real GPUs. As illustrated in Figure 2 , AutoCompress takes a pretrained base model and a deployment target specifying the hardware, workload, and resource constraints, and produces a standalone compressed model. The process is fully automated, from cost modeling and architecture selection to pruning and quality recovery, eliminating manual architecture design and translation of deployment requirements into parameter budgets.
Across three distinct deployment scenarios, AutoCompress improves average accuracy over a deployment-adapted Minitron baseline by 6.57, 2.35, and 0.57 percentage points on RTX 5070, RTX 5080, and H100, respectively, while using approximately 2-3.3 × \times fewer search tokens. We further demonstrate scalability by compressing Nemotron 3.5 Super from 120B to 74B parameters, enabling BF16 serving at 128K context and batch size 16 within 178 GB on a single B200, with a 2.85-point decrease in mean benchmark score. This paper makes the following key contributions: • Hardware-guided compression. We introduce AutoCompress , a differentiable search framework that jointly optimizes global and per-layer structure under latency, throughput, parameter, and memory constraints. • Serving-aware cost models. We develop and validate cost models that capture execution time and memory allocations within the target serving engine. • Diverse deployment objectives. We evaluate AutoCompress on long-context local coding, batched datacenter serving, and latency-sensitive in-game interaction against a deployment-adapted Minitron baseline. • Accuracy within budget. AutoCompress improves average benchmark accuracy by 6.57, 2.35, and 0.57 percentage points on RTX 5070, RTX 5080, and H100, respectively, while meeting deployment targets.

(a) Router outputs define soft architecture masks, updated through gradients from distillation and budget losses. (b) As search progresses, the distributions sharpen toward discrete choices, yielding a heterogeneous architecture. AutoCompress selects a compressed architecture for a specified deployment target by jointly training an architecture router and a weight-sharing supernet.
Given a pretrained parent and a search space, the router learns architectural choices that balance model quality against resource constraints. The selected architecture is then extracted from the parent and recovered through knowledge distillation. 2.1 Deployment Target and Search Procedure Given a pretrained model, which we refer to as the parent , our goal is to derive a smaller model that satisfies a deployment target 𝒟 \mathcal{D} . 𝒟 \mathcal{D} specifies the hardware, serving configuration, precision, and workload, including batch size, cached-prefix length, and input/output lengths. Resource constraints impose a memory limit, a latency limit or throughput requirement, or a combination of these. Our procedure has four stages. First, we construct cost models for the target deployment (see § 3 for more details). Second, we rank the parent’s components by importance and reorder its weights to initialize a supernet , which shares weights across candidate architectures. Third, we jointly train an architecture router, which selects among these candidates, and the supernet using distillation from the frozen parent and resource penalties. Finally, we extract the selected architecture from the reordered parent’s weights and recover its quality through distillation, producing a standalone model. 2.2 Search Space and Shared Weights Our search combines global dimensions shared across layers with per-layer dimensions that allow heterogeneous architectures. Candidate choices depend on the parent model, deployment target, and serving-engine support. We search over hidden size and Mamba head count, together with per-layer expert counts and routed and shared FFN widths. Mamba head count is shared across layers when varied globally. Supported per-layer choices also include zero width to remove a layer: for MoE layers, zero routed width results in a dense MLP when shared width is positive, while setting both widths to zero removes the layer. Thus, layer removal is represented within the same search space as width pruning. § 4.2 specifies the candidate values and fixed dimensions for each deployment. To share weights across candidates, we rank components by activation-based importance and permute their weights so that the highest-ranked components come first ( Muralidharan et al., 2024 ) . This ordering covers residual channels, Mamba heads within each head group, experts, and routed and shared FFN channels. Each candidate therefore uses a subset of the same supernet weights. 2.3 Architecture Router The architecture router learns logits over the candidate values for each search axis, with separate logits for each layer on per-layer axes. As illustrated in Figure 3 (a), these choices define a soft architecture optimized through distillation and budget losses. We sample differentiable architecture choices using Gumbel-softmax ( Jang et al., 2017 ; Maddison et al., 2017 ) : y c = exp ⁡ ( ( κ t ​ z c + g c ) / τ t ) ∑ j exp ⁡ ( ( κ t ​ z j + g j ) / τ t ) . y_{c}=\frac{\exp((\kappa_{t}z_{c}+g_{c})/\tau_{t})}{\sum_{j}\exp((\kappa_{t}z_{j}+g_{j})/\tau_{t})}. (1) Here, z c z_{c} is the logit for choice c c , g c g_{c} is independent standard Gumbel noise, and the sum spans all choices on the axis. The logit scale κ t \kappa_{t} controls the strength of learned preferences relative to noise, while the temperature τ t \tau_{t} controls how closely the relaxed choices approach one-hot selections. Increasing κ t \kappa_{t} and decreasing τ t \tau_{t} progressively sharpen the soft architecture toward discrete choices (Figure 3 (b)); their schedules are specified in § 4.4 . Soft architecture masks. We translate each sampled choice into a mask over the importance-sorted components. A component’s mask is the sum of y c y_{c} over choices that retain it. For example, when choosing between widths 64 and 128, the first 64 channels receive weight one, while the remaining channels receive weight y 128 y_{128} . These masks allow gradients to update architecture choices while the shared weights adapt. Each batch is divided equally among independently sampled configurations. Expert-count masks additionally account for top- k k expert selection, as described in § 6.2 . Joint objective. The frozen parent serves as the distillation teacher, while the router and supernet are trained jointly. We combine logit distillation ( Hinton et al., 2015 ) with a resource penalty: ℒ = ℒ KD + α ​ ∑ r [ max ⁡ ( 0 , ρ r − 1 ) + max ⁡ ( 0 , 1 − δ − ρ r ) ] . \mathcal{L}=\mathcal{L}_{\mathrm{KD}}+\alpha\sum_{r}\left[\max(0,\rho_{r}-1)+\max(0,1-\delta-\rho_{r})\right]. (2) Here, ℒ KD \mathcal{L}_{\mathrm{KD}} is the forward KL divergence from the parent’s token distribution to the sampled supernet’s distribution. For each constrained resource r r , ρ r \rho_{r} is the cost predicted from the soft architecture choices divided by its budget. For example, a latency cap T max T_{\max} gives ρ T = T ^ / T max \rho_{T}=\hat{T}/T_{\max} . At a fixed workload, a throughput requirement is expressed as an upper bound on serving time. The coefficient α \alpha balances resource constraints against distillation, while δ \delta controls the permitted unused budget. We use δ = 0.02 \delta=0.02 , yielding zero penalty between 98% and 100% of each cap. The penalty discourages budget violations above this band and encourages greater capacity below it. 2.4 Architecture Extraction and Recovery Once architecture search converges, we select the highest-logit choice from each router gate and evaluate the resulting discrete architecture using our cost models. We initialize the selected model with the corresponding weights from the importance-sorted parent and recover its quality through logit distillation (§ 4.5 ). Recovery thus starts from the retained parent weights, not the trained supernet weights. 3 Modeling Deployment Cost Figure 4: Measuring per-layer latency and memory (1) A model with multiple different layer configurations is instantiated. AutoCompress uses cost models to estimate each search candidate’s latency, throughput, and memory usage under the target serving configuration. We instead measure individual layer configurations within the target serving engine and combine their runtimes to estimate model latency. A deployment scenario 𝒟 \mathcal{D} specifies the hardware, serving configuration, precision, and workload, including concurrency, batch size, and input and output lengths. (3) Here, d d is the global hidden size, L L is the parent’s layer count, and a ℓ a_{\ell} specifies the configuration at layer ℓ \ell . The measured runtime t ℓ t_{\ell} is zero for a removed layer, while T 0 T_{0} accounts for embedding, the LM head, sampling, and serving-engine overhead. Measurement procedure. Each profiling run serves a short model containing approximately ten different layer configurations initialized with dummy weights. We match the target deployment’s engine, precision, batch size, sequence lengths, and cache settings, and use Nsight Systems traces to measure GPU time at layer boundaries separately for prefill and decode. A single run therefore populates multiple entries in the timing table (Figure 4 ). We estimate each candidate’s latency by summing its corresponding entries and adding T 0 T_{0} . Profiling within the serving engine captures deployment-specific kernels and execution behavior. However, architectural changes can affect kernel selection, cache behavior, and overhead, limiting the accuracy of an additive estimate. We validate these estimates on complete architectures excluded from timing-table construction (§ B.1 ). 3.2 Memory For architecture a a under deployment scenario 𝒟 \mathcal{D} , we estimate serving memory as M ^ ​ ( a ∣ 𝒟 ) = W + C + P + R + ϵ 𝒟 . \hat{M}(a\mid\mathcal{D})=W+C+P+R+\epsilon_{\mathcal{D}}. (4) Here, W W is weight memory computed from tensor shapes and deployed data types. The request cache C C includes attention KV and Mamba convolution and SSM caches, sized for the target sequence length and batch size. The prefill workspace P P depends on the query-head configuration and prefill chunk size, while runtime buffers R R include MoE matrix-multiplication and Mamba projection workspaces sized by the relevant widest layers. The allowance ϵ 𝒟 \epsilon_{\mathcal{D}} accounts for CUDA context, graph allocations, and other unmodeled memory. We therefore adapt the Minitron pruning and screening procedure ( Muralidharan et al., 2024 ) to use our serving-cost models, with the same importance-sorted parent and deployment budgets as AutoCompress . We call this new baseline Minitron++. We use uniform per-layer dimensions and retain all layers. We enumerate combinations from Table 2 , except on RTX 5070, where Mamba head counts range from 64 to eight in steps of eight and zero FFN widths are excluded. We retain candidates within 5% below every resource cap that cannot be enlarged along any axis without shrinking another or violating a constraint. This yields 6, 11, and 95 candidates for RTX 5070, RTX 5080, and H100, respectively. We use a wider band than AutoCompress ’s 2% because the latter admits only one maximal RTX 5080 candidate. Each candidate receives 100 distillation iterations (approximately 1.7B tokens), using the target’s batch size, data, and peak learning rate. We select the candidate with the lowest mean loss over iterations 76–100. For H100, we first rank all 95 candidates by loss before training and screen only the top five. The selected architecture receives the same recovery training as AutoCompress ’s student. 4.4 Search Training Details Router and optimization. Each router gate is a two-layer network with hidden width 256. Its output layer is zero-initialized, while the first layer is randomly initialized. The router uses a learning rate of 2 × 10 − 3 2\times 10^{-3} without warmup. The supernet uses peak and minimum learning rates of 4 × 10 − 5 4\times 10^{-5} and 5 × 10 − 6 5\times 10^{-6} , with a 60-step warmup. Each batch contains 2048 sequences of 8192 tokens, divided equally among 32 sampled configurations. Sampling schedule and termination. Over 250 steps, the logit scale in Eq. 1 increases linearly from 1 to 10, while the temperature decreases geometrically from 1.0 to 0.05. Approximately 0.4% of samples use hard one-hot choices. We extract an architecture once every gate assigns at least 0.95 probability to its leading choice. The reported architectures were extracted at iterations 170, 249, and 179 for RTX 5080, RTX 5070, and H100, respectively. Budget-weight selection. The resource penalty is zero between 98% and 100% of each cap. We selected α = 0.3 \alpha=0.3 through an H100 sweep and reused it for RTX 5080. RTX 5070 uses a higher budget weight of α = 1 \alpha=1 due to its tighter budget constraints. Parallelism. RTX 5080- and H100-targeted searches use eight-way tensor parallelism and eight-way expert parallelism across 32 H100 nodes. The RTX 5070-targeted search uses four-way tensor parallelism and eight-way expert parallelism across 8 H100 nodes. We then analyze the search dynamics and learned architectures to understand how distillation and resource constraints shape global and per-layer choices. 6.1 Router Initialization Random router-output initialization creates an initial bias over architecture choices. Learning-rate warmup limits the early updates that could correct this bias before the sampling distribution sharpens. We therefore initialize the router’s output layer to zero and remove router warmup, while retaining warmup for the model weights.
In the RTX 5080 comparison, this configuration selects an architecture with 10.9% lower distillation loss than random router-output initialization with warmup, as shown in Figure 7 . We have found that this reduces traffic to experts retained only by larger architecture choices. These experts then contribute little gradient to the architecture router. As an alternative, output masking applies the soft mask after expert selection, preserving access to these experts during search.

On H100, AutoCompress and Minitron++ select the same hidden size and Mamba head count. Minitron++ uses uniform MoE routed expert counts and intermediate sizes, while AutoCompress varies both across layers. At the same throughput target, AutoCompress achieves 0.6% lower distillation loss and 0.57 percentage points higher Avg 8 (Table 3 ). These gains come with a 3.3 × \times reduction in architecture-selection tokens relative to Minitron++. Complete architectures are given in Appendix A . 7 Related Work Structured LLM pruning. Structured pruning reduces model size by removing layers, attention heads, or hidden and intermediate dimensions ( Xia et al., 2022 ; Ma et al., 2023 ; Xia et al., 2024 ; Ashkboos et al., 2024 ; Men et al., 2025 ) , with recent work extending pruning and recovery to large MoE models ( Tang et al., 2026 ) . Minitron ( Muralidharan et al., 2024 ) combines importance-based pruning with knowledge distillation; we follow this recipe to initialize our supernet and adapt its architecture-selection procedure as our evaluation baseline. These methods primarily optimize retained structure and quality recovery at a prescribed model size or compression ratio. Hardware-aware approaches incorporate execution cost into architecture selection. ZipLM ( Kurtić et al., 2023 ) iteratively removes components according to their loss–runtime trade-off, while SPRINT ( Park et al., 2025 ) selects sublayers using latency reduction and post-pruning tunability. Related approaches include latency-constrained knapsack optimization ( Shen et al., 2022 ) , hardware-in-the-loop architecture search for mobile deployment ( Huang et al., 2026 ) , and joint optimization of latency and model size ( Ali et al., 2026 ) .
Puzzle ( Bercovich et al., 2024 ) is particularly relevant: it
evaluates candidate block replacements using blockwise distillation, selects a heterogeneous architecture through mixed-integer programming under throughput and memory constraints, and recovers quality through global distillation. Its formulation selects per-layer replacements at a fixed hidden dimension and does not support hidden-dimension pruning. The hybrid MoE extension introduces iterative compression, heterogeneous expert widths and routing budgets, and Mamba state pruning ( Bercovich et al., 2026 ) ; however, the public implementation does not include Mamba head or expert-width pruning. In contrast, AutoCompress jointly optimizes hidden size, Mamba head count, and per-layer MoE structure through differentiable search, guided by serving-engine cost models calibrated to the target hardware, workload, and precision. Cost models and serving. Prior work highlights the need to validate latency predictors for both accuracy and architecture ranking ( Akhauri and Abdelfattah, 2024 ; Zhang and others, 2021 ) . MoE serving costs also depend on execution phase and parallelism, which FLOPs alone do not capture ( Patel et al., 2026 ) . Complementary approaches optimize runtime memory use ( Ukarande et al., 2026 ) or serving configurations for a fixed model ( Cho et al., 2026 ) . We instead guide architecture search with cost models derived from serving-engine measurements and allocation rules ( Kwon et al., 2023 ) , using the target workload and precision, and validate their predictions on held-out models running on the target hardware (§ B.1 ). 8 Conclusion We have presented AutoCompress , a hardware-guided compression framework that jointly optimizes global and per-layer structure under latency, throughput, parameter, and memory constraints. Its cost models capture execution time and memory allocations within the target serving engine, accounting for the hardware and workload used in deployment. A budget-aware architecture router combines these cost estimates with distillation signals to learn how much capacity to retain across layers. The selected architecture is extracted from the parent and recovered through distillation, producing a standalone model without manual architecture design. Across long-context local coding, batched datacenter serving, and latency-sensitive in-game interaction, AutoCompress improves accuracy over the deployment-adapted Minitron++ baseline. With matched recovery training, Avg 8 increases by 6.57, 2.35, and 0.57 percentage points on RTX 5070, RTX 5080, and H100, respectively, while architecture-selection tokens decrease by factors of approximately 2.0, 3.0, and 3.3.
All selected architectures meet their predicted deployment budgets, with serving measurements confirming latency and memory adherence for both RTX AutoCompress students.
The 120B-to-74B Nemotron 3.5 Super case study extends these results to larger models, enabling single-GPU BF16 serving at 128K context while retaining approximately 95% of the parent’s mean benchmark score.
