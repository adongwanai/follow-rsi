In addition to the widely studied directions of parameter tuning and harness optimization, we propose the third direction: optimization over stationary environments. Agents are often deployed in rich environments shared by many tasks, such as a company’s Slack workspace or a complex collection of data sources, documents or tickets. We call these environments stationary environments . We introduce EnvOpt , a method for automated end-to-end optimization of stationary environments for any given model and harness, using real or synthetic tasks without needing any graders or reference answers. On AutomationBench, EnvOpt reduces the cost of Claude Haiku 4.5 by 72.7% and raises its pass rate by 14.34%. The same environment transfers to Opus 5, cutting its cost by 68.1% with a 1.34% gain. Added on top of Meta-Harness’s optimized harness for Haiku 4.5, it lowers cost by a further 83.4% and adds 11.17% accuracy over Meta-Harness alone. Across 5 benchmarks, EnvOpt significantly reduces the cost of agents while improving or maintaining pass rate, and is transferable to different models and different harnesses. We also discuss common successful and rejected environment optimization strategies during automated optimization. More broadly, our results show that how information is represented to an agent shapes both its cost and its success, making the environment worth optimizing in addition to the parameters and the harness. 1 Introduction An LLM agent’s cost and success rate depend on three things: the model parameters, the harness, and the structure of the environment it interacts with. The first two are actively optimized through parameter tuning and harness optimization ( Lee et al., 2026 ; Agrawal et al., 2026b ) , while the environment is often considered immutable. Yet, the same information can be given to an agent in very different forms. For example, a company’s Slack history can either sit behind a remote server and be accessible via MCP or exported in plain text files that can be read and searched with terminal tools like grep. This choice alone can significantly affect how much work the agent needs to perform to solve a task ( Mak et al., 2026 ) . In this paper, we propose optimizing stationary environments as a third axis for improving LLM agents, alongside model parameter tuning and harness optimization. Stationary environments refer to environments with large collections of artifacts that remain the same or are similar across many tasks. For example, a banking agent uses the same enterprise platforms and databases for a massive number of queries; many tasks for a company’s Slack assistant depend on the same Slack workspace; feature requests for a toolkit can rely on the same code repository. We aim to optimize how the stationary environments are organized and represented to agents. Figure 1 : EnvOpt on AutomationBench. Left: EnvOpt costs around USD $150 for an offline optimization of the stationary environment in AutomationBench, and saves cost of running Claude Opus 4.8 by 77.5%, easily saving many times the cost of running EnvOpt . Lines are derived by random sampling actual cost of running the test set tasks. Right: Illustration of how offline optimization works in EnvOpt . With a fixed model and harness, EnvOpt uses disjoint sets of training tasks (without verifiers) at each step to optimize the environment. After each step, the optimized environment is tested on a separate validation set to determine when the whole process should be stopped. Though the environment has not received the same systematic optimization as model parameters and harnesses, previous work has shown that refining agent-environment interactions can improve agent performance. SWE-agent ( Yang et al., 2024 ) and subsequent work ( Xu et al., 2026 ) showed that the same model fixes more issues with fewer steps when given a better interface to the repository ( Xu et al., 2026 ) , but these interfaces were manually designed. Later work reshapes environments to create more training signal for reinforcement learning (RL) ( Lu et al., 2026 ; Huang et al., 2026 ) , but these modifications are designed to improve model training rather than the execution efficiency of deployed agents. PREPING and corpus2skill mainly focus on distilling information from the environment into reusable agent memory and skills, rather than directly optimizing how the stationary environment itself is organized and represented ( Choi et al., 2026 ; Sun et al., 2026 ) . In sum, the community has explored how to utilize environment during RL, optimize the tool interface of environment, or refine the environment for specific use cases, but environment optimization itself as the third direction of agent optimization remains underexplored. We present EnvOpt , which is an automated pipeline to optimize the environment for any agent and any stationary environment. Using training tasks without verifiers, we let a coding agent, equipped with access and budget to run a target agent on the stationary environment, to optimize the environment representation for the target agent. The optimization target includes what the environment holds (e.g. adding a database to the environment or restructuring it) and ways it is exposed to the target agent (e.g. new API endpoints). The optimized environment is monitored with a validation set with verifiers to track cost and pass rate, and tested on a held-out test set. Across five benchmarks covering workspace tasks, data engineering tasks, and software engineering tasks (see Section 3 ), EnvOpt reduces the cost of the target agent on unseen test sets by an average of 48%, with higher or similar pass rates. On AutomationBench ( Shepard and Salimans, 2026 ) , EnvOpt outperforms Meta-Harness ( Lee et al., 2026 ) by 9.67% pass rate with only 15% of its cost. We also show that EnvOpt constitutes an optimization direction orthogonal to harness optimization and parameter tuning in two ways: (1) the environments optimized for the target agents can transfer to other agents, even to those with different harnesses and to models stronger than the one proposing the optimizations; (2) we applied the environment from EnvOpt on top of Meta-Harness and observe similar cost reductions and 16% improvement in pass rate, outperforming either Meta-Harness or EnvOpt alone. Our contributions are as follows: • We define environment optimization over stationary environments as a new orthogonal direction for improving LLM agents. Our method can be combined with parameter tuning and harness optimization. • We develop EnvOpt , an automated pipeline for environment optimization, and show that across 5 benchmarks over 3 types of tasks, it can significantly reduce the cost of running agents on unseen tasks while improving or maintaining the pass rates. • We demonstrate that EnvOpt is indeed orthogonal to parameter tuning and harness optimization by showing strong transferability of environment optimizations to different frontier models and harnesses, and that EnvOpt can further improve results combined with Meta-Harness. • We systematically discuss the accepted and rejected design choices during running EnvOpt , which can be used for future work on environment optimization. 2 Method EnvOpt is an automated research pipeline that uses a coding agent such as Codex as a research agent R R to automatically optimize the environment representation for another target agent T T on tasks sharing a stationary environment. We denote a stationary environment as E ⁡ ( I ) E(I) , where I I is the information underlying the environment, such as the conversations in a Slack channel; E E is the representation of that information in a specific format, such as an official Slack workspace accessible via MCP tools or a Markdown file storing all the conversations. Our premise is that for a fixed I I needed for the tasks, a better representation E ∗ ​ ( I ) E^{*}(I) can significantly improve the token efficiency of agents on the tasks and, in some cases, improve accuracy as well. Given task instances X train , X val , X test ∼ 𝒳 X_{\text{train}},X_{\text{val}},X_{\text{test}}\sim\mathcal{X} on the initial stationary environment E 0 ​ ( I ) E_{0}(I) , the objective of EnvOpt is to find E ∗ E^{*} that minimizes the cost of the target agent T T on 𝒳 \mathcal{X} : E ∗ = arg ⁡ min E ​ 𝔼 x ∼ 𝒳 ​ [ cost ⁡ ( T , E ⁡ ( I ) , x ) ] . E^{*}\;=\;\arg\min_{E}\;\mathbb{E}_{x\sim\mathcal{X}}\bigl[\mathrm{cost}\bigl(T,E(I),x\bigr)\bigr]. (1) Environment Evolution As illustrated in Algorithm 1 , EnvOpt optimizes E ⁡ ( I ) E(I) over N N steps. At step k k , the research agent R R is spawn in a sandbox and given a set of training tasks X k ⊂ X train X_{k}\subset X_{\text{train}} , the stationary environment E k − 1 ​ ( I ) E_{k-1}(I) from step k − 1 k-1 , the access to running the target agent T T , and a set budget. We only provide a subset of X train X_{\text{train}} , since too much context for LLM-based optimization has been shown to be harmful ( Li et al., 2026 ) . We provide disjoint sets for tasks for each step to prevent overfitting. The research agent is instructed to run T T on E k − 1 ​ ( I ) E_{k-1}(I) , analyze the trajectories, and edit E k − 1 ​ ( I ) E_{k-1}(I) as a directory in its filesystem to reduce the cost of T T on X k X_{k} without hurting the pass rate (which the research agent judges on itself by proxies or answer consistency, since no verifier is provided for the training tasks as elaborated below). For example, if E k − 1 ​ ( I ) E_{k-1}(I) is a big directory of files with no structure, E k ​ ( I ) E_{k}(I) can be edited to have a separate directory for each domain, make cheat sheets on how to access things, build a small database, make a new tool endpoint for better tool calling, etc. In cases where the environment is highly similar but not identical across tasks, a program can be written to automatically convert a new environment (see ). In implementation, we use frontier agents as the research agent, and give it freedom to choose any design choices. The research agent iterates internally over the step- k k training tasks and deliver the best E k ​ ( I ) E_{k}(I) it can find at the end of the step. Notably, we do not allow the research agent to modify the harness of T T (any changes, though not observed in our experiments, will be discarded at the end of the step). This makes our environment evolution an orthogonal direction to harness optimization, and a good environment can show significant cost reduction even for different agents ( ). This also mitigates the scarcity of high quality tasks for some stationary environments, as we can synthesize in-distribution queries (without synthesizing the verifiers) for training (see Section 3 ). We keep a separate validation set X val X_{\text{val}} with verifiers and run the target agent with E k ​ ( I ) E_{k}(I) on it at the end of each training step k k to decide when to stop the environment evolution. Concretely, if cost ⁡ ( T , E k ​ ( I ) , X val ) > cost ⁡ ( T , E k − 1 ​ ( I ) , X val ) \mathrm{cost}\bigl(T,E_{k}(I),X_{\text{val}}\bigr)>\mathrm{cost}\bigl(T,E_{k-1}(I),X_{\text{val}}\bigr) , or if the pass rate on the validation set becomes significantly worse than step k − 1 k-1 , we stop the evolution and use E k − 1 E_{k-1} as the final optimized environment. 3 Experiments We evaluate EnvOpt across 5 benchmarks over 3 types of tasks: workspace tasks (AutomationBench ( Shepard and Salimans, 2026 ) , Workspace-Bench ( Tang et al., 2026 ) ), data engineering tasks (Data-Eng-Bench ( Snowflake Inc., 2026 ) ), and software engineering tasks (Bleve repository tasks as used in gskill ( Agrawal et al., 2026a ) and the SWE Agent Efficiency tasks as used in advisor models ( Asawa et al., 2026 ) ). Comparing with the baseline, we observe substantial cost reduction up to 88%, with higher or similar agent success rate. We also show that across all tested scenarios, the optimized environment can also greatly improve token efficiency and pass rate for different harnesses and different models, including agents stronger than the target agent, demonstrating strong transferability. Notably, EnvOpt can also build on top of harness optimization methods like Meta-Harness and further push the Pareto frontier. AutomationBench includes workspace tasks that ask an agent to answer questions or complete work inside an enterprise environment, often covering multiple platforms such as Slack, GitHub, Gmail, Salesforce, etc. From the 600 publicly available tasks, we randomly sample 200 tasks for X test X_{\text{test}} , 96 for X val X_{\text{val}} , and use the rest for the training task pool. Training proceeds with 20 tasks per step and stops at step 5, where results on X val X_{\text{val}} begin to saturate. We use Claude Code ( Anthropic, 2025a ) with Claude Opus 4.8 ( Anthropic, 2026b ) as the research agent, and Claude Code with Claude Haiku 4.5 ( Anthropic, 2025b ) as the target agent. As shown in , we observe substantial improvement of token efficiency and pass rate for the target agent, with a final cost reduction of 72.7% and pass rate increase of 14.3%. We show the per-step performance in . We also run GEPA ( Agrawal et al., 2026b ) and Meta-Harness ( Lee et al., 2026 ) using the same training task pool, same research agent or proposer, same target agent, and evaluate on the same X test X_{\text{test}} . EnvOpt produces an environment that that achieves significantly better outcomes on both cost and pass rate, even without verifiers for training tasks. We also examine the transferability of the optimized environment across different harnesses and models, with an average cost reduction of 75.7% and generally higher pass rates. Notably, EnvOpt with a research agent of Claude Code and Opus 4.8 is able to transfer to Claude Code with Opus 5 ( Anthropic, 2026c ) . Haiku 5.5 ( Anthropic, 2026a ) with EnvOpt achieves pass rate higher than Opus 4.8 and even close to Opus 5. Additionally, EnvOpt can be applied on top of Meta-Harness to further improve agent’s token efficiency and pass rate. Using the optimized harness for Haiku 4.5, EnvOpt can further push the Pareto frontier for Haiku 4.5. When transferring to Opus 5, although Meta-Harness alone does not show gain on pass rate, EnvOpt on top of Meta-Harness still improves the pass rate with much lower cost. Workspace-Bench evaluates agents on workers’ personal workspaces, including researchers, engineers, product managers, etc. We use the public set of 100 tasks as used in the official leaderboard and split into 80 tasks for X test X_{\text{test}} and 20 for X val X_{\text{val}} . Since our training steps do not require verifiers and the number of tasks is sparse for this benchmark, we directly synthesize queries without verifiers with Claude Code and Claude Opus 5 to serve as training tasks. We provide 20 distinct training tasks per step, and use Claude Code with Opus 4.8 as the research agent, Codex ( OpenAI, 2025 ) with GPT-5.4-mini ( OpenAI, 2026b ) as the target agent. Claude Code with Sonnet 5 is used as the judge agent for evaluation on X test X_{\text{test}} and X val X_{\text{val}} . We present the results in . We observe 47.65% in cost reduction and 3.3% in pass rate improvement for the target agent. On transferability to non-target agents, we evaluate on Codex with GPT-5.6-Sol ( OpenAI, 2026a ) and Claude Code with Opus 5, and observe an average 56.7% cost reductions with steady pass rates compared with the baselines. Data-Eng-Bench evaluates agents on dbt data engineering tasks. We use 73 tasks as X test X_{\text{test}} and 19 as X val X_{\text{val}} . Similarly, due to the scarcity of existing tasks, we synthesized queries without verifiers for training, with 20 distinct tasks per step. We use Codex with GPT-5.6-Sol as the research agent and Codex with GPT-5.6-luna as the target, and reduced cost by 53.44% without hurting the performance. On non-target agents, we observe an average cost reduction of 53.54% (see ). Software Engineering Tasks We take two benchmarks from previous work that improves token efficiency of agents on SWE-Bench style tasks, where an agent is asked to fix a bug in a given code repository, with all tasks sharing the same codebase. gskill optimizes skills for coding agents using tasks with verifiers from the same codebase and reports higher pass rate and faster completion time on the Bleve search library. Advisor models ( Asawa et al., 2026 ) uses reinforcement learning to train an advisor model that produces advice to the coding agent. On the SWE Agent Efficiency benchmark based on the tenacity library, advisor models maintains the same pass rate as baseline while using significantly fewer steps. We run EnvOpt using the same X train X_{\text{train}} , X test X_{\text{test}} , and X val X_{\text{val}} as provided by gskill and advisor models and use the same target agent. As shown in Fig. 2 , on Bleve repository, EnvOpt remains close to perfect score using only 56.9% of the completion time of gskill . On the tenacity repository, EnvOpt achieves 8.9% higher pass rate with fewer steps than Advisor Models . These results show that EnvOpt significantly outperforms other methods to improve agent token efficiency even on software engineering tasks. The target agent can thus directly read the text instead of spending tokens on massive tool calls. On Workspace-Bench, different formats of files such as .xlsx are converted to .txt files so that the target agent can read the files more easily and do not need to do further parsing. Making Cheatsheets Cheatsheets that store important information for future tasks are created during training. For example, a cheatsheet for AutomationBench stores all the API endpoints the agent needs to create Jira issues, post messages on Slack, record a Xero payment, etc., so it does not need to call api_search or api_fetch to get the endpoints. For the Bleve repository bug fixes, a cheatsheet was built that stores template commands for complex tool calls, so the agent does not need to compose search commands from scratch. Indexing For Workspace-Bench, the agent is deployed with massive amount of files simulating an enterprise employee’s computer. The research agent thus builds a indexing map as a single text file, that stores the paths, sizes, and types of all files needed, so the can simply search over the indexing file instead of spending tokens and time on the huge filesystem. Building Database On Data-Eng-Bench, the research agent built an SQLite database that stores the locations of tables, which files each code script writes to, what are the types of information stored in each table, etc. The target agent can quickly locate the information needed without browsing through thousands of files. Building Programs that Ranks File Priority For the Bleve repository, the research agent built a program that takes any bug report and outputs the 8 .go files that are most likely to be impacted based on keyword matching. The target agent can quickly locate the files it potentially need investigate to fix the bugs. Automated Testing of Edits For the Tenacity repository, a validate_tenacity.py is built to automatically fetch the code change made by the target agent, search for relevant test files, run the tests, and return verdicts. This quickly validates candidates edit with no extra token cost and speeds up the whole bug fix workcycle for the target agent. 4.2 Rejected Environment Optimizations We summarize environment optimizations that are discarded during training or after running on X val X_{\text{val}} : Storing too much information in one file leads to more exploration For Data-Eng-Bench, the research agent tried to create a big file to store all possible values for all columns in a database. Though this is meant to help the agent retrieve the correct information with less token, putting everything into a big file encouraged the agent to make more tool calls to explore the values, since one tool result reveals to the agent that there is much information it has not explored, which eventually increased the cost. Building a search tool that returns too many files causes more reading For Workspace-Bench, a search tool was built to help the agent locate the files that it needs to read for the task. Though the tool successfully reduced token cost for searching the needed files, it often included unnecessary files in the search results, which motivated the agent to read more files, thus increasing the cost. Adding tests that only fit a subset of the training tasks In step-2 of EnvOpt on the Bleve repository, a check was added to a test script in the repository that scans for a particular bug fix code snippet and fails the test directly if the snippet is present. This was meant to save the time needed to fix a bug and worked well for X 2 X_{2} . However, for X 3 X_{3} , some correct bug fixes were rejected by this additional check, and the agent needed to spend much more time to bypass the check. 4.3 Cost Reduction Analysis To illustrate where the cost reduction of EnvOpt comes from, we break down input tokens and output tokens into categories, including different kinds of tool calls, tool execution results (environment feedback), thinking tokens, agent history, etc. We compare the numbers of tokens of each category between the baseline environment and EnvOpt environment, and show results in . We observe that the most significant token cost reduction comes from the environment feedback categories for the input tokens. There are also significant savings on the tool call categories of the output token side. These results align with our motivation to optimize the environment for better agent interaction. 4.4 Ablation: Tool Optimization Only During environment optimization, EnvOpt can also optimize ways to access the new environment, including new tools. We study the effectiveness of only using the new tools. On AutomationBench, we test Claude Code with Haiku 4.5 on the original environment E 0 E_{0} with the tools from E 5 E_{5} . As presented in , we find that tool optimization alone can lead to improvements on both token efficiency and pass rate, but is significantly lower than optimizing both the tools and the environment. Since tool optimization might be covered by harness engineering, this ablation shows that EnvOpt brings significantly more headroom for optimization in addition to harness engineering. 4.5 Training Cost and Time We present the total training cost (including the cost of target agent runs launched by the research agent) and clock time for all 5 benchmarks in . In , we compare the cumulative training cost with the cost saved for running different agents on unseen tasks, assuming there are 1000 such tasks. We show that for frontier agents deployed in large scale, we can easily save more than 10 times of the cost of running EnvOpt . 4.6 Research Agent Behaviors Here we present some interesting behaviors we observed from the research agent, including but not limited to failure modes and how behaviors during training can be related to EnvOpt performance on heldout tasks. Using unreliable verification proxy Since we do not provide verifiers for training tasks, the research agent for Workspace-Bench occasionally used proxies such as answer length and keyword matching to confirm answer quality during training steps. This often turns out to hurt performance on heldout tasks. After observing validation set, we updated the instruction for research agent to prevent this behavior (see Appendix A ). Predicting validation performance using research agent behavior We find that for AutomationBench, cost reduction on validation set is correlated with how much tool call patterns change during each training step as measured in the per-task difference in tool call counts between training runs before and after the step, with Pearson correlation of 0.75. Alternatively, by looking at the fraction of training tasks that received more than 30% cost reduction in each step, its Pearson correlation with validation set cost reduction is 0.82 for AutomationBench, 0.70 for Workspace-Bench, and 0.56 for Data-Eng-Bench. Fail to follow the instruction Despite being told not touch anything related to the model or the harness, the research agent in Workspace-Bench still tried to change the reasoning effort of Codex during its step 6. This change was not effective on heldout tasks, as we only keep the environment directory in the research agent’s sandbox and discard the other artifacts. However, such behavior early in one training step could significantly affect the research agent’s optimizations during that step, potentially harming the performance. How far can we go without a validation set From the tested five benchmarks, we observe that it is generally safe to run EnvOpt for 3 training steps even without running the validation tasks. However, we note that this is only an empirical claim and that the validation set with real verifiers is still important for auditable environment optimization. Early flaw in optimization can remain uncovered in many later steps In Data-Eng-Bench, the research agent introduced a SQL statement splitter in step 1 that parses based on semicolon. But the splitter will fail if the semicolon is in quoted text. This bug in the optimization from step 1 remain uncovered until step 5. This inflates cost through all the 4 steps, as the target agent cannot tell that the splitter corrupted its query, so it attributes the failure to its own model and spends tokens to rebuild it. 5 Conclusion We formulate optimization over stationary environments as the third direction of agent optimization, alongside harness optimization and parameter tuning. This work introduces EnvOpt , an automated research pipeline for end-to-end environment optimization, and shows that it significantly reduces agent cost while maintaining or improving success rates across five benchmarks. EnvOpt transfers effectively across different models and harnesses, outperforming prior agent optimization methods including GEPA, Meta-Harness, gskill , and advisor models . In addition, EnvOpt can build upon Meta-Harness to push the Pareto frontier even further. Our analysis shows that EnvOpt significantly outperforms tool-only optimization and yields cost savings exceeding 10 times the cost of running EnvOpt itself. Finally, we detail key examples of successful and rejected environment optimizations to serve as a qualitative reference and provide design experience for future research.
