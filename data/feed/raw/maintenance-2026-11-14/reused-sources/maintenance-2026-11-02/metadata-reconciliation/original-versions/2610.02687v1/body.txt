Context engineering offers a practical alternative to weight updates by improving model behavior through instructions, strategies, and evidence supplied at inference time. However, adapting context online typically requires a costly trial-and-error process, while queries are often processed independently, preventing useful experience from carrying forward. Memory systems address this limitation by retaining information across interactions, but approaches that continually append information to a shared context face increasing token costs, context-window limits, and performance degradation as the context expands. We introduce a unified formulation of context optimization and show that an agent memory system update can be interpreted as optimization update procedure over the model’s context. This perspective attempts to provide a principled framework for studying memory design and its efficiency. We then propose GraphMemory, a lightweight graph-based memory that accumulates, refines, organizes, and connects reusable strategies. For each query, GraphMemory retrieves only the relevant subgraph, enabling online context adaptation without exposing the model to the entire memory. Under bounded retrieval, the amount of retrieved memory remains constant as the number of processed examples grows. Experiments show that GraphMemory achieves competitive downstream performance while using approximately 81 81 – 85 % 85\% fewer memory-construction tokens than our baselines. 1 Introduction Modern large language models (LLMs) achieve strong performance across reasoning, question answering, and open-ended generation tasks [ 20 ] . Yet deployed agents largely remain static: with fixed parameters, information acquired from one interaction does not naturally improve later behavior. Parameter-efficient fine-tuning (PEFT) provides one mechanism for adaptation [ 8 , 6 , 11 ] , while more recent methods generate context-specific adapters on the fly in a single forward pass [ 4 ] . These approaches still require access to model weights and training infrastructure, and encode their learned state in model-specific parameters. This limits continual adaptation during deployment and makes the acquired knowledge difficult to transfer across agents. Context engineering offers a weight-free alternative by adapting a frozen model through instructions, demonstrations, strategies, or evidence supplied alongside each query to leverage its in-context learning abilities [ 3 ] . Prompt-optimization methods treat this context as the optimization variable and search for task-level prompts that improve performance [ 23 , 10 , 14 , 1 ] . However, they generally optimize a single prompt against an offline dataset or user-defined evaluator rather than accumulating experience during deployment. Other methods use a hybrid setup that derives training signals from model behavior itself [ 16 ] . Persistent memory systems instead update an external natural-language memory as new problems are solved. Dynamic Cheatsheet stores reusable strategies in a persistent file [ 17 ] , while Agentic Context Engineering (ACE) incrementally evolves a structured playbook through a Generator–Reflector–Curator architecture [ 25 ] . Because this memory remains external to the model, it can be inspected, edited, and transferred across agents and has shown success in large-scale enterprise applications [ 18 , 13 ] . Nevertheless, scaling such memory introduces a fundamental problem. Because existing systems largely maintain a flat collection or a single evolving file, the model must process an increasingly large and heterogeneous memory context for every query. This increases token usage, pushes against context-window limits, and can lead to context degradation or collapse. To address these limitations, we introduce GraphMemory , a structured external memory for scalable test-time learning. GraphMemory represents reusable ACE-style knowledge points as nodes and captures useful relationships between them as weighted edges. For each query, the system identifies a small set of relevant entry nodes and traverses their local neighborhoods, exposing only the resulting subgraph to the language model. This representation enables selective retrieval without requiring all experience to be compressed into one global playbook or assigned exclusively to an isolated section. It also makes relationships among individual lessons explicit, allowing knowledge acquired from different experiences to be retrieved together when their connection is useful to the current problem. Our contributions are listed as follows: • A unified context-optimization framework. We formulate adaptation of a frozen language model as optimization over its textual context and show that persistent memory systems can be interpreted as optimization procedures that update this context across examples. Under bounded update sizes, we show that the context used by append-only memory grows as O ⁡ ( N ) O(N) , whereas bounded retrieval maintains an O ⁡ ( 1 ) O(1) memory-context length per query. • GraphMemory. We introduce GraphMemory , a lightweight external memory that accumulates, refines, organizes, and connects reusable strategies in an evolving graph. Nodes represent ACE-style knowledge points, while weighted edges capture useful relationships among them. For each query, GraphMemory identifies relevant entry nodes, traverses their local neighborhoods, and supplies only the resulting subgraph to the language model. This replaces full-memory prompting with selective relational retrieval while preserving the interpretability, portability, and weight-free adaptation of natural-language memory. • Competitive performance at substantially lower cost. Across three dataset–model settings on two financial reasoning tasks, Formula and FiNER , GraphMemory remains within 4.0 4.0 percentage points of ACE with Claude Haiku 4.5 and outperforms ACE by 1.5 1.5 points on Formula with Qwen3.8-27B. Optimizing Equation ( 4 ) is not claimed to be equivalent to optimizing the global objective in Equation ( 1 ). A block may overfit its source example and need not generalize in isolation. The motivation for this surrogate is primarily practical. First, it models the update procedure of a memory system. Second, it makes the oracle’s task more local: proposing a focused update Δ i \Delta_{i} is a simpler generation task than proposing changes to improve performance over the entire dataset. A separate composition or retrieval mechanism must determine which blocks should form the context for a new input; the local surrogate alone does not ensure generalization. We expand on this distinction in Appendix A.2 . Dynamic Cheatsheet and ACE instantiate this view by integrating locally extracted lessons into a shared natural-language memory [ 17 , 25 ] . The blocks are integrated into one shared context, making accumulated lessons available across examples and producing a single task-level memory for deployment. GraphMemory changes ACE at precisely two interfaces: what the Generator ( f f ) reads and what the Curator ( 𝒪 \mathcal{O} ) writes. Instead of exposing the complete playbook to every query, we prepend a retrieval stage; instead of writing only bullet-point updates, the Curator can also write relations between them. The resulting adaptation loop is Retrieve–Generate–Reflect–Curate , as illustrated in Figure 2 . For retrieval, we maintain a compact index containing each node’s identifier and a short key, but not its full bullet-point content. Given a query, the Retriever reads this index and selects a small set of entry nodes. We then perform a deterministic breadth-first traversal from those entries, expanding neighbors in order of learned edge utility, under fixed hop, node, and token budgets. Only the full contents of the nodes reached during this traversal are loaded and passed to the Generator. The LLM therefore makes the initial semantic choice, while the graph provides a cheap and deterministic mechanism for bringing in connected knowledge. Generation follows ACE. Reflection is extended in one respect: beyond ACE-style critique, the Reflector labels the Generator’s reported memory transitions as helpful, harmful, or neutral. Helpful and harmful labels contribute confidence-weighted evidence to the corresponding edges, while neutral labels leave the counters unchanged. The traversal utility is the mean of the resulting Beta posterior, so retrieval preferentially follows transitions with stronger helpful evidence. The difference appears during curation: the Curator produces a graph update that may add or revise bullet-point nodes, add or revise edges, or do both. The update is applied locally without rewriting the rest of the graph. New nodes are added to the compact index, while new edges determine which lessons can be reached together during later retrieval. We provide the detailed construction of GraphMemory in Appendix B . It is important to note that this realization is not strictly O ⁡ ( 1 ) O(1) end to end because the Retriever still reads an index that grows with the number of nodes. The bound in Proposition 2 applies to the full memory content supplied to the Generator. Since each index entry contains only an identifier and a short key, however, this residual growth is far smaller than repeatedly supplying every bullet in full. Thus, GraphMemory trades a modest increase in per-query latency for substantially lower context length, training cost, and test-time token consumption. 5 Conclusion, Limitations, and Future Work We cast agentic memory construction as iterative optimization over textual context, enabling a common analysis of flat and retrieval-based memory. We introduce GraphMemory , which organizes ACE-style procedural knowledge as a graph and retrieves bounded, query-relevant context. Related memory systems include A-MEM, which links episodic notes in a Zettelkasten-inspired structure [ 21 ] ; RIZZ, which organizes procedural rules into dynamic branches [ 7 ] ; and HAGE, which learns graph traversal policies [ 9 ] . GraphMemory learns relations between strategies from confidence-weighted helpful and harmful feedback, supporting their composition without requiring predefined edge types or training a retrieval policy. Our formulation shows how bounded retrieval changes memory-context scaling from linear growth under append-only prompting to a constant bound on retrieved content per query. Across two financial tasks and two LLM backbones, GraphMemory remains competitive with ACE while reducing memory-construction tokens by 81 81 – 85 % 85\% , test-time tokens by 79 79 – 92 % 92\% , and estimated API cost similarly. Learning trajectories suggest slower initial adaptation but greater stability and continued improvement. Our results remain preliminary, covering two related tasks, two models, and one primary baseline. Broader evaluations, additional memory and prompt-optimization baselines, and repeated runs are needed. Retrieval overhead also makes individual test queries slower despite lower token usage, motivating embedding-based and hybrid retrievers, caching, and improved graph routing. Finally, longer continual-learning streams and cross-model transfer will test whether improvements persist beyond one epoch and whether memory built by larger models can efficiently adapt smaller ones. Allowing a separate Δ i \Delta_{i} for each example enlarges the search space and can produce a maximally biased solution: an unconstrained block could simply encode the answer to its source input. Equation ( 4 ) is therefore not a reformulation with the same minimizer as Equation ( 1 ). It is a surrogate for constructing the elements of a reusable memory. The motivation is the asymmetry between classical optimization and textual optimization. If a reliable descent direction for the global context were available, decomposing the problem into per-example variables would offer little benefit and would create an obvious generalization problem. In the black-box setting, however, the update direction must itself be produced by an imperfect model-based oracle. Asking that oracle to extract one short lesson from one observed success or failure is a more localized generation task than asking it to rewrite a growing global context to improve average performance over all examples. Generalization is delegated to the memory interface. Given a memory bank δ \delta , a composer or retriever constructs c ϕ ​ ( x ) = ϕ ⁡ ( δ , x ) c_{\phi}(x)=\phi(\delta,x) for a new input. A block is useful only when it encodes reusable information and ϕ \phi exposes it on inputs for which that information is relevant. This is why context-block quality cannot be judged only by Equation ( 4 ); final validation and test risk must still be measured using the composed or retrieved contexts, as in Equation ( 16 ) for GraphMemory. Appendix B Implementation Details B.1 Directed Evidence-Weighted Memory Graph GraphMemory maintains a directed graph G ( t ) = ( V ( t ) , E ( t ) ) G^{(t)}=(V^{(t)},E^{(t)}) . The retrieval weight is a smoothed estimate of how often the Reflector has judged an observed directed transition helpful under the current retrieval policy. It should not be interpreted as a causal measure of interaction between two nodes or as a calibrated probability that retrieving the edge will improve accuracy. Evidence is policy-dependent because highly ranked edges are more likely to be observed again, and ranking by the posterior mean does not explicitly reward uncertainty. These limitations are important when interpreting the learned graph. B.2 Retrieval and Traversal Retrieval has two stages. First, an LLM Retriever reads the compact index and returns a structured selection of up to two index sections and at most six entry nodes. Second, GraphMemory performs a weight-prioritized breadth-first traversal over outgoing edges. Entry nodes have depth zero. At each breadth level, active outgoing neighbors are ordered by decreasing posterior-mean weight from Equation ( 19 ), with target-node identifier used as a deterministic tie-break, and at most the two highest-scoring neighbors of a loaded node are considered. Traversal is bounded by two hops from each entry node, at most 12 loaded nodes, and at most 2,500 tokens of serialized node content. A node is not loaded if doing so would violate either the node or token budget. Algorithm 1 gives the retrieval procedure. The queue preserves breadth-first depth order, while edge scores determine the priority among neighbors at the same expansion point. B.4 Model and Evaluation Configuration For the Qwen3.8-27B experiments, the model is loaded through Hugging Face. We retain the checkpoint configuration except for three explicit runtime choices: 4-bit quantization, scaled dot-product attention (SDPA), and disabled thinking mode. Disabling thinking prevents unnecessarily long reasoning outputs. These model and inference settings are identical for ACE and GraphMemory. For the Claude Haiku 4.5 experiments, all model calls are made through LiteLLM using its default request configuration. Within each dataset–backbone comparison, ACE and GraphMemory use the same backbone and model configuration; the method-specific difference is the memory interface rather than the underlying language model. Each system processes the training split for one epoch, and the then-current memory is evaluated on the validation split every 100 updates. The checkpoint with the highest validation accuracy is selected for the held-out test evaluation. In the Claude experiments, ACE uses the 80,000-token memory cap reported in the main text. Formula uses 500/300/200 train/validation/test examples, and FiNER uses 1,000/500/441 examples. B.5 Token and Latency Accounting The bounded-retrieval result in Proposition 2 applies to the serialized node content supplied to the Generator. It does not include the compact index read by the Retriever. Because the present Retriever reads the complete index, its input grows with the number of indexed nodes. Total system usage includes the Retriever’s index, retrieved node content, fixed instructions and query tokens, and the remaining input and output tokens from the Retriever, Generator, Reflector, and Curator. Only the retrieved node content supplied to the Generator is covered by the constant retrieved-content bound. The wall-clock measurements include the additional retrieval call made by GraphMemory, which explains why GraphMemory can use fewer tokens while having higher per-query latency.
