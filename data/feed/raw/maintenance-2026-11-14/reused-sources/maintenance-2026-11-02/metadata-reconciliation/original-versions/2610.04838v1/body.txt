Abstract As coding agents take on long-horizon software evolution tasks spanning multiple files and stages, longer execution trajectories introduce two coupled challenges: (1) accumulated histories strain context budgets, and (2) repository changes can invalidate earlier execution evidence. Existing approaches address these challenges through techniques like larger context windows, compression, retrieval, or repository representations, but often fail to reconstruct a consistent task state after a context refresh or verify whether recalled evidence remains valid. Thus, we introduce MemTrace , a provenance-aware memory system that preserves execution history and aligns its reuse with the evolving task (e.g., iterative cross-file repair) and repository state. MemTrace stores history as immutable Memory Traces anchored to key information (e.g., files, symbols, tests), and organizes their execution order and dependencies in a Memory Trace Graph . When context is constrained, working memory retains only compact Memory Anchors , from which the agent can reconstruct the latest execution state and locate evidence relevant to its next action. Before restoring historical evidence, MemTrace checks its validity against the current repository state and retrieves only what the next action requires. Across three complementary long-horizon coding benchmarks, MemTrace consistently outperforms all fully evaluated baselines under the same backbone and harness, improving DeepSWE pass@1 by 21.2 points, SWE-EVO Resolved Rate by 4.4 points, and SWE-Milestone Score by 17.8 points under Codex CLI. GitHub: https://github.com/Homy-Xu/MemTrace 1 Introduction Coding agents are moving from isolated bug fixing toward cross-file, multi-stage software maintenance and development, which requires iterative code inspection, coordinated edits, testing, and revision [ 17 , 32 , 13 ] . As execution lengthens, growing interaction history increases context pressure, while ongoing repository changes can make earlier observations, test outcomes, and decisions no longer applicable to the current state. This challenge already appears in deployed coding agents: systems such as Codex CLI [ 3 ] use context compaction to continue long-running tasks across context boundaries. Such mechanisms preserve execution continuity, but continuity alone does not determine whether recovered evidence still applies after the repository has changed. Long-horizon execution therefore requires the agent to maintain an accurate representation of task progress: what has been completed, what remains unresolved, and which prior evidence still applies. Task-state drift arises when this representation no longer matches the current task and repository state. The problem becomes particularly important after a context refresh, when the agent must reconstruct prior progress and recover evidence that remains applicable before continuing the unfinished task. Existing approaches mitigate different parts of this problem. Longer context windows accommodate more interaction history, while prompt compression condenses earlier context and observation masking selectively removes prior observations and tool outputs. External-memory systems offload historical information for later retrieval [ 24 , 18 , 4 ] , while repository graphs represent files, symbols, and dependencies for code localization [ 22 , 23 ] . These approaches improve history access and code localization, but access alone does not determine which historical evidence still supports the task state being resumed. The remaining challenge is to recover the current task state, not merely historical content. As illustrated in Figure 1 (a), a refreshed context may retrieve an earlier test failure even after a repair and a passing rerun. Without the relation to these later events, the failure may be mistaken for an unresolved issue. We call this mismatch between recovered history and the current task and repository state state-memory misalignment . Addressing it requires reconstructing the current task state and identifying which prior evidence remains valid in the current repository and relevant to the next action. To address this gap, we introduce MemTrace , a provenance-aware memory system that casts long-horizon coding memory as a state-alignment problem rather than mere history retention. Completed execution is sealed into immutable Memory Traces with explicit repository bindings and organized through two complementary views. A Memory Trace Graph (MTG) encodes depend , verify , correct , and supersede relations, enabling relation-aware traversal from the current execution frontier to evidence that establishes, revises, or invalidates its state. A Repository State Graph (RSG) maintains the current files, symbols, tests, and their structural relations. Trace-to-entity bindings project candidate traces onto this evolving state to determine whether their referenced evidence remains applicable. Under context pressure, trace bodies are offloaded while Memory Anchors preserve addressability. After a context refresh, MemTrace reconstructs the frontier through the MTG, checks candidate evidence against the RSG, filters stale or superseded traces, and loads only the validated evidence required for the next action back into working context (Figure 1 (b)). To assess MemTrace’s effectiveness in long-horizon coding, we evaluate it on three complementary benchmarks covering repository-level engineering, multi-step software evolution, and continuous milestone-based development: DeepSWE, SWE-EVO, and SWE-Milestone. MemTrace consistently outperforms fully evaluated baselines across agent harnesses, while achieving a 46.4% overall score on SWE-Milestone under Codex. Ablations show that persistence alone is insufficient: both structured execution memory and repository-state grounding are important for maintaining state-consistent memory over long-horizon execution. Contributions. This paper makes the following contributions. (1) We introduce a state-bound execution-memory representation for long-horizon tasks that preserves historical evidence with its original repository bindings and records how later execution supports, revises, or supersedes earlier evidence. (2) We present MemTrace, which links the MTG and RSG through shared repository references to reconstruct task state and selectively restore applicable historical evidence after a context refresh. (3) On three long-horizon coding benchmarks, MemTrace consistently outperforms the evaluated baselines under matched backbone and agent harness, while ablations confirm the complementary roles of persistent storage, structured execution memory, and repository-state grounding. 2 Related Work Table 1: Comparison of representative methods discussed in Related Work. ✓ \checkmark , △ \triangle , and × \times denote explicit, partial, and no support under the criteria below. Long-horizon agents must manage growing interaction histories within a finite context window. LLMLingua and LongLLMLingua compress prompts [ 15 , 16 ] , while observation masking and SWE-Pruner reduce the tool content retained in context [ 20 , 34 ] . MemGPT manages information across working and external memory [ 24 ] ; ReadAgent, MemWalker, and RAPTOR use summaries and retrieval to access long documents [ 18 , 4 , 27 ] . For agent trajectories, Context as a Tool and Context-Folding organize history around tasks or subtrajectories [ 21 , 30 ] , while Self-GC and Scroll retain recoverable history outside the active context [ 12 , 19 ] . These approaches make longer histories manageable. However, recovering historical content does not establish whether it still supports the task after later edits or tests. MemTrace couples history retrieval with task-state recovery, using relations among execution records to determine what has been completed and what remains unresolved. Agent memory and execution-state management. Agent-memory systems retain experiences and reflections for later decisions [ 25 , 28 ] . Mem0 updates salient memories, A-MEM links related memory notes, and Zep tracks the temporal validity of facts while retaining superseded information [ 7 , 39 , 26 ] . Beyond storing reusable knowledge, recent systems also use memory to maintain an explicit view of ongoing task progress. MAGE maintains a hierarchical state tree with summary validation and rollback [ 5 ] , while Ledger uses change counters to track observation freshness and reduce redundant actions [ 35 ] . These mechanisms help preserve execution state across long trajectories. In coding, however, maintaining task progress alone is insufficient: stored observations and test results may become stale as the repository changes. Recovering offloaded evidence therefore requires not only reconstructing what happened later, but also checking whether the evidence still applies to the current repository. MemTrace addresses this by binding immutable execution traces to repository state, recording verification, correction, and supersession relations in its Memory Trace Graph (MTG), and validating evidence before restoration. Repository-level coding and code graphs. Repository-level coding systems coordinate localization, editing, and validation through agent–environment interaction or structured repair pipelines [ 40 , 42 , 38 ] . CodePlan further uses dependency analysis to plan coordinated changes across files [ 2 ] . CodexGraph, RepoGraph, and LocAgent represent code entities and their relations to support repository navigation and localization [ 22 , 23 , 6 ] . These representations expose structural dependencies that are difficult to recover from isolated code snippets. However, code structure alone does not record which observations supported an edit, which tests verified it, or whether later execution replaced an earlier conclusion. MemTrace links its Repository State Graph (RSG) to the MTG through shared repository entities, allowing relevant execution evidence to be located and checked against the evolving codebase. We next present state-bound Memory Traces, the MTG–RSG alignment through shared repository entities, and validated restoration after a context refresh. 3.1 State-Bound Memory Traces Long execution histories consume context, while repository changes can invalidate earlier observations. To support compact retention and reliable reuse, MemTrace organizes history into immutable Memory Traces , each binding a completed unit of execution evidence to the repository state in which it was produced. Trace construction and offloading proceed as follows. Identify and seal reusable evidence. MemTrace seals a unit of work when it is complete and provides evidence that can support subsequent actions, such as an edit, test outcome, failure diagnosis, or correction. Each trace is represented as τ = ( x τ , ρ τ , ℰ ⁡ ( τ ) , α τ ) , \tau=\bigl(x_{\tau},\,\rho_{\tau},\,\mathcal{E}(\tau),\,\alpha_{\tau}\bigr), where x τ x_{\tau} contains the execution evidence and its provenance; ρ τ \rho_{\tau} records the repository state at evidence creation; ℰ ⁡ ( τ ) \mathcal{E}(\tau) identifies the files, symbols, and tests referenced in the body; and α τ \alpha_{\tau} is a compact Memory Anchor that provides a stable reference to the trace. Sealing adds τ \tau to the persistent Trace Store ℋ t \mathcal{H}_{t} and its anchor to 𝒜 t \mathcal{A}_{t} . A unit that exceeds the size of a single trace body is split into multiple traces, each with its own anchor. Preserve provenance as the repository evolves. Once sealed, a trace is never modified. Subsequent edits or corrections produce new traces and relations, preserving the original evidence, repository state, and entity bindings. These records make the conditions under which evidence was produced available for later validation. Persistence alone, however, does not establish current validity: a recorded test pass may no longer apply after the tested code changes. MemTrace therefore retains historical traces for provenance but reuses their evidence only when it remains applicable. Section 3.3 describes how ρ τ \rho_{\tau} and ℰ ⁡ ( τ ) \mathcal{E}(\tau) are checked against the current repository state R t R_{t} and task state m t m_{t} before restoration. Offload bodies while retaining access. When working memory C t C_{t} approaches the context budget B B , Memory Offloading removes selected completed trace bodies from the active context while preserving their full records in ℋ t \mathcal{H}_{t} . Compact Trace Synopses summarize the offloaded content, and Memory Anchors provide stable references to it. Both count toward B B , so only a budgeted subset remains in C t C_{t} . Anchors omitted from the active context remain stored with their traces and are recoverable through the persistent index. This separates persistent retention from in-context use: evidence remains accessible, while its restoration depends on the validation procedure in Section 3.3 . Repository bindings connect execution traces to current repository entities, allowing MTG–RSG traversal to locate relevant traces for validated restoration. 3.2 MTG–RSG Projection MemTrace links execution history to the evolving codebase through two complementary graphs: the Memory Trace Graph (MTG) records task progress, and the Repository State Graph (RSG) represents current repository structure. Their nodes and edges remain separate; the projection Π t \Pi_{t} connects traces to repository entities. Execution and repository graphs. The MTG G t M G^{\mathrm{M}}_{t} contains one node per trace in ℋ t \mathcal{H}_{t} , with relations recording execution order, dependencies, verification, correction, and supersession. For example, a repair trace may depend on a failure diagnosis and supersede an earlier edit, while a passing-test trace verifies the repair. These relations identify evidence that supports or revises the frontier m t m_{t} . The RSG G t R G^{\mathrm{R}}_{t} connects task-relevant files, symbols, and tests through defines , calls , imports , and covers relations. Here, covers denotes a test-to-code association for localization, not measured coverage or a passing result. MemTrace incrementally updates the graph around the execution frontier as R t R_{t} changes. Its structural relations guide retrieval without establishing the validity of historical evidence. Trace–repository projection. Each entity reference identifies a file, symbol, or test within its repository scope; symbols include their file path and qualified name. Sealing a trace records its bindings in Π t = { ( τ , e ) ∣ τ ∈ ℋ t , e ∈ ℰ ( τ ) } . \Pi_{t}=\bigl\{(\tau,e)\mid\tau\in\mathcal{H}_{t},\;e\in\mathcal{E}(\tau)\bigr\}. RSG traversal follows covers to CacheManager.invalidate and calls to clear_cache; lookups through Π t \Pi_{t} then retrieve the associated traces T 5 T_{5} and T 6 T_{6} . Candidate retrieval. Retrieval starts from anchored traces, traces supporting m t m_{t} , or repository references. RSG expansion follows a bounded, request-specific sequence of relations; the figure’s two-relation path is illustrative, not a global limit. Candidates may then expand by at most two MTG hops along dependency, verification, correction, and supersession relations. Traversal inspects incoming and outgoing edges without changing their meaning, allowing a failure trace to locate a later repair. Direct candidates precede expanded neighbors, and duplicates are removed before validation. 3.3 Validated Restoration MemTrace restores evidence only when it is relevant to the next action, applicable to the current execution state, and within the context budget. Applicability check. A trace is applicable when applies ⁡ ( τ , R t , m t ) ⇔ aligned ⁡ ( τ , R t ) ∧ ¬ superseded ⁡ ( τ , m t ) . \mathrm{applies}(\tau;R_{t},m_{t})\iff\mathrm{aligned}(\tau,R_{t})\;\wedge\;\neg\mathrm{superseded}(\tau,m_{t}). (2) The predicate aligned \mathrm{aligned} checks the evidence’s recorded source conditions against R t R_{t} , using ρ τ \rho_{\tau} , ℰ ⁡ ( τ ) \mathcal{E}(\tau) , and provenance in x τ x_{\tau} . It does not require the entire repository to remain unchanged. For a test result, however, both the test and its recorded dependencies must be checked; an unchanged target function alone is insufficient. Changed or unverifiable conditions prevent automatic reuse. The predicate superseded \mathrm{superseded} requires an explicit MTG relation indicating replacement for the current frontier; temporal order alone is insufficient. Selective restoration. MemTrace inspects retrieved candidates and, if needed, expands them as described in Section 3.2 . Relevant traces satisfying Eq. ( 2 ) are restored with their source labels and anchors until the request is satisfied. Blocks that exceed the remaining budget are deferred rather than truncated. Explicit historical queries may retrieve older or superseded traces labeled as historical evidence. If applicable evidence is unavailable, the agent reads the current file or symbol, or reruns the required test. Budget-deferred evidence is tracked separately from unavailable or invalid evidence. Recovery after a context refresh. Before refreshing the context, MemTrace offloads completed bodies and checkpoints m t m_{t} and the anchors for active work; the Trace Store, both graphs, and Π t \Pi_{t} persist. Recovery then proceeds in three steps: (1) reconstruct task progress from MTG traces supporting or revising the frontier; (2) use Π t \Pi_{t} and the RSG to locate repository entities relevant to continuation; and (3) restore relevant candidates that pass validation and fit within B B . We compare task performance (Section 4.2 ) and analyze component contributions and memory behavior (Section 4.3 ). Wall-clock results are in Appendix A.2 . 4.1 Experimental Setup Benchmarks. We evaluate on three long-horizon software engineering benchmarks covering complementary task settings. DeepSWE [ 13 ] contains 113 tasks across 91 repositories and five programming languages. SWE-EVO [ 32 ] comprises 48 software-evolution tasks constructed from release histories of seven Python projects. Two instances already pass all FAIL_TO_PASS tests without code changes, so we evaluate the remaining 46 tasks. SWE-Milestone [ 8 ] contains 98 human-verified milestones across seven continuous software-evolution itineraries spanning five languages. Backbone, harnesses, and baselines. We use deepseek-v4-flash-0731-high for all experiments, with a 200K-token context window and no explicit step limit. Experiments are conducted under Codex CLI v0.144.4 [ 3 ] and mini-swe-agent v2.4.6 [ 31 ] . We compare against three baselines. Native uses the default context management of each harness. Observation Masking [ 20 ] masks older tool observations outside a rolling window while retaining the reasoning and action history. RepoGraph [ 23 ] augments the agent with repository-level structural retrieval and is evaluated only on Python tasks, following its implementation scope. Metrics. We report benchmark-specific effectiveness metrics together with wall-clock time. For DeepSWE, we report pass@1 and the average wall-clock time per task, where pass@1 measures the fraction of tasks successfully resolved. For SWE-EVO, we report Resolved Rate, Fix Rate, and Apply, measuring complete resolution, partial functional progress, and successful patch application, respectively [ 32 ] ; we additionally report the average wall-clock time per task. For SWE-Milestone, we report Score, Precision, Recall, and Resolved Rate. Score is the harmonic mean of Precision and Recall, which measure functional correctness with respect to regressions and the fraction of required functionality completed, respectively [ 8 ] . 4.2 Main Results Table 2 compares MemTrace with the baselines across three benchmarks and two agent harnesses. Adding the MTG to the Trace Store improves DeepSWE from 32.1% to 44.2%, showing that execution relations help connect earlier edits, tests, and corrections across a long trajectory. Adding the RSG further raises performance to 56.6%, indicating the value of tracking relations among files, symbols, and tests when task progress spans a broad repository context. This effect is much smaller on SWE-EVO, where removing the RSG leaves performance unchanged at 69.6%. One likely reason is the difference in task scope: DeepSWE covers repository-level tasks across many repositories and languages, whereas SWE-EVO follows release-level evolution within a smaller set of projects. The exposure rate, however, shows no clear monotonic increase with execution length (Figure 5 (d)), indicating that the added maintenance load is driven mainly by more stored history and repository changes rather than a higher per-trace exposure rate. 5 Conclusion and Future Work We introduced MemTrace , a state-consistent memory system for long-horizon coding agents that preserves execution evidence with repository provenance and validates it before reuse. Across long-horizon benchmarks, MemTrace consistently improves the primary task-level metric over fully evaluated baselines across two agent harnesses, while our analyses show the complementary value of structured execution memory and repository-state grounding. These results suggest that long-horizon memory should maintain not only historical information, but also its applicability to the current execution state. Future work will evaluate MemTrace with additional backbone models and context-window sizes, and extend it to persistent development settings spanning multiple tasks and sessions within the same repository.
