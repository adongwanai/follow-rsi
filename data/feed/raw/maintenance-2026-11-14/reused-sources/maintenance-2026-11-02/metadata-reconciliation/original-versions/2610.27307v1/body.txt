Evolving Self-tuning Benchmarks for Long-Horizon Tool Use Hyunji Alex Nam Michael Dennis Affiliation: Google Deepmind Natasha Jaques Minsuk Chang Affiliation: Stanford University Affiliation: University of Washington Correspondence: hjnam@stanford.edu Abstract For AI assistants to move beyond simple chat interfaces and reliably assist users with applications like Gmail, Venmo, and Slack, we need to improve their tool-use capabilities. However, existing tool use benchmarks are still limited and difficult to scale because they rely on human supervision or are too domain-specific. To make data generation scalable, we propose, TURTLE ( T ool U se R elated T asks with L ong-Horizon E volution), an Unsupervised Environment Design (UED) approach to evolve existing tasks using a proposer, a solver, and a feedback generator. The proposer is rewarded for difficult yet solvable tasks based on the solver’s empirical performance, and the feedback generator summarizes the solver’s execution traces for the proposer to exploit. TURTLE produces evolving, self-tuning test suites adaptable to different environment requirements, from supporting user simulators and dense document retrieval to interacting across multiple apps. Empirical results on AppWorld, τ \tau -Bench, and AutomationBench using Gemma 4 31B-it show that the evolved tasks target the desired difficulty range (e.g., a 165% increase in the percentage of hard tasks on AppWorld), increase task diversity (in terms of reasoning and simultaneous tool interactions), and elicit a broader range of failure modes than the original tasks. † † footnotetext: † Equal advising. ‡ Work done during internship at Google DeepMind. 1 Introduction Figure 1: Even with the same underlying toolset, task difficulty can change depending on the instruction and the amount of reasoning and multi-step interaction required. Rather than building new benchmarks from scratch, TURTLE evolves existing tasks using a task proposer, a solver, and a feedback generator LLM without human supervision. During the evolutionary search, the proposer modifies the parent task, generating increasingly challenging but solvable tasks, while trivial or infeasible tasks are pruned based on their scores. As Large Language Models (LLMs) become more pervasive and integrated into our everyday lives and workflows, evaluating models across a wide range of scenarios is crucial for safe deployment. Especially for nascent applications like tool-use, evaluating models across diverse task suites is important for understanding their capabilities and vulnerabilities. However, existing tool use benchmarks are still limited and difficult to scale. Many existing benchmarks are domain-specific ( Merzouki et al., 2026 ; Shepard and Salimans, 2026 ; Yang et al., 2026 ) , or they rely on humans in the loop for task design and refinement ( Trivedi et al., 2024 ; Shi et al., 2026 ; Barres et al., 2025 ) . Furthermore, many new datasets are built from scratch and show little to no compatibility with the existing harnesses and testing setups of prior benchmarks, creating engineering overhead when incorporating new tests into an existing evaluation pipeline. Therefore, we need a scalable way to generate new tasks that test the robustness of models without adding to the engineering burden. Our key insight is that we do not need to reinvent the wheel . Instead, we can reuse components of existing tasks to build new tasks. Existing tasks give us primitives and steps that we can recombine to produce a vast space of possible new tasks. By searching this space to target gaps in the solver’s performance, we can still generate new tasks efficiently while ensuring task robustness. We propose TURTLE ( T ool U se R elated T asks with L ong-Horizon E volution), an Unsupervised Environment Design (UED) approach ( Dennis et al., 2021 ; Wei et al., 2026 ; Rutherford et al., 2024 ) based on evolutionary search ( Bäck and Schwefel, 1993 ; Mouret and Clune, 2015 ) . TURTLE consists of a proposer, a solver, and a feedback generator, each responsible for new task generation, reward evaluation, and task reflection. Similar to UED and compositional environment design ( Gur et al., 2022 ) , we use a Proposer agent to automatically generate new tasks that target the solver’s current level. We implement the proposer using an advanced evolutionary search operator, AlphaEvolve ( Novikov et al., 2025 ) . This allows our generation pipeline to incorporate highly capable models as the proposer—even closed-source ones—without requiring access to their weights, since evolutionary search hanldes gradient-free optimization. This is important given the large capability gap and varied behaviors observed across models of different sizes and release dates ( Marchand et al., 2026 ) . Evolutionary approaches have shown success in environment generation ( Faldor et al., 2025 ) , persona generation ( Paglieri et al., 2026 ; Chopra et al., 2026 ) , strategy discovery ( Wang et al., 2026a ) , and red-teaming ( Samvelyan et al., 2024 ) , but they remain under-explored for tool-use task generation. The proposer receives an initial task and a toolset from open-source datasets and suggests mutations to the task based on the sovler’s prior execution traces and failure reflections. The modified task is then attempted by the solver N N independent times. To avoid tasks that are either too difficult or too easy, we design rewards based on the solver’s completion rate, targeting a 50% average completion rate, as in sampling for learnability ( Rutherford et al., 2024 ) , which maximizes the variance of the solver’s success rate in 2D grid navigation environments. As a result, TURTLE produces evolving, self-tuning benchmarks tailored to the current solver. When evaluating the evolved tasks, we focus on three aspects: (1) the solver’s empirical performance, (2) task diversity, and (3) elicited failure modes. Our empirical results span open-source benchmarks with different requirements, featuring user simulators ( Barres et al., 2025 ; Shi et al., 2026 ) , documents for knowledge retrieval ( Shi et al., 2026 ) , 47+ simulated SaaS applications ( Shepard and Salimans, 2026 ) , and extensive user databases and product catalogs modeled after real-world software applications like Amazon and Spotify ( Trivedi et al., 2024 ) . Our main results are reported with Gemma 4 31B-it ( Team et al., 2026 ) as the solver, but we also include ablations with other models, such as Gemini 3.6 Flash ( Doshi and Google Gemini Team, 2026 ) and Gemini 3.1 Flash Lite ( Google Gemini Team, 2026 ) , to show that TURTLE adapts to different solver types. In summary, TURTLE is a multi-agent evolutionary data-generation approach for eliciting long-horizon tool-use capabilities. It: • Increases task difficulty when the original tasks are too easy (e.g., a 165% increase in the proportion of hard tasks compared to the original AppWorld tasks for Gemma 4 31B-it) • Increases the frequency of desirable task features, such as logical filtering and reasoning, by 29–212% on AppWorld, and makes both semantic and functional changes to the task instructions; • Can be used to diagnose solver vulnerabilities, broadening the coverage of (task feature × \times elicited error type) pairs from 49 to 54. 2 Related Work Tool-use benchmarks for LLMs. Frontier models still struggle on long-context benchmarks requiring multi-step reasoning, such as FactoryBench ( Merzouki et al., 2026 ) , AutomationBench ( Shepard and Salimans, 2026 ) , ProgramBench ( Yang et al., 2026 ) , and τ \tau -bench (banking) ( Shi et al., 2026 ) . Despite their usefulness, these benchmarks are difficult to scale because they mainly provide static environments and tasks. Therefore, once models learn to solve problems in these datasets, the benchmarks cannot be reused to discover new tasks or model failures. Methods have been developed to generate new tasks. For example, Tool-R0 ( Acikgoz et al., 2026 ) and GenEnv ( Guo et al., 2025b ) operate only in text space to generate and verify tasks. However, LLM-simulated environments may suffer from hallucinations and inconsistencies ( Wang et al., 2024 ) . Alternatively, Lu et al. (2025) ; Barres et al. (2025) ; Yao et al. (2024) ; Shi et al. (2026) ; Trivedi et al. (2024) ; Esfandiarpoor et al. (2025) build tool-interactive sandboxes and database states that more closely resemble real-world applications. However, these are challenging to scale, as they require humans to refine tasks or evaluation environments for robustness. Furthermore, they are often tailored to specific domains (e.g., τ \tau -bench for travel and retail ( Yao et al., 2024 ) , banking ( Shi et al., 2026 ) , and telecom ( Barres et al., 2025 ) are all separate benchmarks). Other methods rely more heavily on prompting for environment design and task discovery, such as EnvScaler ( Song et al., 2026 ) and Agent World Model ( Wang et al., 2026b ) . Agent-World ( Dong et al., 2026 ) uses prompts to adjust task difficulty with hand-designed task features, such as the number of reasoning steps and the number of unique tools used per task. Validating task feasibility remains challenging in automated task generation. To guarantee solvability, ToolGrad ( Zhou et al., 2026 ) reverses the task-generation process by first constructing the ground-truth tool-call sequence, then writing a matching natural language instruction for the given sequence. TURTLE is different from prior approaches in two ways: (1) evolutionary: using gradient-free evolutionary optimization to incorporate advanced models, and (2) self-tuning: minimizing human oversight in task design and adapting to particular solvers. Our work shares the motivation of Cai et al. (2025) ; Fang et al. (2025) , which use existing tool-use datasets to automate task generation. However, they rely on state-dependency graphs and random walks, which can limit the flexibility of task generation, and building graphs become challenging as the number of tools increases and their inter-dependencies grow complex. TURTLE combines the best of both approaches by leveraging existing benchmarks and verified API implementations, while evolving them to adjust their difficulty based on the solver’s performance. LLM-powered evolutionary search. Evolutionary algorithms are gradient-free optimization inspired by biological evolution ( Bäck and Schwefel, 1993 ; Mouret and Clune, 2015 ) . They iteratively mutate a population of programs and select candidates based on their fitness scores, while allowing fitter individuals to reproduce more often than less fit ones. Incorporating large language models into evolutionary search has proven successful in scientific and mathematical optimization ( Novikov et al., 2025 ; Assumpção et al., 2026 ) , red-teaming ( Yuan et al., 2026 ) , and social applications using conversational assistants, such as generating diverse user personas ( Chopra et al., 2026 ; Paglieri et al., 2026 ) and strategy discovery ( Wang et al., 2026a ) . AlphaEvolve ( Novikov et al., 2025 ) and OpenEvolve ( Rudes et al., 2025 ) are among the popular frameworks for orchestrating evolutionary search using LLMs. 3 Method TURTLE consists of three key LLM agents: (1) a proposer implemented with AlphaEvolve; (2) a solver , which attempts the new task yielding fitness scores; and (3) a feedback generator , which identifies the main reason for failure based on the solver’s execution traces and the ground-truth solution. We leverage multi-agent dynamics to propose, evaluate, and refine task mutations according to the solver’s problem-solving competence. We then apply a filtering step with an LLM judge (Gemini 3.6 Flash) to remove tasks with trivial solver failures, such as formatting mismatches or paraphrases of the same content, which can be attributed to ambiguous or underspecified instructions (see judge prompt in Appendix Fig. 9 ). 3.1 Evolutionary Task Proposer Task structure. A task is presented as a Python program, and the proposer is instructed to act as a programmer. In particular, on AppWorld, we provide minimal instructions to explore how AlphaEvolve discovers task features on its own (proposer instruction prompts are included in Appendix A ). Depending on the features of the initial task, the proposer is given different items specifying the task. For example, in AppWorld, a task is defined by: (1) the initial database state , which specifies the user’s account information, friends list, message history, Amazon product catalogs etc.; (2) the original task instruction in natural language (e.g., “ Give me a comma-separated list of the six most-played EDM songs from my Spotify playlist. "); (3) the ground-truth solution , which shows the sequence of API calls and their arguments; and (4) optionally, evaluation criteria . If a task changes only part of the database state, the evaluation criteria are set automatically to the oracle final state obtained by executing the ground-truth solution in a simulated environment, so the proposer does not need to specify them. If enumerating all state changes is too expensive, the proposer additionally specifies which parts of the database must be inspected, and the solver is evaluated only on the changes made to those parts. Task mutation. During each evolutionary step, the proposer is given a parent task and five additional tasks sampled from the archive, stochastically chosen between the best global and local tasks (highest-scoring per metric). Each task is represented by its instruction text, a corresponding score, and a summary by the feedback generator. The proposer uses this information to propose modifications to the parent task that can maximize the fitness function. Unlike prior work that uses RL post-training to update the proposer ( Acikgoz et al., 2026 ; Guo et al., 2025b ) , we frame task generation as a search problem seeded with a parent task and use AlphaEvolve to discover variants of the original task. ⬇ 1 def task (): 2 return { 3 db_changes : # initial database state, 4 full_description : # user account information (e.g., acces tokens, emails, tool-discovery instruction), 5 instruction : # natural language instruction, 6 ground_truth_calls : # ground truth API sequence, 7 } Listing 1: Appworld task as a program. Task verification. Before sending a new task to the solver, we execute the proposed ground-truth solution in the simulated environment to verify there are no system errors. This step filters out tasks with inconsistent state dependencies (e.g., asking to send a message to a friend who is not in the contact list). If the proposer specifies evaluation criteria, we verify that the ground-truth solution achieves a perfect score under those criteria. 3.2 Solver (Task Difficulty Evaluator) A new task is evaluated based on the solver’s empirical performance. In particular, we reward tasks that are solvable but not consistently solved perfectly. Each task is attempted N N times, and an attempt scores 1 if the solver fully completes the task; otherwise 0 (partial credits are allowed in AutomationBench ( Shepard and Salimans, 2026 ) to avoid reward sparsity on harder domains). To avoid penalizing trivial string mismatches, we additionally prompt the LLM judge to evaluate semantic state matching using the original task instruction and the observed versus expected final states. How to avoid reward hacking. Some works on multi-agent task generation leverage zero-sum adversarial dynamics, where the proposer attempts to minimize the solver’s performance, in order to ensure robustness ( Liu et al., 2026 ) . However, in the case of tool-use task generation this objective is badly posed. Adversarial dynamic between the proposer and the solver can lead to reward hacking, since the proposer may be incentivized to generating ambiguous or partially solvable instructions. Therefore, to ensure the tasks are feasible, we check that they are solved perfectly in at least one of the solver attempts. Fitness function. Our main objective is to generate long-horizon tasks that can reveal different model failures. To this end, we construct a multi-objective reward function based on the solver’s completion rate. We define c c as the solver’s average completion rate across N N independent attempts, and L L as the average solver’s trajectory length. To encourage more complex tasks, we reward the proposer for generating longer tasks that the solver is still able to complete. To prevent the proposer from trivially extending the ground-truth task length with unnecessary tool calls that do nothing (a reward hacking behavior we initially observed), we base these rewards on the length of the solver’s successful trajectory. During the evolutionary search, the proposer stochastically chooses between global optimality (the highest-scoring task on average across six metrics) and local optimality (the highest-scoring task for one of the six metrics) to balance exploration and exploitation. When suggesting modifications, the proposer reviews the parent task, along with five sampled in-context examples, and their corresponding textual and numeric performance summaries, and is instructed to optimize the average fitness score based on the individual score report. 3.3 Feedback Generator One key advantage of LLM-powered evolutionary search is that the task proposer can use natural-language feedback, in addition to fitness scores, to guide its search for better performing mutations. To leverage this strength, we incorporate a feedback generator LLM into the evolutionary search. For tasks with unsuccessful solver attempts, the feedback generator outputs a short explanation of what went wrong by comparing the solver’s outcome against the ground-truth solution and the provided task instruction. This feedback is stored in the task archive alongside the solver’s execution traces and provided to the proposer during mutation. 4 Experiment TURTLE is applied to four different benchmarks: AppWorld ( Trivedi et al., 2024 ) , τ \tau -telecom ( Barres et al., 2025 ) , τ \tau -banking ( Shi et al., 2026 ) , and AutomationBench ( Shepard and Salimans, 2026 ) . Tasks with 100% completion rates are excluded from the numerator since they do not elicit any failure, but they remain in the denominator. 6 Discussion & Conclusion As LLM capabilities advance, we need a scalable task generation approach to understand their current challenges and ways to improve them. We propose TURTLE , a multi-agent evolutionary approach for generating solvable yet difficult tasks. TURTLE shows that hard tasks do not always require building new testing environments or APIs from scratch. Instead, existing tasks can be evolved and expanded by modifying instructions and recombining tool call sequences. TURTLE has two clear advantages over existing data generation methods. (1) Evolving: Tasks evolve from the parent seed to target the solver’s competence, rather than converging on a one-size-fits-all static evaluation set. It also uses a gradient-free evolutionary search algorithm, which allows task generation to incorporate closed, frontier models for higher-quality generation. (2) Self-tuning: Unlike prior works that rely on humans for task design and refinement, TURTLE is fully automated, with self-verification in a Dockerized environment and tuning based on the solver’s completion rate to ensure task reliability. We apply TURTLE to popular benchmarks, including AppWorld, τ \tau -bench, and AutomationBench, and evaluate the difficulty of the generated tasks relative to the original datasets. When the original tasks are too easy, TURTLE yields tasks that are more difficult, leading to a broader range of solver failures. While we mainly use TURTLE for evaluation, it can also be integrated into model training by scaling up training data generation with minimal human supervision. In particular, Rutherford et al. (2024) show that generating tasks with maximum outcome variance is ideal for learning, since they target the solver’s learning frontier. We can first generate a new curriculum with TURTLE and train the solver using reinforcement learning with verifiable rewards ( Lambert et al., 2025 ; Guo et al., 2025a ) or apply filtered behavioral cloning to successful trajectories ( Hong et al., 2023 ) . This process of generating new tasks and training the solver can be repeated until the solver’s learning plateaus, without collecting new human data or manually adjusting task difficulty. This can help close the model-improvement loop, from synthetic data generation for evaluation to training. Limitations TURTLE uses gradient-free evolutionary search, so it can be applied to both open-weight and closed-weight models through API calls. However, the inference cost of proprietary models can be a limiting factor. We ran some ablations with different solver models (e.g., Gemini 3.6 Flash and Gemini 3.1 Flash Lite) on AppWorld using only a small subset of initial tasks. Our main objective was to show that TURTLE applies to different solver types and is not overfitted to the Gemma solver, and to demonstrate different ways the generated tasks may be used. To make the datasets larger and more useful for future use, the initial task sets would need to be seeded with more parent tasks. Ethical Consideration. As LLMs become more pervasive and integrated into our everyday lives and workflows, evaluating their failure modes is crucial for safe deployment and user control over AI systems. Our work contributes to safety by proposing new ways of generating task data to assess model capabilities, while minimizing human supervision, reducing the engineering and data-generation burden. However, overreliance on AI systems based on their benchmark performance can be harmful, since benchmarks are designed to assess only certain aspects of a model’s competence and can become saturated as models are continuously optimized against publicly released datasets. We also used AI to polish the paper (both the writing and the formatting in Overleaf) and to polish the prompts used in our experiments. When LLMs are used as the evolutionary search orchestrator or as judges (e.g., evaluating task difficulty, labeling task features, and identifying failure reasons), their uses are described in the Methods section. Appendix B Appendix: Datasets AppWorld ( Trivedi et al., 2024 ) includes a set of 4,571 executable APIs covering everyday mobile applications like Spotify, Amazon, Venmo, and Gmail. Tasks look like: ‘Send a Venmo request to {a friend’s name}" and “Download a song by {artist name} on Spotify and add it to my playlist", and require the LLM agent to take actions on behalf of the assigned user (i.e., human supervisor). The dataset is split into a larger test set and relatively smaller datasets for training and validation, which include the initial database states, task specifications, and ground truth API sequences. Our design choice. To verify whether a task is fully solved, we initialize two identical environments with a given database state, execute the ground-truth API calls and the solver’s actions in parallel across each copy, and compare their final states. For any key-value pairs in the final state dictionary that do not match between the ground truth and the solver, we run an LLM judge as a fallback state-equivalence check to filter out differences caused by formatting or exact string mismatches. τ \tau -bench is a tool use benchmark for evaluating the model’s capability as a customer-facing service agent across different domains. In particular, we use telecom ( Barres et al., 2025 ) and banking ( Shi et al., 2026 ) . In both domains, since the instruction is provided through the interactions with the user simulator, the user ends the conversation when their goal is satisfied. τ \tau - telecom ( Barres et al., 2025 ) evaluates a dual-control, multi-turn dialogue setup, where both the user and the agent are capable of making non-overlapping sets of tool calls. The LLM solver is prompted to act as a customer service agent resolving the simulated user’s problem. Certain tool calls can only be executed by the user, so the agent must guide the user through step-by-step instructions to achieve the desired tool execution. In our setup, we use the same base model for both roles. The user is given an additional prompt specifying their persona and guidelines on how to respond to requests or information-gathering questions made by the agent. The full dataset features 2,285 tasks across three user persona types alongside different tasks. When evaluating solver attempts against the ground-truth tool calls, we need to check for all environment changes, including those invoked by the solver (agent) as well as the user. Our design choice. We allow the solver to continue interacting with the user for maximum 25 turns per task (since the longest task requires 12 actions), and three consecutive errors in a conversation result in early terminations with a 0 reward. Following Barres et al. (2025) , we only allow atomic solver actions per turn. τ \tau - Banking ( Shi et al., 2026 ) is specialized for testing an agent’s document retrieval and long-context reasoning capabilities. The agent must navigate large, unstructured knowledge bases covering financial topics, like checking and savings accounts, credit card terms, annual percentage yields, and internal protocols to resolve users’ transaction disputes and product inquiries. The internal database consists of 698 documents spanning 21 product categories, and the dataset has 97 complex problems that require information retrieval, multi-step tool execution, and policy constraint resolution, while navigating multi-turn user dialogue. Each task requires on average 18.6 documents and 9.5 tool calls, with 33 maximum number of tool calls. Different configurations are available for retrieval: dense retrieval with text embeddings, sparse retrieval with BM25, terminal use (knowledge base is exported as files and the agent can use shell commands), and golden (ground truth documents are directly supplied in context, no retrieval required). Our design choice. Our solvers are evaluated with BM25 and golden retrieval, and allowed up to 50 max turns and 3 consecutive errors per task. Following Shi et al. (2026) , we allow solvers to execute simultaneous tool-calls in a single turn. Our evaluation covers both state-mutating and non-mutating tasks. For state-mutating tasks, we initialize the environment and compare the resulting state changes between the ground truth execution and the solver’s tool calls. We assign a score of 1 for an exact match and 0 otherwise. For non-mutating tasks (e.g., escalating an issue to a human agent), we evaluate action matching based on whether the agent makes the correct tool with the correct parameters. Failure type Source Dataset Description Examples Missing items AppWorld The agent failed to include or process some requested items. If the instruction includes processing N N transactions, N N messages to friends, or N N downloads, the agent only processed a subset of N N successfully. Commonsense error AppWorld Non-tool-call related errors Calculation or sorting errors (e.g., asked to identify the largest item, but the agent chose the smaller item). Constraint violation AppWorld, Automation Bench, τ \tau -bench, SWEBench The agent did not respect specified constraints or priorities. If the instruction says to only download songs by artist xyz, but songs not by this artist are downloaded; the instruction says to filter by some condition but that is not satisfied; or if the instruction has an "if-then" conditional, but the condition is not checked before executing then. Incorrect data processing AppWorld, GDPval The agent processed the data incorrectly. Incorrectly reading the last 4 digits of a credit card number; incorrect response data parsing or extraction. Invalid APIs AppWorld The agent hallucinated input, made incorrect API names, or used an incorrect API Agent uses an incorrect tool call or the returned tool call cannot be parsed into an existing tool or API name Incompletion AppWorld, GDPval The agent failed to include or process some requested items, or followed some parts of the instruction while missing other details. Agent returned the correct artist names but didn’t download their songs, when the instruction requested both answering the artist names and downloading their songs; or adding new items to the bucket list but not marking them as incomplete; or navigating to “photographs" folder instead of “pictures" after making filesystem changes Incorrect search assumptions Automation Bench, τ \tau -bench, SWEBench If the agent’s generic search fails, then they need to retrieve information differently, but the agent relies on its assumptions of where to look for things If the data is present in notes and google spreadsheet, but the agent assumes it exists in google spreadsheet and doesn’t look thoroughly across available tools Hallucination AppWorld The solver made up information without retrieving this from tool calls Making up roommate names; making up numbers or accounts Formatting errors AppWorld, GDPval The agent’s output formatting was incorrect. Completed tasks correctly but made formatting mistakes in the answer, file, or message text string. Incorrect task ordering τ \tau -bench If either the constraint document or the logical ordering of the subtasks need to be done in a particular way, but the agent messes up the subtask order and therefore arrives at a different answer or conclusion Subtracting then dividing is different from dividing then subtracting, leading to different outcomes
