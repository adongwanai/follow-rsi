SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown

Executable Agent Skills combine natural-language instructions and scripts into reusable packages for LLM agents, and revising them requires fixing errors without breaking correct behavior. Existing benchmarks do not systematically distinguish documentation repair, script repair, and preservation when evaluating skill self-evolution. We introduce SkillScriptBench, a 350-task benchmark designed to evaluate these capabilities separately. From a survey of over 35,000 GitHub-hosted Skill roots, we select 100 packages and construct 150 repair tasks. Each task pairs a package containing injected script faults with a maintenance request and executable checks of the required behavior. A complementary controlled track contains 200 tasks from 50 packages, each evaluated under the same maintenance request in four states: clean, documentation faults, script faults, and faults in both. Across four LLMs, methods that edit both documentation and scripts can repair script faults but do not consistently outperform Markdown-only revision on documentation repair or preservation. We therefore introduce AST-Guided Skill Revision, which uses abstract syntax trees and calling relationships to link maintenance requirements to relevant code locations. It restricts script edits to these locations and updates the documentation to match the revised scripts. Averaged across models, this revision stage yields absolute gains in repair success of 21.9% for Raw Package and 27.7% for CoEvoSkills on faulty packages. Absolute gains in the proportion of tasks solved in all three runs reach 20.8% and 31.5%, respectively, indicating more consistent repair success across repeated runs.
The benchmark and evaluation tools are available at https://github.com/KnowComp/SkillScriptBench .

1 Introduction

LLM agents increasingly perform multi-step tasks through sustained interaction with tools, files, and execution environments ( Yao et al., 2023 ; Yang et al., 2024 ) . Reliable execution depends on procedural knowledge for coordinating operations, recovering from failures, and validating outputs ( Wang et al., 2023 ; Shinn et al., 2023 ) . Agent Skills make this knowledge reusable by organizing instructions in a SKILL.md file, optionally accompanied by executable scripts and supporting resources ( Agent Skills, 2026 ; Li et al., 2026 ) . These packages provide workflows that agents can reuse across tasks, while skill self-evolution uses experience and feedback to revise them as requirements change or failures emerge ( Zhong et al., 2026 ; Zhang et al., 2026b ; Liu et al., 2026a ; Liu et al., 2026b ) . For executable skills, this process involves both the documented workflow and its implementation, making consistency between documentation and scripts an important part of reliable evolution.

Existing research spans three settings: evaluating the downstream utility of fixed skills, generating reusable skills from task experience or source corpora, and refining existing skills through feedback. Fixed-skill benchmarks assess packages without revising them, while representative skill-generation and continual-learning benchmarks often use a SKILL.md document as the learned artifact ( Li et al., 2026 ; Han et al., 2026 ; Zhong et al., 2026 ; Zhou et al., 2026 ) . Among self-evolution methods, SkillOpt and SkillAudit primarily revise instruction documents, whereas CoEvoSkills and SkillEvolver support executable multi-file packages ( Yang et al., 2026 ; Gao et al., 2026 ; Zhang et al., 2026b ; Zhang et al., 2026a ) .

Despite this progress, the self-evolution of existing executable skill packages remains underexplored in current benchmarks, particularly the revision of scripts and their consistency with documentation. These components can fail independently: a documented command may pass an unsupported option to an otherwise correct script, while a script may mishandle an option that is correctly documented. Task success and broader skill-quality assessments do not, by themselves, distinguish documentation repair from script repair, and aggregate results can obscure regressions in packages that were already correct ( Li et al., 2026 ; Zhong et al., 2026 ; Yang et al., 2026 ; Zhang et al., 2026b ) . Addressing these gaps requires a benchmark that evaluates revisions for fault repair, documentation–script consistency, and preservation of correct behavior across diverse executable packages.

To address these gaps, we introduce SkillScriptBench , a 350-task benchmark that treats existing executable Agent Skill packages as the unit of self-evolution and evaluation. Each task pairs a package with a maintenance request. For the In-the-Wild Repair track, we scan over 35,000 GitHub directories containing SKILL.md and construct 150 repair tasks by injecting script faults into 100 curated packages. The Controlled Repair track contains 200 tasks from 50 packages, each provided in clean, documentation-fault, script-fault, and joint-fault states with its maintenance request held fixed. Together, the two tracks cover varied package structures, programming languages, and maintenance requirements while supporting controlled comparisons of repair and preservation. Across four LLMs, methods that revise both documentation and scripts can repair script faults but do not consistently outperform Markdown-only revision on documentation repair or clean-package preservation. To better coordinate repair and preservation, we introduce AST-Guided Skill Revision as an additional stage for existing revision methods. It analyzes the original package and an initial revision, links maintenance requirements to abstract syntax tree (AST) nodes, and uses calling relationships to provide context for targeted edits. Script edits are restricted to selected nodes and guided by preservation constraints derived from requirements assessed as satisfied. The documentation is then aligned with the maintenance request and revised implementation. Averaged across the four models, this stage increases repair success on faulty packages from 54.8% to 76.7% for Raw Package and from 48.8% to 76.5% for our CoEvoSkills adaptation. The proportions of tasks solved in all three runs increase by 20.8 and 31.5 percentage points, respectively, and both augmented methods improve clean-package preservation relative to their corresponding baselines.

2.1 Task formulation

Each SkillScriptBench task provides an existing executable Agent Skill package S S and
a natural-language request q q describing the required functionality or a failure
to be resolved. Revision targets the natural-language instructions and behavioral
specifications in SKILL.md , the implementation code of bundled executable
scripts, or both. A method returns a candidate package S ′ S^{\prime} whose executable
behavior satisfies q q and whose documentation consistently describes that
behavior, while preserving behavior outside the requested scope.

2.2 Benchmark construction

We survey 35,554 GitHub-hosted Skill roots and identify 4,981 containing
source files under scripts/ or script/ . We select packages
that permit redistribution and whose behavior can be checked using repository
tests or task-specific executable tests. We record the source repository and
commit for each selected package.

We construct 150 repair tasks from 100 packages by introducing script faults
based on fault patterns identified in our GitHub survey. Each task pairs the faulty package with a
maintenance request describing the expected behavior or a failure symptom.
Executable checks distinguish the faulty version from a correct reference
implementation. Tasks from the same package target different maintenance requirements.

This track tests whether methods repair faulty documentation and scripts while
preserving correct ones. For each of 50 repository-derived packages, we keep
the maintenance request fixed and construct four states: Clean without faults,
Doc with documentation faults only, Script with script faults only, and Joint
with both.
The 200 tasks support within-package comparisons.

We check package integrity and alignment between maintenance requests and
tested behavior. Reference packages must pass the task-specific checks, while
faulty versions must fail checks for the injected faults ( Jia and Harman, 2011 ) .
For Controlled Repair, we verify that Doc and Script retain the unaffected
artifact and that Joint combines their faults under the same request.

2.4 Evaluation framework

We evaluate functional correctness and documentation–script consistency.
Behavioral tests check the requested
functionality and preservation of correct behavior, while documentation-driven
tests execute task-relevant invocations and workflows from SKILL.md against the revised scripts. Success requires passing all applicable tests
in both categories.

Behavioral tests check task-specific outputs, side effects, and argument
propagation. Documentation-driven tests use controlled inputs and simulate
external services where needed. For Clean and Doc-fault tasks, preservation
checks verify that the revised scripts retain the package’s existing correct
functionality. All methods are evaluated against the same task-specific
criteria. Appendix A.2 details the execution protocols
and evaluator calibration.

3 AST-Guided Skill Revision

AST-Guided Skill Revision coordinates Markdown–script repair by linking
maintenance requirements to executable structure. We assess documentation and
implementation separately against the same request, identifying discrepancies
to repair and correct behavior to preserve. Given an initial revision S ~ = M ⁡ ( q , S ) \widetilde{S}=M(q,S) from a base method M M , we analyze the original package S S and S ~ \widetilde{S} to derive repair targets and preservation constraints.
These guide subsequent script edits, after which we align documented usage
with q q and the revised implementation to produce the final package S ′ S^{\prime} (Figure 3 ).

Figure 3: AST-Guided Skill Revision on a dry-run example.
Numbered issues (1–3) map through revision feedback ℛ \mathcal{R} to
corresponding script edits, enabling preview generation and conflict checking
without renaming files or writing reports in dry-run mode. The SKILL.md command is updated with --dry-run to match the repaired implementation.

3.1 Requirement–Structure Grounding

The LLM interprets the behavior required by q q and identifies related claims
in Markdown. It links these requirements and claims to their applicability
conditions, supporting passages, and relevant implementation sites.
Language-native AST/CST analysis binds the proposed sites to uniquely matched
syntax nodes. Caller–helper relationships connect these nodes to related
implementation sites, providing context for requirements that span function
boundaries.

3.2 Repair Targets and Preservation Constraints

For each grounded requirement, the LLM assesses the implementation and
documentation separately under its applicability conditions. We map assessed implementation
discrepancies to resolved, editable syntax nodes, forming repair targets that
define the scope of subsequent script edits.
Behavior assessed as satisfying the requirement supplies
preservation constraints, including when the corresponding documentation
requires correction. Related callers and helpers provide supporting context
without necessarily becoming edit targets. We assess both S S and S ~ \widetilde{S} , retaining requirement-linked symbols and call context from S S when the initial revision removes them. Together, these assessments and
structural bindings form the revision feedback ℛ = G ⁡ ( q , S , S ~ ) \mathcal{R}=G(q,S,\widetilde{S}) supplied to the script editor.

3.3 Coordinated Markdown–Script Revision

The revision model uses the repair targets, caller–helper context, and
preservation constraints in ℛ \mathcal{R} to generate node-level script
replacements for each package version. Edits leave source text outside the
selected spans unchanged and are accepted only if the resulting scripts pass
syntax and applicable interface-preservation checks. Assembly uses S ~ \widetilde{S} as its base, retaining its validated edits and incorporating
compatible edits from S S through unique source matching.
The model then aligns documented invocations and operational instructions with
the maintenance request q q and the resulting scripts, correcting identified
inconsistencies through localized Markdown edits supported by script evidence.
Appendices A.3 and A.4 detail
the feedback representation, edit validation, and package assembly rules.

3.4 Integration with CoEvoSkills

We adapt CoEvoSkills ( Zhang et al., 2026b ) to maintenance-request-driven
revision of executable Skill packages. An independent surrogate verifier
assesses the package against the request and produces requirement-linked checks
and a diagnosis. A failure reported by the verifier or its executed checks
triggers the generator to revise SKILL.md and scripts using the
diagnosis and check results. To obtain CoEvoSkills + AST, we use the returned
package as the initial revision S ~ \widetilde{S} and apply AST-Guided Skill
Revision to ( q , S , S ~ ) (q,S,\widetilde{S}) .

4.2 Main Results

Full-package baselines achieve broader repair coverage, but documentation repair
remains a weakness. Averaged across four backbones, Raw Package and CoEvoSkills
achieve Overall Avg scores of 54.8% and 48.8%, respectively. Both baselines
repair script faults, joint faults, and In-the-Wild cases. However, their
documentation-repair Avg scores are
27.3% and 23.2%, respectively, compared with 27.0% for Markdown-only.

AST-guided revision improves repair success across all four backbones. Raw Package + AST and CoEvoSkills + AST achieve Overall Avg
scores of 76.7% and 76.5%, improving over their respective baselines by 21.9
and 27.7 pp. Their P@3 reaches 86.1% and 85.9%, while Hit 3 \mathrm{Hit}^{3} reaches 65.0% and 65.7%, respectively. All three metrics
improve for both generators on every backbone.

5 Analysis

We analyze package revision along two dimensions: the balance between fault
correction and behavior preservation, and the variation in revision gains
across task characteristics.

5.1 RQ1: What does AST-guided revision add beyond full-package access?

By linking Markdown requirements to script structure, its feedback provides

6 Related Work

SkillOpt and SkillAudit focus on revising skill documents, using bounded textual edits
and paired-trajectory feedback, respectively ( Yang et al., 2026 ; Gao et al., 2026 ) .
CoEvoSkills and SkillEvolver support broader package-level evolution, jointly constructing
and refining natural-language instructions and executable
code ( Zhang et al., 2026b ; Zhang et al., 2026a ) . However, downstream task success alone
does not separately assess documentation repair, script repair,
documentation–script consistency, and preservation of correct behavior.

SkillsBench and SWE-Skills-Bench evaluate the utility of supplied skills across diverse agent tasks
and repository-based software engineering, respectively ( Li et al., 2026 ; Han et al., 2026 ) .
SkillLearnBench evaluates continual skill generation through specification quality, execution
trajectories, and task outcomes, while SkillGenBench compares pipelines that distill repositories
and documents into reusable skills ( Zhong et al., 2026 ; Zhou et al., 2026 ) .
However, these benchmarks do not systematically evaluate the repair of existing Skill packages
comprising both Markdown instructions and executable scripts.

Structure-aware program repair uses program representations to guide code changes.
Astor applies AST-level transformations to Java programs, Getafix learns hierarchical fix patterns
from past edits, and TBar applies repair templates at localized fault
sites ( Martinez and Monperrus, 2016 ; Bader et al., 2019 ; Liu et al., 2019 ) . LLM-based approaches such as
Agentless organize repository repair into localization, patch generation, and
validation ( Xia et al., 2024 ) . Repository-level benchmarks such as
SWE-bench evaluate patches against real issue descriptions and executable
tests ( Jimenez et al., 2024 ) . Complementary work updates natural-language comments
to reflect changes in the associated code ( Panthaplackel et al., 2020 ) .
These settings do not explicitly address joint revision
of Markdown instructions and executable scripts to restore their consistency.

7 Conclusion

We introduced SkillScriptBench , a 350-task benchmark for self-evolution of executable
Agent Skill packages. It combines In-the-Wild Repair, built from a scan of over
35,000 public Skill roots, with Controlled Repair across matched clean,
documentation-fault, script-fault, and joint-fault states. Across four LLM backbones,
full-package baselines broaden repair coverage but do not consistently outperform
Markdown-only revision in documentation repair or clean-package preservation. We proposed
AST-Guided Skill Revision to coordinate Markdown and script revisions through
requirement-grounded structural feedback. Applied to Raw Package and CoEvoSkills,
it improves both repair and preservation while increasing mean all-three-run
success ( Hit 3 \mathrm{Hit}^{3} ) across all four artifact states.
Evaluation of executable Skill evolution should distinguish fault repair from
preservation of correct package behavior.

A.2 Evaluation details

For task t t , 𝒞 t \mathcal{C}_{t} contains the acceptance checks for required
behavior, documented use, and preservation of correct functionality.
All methods are evaluated with the same task-specific checks. A revised
package S ′ S^{\prime} succeeds when all checks pass:

Behavioral tests exercise target functions, script entry points,
caller–helper workflows, or repository test suites. Function-level tests
execute the selected source with its required dependency closure; entry-point
probes import the revised module or launch the revised script. Assertions
check task-relevant return values, emitted files, exit status, output streams,
or arguments passed to downstream calls. Controlled fixtures supply external CLI tools,
HTTP responses, hardware interfaces, and other dependencies as needed.

Task-specific evaluators extract commands and workflows from the revised SKILL.md and execute them with the revised scripts under predefined
test scenarios. Entry points and arguments come from the documented commands;
working directories and variable bindings come from the surrounding workflow.
Shell parsing preserves quoting and line continuations. Test inputs instantiate
documented placeholders, and controlled fixtures supply external dependencies.
Assertions check exit status, outputs, generated artifacts, and downstream
arguments against the task requirements.

Appendix A.8 details a VCP repair case, including
the executed command, test inputs, output assertions, and checks that
referenced package files are present and readable.

Coverage checks match task-relevant documented invocations to execution records.
Missing invocations, empty extraction results, and unresolved workflow context
are reviewed to identify package defects or evaluation errors. Evaluator and
environment errors are corrected before the unchanged package is re-evaluated.

For documentation-fault tasks, evaluators execute invocations from both the
revised and reference documentation against the revised scripts. The former
tests the revised usage instructions; the latter tests preservation of
existing behavior. Clean tasks require the revised package to retain both
its behavioral correctness and documented-use correctness.

The entry-point probe suite runs as an unprivileged user in a network-disabled
container with a read-only filesystem and a writable temporary directory.
The revised package and probe code are mounted read-only. The standard
container limit is one CPU, 512 MiB memory, and a 35-second outer timeout;
the browser fixture uses a separate image and a 1 GiB memory limit.
Other execution backends use task-specific subprocess or
language-runtime boundaries. Execution logs record the package
hash, command, exit status, outputs, and assertion outcomes.

Test inputs distinguish faulty behavior from the required behavior.
Caller–helper probes use distinct values at different argument positions
so that swapping or reusing an argument produces an observable failure.
For a CLI limit, probes cover an omitted option, zero, and nonzero explicit
values, checking the value in the outgoing API request.

A.3 Requirement feedback and structural binding

Requirement records connect requested behavior to source evidence,
implementation assessments, and editable locations in both S S and S ~ \widetilde{S} (Table 9 ).
The LLM reads q q , SKILL.md , and the supported scripts in S S and S ~ \widetilde{S} to extract behavioral requirements, applicability conditions,
and supporting passages. Request passages
support explicit requirements and inferences from reported problems;

For each source snapshot, the editor either abstains or returns exactly one

The edits derived from S S are incorporated only if every affected file

and interface-preservation checks. Otherwise, the assembly starting point is retained.

After script assembly, the LLM aligns SKILL.md with q q and the
assembled implementation, including when no script edits were made.

contradiction, cite an exact excerpt from the assembled scripts, and match

the cited invocation spans, including their explanatory paragraphs for inline
invocations, and must intersect every span cited by that edit.
Replacements must be non-empty and change the original content. Invalid

remaining edits are applied together if final syntax and path-scope checks

package entering alignment.

Final checks verify script syntax and restrict changed paths to SKILL.md and files under scripts/ . The resulting package is S ′ S^{\prime} ; the procedure ends after one pass of script revision and Markdown alignment.

Appendix D Limitations

The In-the-Wild track is predominantly Python, and both tracks use constructed
faults to evaluate package maintenance. Broader language coverage and tasks
derived from naturally occurring failures would help assess generalization
to the wider Skill ecosystem. Our evaluation measures package-level correctness
and documentation–script consistency; reliability in long-horizon downstream
Agent workflows remains to be evaluated.
