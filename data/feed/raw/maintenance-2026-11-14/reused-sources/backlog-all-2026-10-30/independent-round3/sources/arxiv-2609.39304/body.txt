Scale and Selection: What Makes Automatic Harness Evolution Work for Visual-Interface Robot Agents Zhijie Wei Ferris Tan Jinghui Wang Hao Zhou Abstract When an off-the-shelf coding agent is used directly as a robot policy, observing a browser-based 3D interface through screenshots and acting by posing a virtual target gripper through a few tools, the agent’s harness, its prompts, tools, and control rules, largely determines success, and until now it has been written by hand. We show that this harness can be improved automatically by another coding agent, the optimizer agent, and report two findings about what makes it work. First, the number of rollouts the optimizer agent sees per round governs whether the evolved harness generalizes: with rounds fixed, held-out success rises as the training batch grows from 5 to 100 rollouts, while small batches overfit the training tasks. Second, the optimizer agent must not be given free rein. Accepting every revision it proposes degrades the harness within a few rounds; a simple Champion–Challenger rule that promotes a revision only if it beats the incumbent on the same fixed cases turns the same loop into one that raises held-out success on LIBERO tasks from 51% to 67% over 30 rounds. The evolved harness is also a natural place to attach a pretrained policy, through one tool that hands it control. Writing the rollouts of that combination back into the policy, by fine-tuning domain experts on them and merging the experts into one policy with multi-teacher on-policy distillation, yields a standalone policy at 62.2% on RoboCasa365 under the official protocol, 4.8 points above the policy it started from with no harness at inference; the evolved harness on top of that distilled policy reaches 71.2% on the RoboCasa365 leaderboard benchmark, 13.1 points above the best published entry, and the loop closes when harness evolution resumes on top of the stronger policy. Automatic harness evolution for visual-interface robot agents is thus feasible, but its gains hinge on the rollout scale behind each decision and on how the optimizer agent’s revisions are selected. 1 1 footnotetext: NovaXBot 2 2 footnotetext: QuantGroup 1 1 footnotetext: Corresponding author. 1 Introduction Foundation-model coding agents such as Codex and Claude Code can now control robots without any robot-specific training [ 6 , 3 , 16 ] , and since the release of GPT-6 Astra, frontier models have been evaluated directly as robot policies across manipulation, dexterous hands, navigation, and humanoid control [ 5 ] . Hu et al. [6] present the robot as a visual interface , a browser-based 3D point-cloud GUI with a virtual target gripper and a few MCP tools, and let the agent operate it as a person would operate 3D design software, reaching 96.7% on three LIBERO-Goal tasks. We refer to such a system as a visual-interface robot agent : a coding agent that controls a robot by operating a visual interface. What the agent can do, however, depends heavily on its harness : the prompt, tool interface, observation format, control protocol, and verification rules that sit between model and robot [ 13 , 23 ] . In that system, a single textual waypoint demonstration in the prompt lifts one agent from 70% to 100% while leaving another unchanged [ 6 ] . This harness was written and tuned by hand. We show that it can instead be improved automatically by another coding agent. We call the agent that runs the robot the task agent and the agent that revises its harness the optimizer agent (Figure 1 ). Each round, the optimizer agent reads evidence from a batch of task-agent rollouts, proposes one bounded change to the harness, and the revised harness is evaluated again; the underlying models are never trained. Automatic harness optimization has been studied for software agents [ 13 , 23 ] , where a rollout takes seconds and is graded by a unit test. For a visual-interface robot agent, each rollout spans tens to over a hundred model turns, each consuming fresh screenshots of the interface, and yields a single noisy binary outcome. This changes what the loop needs in order to work, and the rest of this paper is about two such requirements. Whether a proposed revision is promoted depends on comparing two success counts on the training sample, and each count is a sum of noisy binary outcomes. With five rollouts per round, one flipped outcome moves the success rate by twenty points, so a revision can be promoted, and the next round built on it, purely by luck; the optimizer agent also sees too few failures to distinguish a systematic mechanism from an accident. Enlarging the batch raises the signal-to-noise ratio of every promotion decision and broadens the evidence the optimizer agent reasons from. Holding the number of rounds fixed at thirty and growing the training set from 5 to 10, 20, and 100 rollouts, held-out success rises from 47% to 67%. Small training sets do not merely help less: at ten rollouts the loop reaches 70% on the training set but only 54% held-out, having fitted the particular cases it saw. A trustworthy, generalizing, steadily improving harness therefore requires rollout scale behind each decision. The second requirement is that the optimizer agent must not be given free rein. The simplest loop accepts every revision it proposes, so the harness follows a single chain of commits. With expensive, noisy rollouts it fails: performance rises for a few rounds and then drifts downward, falling from 42% to 34% on the training set within ten rounds, because a revision that scored well on a lucky batch is kept and every later revision builds on it. The most basic safeguard repairs this: Champion–Challenger selection, in which a revision is promoted only if it strictly beats the incumbent harness on the same fixed evaluation set and is otherwise logged and discarded. With this rule and a training set of 100 rollouts, optimizing on tasks drawn from robosuite and LIBERO [ 15 ] and reporting on a disjoint held-out set of 100 rollouts from different tasks, thirty rounds raise held-out success from 51% to 67%. The evolved harness is also a natural place to attach a learned policy. Adding one tool that hands control to the Xiaomi-Robotics-1 vision-language-action policy [ 22 ] , with the agent deciding when to invoke it and when to take over, turns the harness into a data engine: its rollouts, written back into the policy as domain experts and merged by multi-teacher on-policy distillation, yield a standalone policy at 62.2% under the official RoboCasa365 protocol, 4.8 points above the policy alone with no harness at inference (Section 4.5 ). The evolved harness on top of that distilled policy reaches 71.2% on the RoboCasa365 leaderboard benchmark, 13.1 points above the best published entry and 13.8 points above the original policy alone (Section 4.6 ). Our contributions are: 1. The first scaling study of harness evolution for a visual-interface robot agent, showing that rollout scale is a necessary condition. An optimizer agent improves the hand-written harness with no training of either model, but only with enough rollouts behind each decision: with rounds fixed, held-out success rises as the training batch grows from 5 to 100 rollouts, reaching 67% against 51% for the baseline, while small batches overfit. 2. The finding that the optimizer agent must not be given free rein. We show that unconditional acceptance of its revisions degrades performance within a few rounds, and that Champion–Challenger selection, the most basic safeguard, turns the same loop into one that improves over 30 rounds. 3. A route from the evolved harness back into the policy. The rollouts produced by the evolved harness are written back into the policy as domain experts, and the experts are merged into one policy by multi-teacher on-policy distillation (MOPD). The resulting standalone policy reaches 62.2% under the official protocol, 4.8 points above the policy it started from, with no harness at inference, and closes a loop in which the stronger policy becomes the executor for the next round of harness evolution. 4. A new best result on the RoboCasa365 leaderboard benchmark. The evolved harness on top of the policy distilled from its own rollouts, through one tool that hands the policy control, reaches 71.2%, 13.1 points above the best published entry and 13.8 points above the original policy alone. 2 Related Work Foundation-model agents for robot control. Three routes turn foundation models into robot controllers. The dominant one fine-tunes a model into a vision-language-action (VLA) policy on robot trajectories [ 26 , 11 , 1 ] ; inference is fast, but the approach needs large robot datasets and yields models smaller and less general than the frontier models it starts from. A second route keeps the model frozen and has it compose perception and control primitives in code [ 14 ] , and CaP-X shows that coding-agent success depends strongly on the abstraction level of those primitives [ 4 ] . A third lets the model produce intermediate spatial targets, such as value maps or keypoint constraints, that a classical optimizer executes [ 8 , 9 , 7 ] . The visual-interface robot agent of Hu et al. [6] belongs to none of these: it exposes the robot as a visual interface and lets a general coding agent operate it through GUI tools with no robot-specific training. Harness VLA and ART likewise wrap or extend a VLA with agentic tool use [ 24 , 2 ] , and Guava maps the design space of such harnesses (agent workflow, action space, observation space) and distills the result into a 4B model [ 16 ] . Since GPT-6 Astra, frontier models have also been benchmarked directly as robot policies, from tabletop manipulation to dexterous hands, navigation, and humanoid control [ 5 ] . In all of these systems the harness around the task agent is designed by hand; it is the object we evolve. Automatic harness optimization. For a fixed model, the harness largely determines agent performance: harness changes alone shift held-out success by 10 to 15 points on tool-use benchmarks [ 25 ] , an automatically discovered harness can outrank hand-built agents on Terminal-Bench [ 13 ] , and the best harness is model-specific because different models fail in different ways [ 23 ] . This has motivated optimizer agents that revise a harness from execution feedback. Meta-Harness gives the optimizer access to the code, scores, and traces of prior candidates [ 13 ] ; Self-Harness lets the task agent mine its own failure clusters and propose minimal, regression-tested edits [ 23 ] ; RHI iterates on prompt-level agent loops with pairwise feedback [ 12 ] ; and PRISM searches over prompt and middleware edits under a budget [ 25 ] . Closest to us, RHO brings harness search to robotics: a coding agent proposes and searches, at training time, a multi-file repository of prompts, tools, and control code that the deployed agent then runs, raising held-out success on an LLM-in-the-loop benchmark from 23.5% to 44.3% [ 3 ] . These methods treat the number of rollouts behind each decision and the rule that accepts a revision as fixed parts of the procedure rather than as variables under study. Recent critiques show that reported gains from harness evolution often disappear under matched budgets and held-out tasks [ 20 ] , and that most claimed improvements on LIBERO are not statistically significant at the standard protocol [ 10 ] . We bring the optimizer-agent loop to a visual-interface robot agent whose rollouts are long and noisy, use a strict train/test split, and treat the rollout scale behind each decision and the rule that selects revisions as the variables under study. Agentic self-improvement in robotics. Coding agents have recently been used to improve robot systems autonomously. ASPIRE has an agent diagnose failures from execution traces, repair control programs, and accumulate a reusable skill library [ 17 ] ; ENPIRE automates the reset, train, roll out, and analyze loop for real-robot policy learning [ 21 ] . These systems evolve skill code or a training pipeline, and the agent that performs the task is not itself a GUI-operating foundation-model agent. We instead evolve the harness of such a task agent, and ask what rollout scale and what selection rule the loop needs to improve reliably. 3 Method 3.1 Setting We study harness evolution for the visual-interface robot agent of Hu et al. [6] . The task agent is an unmodified coding agent (Codex with GPT-5.6 Sol) that controls a simulated manipulator by taking screenshots of a browser-based 3D interface and calling a small set of MCP tools to pose a virtual target gripper, execute waypoints, and end the episode. Everything between the model and the robot constitutes the harness : the system prompt and operating guide, the MCP tool set and the semantics of each tool (for example the maximum translation per call), the observation returned after each tool call, the control rules for staging and executing waypoints, and the verification and termination logic. All of this is ordinary code and text in the agent’s repository and is the object of optimization. The task-agent model, the simulator, the task set, the success detectors, and the evaluation control plane are frozen and never edited. 3.2 The harness-evolution loop Algorithm 1 summarizes the loop and Figure 1 (b) illustrates one round. It controls how much information the optimizer agent receives each round: the trajectories it reads when diagnosing failures, and the outcomes on which each promotion is decided. Scaling laws in language modeling show that, with the model class held fixed, performance improves predictably as the amount of data seen during training grows. We ask whether an analogous regularity holds for harness evolution: with the optimizer agent, the task-agent model, the number of rounds, and the held-out set all held fixed, does the evolved harness improve as the number of rollouts per round grows? We therefore run otherwise identical campaigns with B ∈ { 5 , 10 , 20 , 100 } B\in\{5,10,20,100\} . Each campaign has its own optimizer session, branch, and result namespace, so campaigns share no information. Because every round evaluates B B rollouts of both the champion and the challenger, B B also sets the cost of a campaign; the question is therefore equally whether spending more rollouts per round buys a better harness. 3.4 Selection rule: unconditional acceptance versus Champion–Challenger The selection step admits two rules. Under unconditional acceptance , H t + 1 = H t ′ H_{t+1}=H^{\prime}_{t} always: every revision the optimizer agent proposes becomes the base for the next round, and the harness follows a single linear chain of commits. Under Champion–Challenger selection, the challenger is promoted if and only if s ⁡ ( H t ′ ) > s ⁡ ( H t ) , s(H^{\prime}_{t})>s(H_{t}), (1) that is, if it strictly beats the incumbent on the same cases. Ties and regressions are rejected; the rejected challenger and its evaluation are retained for audit, and the next round starts again from the unchanged champion. Section 4 compares the two rules at equal B B and shows that unconditional acceptance degrades within ten rounds while Champion–Challenger improves over thirty. 4 Experiments 4.1 Setup Tasks and splits. The training sample is drawn from ten tabletop manipulation tasks in robosuite and LIBERO [ 15 ] : lift, square, and stack from robosuite, and seven LIBERO tasks spanning the Object, Goal, Spatial, 90, and 10 suites. The held-out set is ten different LIBERO tasks from the Object, Spatial, Goal, and 90 suites; the two task sets are disjoint. Every task is instantiated with fixed seeds that determine the initial object placement, so a case (task, seed) is reproducible across rounds and across harness versions. The largest training batch uses ten seeds per task ( B = 100 B=100 ); the held-out set always uses ten seeds per task (100 rollouts). Success is decided by each task’s built-in detector. Section 4.4 additionally uses RoboCasa [ 19 ] , a kitchen benchmark with articulated appliances and a mobile manipulator: ten kitchen tasks for harness evolution, run under our own protocol (ten seeds per task, a one-hour wall-clock limit per rollout; stated in full in Section 4.4 ), and the 50-task RoboCasa365 leaderboard benchmark [ 18 ] , run under the official protocol, for distilling the harness’s rollouts back into a standalone policy (Section 4.5 ) and for combining the evolved harness with the distilled policy (Section 4.6 ). Agents and protocol. The task agent is Codex with GPT-5.6 Sol at the highest reasoning effort, run through MCP tools with a 30-minute wall-clock limit per rollout; its model and settings are identical for every harness and every evaluation. The optimizer agent is the same model in a separate persistent session; each campaign has its own session, branch, and result namespace. Rollouts of one evaluation run concurrently in isolated sandboxes, so a B = 100 B=100 evaluation takes about one wall-clock episode. All main campaigns run T = 30 T=30 rounds. To isolate the selection rule we compare, at each batch size, a campaign that accepts every revision unconditionally with the Champion–Challenger campaign of Section 4.2 . The unconditional campaigns use the same optimizer agent, task agent, evidence manifest, and fixed training samples; the only difference is that the challenger always becomes the next base. Figure 3 shows the training trajectories. Unconditional acceptance drifts downward. Under unconditional acceptance, training success rises for a few rounds and then falls at every batch size. At B = 100 B=100 the harness goes from 42% to a peak of 47% at round 5 and then to 34% by round 8 and 38% at round 10. At B = 20 B=20 the harness falls from 40% to 15% within 20 rounds, at B = 10 B=10 from 30% to 10%, and at B = 5 B=5 from 40% to 0%. The mechanism is visible in the trajectories: a revision that scores well on one batch is kept, every later revision is built on top of it, and there is no way back when the next batch shows it was not an improvement. The harness simply accumulates every ill-judged edit. Champion–Challenger turns the same loop into a monotone one. With the selection rule, the champion’s training score is non-decreasing by construction, and the question is whether it keeps rising rather than stalling. At B = 100 B=100 it does: from 41% at the start to 60% at round 29, with promotions spread across the 30 rounds. The rejected challengers, plotted as crosses, show what the rule is filtering out: 22 of 30 challengers at B = 100 B=100 scored at or below the champion, and many scored well below it, so most of what the optimizer agent proposes would have been a regression. On the held-out set the final champion reaches 67% against the baseline’s 51%, so the gains the rule admitted on the training sample are real improvements rather than fits to the fixed cases. The ten tasks are a small subset of RoboCasa’s kitchen tasks chosen for harness evolution, not the leaderboard’s task set. Each task is run with ten seeds of our own under the simulator’s default scene and object sampling rather than the benchmark’s pretraining split, and a rollout counts as a success only if the task’s built-in detector fires within a wall-clock limit of one hour and a cap of 4,500 simulator steps, the same cap for every task. The wall-clock limit is the binding constraint for an agentic rollout, in which every model turn takes seconds to minutes, so a harness that reaches the goal only slowly is scored as a failure. The leaderboard protocol instead fixes the object split, the seeds, and a per-task simulator-step horizon with no wall-clock limit; it is used only in Sections 4.5 and 4.6 . Starting from the round-2 champion, we added one MCP tool, vla_run , that hands control to the Xiaomi-Robotics-1 vision-language-action policy [ 22 ] for a bounded number of simulator steps and returns a screenshot and the resulting gripper pose; the task agent (GPT-6 Astra) issues the instruction, judges the outcome from the screenshot, and either re-invokes the policy with a revised instruction or takes over with the original waypoint tools. Every rollout of this system is a trajectory in the policy’s own action space, with the harness’s decomposition, object choices, and take-overs written into the actions and labelled by the simulator’s success detector. The procedure has three stages, all in simulation and none using additional human demonstrations (Figure 5 ). (i) Collect. The evolved harness drives the policy on a large batch of rollouts, exactly as in the evolution loop, and the full trajectories are recorded together with their verdicts. (ii) Domain experts. The rollouts are grouped by task family, and for each family a copy of the policy is fine-tuned on that family’s successful trajectories mixed with the policy’s original pretraining demonstrations. Each expert is specialized to its family and is not meant to be deployed on its own. (iii) Multi-teacher on-policy distillation. A single student π θ \pi_{\theta} , initialized from the original policy, is trained on its own rollouts. Each rollout is assigned the expert ϕ k ⁡ ( o ) \phi_{k(o)} of its task family, and the student’s flow-matching head is regressed onto the expert’s velocity field evaluated at the student’s own noisy-action samples under the expert’s conditioning, ℒ MOPD = 𝔼 o , a ∼ π θ , t , ϵ ​ [ ‖ v θ ​ ( x t , t ∣ o ) − v ϕ k ⁡ ( o ) ​ ( x t , t ∣ o ) ‖ 2 ] , x t = ( 1 − t ) ​ ϵ + t ​ a , \mathcal{L}_{\mathrm{MOPD}}=\mathbb{E}_{o,\;a\sim\pi_{\theta},\;t,\;\epsilon}\Big[\big\|v_{\theta}(x_{t},t\mid o)-v_{\phi_{k(o)}}(x_{t},t\mid o)\big\|^{2}\Big],\qquad x_{t}=(1-t)\,\epsilon+t\,a, (2) where o o is the observation, a a the action chunk the student executed, ϵ \epsilon Gaussian noise, and t t the flow time. Because the targets are evaluated at the student’s own samples, the objective is mode-seeking, the analogue of the reverse-KL objective used for on-policy distillation of language models, and the student’s rollouts are used whether or not they succeed: failed rollouts are exactly the states on which the expert’s correction matters. Human pretraining demonstrations are kept as a replay group with the standard flow-matching target. The experts are needed only during training; the student keeps the policy’s original architecture and inference code. The distillation stage itself is short, 800 optimizer steps at an effective batch size of 256. A stronger standalone policy. On the RoboCasa365 leaderboard benchmark (Table 5 ) the combination reaches 71.2% overall, 13.1 points above the best published entry, Paimon-0 (58.1%), 13.8 points above the original policy alone (57.4%), and 9.0 points above the distilled policy alone (62.2%). Relative to the original policy the gains are nearly uniform, 13.5 to 14.1 points on each split, but Table 5 shows that they arrive in two different ways. On the composite-unseen split the distilled policy alone already reaches 45.3%, and the harness on top of it adds only 0.3 points: the object choices, task decomposition, and repositioning that the agent supplied on unseen tasks have been written into the weights. On the two seen splits the distilled policy is within a point of the original, and the harness adds 13.0 and 13.2 points at test time; on these splits the policy does almost all the work, with 95% of successful episodes finishing without the agent touching a waypoint tool, and the harness’s contribution is monitoring the policy, re-issuing instructions, and taking over when it stalls. The combination above is already the first turn of a loop: the harness’s rollouts produced a stronger policy, and that policy now sits behind vla_run as the executor. The loop closes when harness evolution resumes on top of π 1 \pi_{1} and the new rollouts are written back again. Section 4.4 showed that the evolved harness is not tied to the model it was evolved with, so a stronger executor raises the whole combination, which in turn produces better rollouts, better experts, and a better distilled policy. We have run one such cycle; the pipeline is built so that the cycle repeats, with the harness and the policy improving each other, and the cost of each cycle is simulation rollouts and one short distillation stage. 5 Conclusion Automatic harness evolution for a visual-interface robot agent needs enough rollouts behind each decision, which lift held-out success from 47% at B = 5 B=5 to 67% at B = 100 B=100 , and Champion–Challenger selection, without which the loop degrades. Writing the harness’s rollouts back into the policy gives a standalone policy at 62.2% on RoboCasa365, and the harness on top of it reaches 71.2%, 13.1 points above the best published entry, closing the loop.
