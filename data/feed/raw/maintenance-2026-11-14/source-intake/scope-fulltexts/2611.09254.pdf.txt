TwinHash: Two-Sided Object Identity Management
for Time- and Energy-Efficient Agentic Workflows
Sangbu Yun1, Jung Gyu Min2, Jin Hyun2, Jeonghwan Ahn1, and Youngjoo Lee1
1KAIST, 2POSTECH
{boo, jhahn09, youngjoo}@kaist.ac.kr, {minjg.epiclab, jinhyun.epiclab}@gmail.com
Abstract—Agentic artificial intelligence (AI) services interleave
large language model (LLM) generation with external tool
execution, and increasingly rely on search-based workflows that
repeatedly revisit shared reasoning states and computations.
These patterns create substantial redundancy across tool outputs,
LLM responses, and key-value (KV) prefixes, yet existing serving
systems primarily optimize shared prompt prefixes, while naive
input-keyed caching is unsafe when identical requests produce
different outputs. We present TwinHash, a unified object man-
agement architecture that assigns each object an input-side hash
key to recognize repeated requests and an output-side content
fingerprint to validate and locate stored state, complemented by
type-specific reuse guards that preserve correctness and response
diversity. A software object identity table maintains reusable
objects across requests and trajectories, while a hardware ob-
ject placement table tracks their residency across hierarchical
memory tiers so that evicted state can be retrieved rather than
recomputed. Across seven agent frameworks and five benchmark
suites, reuse follows workflow structure more than benchmark
identity. TwinHash serves up to 81% of tool outputs wherever
deterministic tool reads recur, and up to 92% of LLM responses
in search-based frameworks. Retrieving an evicted KV-prefix
from DRAM reduces TTFT by up to 5.6× on Qwen3-32B,
with greater gains projected for larger dense models. Under
search-based frameworks, TwinHash reduces end-to-end wall-
clock time by up to 87% and measured task energy by up to
81% over a prefix-cached baseline, while a per-key serving cap
controls the quality-reuse trade-off in adaptive search. These
results demonstrate that unified identity, safety, and placement
management can convert structural redundancy in emerging
agentic workflows into substantial serving-efficiency gains.
I. INTRODUCTION
Nowadays, large language models (LLMs) have emerged
as core building blocks for coding, question answering, and
knowledge-intensive tasks [6], [42]. Techniques like chain-of-
thought (CoT) and tree-structured prompting elevate single-
step generation into multi-step reasoning traces [54], [60].
Furthermore, agentic workflows introduce tool use with an
outer action loop where the model issues API calls, executes
code, or queries a retriever, conditioning its subsequent steps
on the resulting observations [48], [50], [61]. Multi-agent
systems further scale these loops by distributing them across
role-specialized collaborators [19], [30], [44], [55]. Through
the progression of agentic workflows, the execution graph of
a request is increasingly built at runtime rather than fixed
in advance. Consequently, benchmarks such as AgentBench,
SWE-bench, and 𝜏-bench evaluate agents on long-horizon
tasks requiring multiple rounds of tool feedback rather than
isolated, single-turn prompts [23], [32], [56], [59].
The transition into tool-augmented service offloads com-
putational burden from the model itself onto external tools.
Recent agent frameworks consequently spend a large fraction
of their end-to-end wall-clock time waiting on tool execution
rather than on model inference [25], [50], [61], [65]. Modern
frameworks exacerbate this overhead by adaptively widening
inference-time tree searches [22] or searching over entire
workflow programs [63], thereby increasing the algorithmic
fan-out that multiplies both tool execution and LLM decoding
costs. Consequently, dynamic and tool-augmented reasoning in
agentic workflows substantially inflates energy and infrastruc-
ture demands compared to conventional LLM services [24].
The shift toward dynamic workflows presents a fundamental
serving problem beyond mere application-level concerns. Con-
ventional serving schedulers treat tool calls as opaque external
waits, causing tool latency to block the critical path while GPU
resources idle [5], [31], [36], [51]. Along with LLM inference,
which dominates the footprint of deployed agent services [24],
[25], [61], growing tool-layer workloads further complicate
cost optimization, including latency and energy.
Modern agentic workflows rarely resolve tasks via single-
shot trajectories. Instead, advanced frameworks rely on iter-
ative trials, result verification, and alternative approach ex-
ploration [22], [25], [56], [59], [63], [65]. Meanwhile, agents
frequently invoke identical tools and LLM decode requests
using identical arguments. The duplicated executions emerge
across retries, parallel search branches, and distinct tasks
sharing identical state. Empirical analysis shows that 31-95%
of tool outputs constitute byte-exact duplicates, and 48-94% of
submitted LLM prompts match previous requests across var-
ious agentic frameworks [22], [59], [63], [65]. The observed
redundancy manifests across three distinct computational ar-
tifacts, including tool invocations, LLM decode requests, and
LLM prefill operations. Re-executing the redundant operations
incurs severe systemic overhead, wasting CPU and GPU
resources, network bandwidth, and external API budgets.
Standard caching mechanisms represent the most basic
approach to exploit computational redundancy. However, con-
ventional input-keyed caches fail in agentic workflows for
two critical reasons. First, identical queries submitted to exter-
nal tools frequently produce divergent outputs. For instance,
database lookups yield strictly deterministic byte sequences,
whereas 31-100% of repeated retrieval-augmented queries
return different results. Second, massive KV tensor volumes
rapidly force cache evictions from hot-tier HBM. The eviction

Our core insight is an architecture that assigns every object
a two-sided hash identity. The input-side key functions as
a deterministic execution signature, which exclusively drives
the elimination of redundant computations. The key genera-
tion applies uniformly across objects, including tool outputs,
model responses, and KV-segments. The output-side content
fingerprint functions as a physical address key and data
integrity validator, derived from an output byte sequence.
The underlying system indexes physical addresses using the
content fingerprint, preventing physical replication. Moreover,
the fingerprint encourages memory pressure to demote objects
to lower-tier memory instead of outright deletion. Conversely,
the fingerprint verifies the integrity of objects promoted to
upper-tier memory, so corrupt or misplaced bytes are not
served. Further validity rules prevent stale reuse.
To this end, we present TwinHash, a unified hash-based ob-
ject cache designed for dynamic agentic workflows. TwinHash
registers every materialized tool and LLM output in an identity
table keyed by an input-side hash, validates candidate hits
via an output-side fingerprint, and tracks object residency
across the memory hierarchy to fetch rather than recompute
evicted data. Consequently, the system jointly recovers tool-
worker CPU cycles, network bandwidth, API budgets, and
GPU compute time. Workflow structure governs the savings,
as recurring deterministic tool reads benefit any framework,
whereas response reuse requires search-based execution.
This paper makes the following primary contributions:
• A characterization of reusability in agentic workflows.
We show that potential reuse heavily depends on agent
frameworks instead of their tasks (benchmarks). Tool out-
put reuse follows tool-request recurrence and is bounded
by tool determinism, whereas LLM response repetition is
confined to search-based policies with hit rates of 14-92%
while single-trajectory policies reach near zero.
• A safe, content-derived identity mechanism. We intro-
duce a two-sided hash architecture TwinHash that cap-
tures structural redundancies including cross-task over-
laps invisible to prefix- or session-scoped caches. The
reuse guards prevent cache poisoning and thus misuse of
cached objects. The validity model adds tool versions,
per-resource state epochs, and sampled audits. In replays
with database and file drift, the model serves no stale
object when change signals precede dependent reads.
• Unified resource savings and robustness under mem-
ory pressure. We demonstrate substantial resource sav-
ings in tool outputs, LLM responses, and KV-prefixes
using a unified caching abstraction. The proposed method
successfully maintains the reuse hit rate under severe
memory pressure thanks to its separated identity tables.
In live paired deployments of search-based frameworks,
TwinHash reduces end-to-end serving latency by up to
87% and measured task energy by up to 81%.
II. BACKGROUND
A. LLM Serving and Agentic Workflows
LLM inference proceeds in two phases. The prefill phase
processes input tokens in parallel and materializes their key
and value projections in a KV cache, whereas the decode phase
autoregressively generates output tokens using the populated
cache [53]. To maximize throughput, serving systems rely on
continuous batching and fine-grained KV-cache management,
as in vLLM’s PagedAttention [27]. For agentic workloads,
this design depends on maintaining a sufficiently large pool
of ready-to-run model requests. External tool invocations
suspend individual trajectories and shrink this pool; when the
remaining request concurrency is insufficient, batch occupancy
decreases and GPU resources become underutilized [24].
Fig. 1 illustrates the architectural evolution that gives rise to
this utilization challenge. Standard LLM deployments expose
a simple request-in, text-out interface [6], [42] ( 1 ), while rea-
soning techniques extend each request with a longer internal
derivation that trades additional decode compute for improved
accuracy [54], [60] ( 2 ). Agentic frameworks then place this
generation process inside an outer control loop that inter-
leaves model reasoning with external actions [48], [50], [61].
Single-trajectory frameworks follow one evolving execution
path or commit to a statically planned graph, as in ReAct’s
reason-act loop and LLMCompiler’s plan-once execution [25],
[61] ( 3 ). Search-based frameworks instead explore multiple
candidate continuations from shared intermediate states, span-
ning LATS’s tree search, AB-MCTS’s adaptive branching,
and AFlow’s workflow-level optimization [22], [63], [65] ( 4 ).
Role-specialized multi-agent organization [19], [30], [44], [55]
is orthogonal to this execution-structure axis, as either family
can distribute its graph across collaborating agents.
Transitioning from a naive single-LLM policy to a richer
agentic workflow can substantially improve task quality, as
demonstrated in Fig. 2. These quality gains, however, come
with increased structural complexity and thus higher service
costs. For instance, multi-step retrieval-and-verification work-
flows improve answer F1 scores on multi-hop QA benchmarks
from 0.12 to 0.48 on HotpotQA, from 0.14 to 0.38 on
MuSiQue, and from 0.19 to 0.49 on 2WikiMultiHopQA [18],
[52], [57]. Dynamic workflows further determine portions of
their execution graph mostly at runtime, introducing irreg-
ular model and tool invocations that are difficult to batch
efficiently [24]. The two architectural families expose redun-
dancy in structurally different forms. Within a single-trajectory
framework ( 3 ), successive model invocations typically append
new observations to a largely shared context, producing sub-
stantial KV-prefix overlap even when their complete prompts
differ. Such trajectories may also revisit deterministic tool
state as reasoning and verification proceed. A search-based
framework ( 4 ) additionally branches from common interme-
diate states, causing multiple candidates to reuse long context
prefixes and repeat identical or equivalent model and tool
requests [4], [35], [65]. As inference-time scaling matures,

B. Existing Serving Optimizations
Recently, extensive research has focused on optimizing the
LLM-side components of agentic workloads as in Table I.
Prefix caches [27], [64] and KV-offload [33], [45] stacks reuse
or relocate prefill state keyed by token position, and workflow-
aware methods [31], [43] extend the same state by prefetching,
overlapping, or scheduling it along predicted execution paths.
Semantic caches instead key on embedding similarity to serve
a broader range of requests [3]. Cache-augmented generation
(CAG) [7] exploits predefined knowledge sources to persist
state across queries. Prior work, however, is mostly limited
to optimizing the prefill phase of LLM services and agentic
workflows. GPTCache [3] reuses whole LLM responses for
similar requests, yet it prioritizes similarity over exactness and
cannot optimize internal flows of agentic services. Hence, tool
invocations and LLM decode responses were not considered
as sources of reusable content while preserving accuracy.

These observations set three requirements for TwinHash.
1) Unified caching mechanism for heterogeneous and non-

two independent features simultaneously: a unified input-side
caching key for heterogeneous objects from either tool or
LLM, and reuse safety determined by invocation nature.
2) Management for physical address with its identity. An
object’s residency and physical location metadata must remain
coupled with its identity, so that the runtime fetches known
objects from lower memory tiers rather than recomputing them
once the hot tier reaches capacity.
3) Reuse policy depends on frameworks rather than tasks.
The agent framework dictates reuse potential far more than the
dataset, as re-issues mostly expose tool and response reuse.
Re-issues that seek diversity from non-determinism should be
protected to preserve the framework’s service quality.
IV. TWINHASH ARCHITECTURE DESIGN
TwinHash introduces a unified object-management layer at
the execution boundaries where an agent’s workflow generates
reusable objects. These boundaries include the external tool in-
terface, the model response for structurally repeated prompts,
and the KV-segment interface. Every eligible request follows

the same path regardless of type: the runtime canonicalizes
the request into a descriptor, digests it into a lookup key,
probes a central object directory, and either serves a validated

A descriptor is the set of structured fields that determine an
object’s content, listed for each object type in §IV-A.
Fig. 8 illustrates the TwinHash unified execution path, which
separates object management into two caching data structures.
The software-level object identity table (OIT) tracks the ex-
istence of requested objects using hash-generated keys and
content fingerprints, while the hardware-level object placement
table (OPT) records the physical location of each object across
the memory hierarchy. Since both OIT and OPT are separated
from the object bytes, the system identifies objects’ existence
and residency even after demotion to a lower memory tier.
A. Two-Sided Hash Identity and OIT
The input-side identity mechanism constructs lookup keys
from semantic meaning rather than framework-specific syn-
tax, capturing cross-agent redundancies across heterogeneous
reusable objects. The descriptor fields adapt to each underlying
object type ( 1 ). For a tool invocation, the descriptor comprises
task scope, tool name and version, regularized tool input, and
the state epochs of the resources that the call reads, as detailed
in §IV-B. The regularization removes transient runtime fields
so that semantically identical calls produce identical keys. For
an LLM response, the descriptor incorporates model identifier,
prompt messages, and sampling parameters. Note that the
random seed and the request identifier are excluded to prevent
fresh seeds from obscuring the structural repetitions of search-
based policies. Sampled diversity is instead managed during
the serving phase, as described in §IV-D. For a KV-segment,
the descriptor captures model configuration, exact token IDs,
and absolute position range. Hence, the KV key remains
position-bounded unlike tool and response keys.
The runtime hashes each descriptor using 128-bit BLAKE2b
and probes a native matching directory ( 2 ). The proposed
OIT is designed as a growable hash table in host DRAM
and thus has no set conflicts ( 3 ). Per-task identities expire
at task end, and shared identities are bounded at 3 MB (64K
entries) under LRU, as in SGLang, vLLM, and LMCache [27],
[33], [64]. Hence, an eviction only forgoes a later reuse. Fig. 9
shows the total number of OIT entries under various workload
evaluations, which require at most 1.4K entries.
The output-side identity mechanism manages reuse of the
stored object by fingerprint. When a tool or model is invoked
for the first time, the OIT lookup misses, so TwinHash finger-
prints the output with 128-bit BLAKE2b ( 4 ) and commits the
key and fingerprint to the OIT. On a hit, TwinHash retrieves
the object’s physical address and metadata from the OPT ( 5 ).
The fingerprint verifies the retrieved object is valid, as external
programs might have mutated the address. Keys producing an
identical fingerprint also collapse into a single copy.
B. Reuse Safety and Reuse-Guard
As analyzed in §III, the determinism spectrum for hetero-
geneous operators, including tools and LLMs, must be consid-
ered when classifying the redundancy. Hence, we introduce an
independent structural scoping method reuse-guard to manage
reuse safety throughout the agentic service ( 6 ).
1 Tool reuse safety. Tool reuse becomes unsafe for two dis-
tinct reasons: a tool might be inherently non-deterministic, and
even an output from a deterministic tool might become out-
dated or invalid as state changes. First, SafeTools is constructed
through fingerprint-based determinism profiling before active
reuse. The profiling pass initially admits candidate read-only
tools but executes every invocation natively. If an identical
input-side key produces nonunique fingerprints, the tool is
classified as nondeterministic and excluded from SafeTools.
Profiling runs once per tool version, which is part of the key.
Between versions, sampled audits re-execute 5% of the hits
of profiled tools off the critical path, and a single mismatch
excludes the tool until its next version. The audits thus detect
a wrong declaration within 20 wrong hits on average, without
added latency and with at most 4% more tool calls across the
evaluated cells. Inputs that a tool reads from its own state,
such as generated tests, are also included in the key.
Active serving then restricts reuse to the resulting allowlist,
while state epochs separately prevent reuse across mutations.
TwinHash maintains per-resource state epochs, one for each
resource a tool declares, such as a database record, a table, a
file, or a web page, not one per session. The key includes the
epochs of the resources a call reads. An epoch advances when
any session writes the resource or its source signals a change,
for example through a change log or a file notification. Any
change thus produces a new key as long as the signal precedes
dependent reads. A predicate read depends on its whole table,
and a tool that declares no resource depends on a global epoch
that every write advances. Unmodified resources remain at
epoch zero and are shared across tasks that start from the same
database or repository snapshot, whereas a modified resource
is private to the modifying task. A source without a change
signal, such as web search, is admitted to SafeTools without
profiling, as its reuse is confined to one task and judged by
task accuracy in §VI-E. The task scope identifies the snapshot
for shared resources and the task in all other cases.
2 Decode response reuse safety. Decode response reuse
should not rely on output comparison as probabilistic sampling
intentionally seeks structural divergence. Instead, TwinHash
establishes safety via an allowlist SafeResponses with three

C. Placement and Lifecycle
The OPT manages overall physical residency of keyed ob-
jects across presumed memory subsystems based on demote-
on-eviction and promote-on-hit policy, i.e., tiered-least recently
used (LRU). Like a page table, the OPT is the authoritative
map that the runtime’s movements consult and update, while
the tiering substrate beneath it performs the movements. Our
demotion-on-eviction policy follows a write-back discipline
of conventional systems, such as Linux demoting cold pages
toward CXL and PMEM nodes during reclaim, and SGLang’s
hierarchical cache offers the same write-back mode for KV
evicted from GPU HBM. It also departs from offloading
methods [33], [45] which copy KV into DRAM proactively at
creation and thus consume memory bandwidth for each object
by maintaining at least two duplicate KV-segment copies.
Conversely, the demotion prevents duplicates as one fingerprint
maps to one physical instance. Serving a lower-tier hit forces a
fetch since a KV-segment must reach the GPU to be consumed;
hence, the OPT hit migrates objects toward fast memory.
A hardware OPT is worthwhile for KV-segments, whereas
a software directory suffices for the much smaller tool outputs
and LLM responses. Since a framework must locate gigabytes
of KV-segments at specific physical tiers, a software-only
process can only observe virtual addresses and incur undesired
user-space duplicates. The kernel also migrates pages inde-
pendently, as in NUMA balancing and memory tiering [37],
so a kernel driver must follow every migration page by page
or pin a dedicated pool. Lookups by the CPU runtime itself
need no hardware, since a software table over a pinned pool
answers within 16-58 ns. Lookups by devices such as GPUs,
however, reach the software table only through the host CPU
and take 4.6 𝜇s with a dedicated host core polling at about
3 W, whereas the OPT answers within 2.25 ns while dissipating
3.83-56.4 mW. Moreover, memory pressure from the KV-
segments evicts cached tool outputs and LLM responses from
HBM, which leads to recompute fallbacks. Here, the table
helps sustain TwinHash’s hit rate within a session by fetching
and promoting the evicted objects from host memory. The
fingerprint thus couples each object identity in the OIT with
a single physical copy that the OPT locates in any tier.
As Fig. 8 shows, the OPT on the host is designed to serve all
tiers, and copy engines of every tier update the OPT without
the host CPU. A copy engine updates an entry only after its
copy completes, and the DRAM and CXL pools lie outside
OS page migration, so a resident entry refers to a complete
copy. A referenced entry is not evicted or demoted.

An OPT entry is in one of three residency states to prevent
data contamination. A resident object resides in a tier and
serves read requests via a direct memory fetch. A filling object
is new, with its bytes still arriving, and blocks concurrent
readers until completion. An identity-only object retains its
OIT presence but has lost its bytes to a bottom-tier eviction or
invalidation, so reads fall back to full re-execution of the tool
or LLM. The OPT maintains reference counts so that a writer
detaches a private copy before mutating a shared object.
D. Serving Integration
We aim to design the unified management scheme for all
eligible requests, including tools and LLMs, as in Algorithm 1.
The path contains one admission rule and three object-specific
decision points, while all other operations are type-agnostic.
The admission rule originates reuse-guard, which manages
reuse safety of each object as detailed in §IV-B.
The first object-specific decision is key construction in
§IV-A. As each key includes the state epochs of the resources
its call reads, a read issued after a write cannot retrieve
an object created before that write. The second decision
validates an entry at serving time. For tool reuse hits, retrieved
bytes must match the fingerprint recorded at insertion. For
response hits, the entry must be finalized and remain within
its serving session. Each response is served at most predefined
𝐾times, and an exceeding request performs a new decode and
replaces the cached response to obtain sample diversity. For
KV hits, the segment must match the model configuration and
absolute position, and promoted segments are verified with a
fingerprint upon arrival. The third decision determines whether
simultaneous requests allow coalescing. For allowlisted tools,
the primary request executes as the owner and concurrent
requests wait for its committed result. Nested tools, which
call other cached tools as in LATS on MATH, bypass the wait,
since waiting requests could otherwise occupy every worker
that the owner’s calls need. In contrast, as search-based frame-
works fan out identical prompts to obtain multiple samples,
coalescing is prohibited to achieve candidate diversity.
Note that TwinHash complements existing prefix caching
methods rather than replaces them. Under the validity condi-
tions of §IV-B, the reuse guards make serving a cached object
safe, and TwinHash does not mutate a shared prefix.
E. Implementation Costs and Overheads
The overhead of TwinHash can be classified as probe
latency (hashing and lookup), metadata storage (OIT), and
physical object storage (OPT). In our custom C++/CUDA
software kernel of TwinHash, a directory probe costs 24-32 𝜇s
per eligible call. As tool executions consume milliseconds to
seconds and LLM calls take seconds to minutes, the kernel
call overhead is orders of magnitude below the reuse target.
OIT memory footprints remain negligible because the di-
rectory tracks key-fingerprint hashes rather than raw content,
where each entry requires only tens of bytes for a 16-byte
key digest, a 16-byte content fingerprint, and access counters.
For the OPT, the prototype packs the 16-byte fingerprint, tier
tag, physical location, size, reference count, and version fields
into a 261-bit payload, roughly 33 bytes. A 2K-entry OPT
managing up to 80 GB of KV-segments therefore requires
only 67.5 KB of SRAM. The OPT prototype is 8-way set-
associative to mitigate the implementation costs, and a full
set demotes its zero-reference tree-PLRU victim. Implemented
in RTL and synthesized using 28-nm CMOS operating at
a 444 MHz clock, the prototype occupies 0.34 mm2 while
dissipating 3.83-56.4 mW at 0.8 V. As lookup and update
operate within a cycle, their latency is at most 2.25 ns. In RTL
simulation over 373,510 operations, including agent traces, the
synthesized table matches a reference model on every response
at one operation per cycle. The functional model of §V also
does not report a hit that the hardware table misses.

Across all experiments, we measure end-to-end savings
using paired runs that differ only in reuse routing. The vanilla
mode is each cell’s default setup, the baseline. The observe
mode performs all directory lookups to calibrate SafeTools
yet bypasses reuse, whereas the memoize mode serves verified
cache hits. The vanilla-memoize difference therefore yields
TwinHash’s overall savings, while the observe-memoize differ-
ence isolates the effect of reuse. SGLang enables its radix KV
cache identically in all modes, so standard prefix reuse cancels
out in the paired ratio, and the reported savings compound on a
state-of-the-art prefix-cached baseline. For decode-layer reuse,
measured the same way, a reverse proxy manages the response
cache by keying on the prompt and sampling controls, exclud-
ing the random seed and refusing to coalesce in-flight model
calls. On the tool side, we instrument the memoizer at AB-
MCTS’s search tools and AFlow’s deterministic scorers.
Measurement and metrics. We count reuse at two levels
for each object type. A duplicate in Fig. 5 is a tool output or
LLM request that repeats an earlier one, and a verified reuse
is a tool call whose request key and output fingerprint both
repeat. Tool hits match the descriptor key, then the output
fingerprint. LLM requests match the model, messages, and
sampling parameters except the seed, and KV-prefixes match
token IDs and absolute positions. Verified reuse in Fig. 6
denotes the fraction of reads whose content check confirms
byte-identical output with a previously materialized object. It
therefore captures the repeated reads that are demonstrably
safe to reuse and serves as an upper bound on the reuse
achievable by a live runtime. Response reuse, by contrast,
measures a substitution rate because sampled LLM responses
cannot be validated through byte-level content checks before
execution, so we audit it by comparing answer quality between
runs with and without substitution. The tool and LLM time
shares in Fig. 3 are computed by merging overlapping execu-
tion intervals. For tree-search policies executing tool and LLM
concurrently, we report the more conservative time share.
Figs. 3-6 use vanilla or observe runs, except the LLM-
prompt duplicates of AB-MCTS and AFlow in Fig. 5, counted
in the request logs of memoize runs. With TwinHash off,
whole prompts that repeat still form 81-91% of the prefix-
cached tokens of AB-MCTS. Fig. 10(a) takes verified reuse
from replayed calls (𝜏-bench, mini-SWE, and LATS on Hot-
potQA), observe runs (AB-MCTS and AFlow), and the cache
hits that memoize runs serve after the reuse guards in the other
cells. The 𝜏-bench cells replay GPT-4o and Claude-Sonnet
transcripts. Fig. 10(b) replays recorded LLM requests, and
Fig. 14(b)-(d) replays the response logs of memoize runs. With
TwinHash off, the radix cache serves 39-99% of the prompt
tokens, so the baseline already includes KV-prefix reuse.
To evaluate energy at different granularities, we measure
per-event energy using idle-corrected RAPL measurements
averaged over ten repetitions for each domain. The reported
measured task energy, the end-to-end energy consumed while
serving one task, combines tool-layer energy with GPU board
energy, computed by integrating board power above idle over
the corresponding interval of each paired run. We also charac-
terize energy and latency at the per-hit KV-reuse granularity.
KV-fetch speedup is the ratio of prefill latency to the memory-
fetch latency to retrieve the corresponding KV state for a single
reuse event. Unless otherwise specified, all experiments use
one request stream and report per-task latency and energy.

E. Reuse Guard Ablation and State Drift
Removing one reuse-guard rule at a time shows what each
rule prevents. Without output checks, an argument-only cache
serves wrong bytes on 251 of 10,330 hits. Without task
scopes, shell reads shared across SWE-bench repositories are
wrong on all 126 hits, and without state epochs, 22 of 103
reads repeated across a write differ. With all rules, the cache
serves no wrong hit. For responses, without the default limit
of §VI-A, 5 of 9 LATS runs stalled on a single key, and
coalescing sampled calls collapsed each 5-way fan-out into
one decode. Our prototype implements the validity rules at low
cost, as task-local scope changes only 4 of 1,695 HotpotQA
reuse decisions and 5% audits find no mismatch while re-
executing up to 4% of tool calls. Including audit energy would
lower the savings of Fig. 12(b) by at most 4 points.
Fig. 15 evaluates whether per-resource state epochs prevent
stale hits in three replays with state drift. With every change
signaled before dependent reads, the epochs serve no stale hit
and still hit 7-79% of reads. In 𝜏-bench, 100 airline and 230
retail sessions share one database per domain (21-24% of tool
calls write). The SQL of 4,495 DBBench tasks [32] queries
152 databases, each shared by eight interleaved sessions. An
external writer changes one row of a random table after each
statement with probability 0.5. In mini-SWE, 114 out-of-band
edits per run each insert a commented-out copy of a line that
is read later. The no tracking baseline sees only a session’s
own writes (𝜏-bench), writes through the cache (SQL), or the
agent’s own commands (mini-SWE), and up to 66% of its
database hits and 93% of its file hits are stale. Compared with
a per-session epoch, per-resource epochs preserve sharing after
a session’s first write (58% to 79% for product lookups), but
any change to a scanned record invalidates a table scan (55% to
28% for user-ID lookups). In Fig. 10(a), 𝜏-bench shares only
reads before a session’s first write, and per-resource epochs
would raise both rates to 83-88% without a stale hit.
Conversely, web results change without a signal. Over 65
days, 28.6% of queries returned different results, whereas 97%
of repeated searches within a task returned identical results.
LLMCompiler on HotpotQA, which reuses only web search,
still retains a task quality of 0.60 with and without reuse.

VII. DISCUSSION AND LIMITATIONS
LLM response reuse and sampling diversity. On the AB-
MCTS MATH benchmark, unbounded reuse of stored samples
under stochastic decoding lowers accuracy from 0.90 to 0.65.
As §VI-C shows, a tighter cap than 𝐾=2 sacrifices most of the
efficiency gain with little additional quality benefit, and each
fresh decode replaces the stored sample and restores sampling
diversity. This degradation is thus specific to stochastic decod-
ing, where repeated sampling contributes to exploration.
Time and energy crossovers for KV fetching. KV-segment
reuse exhibits different time and energy crossovers at the
NVMe tier. For Qwen3-8B, an NVMe-tier fetch is faster for
the 848-token prompt (1.31×), and recomputation is faster
beyond roughly 1.6K tokens, with recompute-to-fetch time
ratios of 0.95× at 1,645, 0.99× at 3,244, and 0.86× at 6,447
tokens. A cold prefill consumes 72.45 J, whereas a tier hit
consumes 1.04 J. Recomputation still draws 300-400 W of net
GPU board power against an estimated 10-15 W for an NVMe
fetch, so the fetch uses an order of magnitude less energy even
where recomputation is faster. The latency crossover thus lies
between the modeled CXL tier and NVMe, and the energy
crossover beyond NVMe. Increasing model size shifts the
latency crossover further in favor of fetching, as prefill cost
scales more rapidly with model size than KV transfer.
Benefits beyond search-based execution. Single-trajectory
agents repeat no response, yet tool reuse still saves up to 12.1%
of their time and 24.7% of their energy, and the saving grows
with tool requests that recur across tasks and users. Evicted
KV-prefix retrieval applies to every framework, as the single-
trajectory agents of §II-A also append to a shared context, and
the prefix cache serves 52-99% of their prompt tokens.
Scaling beyond a single node. A cluster can shard the OIT
by key hash, with each owner shard storing the in-flight state
of its keys. Each node’s OPT treats peer memory as a lower
tier, as in distributed KV pools [45]. In a trace-driven 𝜏-bench
simulation, task-affine routing over eight node-local directories
retains 96% of the reuse, and key sharding loses no reuse.
Limitations. Per-resource state epochs assume that change
signals precede dependent reads. Sources without a change
signal, such as web search, are reused only within a task. We
validate the OPT prototype through synthesis and trace-driven
simulation, while silicon or FPGA integration, physical CXL
memory, and multi-node deployment remain future work.
VIII. RELATED WORK
Agentic frameworks and inference-time scaling. CoT [54]
introduces intermediate reasoning steps, while ToT [60] and
GoT [4] organize them into tree- and graph-structured repre-
sentations. ReAct [61] interleaves reasoning with actions and
observations, LLMCompiler [25] generates dependency-aware
function-call plans, and multi-agent frameworks [19], [30],
[44], [55] coordinate role-specialized collaborators. Search-
based systems [2], [15], [21], [22], [62], [65] further explore
multiple reasoning or execution paths, repeatedly invoking
tools and models. TwinHash complements these frameworks
without modifying reasoning or search policies, instead re-
claiming repeated work exposed by their execution structures.
Agent-aware scheduling. Parrot [31] and Autellix [36]
schedule agent programs to reduce queueing delays and
context churn. KVFlow [43] prefetches predicted KV state,
FlashAgents [12] overlaps decoding with prefilling, and
PASTE [51] and TokenCake [5] mitigate tool-induced stalls
through speculation and wait-aware KV-cache management.
These techniques reduce latency or memory pressure through
scheduling, prefetching, speculation, and overlap, whereas
TwinHash avoids verified duplicate execution.
Model-side serving reuse. vLLM [27], SGLang [64],
Prompt Cache [13], and CAG [7] reuse compatible pre-
fixes and position-aware or preloaded model state, while
CacheBlend [58] extends KV reuse to retrieval-augmented
inputs [29]. Other systems move model parameters or KV
state across memory tiers, hosts, and storage [1], [20], [28],
[33], [34], [45], [49]. In contrast, TwinHash generalizes reuse
beyond model-native state to tool outputs, model responses,
and KV segments through a unified identity abstraction.
Content-addressed storage and build caches. Content-
addressed stores identify data by a hash of its bytes [41],
[46], [66], and copy-on-write file systems share blocks until
a write [47], as the OPT reference counts do. Build caches
key outputs by a hash of their inputs [10], [11], [16], [40], as
does memoization [39]. Input-keyed caches assume hermetic
producers, which agentic tools and sampled decoding are not.
TwinHash extends both hashes with versions, state epochs,
audits, and serving caps as rules for valid reuse.
IX. CONCLUSION
As agentic AI shifts from isolated model calls to dynam-
ically constructed workflows, serving efficiency increasingly
depends on eliminating repeated work rather than merely
accelerating each invocation. TwinHash addresses this op-
portunity through a unified object-management architecture
that spans tool outputs, LLM responses, and KV prefixes us-
ing input-side identities, output-side fingerprints, type-specific
reuse guards, and hierarchical placement metadata. Across
seven agent frameworks and five benchmark suites, we find
that reuse is governed primarily by workflow structure rather
than benchmark identity, with TwinHash serving up to 81%
of tool outputs and 92% of LLM responses. By independently
eliminating redundant work at the tool and GPU layers,
TwinHash converts these reuse opportunities into end-to-end
reductions of up to 87% in wall-clock time and 81% in mea-
sured task energy over a prefix-cached baseline. Extending the
same identity to object placement further preserves reusable
state under severe memory pressure, increasing the object
hit rate from 19.5% to 79.4% at 1% resident capacity. The
hardware OPT records object placement across all tiers with-
out the host CPU, within 2.25 ns at 3.83-56.4 mW. Therefore,
TwinHash unifies object management across heterogeneous
objects, establishing a cost-effective and scalable framework
for the emerging era of complex agentic workflows.
